# 智能问答网页方案

本文档是在当前 `P4_RAG项目案例` 基础上的下一步规划文档。目标不是继续讲 LangChain 基础，而是把项目收束成一个真正可以落地开发的方向。

当前决定如下：

- 先不做 RAG
- 先不做 Agent
- 先不做复杂工作流
- 先做一个“类似 ChatGPT / 豆包 / DeepSeek 网页端”的多模态智能问答网页
- 模型优先使用本地 `Ollama` 服务上的 `qwen3.5:27b-q8_0`

这个阶段的核心目标是：

> 把现在的教学 demo，升级成一个前后端分离、可持续迭代、具备产品形态的多模态智能问答系统。

---

## 1. 项目新定位

### 1.1 不再是“知识库问答 demo”

当前项目更像：

- 单机 Streamlit 示例
- 文本知识上传
- 简单 RAG 问答

这个形态适合学习，但不适合作为一个完整的网页产品。

### 1.2 新定位

建议把项目重新定义为：

**本地多模态智能问答工作台**

更具体一点，可以写成：

**基于本地 Ollama 的多模态智能问答 Web 应用**

它的核心价值不再是“知识库检索”，而是：

- 统一聊天入口
- 多轮上下文记忆
- 图片理解
- 文档临时分析
- 会话管理
- 可扩展到多模型 / 多 provider
- 可扩展到后续 RAG / Agent / 插件能力

这类项目在简历上的说法会更自然：

- 自研 ChatGPT 类网页端
- 支持本地模型接入
- 支持多模态输入
- 支持历史会话与持久化
- 支持前后端分离部署

可选名称：

- `LocalMind`
- `Ollama Chat Studio`
- `QwenDesk`
- `智答工作台`

为了先推进，文档里先用：

**Ollama 多模态智能问答工作台**

### 3.2 一句话描述

一个支持本地大模型、多轮上下文、图片理解、文件分析、历史会话与可扩展模型配置的前后端分离式 AI Web 应用。

## 6. 技术架构建议

这里不建议再用 Streamlit。

建议改成标准前后端分离。

### 6.1 总体架构

```text
Frontend (Next.js)
    |
    | HTTP / SSE
    v
Backend API (FastAPI)
    |
    | 调用
    v
Ollama Service

Backend API
    |
    | 读写
    v
PostgreSQL / SQLite

Backend API
    |
    | 文件存储
    v
Local Storage / MinIO(后续)
```

### 6.2 前端建议

建议使用：

- `Next.js`
- `TypeScript`
- `Tailwind CSS`
- `shadcn/ui`
- `assistant-ui` 或自定义聊天组件

为什么选这一套：

- AI 聊天前端生态成熟
- 模板多
- UI 组件成熟
- 适合流式聊天
- 便于后面扩展

### 6.3 后端建议

建议使用：

- `FastAPI`
- `SQLAlchemy`
- `Pydantic`
- `SSE` 或 WebSocket 做流式输出

为什么：

- 你当前项目本身就是 Python 方向
- LangChain / 文档解析 / 文件处理都更自然
- 接 Ollama 更直接

### 6.4 数据库建议

第一版建议：

- 开发期可先 SQLite
- 稳定后切 PostgreSQL

如果你希望简历上更规范，可以直接用 PostgreSQL。

建议最终还是：

- `PostgreSQL`

因为它更像正经 Web 项目。

### 6.5 文件存储建议

第一版可先：

- 本地磁盘目录

后续可替换成：

- MinIO
- 对象存储

文件类型主要包括：

- 聊天图片附件
- 文档附件
- 用户头像

## 10. 聊天流程怎么设计

这是最核心的后端主流程。

### 10.1 普通文本聊天

1. 前端发送用户消息
2. 后端查询该会话历史消息
3. 后端拼接为模型输入
4. 调用 Ollama 流式接口
5. 将流式 token 转发给前端
6. 回答完成后保存 AI 消息

### 10.2 图片聊天

1. 前端上传图片
2. 后端保存图片
3. 消息发送时附带图片引用
4. 后端读取图片并转换为 Ollama 所需格式
5. 文本 + 图片一起送给模型
6. 流式返回结果

### 10.3 文档聊天

第一版先做“当前会话临时文档上下文”。

1. 前端上传文档
2. 后端解析文本
3. 将解析出的文本截断或分段
4. 作为本轮消息上下文拼进输入
5. 模型回答后，不做索引入库

这和 RAG 区别很大：

- 这里是临时上下文拼接
- 不是长期知识库检索

## 11. 关于上下文记忆，第一版怎么做

你提到“上下文记忆”，这个是必做的。

第一版建议先做最经典的会话级记忆：

- 同一个 conversation 内，按消息时间顺序拼上下文

但不能无限拼接，要有策略：

### 建议策略

- 先保留最近 N 轮消息
- 或按 token 预算裁剪
- system prompt 始终保留
- 当前消息与附件始终保留

因为就算模型支持大上下文，也不能无脑把所有历史永远拼进去，否则：

- 成本高
- 响应慢
- 模型注意力分散

后续再考虑：

- 自动总结历史
- 长对话压缩摘要

## 12. 用户配置能力怎么规划

你提到以后可能希望支持前端配置 `URL` 和 `API Key`。

这个方向可以预留，但建议分期做。

### 第一版

- 固定后端配置的 Ollama 地址
- 固定默认模型
- 前端只允许选择少量参数

### 第二版

- 每个用户可配置 `ollama_base_url`
- 可配置 OpenAI-compatible `base_url`
- 可配置 `api_key`
- 可选择 provider 和模型

### 设计原则

前端上允许用户配置，不代表前端直接调用模型服务。

建议仍然走：

- 前端只存用户配置
- 后端读取配置并代为调用 provider

不要把敏感调用逻辑全放前端。

## 13. 是否需要登录

这个问题要单独说一下。

### 方案 A：第一版不做登录

优点：

- 开发快
- 更容易先把核心聊天体验跑通

缺点：

- 会话无法按用户隔离
- 简历上“完整系统感”差一点

### 方案 B：第一版就做登录

优点：

- 更像正式产品
- 会话和设置都能归属到用户

缺点：

- 开发工作量明显增加

### 我的建议

如果你想尽快做出第一个能用版本：

- **第一阶段可以先不做登录**

如果你想一开始就更完整：

- **第二阶段尽快补登录**

也就是说，登录不是必须最先做，但最好不要永远不做。

## 16. 这个项目后续为什么仍然能接回 RAG / Agent

虽然现在决定先不做 RAG / Agent，但这套架构不是浪费的。

因为后面完全可以在后端继续扩展：

### 后续接 RAG

在聊天流程里新增：

- 文档入库
- 检索服务
- `chat mode = normal / knowledge`

### 后续接 Agent

在后端新增：

- route 节点
- 工具调用
- LangGraph 状态流

也就是说：

- 第一版做聊天工作台
- 第二版做知识增强
- 第三版做 Agent 能力

这条演进路线是连贯的。

## 17. 这个版本作为简历项目，怎么讲

如果你把第一版做好，它已经可以这样表述：

### 项目名称

基于本地 Ollama 的多模态智能问答 Web 平台

### 项目描述

设计并实现一个前后端分离的 AI 聊天平台，对标 ChatGPT / DeepSeek 类网页端，支持多轮对话、会话持久化、图片理解、文档临时分析、流式生成和模型参数配置，后端统一接入本地 Ollama 大模型服务。

### 技术亮点

- 前后端分离：`Next.js + FastAPI`
- 支持流式聊天输出与会话持久化
- 支持多模态输入，覆盖文本、图片和文档附件
- 支持本地 Ollama 模型接入与后续多 provider 扩展
- 为后续 RAG / Agent 能力预留统一会话与模型调用层

这已经比“一个简单的 RAG demo”更像一个正经项目。

## 18. 当前最推荐的落地策略

基于以上分析，我建议当前路线定为：

### 产品路线

先做：

**多模态智能问答工作台**

不是：

- 先做知识库系统
- 也不是先做 Agent 平台

### 技术路线

先做：

- `Next.js` 前端
- `FastAPI` 后端
- `Ollama` 模型调用
- `PostgreSQL` 会话持久化

### 范围路线

先做：

- 文本聊天
- 会话历史
- 图片上传
- 文档上传
- 流式输出
- 设置页

后做：

- 登录
- provider 配置
- RAG
- Agent
