# 智能问答网页方案

本文档是在当前 `P4_RAG项目案例` 基础上的下一步规划文档。目标不是继续讲 LangChain 基础，而是把项目收束成一个真正可以落地开发的方向。

当前决定如下：

- 先不做 RAG
- 先不做 Agent
- 先不做复杂工作流
- 先做一个“类似 ChatGPT / 豆包 / DeepSeek 网页端”的多模态智能问答网页
- 模型优先使用本地 `Ollama` 服务上的 `qwen3.5:27b-q8_0`

这个阶段的核心目标是：

> 把现在的教学 demo，升级成一个前后端分离、可持续迭代、具备产品形态的多模态智能问答系统。

---

## 1. 项目新定位

### 1.1 不再是“知识库问答 demo”

当前项目更像：

- 单机 Streamlit 示例
- 文本知识上传
- 简单 RAG 问答

这个形态适合学习，但不适合作为一个完整的网页产品。

### 1.2 新定位

建议把项目重新定义为：

**本地多模态智能问答工作台**

更具体一点，可以写成：

**基于本地 Ollama 的多模态智能问答 Web 应用**

它的核心价值不再是“知识库检索”，而是：

- 统一聊天入口
- 多轮上下文记忆
- 图片理解
- 文档临时分析
- 会话管理
- 可扩展到多模型 / 多 provider
- 可扩展到后续 RAG / Agent / 插件能力

这类项目在简历上的说法会更自然：

- 自研 ChatGPT 类网页端
- 支持本地模型接入
- 支持多模态输入
- 支持历史会话与持久化
- 支持前后端分离部署

一个支持本地大模型、多轮上下文、图片理解、文件分析、历史会话与可扩展模型配置的前后端分离式 AI Web 应用。

## 6. 技术架构建议

这里不建议再用 Streamlit。

建议改成标准前后端分离。

### 6.1 总体架构

```text
Frontend (Next.js)
    |
    | HTTP / SSE
    v
Backend API (FastAPI)
    |
    | 调用
    v
Ollama Service

Backend API
    |
    | 读写
    v
PostgreSQL / SQLite

Backend API
    |
    | 文件存储
    v
Local Storage / MinIO(后续)
```

### 6.2 前端建议

建议使用：

- `Next.js`
- `TypeScript`
- `Tailwind CSS`
- `shadcn/ui`
- `assistant-ui` 或自定义聊天组件

为什么选这一套：

- AI 聊天前端生态成熟
- 模板多
- UI 组件成熟
- 适合流式聊天
- 便于后面扩展

### 6.3 后端建议

建议使用：

- `FastAPI`
- `SQLAlchemy`
- `Pydantic`
- `SSE` 或 WebSocket 做流式输出

为什么：

- 你当前项目本身就是 Python 方向
- LangChain / 文档解析 / 文件处理都更自然
- 接 Ollama 更直接

### 6.4 数据库建议

第一版建议：

- 开发期可先 SQLite
- 稳定后切 PostgreSQL

如果你希望简历上更规范，可以直接用 PostgreSQL。

建议最终还是：

- `PostgreSQL`

因为它更像正经 Web 项目。

### 6.5 文件存储建议

第一版可先：

- 本地磁盘目录

后续可替换成：

- MinIO
- 对象存储

文件类型主要包括：

- 聊天图片附件
- 文档附件
- 用户头像

## 10. 聊天流程怎么设计

这是最核心的后端主流程。

### 10.1 普通文本聊天

1. 前端发送用户消息
2. 后端查询该会话历史消息
3. 后端拼接为模型输入
4. 调用 Ollama 流式接口
5. 将流式 token 转发给前端
6. 回答完成后保存 AI 消息

### 10.2 图片聊天

1. 前端上传图片
2. 后端保存图片
3. 消息发送时附带图片引用
4. 后端读取图片并转换为 Ollama 所需格式
5. 文本 + 图片一起送给模型
6. 流式返回结果

### 10.3 文档聊天

第一版先做“当前会话临时文档上下文”。

1. 前端上传文档
2. 后端解析文本
3. 将解析出的文本截断或分段
4. 作为本轮消息上下文拼进输入
5. 模型回答后，不做索引入库

这和 RAG 区别很大：

- 这里是临时上下文拼接
- 不是长期知识库检索

## 11. 关于上下文记忆，第一版怎么做

你提到“上下文记忆”，这个是必做的。

第一版建议先做最经典的会话级记忆：

- 同一个 conversation 内，按消息时间顺序拼上下文

但不能无限拼接，要有策略：

### 建议策略

- 先保留最近 N 轮消息
- 或按 token 预算裁剪
- system prompt 始终保留
- 当前消息与附件始终保留

因为就算模型支持大上下文，也不能无脑把所有历史永远拼进去，否则：

- 成本高
- 响应慢
- 模型注意力分散

后续再考虑：

- 自动总结历史
- 长对话压缩摘要

## 12. 用户配置能力怎么规划

你提到以后可能希望支持前端配置 `URL` 和 `API Key`。

这个方向可以预留，但建议分期做。

### 第一版

- 固定后端配置的 Ollama 地址
- 固定默认模型
- 前端只允许选择少量参数

### 第二版

- 每个用户可配置 `ollama_base_url`
- 可配置 OpenAI-compatible `base_url`
- 可配置 `api_key`
- 可选择 provider 和模型

### 设计原则

前端上允许用户配置，不代表前端直接调用模型服务。

建议仍然走：

- 前端只存用户配置
- 后端读取配置并代为调用 provider

不要把敏感调用逻辑全放前端。

## 13. 是否需要登录

这个问题要单独说一下。

### 方案 A：第一版不做登录

优点：

- 开发快
- 更容易先把核心聊天体验跑通

缺点：

- 会话无法按用户隔离
- 简历上“完整系统感”差一点

### 方案 B：第一版就做登录

优点：

- 更像正式产品
- 会话和设置都能归属到用户

缺点：

- 开发工作量明显增加

### 我的建议

如果你想尽快做出第一个能用版本：

- **第一阶段可以先不做登录**

如果你想一开始就更完整：

- **第二阶段尽快补登录**

也就是说，登录不是必须最先做，但最好不要永远不做。

## 23. 2026-05-19 对标 Ragent 后的产品方向升级

2026-05-19 对 Ragent 官网与本地源码 `/disk2/gengnan/ragent` 做了初步阅读。Ragent 的定位是企业级 Agentic RAG 平台，不是普通聊天 Demo。它覆盖文档入库、知识库管理、多通道检索、意图识别、问题重写、模型路由容错、MCP 工具调用、RAG Trace 和管理后台。

我们当前项目不应该照搬 Ragent 的 Java / Spring Boot 技术栈，也不应该一次性复制完整企业级复杂度。但它的产品方向和工程分层非常适合指导 AI Web Studio 的下一阶段升级。

### 23.1 Ragent 给我们的核心启发

Ragent 值得借鉴的不是“用了哪些框架”，而是这些工程化能力：

1. 从聊天系统升级为知识系统
   普通聊天只管理会话，知识系统还要管理知识库、文档、分块、索引、检索、引用和反馈。

2. 从单轮附件升级为可复用知识入库
   当前 AI Web Studio 的附件主要服务于当前轮或当前会话。Ragent 的文档入库链路则把文件变成可检索、可复用、可追踪的知识资产。

3. 从单一检索升级为多路召回
   Ragent 的多通道检索把向量全局检索、意图定向检索、关键词检索和后处理链拆开。我们后续可以先做关键词 + 工作区文件 + 当前会话附件 + 长期记忆的轻量多路召回，再升级 embedding。

4. 从不可见黑盒升级为可观测链路
   RAG 系统的问题往往不是模型本身，而是“召回了什么、裁掉了什么、Prompt 怎么组装、哪个节点慢、哪个节点失败”。Ragent 的 Trace 设计说明可观测性必须成为核心能力。

5. 从 provider 切换升级为模型路由
   企业级系统不能只保存一个模型配置，而要知道模型能力、健康状态、失败次数、首 token 延迟和备用模型。

6. 从设置弹窗升级为管理后台
   知识库、文件、Prompt、模型、Trace、用户反馈这些能力不适合全部塞进聊天页，需要逐步演进出轻量管理面板。

### 23.2 AI Web Studio 的新目标

下一阶段，AI Web Studio 的产品定位建议升级为：

**面向个人与项目工作区的本地优先知识库型 AI 工作台。**

它应该解决的问题是：

- 用户可以把论文、课程资料、项目文档、实验记录、代码说明、图片和日常资料放入不同工作区。
- 系统自动解析、切分、索引这些资料。
- 用户提问时，系统能结合当前会话、长期记忆、工作区知识库和当前上传附件做上下文组装。
- 回答后能展示本轮使用了哪些记忆、摘要、附件片段和知识库片段。
- 用户能管理知识库文件、查看索引状态、查看 Trace、导出会话和复盘模型效果。

### 23.3 新阶段的产品分层

后续不建议再只按“聊天功能”拆需求，而应按以下产品层次推进：

1. Chat Layer
   继续保留当前聊天体验，包括多轮对话、模型切换、附件输入、Markdown、分享、导出、重生成和编辑重答。

2. Workspace Layer
   工作区成为项目级组织单位，承载会话、文件、知识库、Prompt 模板、默认模型、System Prompt、上下文策略和统计信息。

3. Knowledge Layer
   新增知识库、文档、分块、索引、召回、引用来源和文件版本管理。

4. Context Governance Layer
   继续负责上下文预算、摘要、长期记忆、附件片段、知识片段、Prompt prefix 稳定性和诊断可视化。

5. Observability Layer
   新增 Trace、请求耗时、首 token 延迟、召回命中、裁剪原因、反馈和错误记录。

6. Model Layer
   从 provider 配置升级为模型能力、模型健康、路由、降级和多模型比较。

### 23.4 不照搬 Ragent 的边界

Ragent 的复杂度更接近企业级后端项目，我们当前不应一次性复制这些能力：

- 暂不切换到 Java / Spring Boot。
- 暂不做完整企业多租户和部门权限。
- 暂不做复杂可配置 Pipeline 画布。
- 暂不优先做 MCP 工具生态。
- 暂不优先做完整三态熔断器和分布式限流。
- 暂不把所有后台能力一次性做完。

更稳的路径是：先把个人知识库和工作区知识召回做扎实，再逐步引入 Trace、模型路由、RAG 引用和管理后台。

## 24. 2026-05-19 深度思考与联网搜索能力规划

在对标 ChatGPT、豆包、DeepSeek、Gemini、Claude 这类网页端产品时，还有两个明显缺口：

- `深度思考`：用户希望遇到复杂问题时，可以显式要求模型使用更强的推理模式，并在前端看到可展示的思考过程或思考摘要。
- `联网搜索`：用户希望对实时性问题、新闻、价格、政策、库版本、网页资料等内容进行外部检索，并让模型基于搜索结果回答和引用来源。

这两个能力不应被理解为普通 UI 小按钮，而是 Chat Layer、Context Governance Layer、Observability Layer 和 Model Layer 的交叉能力。

### 24.1 深度思考的产品定位

深度思考不是所有模型都有，也不是所有 provider 都用同一套字段。主流模式大致分为三类：

1. 模型原生返回可见 thinking 字段。
   例如 Ollama 官方文档说明，支持 thinking 的模型可以通过 `think` 参数控制，并在 `message.thinking` 与 `message.content` 中分离思考内容和最终回答。

2. OpenAI-compatible provider 通过扩展字段开启。
   例如 SiliconFlow 文档中，部分 Qwen / DeepSeek / GLM 等模型支持 `enable_thinking`，并支持 `thinking_budget` 控制推理 token 上限。这个字段不是 OpenAI 标准字段，必须通过 provider profile 适配。

3. 只返回 reasoning summary，不暴露原始思维链。
   OpenAI reasoning 文档强调不暴露 raw reasoning tokens，而是通过 reasoning summary 暴露摘要。Gemini 也提供 `includeThoughts` 和 `thinkingBudget` 之类配置。Claude Extended Thinking 则有 thinking content block 和 thinking budget。

因此，我们产品里的“深度思考”按钮应该定义为：

> 尽量启用当前模型/服务商支持的更强推理模式；如果服务商返回可展示的思考内容或摘要，则折叠展示；如果服务商不返回，则只展示“已启用深度推理参数，但该模型不返回可见思考过程”。

不能承诺所有模型都能显示完整思考链，也不能把普通“等待首 token”的 loading 文案伪装成真实思考过程。

### 24.2 深度思考在前端的交互

建议在输入框附近加入一个轻量 toggle：

```text
附件按钮 | 联网搜索 | 深度思考 | 发送
```

交互规则：

- 默认关闭，避免普通问题成本和延迟增加。
- 当前模型支持时，按钮可点击。
- 当前模型能力未知时，按钮可点击但提示“将尝试开启，若 provider 不支持会自动降级为普通回答”。
- 当前模型明确不支持时，按钮置灰并显示原因。
- 回答生成时，如果收到 reasoning 内容，在回答上方或内部显示一个可折叠块：

```text
思考过程  12.3s
展开 / 收起
```

展示策略：

- 默认折叠，避免占用聊天区域。
- 流式生成时先展示思考块，再展示最终回答。
- 对 OpenAI / Gemini 这类只给 summary 的 provider，标题用“思考摘要”而不是“完整思考过程”。
- 对不返回 thinking 的 provider，回答下方诊断里记录 `thinking_enabled=true`、`reasoning_visible=false`。

### 24.3 联网搜索的产品定位

联网搜索有两种主流实现：

1. Provider 原生搜索工具。
   例如 OpenAI Responses API 提供 Web Search Tool，可以由模型侧调用搜索并返回引用。这种体验好，但强绑定 OpenAI API，不适合本地 Ollama，也不一定兼容 SiliconFlow 这种 OpenAI-compatible Chat Completions 服务。

2. 应用层外部搜索 API + 搜索结果注入上下文。
   后端先调用 Tavily / Brave / Bing / SerpAPI 等搜索服务，清洗标题、URL、摘要、发布时间、正文片段，再把结果作为一层上下文注入给模型。这个方案 provider 无关，本地 Ollama 和在线 API 都可以用。

结合当前项目“本地优先、多 provider 兼容”的定位，第一版建议采用第二种：

> 后端使用 Tavily 作为默认搜索 provider，搜索结果进入 Context Governance，由模型基于搜索结果回答，并在前端展示来源引用。

后续再在 provider 支持时增加 OpenAI native web_search 等原生工具模式。

### 24.4 联网搜索在前端的交互

建议在输入框旁边加入“联网搜索”按钮，采用单轮开关：

- 默认关闭。
- 用户点击后，当前这一轮会联网搜索。
- 会话级默认值可以后续加到设置里，但第一版不要让行为过于隐蔽。
- 发送后消息状态分两段：

```text
正在搜索...
已找到 5 条来源
正在生成回答...
```

回答展示：

- 回答正文中要求模型用 `[1] [2]` 形式引用来源。
- 回答下方展示来源卡片：标题、域名、摘要、发布时间、打开链接。
- 上下文面板里展示本轮搜索 query、搜索耗时、召回数量、注入 token、被裁剪来源。
- 导出会话时可选择包含搜索来源。

隐私提示：

- 第一次开启联网搜索时，应提示用户“你的问题会发送给第三方搜索服务”。
- 如果用户上传了文件，第一版不要默认把文件全文作为搜索 query，只使用用户当前问题和必要的短关键词。

### 24.5 与当前 AI Web Studio 的关系

这两个功能建议作为 `P2.5` 插入，不抢占 P3 知识库主线：

1. 先做深度思考按钮 MVP。
   原因是当前后端已经在 Ollama 和 SiliconFlow 调用层显式关闭 thinking，改造入口清晰，适合先完成 provider 参数适配和 reasoning 流式展示。

2. 再做联网搜索按钮 MVP。
   原因是联网搜索会引入第三方 API key、搜索结果数据表、引用展示和上下文预算，需要比 thinking 多一层链路。

3. 最后继续 P3 附件片段持久化索引与知识库召回。
   联网搜索的 `SearchResult`、`SourceCitation`、`Trace` 设计可以复用到后续知识库引用。

## 25. 2026-05-19 外部信息源与工具增强总体架构

前面第 24 节把“联网搜索”初步规划为 Tavily 搜索结果注入上下文。但从架构角度看，这个设计还不够。ChatGPT、Gemini、Claude、Perplexity、豆包这类产品的“联网”并不只是一个搜索 API，而是一套外部信息获取和工具调用能力。

因此，AI Web Studio 后续不应该把 Tavily、天气、高德地图、MCP、知识库检索分别硬塞到聊天逻辑里。更合理的定位是：

> `联网搜索` 是 External Context / Tool Layer 的一个入口；搜索、网页解析、天气、地图、金融、知识库召回、MCP 工具都应该通过统一接口进入系统，再由上下文治理和 Trace 统一管理。

### 25.1 主流网页端的实现方式

调研后可以把主流方案分为四类。

第一类：模型厂商原生搜索工具。

- OpenAI Responses API 支持 `web_search` tool，模型可以决定是否搜索，并返回 `web_search_call`、sources 和 citations。
- Gemini 提供 Grounding with Google Search，启用 `google_search` 后，模型负责搜索、处理、引用。
- Claude API 提供 web search tool，Claude 可以多次搜索，最后返回带引用的回答；新版本还支持 dynamic filtering，把不相关网页内容先过滤掉，减少 token 消耗。

优点是体验一致、引用链路由模型厂商处理。缺点是绑定具体 provider，不适合本地 Ollama，也不一定兼容 SiliconFlow 这种 OpenAI-compatible Chat Completions 服务。

第二类：带搜索能力的模型 API。

- Perplexity / Sonar 这类 API 将搜索和回答融合在模型服务里。
- 一些搜索模型会固定先搜索再回答。

优点是接入简单。缺点是可控性较弱，搜索结果、预算、工具链路、缓存和多源融合不一定由我们掌控。

第三类：应用层搜索 API。

- Tavily：面向 LLM 应用，支持 search depth、answer、raw content、domain include/exclude。
- Brave Search：提供 Web Search、LLM Context、freshness、country/language、local enrichments、rich results。
- SerpAPI：聚合 Google、Bing、Yahoo、YouTube、Tripadvisor、Google Maps 等搜索结果，适合需要 SERP 结构化字段的场景。
- Exa：偏语义搜索和研究场景，支持 neural / auto / deep 等搜索类型，并可提取网页内容。

优点是 provider 无关，适合本地模型和多模型系统。缺点是应用自己要做 query rewrite、结果清洗、去重、引用、预算和失败处理。

第四类：垂直 API / MCP 工具。

- 天气可以直接接 wttr.in、OpenWeather、高德天气、Brave rich results 或其他天气 API。
- 地图可以接高德地图 REST API、百度地图 MCP、高德地图 MCP。
- 金融、体育、航班、日历、数据库、GitHub、飞书等都更适合作为工具，而不是普通网页搜索。
- MCP 标准提供了 tools/list、tools/call、resources/read 等协议，适合后续把第三方工具纳入统一工具层。

这类能力不应该用“联网搜索”四个字概括，更准确的是“外部信息源 / 工具增强”。

### 25.2 我们项目的产品设计取舍

AI Web Studio 的定位是本地优先、多 provider、个人知识库型 AI 工作台。基于这个定位，推荐策略是：

1. 第一阶段不依赖某个模型厂商的原生搜索。
   因为本地 Ollama 无法使用 OpenAI / Gemini / Claude 的托管搜索工具，SiliconFlow 也不等价于 OpenAI Responses API。

2. 第一阶段使用应用层搜索 API。
   Tavily 可以作为默认 web search provider，但接口必须设计成可替换，后续能接 Brave、SerpAPI、Exa。

3. 垂直信息走工具，不走普通搜索。
   天气、地图、路线、POI、金融价格等问题，优先调用结构化工具，而不是搜索网页后让模型猜。

4. MCP 作为后续工具接入标准。
   第一版可以先做内置 Python Tool Provider，后面再做 MCP Client，把高德地图 MCP、百度地图 MCP、GitHub MCP、数据库 MCP 等接进来。

5. 前端按钮保持简单。
   用户不应该看到一堆 Tavily / Brave / 天气 / 高德按钮。输入框保留“联网搜索”和“深度思考”；工具路由在后台根据问题意图选择。后续可以增加一个“工具调用详情”面板，而不是增加很多入口。

### 25.3 推荐的产品交互

输入区：

```text
上传附件 | 联网搜索 | 深度思考 | 发送
```

其中 `联网搜索` 的真实含义应该是：

- 允许本轮使用外部实时信息。
- 第一版只触发 Web Search。
- 后续可以触发天气、地图、金融、体育、MCP 等只读工具。
- 如果工具需要敏感参数或有副作用，必须要求用户确认。

回答过程状态：

```text
正在判断是否需要外部信息...
正在搜索网页...
正在查询天气...
正在调用地图工具...
已获得 5 条来源，正在生成回答...
```

回答下方统一展示：

- 网页来源
- 工具调用结果
- 地图 / 天气结构化卡片
- 知识库片段来源
- 本轮 Trace

### 25.4 为什么不能简单堆功能

如果每来一个功能都在聊天接口里加一个 if/else，代码会很快失控：

```text
if web_search:
  ...
if weather:
  ...
if amap:
  ...
if mcp:
  ...
if knowledge:
  ...
```

更稳的架构是把它们都抽象成“可召回外部上下文的通道”：

```text
User Message
  -> Intent / Tool Router
  -> External Context Channels
     - WebSearchChannel
     - WeatherToolChannel
     - MapToolChannel
     - WorkspaceKnowledgeChannel
     - CurrentAttachmentChannel
     - MCPToolChannel
  -> PostProcessors
     - Deduplicate
     - Normalize Score
     - Source Attribution
     - Budget Trim
     - Rerank
  -> Context Governance
  -> Prompt Builder
  -> LLM
```

这个思路和 Ragent 的 `SearchChannel + MultiChannelRetrievalEngine + SearchResultPostProcessor` 很接近。区别是我们不只做知识库检索，而是把 web、天气、地图、MCP 也纳入 External Context Channel。

### 25.5 分阶段路线

近期建议不要一次性做完整 Agent。更稳的路线是：

1. 先做 External Context 抽象。
   把 Tavily 搜索实现为第一个 `WebSearchProvider`，输出统一 `ExternalSource`。

2. 再做 Tool Registry。
   把天气查询、高德地图查询定义成只读 Tool Provider，统一工具描述、参数 schema、输出 schema、权限和 Trace。

3. 再做 Tool Router。
   第一版用规则判断：天气问题走 weather，路线/地点问题走 map，实时事实问题走 web search。后续再用 LLM 做意图识别。

4. 再做 MCP Client。
   支持连接高德地图 MCP、百度地图 MCP、GitHub MCP 等外部 server，但默认只启用只读工具。

5. 最后再考虑模型原生工具。
   如果 provider 是 OpenAI Responses / Gemini / Claude，可以选择走原生 web_search。但仍然要把结果转换为系统统一的 Source / Trace 结构，避免前端和上下文治理被 provider 绑死。

### 25.6 架构原则

后续所有外部工具必须遵守这些原则：

- Provider 可替换：Tavily 不是唯一实现。
- 输出结构统一：网页、天气、地图、知识库都要转成统一 Source / ToolResult。
- Trace 必须记录：调用了什么工具、参数是什么、耗时多少、是否失败、进入 Prompt 的内容有哪些。
- 上下文预算统一治理：工具返回再多内容，也必须经过 token 预算裁剪。
- 默认只读：第一阶段只接查询类工具，不做下单、发消息、删文件等副作用操作。
- 敏感操作确认：MCP 工具如果有副作用，必须弹窗确认。
- 密钥隔离：搜索 API key、地图 API key、MCP 配置都要按用户或工作区隔离。
- 失败可降级：工具失败时可以提示失败原因，并允许退回普通回答。

## 26. 2026-05-19 工具路由与意图识别设计

开启“联网搜索”不应该理解为“每轮都调用所有外部工具”。它更准确的含义是：

> 用户允许本轮使用外部实时信息，但系统仍然需要判断是否需要调用工具、调用哪个工具、调用几个工具、是否需要降级为默认搜索。

如果每次都同时调用 Tavily、天气、地图、MCP、知识库，不仅慢、贵、容易触发限流，而且会把大量无关信息塞进上下文，反而降低回答质量。

### 26.1 主流平台给我们的启发

Dify 的 Agent 节点支持两种典型策略：

- Function Calling：把工具定义和参数 schema 交给支持 function calling 的模型，由模型决定是否调用工具。
- ReAct：对不擅长原生函数调用的模型，用 Reason + Act 的提示词循环让模型选择工具。

Dify 的关键点不是“每次调用所有工具”，而是工具要有清晰 description、参数 schema、授权配置和最大迭代次数，模型按任务动态选择。

Coze / Coze Studio 更偏插件和工作流：

- 插件工具可以扩展联网搜索、科学计算、画图等能力。
- 自定义插件限定在 workspace 范围内。
- 工作流可以发布成可调用能力，再通过输入 schema 被 Agent 或外部系统调用。

Coze 的启发是：复杂能力应该可以封装成工具或工作流，但调用前仍然依赖工具描述、参数 schema 和路由判断。

Ragent 的实现更适合我们参考。它不是直接把所有工具暴露给聊天链路，而是：

- 建立 `IntentTree`。
- 每个叶子意图有描述、示例、类型。
- 类型包括 `KB / SYSTEM / MCP`。
- MCP 节点可以挂 `mcpToolId` 和参数提取 Prompt。
- LLM 对叶子意图打分。
- 后续根据分数阈值和类型过滤 KB / MCP / SYSTEM。
- 检索和 MCP 结果再进入 Prompt。

这说明更稳的生产方案是“意图路由 + 工具白名单 + 阈值 + 参数校验”，而不是“开关打开后全量工具调用”。

### 26.2 我们项目的产品定义

前端仍然保留一个简单的 `联网搜索` 按钮，但内部语义改成：

```text
allow_external_context = true
```

它只表示允许本轮使用外部信息。真正调用什么工具由后端决定。

用户体验：

- 用户问“今天广州天气怎么样”：调用天气工具，不调用 Tavily。
- 用户问“广州南站附近有什么咖啡店”：调用地图 / POI 工具，不调用天气。
- 用户问“LangChain 最新版本有什么变化”：调用 Tavily / Brave / Exa 这类 Web Search。
- 用户问“我上传的项目文档里怎么配置数据库”：调用工作区知识库，不调用外网。
- 用户问“你好”：不调用任何工具。
- 用户问“明天去深圳出差，天气怎么样，附近有没有地铁”：可以调用天气 + 地图，但最多调用相关工具，不全量调用。

### 26.3 推荐路由策略

建议采用三段式路由，而不是一开始就做完整 Agent。

第一段：快速规则门控。

作用是用低成本规则过滤明显不需要工具的问题。

```text
问候 / 翻译 / 写作 / 代码解释 / 总结当前文本 -> 不调用外部工具
天气 / 气温 / 下雨 / 台风 -> 候选 weather
附近 / 地址 / 路线 / 怎么去 / POI -> 候选 map
今天 / 最新 / 官网 / 价格 / 版本 / 新闻 / 政策 -> 候选 web_search
文档 / 上传 / 工作区 / 资料 / 附件 -> 候选 knowledge
```

第二段：意图打分。

当规则门控无法明确判断，或者候选工具超过一个时，调用轻量 Tool Router。

Tool Router 输出结构化计划：

```json
{
  "should_use_tools": true,
  "calls": [
    {
      "tool_key": "weather.current",
      "confidence": 0.91,
      "reason": "用户询问当前天气",
      "arguments": {"city": "广州"}
    }
  ],
  "fallback": "web_search"
}
```

第三段：执行约束。

即使 router 输出多个工具，也要做硬约束：

- 默认最多调用 1 个工具。
- 多意图问题最多调用 2 个工具。
- 只有用户明确提出多项实时需求时才并行调用。
- 每个工具有 timeout。
- 每轮有总调用预算。
- 低置信度工具不调用，降级为 Tavily / 普通回答。

### 26.4 默认工具策略

Tavily 可以作为默认兜底，但不应该成为所有实时问题的唯一入口。

建议规则：

- `weather` 置信度高于 0.75：调用天气工具。
- `map` 置信度高于 0.75：调用地图工具。
- `knowledge` 置信度高于 0.65：调用工作区知识库。
- `web_search` 置信度高于 0.65：调用 Tavily。
- 如果多个工具置信度接近，并且问题确实包含多个子任务，最多取前 2 个。
- 如果所有专用工具置信度低，但用户开启联网搜索，则调用 Tavily 兜底。
- 如果用户没开联网搜索，除工作区知识库和当前附件外，不调用外部网络工具。

### 26.5 为什么不要一开始做完全自主 Agent

完全自主 Agent 的问题是：

- 本地模型 function calling 稳定性不一定足够。
- 工具多了以后，模型容易误调用。
- 多轮工具循环容易拖慢前端体验。
- 很难控制预算、隐私和副作用。
- 调试成本高。

所以近期更适合：

```text
规则门控 + 轻量 LLM Router + 后端强校验 + 单轮工具执行
```

等工具层稳定后，再考虑：

```text
Function Calling Agent / ReAct Agent / MCP 多步工具链
```

### 26.6 和深度思考的关系

`深度思考` 和 `联网搜索` 应该是两个独立维度。

- 深度思考：影响模型推理模式。
- 联网搜索：允许外部信息源。

组合情况：

- 两者都关：普通聊天。
- 只开深度思考：复杂推理，但不调用外部工具。
- 只开联网搜索：调用必要工具，但模型普通推理。
- 两者都开：复杂问题 + 必要工具 + 更强推理。

不要因为开了深度思考就自动调用工具，也不要因为开了联网搜索就自动开启深度思考。

## 29. 2026-05-28 工具层可配置化与插件化路线

本节只确定方向和边界，暂不进入代码实现。目标是把当前 `联网搜索` 从“后端硬编码 Tavily / 高德”的功能，升级为个人智能问答和个人知识库系统中的通用外部工具层。

### 29.1 当前项目现状

目前项目已经具备第一版外部信息能力：

- 前端有 `联网搜索` 开关。
- 后端按规则把天气问题路由到高德天气，把地图/路线/附近问题路由到高德地图，把其他实时网页问题路由到 Tavily。
- 工具结果统一转成 `ExternalSource`，再注入 Prompt，并在回答下方展示来源。
- 消息表中已经持久化 `external_sources`，可以在历史消息中重新展示来源。

但当前仍有明显限制：

- `ExternalContextService` 同时承担 router、provider、formatter、assembler 职责，后续继续加工具会膨胀。
- 工具调用过程没有前端可视化，只能看到最后的来源。
- 工具调用没有独立 Trace 表，无法追踪每次工具是否命中、耗时、失败原因、fallback 路径。
- Tavily 和高德 API Key 仍来自后端 `.env`，不是用户级或工作区级配置。
- 工具列表是代码固定的，不支持用户选择启用、禁用、配置、导入。

### 29.2 调研结论

参考 Dify、Coze、Ragent 和主流 Agent 平台，可以抽象出几条共性：

- 工具不应该直接写死在聊天主流程里，而应该先注册到 Tool Registry，再由 Router 选择，再由 Executor 执行。
- 工具凭证应该和用户/工作区绑定，后端环境变量只适合作为本地单用户开发 fallback。
- 工具调用过程需要可观测，包括计划、开始、结束、失败、fallback、来源注入情况。
- 工具结果不应该只有通用文本来源卡片，天气、地图、网页、知识库引用应该有不同展示方式。
- 插件市场不是第一步。更合理的是先做内置集成目录，再做自定义 HTTP 工具，最后再考虑 MCP 或外部插件包。

相关参考：

- Dify Tools 文档：https://docs.dify.ai/en/use-dify/workspace/tools
- Dify 插件安装文档：https://docs.dify.ai/en/plugins/quick-start/install-plugins
- Dify Marketplace：https://marketplace.dify.ai/
- Tavily Search API：https://docs.tavily.com/documentation/api-reference/endpoint/search
- 高德 Web 服务 API：https://lbs.amap.com/api/webservice/summary

### 29.3 六项能力的产品边界

第一项：工具调用过程可视化。

前端不只显示最终来源，还要显示：

- 正在判断是否需要工具。
- 计划调用哪些工具。
- 正在调用 Tavily / 高德天气 / 高德地图。
- 工具成功、失败、fallback 和耗时。
- 最终哪些来源进入 Prompt。

第二项：外部工具层拆分。

把当前单体 `ExternalContextService` 拆成：

- `ToolRegistry`：登记有哪些工具。
- `ToolRouter`：判断本轮应该调用什么工具。
- `ToolExecutor`：统一执行工具、控制 timeout、处理错误。
- `ExternalSourceFormatter`：把 provider 原始返回转成统一来源结构。
- `ExternalContextAssembler`：决定哪些来源进入 Prompt。
- `ToolTraceRepository`：持久化调用过程。

第三项：Tool Trace 持久化。

工具调用不只存在内存和前端流里，还要落库。这样后续可以做：

- 历史回答的工具调用回放。
- 来源和工具调用详情查看。
- 工具耗时统计。
- 搜索质量和工具命中率分析。
- API Key 或 provider 问题排查。

第四项：来源卡片增强。

来源展示按类型区分：

- 网页来源：标题、域名、摘要、分数、链接。
- 天气来源：城市、天气、温度、湿度、风向、发布时间。
- 地图 POI：地点名、地址、类型、距离、电话、地图跳转。
- 路线规划：起点、终点、距离、预计耗时、路线步骤。
- 知识库引用：文件名、chunk、页码、相似度、点击定位。

第五项：工具可配置性。

设置页需要新增 `工具与集成` 区域。Tavily、高德这类需要 API Key 的工具，应该允许用户配置自己的凭证。

推荐配置优先级：

```text
用户级工具凭证 / 工作区工具凭证
-> 后端 .env fallback
-> 未配置则工具不可用，并提示用户去设置
```

第六项：工具导入与选择。

当前阶段不做完整插件市场，但要按照可扩展方向设计：

- 第一阶段：内置工具目录，包含 Tavily、高德天气、高德地图。
- 第二阶段：本地工具清单，使用 JSON/YAML manifest 描述工具。
- 第三阶段：自定义 HTTP 工具，用户配置 endpoint、method、headers、鉴权和结果映射。
- 第四阶段：MCP Client，允许连接本地或远程 MCP Server。
- 第五阶段：插件市场或 GitHub 导入，仅在安全和沙箱机制成熟后考虑。

### 29.4 设置页方向

当前设置是聊天页里的小弹窗，已经承载了模型、上下文、主题、模板、工具等太多内容。当前版本已经补出第一版独立 `/settings` 页面，后续仍需继续把旧弹窗中的剩余能力迁入；长期目标仍是完整独立设置页：

```text
  工具与集成
  工具凭证
  隐私与导出

```

其中 `工具与集成` 应支持：

- 查看可用工具。
- 启用/禁用工具。
- 配置 API Key。
- 测试连接。
- 查看最近调用状态。
- 设置工作区默认工具。

当前第一版已经落地的范围：

- `/settings` 路由已可独立访问。
- 已集中承接模型服务、生成参数、上下文、长期记忆概览、系统提示、工具与集成、工作区默认设置、外观、隐私概览。
- 聊天主界面中的“设置”主入口已切到独立页面，旧弹窗作为过渡性“高级”入口保留。
- 用户级 provider API Key 与工具 API Key 在接口层只返回掩码，不再返回明文。
- 工具目录已经从纯代码内置过渡到本地 manifest 驱动，后端从 `backend/app/tool_manifests/default_tools.json` 读取内置工具定义。

### 29.5 为什么先不做完整插件市场

Dify / Coze 的插件市场面向“搭建应用和智能体”的平台型场景，而当前项目主要定位是个人智能问答和个人知识库系统。

如果现在直接做完整插件市场，会引入：

- 插件包格式。
- 安装和升级。
- 权限模型。
- 安全沙箱。
- 第三方代码执行风险。
- 插件版本兼容。
- UI 和后端复杂度显著上升。

所以更稳妥的路线是：

```text
内置工具注册表 -> 用户级凭证 -> 工具 Trace -> 专用来源卡片 -> 自定义 HTTP 工具 -> MCP -> 插件市场
```

## 32. 2026-06-10 RAG-3 文本索引与检索测试

- 检索测试接口。

- 检索测试面板。

- 保留 `parsed_assets_json` 作为后续 OCR、caption、多模态 embedding 的扩展点。
- 向量当前只保存在 FAISS 文件，PostgreSQL 保存 chunk metadata 和 vector id。
- 索引单个文档后当前会整库重建 FAISS，优先保证正确性；后续再做增量索引和后台 worker。

- `RAG-5`：聊天页知识库选择、上下文注入和引用来源。

## 34. 2026-07-28 RAG Query Rewrite 与 Tool 数据流补充

本节用于覆盖前面仍停留在 FAISS/单知识库阶段的历史描述。当前向量检索已经迁移到 PostgreSQL + pgvector，知识库任务也已演进为 Outbox + Redis Stream Worker；本轮继续补齐两项适合在现有架构内小步实现的能力。

### RAG Query Rewrite

聊天知识库检索新增确定性的上下文扩展：当本轮是包含“它、这个、上述、前者/后者”等明确指代的短问题时，只读取最近一条历史 user 消息，把它与当前追问组合成实际 retrieval query。Assistant 内容不参与改写，避免把模型幻觉固化成检索意图。

原始问题继续用于最终回答和 Retrieval Log 的主 `query`；实际检索词、改写策略和引用的历史消息 ID 写入 diagnostics。该能力是有界规则 MVP，不是 LLM Rewrite、Multi-Query、Query Decomposition、Multi-step RAG 或 PCR-RAG。

### Tool Result Binding

Bounded Tool Workflow 现在允许下游调用声明 `result_bindings`，把已声明 `depends_on` 上游的结构化结果传给下游参数。安全边界为：

- 只能读取 `/sources/<index>/metadata/raw/...`，不能从自由文本 `display_text` 取值。
- 只能写入下游 Input Schema 声明的顶层参数，禁止模型参数与 Binding 同时提供同一目标。
- 只接受有长度上限的标量或短标量数组，不执行表达式或代码。
- 绑定完成后重新执行完整 JSON Schema 校验；缺失、越界、类型不符或依赖失败时，下游调用不执行。
- Trace 只记录来源路径、目标字段和类型，不记录实际绑定值。

因此准确表述是“最多两轮、每份计划最多五次调用的 Bounded Tool Workflow，支持受控结构化 Result Binding”，不能表述为任意 DAG 编排平台或 Durable Agent Runtime。

> 2026-07-31 更新：同步 Chat 主链仍保持上述 Bounded Tool Workflow；另新增了独立的低风险只读 Durable Tool DAG 控制面。后者使用 AgentRun/Step、PostgreSQL Outbox、Lease/Fencing、Checkpoint、有限重试、DLQ 和 Artifact，但不接收任意写工具。文件修改仍走专用 Diff/Approval/CAS continuation，因此不能概括成“任意 Tool 都已 Durable 化”。会话在线主存储继续使用 PostgreSQL，JSONL 仅作为版本化导出和回放格式。

已实现的专用文件修改链路具备 `AgentRun/Step/Checkpoint/Approval/PatchDraft/FileRevision`、参数哈希、一次性确认 continuation 与版本 CAS；低风险只读 Tool 具备跨请求幂等、Outbox、Lease/Fencing、有限重试、DLQ、受控重放和对账。它们不能被泛化为任意外部副作用的自动执行能力。

## 35. 2026-07-31 显式 Skill 执行主链

Skill 已从“设置页安装状态”进入同步 Chat 主链。用户在输入区显式选择一个已安装、已启用且当前工作区可执行的 Skill；服务端重新校验安装状态、必需 Tool、工作区开关和凭据，再生成只包含审核字段的 `SkillExecutionContext`。

执行链为：

```text
用户显式选择 Skill
-> 后端解析安装/启用/工作区/凭据
-> Skill required + 当前可用 optional Tool 形成 allowlist
-> Candidate Selector 只能在 allowlist 内召回
-> Skill instructions 注入 LLM Planner 的可信系统约束
-> Planner 输出 ToolPlan JSON
-> 代码 Tool Workflow / Executor 执行
-> Tool 结果作为不可信 evidence 注入最终上下文
-> Skill output_contract 作为可信系统约束指导最终回答
-> skill_activation / Planner / Tool / skill_result 写入 Trace 和指标
```

当前内置四项受审核 Skill：联网研究简报、项目文档审阅、出行路线规划、Agent 产物复盘。Skill Manifest 不接受脚本、Shell、URL、凭据或自定义权限，只能组合已有 Tool。文件审阅 Skill 不包含 `workspace.files.apply_edit`；Shell、SQL、删除、支付、邮件、外部发布和任意 HTTP 写入仍未开放。

第一版只支持用户显式选择，不让模型自动安装或自动激活 Skill；第三方市场、签名审核、升级回滚和质量 Gold Set 仍是后续工作。

## 36. 2026-07-31：个人知识库工作平台的 Skill 治理与受限 Agent 收口

产品定位收敛为“围绕个人资料的组织、检索、审阅、研究与安全行动的本地知识库工作平台”。因此不追求 Codex 式编码代理，也不以支付、邮件发送、外部发布、任意 HTTP 写入、Shell/SQL、删除文件或任意本机文件写入为功能目标。

本阶段新增的闭环如下：

- Skill 安装锁定 canonical manifest digest，并保留 append-only 审核快照；目录升级不会静默改变已安装 Skill，用户通过显式升级或回滚切换版本。
- `repository_attestation` 只是仓库内发布/审核完整性标记，不等于已实现第三方的 detached cryptographic signature。第三方市场仍需要可信公钥、签名验证、隔离拉取和人工发布审批。
- 系统可基于输入和 manifest 元数据推荐已经安装且当前可执行的 Skill；界面只显示推荐，点击后才选择，推荐服务不安装、不启用、不扩大 Tool allowlist。
- Gold Set 固定记录 Skill/Tool 预期，评测接口统计 Skill Recall@3、Tool Recall、选择正确率、参数正确率、任务成功率和延迟；未跑 Provider 的样本不会伪装成线上质量结论。
- 低风险只读 Skill 可显式进入 Durable Tool DAG；同步 Chat 仍严格两轮 observe -> re-plan。第二轮还请求继续时，Trace 写入 `max_rounds_reached`，而不是暗中扩展为开放式 ReAct。
- Durable Step 支持 DLQ、用户触发的受控重放、缺失投递意图对账、Lease/Fencing 和警告指标；worker 会再次验证持久化的 Skill allowlist、当前 Tool 的只读/低风险属性和工作区策略。

上下文治理升级为结构化证据层：会话摘要、长期记忆、附件、外部 Tool 证据、知识库证据分别保留内部层标识；超预算时依次移除摘要、记忆、附件、外部证据，再压缩最后剩余层，当前问题和 system prompt 不会与 evidence 混合后被优先截断。

## 2026-08-01：System Prompt 与工具说明治理

平台行为合同进一步明确个人知识库工作台的角色、结论优先原则、资料不足时的检索策略、证据不可信规则、任务执行模式和产品非目标。动态 query、记忆、摘要、RAG、附件和 Tool 返回继续作为 evidence 注入，不得覆盖系统边界。工具说明统一补充适用场景、只读/高风险权限、MCP 返回不可信和工作区范围；真正权限仍由 Executor、Approval、CAS 和 ACL 决定。
