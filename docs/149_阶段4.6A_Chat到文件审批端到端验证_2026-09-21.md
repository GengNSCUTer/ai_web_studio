# 阶段 4.6A：Chat 到工作区文件审批端到端验证

日期：2026-09-21

## 1. 阶段目标

把已经存在的工作区文件工具接入一条可验证的业务链路，而不是只在 Provider 或服务层做孤立单测：

```text
Chat 请求
 -> workspace.files.search/read/apply_edit
 -> 生成持久化 PatchDraft 和 Diff
 -> confirmation_required
 -> 用户在前端确认
 -> challenge
 -> apply
 -> FileRevision/CAS 写入
 -> 重新读取并核验新版本
```

本阶段不新增工具、不开放任意本机文件写入，也没有把默认 Chat 改成自动编辑。默认 `ask` 模式下，修改操作必须先生成审批草案，用户确认后才写入；`full_workspace` 也只在当前用户、当前项目、ACL 和版本 CAS 条件满足时放行。

## 2. 实际实现链路

### 后端

- `backend/app/services/tools/providers/workspace_files.py`
  - 提供 `workspace.files.list/search/read/propose_edit`。
  - 读取和编辑提案都绑定当前项目文件与 `FileRevision`，避免只依赖文件名或旧文本。
- `backend/app/services/tools/executor.py`
  - 统一执行 schema、工具权限和审批边界。
  - `workspace.files.apply_edit` 不绕过 Agent Runtime 直接写文件。
- `backend/app/services/agent_runtime_service.py`
  - 创建 `AgentRun`、`AgentStep`、`PatchDraft`、`AgentApproval`。
  - challenge 只签发一次性审批凭据，apply 阶段重新校验参数哈希、用户/项目范围和当前 Revision，并通过 CAS 写入 `FileRevision`。
- `backend/app/services/workspace_file_provenance.py`
  - 生成和复用当前文件的 Revision 证明，提供内容哈希和版本身份。
- `backend/app/api/routes/agent_runtime.py`
  - 提供审批 challenge/apply/reject API。

### 前端

- `frontend/src/components/chat-thread.tsx`
  - 解析 Chat NDJSON 工具事件，保存 `tool_confirmation_required` 状态。
  - 流结束刷新历史消息时仍保留工具事件，避免审批卡片被刷新覆盖。
- `frontend/src/components/tool-trace-panel.tsx`
  - 展示工具名称、原因、文件名、Diff 和审批状态。
  - 用户点击“确认并应用 Diff”后，按 `challenge -> apply` 顺序调用接口，并显示“已通过版本 CAS 应用修改”。
- `scripts/stage46a_playwright.py`
  - 使用受控 Chat NDJSON 和审批 API 响应验证真实浏览器交互、刷新保留、Diff 展示和确认收口，同时收集 `pageerror`/console error。

## 3. 测试结果

### 后端业务/API 测试

新增 `backend/tests/test_tool_routes.py::test_file_edit_api_confirmation_flow_is_idempotent`，使用真实 `ToolExecutor`、工作区 Provider 和 Agent Runtime，覆盖：

1. 文件编辑请求只返回 `confirmation_required`，原文不变；
2. challenge 后 apply 写入第二个 `FileRevision`；
3. 重复 apply 或错误 token 不会产生第二次写入；
4. 最终版本号、内容哈希和审批状态一致。

阶段定向测试：`63 tests OK`。

### 前端浏览器测试

Playwright 验证：

1. 登录并进入 Chat 页面；
2. 发送文件修改请求；
3. 流式工具事件在刷新后仍显示；
4. 展开工具过程和详情后能看到 Diff/原因；
5. 点击确认后依次调用 challenge/apply，并显示 CAS 应用成功；
6. 页面无 `pageerror` 或 console error。

该脚本使用受控流与审批响应，验证的是前端与 API 合同及状态展示，不宣称真实 LLM 已经稳定自动规划出文件编辑调用。

## 4. 当前边界

- 文件工具仍是当前用户/当前项目范围内的受控工作区能力，不是任意本机路径读写。
- 默认 Chat 不会因为普通问答自动修改文件，修改必须有明确工具计划和用户确认。
- 本阶段没有接入真实 LLM 自动规划文件编辑；真实在线模型链路仍需在后续阶段用固定、低风险工作区用例单独验证。
- 文件编辑完成后已具备 Revision/CAS 和重新读取核验；跨请求 Durable handoff、长任务自动恢复和更多文件操作仍属于后续优化。
