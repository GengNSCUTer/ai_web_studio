## 1. 这份文档解决什么问题

目前项目已经进入“功能较多、链路较长”的阶段，后端不再只是几个接口，而是包含：

- 登录鉴权、用户设置、会话、消息、附件、项目、分享、Prompt 模板。
- 聊天流式输出、上下文治理、长期记忆、工具调用、MCP、联网搜索。
- 知识库、文档解析、MinerU、分块、Embedding、BM25、Hybrid、Rerank、Parent-Child 检索、RAG 聊天接入。

如果直接从某个 service 文件开始看，容易迷失在实现细节里。更稳的方式是先从第一性原理拆解：

- 后端本质上接收什么请求？
- 请求经过哪些层？
- 哪一层负责 HTTP，哪一层负责业务，哪一层负责数据库？
- 哪些对象是 API 入参/出参，哪些对象是数据库表，哪些对象只是内部流程数据？
- 某个功能出问题时，应该定位到哪条链路？

### 1.1 后端审查与学习台账

这张台账同时记录两个不同进度，避免把“AI 已经修过代码”误认为“学习者已经真正掌握”：

```text
项目审查进度：代码是否按真实链路检查、修复并补过测试。
学习掌握进度：是否看过小段源码、亲自推演状态、观察失败实验，并能用自己的话解释。
```

学习掌握等级：

| 等级 | 含义 |
| --- | --- |
| L0 未开始 | 还没有形成模块地图 |
| L1 看过 | 知道入口和主要文件，但容易停留在结论或文件名 |
| L2 精读 | 能解释核心代码、输入输出、副作用和失败路径 |
| L3 可迁移 | 能独立设计类似功能、比较方案，并回答相关实习面试问题 |

当前台账（每完成一个小专题后更新）：

| 模块 | 项目审查进度 | 学习掌握 | 测试保护 | 当前遗留问题 | 对应传统后端 / Agent 能力 |
| --- | --- | --- | --- | --- | --- |
| FastAPI 入口 / Config / DB / Depends | 已完成第一轮 | L1，需按请求生命周期回访 | 间接覆盖 | 运行期 schema 补丁、生产配置校验 | HTTP 生命周期、依赖注入、配置管理、Session |
| Auth | 已审查并加固 | L1，需按 JWT 与事务专题精读 | `test_auth_service` | 生产密钥、限流、登录安全策略 | 认证、密码哈希、JWT、唯一约束、并发注册 |
| Settings / Secret | 已审查并加固 | L1，需按密钥生命周期回访 | `test_setting_service`、凭据测试 | 密钥轮换、审计日志 | 敏感数据、加密存储、PATCH 语义、外部 Provider 配置 |
| Conversation / Message | 已审查并加固 | L1～L2，理解聚合边界但需亲自推演 | `test_conversation_message_contracts` | 同会话并发写入、`sequence` 数据库约束 | REST、资源所有权、事务、并发序号、数据生命周期 |
| Chat Streaming | 已完成第一轮 | L1，需按 streaming 状态机精读 | `test_chat_execution_service` | Route 持久化职责偏重、取消/异常恢复 | 流式 HTTP、异步、取消、状态机、错误恢复 |
| Prompt / Context Governance | 已审查并修复权限层级 | L2，已看过指令与资料边界 | `test_prompt_context_governance` | 更完整的 Prompt Injection 评测 | Prompt 层级、上下文预算、AI 安全、可解释性 |
| RAG Query / Context | 已审查 vector、lexical、hybrid、rerank | L1～L2，仍需算法小样例 | `test_knowledge_service` | BM25 缺失时同步重建、失败日志 | 检索、降级、来源追踪、RAG 评测 |
| RAG 单文档索引 | 已完成 legacy generation 兼容读取基础 | L2 进行中 | Embedding/FAISS/向量校验/generation 隔离测试 | generation 发布器、并发 CAS、全库 Embedding | 事务边界、文件原子发布、版本快照、乐观并发、索引一致性 |
| Chunker / Parent-Child | 功能已有，未完成精读 | L0～L1 | 有正常路径测试 | offset、边界质量、中文/Markdown 切分 | 文本算法、数据建模、RAG chunk 策略 |
| Parser / Upload / MinerU | 做过真实 PDF 验证，未系统审查 | L0～L1 | 部分 | 路径安全、重复解析、长任务 | 文件上传、第三方 API、轮询、Zip 安全、后台任务 |
| Knowledge CRUD / Eval | 已精读评测引用的重索引/删除边界 | L2 进行中 | 外键生命周期与跨库归属测试 | 文档删除后的索引发布、测试检索日志 | CRUD、外键、409 冲突、状态机、评测数据模型 |
| Memory | Chat 组装时接触，未系统审查 | L0～L1 | 部分 | 冲突、来源、提取可靠性 | 用户状态、长期记忆、AI 数据治理 |
| Tools / MCP / Planner / Workflow | 早期功能有测试，尚未按当前方法精读 | L0～L1 | tools 系列测试 | 多步循环、权限、幂等、副作用控制 | Agent Tool Calling、MCP、工作流、执行安全 |
| Background Job / Worker | 当前只有同步 Job 状态记录 | L0 | 无完整 Worker 测试 | 队列、重试、崩溃恢复、进度 | 后台任务、幂等、分布式系统、Agent durable execution |
| Observability / Production | 零散实现 | L0～L1 | 无系统覆盖 | 指标、结构化日志、trace、迁移、部署安全 | 线上诊断、SRE 基础、Agent trace/evaluation |

当前学习主线不是“把所有文件依次读完”，而是两条能力线交叉推进：

```text
传统后端：API -> 数据库/事务 -> 并发 -> 后台任务 -> 可观测性 -> 部署安全
AI / Agent：模型调用 -> Prompt/Context -> RAG -> Memory -> Tools/MCP -> Agent Workflow -> Evaluation
```

当前所在交叉点：

```text
传统后端：事务、外键、数据生命周期、文件发布、并发
AI / RAG：Chunk、Embedding、FAISS、BM25、索引更新、评测引用
```

后续每个专题都应同时产出：

1. 一小段可解释的真实源码。
2. 一个可观察的失败或边界实验。
3. 一个项目修复或明确保留的工程权衡。
4. 一条能迁移到其他项目、也能用于面试表达的知识结论。

## 2. 第一性原理：读后端代码先问什么

读每个文件时，建议固定问这 7 个问题：

| 问题 | 目的 |
| --- | --- |
| 这个文件属于哪一层？ | 判断它应该做什么、不应该做什么 |
| 它的输入是什么？ | HTTP body、query、当前用户、数据库记录、内部对象 |
| 它的输出是什么？ | Pydantic schema、数据库对象、流式事件、内部结果 |
| 谁调用它？ | 找上游入口，知道它何时执行 |
| 它调用谁？ | 找下游依赖，知道它影响哪些模块 |
| 它读写哪些表/文件/外部 API？ | 明确副作用和风险 |
| 它的错误怎么处理？ | 判断前端看到的报错从哪里来 |

不要先纠结每行代码，而是先判断“职责边界”。职责边界清楚后，具体实现才容易理解。

## 3. 后端是什么框架

后端主框架是 FastAPI。

核心运行模型：

- `backend/app/main.py` 创建 `FastAPI` 应用。
- `backend/app/api/routes/*.py` 定义 HTTP API。
- `backend/app/api/deps.py` 定义公共依赖，例如数据库 Session、当前登录用户。
- `backend/app/schemas/*.py` 定义 API 入参/出参的 Pydantic 模型。
- `backend/app/models/*.py` 定义 SQLAlchemy 数据库模型。
- `backend/app/repositories/*.py` 封装数据库读写。
- `backend/app/services/*.py` 封装业务逻辑。
- `backend/app/services/tools/*.py` 封装工具调用、MCP、Planner、Workflow。

可以把后端理解成下面这条主线：

```text
HTTP 请求
  -> FastAPI Router
  -> Depends 注入 db / current_user
  -> Pydantic Schema 校验
  -> Service 执行业务
  -> Repository 读写数据库
  -> Model 映射数据库表
  -> Schema 返回给前端
```

聊天和 RAG 链路会更复杂，因为它们还会调用模型服务、工具服务、外部 API、向量检索和流式输出，但入口仍然是这个结构。

## 4. 目录结构和分层

后端源码主目录：

```text
backend/app/
├── main.py                         # FastAPI 应用入口，注册中间件和路由
├── api/
│   ├── deps.py                     # 公共依赖：数据库 Session、当前用户
│   └── routes/                     # HTTP 接口层
├── core/
│   ├── config.py                   # 环境变量和全局配置
│   ├── database.py                 # SQLAlchemy engine/session/base
│   └── startup.py                  # 启动时的运行期 schema 补丁
├── models/                         # SQLAlchemy ORM 模型，贴近数据库表
├── repositories/                   # 数据访问层，封装 CRUD 查询
├── schemas/                        # Pydantic 入参/出参模型
├── services/                       # 业务逻辑层
│   └── tools/                      # 工具调用、MCP、Planner、Workflow 子系统
└── tool_manifests/
    └── default_tools.json          # 默认工具 manifest
```

### 4.1 Router 层

位置：`backend/app/api/routes/`

职责：

- 定义 URL、HTTP method、response_model。
- 通过 `Depends(get_db)` 获取数据库 Session。
- 通过 `Depends(get_current_user)` 获取当前用户。
- 调用 service。
- 不应该堆复杂业务逻辑。

代表文件：

- `auth.py`：注册、登录、获取当前用户。
- `chat.py`：聊天、重新生成、编辑后重答、流式响应。
- `knowledge.py`：知识库、文档、解析、索引、检索测试、RAG 日志、知识库凭据。
- `tools.py`：工具配置、MCP server、工具目录、工具测试。
- `settings.py`：用户设置、模型设置、知识库模型设置。

### 4.2 Schema 层

位置：`backend/app/schemas/`

职责：

- 定义前端传入的数据格式。
- 定义后端返回给前端的数据格式。
- 做基础字段校验。

示例：

- `schemas/auth.py`：`UserRegisterRequest`、`UserLoginRequest`、`TokenResponse`。
- `schemas/knowledge.py`：知识库、文档、检索、评测相关入参出参。
- `schemas/setting.py`：问答模型、知识库模型、上下文策略等设置。

阅读方法：

- 如果想知道一个接口需要前端传什么，先看 route 的参数类型，再跳到对应 schema。
- 如果想知道前端为什么拿不到某个字段，也先看 response_model 对应 schema 是否声明了它。

### 4.3 Model 层

位置：`backend/app/models/`

职责：

- 描述数据库表结构。
- 字段类型、索引、外键、默认值。
- 不应该写业务流程。

代表模型：

- `user.py`：用户。
- `conversation.py`：会话。
- `message.py`：消息。
- `attachment.py`：附件。
- `knowledge.py`：知识库、文档、chunk、embedding、检索日志等。
- `tool_config.py`：工具、MCP server、用户凭据配置。
- `tool_trace.py`：工具调用过程持久化。
- `user_setting.py`：用户设置。

注意：

- 目前项目使用 `core/startup.py` 做运行期 schema 补丁。这是开发期为了快速演进的务实做法，但你改 model 时要同时理解启动补丁，否则可能出现“代码字段有了，数据库字段没有”或反过来的问题。

### 4.4 Repository 层

位置：`backend/app/repositories/`

职责：

- 封装数据库查询和写入。
- service 不直接到处写复杂 SQL。
- 让业务层更关注流程，而不是 SQLAlchemy 细节。

代表文件：

- `user_repo.py`
- `conversation_repo.py`
- `message_repo.py`
- `knowledge_repo.py`
- `tool_config_repo.py`
- `tool_trace_repo.py`

阅读方法：

- 想知道“某个数据到底从数据库怎么查出来”，看 repository。
- 想知道“某个接口改了哪些表”，从 service 往下找 repository 方法。

### 4.5 Service 层

位置：`backend/app/services/`

职责：

- 封装业务流程。
- 协调 repository、外部模型 API、文件解析、工具调用、RAG 检索等。
- 是后端最需要重点阅读的层。

目前主要 service 族：

- 登录鉴权：`auth_service.py`
- 用户设置：`setting_service.py`
- 会话消息：`conversation_service.py`、`message_service.py`
- 聊天编排：`chat_execution_service.py` 及其拆分 service
- 上下文治理：`context_governance_service.py`、`prompt_builder_service.py`、`tokenizer_service.py`
- 附件上下文：`attachment_context_service.py`、`file_parser_service.py`
- 工具调用：`external_context_service.py`、`services/tools/*`
- 知识库：`knowledge_service.py`、`knowledge_parser_service.py`、`knowledge_index_service.py`、`knowledge_retrieval_pipeline.py`、`knowledge_context_service.py`

阅读 service 的关键是分清：

- 哪些是“流程编排”。
- 哪些是“纯计算/转换”。
- 哪些是“外部副作用”，例如调用 API、写数据库、读文件。

## 5. 一次请求如何流动

以登录接口为例：

```text
POST /api/auth/login
  -> api/routes/auth.py::login()
  -> Depends(get_db) 创建数据库 Session
  -> AuthService(UserRepository(db)).login_user(payload)
  -> UserRepository.get_by_email()
  -> bcrypt 校验密码
  -> jwt.encode() 生成 token
  -> TokenResponse 返回给前端
```

以需要鉴权的接口为例：

```text
请求 Header: Authorization: Bearer <token>
  -> api/deps.py::get_current_user()
  -> jwt.decode()
  -> payload["sub"] 得到 user_id
  -> UserRepository.get_by_id(user_id)
  -> route 函数拿到 current_user
```

以知识库检索聊天为例：

```text
POST /api/chat
  -> chat route
  -> ChatExecutionService
  -> 读取会话、消息、用户设置
  -> 如果启用知识库，调用 KnowledgeContextService
  -> KnowledgeRetrievalPipeline 检索 chunk
  -> PromptBuilderService 组装 prompt
  -> ChatProviderService 调用模型
  -> 流式事件返回前端
  -> 保存 assistant 消息、上下文诊断、工具 trace、RAG 来源等
```

以工具调用为例：

```text
用户开启联网搜索 / 工具
  -> ExternalContextService
  -> ToolCatalog 合并静态 manifest 和 MCP tools
  -> ToolCandidateSelector 选择候选工具
  -> LLMToolPlanner 生成工具计划
  -> ToolWorkflowService 执行有限轮工具调用
  -> ToolExecutor 调 MCP / HTTP 工具
  -> Tool Trace 持久化
  -> 工具结果进入最终回答上下文
```

## 10. 当前后端复杂点和注意事项

### 14.1 `core/config.py`：配置层

文件位置：`backend/app/core/config.py`

这个文件的核心职责是把“外部环境”转换成“代码内部可使用的配置对象”。

关键代码：

```python
ROOT_DIR = Path(__file__).resolve().parents[2]
load_dotenv(ROOT_DIR / ".env")
```

这里先定位项目后端根目录，再加载 `.env`。`Path(__file__).resolve()` 得到当前文件的绝对路径，`parents[2]` 向上两级。对当前文件来说：

```text
backend/app/core/config.py
  parents[0] -> backend/app/core
  parents[1] -> backend/app
  parents[2] -> backend
```

所以这里加载的是：

```text
backend/.env
```

这点很重要。如果你以后发现改了 `.env` 没生效，要先确认你改的是不是 `backend/.env`，而不是项目根目录下的其他 `.env`。

核心配置类：

```python
@dataclass(frozen=True)
class Settings:
    app_name: str = os.getenv("APP_NAME", "ai_web_studio_backend")
```

这里使用 `dataclass(frozen=True)`。含义是：

- `dataclass` 自动生成初始化、repr 等基础方法。
- `frozen=True` 表示实例创建后字段不能再被赋值修改。
- 这让 `settings` 更像一个只读配置对象，避免运行中某个地方随手改配置，造成不可预测行为。

需要理解一个细节：这些字段的默认值是在类定义时通过 `os.getenv()` 读取的。因为文件底部立即执行：

```python
settings = Settings()
```

所以正常情况下它相当于“应用启动时读取一次配置”。如果进程运行中修改 `.env`，不会自动刷新，必须重启后端进程。

数据库连接字符串：

```python
@property
def sqlalchemy_database_uri(self) -> str:
    auth = self.postgres_user
    if self.postgres_password:
        auth = f"{auth}:{self.postgres_password}"
    return (
        f"postgresql+psycopg://{auth}"
        f"@{self.postgres_host}:{self.postgres_port}/{self.postgres_db}"
    )
```

这是一个计算属性，不是普通字段。它把分散的数据库配置拼成 SQLAlchemy 能识别的连接 URL。

`postgresql+psycopg://` 的含义：

- `postgresql` 表示数据库类型是 PostgreSQL。
- `psycopg` 表示使用 psycopg 这个 Python PostgreSQL driver。
- SQLAlchemy 负责统一 ORM 和连接池逻辑，底层 driver 负责真实网络通信。

配置分组可以这样理解：

- 应用自身：`APP_NAME`、`APP_ENV`、`APP_HOST`、`APP_PORT`。
- 数据库：`POSTGRES_HOST`、`POSTGRES_PORT`、`POSTGRES_DB`、`POSTGRES_USER`、`POSTGRES_PASSWORD`。
- 本地模型：`OLLAMA_BASE_URL`、`OLLAMA_DEFAULT_MODEL`、`OLLAMA_KEEP_ALIVE`、`OLLAMA_REQUEST_TIMEOUT_SECONDS`。
- 鉴权：`AUTH_SECRET_KEY`、`AUTH_ALGORITHM`、`AUTH_ACCESS_TOKEN_EXPIRE_MINUTES`。
- 文件和知识库：`UPLOAD_DIR`、`KNOWLEDGE_INDEX_DIR`、`KNOWLEDGE_PARSE_MAX_CHARS`。
- 外部工具：`TAVILY_API_KEY`、`AMAP_API_KEY`、`MINERU_API_TOKEN`。
- 敏感信息加密：`SECRET_ENCRYPTION_KEY`。

第一性原理判断：

- 配置层不应该依赖业务 service。
- 配置层不应该访问数据库。
- 配置层只负责“读取和组织配置”，不负责“使用配置做业务”。

当前可留意的点：

- `AUTH_SECRET_KEY` 有默认值，开发方便，但生产必须覆盖。
- `SECRET_ENCRYPTION_KEY` 默认为空，需要看 `secret_service.py` 如何处理空值。
- 复杂项目里更常见的做法是用 Pydantic Settings，因为它有更强的类型校验和 env 解析能力；当前 dataclass 方案简单直接，适合本项目现阶段。

### 14.2 `core/database.py`：数据库连接层

文件位置：`backend/app/core/database.py`

这个文件回答的问题是：后端如何建立数据库连接，以及 ORM 模型从哪里继承。

关键代码：

```python
engine = create_engine(settings.sqlalchemy_database_uri, pool_pre_ping=True)
```

`engine` 是 SQLAlchemy 的数据库引擎。它不是单个数据库连接，而是数据库连接和连接池的管理对象。

`pool_pre_ping=True` 的作用是：每次从连接池取连接前，先检查连接是否还活着。如果数据库重启、网络断开、连接被服务端关闭，这个参数可以减少“拿到一条已经失效的连接”导致的请求失败。

然后是：

```python
SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)
```

`SessionLocal` 是 Session 工厂，不是 Session 本身。每次请求需要数据库时，会调用 `SessionLocal()` 创建一个新的数据库会话。

参数含义：

- `autocommit=False`：不会自动提交事务，写操作需要显式 `commit()`。
- `autoflush=False`：不会在查询前自动把 pending changes flush 到数据库，减少隐式副作用。
- `bind=engine`：这个 Session 工厂使用上面创建的数据库 engine。

最后：

```python
Base = declarative_base()
```

`Base` 是所有 ORM 模型的共同基类。`models/*.py` 里的表模型应该继承它。SQLAlchemy 通过这个 Base 收集模型元数据，例如表名、字段、索引、外键。

第一性原理判断：

- `database.py` 只负责建立“数据库基础设施”。
- 它不应该知道 User、Message、Knowledge 这些业务表。
- 它不应该直接创建业务数据。
- 它提供的是 `engine`、`SessionLocal`、`Base` 三个底座。

典型请求生命周期：

```text
请求进来
  -> get_db() 调用 SessionLocal() 创建 Session
  -> route/service/repository 使用这个 Session 查询或写入
  -> 请求结束
  -> get_db() finally 关闭 Session
```

注意：`db.close()` 是把 Session 关闭并释放连接回连接池，不等于关闭整个数据库服务。

当前可留意的点：

- 当前是同步 SQLAlchemy，不是 async SQLAlchemy。所以 route/service 里大量数据库操作是同步执行。
- 如果未来并发和长任务更多，知识库解析/索引这类任务更适合放后台队列，而不是让请求线程一直占用资源。

#### 14.2.1 PostgreSQL 和 SQLAlchemy 的最简区别

```text
PostgreSQL：真正运行、存储和约束数据的数据库服务。
SQLAlchemy：Python 后端用来连接数据库、生成 SQL、映射对象和管理事务的工具库。
```

在本项目中的调用关系：

```text
FastAPI Route / Service / Repository
  -> SQLAlchemy ORM + Session
  -> PostgreSQL
```

对应关系：

| Python / SQLAlchemy | PostgreSQL |
| --- | --- |
| `KnowledgeDocument` 类 | `knowledge_documents` 表 |
| 一个 `document` 对象 | 表中的一行 |
| `document.index_status` | `index_status` 列 |
| `select(KnowledgeDocument)` | `SELECT ... FROM knowledge_documents` |
| `db.commit()` | 请求 PostgreSQL 提交事务 |
| `db.rollback()` | 请求 PostgreSQL 回滚事务，并恢复 Session 状态 |

ORM（Object-Relational Mapping）负责把 Python 类/对象映射成关系数据库的表/行；Session 负责跟踪对象变化和组织一次事务。但数据最终是否写入、外键是否允许删除、并发事务是否成立，仍由 PostgreSQL 执行和保证。

错误也会逐层翻译：

```text
PostgreSQL ForeignKeyViolation
  -> SQLAlchemy IntegrityError
  -> Service 领域异常
  -> FastAPI HTTP 409
```

最简记忆：

```text
SQLAlchemy 负责“让 Python 会操作数据库”；
PostgreSQL 负责“真正保存数据并保证数据库规则”。
```

### 14.3 `api/deps.py`：FastAPI 依赖注入层

文件位置：`backend/app/api/deps.py`

这个文件是 FastAPI 项目里很关键的“请求级公共依赖”入口。它解决两个问题：

- 一个接口需要数据库 Session，怎么拿？
- 一个接口需要当前登录用户，怎么拿？

数据库依赖：

```python
def get_db() -> Generator[Session, None, None]:
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```

这是 FastAPI 里常见的 yield dependency。它的执行过程是：

```text
进入请求
  -> 执行 yield 前代码：创建 db
  -> yield db，把 db 注入给 route/service
  -> route 执行完成或抛异常
  -> 执行 finally：关闭 db
```

这比在每个 route 里手动写 `db = SessionLocal()` 更好，因为它统一管理资源释放。

鉴权方案：

```python
bearer_scheme = HTTPBearer(auto_error=False)
```

`HTTPBearer` 会从请求头读取：

```text
Authorization: Bearer <token>
```

`auto_error=False` 表示没有 token 时不要让 FastAPI 自动抛错，而是返回 `None`，交给 `get_current_user()` 自己抛出更可控的错误。

当前用户依赖：

```python
def get_current_user(
    credentials: HTTPAuthorizationCredentials | None = Depends(bearer_scheme),
    db: Session = Depends(get_db),
) -> User:
```

这里体现了 FastAPI 依赖注入的组合能力：

- `credentials` 来自 `bearer_scheme`。
- `db` 来自 `get_db()`。
- 调用这个依赖的 route 不需要自己解析 Header，也不需要自己创建数据库 Session。

JWT 解码：

```python
payload = jwt.decode(
    credentials.credentials,
    settings.auth_secret_key,
    algorithms=[settings.auth_algorithm],
)
```

这里会验证：

- token 签名是否由同一个 `AUTH_SECRET_KEY` 生成。
- token 算法是否匹配。
- token 是否过期，因为 `auth_service.py` 生成 token 时写入了 `exp`。

然后取用户 ID：

```python
user_id = payload.get("sub")
```

JWT 里的 `sub` 通常表示 subject，也就是这个 token 代表的主体。这里主体是用户 ID。

最后查数据库：

```python
user = UserRepository(db).get_by_id(user_id)
```

这一步很重要：后端没有只相信 token，而是又查了一次数据库，确认用户仍然存在。这样如果用户被删除，旧 token 也不能继续通过鉴权。

错误处理路径：

| 场景 | 返回 |
| --- | --- |
| 没有 Authorization Header | 401 `Authentication required` |
| token 签名错误、过期、格式非法 | 401 `Invalid or expired token` |
| token 里没有 `sub` | 401 `Invalid token payload` |
| `sub` 对应用户不存在 | 401 `User not found` |

第一性原理判断：

- `deps.py` 不应该写具体业务。
- 它负责把“请求上下文”转成“业务代码可直接使用的对象”。
- 比如把 Header 里的 token 转成 `User` ORM 对象，把数据库连接池转成请求级 `Session`。

典型 route 使用方式：

```python
@router.get("/me")
def me(current_user: User = Depends(get_current_user)):
    return current_user
```

或者：

```python
@router.post("/something")
def create_something(
    payload: SomeRequest,
    db: Session = Depends(get_db),
    current_user: User = Depends(get_current_user),
):
    ...
```

读这类代码时要意识到：函数参数不一定全部来自前端 body，有些来自 FastAPI 依赖注入。

### 14.4 这三个文件连起来看

这三个文件形成了后端基础链路：

```text
config.py
  -> 读取 .env 和环境变量
  -> 生成 settings

database.py
  -> 使用 settings.sqlalchemy_database_uri
  -> 创建 engine / SessionLocal / Base

deps.py
  -> 使用 SessionLocal 创建请求级 db
  -> 使用 settings.auth_secret_key 解码 JWT
  -> 使用 UserRepository(db) 查当前用户

routes/*.py
  -> Depends(get_db)
  -> Depends(get_current_user)
  -> 拿到 db 和 current_user 后进入业务 service
```

这就是后端大多数接口的基础运行方式。

### 14.5 你做注释时可以继续保持的原则

你现在加的注释主要解释“这一行做什么”，这是入门阅读很有用。后面建议逐步升级成三类注释：

- 事实注释：解释不直观的库调用，例如 `pool_pre_ping=True`。
- 设计注释：解释为什么这里用依赖注入、为什么配置冻结。
- 风险注释：解释这里改错会影响什么，例如 `AUTH_SECRET_KEY` 改了会让旧 token 全部失效。

不建议长期保留太多“导入某某工具”这类注释，因为熟悉后会显得冗余。更有价值的是解释设计意图和边界，例如：

```python
# 每个请求独立创建 Session，并在请求结束后释放连接回连接池。
def get_db() -> Generator[Session, None, None]:
    ...
```

或者：

```python
# 只在启动时读取配置；修改 .env 后需要重启后端进程。
settings = Settings()
```

## 15. 配置边界补充：全局配置和用户态凭据怎么区分

阅读 `core/config.py` 时容易产生一个疑问：Tavily、高德地图、MinerU 这些 API key 已经计划做成用户自己配置，为什么还会出现在全局 `Settings` 里？

从第一性原理看，需要先区分两类配置：

| 类型 | 例子 | 应该属于谁 | 原因 |
| --- | --- | --- | --- |
| 系统运行配置 | 端口、数据库地址、上传目录、超时时间、索引目录 | 系统全局 | 决定后端进程怎么运行，和具体用户无关 |
| 用户外部服务凭据 | Tavily key、高德 key、MinerU token、用户自己的 MCP server token | 用户态 | 每个用户额度、权限、账单、安全边界不同 |

所以正确方向是：

- `APP_PORT`、`POSTGRES_HOST`、`UPLOAD_DIR`、`KNOWLEDGE_INDEX_DIR` 这类配置继续放在 `config.py`。
- `TAVILY_API_KEY`、`AMAP_API_KEY`、`MINERU_API_TOKEN` 这类敏感外部服务 key 不应该作为业务主路径的唯一来源。
- 用户进入系统后，应该在设置页配置自己的 key，后端加密保存，不向前端回显明文。

当前代码里的实际实现是“用户态优先，全局 env 兜底”：

```text
ToolCredentialResolver.resolve(user_id, provider_key)
  -> 如果数据库存在用户凭据，并且启用
       -> 解密并返回用户 key，source = "user"
  -> 如果用户禁用了该凭据
       -> 返回 disabled，source = "user_disabled"
  -> 如果没有用户 key 或为空
       -> 尝试读取环境变量 key，source = "env"
  -> 如果 env 也没有
       -> missing
```

2026-07-02 已进一步收敛边界：env fallback 不再默认开启，必须显式配置：

```env
ALLOW_ENV_TOOL_CREDENTIAL_FALLBACK=true
```

如果该开关为默认值 `false`：

```text
用户没有配置凭据
  -> 即使 backend/.env 存在 TAVILY_API_KEY / AMAP_API_KEY / MINERU_API_TOKEN
  -> ToolCredentialResolver 也不会把它作为用户请求的工具凭据
  -> source 返回 missing 或 env_fallback_disabled
```

这样默认行为更符合多用户产品边界：用户自己的外部服务调用应该使用自己的凭据。

对应文件：

- `backend/app/services/tools/credentials.py`
- `backend/app/services/secret_service.py`
- `backend/app/repositories/tool_config_repo.py`
- `backend/app/models/tool_config.py`
- `backend/app/services/knowledge_service.py` 的 MinerU 凭据接口

这意味着当前 `config.py` 里的：

```python
tavily_api_key: str = os.getenv("TAVILY_API_KEY", "")
amap_api_key: str = os.getenv("AMAP_API_KEY", "")
mineru_api_token: str = os.getenv("MINERU_API_TOKEN", "")
```

更准确的定位应该是：

```text
开发/部署级默认凭据，作为兜底 fallback；
不是多用户产品里的首选凭据来源。
```

这个兜底有现实价值：

- 本地开发时可以不进前端设置页，直接通过 `.env` 快速验证工具。
- 单用户私有部署时可以由管理员统一配置默认 key。
- 用户还没配置 key 时，系统可以选择使用默认服务能力。

但它也有风险：

- 如果所有用户都 fallback 到同一个 env key，会混用额度和账单。
- 用户可能误以为自己没配置 key，但实际调用的是服务器默认 key。
- 多用户 SaaS 场景下，全局 key 可能造成权限和成本边界不清。

因此后续读代码或继续优化时，建议遵守这个规则：

```text
用户态凭据是主路径；
全局 env 凭据只能作为显式开启后的开发/管理员默认/fallback；
前端和 Tool Trace 应该显示凭据来源 user/env/missing/disabled；
生产多用户部署应保持 env fallback 关闭。
```

2026-07-02 已处理的 provider 边界：

- `services/tools/providers/tavily.py` 不再直接 fallback 到 `settings.tavily_api_key`。
- `services/tools/providers/amap.py` 不再直接 fallback 到 `settings.amap_api_key`。
- Provider 只使用显式传入的 `api_key` 或实例初始化时传入的 `api_key`。
- 是否允许 fallback env，由 `ToolCredentialResolver` 统一决定。

当前明确后的架构方向是：

```text
Provider 只接收显式传入的 api_key；
是否允许 fallback env，由 ToolCredentialResolver 统一决定；
provider 本身不再直接读取 settings 里的第三方 key。
```

这能让凭据来源集中管理，避免后续工具越来越多时出现“有的工具走用户态，有的工具偷偷走 env”的混乱。

## 16. 第二组源码精读：Auth 认证链路与并发安全

Auth 是最适合练习后端分层阅读的第一条业务链路，因为它短、闭环、边界清楚。它解决的不是“写几个登录接口”，而是建立一条可信身份链路：

```text
用户输入账号密码
  -> 后端验证输入格式
  -> 后端验证身份规则
  -> 数据库保存唯一用户身份
  -> 密码只保存不可逆 hash
  -> 后端签发可校验、可过期的 token
  -> 后续请求通过 token 找回当前用户
```

涉及文件：

| 层 | 文件 | 责任 |
| --- | --- | --- |
| Router | `backend/app/api/routes/auth.py` | 定义 `/api/auth/register`、`/api/auth/login`、`/api/auth/me` |
| Schema | `backend/app/schemas/auth.py` | 定义注册/登录入参和 token/user 出参 |
| Service | `backend/app/services/auth_service.py` | 注册、登录、密码 hash、JWT 生成、事务提交/回滚 |
| Repository | `backend/app/repositories/user_repo.py` | 封装 `users` 表查询和写入 |
| Model | `backend/app/models/user.py` | 描述 `users` 表字段、唯一索引、ORM 关系 |
| Dependency | `backend/app/api/deps.py` | 从 Bearer Token 解析当前用户 |
| Config | `backend/app/core/config.py` | 提供 `AUTH_SECRET_KEY`、token 过期时间等配置 |
| Startup | `backend/app/core/startup.py` | 启动时补齐 `users` 表唯一索引 |
| Test | `backend/tests/test_auth_service.py` | 覆盖注册、登录、邮箱格式、重复注册等核心行为 |

### 16.1 Auth 分层边界

当前 Auth 链路遵循这条分层：

```text
HTTP 请求
  -> Router
  -> Schema
  -> Service
  -> Repository
  -> Model / Database
```

每层边界如下：

| 层 | 应该做 | 不应该做 |
| --- | --- | --- |
| Router | 定义路由、依赖注入、调用 Service | 不直接校验密码、不直接生成 JWT、不直接写 SQL |
| Schema | 校验入参/出参的数据契约 | 不查数据库、不做业务去重 |
| Service | 处理业务规则、事务边界、异常转换 | 不写复杂 SQL 细节 |
| Repository | 封装数据库查询和写入动作 | 不决定注册是否成功、不决定 HTTP 状态码 |
| Model | 描述表结构和约束 | 不处理业务流程 |
| Database | 保证最终一致性 | 不负责用户友好错误文案 |

### 16.2 注册链路

```text
POST /api/auth/register
  -> routes/auth.py::register(payload, db)
  -> UserRegisterRequest 做邮箱格式和基础字段校验
  -> AuthService(UserRepository(db)).register_user(payload)
  -> UserRepository.find_existing_identity(email, username)
  -> bcrypt 生成 password_hash
  -> UserRepository.create(user)
  -> db.commit()
  -> AuthService.create_access_token(created)
  -> TokenResponse 返回 access_token + user
```

第一性原理看，注册本质上做三件事：

- 建立用户身份记录。
- 把明文密码转换成不可逆 hash 后保存。
- 生成 token，让用户注册后直接处于登录状态。

当前注册步骤：

1. Router 接收请求体 `UserRegisterRequest`。
2. Schema 用 `EmailStr` 校验邮箱格式，用 `Field` 校验用户名和密码长度。
3. Service 先查邮箱/用户名是否已存在，给普通重复注册提供友好错误。
4. Service 用 bcrypt 把明文密码转换成 `password_hash`。
5. Repository 把 `User` 加入 SQLAlchemy Session，并执行 `flush()`。
6. Service 执行 `commit()`，提交注册事务。
7. 数据库唯一索引兜住并发重复注册。
8. 如果提交成功，Service 生成 JWT token。
9. 返回 `TokenResponse`，包含 `access_token` 和当前用户信息。

### 16.3 登录链路

```text
POST /api/auth/login
  -> routes/auth.py::login(payload, db)
  -> UserLoginRequest 做基础字段校验
  -> AuthService.login_user(payload)
  -> UserRepository.get_by_email(email)
  -> bcrypt.checkpw(password, password_hash)
  -> AuthService.create_access_token(user)
  -> TokenResponse 返回 access_token + user
```

登录链路的安全点：

- 先按 email 找用户。
- 用户不存在或密码为空时，统一返回 `Invalid email or password`。
- 密码错误时，也返回同一个错误。
- 不区分“邮箱不存在”和“密码错误”，避免暴露账号是否存在。

登录失败统一返回：

```text
401 Invalid email or password
```

这样做的安全原因是：不向攻击者暴露“邮箱是否存在”。

### 16.4 当前用户 `/me` 链路

```text
GET /api/auth/me
  -> Depends(get_current_user)
  -> HTTPBearer 从 Authorization Header 取 token
  -> jwt.decode 校验签名、算法、过期时间
  -> payload["sub"] 取 user_id
  -> UserRepository.get_by_id(user_id)
  -> UserResponse.model_validate(current_user)
```

`get_current_user()` 做的事情：

- 如果没有 token，返回 401。
- 如果 token 无效、过期、签名不对，返回 401。
- 如果 token payload 里没有 `sub`，返回 401。
- 如果数据库里找不到 `sub` 对应用户，返回 401。
- 校验通过后，返回当前 `User` ORM 对象。

这说明后端不是只信 token 本身，还会重新查数据库确认用户仍然存在。

### 16.5 密码安全

注册时不会保存明文密码。

当前代码使用 bcrypt：

```python
bcrypt.hashpw(password.encode("utf-8"), bcrypt.gensalt())
```

核心点：

- `gensalt()` 会为每个密码生成独立 salt。
- 同一个密码每次生成的 hash 也不同。
- 数据库只保存 `password_hash`。
- 不需要单独保存 salt，因为 bcrypt hash 里已经包含 salt 和成本参数。

登录校验：

```python
bcrypt.checkpw(password.encode("utf-8"), password_hash.encode("utf-8"))
```

这里会用数据库里的 hash 自带的 salt 和成本参数重新计算并比较。

### 16.6 JWT token

`auth_service.py` 里生成 token 的 payload：

```python
payload = {
    "sub": user.id,
    "email": user.email,
    "exp": expire_at,
}
```

含义：

- `sub`：subject，表示 token 代表的主体，这里是用户主键。
- `email`：冗余用户邮箱，方便调试或后续扩展。
- `exp`：过期时间，PyJWT 解码时会自动校验。

真正鉴权依赖的是：

```text
payload["sub"] -> UserRepository.get_by_id(user_id)
```

也就是说，后端不会只凭 token 里的 email 判断用户身份。

#### 16.6.1 `AUTH_SECRET_KEY` 边界

`AUTH_SECRET_KEY` 是 JWT 签发和验证的根密钥。

如果它变化：

```text
旧 token 无法再通过 jwt.decode()
用户需要重新登录
```

这是预期安全边界，不是 bug。密钥泄露或主动轮换时，让旧 token 失效是合理行为。

部署时要注意：

- 生产环境不能使用默认 `AUTH_SECRET_KEY`。
- 多实例部署时，所有实例必须使用同一个 `AUTH_SECRET_KEY`，否则 A 实例签发的 token 可能无法被 B 实例验证。
- 如果要做平滑密钥轮换，后续可以引入 `kid` 和多密钥验证策略。

### 16.7 并发重复注册问题

注册最大的并发风险是：

```text
两个请求同时注册同一个 email 或 username
```

如果只靠 Service 先查重，会出现竞态：

```text
T1: 请求 A 查询 email，不存在
T2: 请求 B 查询 email，不存在
T3: 请求 A 插入成功
T4: 请求 B 也尝试插入
```

所以第一性原理结论是：

```text
Service 层查重只能优化体验；
最终一致性必须由数据库唯一约束保证。
```

当前解决方案是三层。

第一层是 Service 先查重。普通重复注册会提前返回友好错误：

```text
409 Username or email already exists
```

第二层是数据库唯一索引兜底。`models/user.py` 里定义：

```python
Index("ux_users_email_lower", func.lower(User.email), unique=True)
Index("ux_users_username_lower", func.lower(User.username), unique=True)
```

含义：

```text
lower(email) 唯一
lower(username) 唯一
```

这样这些会被认为是同一个邮箱：

```text
tester@example.com
TESTER@example.com
Tester@Example.com
```

第三层是捕获 `IntegrityError`。如果两个请求并发通过 Service 查重，第二个请求在数据库写入时会触发唯一索引冲突：

```python
except IntegrityError as exc:
    self.repo.db.rollback()
    raise HTTPException(
        status_code=status.HTTP_409_CONFLICT,
        detail="Username or email already exists",
    ) from exc
```

作用：

- 不让数据库异常变成 500。
- 回滚失败事务，让 Session 回到可用状态。
- 对前端稳定返回 409。

### 16.8 事务边界

之前的问题：

```text
UserRepository.create() 自己 commit()
```

这在简单创建用户时能工作，但长期不利于复杂业务。Repository 不知道完整业务用例，未来注册可能需要：

- 创建默认用户设置。
- 创建默认工作区。
- 写审计日志。
- 初始化欢迎会话。

如果 Repository 创建用户时已经提前 commit，后续步骤失败就会出现半成功状态。

现在调整为：

```text
Repository.create()
  -> add
  -> flush
  -> refresh

AuthService.register_user()
  -> commit 或 rollback
```

边界更清楚：

```text
Repository 管数据库动作
```

### 16.10 当前已解决的问题

2026-07-02 已完成的 auth 收敛：

- `schemas/auth.py` 的 `email` 已改为 Pydantic `EmailStr`，在 API 边界层直接拒绝明显非法邮箱格式。
- `models/user.py` 已增加 `lower(email)` / `lower(username)` 唯一索引，`core/startup.py` 启动时也会补齐 PostgreSQL 表达式唯一索引。
- `UserRepository.create()` 不再提交事务，只负责 `add/flush/refresh`，注册链路由 `AuthService.register_user()` 统一 `commit/rollback`。
- `AuthService.register_user()` 捕获数据库 `IntegrityError`，把并发重复注册转成稳定的 `409 Username or email already exists`。
- `AUTH_SECRET_KEY` 变更会让旧 token 全部失效，这一点已在 token 生成处注释说明，作为密钥轮换的预期安全边界。

这些优化背后的第一性原理：

- 格式问题在系统边界解决：非法邮箱不应该进入业务层。
- 最终一致性由数据库兜底：Service 层查重提供友好错误，但不能替代唯一索引。
- 事务边界跟业务用例走：注册是一个业务用例，因此由 `AuthService` 决定何时提交或回滚。
- 安全边界要显式：`AUTH_SECRET_KEY` 是签发和验证 token 的根密钥，轮换必然影响旧 token。

## 17. 第三组源码精读：Settings 用户设置链路

Auth 解决“谁在使用系统”，Settings 解决“这个用户以什么配置使用系统”。它是 Chat、Tool、RAG 的共同前置依赖。

从第一性原理看，Settings 链路解决的是：

```text
用户身份 user_id
  -> 找到或创建用户设置
  -> 保存模型/上下文/知识库/外观等偏好
  -> 加密保存用户级密钥
  -> 响应时只返回掩码和是否已配置
  -> 下游 Chat/RAG/Tool 按 user_id 读取配置
```

### 17.1 相关源码文件

| 层 | 文件 | 责任 |
| --- | --- | --- |
| Router | `backend/app/api/routes/settings.py` | 定义设置读取、更新、模型连接测试、知识库模型候选接口 |
| Schema | `backend/app/schemas/setting.py` | 定义设置入参/出参，控制哪些字段可更新、哪些字段可返回 |
| Service | `backend/app/services/setting_service.py` | 默认值、历史兼容、归一化、密钥加密、响应脱敏 |
| Repository | `backend/app/repositories/setting_repo.py` | 查询和保存 `user_settings` |
| Model | `backend/app/models/user_setting.py` | 描述用户设置表字段和 `user_id` 唯一关系 |
| Secret | `backend/app/services/secret_service.py` | 对用户级密钥加密、解密、掩码展示 |
| Provider | `backend/app/services/chat_provider_service.py` | 测试问答模型服务、获取模型列表 |
| Knowledge Catalog | `backend/app/services/knowledge_model_catalog_service.py` | 获取 embedding/rerank 候选模型 |

### 17.2 Settings 与 Config 的边界

这里最容易混淆的是 `config.py` 和 `user_settings`。

边界如下：

| 类型 | 例子 | 生命周期 | 所属 |
| --- | --- | --- | --- |
| 进程级配置 | 数据库地址、默认 Ollama URL、上传目录、JWT 密钥 | 后端启动时确定 | 系统全局 |
| 用户级设置 | 默认模型、API base URL、上下文窗口、知识库模型、主题 | 用户可修改 | 单个 user |
| 用户级密钥 | 问答模型 API key、embedding key、rerank key | 用户可修改且加密保存 | 单个 user |

第一性原理判断：

```text
config.py 决定后端进程怎么运行；
user_settings 决定某个用户的业务行为怎么运行。
```

### 17.3 读取设置链路

入口：

```text
GET /api/settings
```

代码链路：

```text
routes/settings.py::get_settings()
  -> Depends(get_current_user)
  -> SettingService.get_or_create_user_settings(current_user.id)
  -> UserSettingRepository.get_by_user(user_id)
  -> 不存在则 _build_default_setting(user_id)
  -> repo.save(setting)
  -> _to_response(setting)
```

读取设置不是简单查询。当前 `get_or_create_user_settings()` 同时承担：

- 新用户第一次进入时创建完整默认配置。
- 老用户历史字段缺失时补默认值。
- 旧版本把 API base URL 错放在 `ollama_base_url` 时做兼容迁移。
- 修正上下文窗口、context mode、主题、记忆、知识库模型等字段。
- 响应前做密钥脱敏。

因此这个方法是 Settings 链路的核心复杂点。

### 17.4 更新设置链路

入口：

```text
PATCH /api/settings
```

代码链路：

```text
routes/settings.py::update_settings()
  -> UserSettingUpdate
  -> SettingService.update_user_settings(user_id, payload)
  -> payload.model_dump(exclude_unset=True)
  -> 普通字段 trim / normalize
  -> 密钥字段跳过普通 setattr
  -> 密钥字段按 clear_* 或 encrypt() 单独处理
  -> 归一化 provider/context/theme/knowledge 字段
  -> repo.save(setting)
  -> _to_response(setting)
```

关键点：`exclude_unset=True` 很重要。

它让 PATCH 语义成立：

```text
字段没传
  -> 不更新

字段传了 null 或空字符串
  -> service 决定如何归一化

clear_api_key = true
  -> 明确清空密钥
```

### 17.5 密钥字段处理

Settings 中有多类密钥：

- `api_key`：问答模型 API key。
- `knowledge_embedding_api_key`：embedding 专用 key。
- `knowledge_rerank_api_key`：rerank 专用 key。

Service 更新时不会让这些字段走普通：

```python
setattr(setting, key, value)
```

而是单独处理：

```text
clear_xxx_api_key = true
  -> 设置为 None

xxx_api_key 有新值
  -> SecretService.encrypt()
```

响应时 `_to_response()` 只返回：

```text
api_key = None
has_api_key = true/false
api_key_masked = xxxx****yyyy
```

不会返回明文。

### 17.6 SecretService

`SecretService` 负责：

- `encrypt(value)`：加密用户级密钥。
- `decrypt(value)`：解密密钥供后端调用模型或工具。
- `mask(value)`：生成前端展示用掩码。

加密密钥来源：

```text
SECRET_ENCRYPTION_KEY
  -> 生产环境必须显式配置
  -> 开发环境未配置时才 fallback 到 AUTH_SECRET_KEY
```

阅读这个文件时要注意：

- 专用 `SECRET_ENCRYPTION_KEY` 是生产环境必需项。
- fallback 到 `AUTH_SECRET_KEY` 只允许用于开发环境兼容。
- 如果加密密钥变化，旧密文可能无法解密。
- `decrypt()` 对没有 `enc::` 前缀的值直接返回，是为了兼容历史明文行。

### 17.7 模型连接测试

问答模型连接测试入口：

```text
POST /api/settings/test-provider
```

它的语义是“临时测试”，不是“保存设置”。

代码逻辑：

```text
前端传 provider_type / base_url / api_key
  -> 如果本次没传 api_key，则读取已保存用户 key
  -> ChatProviderService.list_models()
  -> 返回模型列表和默认模型候选
```

这里体现了一个重要边界：

```text
测试连接可以使用临时输入；
真正保存配置必须走 PATCH /settings。
```

### 17.8 知识库模型候选

知识库模型候选入口：

```text
POST /api/settings/knowledge-model-options
```

它服务两类模型：

- `embedding`
- `rerank`

关键逻辑：

```text
model_kind = embedding
  -> 优先使用 knowledge_embedding_api_key
  -> 没有则视为未配置 embedding key

model_kind = rerank
  -> 优先使用 knowledge_rerank_api_key
  -> 没有则视为未配置 rerank key
```

2026-07-03 已移除知识库通用 key，只保留 embedding/rerank 两个专用 key。这样配置语义更清晰：

```text

rerank 调用只看 rerank key；
不存在“通用 key 隐式兜底”。
```

### 17.9 当前审查结论

当前 Settings 链路整体边界是清楚的：

- Router 只做入口和调用 service。
- Schema 定义可更新字段和响应字段。
- Service 负责默认值、兼容、归一化、加密、脱敏。
- Repository 保持很薄。
- Model 字段完整，覆盖问答、上下文、记忆、UI、知识库模型配置。
- 密钥明文不会通过响应返回前端。

当前值得注意的风险：

- `SettingService` 已经比较大，后续可以按“问答模型设置 / 知识库模型设置 / UI 与上下文设置 / 密钥处理”拆分内部 helper。

2026-07-03 已完成的 Settings 收敛：

- 移除 `knowledge_api_key` 通用 key，只保留 `knowledge_embedding_api_key` 和 `knowledge_rerank_api_key` 两个专用 key。
- `get_or_create_user_settings()` 首次并发创建同一个用户设置时，会捕获 `IntegrityError`，回滚后重新读取已创建记录。
- `UserSettingRepository.save()` 不再提交事务，只做 `add/flush/refresh`；`SettingService` 负责 `commit/rollback`。
- `SecretService` 在生产环境中要求显式配置 `SECRET_ENCRYPTION_KEY`，开发环境才允许 fallback 到 `AUTH_SECRET_KEY`。
- 清理了 `SettingService` 中重复的默认字段赋值，并把保存逻辑收敛到 `_save_setting()`。

当前阶段建议先理解链路，不急着重构。下一步如果继续审阅，可以看 `Conversation / Message`，因为它们是 Chat 主链路的数据基础。

## 18. 第四组源码精读：Conversation / Message 会话与消息链路

这组文件是 Chat 主链路的数据地基。第一性原理上，聊天系统最核心的持久化事实只有两个：

- `Conversation`：一次长期会话的容器，归属于某个用户，可归属某个工作区。
- `Message`：会话中的一条历史消息，本身不直接保存 `user_id`，通过 `conversation_id` 间接归属用户。

因此这组代码的关键不是“怎么展示聊天记录”，而是：

```text
用户是否拥有 conversation
  -> 用户是否能读写该 conversation 下的 messages
  -> 删除/导出/重生成/RAG 来源定位是否都守住这条边界
```

### 18.1 本轮阅读文件

本轮按分层阅读这些文件：

```text
models/conversation.py
models/message.py

schemas/conversation.py
schemas/message.py

repositories/conversation_repo.py
repositories/message_repo.py

services/conversation_service.py
services/message_service.py

api/routes/conversations.py
api/routes/messages.py
```

阅读顺序要先看 `models`，因为数据库模型决定真实数据结构；再看 `repositories`，因为它决定查询边界；再看 `services`，因为它表达业务规则；最后看 `routes`，确认 HTTP 入口是否做了用户归属和参数校验。

### 18.2 Conversation 模型：会话是聚合根

`Conversation` 表的核心字段：

- `id`：会话主键。
- `user_id`：会话所属用户。正常登录态创建的会话都应该有 `user_id`。
- `project_id`：会话所属工作区。它只是组织关系，不替代 `user_id` 权限判断。
- `title`：会话标题。
- `model_name`：当前会话默认模型。
- `system_prompt`：当前会话系统提示。
- `context_summary`：上下文治理生成的滚动摘要。
- `context_summary_boundary_message_id`：摘要覆盖到哪条消息为止。
- `last_prompt_prefix_hash` / `last_prompt_prefix_token_count`：prompt prefix 缓存/观测字段。
- `is_pinned` / `is_archived`：会话列表展示状态。

关键设计点：

```text
Conversation 是聚合根；
Message、Attachment、Share 都从属于 Conversation；
用户权限必须先证明 current_user 拥有 Conversation。
```

`Conversation.messages` 设置了 `cascade="all, delete-orphan"`，所以删除会话会级联删除消息。`Message.attachments` 也有级联关系，所以删除消息会删除附件元数据。

这带来一个重要后果：

```text
删除 Conversation 前，要先处理不受 ORM cascade 管控的外部引用。
```

例如 RAG 检索日志 `KnowledgeRetrievalLog` 会引用 `conversation_id/user_message_id/assistant_message_id`，所以 `ConversationService.delete_conversation()` 会先调用 `detach_conversation_links()`，再删除会话。

### 18.3 Message 模型：消息没有 user_id

`Message` 表的核心字段：

- `id`：消息主键。
- `conversation_id`：消息所属会话。
- `sequence`：会话内显式消息顺序。
- `role`：消息角色，可能是 `user`、`assistant`、`system`。
- `content`：消息正文。
- `reasoning_content`：深度思考过程。
- `external_sources`：工具调用/联网搜索/RAG 等外部来源信息，目前以文本字段保存。
- `status`：消息状态，例如 `done`、`streaming`、`failed`、`stopped`。

最重要的不变量：

```text
Message 不存 user_id；
公开 API 不能只凭 message_id 操作消息；
必须先校验 conversation_id 属于 current_user。
```

2026-07-03 对抗性审查补充：

```text
created_at 受数据库时间精度影响；
同一秒/同一时间戳内创建 user + assistant 消息时，只靠 created_at 不足以稳定判断最后一轮；
随机 UUID id 也不能当顺序字段，因为它不代表创建时间。
```

因此 `messages` 增加了 `sequence` 字段，由 `MessageRepository.create()/save()` 在新消息写入时分配会话内递增序号。当前排序仍以 `created_at` 为第一顺序，`sequence` 作为同时间戳内的显式顺序补充。

注意：当前 `sequence` 是应用层分配，正常单请求写入路径足够；如果未来允许同一会话多请求并发写消息，需要数据库唯一约束或行锁进一步保证强一致。

这就是为什么消息路由里每个接口第一步都要：

```text
ConversationRepository.get_by_user(conversation_id, current_user.id)
```

然后再操作该会话下的消息。

### 18.4 Schema：外部 API 契约必须小于内部模型

`ConversationCreate` 允许外部传：

- `title`
- `model_name`
- `system_prompt`
- `project_id`

其中 `project_id` 必须确认属于当前用户。2026-07-03 已把这条不变量下沉到 `ConversationService`，创建会话和移动会话都会统一检查 project ownership。

2026-07-03 对抗性审查补充：

```text
title / model_name 会在 schema 层 strip；
创建会话时 title/model_name 不能为空；
更新会话时 title 如果传入，也不能为空；
system_prompt/project_id 的空字符串会归一为 None。
```

原因是 HTTP 输入不可信。标题和模型名是后续列表展示、模型调用和审计定位的基础字段，不应该允许纯空白字符串进入数据库。

`ConversationUpdate` 现在只允许修改用户可编辑字段：

- `title`
- `system_prompt`
- `is_archived`
- `is_pinned`
- `project_id`

本轮已把 `context_summary` 从 `ConversationUpdate` 移除，并设置 `extra="forbid"`。原因是：

```text
context_summary 是上下文治理内部状态；
如果暴露给普通 PATCH，会让客户端能够篡改 prompt 记忆边界；
即使 service 暂时不处理它，也不应该让 API 静默接受这个字段。
```

`MessageCreate` 现在只允许公开接口创建 `role="user"` 的消息。原因是：

```text
role 会被 prompt builder 原样交给模型；
如果外部 API 能伪造 assistant/system 消息，就可能污染后续对话历史；
assistant/system 消息应该只能由聊天编排内部创建。
```

内部仍然可以通过 `MessageService.create_system_message()` 创建 `user/assistant/system` 等可信消息。这里函数名里的 `system` 表示“系统内部可信调用”，不是固定创建 `role=system`。

2026-07-03 对抗性审查补充：

```text
MessageCreate.content / ChatStreamRequest.content / ChatEditLastUserRequest.content
  -> strip
  -> 不允许为空
  -> 最大 200000 字符

MessageBulkDeleteRequest.message_ids
  -> 单个 ID 最大 64 字符
  -> 一次最多 200 个
```

原因是公开 API 不应该允许空消息、纯空白消息或无限大的批量操作直接进入 service/repo。

### 18.5 ConversationRepository：会话查询边界

`ConversationRepository` 的核心方法：

```text
list_by_user(user_id)
get_by_user(conversation_id, user_id)
create(conversation)
save(conversation)
update_context_summary(conversation_id, ...)
touch(conversation_id)
delete(conversation)
```

最关键的方法是：

```text
get_by_user(conversation_id, user_id)
```

它同时匹配 `conversation_id` 和 `user_id`，这是会话域的权限闸门。

`list_by_user()` 当前排序规则：

```text
is_pinned desc
updated_at desc
created_at desc
id desc
```

这解释了为什么置顶会话排前面，最近更新的会话排在未置顶列表前面。

2026-07-03 对抗性审查补充：

- `list_by_user()` 支持 `limit/offset`，HTTP 入口允许 `limit<=200`。前端当前仍可不传分页参数保持原行为，后续可以逐步接入无限滚动或分页加载。
- 排序最后追加 `id desc` 作为确定性兜底，避免多个会话时间戳完全相同时 offset 分页跨页抖动。

当前值得注意的点：

- `create()` / `save()` 仍然由 repository 自己 `commit()`。简单 CRUD 可以接受，但聊天主链路这种多对象写入后续更适合把事务边界上移。
- `update_context_summary()` 使用 `db.get(Conversation, conversation_id)`，不校验 `user_id`。目前它是上下文治理内部方法，不能直接暴露为公开 API；如果未来暴露，必须改成 `conversation_id + user_id` 双条件。

### 18.6 MessageRepository：消息查询边界

`MessageRepository` 的核心方法：

```text
list_by_conversation(conversation_id)
create(message)
save(message)
get_by_id_and_conversation(message_id, conversation_id)
mark_stale_streaming_messages(conversation_id)
delete(message)
bulk_delete(conversation_id, message_ids)
delete_by_conversation(conversation_id)
```

最关键的方法是：

```text
get_by_id_and_conversation(message_id, conversation_id)
```

它避免只凭 `message_id` 删除或读取消息。

`bulk_delete()` 也会按 `conversation_id` 过滤，所以即使客户端传了其他会话的 `message_id`，也不会删掉。

2026-07-03 阻断级问题修复：

- 批量删除前，`MessageService.bulk_delete_messages()` 会先通过 `MessageRepository.list_by_ids_and_conversation()` 取得真实属于当前会话的消息。
- RAG 检索日志断链只使用这批 scoped message ids。
- 这样可以防止客户端夹带其他会话的 message_id，导致其他会话消息虽然没被删除，但来源定位里的 `user_message_id/assistant_message_id` 被误清空。

`mark_stale_streaming_messages()` 是一个 UI 恢复机制：

```text
如果 assistant 消息 status=streaming；
并且 15 分钟没有更新；
读取消息列表时把它标记为 failed。
```

这是为了解决服务重启、浏览器切会话、流式请求中断后，前端一直显示“模型正在思考”的问题。

当前值得注意的点：

- `list_by_conversation()` 现在按 `created_at + sequence` 排序。正常写入路径下可以稳定区分同时间戳内的 user/assistant 顺序；高并发同会话写入仍需要后续数据库级约束。
- `create()` / `save()` 每次都 `commit()`。流式生成过程中 assistant 消息会多次保存，提交频率是后续性能优化点。

### 18.7 ConversationService：会话业务规则

`ConversationService` 负责：

- 列出当前用户会话。
- 获取当前用户某个会话。
- 创建会话。
- 更新标题、系统提示、归档、置顶、工作区归属。
- 删除会话。

关键边界：

```text
ConversationService 通过 repo.get_by_user() 保证会话属于当前用户。
```

本轮审查发现并修正了一个边界分散点：

```text
旧逻辑：
  create_conversation() 默认信任 payload.project_id 已经在 route 层校验；
  update_conversation() 移动会话到 project_id 时没有统一校验 project 归属。
```

风险是：

```text
用户可以把自己的 conversation.project_id 指向其他用户的 project.id；
这不会直接读取对方项目内容，但会造成跨用户数据关联污染；
后续按 project 统计、筛选、清理时可能引入隐性问题。
```

修正后：

```text
ConversationService 接收 ProjectRepository；
create_conversation() 校验 project_id 属于当前用户；
update_conversation() 移动 project_id 时同样校验；
project_id=None 允许，表示移出工作区。
```

删除会话时：

```text
detach_conversation_links()
  -> delete(conversation)
```

2026-07-03 对抗性审查已修正：删除会话时，RAG 检索日志断链和 conversation 删除会在同一个 service 事务中提交；失败会 rollback，避免只完成其中一半。

### 18.8 MessageService：消息业务规则

`MessageService` 负责：

- 列出消息。
- 创建公开 user 消息。
- 创建内部可信消息。
- 保存消息。
- 挂载上传附件。
- 替换上传附件。
- 删除消息前断开 RAG 日志引用。
- 序列化消息和附件。

关键边界：

```text
MessageService 默认调用者已经校验过 conversation 属于 current_user。
```

这意味着 route 层漏掉会话归属校验就会很危险。当前 `api/routes/messages.py` 已经在每个入口先校验 `ConversationRepository.get_by_user()`。

附件挂载逻辑有一个安全收口：

```text
storage_key 必须以 "{user_id}/" 开头；
否则不会被挂到消息上。
```

这能防止用户把别人的上传文件通过 storage_key 挂载到自己的消息里。

`_build_storage_key()` 会把本地绝对路径转换成相对 `upload_dir` 的 key；如果解析失败就返回空字符串，避免响应里泄露任意本地路径。

### 18.9 Routes：HTTP 入口和越权检查

`api/routes/conversations.py` 负责：

- `GET /conversations`
- `POST /conversations`
- `GET /conversations/{conversation_id}`
- `GET /conversations/{conversation_id}/export`
- `PATCH /conversations/{conversation_id}`
- `DELETE /conversations/{conversation_id}`

重要检查：

- 创建会话时，如果传 `project_id`，先确认 project 属于当前用户。
- 导出会话时，先确认 conversation 属于当前用户，再读取消息。
- 更新/删除会话时，通过 service 内部的 `get_by_user()` 收口。

2026-07-03 对抗性审查补充：

- `export_conversation.message_ids` 增加 query 长度上限。
- `_parse_requested_message_ids()` 会限制最多导出 200 条指定消息。
- 单个 message id 最大 64 字符，非法时返回 400。

这个限制不是分页优化，而是输入边界保护：导出接口需要允许选择消息，但不能允许客户端构造极大的 query 字符串或超大 ID 集合拖垮解析和过滤。

`api/routes/messages.py` 负责：

- `GET /conversations/{conversation_id}/messages`
- `POST /conversations/{conversation_id}/messages`
- `DELETE /conversations/{conversation_id}/messages/{message_id}`
- `POST /conversations/{conversation_id}/messages/bulk-delete`

每个消息接口第一步都做：

```text
ConversationRepository(db).get_by_user(conversation_id, current_user.id)
```

这是因为 `Message` 没有 `user_id`。

### 18.10 本轮对抗性审查结论

本轮已修正：

- `ConversationUpdate` 不再暴露 `context_summary`，并设置 `extra="forbid"`，防止客户端静默传入内部上下文字段。
- `MessageCreate` 不再允许公开接口伪造 `assistant/system` 消息，只允许创建 `user` 消息。
- `ConversationService` 统一校验 `project_id` 归属，防止创建/移动会话时产生跨用户 project 关联。
- `ConversationCreate/ConversationUpdate` 会 trim 标题、模型名等文本字段，并拒绝空标题。
- `MessageCreate/ChatStreamRequest/ChatEditLastUserRequest` 会 trim 用户内容，并拒绝空消息。
- `MessageBulkDeleteRequest` 和导出 `message_ids` 增加单次数量与单个 ID 长度限制。
- `Message` 增加会话内 `sequence` 字段，由 `MessageRepository` 分配，用于提高最后一轮判断和 prompt 历史顺序稳定性。
- 会话列表后端支持 `limit/offset`，为后续前端分页/无限滚动打基础。
- 删除会话、删除消息、批量删除消息时，RAG 检索日志断链和主对象删除进入同一个 service 事务。
- 删除单条消息时，RAG 日志只断开被删除的那一侧字段；例如删除 assistant message 不再清空仍存在的 user_message_id。
- 批量删除消息时，RAG 日志断链也只作用于当前 conversation 内实际被删除的消息，不再使用客户端原始 message_ids。
- 新增契约测试覆盖这些边界，并验证 `MessageRepository.bulk_delete()` 不会跨 conversation 删除消息、`MessageService.bulk_delete_messages()` 不会跨 conversation 断开 RAG 来源链接。

当前仍值得后续优化：

- `ConversationRepository` 和 `MessageRepository` 仍然默认自己提交事务。当前已对删除会话/消息这类跨表操作做局部事务收口；更彻底的 Unit of Work 可以等更多 service 审完后统一设计。
- 附件物理文件清理不在消息删除链路里，目前只删附件元数据；后续如果要做存储回收，需要设计引用计数或后台清理任务。

### 18.11 下一步建议

这组链路看完后，下一步建议进入 Chat 主链路，但不要直接从大文件开始。

建议顺序：

```text
api/routes/chat.py
  -> chat_turn_bootstrapper.py
  -> chat_context_assembly_service.py
  -> chat_execution_models.py
  -> chat_execution_service.py
  -> chat_provider_service.py
```

原因是：

- `chat_turn_bootstrapper.py` 解释新一轮用户消息和 assistant 占位消息是怎么创建的。
- `chat_context_assembly_service.py` 解释上下文、附件、长期记忆、知识库、工具来源如何组装。
- `chat_execution_service.py` 才是流式执行编排，不先理解前两层会很难读。

## 19. 第五组源码精读：Chat 主链路

Chat 主链路不是单个文件，而是一条分层流水线。第一性原理上，聊天请求要完成五件事：

```text
1. 确认当前用户能在哪个 conversation 里说话
2. 把本轮 user message 和 assistant streaming 占位消息写入数据库
3. 组装模型需要的上下文：历史、摘要、记忆、附件、工具、知识库
4. 调用模型供应商并把增量 token 流式返回给前端
5. 把最终 answer/reasoning/sources/status 持久化到 assistant message
```

对应代码层次：

```text
api/routes/chat.py
  HTTP 入口 + StreamingResponse + 重生成/编辑重答入口

services/chat_execution_service.py
  Chat 主链路门面，连接“落库本轮消息”和“组装上下文”

services/chat_turn_bootstrapper.py
  创建/复用 conversation，写入 user message 和 assistant 占位消息

services/chat_context_assembly_service.py
  组装长期记忆、附件、工具、知识库、滚动摘要、prompt 诊断和上下文预算

services/chat_execution_models.py
  prepare 阶段和 streaming 阶段之间传递的数据对象

services/chat_provider_service.py
  模型供应商适配层，屏蔽 Ollama / OpenAI-compatible 差异
```

### 19.1 `api/routes/chat.py`：HTTP 流式入口

这个文件有三个主要入口：

```text
POST /chat/text-stream
POST /chat/events-stream
POST /chat/regenerate-last-stream
POST /chat/edit-last-user-stream
```

其中 `events-stream` 是当前主路径，返回 NDJSON 事件：

```text
tool_plan / tool_call_start / tool_call_end / tool_sources
reasoning_delta
answer_delta
done
model_error
```

`_build_streaming_response()` 是真正调用模型并写回 assistant message 的位置。它接收的是已经准备好的 `ChatExecutionContext`，所以它不负责创建消息、不负责检索知识库、不负责工具规划，只负责：

```text
for event in provider_service.stream_chat_events(...)
  -> reasoning_delta 写入 reasoning_parts
  -> answer_delta 写入 content_parts
  -> yield 给前端

模型结束
  -> assistant_message.status = done
  -> 保存完整 content/reasoning/sources

客户端取消
  -> assistant_message.status = cancelled
  -> 保存 partial content/reasoning/sources

模型异常
  -> assistant_message.status = failed
  -> 保存 partial content/reasoning/sources
```

2026-07-03 对抗性审查修正：

- 重生成和编辑重答在重新开始流式输出前，会清空旧 `reasoning_content` 和旧 `external_sources`。
- `CancelledError` / 普通异常路径也会保存本轮 `external_sources`，避免旧来源残留或诊断丢失。

### 19.2 重生成和编辑重答的限制

当前后端只支持最后一轮重生成/编辑：

```text
history_rows[-1] 必须是指定 assistant_message
assistant 前面最近的 user_message 必须是指定 user_message
```

原因是中间历史重写会引入复杂问题：

- 中间消息之后的回答是否要全部删除？
- RAG 日志、工具 trace、附件引用如何重算？
- 上下文摘要边界是否要回滚？
- 会话统计和来源定位如何保持一致？

所以当前选择是先支持最后一轮，这是合理的渐进式实现。

### 19.3 `chat_execution_service.py`：主链路门面

`ChatExecutionService` 是 route 和下游服务之间的门面。

它初始化这些依赖：

```text
ConversationRepository
ProjectRepository
MessageRepository
MessageService
SettingService
MemoryService
ToolTraceRepository
ChatTurnBootstrapper
ChatContextAssemblyService
```

两个主方法：

```text
prepare_chat_execution(payload)
  -> 新问题
  -> get_or_create_user_settings
  -> bootstrap_new_turn
  -> build_runtime_config
  -> build_execution_context

prepare_existing_turn_execution(input)
  -> 重生成/编辑重答
  -> apply_turn_overrides
  -> validate attachments
  -> build_runtime_config
  -> build_execution_context
```

注意：

```text
prepare 阶段不调用最终回答模型；
它只是把数据库消息和上下文准备好；
真正调用模型发生在 route 的 StreamingResponse 里。
```

`_build_runtime_config()` 合并了用户设置和会话状态：

- 会话 `model_name` 优先。
- 用户设置提供 `provider_type/base_url/api_key/context_window/context_mode`。
- `ContextBudgetPlanner` 计算上下文预算。
- `TokenizerEstimator` 估算 token。
- `ContextGovernanceService` 负责最终消息预算治理。

### 19.4 `chat_turn_bootstrapper.py`：本轮消息落库

这个文件负责“模型调用前必须先落库”的部分。

新问题流程：

```text
如果 payload.conversation_id 存在
  -> 校验 conversation 属于当前用户

否则
  -> 用 title/content/default settings 创建 conversation

如果 conversation.title == New Chat
  -> 用当前问题生成标题

应用本轮 model/system_prompt 覆盖
校验附件是否能进入上下文
创建 user message，status=done
挂载上传附件
读取 history_rows
创建 assistant message，status=streaming
touch conversation
```

一个细节：

```text
history_rows 包含刚创建的 user message；
不包含刚创建的空 assistant streaming 占位消息。
```

这保证当前用户问题会进入 prompt，但空 assistant 占位不会被发给模型。

### 19.5 `chat_context_assembly_service.py`：上下文组装

这是 Chat 链路里最重要也最复杂的一层。它不创建消息，不调用最终回答模型，而是把上下文来源汇总成最终 prompt。

顺序大致是：

```text
build_memory_context
  -> 长期记忆

AttachmentContextService.build_context
  -> 当前轮附件片段

ExternalContextService.build_context
  -> 工具/联网/地图/天气等外部上下文
  -> 写 Tool Trace

KnowledgeContextService.build_context
  -> 知识库检索片段
  -> RAG retrieval log 绑定 user/assistant message

_refresh_context_summary
  -> 必要时刷新滚动摘要

ContextPromptBuilder.build_chat_messages
  -> 合并系统提示、记忆、摘要、外部来源、知识库、附件、最近历史

ContextGovernanceService.govern_messages
  -> 根据上下文预算截断/治理

_build_prompt_diagnostics
  -> prompt prefix hash / token 观测
```

这层的第一性原则是：

```text
上下文不是越多越好；
上下文必须可解释、可预算、可追踪来源、可被截断。
```

因此它不仅返回 `history_messages`，还返回：

- `context_notices`
- `context_stats`
- `context_details`
- `tool_events`
- `external_sources`
- `context_summary`

这些信息会被前端上下文面板、Tool Trace、来源卡片使用。

### 19.6 `chat_execution_models.py`：阶段交接对象

这里的 dataclass 不是数据库模型，也不是 API schema，而是内部流程对象。

最重要的是 `ChatExecutionContext`：

```text
prepare 阶段输出 ChatExecutionContext；
streaming 阶段消费 ChatExecutionContext。
```

它包含：

- 会话和消息对象。
- provider/model/base_url/api_key。
- 已治理后的 `history_messages`。
- 温度、top_p、max_tokens。
- 上下文统计和诊断。
- thinking 配置。
- tool events 和 external sources。

这个对象的存在让 route 不需要知道上下文是怎么组装的。

### 19.7 `chat_provider_service.py`：模型供应商适配

这一层只和模型服务通信，不应该知道用户权限、会话、RAG、工具或上下文治理。

它统一输出：

```text
ChatStreamEvent(type="reasoning_delta", text="...")
ChatStreamEvent(type="answer_delta", text="...")
```

Ollama 和 OpenAI-compatible 的差异都在这里消化。

深度思考字段不是标准 OpenAI 字段，所以 `_build_openai_extra_body()` 只对已知兼容服务或模型附加：

```text
enable_thinking
thinking_budget
```

当前识别条件包括：

- `siliconflow`
- `qwen3`
- `qwen/qwen3`
- `deepseek-r1`

这部分后续如果接更多供应商，应该继续保持在 Provider Adapter 层，不要散落到 route 或 ChatExecutionService。

### 19.8 本轮对抗性审查结论

本轮已修正：

- 新会话创建路径中，`ChatExecutionService` 会把 `ProjectRepository` 传入 `ChatTurnBootstrapper`，保持 project ownership 校验边界一致。
- 重生成/编辑重答开始前会清空旧 `reasoning_content` 和旧 `external_sources`。
- 流式取消/异常时会保存本轮 `external_sources`，避免旧来源残留或诊断丢失。
- `MessageRepository` 会为新消息分配会话内递增 `sequence`，降低最后一轮判断依赖时间戳精度的风险。
- 删除会话/消息涉及 RAG 检索日志断链时，已做局部事务收口，避免断链和删除只成功一半。
- 删除单条消息时，RAG 日志只断开被删除的字段，不再无差别清空 user/assistant 两侧链接。
- 批量删除消息时，RAG 日志断链先按 conversation 过滤实际消息，再执行断链，避免恶意或异常请求夹带其他会话 message_id 造成来源定位损坏。

当前仍值得后续审查：

- `api/routes/chat.py` 仍承担了较多 streaming 状态保存逻辑，后续可考虑拆出 `ChatStreamingPersistenceService`。
- `ChatContextAssemblyService` 仍然偏复杂，但它目前是“上下文总装层”，不建议在没看完 PromptBuilder / KnowledgeContext / ExternalContext 前继续拆。
- 重生成/编辑重答只支持最后一轮，这是当前合理约束；如果未来支持中间消息编辑，需要同时设计消息截断、RAG 日志、工具 trace、上下文摘要回滚。
- `apply_turn_overrides()` 会持久化单轮传入的 system_prompt/model_name，它不是临时 override。这个产品语义后续需要确认。
- `Message.sequence` 当前由应用层分配。正常单请求写入足够；如果未来允许同一会话并发生成，需要数据库约束或锁。

### 19.9 多角度审查：性能、并行、可维护性

从性能角度看，`ChatContextAssemblyService.build_execution_context()` 当前按顺序执行：

```text
memory
attachment
external tools
knowledge retrieval
summary refresh
prompt build
governance
diagnostics
```

这里不是所有步骤都必须串行。

理论上可以并行的部分：

- `build_memory_context()`：只读用户记忆。
- `AttachmentContextService.build_context()`：只处理当前轮附件。
- `ExternalContextService.build_context()`：工具/联网调用。
- `KnowledgeContextService.build_context()`：知识库检索。

必须串行或半串行的部分：

- RAG retrieval log 绑定必须等知识库检索完成，并且需要本轮 user/assistant message id。
- Tool Trace 持久化必须等外部工具规划/调用完成。
- 滚动摘要刷新依赖 `history_rows` 和上下文治理策略。
- PromptBuilder 必须等 memory/attachment/external/knowledge/summary 都准备好。
- ContextGovernance 必须等 prompt messages 生成后执行。

当前阶段不建议立即并行化，原因是：

```text
并行化会改变异常传播、超时处理、局部失败降级和诊断统计；
工具调用/知识库检索/摘要刷新各自都有副作用或日志绑定；
如果没有更细的测试保护，容易把“更快”换成“不稳定”。
```

更稳的路线：

```text
1. 先把 build_execution_context 拆出更清晰的 Bundle 构造函数。
2. 给 memory/attachment/external/knowledge 分别补失败降级和耗时统计。
3. 再把纯只读、无副作用的步骤并行化。
4. 最后处理有副作用的 tool trace / retrieval log 绑定。
```

从可维护性角度看，下一步可以优先拆：

- `ChatStreamingPersistenceService`：封装 done/cancelled/failed 三种 assistant 落库逻辑。
- `ContextSourceCollector`：收集 memory/attachment/external/knowledge 的来源结果。
- `PromptDiagnosticsService`：封装 prefix hash、token 统计和上下文面板诊断。

这些拆分应该以测试保护为前提，不应该为了“文件短”而拆。

## 20. 第六组源码精读：Prompt / Context Governance

这一组代码回答的是 Chat 系统最核心的问题：

```text
模型最终看到的 messages 到底是什么？
哪些内容是指令，哪些内容只是参考资料？
上下文超预算时，先裁剪谁，最后保留谁？
```

从第一性原理看，LLM 调用前的上下文不是“堆得越多越好”，而是必须同时满足四个约束：

- 权限约束：用户只能看到自己会话、自己知识库、自己工具结果。
- 层级约束：system 指令高于参考资料；参考资料不能反过来改写系统行为。
- 预算约束：prompt 不能超过模型上下文窗口。
- 可解释约束：前端要能看到使用了哪些来源、裁剪了什么、为什么裁剪。

### 20.1 本轮阅读文件

本轮聚焦这几个文件：

```text
services/chat_context_assembly_service.py
services/prompt_builder_service.py
services/context_governance_service.py
services/chat_execution_models.py
```

它们之间的关系：

```text
ChatContextAssemblyService
  -> 收集 memory / attachment / external tools / knowledge / summary
  -> 调 ContextPromptBuilder 生成 prompt messages
  -> 调 ContextGovernanceService 做预算治理
  -> 返回 ChatExecutionContext 给 streaming 层
```

### 20.2 真实请求链路：用户开启知识库提问

以一个真实场景为例：

```text
用户开启知识库，问：介绍一下 SkillRouter
```

在 prepare 阶段，代码大致走：

```text
ChatExecutionService.prepare_chat_execution()
  -> ChatTurnBootstrapper.bootstrap_new_turn()
     -> 创建/获取 conversation
     -> 写入 user message
     -> 创建 assistant streaming 占位消息
  -> ChatContextAssemblyService.build_execution_context()
     -> build_memory_context()
     -> AttachmentContextService.build_context()
     -> ExternalContextService.build_context()
     -> KnowledgeContextService.build_context()
     -> _refresh_context_summary()
     -> ContextPromptBuilder.build_chat_messages()
     -> ContextGovernanceService.govern_messages()
     -> 返回 ChatExecutionContext
```

真正发给模型的是：

```text
ChatExecutionContext.history_messages
```

名字叫 `history_messages`，但它不只是历史消息，而是已经拼装和治理后的 provider messages。

### 20.3 `ChatContextAssemblyService`：上下文总装层

这个类不创建新消息，也不直接调用最终回答模型。它的职责是把不同来源的上下文变成一个模型可消费的 prompt。

输入关键对象：

- `conversation`：当前会话，提供 `system_prompt/context_summary/project_id`。
- `history_rows`：最近历史消息，包含本轮 user message，不包含空 assistant 占位。
- `user_message`：本轮用户消息。
- `assistant_message`：本轮 assistant streaming 占位，用于绑定 tool trace / RAG log。
- `runtime`：模型、API key、上下文预算、tokenizer、governance service。

输出关键对象：

- `history_messages`：最终发给模型的 messages。
- `context_stats`：上下文预算、token 估算、来源注入、裁剪情况。
- `context_details`：附件片段、外部来源、知识库来源、工具事件。
- `external_sources`：前端来源卡片和定位使用。
- `tool_events`：前端 Tool Trace 使用。

这里的核心不变量：

```text
build_execution_context() 不能绕过权限；
工具 trace 和 RAG log 必须绑定到本轮 user/assistant message；
最终 prompt 必须经过 ContextGovernanceService；
普通回答不应该因为摘要刷新失败而失败。
```

### 20.4 `ContextPromptBuilder`：把上下文变成 provider messages

这层做的是“语义分层”，不是预算裁剪。

本轮修复前，长期记忆、会话摘要、外部信息源、知识库片段都会拼进一个 system message。这个做法虽然简单，但从安全和行为控制上有问题：

```text
知识库/网页/工具结果/附件本质上是资料；
资料可能包含 prompt injection 文本；
如果直接进入 system role，模型更容易把资料里的恶意内容当成高优先级指令。
```

修复后，PromptBuilder 的角色层级变成：

```text
system message
  -> 平台上下文模板
  -> 用户/会话显式 system_prompt

reference context user message
  -> 长期记忆
  -> 会话滚动摘要
  -> 外部信息源
  -> 知识库片段
  -> 明确说明“这些是 evidence，不是 instruction”

recent history messages
  -> 最近用户/助手消息
  -> 当前轮附件片段附加到最后一条 user message
```

这样做的含义：

- system 只放真正的行为约束。
- RAG/工具/记忆是参考资料，不再获得 system 级权限。
- 治理层可以识别 reference context，并在预算紧张时优先裁剪它。

### 20.5 `ContextGovernanceService`：预算治理层

这层的任务是控制 prompt 大小，并尽量保持回答质量。

当前输入分三类：

```text
leading system
reference context
recent history
```

治理策略：

```text
1. 保留 leading system。
2. 保留 reference context，但它可被裁剪。
3. recent history 先按 max_history_messages 保留最近若干条。
4. 如果仍超预算，先删除较旧 user/assistant 历史。
5. 如果还超预算，裁剪 reference context。
6. 最后才截断当前用户消息。
```

这个顺序很重要。第一性原则是：

```text
当前用户问题是本轮任务定义；
参考资料是证据；
证据不能比任务定义更重要。
```

因此不能为了保留很长的知识库片段，把用户当前问题截断掉。

### 20.6 本轮对抗性审查发现并修复的问题

已修复：

- 参考资料上下文不再拼进 system role，避免把知识库、网页、工具结果、长期记忆里的非可信文本提升为高优先级指令。
- `PromptBuildResult.messages` 保留 `_context_layer` 给治理层识别，但 `GovernedContext.messages` 会统一剥离内部字段，避免把 `_context_layer` 发送给模型供应商。
- 预算超限时，治理层会在删除旧历史之后优先裁剪 reference context，最后才截断当前用户消息。
- 新增测试覆盖两个关键不变量：参考资料不是 system role；预算紧张时当前用户问题优先保留。

当前仍值得后续继续审查：

- `ChatContextAssemblyService.build_execution_context()` 仍然串行执行 memory、attachment、external tools、knowledge retrieval。性能上可以并行一部分，但要先拆清楚副作用和失败降级。
- `prompt_prefix_hash` 当前基于治理前的 stable prefix 计算。如果 reference context 被治理层裁剪，prefix token 观测可能和最终 prompt 有偏差；这属于诊断精度问题，不是权限问题。
- `ContextGovernanceService` 目前主要按字符和估算 token 治理；如果后续接更强 tokenizer，可继续减少估算误差。
- reference context 现在作为 user message 注入。多数 chat completion 模型支持，但不同 provider 对“连续 user message”的行为可能略有差异，后续可以做 provider-specific prompt template。

### 20.7 下一步建议

Prompt / Governance 第一轮已经能回答：

```text
模型看到什么；
资料和指令如何分层；
预算超限时谁先被裁剪。
```

下一轮建议继续看：

```text
KnowledgeContextService
KnowledgeRetrievalPipeline
Knowledge retrieval log 绑定
```

原因是：RAG 现在已经进入 Chat 主路径，下一步应该确认“知识库检索结果怎么产生、怎么排序、怎么进入 reference context、怎么定位回来源片段”。这比继续拆 `ChatContextAssemblyService` 更有价值。

## 21. 第七组源码精读：KnowledgeContext / RetrievalPipeline

这一组代码回答的是：

```text
用户在 Chat 中选择知识库后，后端怎么检索片段？
哪些片段真的进入 prompt？
前端来源卡片和 RAG log 怎么和 prompt 对齐？
```

从第一性原理看，RAG 链路必须守住三个不变量：

- 权限不变量：只能检索当前用户有权访问的知识库和 chunk。
- 对齐不变量：进入 prompt 的片段、前端来源卡片、retrieval log 的 selected 必须一致。
- 降级不变量：知识库检索失败或超时不能阻断普通聊天，只能降级并给出 notice。

### 21.1 真实链路

Chat 主链路调用位置：

```text
ChatContextAssemblyService.build_execution_context()
  -> KnowledgeContextService.build_context()
     -> _normalize_knowledge_base_ids()
     -> _build_single_context() 或多知识库 gather
     -> KnowledgeRetrievalPipeline.retrieve_async()
     -> _format_context()
     -> retrieval_log_repo.create()
     -> _build_sources()
```

`KnowledgeContextService` 做的是 Chat 侧上下文接入；`KnowledgeRetrievalPipeline` 做的是 query-time 检索编排。前者不应该知道 FAISS/BM25 细节，后者不应该知道 Chat message id。

### 21.2 `KnowledgeContextService._build_single_context()`：权限、降级、日志

核心代码片段：

```python
knowledge_base = self.base_repo.get_by_user(knowledge_base_id, self.user_id)
if not knowledge_base:
    return self._empty(
        enabled=True,
        error=1,
        notices=["所选知识库不存在或无权访问，已跳过知识库检索。"],
    )
```

这行是权限边界。知识库不是只按 id 取，而是按 `knowledge_base_id + user_id` 取。

继续看空 query 和未索引处理：

```python
if not query.strip():
    return self._empty(...)

total_chunks = self.chunk_repo.count_by_knowledge_base(knowledge_base.id, self.user_id)
if total_chunks <= 0:
    return self._empty(...)
```

这里的行为是“跳过 RAG，不阻断 Chat”。这是对的，因为知识库是增强上下文，不是聊天主链路的硬依赖。

检索执行有超时保护：

```python
results = await asyncio.wait_for(
    index_service.retrieve_async(...),
    timeout=settings.knowledge_context_timeout_seconds,
)
```

如果超时或异常：

```python
except asyncio.TimeoutError:
    return self._empty(... notices=["...已跳过本轮知识库上下文。"])
except Exception as exc:
    return self._empty(... notices=[f"知识库「{knowledge_base.name}」检索失败：{exc}"])
```

这保证了 RAG 失败不会导致整条回答失败。

### 21.3 `KnowledgeRetrievalPipeline.retrieve_async()`：检索模式编排

核心代码片段：

```python
retrieval_mode = (knowledge_base.retrieval_mode or "vector").strip().lower()
if retrieval_mode == "lexical":
    results = self._retrieve_lexical_results(...)
    return await self._rerank_if_needed(...)

if retrieval_mode == "hybrid":
    try:
        vector_results = await self._retrieve_vector_results(...)
        vector_error = None
    except Exception as exc:
        vector_results = []
        vector_error = str(exc)
    lexical_results = self._retrieve_lexical_results(...)
    results = self._fuse_rrf(...)
    return await self._rerank_if_needed(...)

results = await self._retrieve_vector_results(...)
return await self._rerank_if_needed(...)
```

这里的设计清晰：

- `vector`：embedding -> FAISS -> chunk 映射 -> rerank。
- `lexical`：BM25 lexical store -> chunk 映射 -> rerank。
- `hybrid`：vector + lexical -> RRF 融合 -> rerank。

对抗性审查结论：

- hybrid 模式下 vector 失败会 fallback 到 lexical，这是合理降级。
- vector 模式下 embedding/FAISS 失败会抛给 `KnowledgeContextService`，再降级为空上下文。
- lexical 失败会尝试 rebuild persistent lexical index，这是实用设计，但大知识库下可能有耗时风险，后续可以加后台重建或冷启动提示。

### 21.4 rerank 和 score threshold

核心代码片段：

```python
if not knowledge_base.rerank_enabled or len(results) <= 1:
    return self._apply_score_threshold(results, knowledge_base.score_threshold)
```

这说明 rerank 是可选增强，不是硬依赖。

rerank 失败时：

```python
except Exception as exc:
    return self._apply_score_threshold(
        self._mark_rerank_fallback(results, str(exc)),
        knowledge_base.score_threshold,
    )
```

这个降级策略是合理的：重排失败不应该丢掉召回结果，而是标记 fallback 后继续使用原结果。

### 21.5 本轮修复：来源卡片必须和实际 prompt 对齐

本轮发现的问题：

```python
selected = results[: max(1, knowledge_base.max_context_chunks)]
context_text = self._format_context(... results=selected, max_chars=knowledge_base.max_context_chars)
sources = self._build_sources(... results=selected)
```

问题在 `_format_context()`：

```python
remaining = max_chars - used_chars - len(header)
if remaining <= 120:
    break
```

也就是说，`selected` 可能有 3 个 chunk，但因为 `max_context_chars` 限制，真正写进 `context_text` 的只有 `[KB1]`。旧逻辑仍会把 3 个 chunk 都作为 sources 和 retrieval log selected。

这违反了 RAG 的对齐不变量：

```text
前端来源卡片显示的“已使用来源”，必须等于 prompt 里真的注入的来源。
```

修复后：

```python
selected = results[: max(1, knowledge_base.max_context_chunks)]
context_text = self._format_context(...)
injected_count = len(self._extract_context_labels(context_text))
injected_results = selected[:injected_count]
```

然后：

```python
"knowledge_chunks_injected": len(injected_results)
candidates=self._serialize_results(results)
selected=self._serialize_results(injected_results)
sources = self._build_sources(... results=injected_results)
```

现在语义更准确：

- `candidates`：检索候选，保留完整检索诊断。
- `selected`：真正进入 prompt 的片段。
- `sources`：前端来源卡片，只展示实际注入 prompt 的片段。
- `knowledge_chunks_injected`：和 prompt 中 `[KBx]` 标签数量一致。

新增测试覆盖：

```text
test_knowledge_context_sources_match_chunks_injected_into_prompt
```

测试构造了 3 个候选 chunk，但人为缩小 `max_context_chars`，让 prompt 只能注入 1 个 `[KB1]`。断言：

- `knowledge_chunks_retrieved == 3`
- `knowledge_chunks_injected == 1`
- `len(result.sources) == 1`
- retrieval log `candidates == 3`
- retrieval log `selected == 1`

### 21.6 当前仍值得后续审查

- 多知识库路径已经用 `_extract_context_labels(context_text)` 做了注入来源裁剪，和本轮单知识库修复后的语义一致。
- 已补 `KnowledgeChunkRepository.list_by_vector_ids_and_knowledge_base()`，vector/lexical 命中后只按命中的 `vector_id` 批量取 chunks，不再每次把整个知识库 chunks 全量拉出。
- 新增 `test_vector_retrieval_fetches_only_hit_chunks_by_vector_id`，用 guarded repo 阻止查询路径调用 `list_by_knowledge_base()`，防止性能回退。

## 22. 第八组源码精读：RAG 单文档索引与一致性

这一组只追踪一个具体动作：用户点击“索引文档”以后，Markdown 如何变成数据库 chunks、FAISS 向量索引和 BM25 倒排索引。先把这条链看清楚，再继续研究更底层的切块质量和增量索引，避免一次打开太多文件。

本轮实际阅读文件：

- `backend/app/api/routes/knowledge.py`
- `backend/app/services/knowledge_service.py`
- `backend/app/services/knowledge_index_service.py`

### 22.1 先分清三个名字相似的层

入口是：

```python
@router.post("/{knowledge_base_id}/documents/{document_id}/index")
def index_document(...):
    result = _document_service(db).index_document(
        knowledge_base_id,
        document_id,
        current_user.id,
    )
```

这里的 route 只做四件事：

```text
解析 URL 参数
-> Depends 注入数据库 Session
-> Depends 解析当前用户
-> 调用业务 service，并把 None 映射成 404
```

它不应该知道 FAISS、Embedding 或 chunk 算法。否则 HTTP 层会和索引实现耦合，以后换后台任务或换向量库时就必须改 route。

第二层是 `KnowledgeDocumentService.index_document()`。它负责业务状态机：

```text
校验 knowledge_base_id + user_id
校验 document_id + user_id
校验 document 属于这个 knowledge base
-> 创建 running job
-> document.index_status = indexing
-> 调用 KnowledgeIndexService
-> 成功：job=succeeded
-> 失败：document/job=failed，并保存错误
```

第三层才是 `KnowledgeIndexService.index_document()`。它负责索引算法和存储编排：

```text
读取 Markdown
-> 切 chunk
-> 构造 KnowledgeChunk
-> 调用 Embedding
-> 替换数据库 chunks
-> 重建 FAISS
-> 重建 BM25
-> document.index_status = indexed
```

可以用一句话区分：

```text
KnowledgeDocumentService 管“这项业务任务现在是什么状态”；
KnowledgeIndexService 管“索引具体怎样构建”。
```

### 22.2 权限检查为什么出现两次

业务入口同时查询：

```python
knowledge_base = self.base_repo.get_by_user(knowledge_base_id, user_id)
document = self.document_repo.get_by_user(document_id, user_id)
if not knowledge_base or not document or document.knowledge_base_id != knowledge_base.id:
    return None
```

三个条件分别防止三类错误：

1. 知识库不属于当前用户。
2. 文档不属于当前用户。
3. 知识库和文档都属于当前用户，但文档属于另一个知识库。

只检查前两个仍然不够。例如用户拥有 A、B 两个知识库，如果请求路径写 A 的 ID、文档却传 B 中的文档 ID，没有第三个条件就会出现资源层级错配。

这是审查嵌套资源 API 时应该固定使用的思路：

```text
检查父资源 ownership
+ 检查子资源 ownership
+ 检查 parent-child relationship
```

### 22.3 索引的核心不变量

当前一个知识库有三份共同描述检索语料的状态：

```text
PostgreSQL knowledge_chunks
FAISS index.faiss
BM25 lexical_index.json
```

FAISS 和 BM25 都使用 `KnowledgeChunk.vector_id` 关联数据库 chunk。因此最重要的不变量是：

```text
DB 中可检索的 vector_id 集合
= FAISS 中的 vector_id 集合
= BM25 postings 中的 vector_id 集合
```

而且同一个 `vector_id` 不仅要“存在”，还必须指向同一份 chunk 内容：

```text
FAISS(vector_id=42) 的 embedding
必须来自
DB(vector_id=42).content
```

如果集合相同但内容错位，系统仍会静默返回错误来源。这种 bug 比直接报错更危险，因为表面上搜索正常，实际向量和文本已经串位。

### 22.4 本轮确认的问题：外部调用发生在数据库提交之后

旧代码顺序是：

```python
saved_chunks = self.chunk_repo.replace_document_chunks(document.id, user_id, chunks)
all_chunks = self.chunk_repo.list_by_knowledge_base(knowledge_base.id, user_id)
all_vectors = asyncio.run(self.embedding_service.embed_texts(...))
```

而 Repository 内部的替换不是暂存，它会立即提交：

```python
for item in existing:
    self.db.delete(item)
for chunk in chunks:
    self.db.add(chunk)
self.db.commit()
```

于是重新索引时可能发生：

```text
旧 chunks 已删除
-> 新 chunks 已 commit
-> Embedding API 超时
-> FAISS/BM25 仍是旧版本
```

这不是抽象上的“事务不够优雅”，而是能真实构造出来的数据损坏路径。

本轮先写了失败测试：

```python
def test_reindex_embedding_failure_preserves_previous_chunks_and_indexes(self):
    # 先成功索引并保存旧 chunks、FAISS bytes、BM25 bytes
    # 再修改 Markdown，让 EmbeddingService 固定抛错
    # 断言旧 chunks 和两个正式索引文件都不变
```

修复前测试观察到：

```text
旧 vector_id = 1，内容包含 ORIGINAL-CONTENT
失败后 vector_id = 2，内容已经变成 NEW-CONTENT
```

这证明数据库确实在外部调用失败之前被改变了。

### 22.5 本轮修复：先完成可失败计算，再改变持久状态

现在的核心顺序是：

```python
existing_chunks = self.chunk_repo.list_by_knowledge_base(knowledge_base.id, user_id)
retained_chunks = [chunk for chunk in existing_chunks if chunk.document_id != document.id]
chunks_to_embed = [*retained_chunks, *chunks]

vectors_to_publish = asyncio.run(
    self.embedding_service.embed_texts(
        user_id=user_id,
        knowledge_base=knowledge_base,
        texts=[chunk.content for chunk in chunks_to_embed],
    )
)
self._validate_vectors(...)

saved_chunks = self.chunk_repo.replace_document_chunks(document.id, user_id, chunks)
```

第一性原则是：

```text
纯内存计算、网络请求、输入校验
应尽量发生在不可逆副作用之前。
```

Embedding 是这条链里最昂贵、最容易因为网络或供应商失败的步骤。把它前移后，Embedding 失败只会丢弃内存中的新 chunks，不会破坏旧的可查询状态。

### 22.6 为什么还要显式建立 vector_id -> vector 映射

Embedding 返回列表的顺序对应 `chunks_to_embed` 的输入顺序。数据库保存后又会重新查询 `all_chunks`。不能仅仅假定两次列表顺序永远相同，所以现在显式绑定：

```python
vector_by_id = {
    chunk.vector_id: vector
    for chunk, vector in zip(chunks_to_embed, vectors_to_publish, strict=True)
}
saved_chunks = self.chunk_repo.replace_document_chunks(...)
all_chunks = self.chunk_repo.list_by_knowledge_base(...)
all_vectors = [vector_by_id[chunk.vector_id] for chunk in all_chunks]
```

这里有两个值得学习的点：

1. `zip(..., strict=True)` 会在两边数量不一致时直接失败，而不是静默截断。
2. 用领域主键 `vector_id` 对齐数据，比依赖“两个列表碰巧顺序一样”更可靠。

### 22.7 索引文件为什么要临时写入再原子替换

旧 FAISS 写法：

```python
faiss.write_index(index, str(index_path))
```

旧 BM25 写法：

```python
index_path.write_text(json.dumps(payload), encoding="utf-8")
```

二者都直接覆盖正式文件。如果进程中断、磁盘空间不足或底层写入异常，旧的完整索引也会被半写文件覆盖。

本轮改成：

```text
在目标目录创建临时文件
-> 完整写入临时文件
-> BM25 flush + fsync
-> os.replace(temp, target)
-> finally 清理残留临时文件
```

同目录很重要，因为 `os.replace()` 只有在同一个文件系统内才具备可靠的原子替换语义。发布结果因此只有两种：

```text
旧完整文件
或
新完整文件
```

不会把半个文件当正式索引使用。

新增测试 `test_faiss_rebuild_failure_preserves_previous_index_file` 会让假的 `faiss.write_index()` 先向临时文件写入损坏字节，再抛出异常，然后断言：

- 正式 `index.faiss` 字节完全没变。
- 临时文件被清理。

### 22.8 外部 Embedding 响应不能只相信类型标注

旧校验只检查：

```text
返回向量数量
每个向量维度
```

但第三方 API 可能返回 `NaN` 或 `Infinity`。它们仍然是 Python `float`，也能通过维度检查，却会在归一化时污染 FAISS index。

现在额外检查：

```python
if any(not isinstance(value, (int, float)) or not math.isfinite(value) for value in vector):
    raise RuntimeError("Embedding 返回了非有限数值，已拒绝写入向量索引。")
```

这个边界体现了：

```text
Python 类型标注约束自己的代码；
运行时校验保护外部系统边界。
```

新增测试：

```text
test_embedding_validation_rejects_non_finite_values
```

### 22.9 当前没有假装解决的问题

本轮修复降低了失败概率和损坏范围，但没有宣称获得了真正的跨资源事务。

仍然存在：

1. 数据库 commit、FAISS 发布、BM25 发布是三个独立动作。正常 Python 异常可以补偿，但机器掉电发生在动作之间时，仍可能不一致。
2. 每索引一份文档仍会对全知识库 chunks 重新调用 Embedding。它实现简单且确保模型配置一致，但成本随全库 chunk 数增长。
3. `max_vector_id() + 1` 是应用层分配。两个文档并发索引时可能拿到相同起点；数据库目前也没有 `(knowledge_base_id, vector_id)` 唯一约束作为最后防线。
4. 同一个知识库的两个索引任务会同时覆盖同一对文件，没有知识库级锁或 generation/version 发布协议。
5. `parse_document` 和 `index_document` 都是同步 HTTP 长任务，Job 目前更像状态记录，不是真正的后台任务队列。

彻底解决第 1、3、4 点通常需要“索引 generation”设计：

```text
为本轮构建生成 generation_id
-> chunks 写入该 generation
-> FAISS/BM25 写入 generation 目录
-> 全部成功后只原子切换 knowledge_base.active_generation
-> 查询只读取 active_generation
-> 后台清理旧 generation
```

这样数据库和文件无需在同一个物理事务里同时提交；真正对外生效的动作只有切换一个 generation 指针。这比不断增加 try/except 补偿更接近正确的索引发布模型，但改动范围较大，应单独设计并迁移。

### 22.12 重索引与评测 Chunk 外键：派生数据的生命周期

继续追问“为什么重索引要删除当前文档的旧 chunks”后，会遇到一个传统后端与 RAG 交叉的问题：评测用例允许通过外键保存精确答案 chunk。

模型原来是：

```python
class KnowledgeEvalCase(Base):
    expected_document_id = mapped_column(
        ForeignKey("knowledge_documents.id"),
        nullable=True,
    )
    expected_chunk_id = mapped_column(
        ForeignKey("knowledge_chunks.id"),
        nullable=True,
    )
```

而重索引使用：

```python
existing = select(KnowledgeChunk).where(
    KnowledgeChunk.document_id == document_id,
    KnowledgeChunk.user_id == user_id,
)
for item in existing:
    db.delete(item)
db.commit()
```

第一性问题不是“外键怎么写”，而是两个对象的生命周期不同：

```text
KnowledgeEvalCase：用户希望长期保留的评测资产。
KnowledgeChunk：由 Markdown 和切块参数生成、可被重建的派生数据。
```

#### 22.12.1 `nullable=True` 为什么没有自动置空

真实 PostgreSQL catalog 查询结果显示：

```text
knowledge_eval_cases.expected_chunk_id
-> knowledge_chunks.id
delete_rule = NO ACTION（默认）
```

`nullable=True` 只表示这一列允许保存 `NULL`，不表示父记录删除时数据库会自动把它改成 `NULL`。删除行为由 Foreign Key 的 `ON DELETE` 决定。

本轮测试显式开启 SQLite 外键后构造：

```text
成功索引文档
-> 评测用例 expected_chunk_id 指向旧 chunk
-> 修改 Markdown
-> 重新索引并删除旧 chunk
```

修复前真实红灯：

```text
DELETE FROM knowledge_chunks ...
sqlite3.IntegrityError: FOREIGN KEY constraint failed
```

PostgreSQL 使用相同的默认 `NO ACTION`，因此线上开发数据库也会阻止该重索引。

#### 22.12.2 四种删除策略如何选择

| 策略 | 删除旧 Chunk 后的行为 | 判断 |
| --- | --- | --- |
| `NO ACTION` | 直接拒绝删除，重索引失败 | 不符合正常产品行为 |
| `CASCADE` | 连同评测用例一起删除 | 丢失用户评测资产，不能接受 |
| 业务代码手工置空 | 每个删除入口先 UPDATE 再 DELETE | 容易遗漏其他删除路径 |
| `SET NULL` | 保留评测用例，只清空失效精确引用 | 符合派生 Chunk 生命周期 |

最终 ORM 语义：

```python
expected_chunk_id = mapped_column(
    ForeignKey("knowledge_chunks.id", ondelete="SET NULL"),
    nullable=True,
    index=True,
)
```

这里不能只改 ORM。`Base.metadata.create_all()` 只会创建不存在的表，不会修改已有 PostgreSQL 外键，所以 `ensure_runtime_schema()` 还需要：

```text
查询 information_schema 中真实 constraint_name/delete_rule
-> 先用旧 chunk 回填历史 expected_document_id
-> DROP 旧约束
-> ADD ... ON DELETE SET NULL
```

迁移后重新查询 PostgreSQL catalog：

```text
knowledge_eval_cases_expected_chunk_id_fkey
options = {ondelete: SET NULL}
```

#### 22.12.3 为什么还要自动保存 expected_document_id

如果评测用例只有：

```text
expected_chunk_id = old_chunk
expected_document_id = NULL
```

重索引后 `SET NULL` 会让它失去所有检索 ground truth。创建评测用例时现在会：

```python
expected_chunk = chunk_repo.get_by_user(payload.expected_chunk_id, user_id)
if not expected_chunk or expected_chunk.knowledge_base_id != knowledge_base_id:
    raise ValueError("期望 Chunk 不存在或不属于当前知识库。")
expected_document_id = expected_chunk.document_id
```

于是生命周期变成：

```text
重索引前：精确到 expected_chunk_id，同时保存 expected_document_id
重索引后：旧 expected_chunk_id 自动变 NULL，expected_document_id 继续保留
```

评测精度会从“精确 chunk 命中”降级为“目标文档命中”，但不会静默删除整个评测用例，也不会完全失去 ground truth。

#### 22.12.4 外键为什么不能替代 ownership 校验

旧业务代码直接保存用户传入的 ID：

```python
expected_document_id=payload.expected_document_id
expected_chunk_id=payload.expected_chunk_id
```

外键只能证明 ID 存在，不能证明：

```text
这个资源属于当前用户；
这个资源属于当前知识库；
expected_chunk_id 和 expected_document_id 属于同一文档。
```

现在 Service 会验证上述三层关系；其他知识库的 chunk/document 会被拒绝，Route 将 `ValueError` 映射为 HTTP 400。

这是嵌套资源 API 的通用边界：

```text
Foreign Key 保证引用完整性；
Service ownership 校验保证业务授权和父子关系。
```

#### 22.12.5 本轮新增行为测试

```text
test_reindex_clears_stale_expected_chunk_but_preserves_eval_case_document_target
test_eval_case_rejects_expected_targets_from_another_knowledge_base
```

第一个测试保护数据生命周期；第二个测试保护用户/知识库归属边界。二者测试的是对外行为，而不是 ORM 内部是否调用了某个方法。

### 22.13 删除整个 Document：为什么先返回 409，而不是级联删除评测资产

重索引只替换 Chunk，Document 继续存在；删除文档则会让 Document 本身退出系统。这两个操作不能机械使用同一种外键策略。

当前删除入口非常短：

```python
def delete_document(knowledge_base_id, document_id, user_id):
    document = document_repo.get_by_user(document_id, user_id)
    if not document or document.knowledge_base_id != knowledge_base_id:
        return False
    document_repo.delete(document)
    return True
```

Repository 会立即提交：

```python
db.delete(document)
db.commit()
```

而真实 PostgreSQL 中：

```text
KnowledgeEvalCase.expected_document_id
-> KnowledgeDocument.id
delete_rule = NO ACTION
```

因此一个被评测用例引用的文档删除时，旧行为会在 `commit()` 抛出底层 `IntegrityError`，最终很可能表现成 HTTP 500，并把 SQLAlchemy Session 留在需要 rollback 的失败状态。

#### 22.13.1 产品语义先于外键语法

四种选择：

| 方案 | 用户删除文档后 | 当前判断 |
| --- | --- | --- |
| `CASCADE` 删除 EvalCase | 评测资产静默消失 | 不接受 |
| `SET NULL` | EvalCase 保留，但只有 query 且无 keywords 时会失去全部 ground truth | 当前信息模型不足 |
| 保存不可变 source snapshot 后 `SET NULL` | 仍可离线评测历史目标 | 长期更合理，但需要新模型和编辑能力 |
| 显式阻止删除并返回 409 | 保留文档和评测资产，要求用户先处理引用 | 当前最小、诚实、可恢复 |

当前选择最后一项。它没有伪装成最终产品形态，而是在尚无 EvalCase 单条编辑/重绑定和 source snapshot 时，优先防止不可逆数据损失。

#### 22.13.2 应用检查和数据库约束各自负责什么

Service 现在先查询引用数量：

```python
if eval_case_repo.count_by_expected_document(document.id, user_id) > 0:
    raise KnowledgeDocumentConflictError(
        "该文档仍被评测用例引用，请先删除或调整相关评测用例。"
    )
```

这样正常请求能得到可理解的业务错误。但检查与 DELETE 之间仍有竞态：另一个请求可能恰好新增 EvalCase。因此数据库 `NO ACTION` 外键继续保留为最终防线，并把竞态下的 `IntegrityError` 翻译成同一个领域冲突：

```python
try:
    document_repo.delete(document)
except IntegrityError as exc:
    document_repo.db.rollback()
    raise KnowledgeDocumentConflictError(...) from exc
```

这里体现经典双层保护：

```text
应用层预检查：提供清晰用户体验；
数据库约束：保证并发下最终正确性。
```

Route 捕获领域异常并返回：

```text
HTTP 409 Conflict
```

409 比 400 更准确，因为请求格式本身合法，冲突来自资源当前状态。

#### 22.13.3 故障测试

新增：

```text
test_delete_document_reports_conflict_when_evaluation_case_still_references_it
```

测试开启外键、建立已索引文档和引用它的 EvalCase，再发起删除。修复前得到数据库 `FOREIGN KEY constraint failed`；修复后断言：

- 抛出包含“评测用例”的领域冲突。
- Document 仍然存在。
- EvalCase 仍然存在。

#### 22.13.4 删除索引文件问题为什么没有混在本节修

允许删除没有评测引用的文档后，当前代码只删除数据库 Document/Chunks，并没有从 `index.faiss` 和 `lexical_index.json` 发布一个不含该文档的新版本。这会留下 stale vector IDs，查询期虽然可能因数据库找不到 chunk 而跳过，但 top-k 可能被无效命中占用，降低召回。

直接在 `delete_document()` 里追加“重写两个文件”仍有跨资源半状态：

```text
先写文件、后删 DB：DB 删除失败 -> 新文件 + 旧 DB
先删 DB、后写文件：文件发布失败 -> 新 DB + 旧文件
```

因此它应和索引 generation / active pointer 一起设计，而不是在删除方法里再堆一套脆弱补偿。下一阶段的设计目标是让“索引文档、重索引、删除文档”都通过同一个版本发布协议。

### 22.14 Index Generation / Active Pointer：先构建完整版本，再原子切换

这一节先完成架构评审，不立即提交半套字段。原因是 generation 必须同时闭合数据库 Chunk、FAISS、BM25 和查询读路径；只改其中一部分，会引入新的版本错配。

#### 22.14.1 当前代码为什么没有“版本”概念

当前 KnowledgeBase 没有 active generation：

```python
class KnowledgeBase(Base):
    id: str
    # 没有 active_index_generation
```

Chunk 也没有 generation：

```python
class KnowledgeChunk(Base):
    knowledge_base_id: str
    document_id: str
    vector_id: int
    # 没有 index_generation
```

索引文件路径只有知识库 ID：

```python
index_root / knowledge_base_id / "index.faiss"
index_root / knowledge_base_id / "lexical_index.json"
```

查询过程：

```text
按 knowledge_base_id 读唯一 FAISS/BM25 文件
-> 得到 vector_ids
-> 按 knowledge_base_id + vector_ids 查询所有 chunks
```

因此系统无法表达：

```text
这些 DB chunks 属于 v1；
这些文件属于 v2；
用户当前应该读取哪一版。
```

#### 22.14.2 为什么只给文件加目录还不够

假设只改成：

```text
<knowledge_base_id>/<generation_id>/index.faiss
```

但数据库 Chunk 没有 generation，查询仍然是：

```python
WHERE knowledge_base_id = :kb
  AND vector_id IN (...)
```

如果不同代都出现 `vector_id=1`，新文件命中可能映射到旧代文本。所以 generation 必须贯穿：

```text
active pointer
DB Chunk
FAISS/BM25 文件
Repository 查询条件
```

#### 22.14.3 第一版数据模型

核心字段：

```text
KnowledgeBase.active_index_generation: str | null
KnowledgeChunk.index_generation: str
```

再增加 generation 记录表，用于观察构建而不是把 pointer 当任务日志：

```text
KnowledgeIndexGeneration
  id                  # UUID，也是 generation_id
  user_id
  knowledge_base_id
  base_generation_id  # 本轮从哪一活跃版本构建
  status              # building / ready / failed / obsolete
  manifest_hash
  error_message
  created_at
  activated_at
```

权威关系：

```text
KnowledgeBase.active_index_generation 是“当前用户查询哪一版”的唯一权威；
Generation.status 用于任务诊断和清理，不能替代 active pointer。
```

文件目录：

```text
knowledge_indexes/
  <knowledge_base_id>/
    generations/
      <generation_id>/
        index.faiss
        lexical_index.json
        manifest.json
```

manifest 至少记录：

```text
generation_id
knowledge_base_id
embedding provider/model/dimensions
vector_id -> chunk_id/content_hash
chunk_count
created_at
```

它用于发布前校验和故障诊断，不替代数据库。

#### 22.14.4 为什么第一版采用全量 Chunk 快照

每一代包含该知识库当时所有活跃文档的完整 chunks：

```text
generation v1:
  Document A chunks
  Document B chunks

generation v2（重索引 B）:
  复制 A 的内容为 v2 chunks
  新生成 B 的 v2 chunks
```

它会暂时增加 DB 空间，但有三个优点：

1. 查询只需过滤一个 `index_generation`，逻辑清晰。
2. `vector_id` 可以在每代从 1 重新编号，并用 `(knowledge_base_id, index_generation, vector_id)` 唯一约束。
3. 当前实现只重切目标文档，其他文档沿用数据库中已持久化的 Chunk 文本；但会对“其他文档的旧 Chunk + 目标文档的新 Chunk”整个合并列表重新请求 Embedding。因此全量 generation 快照没有额外放大当前的 Embedding 计算量，但当前计算量本身就有优化空间。

当前真实数据只有 1 个知识库、376 个 chunks、3 个已索引文档，第一版快照成本可接受。后续再把不变 Chunk/Embedding 抽成可复用实体，避免在正确性协议尚未稳定时同时做去重优化。

##### 全库重新 Embedding 的根因，以及它与 generation 的关系

现在 `KnowledgeChunk` 持久化了 `content` 和 `content_hash`，却没有持久化可按内容取回的 Embedding 向量。向量主要存在 FAISS 文件中，现有代码没有“给我这个 `content_hash` 对应的原始向量”的持久化查询层。所以重建 FAISS 时，即使大部分 Chunk 内容没变，也只能再调一次 Embedding API。

这不是“Embedding 没有持久化”的字面问题——FAISS 确实已经持久化了可搜索向量；更准确的问题是：

```text
向量被持久化成“搜索索引”，
却没有被持久化成“可按稳定 key 复用的 Embedding 缓存”。
```

它应与 generation 一起解决，但分成两个可独立测试的层次：

```text
第一层：持久化 Embedding Cache，解决“相同内容不重复调外部 API”。
第二层：generation publisher 从缓存取向量并构建完整快照，解决“多资源一致发布”。
```

缓存 key 不能只用 `content_hash`。同一段文本使用不同模型、维度或预处理版本时，向量并不相同。第一版建议的唯一键是：

```text
(user_id, content_hash, provider, model, dimensions, embedding_version)
```

`user_id` 用来避免用户之间无意共享内容特征；`embedding_version` 用来表示代码中的文本预处理或请求协议版本。向量可先用 float32 `LargeBinary` 存储，这比 JSON 紧凑，又不会立即让 SQLite 测试强依赖 PostgreSQL `pgvector`。

新 generation 的计算路径将变成：

```text
构造期望的全量 Chunk 快照
-> 按缓存 key 批量查找向量
-> 只对 miss 的 Chunk 请求 Embedding
-> 校验并保存新向量
-> 用 hit + miss 的完整向量集构建 FAISS
-> 写 BM25 / manifest
-> CAS 切换 active generation
```

因此 generation 仍是“全库快照”，但不再等于“全库重新调 Embedding API”。这是一个重要的后端分层思路：快照的完整性和计算结果的复用性可以同时成立。

#### 22.14.5 新增/重索引的构建与发布协议

```text
1. 读取 knowledge_base.active_index_generation，记为 base_generation。
2. 创建 Generation(status=building, base_generation_id=base_generation)。
3. 从 base_generation 构造新一代全量 Chunk 快照。
4. 计算 Embedding，校验数量、维度、有限值。
5. 将新代 chunks 写入 DB；它们尚未 active，失败不会影响查询。
6. 写 generation 专属 FAISS/BM25/manifest。
7. 校验 manifest、DB vector_ids、FAISS ids、BM25 ids 一致。
8. 在一个数据库事务中执行 active pointer 的比较并交换，并更新 Document/Generation 状态。
9. pointer 切换成功后，新查询自动读取新代；旧代进入可清理状态。
```

文件必须在 pointer 切换前完整存在。于是关键失败点的结果为：

| 失败时刻 | 对用户查询的影响 |
| --- | --- |
| Embedding 失败 | active pointer 未变，继续读旧代 |
| 新代 chunks 写入失败 | active pointer 未变，继续读旧代 |
| FAISS/BM25 写入失败 | active pointer 未变，继续读旧代；留下可清理构建产物 |
| pointer 事务失败 | active pointer 未变，新代标记 failed/obsolete |
| pointer 成功后进程崩溃 | 新代 DB 和文件已就绪，查询仍可用；清理任务稍后执行 |

#### 22.14.6 并发为什么需要 Compare-And-Swap

假设两个任务都从 v1 开始：

```text
任务 A：在 v1 上加入 Document C，构建 v2-A
任务 B：在 v1 上加入 Document D，构建 v2-B
```

如果都无条件保存 active pointer，后提交者会覆盖前者，导致 C 或 D 丢失。发布必须带基线条件：

```sql
update knowledge_bases
set active_index_generation = :new_generation
where id = :knowledge_base_id
  and active_index_generation is not distinct from :base_generation;
```

解释：

```text
任务 A 先把 v1 -> v2-A，成功更新 1 行。
任务 B 仍要求 active=v1，但现在已经是 v2-A，更新 0 行。
任务 B 不能激活旧基线产物，必须从 v2-A 重新构建，才能同时包含 C 和 D。
```

这叫 Compare-And-Swap / Optimistic Concurrency Control：

```text
只有“我开始计算时看到的版本仍是当前版本”，才允许提交结果。
```

#### 22.14.7 查询读路径

查询必须先读取：

```python
generation_id = knowledge_base.active_index_generation
```

然后所有资源使用同一个 generation：

```text
FAISS path: <kb>/generations/<generation>/index.faiss
BM25 path:  <kb>/generations/<generation>/lexical_index.json
DB query:   WHERE knowledge_base_id=:kb AND index_generation=:generation
```

Repository 方法不建议把 generation 做成随意可省略的参数；检索热路径应强制显式传入，避免新代码忘记过滤后跨代混读。

#### 22.14.8 删除文档如何接入同一协议

允许删除前仍先检查 EvalCase 引用。无冲突时：

```text
1. 从 active generation 构造“不包含目标 Document”的候选 generation。
2. 写入候选 chunks 和文件。
3. 在同一数据库事务中：CAS 切换 active pointer + 删除 Document。
4. 若并发新增 EvalCase 导致 Document 外键删除失败，整个事务回滚，active pointer 也不切换。
5. 候选 generation 成为未激活产物，后台清理。
```

这里“pointer 切换和 Document DELETE 同事务”很关键：它解决先改文件还是先删 DB 的两难。文件在事务前已经就绪，但只有数据库事务成功后才对查询生效。

#### 22.14.9 Legacy 迁移

当前已有 1 个知识库、376 个 chunks、3 个 indexed documents，不能直接让新字段为空后停止查询。

建议兼容迁移：

```text
1. KnowledgeChunk.index_generation 回填为 "legacy"。
2. 有 chunks 的 KnowledgeBase.active_index_generation 回填为 "legacy"。
3. legacy generation 暂时读取旧路径 <kb>/index.faiss 和 lexical_index.json。
4. 新构建一律写 generations/<uuid>/...。
5. 等所有知识库至少发布一次新代后，再清理 legacy 兼容分支。
```

这样迁移 DDL 后现有索引仍能读取，不要求在同一次启动里原子搬动数据库和文件。

`legacy` 不是 Embedding 模型版本，也不是一条旧代码分支。它只是一个兼容哨兵值（sentinel）：为generation 功能上线之前已存在、当时没有版本标签的 Chunk 和索引补一个名字。可以把它理解为：

```text
旧仓库里的箱子原来没贴批次号；
迁移时统一贴上“legacy”标签，但不搬动箱子。
```

当 active pointer 是 `legacy` 时，Store 仍读旧文件路径；第一个新 UUID generation 成功发布后，pointer 才从 `legacy` 切换到该 UUID。`legacy` 数据随后只是未激活的兼容旧代，等保留策略确定后再清理。

不能一次性修改所有模型、Repository、Store、索引和查询后再测试。建议拆成三个可验证阶段：

### 22.15 pgvector 替换 FAISS：环境可行性与迁移边界

#### 22.15.1 为什么目标不再是“pgvector 只做缓存”

当前向量索引横跨 PostgreSQL 和 FAISS 文件，所以 generation 发布器必须处理数据库事务无法覆盖的文件状态。如果 pgvector 只保存一份缓存，FAISS 仍然负责查询，则只减少 Embedding API 请求，不能消除双写一致性问题。

因此已确定的目标架构是：

```text
PostgreSQL + pgvector
  -> 持久化 Chunk 和 Embedding
  -> 执行向量距离查询
  -> 在数据库事务中管理 generation 和 active pointer

FAISS
  -> 迁移完成后删除
```

这里的首要收益不是“少一个文件”，而是把一个跨资源一致性问题收敛为 PostgreSQL 事务问题。

#### 22.15.2 真实环境评估

旧环境实测：

```text
PostgreSQL 12.20
port = 35432
database size = 14 MB
knowledge_chunks = 376
data directory = /disk2/gengnan/rag_agent/.pgdata
installed extensions = plpgsql
available vector extension = none
```

所以旧库不能只执行 `CREATE EXTENSION vector`；它缺少 pgvector 的 control、SQL 和共享库文件。Docker CLI 虽存在，当前用户没有 Docker daemon socket 权限，因此本机可执行方案是用独立 Conda 环境建立新 PostgreSQL 集群。

已建立且验证：

```text

         ai_web_studio_pre_pgvector_2026-07-12.dump
```

采用的是逻辑迁移，而不是让 PostgreSQL 18 直接打开 PostgreSQL 12 数据目录：

```text

```

#### 22.15.3 验证不只是“扩展创建成功”

已执行三层验证：

1. 数据层：恢复后仍有 376 个 Chunk 和 3 个 Document。
2. 向量层：建立 `vector(3)` 临时表和 HNSW cosine 索引，`[1,0,0]`、`[0.9,0.1,0]`、`[0,1,0]` 的排序结果符合预期。
3. 扩展层：pgvector 自带的 vector/halfvec/sparsevec、HNSW、IVFFlat、cast、copy 等 14 项回归测试全部通过。
4. 应用层：临时使用 `POSTGRES_PORT=35433` 启动后端，`/health` 返回 HTTP 200，验证后已停止临时进程。

#### 22.15.4 下一个不能跳过的建模问题：向量维度

当前 `KnowledgeBase.embedding_dimensions` 是知识库级配置，理论上不同知识库可以使用 768、1024 或 1536 维向量。如果直接把列写死为：

```sql
embedding vector(1024)
```

那么它能建立明确的 HNSW 索引，但其他维度不能写入。如果列使用不限维度的 `vector`，则可以存放不同维度，但不能直接对整列建立单一的普通 HNSW 索引。

第一版迁移建议：

```text
1. KnowledgeChunk.embedding 先使用可变维度 vector，允许为 null。
2. 旧 Chunk 通过可恢复的 backfill 任务填充向量。
3. 376 条规模先使用精确距离查询，建立 FAISS/pgvector 结果对照基线。
4. 再根据允许的模型维度，设计部分表达式 HNSW 索引，或明确限制整个部署的向量维度。
```

这个顺序先保证数据模型不说谎，再用实测决定索引策略；不会为了先用上 HNSW 而偷偷把现有的多模型配置能力改成假能力。
