## 1. 这份文档解决什么问题

目前项目已经进入“功能较多、链路较长”的阶段，后端不再只是几个接口，而是包含：

- 登录鉴权、用户设置、会话、消息、附件、项目、分享、Prompt 模板。
- 聊天流式输出、上下文治理、长期记忆、工具调用、MCP、联网搜索。
- 知识库、文档解析、MinerU、分块、Embedding、BM25、Hybrid、Rerank、Parent-Child 检索、RAG 聊天接入。

如果直接从某个 service 文件开始看，容易迷失在实现细节里。更稳的方式是先从第一性原理拆解：

- 后端本质上接收什么请求？
- 请求经过哪些层？
- 哪一层负责 HTTP，哪一层负责业务，哪一层负责数据库？
- 哪些对象是 API 入参/出参，哪些对象是数据库表，哪些对象只是内部流程数据？
- 某个功能出问题时，应该定位到哪条链路？

## 2. 第一性原理：读后端代码先问什么

读每个文件时，建议固定问这 7 个问题：

| 问题 | 目的 |
| --- | --- |
| 这个文件属于哪一层？ | 判断它应该做什么、不应该做什么 |
| 它的输入是什么？ | HTTP body、query、当前用户、数据库记录、内部对象 |
| 它的输出是什么？ | Pydantic schema、数据库对象、流式事件、内部结果 |
| 谁调用它？ | 找上游入口，知道它何时执行 |
| 它调用谁？ | 找下游依赖，知道它影响哪些模块 |
| 它读写哪些表/文件/外部 API？ | 明确副作用和风险 |
| 它的错误怎么处理？ | 判断前端看到的报错从哪里来 |

不要先纠结每行代码，而是先判断“职责边界”。职责边界清楚后，具体实现才容易理解。

## 3. 后端是什么框架

后端主框架是 FastAPI。

核心运行模型：

- `backend/app/main.py` 创建 `FastAPI` 应用。
- `backend/app/api/routes/*.py` 定义 HTTP API。
- `backend/app/api/deps.py` 定义公共依赖，例如数据库 Session、当前登录用户。
- `backend/app/schemas/*.py` 定义 API 入参/出参的 Pydantic 模型。
- `backend/app/models/*.py` 定义 SQLAlchemy 数据库模型。
- `backend/app/repositories/*.py` 封装数据库读写。
- `backend/app/services/*.py` 封装业务逻辑。
- `backend/app/services/tools/*.py` 封装工具调用、MCP、Planner、Workflow。

可以把后端理解成下面这条主线：

```text
HTTP 请求
  -> FastAPI Router
  -> Depends 注入 db / current_user
  -> Pydantic Schema 校验
  -> Service 执行业务
  -> Repository 读写数据库
  -> Model 映射数据库表
  -> Schema 返回给前端
```

聊天和 RAG 链路会更复杂，因为它们还会调用模型服务、工具服务、外部 API、向量检索和流式输出，但入口仍然是这个结构。

## 4. 目录结构和分层

后端源码主目录：

```text
backend/app/
├── main.py                         # FastAPI 应用入口，注册中间件和路由
├── api/
│   ├── deps.py                     # 公共依赖：数据库 Session、当前用户
│   └── routes/                     # HTTP 接口层
├── core/
│   ├── config.py                   # 环境变量和全局配置
│   ├── database.py                 # SQLAlchemy engine/session/base
│   └── startup.py                  # 启动时的运行期 schema 补丁
├── models/                         # SQLAlchemy ORM 模型，贴近数据库表
├── repositories/                   # 数据访问层，封装 CRUD 查询
├── schemas/                        # Pydantic 入参/出参模型
├── services/                       # 业务逻辑层
│   └── tools/                      # 工具调用、MCP、Planner、Workflow 子系统
└── tool_manifests/
    └── default_tools.json          # 默认工具 manifest
```

### 4.1 Router 层

位置：`backend/app/api/routes/`

职责：

- 定义 URL、HTTP method、response_model。
- 通过 `Depends(get_db)` 获取数据库 Session。
- 通过 `Depends(get_current_user)` 获取当前用户。
- 调用 service。
- 不应该堆复杂业务逻辑。

代表文件：

- `auth.py`：注册、登录、获取当前用户。
- `chat.py`：聊天、重新生成、编辑后重答、流式响应。
- `knowledge.py`：知识库、文档、解析、索引、检索测试、RAG 日志、知识库凭据。
- `tools.py`：工具配置、MCP server、工具目录、工具测试。
- `settings.py`：用户设置、模型设置、知识库模型设置。

### 4.2 Schema 层

位置：`backend/app/schemas/`

职责：

- 定义前端传入的数据格式。
- 定义后端返回给前端的数据格式。
- 做基础字段校验。

示例：

- `schemas/auth.py`：`UserRegisterRequest`、`UserLoginRequest`、`TokenResponse`。
- `schemas/knowledge.py`：知识库、文档、检索、评测相关入参出参。
- `schemas/setting.py`：问答模型、知识库模型、上下文策略等设置。

阅读方法：

- 如果想知道一个接口需要前端传什么，先看 route 的参数类型，再跳到对应 schema。
- 如果想知道前端为什么拿不到某个字段，也先看 response_model 对应 schema 是否声明了它。

### 4.3 Model 层

位置：`backend/app/models/`

职责：

- 描述数据库表结构。
- 字段类型、索引、外键、默认值。
- 不应该写业务流程。

代表模型：

- `user.py`：用户。
- `conversation.py`：会话。
- `message.py`：消息。
- `attachment.py`：附件。
- `knowledge.py`：知识库、文档、chunk、embedding、检索日志等。
- `tool_config.py`：工具、MCP server、用户凭据配置。
- `tool_trace.py`：工具调用过程持久化。
- `user_setting.py`：用户设置。

注意：

- 目前项目使用 `core/startup.py` 做运行期 schema 补丁。这是开发期为了快速演进的务实做法，但你改 model 时要同时理解启动补丁，否则可能出现“代码字段有了，数据库字段没有”或反过来的问题。

### 4.4 Repository 层

位置：`backend/app/repositories/`

职责：

- 封装数据库查询和写入。
- service 不直接到处写复杂 SQL。
- 让业务层更关注流程，而不是 SQLAlchemy 细节。

代表文件：

- `user_repo.py`
- `conversation_repo.py`
- `message_repo.py`
- `knowledge_repo.py`
- `tool_config_repo.py`
- `tool_trace_repo.py`

阅读方法：

- 想知道“某个数据到底从数据库怎么查出来”，看 repository。
- 想知道“某个接口改了哪些表”，从 service 往下找 repository 方法。

### 4.5 Service 层

位置：`backend/app/services/`

职责：

- 封装业务流程。
- 协调 repository、外部模型 API、文件解析、工具调用、RAG 检索等。
- 是后端最需要重点阅读的层。

目前主要 service 族：

- 登录鉴权：`auth_service.py`
- 用户设置：`setting_service.py`
- 会话消息：`conversation_service.py`、`message_service.py`
- 聊天编排：`chat_execution_service.py` 及其拆分 service
- 上下文治理：`context_governance_service.py`、`prompt_builder_service.py`、`tokenizer_service.py`
- 附件上下文：`attachment_context_service.py`、`file_parser_service.py`
- 工具调用：`external_context_service.py`、`services/tools/*`
- 知识库：`knowledge_service.py`、`knowledge_parser_service.py`、`knowledge_index_service.py`、`knowledge_retrieval_pipeline.py`、`knowledge_context_service.py`

阅读 service 的关键是分清：

- 哪些是“流程编排”。
- 哪些是“纯计算/转换”。
- 哪些是“外部副作用”，例如调用 API、写数据库、读文件。

## 5. 一次请求如何流动

以登录接口为例：

```text
POST /api/auth/login
  -> api/routes/auth.py::login()
  -> Depends(get_db) 创建数据库 Session
  -> AuthService(UserRepository(db)).login_user(payload)
  -> UserRepository.get_by_email()
  -> bcrypt 校验密码
  -> jwt.encode() 生成 token
  -> TokenResponse 返回给前端
```

以需要鉴权的接口为例：

```text
请求 Header: Authorization: Bearer <token>
  -> api/deps.py::get_current_user()
  -> jwt.decode()
  -> payload["sub"] 得到 user_id
  -> UserRepository.get_by_id(user_id)
  -> route 函数拿到 current_user
```

以知识库检索聊天为例：

```text
POST /api/chat
  -> chat route
  -> ChatExecutionService
  -> 读取会话、消息、用户设置
  -> 如果启用知识库，调用 KnowledgeContextService
  -> KnowledgeRetrievalPipeline 检索 chunk
  -> PromptBuilderService 组装 prompt
  -> ChatProviderService 调用模型
  -> 流式事件返回前端
  -> 保存 assistant 消息、上下文诊断、工具 trace、RAG 来源等
```

以工具调用为例：

```text
用户开启联网搜索 / 工具
  -> ExternalContextService
  -> ToolCatalog 合并静态 manifest 和 MCP tools
  -> ToolCandidateSelector 选择候选工具
  -> LLMToolPlanner 生成工具计划
  -> ToolWorkflowService 执行有限轮工具调用
  -> ToolExecutor 调 MCP / HTTP 工具
  -> Tool Trace 持久化
  -> 工具结果进入最终回答上下文
```

## 7. 关键链路阅读顺序

### 7.1 最小后端骨架

先看：

1. `backend/app/main.py`
2. `backend/app/core/config.py`
3. `backend/app/core/database.py`
4. `backend/app/api/deps.py`

看完这四个文件，你应该能回答：

- 后端应用怎么创建？
- 路由在哪里注册？
- 环境变量怎么读？
- 数据库 Session 怎么创建和关闭？
- 登录用户怎么从 token 解析出来？

### 7.2 登录鉴权链路

再看：

1. `api/routes/auth.py`
2. `schemas/auth.py`
3. `services/auth_service.py`
4. `repositories/user_repo.py`
5. `models/user.py`

这条链路短、清晰，适合作为理解整个后端分层的第一个样例。

### 7.3 用户设置链路

建议第三步看设置，因为后面聊天、工具、知识库都依赖用户设置：

1. `api/routes/settings.py`
2. `schemas/setting.py`
3. `services/setting_service.py`
4. `repositories/setting_repo.py`
5. `models/user_setting.py`

重点看：

- 问答模型配置在哪里保存。
- 知识库 embedding / rerank 配置在哪里保存。
- Ollama URL、API base URL、API key 如何区分。
- 前端设置项如何映射到后端字段。

### 7.4 知识库链路

建议按生命周期读：

```text
创建知识库
  -> 上传文档
  -> 解析文档
  -> 预览 markdown
  -> 分块
  -> embedding
  -> 建索引
  -> 检索测试
  -> 聊天时注入知识库上下文
```

对应文件：

1. `api/routes/knowledge.py`
2. `schemas/knowledge.py`
3. `models/knowledge.py`
4. `repositories/knowledge_repo.py`
5. `knowledge_service.py`
6. `knowledge_parser_service.py`
7. `knowledge_index_service.py`
8. `knowledge_retrieval_pipeline.py`
9. `knowledge_context_service.py`

重点看：

- 文档原始文件、解析 markdown、图片资源、chunk、embedding 分别怎么保存。
- 检索 pipeline 如何组合向量、BM25、Hybrid、Rerank、Parent-Child。
- RAG 来源定位如何从 chunk 找回文档和页码。

### 7.5 聊天链路

聊天链路是后端最复杂的部分，不建议一开始就读。建议先读完鉴权、设置、知识库基础后再看。

推荐顺序：

1. `api/routes/chat.py`
2. `services/chat_execution_models.py`
3. `services/chat_execution_service.py`
4. `services/chat_turn_bootstrapper.py`
5. `services/chat_context_assembly_service.py`
6. `services/prompt_builder_service.py`
7. `services/context_governance_service.py`
8. `services/chat_provider_service.py`

重点看：

- 一轮对话开始时创建了哪些对象。
- 用户消息和 assistant 消息何时写入数据库。
- 上下文治理、附件、知识库、工具结果分别在哪一步进入 prompt。
- 流式事件如何返回前端。
- 失败、停止生成、模型报错分别如何处理。

### 7.6 工具/MCP 链路

推荐顺序：

1. `services/external_context_service.py`
2. `services/tools/catalog.py`
3. `services/tools/registry.py`
4. `services/tools/selector.py`
5. `services/tools/planner.py`
6. `services/tools/workflow.py`
7. `services/tools/executor.py`
8. `services/tools/mcp_client.py`
9. `models/tool_config.py`
10. `models/tool_trace.py`

重点看：

- 工具从哪里发现：静态 manifest、MCP server、数据库配置。
- LLM planner 拿到的 schema 是什么。
- 工具候选如何筛选。
- 工具调用如何限制轮数、超时、重复调用。
- Tool Trace 如何记录 planner、schema validation、fallback、调用结果。

## 8. 读单个文件的检查表

打开任意文件时，建议按这个顺序读：

1. 看 import：它依赖哪些层？是否出现反向依赖？
2. 看 public 函数/类：这个文件对外暴露什么能力？
3. 看入参类型：来自 schema、model、普通 dict，还是内部 dataclass？
4. 看返回类型：给前端、给 service、还是写数据库？
5. 看数据库读写：是否通过 repository？是否直接 db.query？
6. 看外部调用：是否调用 LLM、MinerU、MCP、HTTP API、文件系统？
7. 看异常处理：是抛 `HTTPException`，还是内部返回 error object？
8. 看事务边界：什么时候 commit？失败时会不会留下半成品？
9. 看测试：有没有覆盖主要成功/失败路径？

## 9. 常见修改场景：应该改哪里

| 修改目标 | 优先修改位置 |
| --- | --- |
| 新增一个 API | `api/routes/*.py` + `schemas/*.py` + 对应 service |
| 新增数据库字段 | `models/*.py` + `core/startup.py` 或迁移方案 + repo/schema/service |
| 前端拿不到字段 | route 的 `response_model` 对应 schema |
| 接口入参校验不对 | `schemas/*.py` |
| 登录状态异常 | `api/deps.py`、`auth_service.py`、前端 token 存储 |
| 模型调用失败 | `chat_provider_service.py`、用户设置、provider 配置 |
| 知识库解析失败 | `knowledge_parser_service.py`、MinerU 凭据、文件解析 fallback |

## 14. 第一组源码精读：`config.py`、`database.py`、`deps.py`

这三个文件是 FastAPI 后端的底座，建议放在业务代码之前阅读。它们分别解决三个基础问题：

| 文件 | 第一性原理问题 | 代码职责 |
| --- | --- | --- |
| `core/config.py` | 程序运行需要哪些外部配置？ | 从 `.env` 和环境变量读取配置，形成全局 `settings` |
| `core/database.py` | 程序如何连接数据库？ | 创建 SQLAlchemy engine、Session 工厂和 ORM Base |
| `api/deps.py` | 每个请求如何拿到公共资源？ | 通过 FastAPI `Depends` 注入数据库 Session 和当前用户 |

### 14.1 `core/config.py`：配置层

文件位置：`backend/app/core/config.py`

这个文件的核心职责是把“外部环境”转换成“代码内部可使用的配置对象”。

关键代码：

```python
ROOT_DIR = Path(__file__).resolve().parents[2]
load_dotenv(ROOT_DIR / ".env")
```

这里先定位项目后端根目录，再加载 `.env`。`Path(__file__).resolve()` 得到当前文件的绝对路径，`parents[2]` 向上两级。对当前文件来说：

```text
backend/app/core/config.py
  parents[0] -> backend/app/core
  parents[1] -> backend/app
  parents[2] -> backend
```

所以这里加载的是：

```text
backend/.env
```

这点很重要。如果你以后发现改了 `.env` 没生效，要先确认你改的是不是 `backend/.env`，而不是项目根目录下的其他 `.env`。

核心配置类：

```python
@dataclass(frozen=True)
class Settings:
    app_name: str = os.getenv("APP_NAME", "ai_web_studio_backend")
```

这里使用 `dataclass(frozen=True)`。含义是：

- `dataclass` 自动生成初始化、repr 等基础方法。
- `frozen=True` 表示实例创建后字段不能再被赋值修改。
- 这让 `settings` 更像一个只读配置对象，避免运行中某个地方随手改配置，造成不可预测行为。

需要理解一个细节：这些字段的默认值是在类定义时通过 `os.getenv()` 读取的。因为文件底部立即执行：

```python
settings = Settings()
```

所以正常情况下它相当于“应用启动时读取一次配置”。如果进程运行中修改 `.env`，不会自动刷新，必须重启后端进程。

数据库连接字符串：

```python
@property
def sqlalchemy_database_uri(self) -> str:
    auth = self.postgres_user
    if self.postgres_password:
        auth = f"{auth}:{self.postgres_password}"
    return (
        f"postgresql+psycopg://{auth}"
        f"@{self.postgres_host}:{self.postgres_port}/{self.postgres_db}"
    )
```

这是一个计算属性，不是普通字段。它把分散的数据库配置拼成 SQLAlchemy 能识别的连接 URL。

`postgresql+psycopg://` 的含义：

- `postgresql` 表示数据库类型是 PostgreSQL。
- `psycopg` 表示使用 psycopg 这个 Python PostgreSQL driver。
- SQLAlchemy 负责统一 ORM 和连接池逻辑，底层 driver 负责真实网络通信。

配置分组可以这样理解：

- 应用自身：`APP_NAME`、`APP_ENV`、`APP_HOST`、`APP_PORT`。
- 数据库：`POSTGRES_HOST`、`POSTGRES_PORT`、`POSTGRES_DB`、`POSTGRES_USER`、`POSTGRES_PASSWORD`。
- 本地模型：`OLLAMA_BASE_URL`、`OLLAMA_DEFAULT_MODEL`、`OLLAMA_KEEP_ALIVE`、`OLLAMA_REQUEST_TIMEOUT_SECONDS`。
- 鉴权：`AUTH_SECRET_KEY`、`AUTH_ALGORITHM`、`AUTH_ACCESS_TOKEN_EXPIRE_MINUTES`。
- 文件和知识库：`UPLOAD_DIR`、`KNOWLEDGE_INDEX_DIR`、`KNOWLEDGE_PARSE_MAX_CHARS`。
- 外部工具：`TAVILY_API_KEY`、`AMAP_API_KEY`、`MINERU_API_TOKEN`。
- 敏感信息加密：`SECRET_ENCRYPTION_KEY`。

第一性原理判断：

- 配置层不应该依赖业务 service。
- 配置层不应该访问数据库。
- 配置层只负责“读取和组织配置”，不负责“使用配置做业务”。

当前可留意的点：

- `AUTH_SECRET_KEY` 有默认值，开发方便，但生产必须覆盖。
- `SECRET_ENCRYPTION_KEY` 默认为空，需要看 `secret_service.py` 如何处理空值。
- 复杂项目里更常见的做法是用 Pydantic Settings，因为它有更强的类型校验和 env 解析能力；当前 dataclass 方案简单直接，适合本项目现阶段。

### 14.2 `core/database.py`：数据库连接层

文件位置：`backend/app/core/database.py`

这个文件回答的问题是：后端如何建立数据库连接，以及 ORM 模型从哪里继承。

关键代码：

```python
engine = create_engine(settings.sqlalchemy_database_uri, pool_pre_ping=True)
```

`engine` 是 SQLAlchemy 的数据库引擎。它不是单个数据库连接，而是数据库连接和连接池的管理对象。

`pool_pre_ping=True` 的作用是：每次从连接池取连接前，先检查连接是否还活着。如果数据库重启、网络断开、连接被服务端关闭，这个参数可以减少“拿到一条已经失效的连接”导致的请求失败。

然后是：

```python
SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)
```

`SessionLocal` 是 Session 工厂，不是 Session 本身。每次请求需要数据库时，会调用 `SessionLocal()` 创建一个新的数据库会话。

参数含义：

- `autocommit=False`：不会自动提交事务，写操作需要显式 `commit()`。
- `autoflush=False`：不会在查询前自动把 pending changes flush 到数据库，减少隐式副作用。
- `bind=engine`：这个 Session 工厂使用上面创建的数据库 engine。

最后：

```python
Base = declarative_base()
```

`Base` 是所有 ORM 模型的共同基类。`models/*.py` 里的表模型应该继承它。SQLAlchemy 通过这个 Base 收集模型元数据，例如表名、字段、索引、外键。

第一性原理判断：

- `database.py` 只负责建立“数据库基础设施”。
- 它不应该知道 User、Message、Knowledge 这些业务表。
- 它不应该直接创建业务数据。
- 它提供的是 `engine`、`SessionLocal`、`Base` 三个底座。

典型请求生命周期：

```text
请求进来
  -> get_db() 调用 SessionLocal() 创建 Session
  -> route/service/repository 使用这个 Session 查询或写入
  -> 请求结束
  -> get_db() finally 关闭 Session
```

注意：`db.close()` 是把 Session 关闭并释放连接回连接池，不等于关闭整个数据库服务。

当前可留意的点：

- 当前是同步 SQLAlchemy，不是 async SQLAlchemy。所以 route/service 里大量数据库操作是同步执行。
- 如果未来并发和长任务更多，知识库解析/索引这类任务更适合放后台队列，而不是让请求线程一直占用资源。

### 14.3 `api/deps.py`：FastAPI 依赖注入层

文件位置：`backend/app/api/deps.py`

这个文件是 FastAPI 项目里很关键的“请求级公共依赖”入口。它解决两个问题：

- 一个接口需要数据库 Session，怎么拿？
- 一个接口需要当前登录用户，怎么拿？

数据库依赖：

```python
def get_db() -> Generator[Session, None, None]:
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```

这是 FastAPI 里常见的 yield dependency。它的执行过程是：

```text
进入请求
  -> 执行 yield 前代码：创建 db
  -> yield db，把 db 注入给 route/service
  -> route 执行完成或抛异常
  -> 执行 finally：关闭 db
```

这比在每个 route 里手动写 `db = SessionLocal()` 更好，因为它统一管理资源释放。

鉴权方案：

```python
bearer_scheme = HTTPBearer(auto_error=False)
```

`HTTPBearer` 会从请求头读取：

```text
Authorization: Bearer <token>
```

`auto_error=False` 表示没有 token 时不要让 FastAPI 自动抛错，而是返回 `None`，交给 `get_current_user()` 自己抛出更可控的错误。

当前用户依赖：

```python
def get_current_user(
    credentials: HTTPAuthorizationCredentials | None = Depends(bearer_scheme),
    db: Session = Depends(get_db),
) -> User:
```

这里体现了 FastAPI 依赖注入的组合能力：

- `credentials` 来自 `bearer_scheme`。
- `db` 来自 `get_db()`。
- 调用这个依赖的 route 不需要自己解析 Header，也不需要自己创建数据库 Session。

JWT 解码：

```python
payload = jwt.decode(
    credentials.credentials,
    settings.auth_secret_key,
    algorithms=[settings.auth_algorithm],
)
```

这里会验证：

- token 签名是否由同一个 `AUTH_SECRET_KEY` 生成。
- token 算法是否匹配。
- token 是否过期，因为 `auth_service.py` 生成 token 时写入了 `exp`。

然后取用户 ID：

```python
user_id = payload.get("sub")
```

JWT 里的 `sub` 通常表示 subject，也就是这个 token 代表的主体。这里主体是用户 ID。

最后查数据库：

```python
user = UserRepository(db).get_by_id(user_id)
```

这一步很重要：后端没有只相信 token，而是又查了一次数据库，确认用户仍然存在。这样如果用户被删除，旧 token 也不能继续通过鉴权。

错误处理路径：

| 场景 | 返回 |
| --- | --- |
| 没有 Authorization Header | 401 `Authentication required` |
| token 签名错误、过期、格式非法 | 401 `Invalid or expired token` |
| token 里没有 `sub` | 401 `Invalid token payload` |
| `sub` 对应用户不存在 | 401 `User not found` |

第一性原理判断：

- `deps.py` 不应该写具体业务。
- 它负责把“请求上下文”转成“业务代码可直接使用的对象”。
- 比如把 Header 里的 token 转成 `User` ORM 对象，把数据库连接池转成请求级 `Session`。

典型 route 使用方式：

```python
@router.get("/me")
def me(current_user: User = Depends(get_current_user)):
    return current_user
```

或者：

```python
@router.post("/something")
def create_something(
    payload: SomeRequest,
    db: Session = Depends(get_db),
    current_user: User = Depends(get_current_user),
):
    ...
```

读这类代码时要意识到：函数参数不一定全部来自前端 body，有些来自 FastAPI 依赖注入。

### 14.4 这三个文件连起来看

这三个文件形成了后端基础链路：

```text
config.py
  -> 读取 .env 和环境变量
  -> 生成 settings

database.py
  -> 使用 settings.sqlalchemy_database_uri
  -> 创建 engine / SessionLocal / Base

deps.py
  -> 使用 SessionLocal 创建请求级 db
  -> 使用 settings.auth_secret_key 解码 JWT
  -> 使用 UserRepository(db) 查当前用户

routes/*.py
  -> Depends(get_db)
  -> Depends(get_current_user)
  -> 拿到 db 和 current_user 后进入业务 service
```

这就是后端大多数接口的基础运行方式。

### 14.5 你做注释时可以继续保持的原则

你现在加的注释主要解释“这一行做什么”，这是入门阅读很有用。后面建议逐步升级成三类注释：

- 事实注释：解释不直观的库调用，例如 `pool_pre_ping=True`。
- 设计注释：解释为什么这里用依赖注入、为什么配置冻结。
- 风险注释：解释这里改错会影响什么，例如 `AUTH_SECRET_KEY` 改了会让旧 token 全部失效。

不建议长期保留太多“导入某某工具”这类注释，因为熟悉后会显得冗余。更有价值的是解释设计意图和边界，例如：

```python
# 每个请求独立创建 Session，并在请求结束后释放连接回连接池。
def get_db() -> Generator[Session, None, None]:
    ...
```

或者：

```python
# 只在启动时读取配置；修改 .env 后需要重启后端进程。
settings = Settings()
```

## 15. 配置边界补充：全局配置和用户态凭据怎么区分

阅读 `core/config.py` 时容易产生一个疑问：Tavily、高德地图、MinerU 这些 API key 已经计划做成用户自己配置，为什么还会出现在全局 `Settings` 里？

从第一性原理看，需要先区分两类配置：

| 类型 | 例子 | 应该属于谁 | 原因 |
| --- | --- | --- | --- |
| 系统运行配置 | 端口、数据库地址、上传目录、超时时间、索引目录 | 系统全局 | 决定后端进程怎么运行，和具体用户无关 |
| 用户外部服务凭据 | Tavily key、高德 key、MinerU token、用户自己的 MCP server token | 用户态 | 每个用户额度、权限、账单、安全边界不同 |

所以正确方向是：

- `APP_PORT`、`POSTGRES_HOST`、`UPLOAD_DIR`、`KNOWLEDGE_INDEX_DIR` 这类配置继续放在 `config.py`。
- `TAVILY_API_KEY`、`AMAP_API_KEY`、`MINERU_API_TOKEN` 这类敏感外部服务 key 不应该作为业务主路径的唯一来源。
- 用户进入系统后，应该在设置页配置自己的 key，后端加密保存，不向前端回显明文。

当前代码里的实际实现是“用户态优先，全局 env 兜底”：

```text
ToolCredentialResolver.resolve(user_id, provider_key)
  -> 如果数据库存在用户凭据，并且启用
       -> 解密并返回用户 key，source = "user"
  -> 如果用户禁用了该凭据
       -> 返回 disabled，source = "user_disabled"
  -> 如果没有用户 key 或为空
       -> 尝试读取环境变量 key，source = "env"
  -> 如果 env 也没有
       -> missing
```

2026-07-02 已进一步收敛边界：env fallback 不再默认开启，必须显式配置：

```env
ALLOW_ENV_TOOL_CREDENTIAL_FALLBACK=true
```

如果该开关为默认值 `false`：

```text
用户没有配置凭据
  -> 即使 backend/.env 存在 TAVILY_API_KEY / AMAP_API_KEY / MINERU_API_TOKEN
  -> ToolCredentialResolver 也不会把它作为用户请求的工具凭据
  -> source 返回 missing 或 env_fallback_disabled
```

这样默认行为更符合多用户产品边界：用户自己的外部服务调用应该使用自己的凭据。

对应文件：

- `backend/app/services/tools/credentials.py`
- `backend/app/services/secret_service.py`
- `backend/app/repositories/tool_config_repo.py`
- `backend/app/models/tool_config.py`
- `backend/app/services/knowledge_service.py` 的 MinerU 凭据接口

这意味着当前 `config.py` 里的：

```python
tavily_api_key: str = os.getenv("TAVILY_API_KEY", "")
amap_api_key: str = os.getenv("AMAP_API_KEY", "")
mineru_api_token: str = os.getenv("MINERU_API_TOKEN", "")
```

更准确的定位应该是：

```text
开发/部署级默认凭据，作为兜底 fallback；
不是多用户产品里的首选凭据来源。
```

这个兜底有现实价值：

- 本地开发时可以不进前端设置页，直接通过 `.env` 快速验证工具。
- 单用户私有部署时可以由管理员统一配置默认 key。
- 用户还没配置 key 时，系统可以选择使用默认服务能力。

但它也有风险：

- 如果所有用户都 fallback 到同一个 env key，会混用额度和账单。
- 用户可能误以为自己没配置 key，但实际调用的是服务器默认 key。
- 多用户 SaaS 场景下，全局 key 可能造成权限和成本边界不清。

因此后续读代码或继续优化时，建议遵守这个规则：

```text
用户态凭据是主路径；
全局 env 凭据只能作为显式开启后的开发/管理员默认/fallback；
前端和 Tool Trace 应该显示凭据来源 user/env/missing/disabled；
生产多用户部署应保持 env fallback 关闭。
```

2026-07-02 已处理的 provider 边界：

- `services/tools/providers/tavily.py` 不再直接 fallback 到 `settings.tavily_api_key`。
- `services/tools/providers/amap.py` 不再直接 fallback 到 `settings.amap_api_key`。
- Provider 只使用显式传入的 `api_key` 或实例初始化时传入的 `api_key`。
- 是否允许 fallback env，由 `ToolCredentialResolver` 统一决定。

当前明确后的架构方向是：

```text
Provider 只接收显式传入的 api_key；
是否允许 fallback env，由 ToolCredentialResolver 统一决定；
provider 本身不再直接读取 settings 里的第三方 key。
```

这能让凭据来源集中管理，避免后续工具越来越多时出现“有的工具走用户态，有的工具偷偷走 env”的混乱。

## 16. 第二组源码精读：Auth 认证链路与并发安全

Auth 是最适合练习后端分层阅读的第一条业务链路，因为它短、闭环、边界清楚。它解决的不是“写几个登录接口”，而是建立一条可信身份链路：

```text
用户输入账号密码
  -> 后端验证输入格式
  -> 后端验证身份规则
  -> 数据库保存唯一用户身份
  -> 密码只保存不可逆 hash
  -> 后端签发可校验、可过期的 token
  -> 后续请求通过 token 找回当前用户
```

涉及文件：

| 层 | 文件 | 责任 |
| --- | --- | --- |
| Router | `backend/app/api/routes/auth.py` | 定义 `/api/auth/register`、`/api/auth/login`、`/api/auth/me` |
| Schema | `backend/app/schemas/auth.py` | 定义注册/登录入参和 token/user 出参 |
| Service | `backend/app/services/auth_service.py` | 注册、登录、密码 hash、JWT 生成、事务提交/回滚 |
| Repository | `backend/app/repositories/user_repo.py` | 封装 `users` 表查询和写入 |
| Model | `backend/app/models/user.py` | 描述 `users` 表字段、唯一索引、ORM 关系 |
| Dependency | `backend/app/api/deps.py` | 从 Bearer Token 解析当前用户 |
| Config | `backend/app/core/config.py` | 提供 `AUTH_SECRET_KEY`、token 过期时间等配置 |
| Startup | `backend/app/core/startup.py` | 启动时补齐 `users` 表唯一索引 |
| Test | `backend/tests/test_auth_service.py` | 覆盖注册、登录、邮箱格式、重复注册等核心行为 |

### 16.1 Auth 分层边界

当前 Auth 链路遵循这条分层：

```text
HTTP 请求
  -> Router
  -> Schema
  -> Service
  -> Repository
  -> Model / Database
```

每层边界如下：

| 层 | 应该做 | 不应该做 |
| --- | --- | --- |
| Router | 定义路由、依赖注入、调用 Service | 不直接校验密码、不直接生成 JWT、不直接写 SQL |
| Schema | 校验入参/出参的数据契约 | 不查数据库、不做业务去重 |
| Service | 处理业务规则、事务边界、异常转换 | 不写复杂 SQL 细节 |
| Repository | 封装数据库查询和写入动作 | 不决定注册是否成功、不决定 HTTP 状态码 |
| Model | 描述表结构和约束 | 不处理业务流程 |
| Database | 保证最终一致性 | 不负责用户友好错误文案 |

### 16.2 注册链路

```text
POST /api/auth/register
  -> routes/auth.py::register(payload, db)
  -> UserRegisterRequest 做邮箱格式和基础字段校验
  -> AuthService(UserRepository(db)).register_user(payload)
  -> UserRepository.find_existing_identity(email, username)
  -> bcrypt 生成 password_hash
  -> UserRepository.create(user)
  -> db.commit()
  -> AuthService.create_access_token(created)
  -> TokenResponse 返回 access_token + user
```

第一性原理看，注册本质上做三件事：

- 建立用户身份记录。
- 把明文密码转换成不可逆 hash 后保存。
- 生成 token，让用户注册后直接处于登录状态。

当前注册步骤：

1. Router 接收请求体 `UserRegisterRequest`。
2. Schema 用 `EmailStr` 校验邮箱格式，用 `Field` 校验用户名和密码长度。
3. Service 先查邮箱/用户名是否已存在，给普通重复注册提供友好错误。
4. Service 用 bcrypt 把明文密码转换成 `password_hash`。
5. Repository 把 `User` 加入 SQLAlchemy Session，并执行 `flush()`。
6. Service 执行 `commit()`，提交注册事务。
7. 数据库唯一索引兜住并发重复注册。
8. 如果提交成功，Service 生成 JWT token。
9. 返回 `TokenResponse`，包含 `access_token` 和当前用户信息。

### 16.3 登录链路

```text
POST /api/auth/login
  -> routes/auth.py::login(payload, db)
  -> UserLoginRequest 做基础字段校验
  -> AuthService.login_user(payload)
  -> UserRepository.get_by_email(email)
  -> bcrypt.checkpw(password, password_hash)
  -> AuthService.create_access_token(user)
  -> TokenResponse 返回 access_token + user
```

登录链路的安全点：

- 先按 email 找用户。
- 用户不存在或密码为空时，统一返回 `Invalid email or password`。
- 密码错误时，也返回同一个错误。
- 不区分“邮箱不存在”和“密码错误”，避免暴露账号是否存在。

登录失败统一返回：

```text
401 Invalid email or password
```

这样做的安全原因是：不向攻击者暴露“邮箱是否存在”。

### 16.4 当前用户 `/me` 链路

```text
GET /api/auth/me
  -> Depends(get_current_user)
  -> HTTPBearer 从 Authorization Header 取 token
  -> jwt.decode 校验签名、算法、过期时间
  -> payload["sub"] 取 user_id
  -> UserRepository.get_by_id(user_id)
  -> UserResponse.model_validate(current_user)
```

`get_current_user()` 做的事情：

- 如果没有 token，返回 401。
- 如果 token 无效、过期、签名不对，返回 401。
- 如果 token payload 里没有 `sub`，返回 401。
- 如果数据库里找不到 `sub` 对应用户，返回 401。
- 校验通过后，返回当前 `User` ORM 对象。

这说明后端不是只信 token 本身，还会重新查数据库确认用户仍然存在。

### 16.5 密码安全

注册时不会保存明文密码。

当前代码使用 bcrypt：

```python
bcrypt.hashpw(password.encode("utf-8"), bcrypt.gensalt())
```

核心点：

- `gensalt()` 会为每个密码生成独立 salt。
- 同一个密码每次生成的 hash 也不同。
- 数据库只保存 `password_hash`。
- 不需要单独保存 salt，因为 bcrypt hash 里已经包含 salt 和成本参数。

登录校验：

```python
bcrypt.checkpw(password.encode("utf-8"), password_hash.encode("utf-8"))
```

这里会用数据库里的 hash 自带的 salt 和成本参数重新计算并比较。

### 16.6 JWT token

`auth_service.py` 里生成 token 的 payload：

```python
payload = {
    "sub": user.id,
    "email": user.email,
    "exp": expire_at,
}
```

含义：

- `sub`：subject，表示 token 代表的主体，这里是用户主键。
- `email`：冗余用户邮箱，方便调试或后续扩展。
- `exp`：过期时间，PyJWT 解码时会自动校验。

真正鉴权依赖的是：

```text
payload["sub"] -> UserRepository.get_by_id(user_id)
```

也就是说，后端不会只凭 token 里的 email 判断用户身份。

#### 16.6.1 `AUTH_SECRET_KEY` 边界

`AUTH_SECRET_KEY` 是 JWT 签发和验证的根密钥。

如果它变化：

```text
旧 token 无法再通过 jwt.decode()
用户需要重新登录
```

这是预期安全边界，不是 bug。密钥泄露或主动轮换时，让旧 token 失效是合理行为。

部署时要注意：

- 生产环境不能使用默认 `AUTH_SECRET_KEY`。
- 多实例部署时，所有实例必须使用同一个 `AUTH_SECRET_KEY`，否则 A 实例签发的 token 可能无法被 B 实例验证。
- 如果要做平滑密钥轮换，后续可以引入 `kid` 和多密钥验证策略。

### 16.7 并发重复注册问题

注册最大的并发风险是：

```text
两个请求同时注册同一个 email 或 username
```

如果只靠 Service 先查重，会出现竞态：

```text
T1: 请求 A 查询 email，不存在
T2: 请求 B 查询 email，不存在
T3: 请求 A 插入成功
T4: 请求 B 也尝试插入
```

所以第一性原理结论是：

```text
Service 层查重只能优化体验；
最终一致性必须由数据库唯一约束保证。
```

当前解决方案是三层。

第一层是 Service 先查重。普通重复注册会提前返回友好错误：

```text
409 Username or email already exists
```

第二层是数据库唯一索引兜底。`models/user.py` 里定义：

```python
Index("ux_users_email_lower", func.lower(User.email), unique=True)
Index("ux_users_username_lower", func.lower(User.username), unique=True)
```

含义：

```text
lower(email) 唯一
lower(username) 唯一
```

这样这些会被认为是同一个邮箱：

```text
tester@example.com
TESTER@example.com
Tester@Example.com
```

第三层是捕获 `IntegrityError`。如果两个请求并发通过 Service 查重，第二个请求在数据库写入时会触发唯一索引冲突：

```python
except IntegrityError as exc:
    self.repo.db.rollback()
    raise HTTPException(
        status_code=status.HTTP_409_CONFLICT,
        detail="Username or email already exists",
    ) from exc
```

作用：

- 不让数据库异常变成 500。
- 回滚失败事务，让 Session 回到可用状态。
- 对前端稳定返回 409。

### 16.8 事务边界

之前的问题：

```text
UserRepository.create() 自己 commit()
```

这在简单创建用户时能工作，但长期不利于复杂业务。Repository 不知道完整业务用例，未来注册可能需要：

- 创建默认用户设置。
- 创建默认工作区。
- 写审计日志。
- 初始化欢迎会话。

如果 Repository 创建用户时已经提前 commit，后续步骤失败就会出现半成功状态。

现在调整为：

```text
Repository.create()
  -> add
  -> flush
  -> refresh

AuthService.register_user()
  -> commit 或 rollback
```

边界更清楚：

```text
Repository 管数据库动作
Service 管业务事务
```

### 16.10 当前已解决的问题

2026-07-02 已完成的 auth 收敛：

- `schemas/auth.py` 的 `email` 已改为 Pydantic `EmailStr`，在 API 边界层直接拒绝明显非法邮箱格式。
- `models/user.py` 已增加 `lower(email)` / `lower(username)` 唯一索引，`core/startup.py` 启动时也会补齐 PostgreSQL 表达式唯一索引。
- `UserRepository.create()` 不再提交事务，只负责 `add/flush/refresh`，注册链路由 `AuthService.register_user()` 统一 `commit/rollback`。
- `AuthService.register_user()` 捕获数据库 `IntegrityError`，把并发重复注册转成稳定的 `409 Username or email already exists`。
- `AUTH_SECRET_KEY` 变更会让旧 token 全部失效，这一点已在 token 生成处注释说明，作为密钥轮换的预期安全边界。

这些优化背后的第一性原理：

- 格式问题在系统边界解决：非法邮箱不应该进入业务层。
- 最终一致性由数据库兜底：Service 层查重提供友好错误，但不能替代唯一索引。
- 事务边界跟业务用例走：注册是一个业务用例，因此由 `AuthService` 决定何时提交或回滚。
- 安全边界要显式：`AUTH_SECRET_KEY` 是签发和验证 token 的根密钥，轮换必然影响旧 token。

## 17. 第三组源码精读：Settings 用户设置链路

Auth 解决“谁在使用系统”，Settings 解决“这个用户以什么配置使用系统”。它是 Chat、Tool、RAG 的共同前置依赖。

从第一性原理看，Settings 链路解决的是：

```text
用户身份 user_id
  -> 找到或创建用户设置
  -> 保存模型/上下文/知识库/外观等偏好
  -> 加密保存用户级密钥
  -> 响应时只返回掩码和是否已配置
  -> 下游 Chat/RAG/Tool 按 user_id 读取配置
```

### 17.1 相关源码文件

| 层 | 文件 | 责任 |
| --- | --- | --- |
| Router | `backend/app/api/routes/settings.py` | 定义设置读取、更新、模型连接测试、知识库模型候选接口 |
| Schema | `backend/app/schemas/setting.py` | 定义设置入参/出参，控制哪些字段可更新、哪些字段可返回 |
| Service | `backend/app/services/setting_service.py` | 默认值、历史兼容、归一化、密钥加密、响应脱敏 |
| Repository | `backend/app/repositories/setting_repo.py` | 查询和保存 `user_settings` |
| Model | `backend/app/models/user_setting.py` | 描述用户设置表字段和 `user_id` 唯一关系 |
| Secret | `backend/app/services/secret_service.py` | 对用户级密钥加密、解密、掩码展示 |
| Provider | `backend/app/services/chat_provider_service.py` | 测试问答模型服务、获取模型列表 |
| Knowledge Catalog | `backend/app/services/knowledge_model_catalog_service.py` | 获取 embedding/rerank 候选模型 |

### 17.2 Settings 与 Config 的边界

这里最容易混淆的是 `config.py` 和 `user_settings`。

边界如下：

| 类型 | 例子 | 生命周期 | 所属 |
| --- | --- | --- | --- |
| 进程级配置 | 数据库地址、默认 Ollama URL、上传目录、JWT 密钥 | 后端启动时确定 | 系统全局 |
| 用户级设置 | 默认模型、API base URL、上下文窗口、知识库模型、主题 | 用户可修改 | 单个 user |
| 用户级密钥 | 问答模型 API key、embedding key、rerank key | 用户可修改且加密保存 | 单个 user |

第一性原理判断：

```text
config.py 决定后端进程怎么运行；
user_settings 决定某个用户的业务行为怎么运行。
```

### 17.3 读取设置链路

入口：

```text
GET /api/settings
```

代码链路：

```text
routes/settings.py::get_settings()
  -> Depends(get_current_user)
  -> SettingService.get_or_create_user_settings(current_user.id)
  -> UserSettingRepository.get_by_user(user_id)
  -> 不存在则 _build_default_setting(user_id)
  -> repo.save(setting)
  -> _to_response(setting)
```

读取设置不是简单查询。当前 `get_or_create_user_settings()` 同时承担：

- 新用户第一次进入时创建完整默认配置。
- 老用户历史字段缺失时补默认值。
- 旧版本把 API base URL 错放在 `ollama_base_url` 时做兼容迁移。
- 修正上下文窗口、context mode、主题、记忆、知识库模型等字段。
- 响应前做密钥脱敏。

因此这个方法是 Settings 链路的核心复杂点。

### 17.4 更新设置链路

入口：

```text
PATCH /api/settings
```

代码链路：

```text
routes/settings.py::update_settings()
  -> UserSettingUpdate
  -> SettingService.update_user_settings(user_id, payload)
  -> payload.model_dump(exclude_unset=True)
  -> 普通字段 trim / normalize
  -> 密钥字段跳过普通 setattr
  -> 密钥字段按 clear_* 或 encrypt() 单独处理
  -> 归一化 provider/context/theme/knowledge 字段
  -> repo.save(setting)
  -> _to_response(setting)
```

关键点：`exclude_unset=True` 很重要。

它让 PATCH 语义成立：

```text
字段没传
  -> 不更新

字段传了 null 或空字符串
  -> service 决定如何归一化

clear_api_key = true
  -> 明确清空密钥
```

### 17.5 密钥字段处理

Settings 中有多类密钥：

- `api_key`：问答模型 API key。
- `knowledge_embedding_api_key`：embedding 专用 key。
- `knowledge_rerank_api_key`：rerank 专用 key。

Service 更新时不会让这些字段走普通：

```python
setattr(setting, key, value)
```

而是单独处理：

```text
clear_xxx_api_key = true
  -> 设置为 None

xxx_api_key 有新值
  -> SecretService.encrypt()
```

响应时 `_to_response()` 只返回：

```text
api_key = None
has_api_key = true/false
api_key_masked = xxxx****yyyy
```

不会返回明文。

### 17.6 SecretService

`SecretService` 负责：

- `encrypt(value)`：加密用户级密钥。
- `decrypt(value)`：解密密钥供后端调用模型或工具。
- `mask(value)`：生成前端展示用掩码。

加密密钥来源：

```text
SECRET_ENCRYPTION_KEY
  -> 生产环境必须显式配置
  -> 开发环境未配置时才 fallback 到 AUTH_SECRET_KEY
```

阅读这个文件时要注意：

- 专用 `SECRET_ENCRYPTION_KEY` 是生产环境必需项。
- fallback 到 `AUTH_SECRET_KEY` 只允许用于开发环境兼容。
- 如果加密密钥变化，旧密文可能无法解密。
- `decrypt()` 对没有 `enc::` 前缀的值直接返回，是为了兼容历史明文行。

### 17.7 模型连接测试

问答模型连接测试入口：

```text
POST /api/settings/test-provider
```

它的语义是“临时测试”，不是“保存设置”。

代码逻辑：

```text
前端传 provider_type / base_url / api_key
  -> 如果本次没传 api_key，则读取已保存用户 key
  -> ChatProviderService.list_models()
  -> 返回模型列表和默认模型候选
```

这里体现了一个重要边界：

```text
测试连接可以使用临时输入；
真正保存配置必须走 PATCH /settings。
```

### 17.8 知识库模型候选

知识库模型候选入口：

```text
POST /api/settings/knowledge-model-options
```

它服务两类模型：

- `embedding`
- `rerank`

关键逻辑：

```text
model_kind = embedding
  -> 优先使用 knowledge_embedding_api_key
  -> 没有则视为未配置 embedding key

model_kind = rerank
  -> 优先使用 knowledge_rerank_api_key
  -> 没有则视为未配置 rerank key
```

2026-07-03 已移除知识库通用 key，只保留 embedding/rerank 两个专用 key。这样配置语义更清晰：

```text
embedding 调用只看 embedding key；
rerank 调用只看 rerank key；
不存在“通用 key 隐式兜底”。
```

### 17.9 当前审查结论

当前 Settings 链路整体边界是清楚的：

- Router 只做入口和调用 service。
- Schema 定义可更新字段和响应字段。
- Service 负责默认值、兼容、归一化、加密、脱敏。
- Repository 保持很薄。
- Model 字段完整，覆盖问答、上下文、记忆、UI、知识库模型配置。
- 密钥明文不会通过响应返回前端。

当前值得注意的风险：

- `SettingService` 已经比较大，后续可以按“问答模型设置 / 知识库模型设置 / UI 与上下文设置 / 密钥处理”拆分内部 helper。

2026-07-03 已完成的 Settings 收敛：

- 移除 `knowledge_api_key` 通用 key，只保留 `knowledge_embedding_api_key` 和 `knowledge_rerank_api_key` 两个专用 key。
- `get_or_create_user_settings()` 首次并发创建同一个用户设置时，会捕获 `IntegrityError`，回滚后重新读取已创建记录。
- `UserSettingRepository.save()` 不再提交事务，只做 `add/flush/refresh`；`SettingService` 负责 `commit/rollback`。
- `SecretService` 在生产环境中要求显式配置 `SECRET_ENCRYPTION_KEY`，开发环境才允许 fallback 到 `AUTH_SECRET_KEY`。
- 清理了 `SettingService` 中重复的默认字段赋值，并把保存逻辑收敛到 `_save_setting()`。

当前阶段建议先理解链路，不急着重构。下一步如果继续审阅，可以看 `Conversation / Message`，因为它们是 Chat 主链路的数据基础。
