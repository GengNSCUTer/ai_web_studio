日期：2026-10-11。范围：按用户授权调研并接入适合个人/小团队知识工作台的少量工具与 Skill，复用现有权限、质量、预算与审批边界。接入验收不等于答案质量评测。

## 一、选型与新增能力

| 官方 MCP | 项目 Tool Key | 用途 |
| --- | --- | --- |
| Exa | `web.exa.search` | 搜索公开资料，取得来源 URL 与摘录 |
| Exa | `web.exa.fetch` | 按已知公开 URL 读取限长正文 |
| Context7 | `docs.context7.resolve` | 从库名/问题定位真实 library ID |

| 平台 Skill | 组合流程 | 使用边界 |
| --- | --- | --- |
| 来源研究简报 `research.source-brief` | 有 URL 直接读；无 URL 先搜索再读取、整理 | 公开资料、来源引用与读取范围披露 |

第三项借鉴 [Anthropic doc-coauthoring](https://github.com/anthropics/skills/blob/main/skills/doc-coauthoring/SKILL.md)，适配为平台声明式 Skill，没有执行上游脚本。“读者检查”是自检，不是已实现独立读者 Agent；没有文件创建工具时给可复制草稿，不声称已新建文件。三项已通过真实安装 API 安装/启用在固定账号，用户在聊天中显式选择后生效，其他用户未静默安装。

Catalog 当前 20 个 Tool、8 个 Skill。旧 `research.web-brief@1.1.0` 和安装版本保留，新增独立 Key，不通过升级旧安装扩大权限。

## Key 获取与项目设置

Exa Key 在 [Exa API Keys](https://dashboard.exa.ai/api-keys) 注册/登录后创建，发送方式是 `X-API-Key` Header。Context7 Key 在 [Context7 Dashboard](https://context7.com/dashboard) 注册/登录后创建，当前官方远程示例使用 `Authorization: Bearer ...`。这些 Key 与硅基流动的模型 Key 无关；文档协作 Skill 使用现有文件工具和模型配置，不需要 Anthropic Key。

项目设置 → 工具与集成 → 工具凭证，可找到 `exa`、`context7` 卡片，填入对应 Key、保存并测试。缺省匿名可用，显式关闭 Provider 时禁止退回匿名绕过；配置了无效 Key 时按失败处理，不静默使用匿名身份。凭据复用加密存储和脱敏响应，不进入 URL、Planner 参数或 Tool Trace。首次验收只有匿名实测和认证路径受控测试；同日后续已用用户提供的两个真实 Key 验证连接、四个工具和两个完整浏览器对话，凭据来源确认为 `user`。

## 二、实际执行链与边界

用户选择 Skill → 后端核对安装/审核/版本/项目 → Skill 范围候选 → 在线 Planner 参数和依赖 → Executor Schema/权限检查 → 既有 MCP Client → 来源解析 → 质量门 → 有限补规划 → 证据/上下文组装 → 最终模型回答 → 消息及轨迹落库。

共用解析器处理 URL/Source 标记，库候选需明确 ID、标题和说明。未知 JSON、错误消息、空正文或无来源文本不算有效证据；格式漂移时质量不足，不声称能零配置处理任意 MCP。fetch 仅接受与请求 URL 相符的来源（去除 fragment 后比较），跨 URL 重定向保守拒绝。

来源正文每条最多 8,000 字符、合计最多 24,000、最多 5 条；Planner 投影仍受既有更小预算约束，最终回答仍走动态上下文预算，不保证整页或全部保留正文进入模型。URL、标题、正文及 raw 元信息存储前脱敏。公共查询发送前拒绝明显凭据；网页 URL 限公开 HTTP(S)、无认证信息、非本机/私网/元数据地址，调用前检查 DNS。实际抓取由远端 MCP 完成，DNS 检查不是对其实现的完整 SSRF 证明，也不是完整语义敏感信息检测。

新 `required_tools` 完成策略适用于已选 Skill，必要证据不依赖中文触发词，不自动猜参数/造请求。只定位库而未查正文、只搜索而未读网页，不能声称完成查证；文件正文未进入模型也不能算已核对。预算耗尽时如实说明未完成，不无限追加调用。普通任务仍保留单一 Tavily 搜索兜底，避免新服务挤占天气/文件候选；显式 Skill 提供自己的 Exa 工具。禁联网覆盖搜索、网页读取和技术文档三类。

## 答案错误排查与修复（同日）

官方资料明确描述按需启动事务：Session 的逻辑事务可能由 add/对象修改等操作触发，实际数据库事务与 SQL/连接操作有关；commit 本身结束当前事务，并不立即开始下一笔数据库事务。[官方 Session Basics](https://docs.sqlalchemy.org/en/20/orm/session_basics.html#auto-begin) 是 Day 7 纠错依据。

已确认两个工程缺口：定位出的五条库简介与正文一起按等份裁剪，容易消耗真正证据预算；“依据正文、区分 API 与示例后续操作”的约束在 Planner 指令里，最终回答只得到较泛的输出合同。来源解析还会把下一条紧邻 Source 标记的标题夹进上一段正文。旧版本追加一次真实调用也得到正确回答，说明原错误具有生成波动；不能断言每次都错，也不能把原错误唯一归因于裁剪。

现已将技术文档 Skill 发布为 1.0.1 并通过现有安装 API 明确更新固定账号的版本锁。Planner 查询要求覆盖用户的具体子问题；最终输出合同明确对象、版本、逻辑状态/实际副作用、触发条件及示例后续行为。只要已有同 Provider 文档正文，库简介留在 Trace/规划观察中、不再竞争回答证据预算，引用编号仍稳定。已知格式的下一条标题不混入上一条正文，未知布局不猜测删除。

受控小预算回归证明修复后能保留正文尾部的触发条件；真实生产上下文与 V3.2 流式回归、两次浏览器 SQLAlchemy 回归均正确区分 flush/commit、连接归还、非立即新事务与后续触发。这没有用 SQLAlchemy 专用替换规则修改生产答案。引用验收接受实际注入来源的标签或 URL；固定事实检查只针对测试问题，不是通用自动事实裁判。

额外 FastAPI 查证出现过 Planner 25 秒超时，只定位库或未调用正文；轨迹确认超时在在线 Provider 规划阶段，不是 Context7 解析失败。为方便定位，fallback 增加 provider/parse_and_validate 阶段及 timeout/invalid_json/invalid_schema/invalid_plan/provider_error 固定分类，异常原文不输出。保留 25 秒与模式总时限，不通过无限等待掩盖失败。

检查发现只有两个文档候选的显式 Skill 也携带地图、天气和文件规则。现在公开只读 Skill 使用更短的通用规划指令，保留 Schema、依赖绑定、质量反馈、公开查询和权限边界；无 Skill 或其他任务继续原提示。定向回归验证提示缩短且关键约束保留。修改后 FastAPI 真实浏览器查证成功：resolve/query、12 条持久化来源、Tool 阶段 36,305 ms、消息 done、浏览器错误 0；事实核验正确区分 Depends 注入依赖、不自动转换同步函数，以及 time.sleep 阻塞事件循环。单次成功不能证明 Provider 不再超时。

测试断言也修正了“注入依赖/依赖注入”、URL/标签引用以及“后续操作开启事务/不会立即开启事务”的合法等价表达，并以两种正确表达及三种错误/不充分表达核对固定规则。不能把这些断言误判记为业务错误。这些规则仅用于固定题目的回归脚本，没有按题目改写生产回答。

联合复验另一次出现 SQLAlchemy 仅完成库定位，下一轮没有产生可执行调用，按 tool_planning_unavailable 收口为未完成查证。它不同于答案错误和 25 秒超时；本报告保留该失败，不能声称本次所有在线尝试零失败。默认验收脚本遇到业务未完成仍返回失败，并带 Schema 诊断事件以便继续排查。

## 五、真实 Key 验收与工具调用全景（同日后续）

用户将 Exa/Context7 Key 放入 backend/.env 后，检查发现 Settings 和 CredentialResolver 尚未识别对应环境变量。本次补齐 `EXA_API_KEY`、`CONTEXT7_API_KEY` 的读取，同时保持 `ALLOW_ENV_TOOL_CREDENTIAL_FALLBACK=false`。通过已有账号凭据接口将两项 Key 加密保存到固定测试账号，其他账号不会因此使用共享 Key；实际 .env 未修改、未提交。
