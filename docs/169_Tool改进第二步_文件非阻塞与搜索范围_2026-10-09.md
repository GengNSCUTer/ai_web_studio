# Tool 四步改进第二步：文件执行与搜索范围

日期：2026-10-09。范围对应 [167 审查报告](167_工具调用审查与主流方案对标_2026-10-09.md)第 2、6 项；第一步改动继续保留。本轮不调整候选筛选、不扩大权限、不增加 Tool。

## 一、宏观变化

以前文件工具虽有 async 入口，却直接做同步 SQL 查询和文本遍历，慢查询可能挡住同一个事件循环里的其它请求；搜索又只检查最近最多 120 个可访问文件，返回空结果时没有说明未查完。

现在同步文件操作交给线程池，每次调用在该线程内创建和关闭独立数据库会话。普通搜索一次检查最多 120 个文件，报告本页实际检查数量、是否还有未检查文件和继续查询位置。已知准确文件名或文件 ID 时优先定向查找，不先挤进最新 120 个文件。仍是当前用户、当前项目内已上传文件的解析文本，不能访问任意本机路径。

例如项目有 126 个文件，最早的一份包含 CedarLedger 的“归档周期 17 天”。知道名称时可直接找到它；不知道名称时，第一页未命中但说明还有更早文件，下一轮用返回位置继续查，找到文件后读取原文，再生成回答。

## 二、代码怎样完成

```text
Planner 输出 list/search/read/propose_edit 的参数
  → Executor 校验 Schema、工具权限和当前项目
  → WorkspaceFileToolProvider.run
  → 线程内创建独立 Session
  → 有范围限制的查询，或文件名/ID 定向查询
  → 列表/搜索取得脱离 ORM 的快照并释放连接
  → 线程内计算匹配分数
  → 对要返回的文件重新查权限、按固定顺序锁行、复核正文并补建版本基线
  → 提交基线、关闭会话，返回有范围说明的来源
  → 受限事实把继续查询位置传给下一轮 Planner
  → 最终模型根据实际文件证据和范围说明回答
```

| 实现文件 | 具体职责 |
| --- | --- |
| `backend/app/services/tools/providers/workspace_files.py` | `run` 把同步文件操作交给线程；`_run_isolated` 创建独立 Session；`_page` 查询并释放快照连接；`_refresh_provenance` 按文件 ID 排序锁行，确保并发读取不会重复创建同一版本；列表/搜索加入定向条件与范围说明。 |
| `backend/app/services/tools/providers/workspace_file_paging.py` | 编码并校验继续查询位置，绑定用户、项目、工具和原查询条件；按创建时间及 ID 继续，避免 offset 因新增文件而移位；签名按用途分隔，最长 160 字符。 |
| `backend/app/tool_manifests/default_tools.json` | list/search 的输入新增受控 `file_name`、`cursor`，search 另支持 `file_id`；描述分页语义；只将页数事实和继续位置加入 Planner 的受限投影。 |
| `backend/app/services/tools/planner.py` | 明确文件名定向、保持查询条件继续翻页、预算不足时不能宣称全局未命中的规划规则。 |
| `backend/app/services/external_context_service.py` | 文件页按页身份及文件 ID 去重；两个空页即使说明文字一样也分别保留，避免第二页位置被正文去重丢掉。 |
| `backend/tests/test_workspace_file_execution.py` | 15 项边界测试，包含非阻塞、连接释放、取消、调用者事务隔离、稳定翻页、隐藏敏感文件、来源投影与 PostgreSQL 并发版本检查。 |
| `scripts/workspace_files_real_e2e.py` | 两个真实浏览器/在线模型会话和独立 Worker 的搜索、读取、产物及原会话回写验收；清理全部临时数据。 |

独立会话使用调用者所绑定的 Engine，不能借用调用者当前 Connection 或 ORM Session。工具只提交自己的版本基线，不把尚未提交的用户消息、审批或 Worker 状态顺便提交。

## 三、范围与继续查询

列表每页最多 30 个文件，搜索每页检查最多 120 个文件、返回最相关的最多 5 个结果。敏感文件名仍被隐藏，文件正文中的凭据仍脱敏。扫描上限没有简单取消。

`cursor` 是服务端给出的“下次从哪里继续”的位置，不是权限凭据。下一次仍重新检查用户、项目和文件范围。修改位置、跨用户/项目复用，或者换了 query/file_name/file_id 却继续用旧位置，都拒绝执行并要求从第一页开始。

| 返回信息 | 含义 |
| --- | --- |
| `scanned_files` | 本页实际检查的可访问文件数，不是项目文件总数。 |
| `has_more`、`next_cursor` | 是否还有更早文件，以及下一次查询的位置。 |
| `coverage_complete` | 已到本次查询条件下的最后一页；不代表正文永远不变，也不代表此前页面都被注入最终上下文。 |
| `matched_files_total` | 当前页快照匹配的数量，不是整个项目的命中总数。 |
| `results_truncated` | 当前页匹配超过 5 个，返回结果有所取舍；需要时进一步收窄条件。 |
| `page_id` | 代码生成的页身份，仅用于区分空页，防止去重丢掉继续位置。 |

空结果改为“当前已检查范围未找到”，有下一页时同时说明尚有未检查文件。说明写入来源正文，最终回答模型能看到；继续位置等有限字段也进入下一轮 Planner，不开放文件正文作为规划指令。

## 五、边界与下一步

这次采用同步驱动 + 线程池 + 独立短会话，消除文件 Provider 对事件循环的直接阻塞；不是将全后端改成原生 AsyncSession，也不保证 SQL 自身更快。线程池/连接池仍有容量上限，正在执行的同步查询不能强杀；取消后线程在查询返回时检查取消标志，回滚并关闭自己的会话。

翻页按稳定排序继续，但不冻结跨请求的整库内容快照。翻页过程中修改/新增内容需要按任务需要重新搜索；选中来源会重新查询和复核，使片段和 revision 来自同一当前正文。搜索仍是轻量词法匹配，没有新增全文索引、语义文件搜索或一次扫描整个磁盘。

Planner 能使用继续位置，不保证每种措辞都形成最短路径；轮数、时长和输出预算仍生效，预算结束前没查完须明确说明范围。当前通过的是固定功能场景，不能把它写成所有工具的任务成功率或并发吞吐指标。

四步进度：第一步截止时间/部分结果完成；第二步文件非阻塞、范围、定向与继续搜索完成；第三步候选容量、文件口语和受控历史线索待开始；第四步再评估完整规划循环持久化及按需发现。Day 6 的 Redis 基础讲解和作答仍待完成，不因代码修复提前进入 Day 7。本轮未提交或推送。
