# Chat 与长期记忆并发容量优化

> 后续状态：[208](208_长期记忆数据库召回与LangGraph迁移取舍_2026-11-05.md)已将生产冷查询改为数据库词法/向量候选及修订标记缓存检查。本文保留该改造之前的测量、实现和当时边界，不再表示当前仍搬运全部记忆向量。

日期：2026-11-05。承接阿里灵犀互娱一面，将“有界读取”和“并发容量验证”合并实施。正式消息、记忆及撤销状态继续保存在 PostgreSQL，不改为 JSONL，不把 Redis 当事实库。

## 1. 实测结论

本次发现的主要问题是应用读取/处理量随历史和记忆数量增长，并非实测出了 PostgreSQL 的最大并发。长会话读取已改为有界；记忆提取按游标查询；重复问题的记忆召回引入 Redis 派生缓存。但不同问题未命中缓存时，仍需全量扫描当前范围内的记忆，冷查询是剩余瓶颈，不能说高并发已彻底解决。

同一服务器、默认连接池，以下为每格 24 个请求的 P95：

| 场景 | 修改前 | 修改后 | 实际读取变化 |
| --- | ---: | ---: | --- |
| 10,000 条历史，单并发 | 261.29 ms | 10.53 ms | 10,000 条正文 → 72 条 |
| 10,000 条历史，16 并发 | 4,247.62 ms | 286.59 ms | 近期 24 + 最早待摘要 48 |
| 1,000 条记忆，单并发、重复问题 | 1,281.31 ms | 39.94 ms | 命中后首次读取最多 8 条正文，仍查询版本清单 |
| 1,000 条记忆，16 并发、重复问题 | 42,281.50 ms | 948.44 ms | 跳过整批向量解析、问题向量调用及排序，注入前仍 PG 复核 |
| 1,000 条记忆，16 并发、关闭 Redis | — | 23,461.42 ms | 正文仍为 1,000 条；仅应用优化有收益但仍慢 |
| 1,000 条记忆，16 并发、每次不同问题 | — | 25,157.03 ms | Redis 全部 miss，仍扫描 1,000 条 |

最新完整矩阵 18 格、432 次计时读取无失败；不同问题另 24 次无失败。“无失败”不表示延迟合格。新旧矩阵没有线上流量、HTTP 入口和模型延迟，不能当 Chat 线上 QPS。短会话存在增加查询次数的开销：100 条历史/16 并发 P95 从 130.27 ms 到 325.05 ms，并非所有格子都变快。

## 2. 测试方法与证据

环境：PostgreSQL 18.3/pgvector，max_connections=100；SQLAlchemy 默认 QueuePool size=5、max_overflow=10；48 个逻辑 CPU。每次测试创建独立临时数据库，结束后仅删除本次库，不写真实用户的历史/记忆。合成正文约 500 字符，记忆向量 1,024 维；并发 1/8/16，每格 24 请求，预热不计入延迟。P99 也保留，但样本少，不作为稳定尾延迟承诺。

使用真实 PG 和 Redis，Embedding 用确定性本地测试替身，避免 API 延迟掩盖数据库/应用处理成本；不运行 Ollama。每个并发请求在自己的事件循环中调用同一服务，属于受控组件负载，不模拟完整 ASGI 接入。实际单用户 Chat 另有并发配额，不能将本组件的 16 并发说成一个账号正常通过 HTTP 同时生成 16 个回答。

修改前先执行旧仓库方法和旧记忆服务，再修改业务代码。所有原始及中间结果保留：

- [原始历史/记忆读取](../backend/evals/results/chat-memory-capacity-20261105-before.json)：18 格、432 次。
- [原始完整记忆服务](../backend/evals/results/chat-memory-capacity-20261105-before-service.json)：9 格、216 次。
- [中间有界读取与 Redis](../backend/evals/results/chat-memory-capacity-20261105-after.json)、[中间关闭 Redis](../backend/evals/results/chat-memory-capacity-20261105-after-no-redis.json)。
- [首次最终矩阵](../backend/evals/results/chat-memory-capacity-20261105-final.json)、[关闭 Redis 对照](../backend/evals/results/chat-memory-capacity-20261105-final-no-redis.json)。前者与无缓存对照末段有重叠负载，仅作中间证据。
- [最终复测 r2](../backend/evals/results/chat-memory-capacity-20261105-final-r2.json)：本表修改后主要来源，18 格、432 次，未同时运行另一套压力矩阵；服务器仍为共享环境，非独占性能实验。
- [每次不同问题](../backend/evals/results/chat-memory-capacity-20261105-unique.json)：24 次，全部 miss，单列而不混入缓存命中分数。
- [连接占用补测](../backend/evals/results/chat-memory-capacity-20261105-connections.json)：1,000 条规模、6 格/144 次；历史 16 并发峰值借出 15 个连接，记忆为 14 个，每格结束均归还为 0。这里测应用连接池，不代替 PG 全局活动/锁/CPU 监控。

旧完整记忆服务的跨线程 SQL/连接等待没有插桩，JSON 中原来的 0 是未采集占位，不能解读为零 SQL 或零等待；新脚本使用 ContextVar 跨线程记录 SQL，未测的池等待为 null。直接 Repository 矩阵的连接取得时间包含 checkout/pre-ping，不是纯数据库锁等待。SQL 客户端耗时也含结果传输和 Python 调度，不能直接当 PG 服务端执行时间。

采样 cProfile 显示，冷查询主要开销包括数字数组的逐维 Python 校验、反复分词和筛选，不只是数据库。现对数据库中缓存的向量采用严格数字 JSON/形状/有限非零校验和 NumPy 批量余弦，复用本轮词法分数，计算移出 Web 事件循环。外部模型新返回的向量仍走原严格校验；不是用线程池宣称 CPU 计算可以无限并行。

联合索引的真实 EXPLAIN ANALYZE 已保存在 r2：10,000 条会话的最近 24 个 ID 使用 `ix_messages_context_order` 的 Index Only Scan，服务端执行约 0.158 ms；这不是整个 Chat 的延迟。

## 3. 当前代码链路

### Chat 和滚动摘要

用户/assistant 在短事务内创建 → 读取近期 24 条、最早未摘要 48 条、已有摘要边界 → 提交前复制正文/附件值 → 外部调用 → 对实际使用窗口及 generation 重新查询比对 → 摘要和边界同事务保存 → 按原模式预算组装回答。

最多加载 73 条消息，非全部注入模型。最终近期消息仍分别按模式保留 10/16/24；数据库的 24 条保留窗口用于避免摘要越过未读积压，不是扩大 Prompt 限额。摘要一次最多推进最早连续批次，缺失边界仍重置。消息授权编辑/删除继续与摘要失效同事务执行；不再为了判断覆盖关系读取所有历史正文。

提交前复制值解决 ORM expire_on_commit 后逐条重读。附件批量加载，避免每条历史额外一条 SQL。重生成/编辑重答单独查实际最近用户，以该问题作为读取上界，避免大量后台回复导致误选摘要批次中的旧问题。摘要网络等待期间释放事务；新 generation 或窗口内容变化仍拒绝旧结果。

当前 `history_rows_loaded` 明示实际加载量；`truncated_history_messages` 仅指已加载窗口中被预算裁剪的数量，不冒充全会话总数。**历史展示接口的全量列表方法仍保留，前端完整历史游标分页未在本轮实现。**

### 后台记忆提取

验证本轮 done assistant → 检查未完成 Job → SQL 按用户消息、sequence 游标和本轮上界取最多 50 条 → 按字符预算形成最多 24 条的批次 → 原有 Job/证据快照/租约/版本与游标提交。

Worker 校验证据只按本 Job 的源 ID 查询；补积压只查询最新 done assistant，不再先读整段历史。仅遇到旧 sequence 为空的数据时按稳定顺序修复序号，该路径读取 ID/序号而非正文；不是所有会话每轮全量修复。

### 长期记忆与 Redis

PG 设置与有效版本清单 → Redis 查询相同问题的派生排名 → 命中且清单一致时取最多 8 个候选 ID → PG 重新检查 active、启用、TTL、用户/项目/来源范围、正文版本和当前设置 → 原记忆选择与预算渲染。

Redis 仅保存候选 ID、已有正文哈希、分数、配置分片与版本清单，不保存答案、正文、向量或模型密钥。查询字段包含问题文本，但含凭证/需要脱敏的问题不缓存，字段不出现在日志/Redis 顶层键中。按数据库、用户、项目隔离；默认 TTL 60 秒，每范围最多 8 个问题、单项 512 KiB；可用 `MEMORY_READ_CACHE_ENABLED=false` 关闭，`MEMORY_REDIS_URL` 可指向独立缓存实例。不配置新地址时复用知识任务 Redis。

命中仍查询 PG 的轻量版本清单，且最终按 ID 重新查正文。撤销、更正、到期、范围或模型配置变化导致重算；撤销后晚到的旧缓存填充不能恢复授权。TTL 只回收空间，不负责即时一致性。Redis 异常/损坏/超量回退 PG，不让缓存错误导致 Chat 失败。缓存网络等待前结束数据库短事务。

冷请求仍读取当前范围的全部合规记忆，保持旧事实的召回机会；排序后只对最多 8 个候选做最终 PG 正文复核，避免整批正文和向量读取两遍。并未引入长期记忆 ANN，也没有用“最近 200 条”悄悄丢掉旧事实。

## 6. 留下的边界与下一步

PG 在本次负载中没有连接失败，但不承诺更高并发或线上容量。100 条短历史有额外查询开销，后续可测窗口查询合并，不能只摘录长会话收益。不同新问题仍 O(N) 读取和计算；下一步应优先评估记忆专用持久索引/候选召回，而非继续加 Redis 查询缓存、扩连接池或更换 JSONL。数万条记忆的元数据清单也会变大，本轮不宣称已解决。

缓存与 Redis Stream 共用实例是本机折中；多用户部署建议通过 MEMORY_REDIS_URL 使用独立缓存实例、配容量/淘汰策略，不能对承载队列的实例直接开启 allkeys 淘汰，更不能把不同 DB 号当作物理内存隔离。真实容量验收仍需多用户 HTTP、多进程、持续负载及数据库资源指标；本轮不把这项后续工作宣称完成。
