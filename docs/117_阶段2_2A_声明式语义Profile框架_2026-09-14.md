# 阶段 2.2A：声明式语义 Profile 框架

日期：2026-09-14
范围：建立可复用的 Tool 业务质量 Profile 机制；不接入真实外部 Tool 合同，不新增 Tool、权限或同步轮数。

## 1. 为什么需要 Profile

单纯的 JSON Schema 只能证明响应结构合法，不能证明结果对当前任务有业务价值。例如 `paths: []` 可以符合输出 Schema，但不能直接回答路线问题。若每个 Provider、每个 Tool 都写一份 Python evaluator，重复逻辑会迅速膨胀，也难以保证不同 Provider 的质量口径一致。

本阶段采用三层边界：Provider Adapter/Mapper 负责把不同供应商的返回整理为稳定的内部 evidence envelope；声明式 Profile 负责复用“证据、身份、结果集合和集合项”的确定性规则；只有真正特殊的审批、写入或跨字段业务才保留 Tool-specific evaluator。LLM 可以帮助生成合同草稿或离线发现异常，但不能成为运行时质量门。

## 2. 当前合同模型

质量合同新增两个字段：

| 字段 | 作用 |
| --- | --- |
| `semantic_profile` | 从固定白名单选择能力类型：`web_search`、`geo_lookup`、`weather`、`distance`、`route`、`poi_search`、`file_list`、`file_search`、`file_read`、`artifact_list`、`artifact_read`、`approval_draft`、`file_revision`。未知 Profile 在 Catalog 加载阶段失败。 |
| `profile_mapping` | 声明式 JSON Pointer 映射，不包含可执行代码。所有 Source 路径必须从 `/sources/` 开始；集合项路径只能相对集合项，禁止从 item 路径跳回整个响应。 |

`profile_mapping` 当前支持：

- `evidence_paths`：至少一个非空业务证据字段；
- `identity_paths`：至少一个非空定位字段，例如 URL、地点标识或文件 ID；
- `collection_paths`：可选的结果集合路径；搜索、地理、天气、距离、路线和 POI Profile 要求声明集合；
- `item_evidence_paths`：集合项至少一个非空证据字段；
- `min_collection_items`：集合最少条数，限制在 1～128。

路径支持有限的 `/sources/*/...` 通配，只读解析最多处理 32 个集合、128 个集合项；超过边界会给出确定性质量原因。合同还会拒绝未知字段、错误的绝对/相对路径、反向跳转和不完整的集合配置。

## 3. 运行行为

Profile 评估只读取 Executor 已脱敏的 Source envelope，不执行文本，不联网，不读取模型生成规则，也不信任远端 MCP metadata。非空结果需要同时满足映射的证据和身份字段；集合存在时还需满足集合项是对象、数量达到下限且每项有业务证据。

空结果仍遵循阶段 2.1 的信任边界：空集合只有在可信本地 Adapter 声明 `result_semantics=empty_answer` 且 manifest `allow_empty=true` 时才可通过；普通空 evidence、未知语义和远端 MCP 自称“正常空结果”继续 `invalid`。因此 Profile 不会把“结构合法但业务空洞”的 Provider 响应放行给依赖步骤。

## 4. 泛化性验证

离线 fixture 验证了同一个 `web_search` Profile 可复用到两种不同 Provider 结构：一种使用 `results/title/url/content`，另一种使用 `items/name/href/text`。两者只改变 `profile_mapping`，评估器、错误原因和 Trace 语义保持一致。

同时覆盖了以下负例：缺证据、缺身份、集合项缺字段、集合项不是对象、空集合未声明 `empty_answer`、Profile 未提供集合映射、item 路径携带 `/sources/` 越界、未知映射字段和超过集合/条目上限。这证明当前框架具备“同类能力复用、Provider 字段差异由映射吸收、边界由代码固定”的基础泛化性，但还不代表高德/Tavily 的生产合同已经完成。

## 5. 主要实现文件

- `backend/app/services/tools/quality.py`：Profile 白名单、合同校验、通配 JSON Pointer、集合/集合项确定性评估。
- `backend/app/services/tools/catalog.py`：加载 manifest 时复用质量合同校验，阻止非法 Profile 进入运行时。
- `backend/app/services/tools/executor.py`：继续作为最终质量门入口，确保 Profile 只能读取可信 Adapter 规范化结果。
- `backend/tests/test_tool_quality.py`：跨 Provider 形态、合法/非法集合、边界与失败关闭测试。
- `backend/tests/test_tool_executor.py`：验证 Profile 在 Executor 归一化之后执行，远端 Adapter 不能伪造 `empty_answer`。

## 7. 后续实际完成情况

阶段 2.2B/C 已在本轮继续完成，详细记录见 [118_阶段2_2B_C_真实Provider映射与请求一致性_2026-09-14.md](118_阶段2_2B_C_真实Provider映射与请求一致性_2026-09-14.md)：

- 统一 MCP payload 提取，优先 `structuredContent`，兼容 `content[].text` JSON；
- Tavily/高德 Mapper 只输出有限 canonical 字段，默认 Tool 切换为专用 Profile；
- 增加真实 Provider fixture 和坏响应失败关闭测试；
- Executor 将已通过 Schema 的 normalized arguments 作为受控 `request_context`，对天气、地理编码和路线执行有限确定性一致性检查；
- 真实只读调用覆盖 Tavily、天气、geo、关键词/周边 POI、距离和驾车路线，均获得 `quality_status=valid`；
- 这仍然是结构和请求字段一致性，不代表完整语义相关性或地理空间证明。

## 8. 提交前复审收口

阶段 2 复审后，默认 Tool 不再只覆盖外部查询：Artifact 读取、工作区文件 list/search/read、编辑预览及受控文件写入全部接入 Profile。`approval_draft` 合同要求 `applied=false`，只能表达“可审查、尚未写入”；`file_revision` 合同要求 `file_id + revision_id + applied=true`，才表示持久化修改完成。

此外，`result_semantics` 的信任边界已从“声明 adapter_type”收紧为“项目内 `ToolAdapterRunner` + 对应本地 Provider 实例”。动态数据库 MCP 默认带 `require_semantic_profile=true`，在新增经审核的 Mapper/Profile 前可被登记和诊断，但不能为后续 Tool、Result Binding 或最终回答提供有效 evidence。
