# 工具调用协议与插件化架构研究

更新时间：2026-05-29

本文档整理 AI Web Studio 后续工具调用层的设计方向，重点回答几个问题：

1. 有没有一种协议，让工具自己提供描述、参数 schema 和调用入口，平台只要接入后就能让 LLM 发现并调用？
2. MCP、OpenAPI、Claude Skills / SKILL.md、Dify 插件、高德 CLI / Skill 分别是什么，边界在哪里？
3. 我们当前项目如果要从“规则正则调用工具”升级为“可扩展 Agent 工具系统”，应该怎么设计？
4. 后续接入新工具时，怎样尽量做到不改聊天主链路、不改旧工具代码？

---

## 1. 当前问题背景

AI Web Studio 当前已经有外部工具调用能力：

- Tavily 网页搜索
- 高德天气
- 高德地图
- Tool Trace 持久化
- 工具来源卡片展示
- 用户级工具 API Key 配置

但是当前工具选择仍然偏传统工程写法：

```text
用户问题
  -> 正则规则识别天气/地图/网页
  -> 调用固定工具
  -> 工具内部继续用正则解析参数
  -> 结果注入模型上下文
```

这种方式能快速跑通 MVP，但问题已经显现：

- 用户换一种说法，规则可能失效。
- “他们 / 刚才那个 / 上面提到的地点”这类指代需要上下文改写，正则很难稳定处理。
- “分别离某地多远，哪个近一点”应该走距离测量，而不是单条路线规划。
- “请再次确认，并说一下具体路线”需要从上一轮工具结果恢复参数。
- 新增工具时需要继续改 router 规则，后续会变成 if/elif 堆叠。

所以工具层需要从：

```text
规则路由 + query 字符串工具
```

升级为：

```text
工具自描述 + LLM 结构化规划 + 参数 schema 校验 + adapter 执行 + Tool Trace
```

## 2. 行业里有没有“工具自己描述自己”的协议？

有。当前最接近这个目标的是 **MCP：Model Context Protocol**。

### 2.1 MCP 是什么

MCP 是 Anthropic 发起的开放协议，用于标准化 AI 应用如何连接外部工具、数据源和服务。

MCP 的关键点是：

- MCP server 可以暴露 tools。
- MCP client 可以通过 `tools/list` 获取工具列表。
- 每个 tool 包含：
  - name
  - description
  - inputSchema
- client 可以通过 `tools/call` 调用工具。
- 工具结果可以返回文本、图片、资源、结构化内容等。

MCP 官方 tools 文档给出的工具结构就是这种模式：

```json
{
  "name": "get_weather",
  "description": "Get current weather information for a location",
  "inputSchema": {
    "type": "object",
    "properties": {
      "location": {
        "type": "string",
        "description": "City name or zip code"
      }
    },
    "required": ["location"]
  }
}
```

这正是“工具自己提供描述和调用格式，模型看到后知道怎么调用”的核心。

参考：

- MCP Tools 官方文档：https://modelcontextprotocol.io/specification/2024-11-05/server/tools
- MCP Client Best Practices：https://modelcontextprotocol.io/docs/develop/clients/client-best-practices
- MCP Security Best Practices：https://modelcontextprotocol.io/specification/2025-06-18/basic/security_best_practices

### 2.2 MCP 解决了什么

MCP 解决的是传统工具集成里的 `N x M` 问题。

以前每个 AI 应用要分别适配每个工具：

```text
Chat App A -> GitHub adapter
Chat App A -> Notion adapter
Chat App A -> Google Drive adapter
Chat App B -> GitHub adapter
Chat App B -> Notion adapter
...
```

MCP 希望变成：

```text
GitHub MCP Server
Notion MCP Server
Google Drive MCP Server

任何支持 MCP 的 AI Client 都能连接它们
```

对我们的启发：

```text
后续 AI Web Studio 不应只支持“本地写死的 Python 工具”
而应该预留 MCP connector，让外部 MCP server 成为工具来源之一
```

### 2.3 MCP 不等于“完全无人工审核”

MCP 可以自动发现工具，但不代表可以自动信任工具。

风险包括：

- 工具描述本身可能被污染，诱导模型误用。
- 工具返回内容可能包含 prompt injection。
- 工具权限可能过大。
- 工具调用可能泄露数据。
- 本地 STDIO 工具可能引入命令执行风险。
- 工具数量太多会造成 context bloat。

MCP 官方安全建议包括：

- 明确展示哪些工具暴露给模型。
- 对危险操作做用户确认。
- 限制权限范围。
- 审计工具调用。
- 标记危险命令模式。
- 防止 token passthrough 和越权访问。

所以合理策略是：

```text
自动发现
但不自动全量启用

自动加载 schema
但允许人工审核和覆写描述

模型可调用
但高风险工具需要权限、审计和用户确认
```

## 3. OpenAPI、MCP、Skill、插件分别是什么

这几个概念容易混淆。

### 3.1 OpenAPI

OpenAPI 是描述 HTTP API 的标准。

它主要描述：

- API 路径
- HTTP 方法
- 参数
- 请求体
- 响应体
- 认证方式

官方 OpenAPI 文档说明，OpenAPI Specification 用于描述通过 HTTP 或类似 HTTP 协议访问的远程 API。

参考：

- OpenAPI 官方介绍：https://learn.openapis.org/introduction.html

OpenAPI 更像：

```text
给程序员和代码生成器看的 HTTP API 合约
```

它可以用于自动生成 SDK、测试、文档，也可以作为工具导入来源。

但 OpenAPI 不是天然适合直接给 LLM 看，原因：

- endpoint 往往太多。
- 参数描述偏工程化。
- 缺少 when_to_use / when_not_to_use。
- 一个用户意图可能需要多个 endpoint 编排。
- 工具返回格式不一定适合直接注入模型上下文。

因此 OpenAPI 更适合作为：

```text
工具 manifest 的生成来源
```

而不是直接作为最终工具层。

### 3.2 MCP

MCP 更像：

```text
给 AI Agent 看的工具协议
```

它不仅描述工具 schema，还规定 client/server 如何发现工具和调用工具。

MCP 常见能力：

- tools/list
- tools/call
- resources
- prompts
- 不同 transport：stdio、HTTP、SSE、Streamable HTTP 等
- 授权和安全规范

OpenAI Agents SDK 已经支持 MCP server 接入，文档里列出了 hosted MCP、stdio、本地 streamable HTTP、SSE 等不同方式。

参考：

- OpenAI Agents SDK MCP 文档：https://openai.github.io/openai-agents-python/mcp/
- OpenAI Agents JS MCP 文档：https://openai.github.io/openai-agents-js/guides/mcp/

Claude 也支持 MCP Connector，可以连接远程 MCP servers，并在 Claude 产品和 API 中使用。

参考：

- Claude Connectors Overview：https://claude.com/docs/connectors/overview
- Claude MCP Connector API 文档：https://platform.claude.com/docs/en/managed-agents/mcp-connector
- Claude Help Center MCP Connectors：https://support.claude.com/en/articles/14503689-mcp-connectors

### 3.3 Claude Skills / SKILL.md

Skills 和 MCP 不是同一种东西。

Claude 官方帮助文档对二者的定位非常清楚：

```text
MCP connections give Claude access to tools.
Skills teach Claude how to use those tools effectively.
```

也就是说：

- MCP：提供能力，负责“能做什么”。
- Skill：提供知识和流程，负责“应该怎么做”。

Claude Code 的 Skills 是文件系统里的 `SKILL.md` 包，Claude 会根据 description 自动决定是否加载。

参考：

- Claude Code Skills 文档：https://docs.claude.com/en/docs/claude-code/skills
- Claude Help Center What are Skills：https://support.claude.com/en/articles/12512176-what-are-skills
- Claude Skills vs MCP 官方博客：https://www.claude.com/blog/skills-explained

对我们的启发：

```text
工具 manifest 只告诉模型这个工具怎么调用。
Skill / workflow 文档告诉模型在某个业务场景下如何组合工具。
```

例如高德地图：

- MCP / Tool manifest 提供：
  - place.resolve
  - distance.matrix
  - route.plan
  - poi.search
- Skill 提供：
  - “如果用户问哪个地点更近，先用 distance.matrix 排序，再必要时 route.plan 展开最近路线。”
  - “如果用户问再次确认具体路线，要复用上一轮 tool trace 中的 origin/destination。”

### 3.4 Dify 插件与 MCP

Dify 已经支持添加 MCP server。

Dify 文档说明，添加 MCP server 后，MCP tools 会出现在 agent、workflow 和 agent node 中，也可以自定义工具描述、参数自动/固定模式等。

参考：

- Dify MCP Tools 文档：https://docs.dify.ai/en/use-dify/build/mcp
- Dify 发布应用为 MCP Server：https://docs.dify.ai/en/guides/application-publishing/publish-mcp

这说明主流 AI 平台的方向是：

```text
平台自身有插件系统
同时也逐步把 MCP 作为外部工具标准入口
```

### 3.5 LangChain / LangGraph 与 MCP

LangChain 现在有 MCP adapters，可以把 MCP tools 转成 LangChain tools。

参考：

- LangChain MCP Adapters：https://reference.langchain.com/python/langchain-mcp-adapters
- LangChain MCP 文档：https://langchain-5e9cc07a.mintlify.app/oss/python/langchain/mcp

这说明 MCP 不是替代 LangChain / LangGraph。

更准确地说：

```text
MCP 是工具协议
LangChain / LangGraph 是应用编排框架
```

二者可以组合：

```text
MCP server 提供工具
LangGraph agent 决定何时调用、如何编排、多步循环如何推进
```

## 4. 高德 CLI / Skill 与 REST API / MCP 的关系

我们之前讨论过高德地图官方 CLI / Skill。

参考：

- 高德地图 CLI 概述：https://lbs.amap.com/api/cli/map-cli/summary
- ClawHub 高德 CLI Skill：https://clawhub.ai/lbs-amap/amap-cli-skill

### 4.1 高德 REST API

高德 REST API 是最底层的 HTTP 能力。

适合：

- 后端服务调用
- 多用户 Web 应用
- 可控稳定的 API 请求
- 路线、天气、POI、地理编码等数据能力

我们当前项目最适合继续以 REST API 为主路径。

### 4.2 高德 CLI

高德 CLI 把地图操作封装成命令行。

例如：

```bash
amap-gui route --from 北京南站 --to 天安门 --type driving
amap-gui searchPOI --keyword 星巴克 --city 北京
```

它适合：

- 本地 Agent 操作地图 GUI
- 地图可视化
- 读取地图状态和用户点击事件

但它不适合当前直接塞进 FastAPI 主链路，原因：

- 共享 Linux 服务器环境不一定适合 GUI 容器。
- 多用户并发会话难管理。
- CLI subprocess 需要更强安全隔离。
- 命令参数必须严格校验，不能让模型自由拼 shell。

### 4.3 高德 Skill

高德 Skill 更像“告诉某个 Agent 怎么使用高德 CLI 的说明包”。

它不是标准 MCP server。

可以理解为：

```text
REST API：底层能力
CLI：命令行封装
Skill：教 Agent 怎么使用 CLI
MCP：标准工具发现和调用协议
```

### 4.4 后续能否接入

可以，但建议作为后续可选工具来源：

```text
adapter_type = cli
tool_key = amap.visual.route
```

更理想的是：

```text
把高德 CLI 包装成 MCP server
AI Web Studio 通过 MCP connector 接入
```

但当前主线仍建议用 REST API + 本地 manifest + Python adapter。

## 5. 主流大厂与平台工具调用趋势

### 5.1 OpenAI

OpenAI 当前主要方向：

- Function Calling
- Structured Outputs
- Responses API tools
- Agents SDK
- Hosted MCP tools
- Apps SDK 基于 MCP 扩展 UI 和工具交互

核心思想：

```text
工具有 schema
模型输出结构化 tool call
应用执行工具
工具结果返回模型
```

参考：

- OpenAI Function Calling：https://platform.openai.com/docs/guides/function-calling
- OpenAI Structured Outputs：https://platform.openai.com/docs/guides/structured-outputs
- OpenAI Agents SDK MCP：https://openai.github.io/openai-agents-python/mcp/
- OpenAI Apps SDK：https://help.openai.com/en/articles/12515353-build-with-the-apps-sdk

### 5.2 Anthropic / Claude

Anthropic 当前方向：

- Claude Tool Use
- MCP Connectors
- Skills
- Connectors Directory
- 面向行业场景的 connectors + plugins

Claude 的结构很有参考价值：

```text
MCP Connector：连接工具和数据
Skill：描述工作流和最佳实践
Plugin：面向特定业务场景打包能力
```

这对我们项目很有启发：

```text
工具层不要只解决“能调用 API”
还要解决“在什么业务流程里如何使用这些 API”
```

### 5.3 Dify / Coze 类平台

Dify 这类平台的工具系统通常包含：

- 工具 marketplace / plugin
- 工具授权
- 参数 schema
- Agent 或 workflow 节点
- 工具执行日志
- MCP server 接入

这类平台更接近我们长期要做的“个人知识库 + 工具扩展工作台”。

### 5.4 LangChain / LangGraph

LangChain / LangGraph 更偏应用编排：

- Tools 抽象
- Agent
- Graph 编排
- MCP adapter
- Middleware
- Tool selection

它们适合后续当我们进入复杂 Agentic RAG 阶段时参考。

当前阶段不一定要立刻上 LangGraph，但工具层接口应该设计得未来能接。

## 6. 对 AI Web Studio 的架构建议

### 6.1 总体目标

我们后续工具层目标不是：

```text
再写更多正则
```

而是：

```text
工具自描述
LLM 可发现
参数 schema 化
adapter 可扩展
权限可控
trace 可观测
```

### 6.2 推荐目标架构

```text
User Query + Recent History + Tool Trace
  -> ToolCatalog
  -> ToolPreselector
  -> LLMToolPlanner
  -> ToolArgumentValidator
  -> ToolExecutor
  -> Adapter
  -> ExternalSource / ToolResult
  -> Tool Trace
  -> Prompt Context
  -> LLM Answer
```

### 6.3 ToolCatalog 支持三类来源

```text
ToolCatalog
  ├── Local Manifest Tools
  ├── OpenAPI Imported Tools
  └── MCP Server Tools
```

第一类：Local Manifest Tools

- 我们自己维护。
- 适合 Tavily、高德、知识库、内部工具。
- 最可控。

第二类：OpenAPI Imported Tools

- 从 OpenAPI spec 导入。
- 自动生成初版 manifest。
- 需要人工筛选和润色描述。

第三类：MCP Server Tools

- 连接 MCP server。
- 通过 tools/list 自动发现工具。
- 通过 tools/call 调用。
- 需要权限、审核、缓存、禁用机制。

### 6.4 Adapter 类型

建议 ToolExecutor 支持：

```text
python_adapter
http_adapter
mcp_adapter
cli_adapter
```

含义：

- `python_adapter`：本地 Python handler，例如高德 REST 编排、Tavily、知识库检索。
- `http_adapter`：普通 REST API / OpenAPI 生成工具。
- `mcp_adapter`：远程或本地 MCP server。
- `cli_adapter`：高德 CLI、其他命令行工具。需要严格安全限制。

### 6.5 工具 manifest 建议结构

```json
{
  "tool_key": "amap.distance.matrix",
  "provider": "amap",
  "category": "map",
  "display_name": "高德距离测量",
  "description": "用于计算一个或多个起点到同一个终点的驾车/步行距离，并比较哪个更近。",
  "when_to_use": [
    "用户问 A 离 B 多远",
    "用户问多个地点分别到 B 多远",
    "用户问哪个地点离 B 更近",
    "用户问两地相距多少公里"
  ],
  "when_not_to_use": [
    "用户要求详细导航步骤时，应使用 amap.route.plan",
    "用户只是查询天气时，应使用 amap.weather.current"
  ],
  "input_schema": {
    "type": "object",
    "properties": {
      "origins": {
        "type": "array",
        "items": { "type": "string" },
        "description": "一个或多个起点"
      },
      "destination": {
        "type": "string",
        "description": "终点"
      },
      "mode": {
        "type": "string",
        "enum": ["driving", "walking"],
        "default": "driving"
      },
      "compare_nearest": {
        "type": "boolean",
        "default": false
      }
    },
    "required": ["origins", "destination"]
  },
  "adapter_type": "python",
  "handler": "app.services.tools.providers.amap_distance:AmapDistanceTool",
  "risk_level": "read_only"
}
```

### 6.6 LLMToolPlanner 输出建议

```json
{
  "intent": "distance_compare",
  "standalone_query": "深圳松岗、广州南站分别到汕头市潮阳区西凤村有多远，哪个近一点",
  "tool_calls": [
    {
      "tool_key": "amap.distance.matrix",
      "arguments": {
        "origins": ["深圳松岗", "广州南站"],
        "destination": "汕头市潮阳区西凤村",
        "mode": "driving",
        "compare_nearest": true
      },
      "confidence": 0.93,
      "reason": "用户询问多个地点到同一目的地的距离并比较近远。"
    }
  ],
  "requires_clarification": false,
  "clarification_question": null
}
```

### 6.7 工具执行安全边界

工具层必须有：

- 用户级凭证隔离。
- 工作区级工具启用/禁用。
- read-only / write / destructive 风险等级。
- 高风险工具调用前确认。
- 参数 schema 校验。
- 调用超时。
- 输出大小限制。
- Tool Trace 持久化。
- 工具来源和版本记录。
- MCP server allowlist / denylist。
- CLI adapter 命令白名单。

## 7. 我们项目的落地路线

### 7.1 第一阶段：本地 manifest 标准化

目标：

- 把当前 `default_tools.json` 升级为完整 manifest。
- 增加 input_schema、when_to_use、when_not_to_use、adapter_type、risk_level。
- 不再只靠 tool_key/provider/category。

### 7.2 第二阶段：拆高德工具

把 `amap.map.basic` 拆为：

```text
amap.place.resolve
amap.distance.matrix
amap.route.plan
amap.poi.search
amap.weather.current
```

优先实现：

- `amap.distance.matrix`
- `amap.route.plan`

直接解决当前：

- 多起点到单终点距离比较
- 具体路线确认
- 上一轮路线跟进

### 7.3 第三阶段：LLMToolPlanner

目标：

- 让 LLM 根据工具 manifest 输出结构化 tool_calls。
- 使用 Pydantic / JSON Schema 校验。
- 校验失败时 retry 一次。
- 仍保留规则 fallback。

### 7.4 第四阶段：MCP Connector 预留

目标：

- 支持配置 MCP server。
- 拉取 tools/list。
- 缓存 tool schema。
- 用户选择启用哪些 MCP tools。
- 通过 mcp_adapter 执行 tools/call。

第一版可以先只支持 HTTP/SSE/Streamable HTTP，不急着支持本地 STDIO。

### 7.5 第五阶段：OpenAPI Importer 预留

目标：

- 用户上传或填写 OpenAPI spec URL。
- 系统解析 endpoint。
- 用户选择要暴露哪些 endpoint。
- 系统生成初版 tool manifest。
- 用户可以编辑 description、when_to_use、参数说明。

### 7.6 第六阶段：Skill / Workflow 层

目标：

- 支持为工具组合定义 workflow instruction。
- 例如地图 Skill：
  - 比较距离先用 `amap.distance.matrix`
  - 需要详细路线再用 `amap.route.plan`
  - 地点不明确时先用 `amap.place.resolve`
  - 多候选不确定时向用户澄清

这类似 Claude Skills 的定位：

```text
MCP / tools 提供能力
Skill / workflow 教模型如何使用能力
```

---

## 8. 关键结论

1. 存在“工具自描述协议”，最接近的是 MCP。
2. OpenAPI 是 HTTP API 合约，适合生成工具，但不等于 Agent 工具协议。
3. Claude Skills / SKILL.md 不是工具协议，而是工作流和知识注入机制。
4. Dify / OpenAI / Claude / LangChain 都在往 MCP + tool schema + adapter 的方向靠拢。
5. 高德 CLI / Skill 适合作为地图可视化插件参考，不建议当前直接接入 FastAPI 主链路。
6. AI Web Studio 应该做成：

```text
Local Manifest + OpenAPI Importer + MCP Connector + LLMToolPlanner + Adapter Executor
```

7. 新增工具的理想路径：

```text
如果工具提供 MCP：添加 MCP server，审核后启用。
如果工具提供 OpenAPI：导入 spec，生成 manifest，人工微调。
如果只有普通文档/API：手写 manifest + adapter。
```

8. 后续最值得优先做的是：

```text
本地工具 manifest 标准化
高德地图工具拆分
LLMToolPlanner 第一版
```

### 10.3 一个重要工程结论

MCP 解决了“工具发现、描述、schema、调用协议”的问题，但不自动解决“复杂自然语言问题怎么拆成多个工具调用”的问题。

以高德地图为例：

- MCP server 暴露的是 `maps_geo`、`maps_distance`、`maps_direction_driving` 等细粒度工具。
- 用户问的是“深圳松岗离汕头市潮阳区西凤村多远”。
- 中间仍需要 planner / workflow 做：
  1. 抽取起点终点。
  2. 调 `maps_geo` 得到坐标。
  3. 调 `maps_direction_driving` 或 `maps_distance`。
  4. 格式化结果给模型。

因此后续方向不是“接了 MCP 就结束”，而是：

```text
MCP 提供工具协议
ToolCatalog 管理工具元数据
LLMToolPlanner / Workflow 负责任务拆解与工具组合
ToolAdapterRunner 负责统一执行和 fallback
```

### 10.4 当前保留的兼容逻辑

为了避免一次性重构导致功能回退，本轮保留：

- 旧 Tavily REST provider
- 旧高德 REST provider
- 高德地点/路线抽取逻辑
- 天气街镇级 geocode/adcode fallback

但它们不再位于聊天主链路，而是作为 `python` adapter fallback 存在。

这比旧架构更可维护：

- 主链路只认 `ToolExecutor`。
- `ToolExecutor` 只认 `ToolCatalog` 和 `ToolAdapterRunner`。
- 工具细节被隔离到 manifest + adapter。

### 10.5 后续建议

下一步不要继续堆正则，而应进入：

1. `LLMToolPlanner`：
   - 使用模型基于 manifest 精简描述生成结构化 tool calls。
   - 对输出做 JSON schema 校验。
   - 失败时回退到当前 `ManifestToolPlanner`。
2. 高德工具拆细：
   - `amap.geo`
   - `amap.weather`
   - `amap.route`
   - `amap.distance`
   - `amap.poi_search`
   - `amap.district`
3. 工具参数校验：
   - 当前只保存 schema，尚未对所有工具执行严格 schema validation。
4. 用户自定义工具：
   - 先支持用户注册远程 MCP server。
   - 再考虑 OpenAPI importer。
