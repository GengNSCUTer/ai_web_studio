# 阶段 2.2B/C：真实 Provider Mapper、Profile 接入与请求一致性

日期：2026-09-14
范围：在阶段 2.2A 声明式 Profile 框架上，接入真实 Tavily/高德 MCP 响应形态，验证规范化字段和请求/结果一致性；不新增工具、不扩大权限、不记录密钥或原始远端响应。

## 1. 2.2B：真实响应解析

真实探测得到两种 MCP 返回形态：

- Tavily 返回 `result.structuredContent.results`，同时带一份兼容性的 `content[].text` JSON；
- 高德当前主要返回 `result.content[].text` JSON，部分 MCP 版本也可能返回 `structuredContent`。

统一入口 `extract_mcp_payload()` 现在优先读取 `structuredContent`，缺失时再解析 `content` 中的 JSON 文本。高德参数归一化和最终结果 Mapper 共用这一入口，避免“最终 Mapper 能解析、路线参数预处理却解析不到坐标”的分叉问题。

Mapper 不再把完整远端响应作为 `metadata.raw` 保存，只保留质量门和 Result Binding 需要的 canonical 字段：

| 能力 | canonical 字段 |
| --- | --- |
| Tavily Search | `url`、`title`、`content`、`score` |
| 高德地理编码 | `formatted_address`、`location`、`adcode`、`city`、`level` |
| 高德天气 | `city`、`adcode`、`weather`、`temperature`、`reporttime` |
| 高德 POI | `id`、`name`、`location`、`address`、`type` |
| 高德距离 | `origin_id`、`destination_id`、`distance`、`duration` |
| 高德路线 | `origin`、`destination`、`distance`、`duration` |

Tavily 的综合 `answer` 不再伪装成一个没有 URL 的网页结果；只有同时具备正文和 URL 的网页结果进入 `web_search` collection。高德 geo、route、POI 已分别使用专用 Mapper；未知/缺关键字段的已知 Mapper 返回空 Source，由质量门失败关闭，不回退为“任意 JSON 非空即有效”。

## 2. 2.2C：请求/结果一致性

阶段 2.2A 只能证明结果结构上有证据和身份，不能证明“结果确实对应这次请求”。本阶段增加受控 `request_matches`：

```text
Planner 参数
  -> Executor Input Schema / 默认值 / fixed 参数校验
  -> 形成 normalized request_context
  -> Profile 对 canonical result 做确定性字段比较
```

`request_context` 只来自 Executor 已通过 Schema 校验的参数，不来自模型原始文本、display_text 或远端自称的 `matched=true`。当前接入：

- `weather`：城市/adcode 与返回城市做宽松文本比较；
- `geo_lookup`：若请求显式带 city，则与返回城市比较；地标名称不强行要求等于行政区格式，避免把合法“广州塔 -> 广东省广州市海珠区”误判为失败；
- `route`：规范化后的 origin/destination 坐标与返回起终点做坐标比较；
- 其它 Profile 仍依赖 canonical identity 和结构检查，暂不声称完成空间范围或语义相关性证明。

请求参数缺失时，只有可选字段的匹配规则会跳过；必填字段已经由 Executor Schema 校验保证存在。匹配失败返回确定性 `request_result_mismatch:<index>`，不解锁依赖步骤。

## 5. 当前边界

本阶段完成的是结构化业务质量和有限请求一致性，不等同于完整语义相关性或地理空间证明。没有使用 LLM 作为最终质量门，也没有把 Provider 的自然语言摘要当作可信指令。后续如需校验 POI 城市范围、路线空间覆盖或搜索结果与 query 的语义相关性，应另建可解释的离线评测/软评分层，不能直接放宽当前确定性质量门。

## 6. 提交前复审补正

复审发现，高德路线 Adapter 可以将合法地点名预处理为实际请求坐标；若质量门仍只读取 Schema 校验后的原始地点名，就会与高德路线结果中的坐标产生错误的 `request_result_mismatch`。现已将质量门的请求上下文调整为：默认使用 Schema 校验后的参数；仅当调用由项目内受控 `ToolAdapterRunner` 执行 MCP 时，才以该 Runner 已脱敏、且不扩展原字段范围的实际 MCP 参数覆盖对应字段。

新增正反测试：受控 MCP Adapter 的“地点名 -> 坐标 -> 路线坐标返回”可通过质量门；普通注入 Adapter 即使伪造相同 `mcp_arguments` 也不能覆盖原始上下文，仍会失败关闭。真实高德驾车路线回归已使用地点名输入验证，结果为 `success + valid`、1 条 canonical route source，未输出凭据或原始响应。

## 7. 第二次复审补正：默认 Tool 全覆盖与混合文本兼容

提交前按阶段 2 验收口径重新检查，补齐并验证了以下缺口：

- `agent.artifacts.read` 使用 `artifact_read`；`workspace.files.list/search/read` 使用文件 Profile；`workspace.files.propose_edit` 使用 `approval_draft`；`workspace.files.apply_edit` 在实际写入完成时使用 `file_revision`。因此全部 16 个默认 Tool 都有明确的质量合同。
- 编辑预览需要 `result_semantics=approval_draft` 且 `applied=false`；用户确认等待态也只能作为草案。草案 Diff 可在专用的面向用户预览路径中展示，但不属于已写入 evidence，不能解锁普通依赖、Result Binding 或 Durable 成功 Artifact；`full_workspace` 的受控写入必须有 `file_id`、`revision_id` 与 `applied=true` 才为 `valid`。
- `empty_answer` / `approval_draft` 只信任项目内 `ToolAdapterRunner` 搭配真实 `WorkspaceFileToolProvider` 或 `AgentArtifactToolProvider`；外部 Runner 伪造本地 adapter 类型和 metadata 会回落为 `evidence` 并失败关闭。
- 动态 MCP 默认设置 `require_semantic_profile=true`；未先完成审核 Mapper/Profile 的工具仍可展示配置或诊断，但普通非空 JSON 不会成为有效 evidence。
- `content[].text` 同时包含说明文本和 JSON 时，统一提取第一段合法 JSON 结构，避免 Tavily/高德专用 Mapper 因收到混合 list 而错误映射为空。

本次补正的定向质量/Mapper/Executor/Workspace/Artifact/Approval 测试共 84 项通过；完整后端回归为 403 项通过、5 项跳过。跳过项仅依赖未配置的 `TEST_POSTGRES_URL` PostgreSQL/pgvector 条件集成环境；`compileall`、默认 manifest JSON 校验和 `git diff --check` 均通过。

## 8. 第三次复审补正：失败关闭与脱敏边界

本次提交前再次按“远端返回不可信、结构合法不等于业务可用”的原则检查，补齐了以下边界：

- `request_matches` 的 JSON Pointer 现在拒绝根路径、通配符、空路径段、尾斜杠和非法 `~` 转义，避免异常路径在运行时被静默视为“可选参数缺失”。
- Profile 的 evidence / identity 只能是有效的非布尔标量；整个对象或列表即使非空，也不能伪装为业务证据或身份。
- 动态 MCP 的默认合同要求已审核的语义 Profile。尚未配置 canonical Mapper/Profile 的非空 JSON 只能用于诊断，不能作为有效 evidence 解锁依赖或写入 Durable 成功 Artifact。
- 工具 Trace、公开 Source 与 Durable Artifact 对嵌套字符串递归脱敏；Tavily canonical 正文在 Mapper 层限制为最多 1,600 个字符，降低远端正文携带敏感片段或过大数据的传播面。序列化出口仍保留二次脱敏。
- `file_revision` 增加完整写入态约束：必须同时具备 `file_id`、`revision_id`、`applied=true` 与 `revision_number >= 1`；仅生成 Diff 的 `approval_draft` 不能被误判为已写入。

这些增强均有正常、缺字段、伪造 Runner、异常路径和嵌套敏感文本回归用例。提交前会重新跑完整后端测试、编译、manifest 校验与差异格式检查；最终结果以本次提交记录为准。

## 9. 第四次复审补正：`approval_draft` 的依赖与 Durable 边界

复审发现，只依据 `success + valid` 判断“结果可消费”会把编辑 Diff 预览误当成已完成副作用，从而可能解锁普通下游 Step 或被 Durable Worker 写成成功 Artifact。现已将可消费语义收紧为 `evidence` 与可信 `empty_answer`：`approval_draft` 明确排除在严格依赖、Result Binding、Durable 成功 Artifact 之外。

为保留正常产品体验，同步 Workflow 对合格草案提供专用收口：其执行状态为 `waiting_approval`、质量仍为 `valid`，Diff 可进入用户可见 Prompt，反馈动作为 `clarify`；后续普通依赖被 `dependency_not_succeeded` 阻断。新增同步 DAG 与 Durable Worker 回归，分别验证“预览可见但下游不执行”和“草案绝不被保存为成功 Artifact”。
