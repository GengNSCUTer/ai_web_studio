# Chat 事务与流式持久化修复

| 项目 | 源码确认 | 本次改动 |
| --- | --- | --- |
| 10.1 长期记忆登记 | `finish()` 与 `_enqueue_memory()` 分别提交。扫描由后续成功轮次或已有提取任务触发，最后一轮可能漏登记。 | 成功 Run、正式 Message、终态事件和待扫描轮次同事务提交。现有 memory-worker 按会话顺序消费，在锁内复核项目、生成版本和设置。扫描结果与删除待消费记录一起提交，异常回滚后延迟 15 秒重试。模型抽取仍由既有后台 Job 执行。 |
| 10.2 SSE 轮询 | 普通轮询读取完整快照并查询事件。 | 建连和空轮询只查询归属、序号和状态。存在新事件时再查有界事件页。裁剪补偿和终态尾游标读取完整快照。空轮询从 250 毫秒逐步放宽到 750 毫秒，有新事件时恢复 250 毫秒，积压立即翻页。 |
| 10.3 增量写入 | 每批更新 `ChatRun` 正文和 `Message` 正文并追加事件。 | 每批聚合增量后写一次 Run 正文和事件。生成中的 Message 每秒最多低频复制一次数据库内的 Run 快照，终态同步完整或已保存的部分正文。活跃流和重连继续从 Run 与事件恢复，生成中的历史列表和导出可能读到最近一次 Message 快照。 |
| 10.4 全局领取锁 | 领取时在全局配额锁内回收过期任务。 | 先选取未过期的候选，空队列无需争用全局锁。配额和领取状态仍在同一短事务裁决。现有 Chat Worker 每两秒独立回收，使用 `SKIP LOCKED`。 |
| 10.5 历史顺序和游标 | 历史主要按 `created_at`，记忆按 `sequence`。旧分配已防止越过记忆游标后复用序号，但删除未扫描的尾部仍可能复用。 | 历史、重生成、摘要边界和记忆入口共享会话顺序。已编号消息按 `sequence`，未编号旧历史按时间和 ID 排在前面。会话水位同消息一起提交，后续新消息从水位、现存最大值和两个记忆游标的最大值递增。旧历史缺号且前缀无空位时，只有未建立记忆游标的会话才会整体移入更大的新号段，保留阅读顺序。已建立游标的会话保留既有编号。 |

## 代码链路

- `chat_run_service.py` 和 `chat_run_worker.py` 负责领取、租约检查、批量写入与终态裁决。取消优先时沿用已提交的片段。成功事务登记 `chat_run_memory_triggers`，`memory_candidate_runtime.py` 在后续事务消费；现有提取权限、显式同意和来源复核继续生效。
- `api/routes/chat_runs.py` 的订阅入口核验用户归属与游标。普通页按本次读取的事件序号上界取最多 256 条事件，裁剪后回退快照。等待期间释放连接。
- `message_repo.py` 负责分配水位和历史顺序。`conversation_summary_service.py` 和 `summary_rebuild_worker.py` 用相同顺序读边界、查找安全版本和重建摘要。
- `20261127_01` 建立待消费触发表并用现存消息和游标初始化水位。若旧历史顺序确实变化，迁移清除对应摘要、取消旧重建任务，后续 Chat 按既有机制重建。迁移不回放上线前的成功轮次。

## 验证与部署范围

后端 212 项 Chat、消息、记忆与迁移回归及 32 项摘要恢复回归通过，均包含真实 PostgreSQL 用例。另验证同会话触发遇错按顺序重试及记忆关闭期边界。`compileall`、11 项前端 SSE 协议测试与 `git diff --check` 通过。

隔离 PostgreSQL 和 Playwright 使用受控生成片段验证提交、流式正文、刷新继续订阅、终态快照和 Last-Event-ID。浏览器控制台错误数为 0。源代码仍按批更新 Run 累积正文，保留的全局锁仍串行裁决配额。对千连接吞吐和实际磁盘写入量需要独立压测。

当前运行实例数据库仍在 `20261118_01`。现有服务部署需要在排空 Chat、停写及备份后依次应用后续迁移至 `20261127_01`，再恢复原 Supervisor 管理的服务。
