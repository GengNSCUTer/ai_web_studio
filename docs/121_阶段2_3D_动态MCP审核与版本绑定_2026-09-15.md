# 阶段 2.3D：动态 MCP 审核、版本绑定与 Candidate Catalog 收口

日期：2026-09-15
范围：将动态 MCP Tool 从“远端宣称只读 + 手工风险审核”升级为“风险审核 + 接入合同 + fixture 验证 + 当前配置 digest”共同约束。

## 1. 启用前的必要条件

动态 MCP Tool 进入 Planner Candidate Catalog 前，必须同时满足：

```text
server enabled
  + tool enabled
  + risk_reviewed
  + read_only=true 且 risk_level=low|medium
  + onboarding_review_status=approved
  + contract digest 一致
  + fixture digest 一致
  + Tool / Server 当前配置 digest 一致
  -> ToolCatalog 可加载
  -> ToolAdapterRunner 执行 declared_canonical mapper
  -> ResultQualityContract
```

任意一项失败，动态 Tool 不会进入 Planner 候选集。设置页仍可显示它用于诊断，但不会把通用远端 JSON 作为证据。

## 2. 持久化字段与状态

`backend/app/models/tool_config.py` 的 `McpTool` 新增：

- `onboarding_contract_json`：受限合同本身，不含 fixture response；
- `onboarding_contract_digest`、`onboarding_fixture_digest`、`onboarding_config_digest`：版本绑定摘要；
- `onboarding_review_status`：`not_configured`、`fixture_failed`、`pending_review`、`approved`、`invalidated`；
- `onboarding_reviewed_at`：人工确认时间。

`backend/app/core/startup.py` 用既有幂等 runtime DDL 为旧 PostgreSQL 部署补列。历史 Tool 没有接入合同，默认不会因为旧的 `is_enabled/risk_reviewed` 进入候选目录。

## 3. 后端状态链路

入口在 `backend/app/api/routes/tools.py`：

1. `POST /tools/mcp-tools/{tool_id}/onboarding`
   - 接收合同和仅用于当前请求的脱敏 fixture；
   - 校验合同 Tool identity 是否等于当前 `McpTool + McpServer`；运行离线 Mapper/质量门；
   - 只保存合同和 digest，验证通过写 `pending_review`，失败写 `fixture_failed`，两种情况都保持 `is_enabled=false`。
2. `POST /tools/mcp-tools/{tool_id}/onboarding-review`
   - 只有已完成低风险只读风险审核、合同/fixture/config digest 仍一致时，显式 `approved=true` 才写入 `approved`；
   - 审核动作本身不会启用 Tool，用户仍要单独打开 `is_enabled`。
3. `PATCH /tools/mcp-tools/{tool_id}`
   - 修改 description override、category、固定参数、风险或只读属性时立即 `invalidated + disabled`；
   - 启用前重复检查完整审核状态。
4. `PATCH /tools/mcp-servers/{server_id}` 与同步 `sync-tools`
   - endpoint、transport、鉴权、凭据提供方、项目作用域变化会撤销所有下属 Tool 审核；
   - 远端 schema/annotation 变化先撤销风险审核；描述/配置摘要漂移也显式标记接入审核失效。
5. `ToolCatalog._load_db_mcp_definitions()`
   - 每次加载重算当前身份/配置 digest；数据库被手工篡改、旧状态残留或 JSON 损坏时均失败关闭。

`backend/app/services/tools/onboarding.py` 集中实现身份/配置摘要、状态检查和失效函数，避免 API 与 Catalog 对“什么会使审核失效”各自维护一份规则。

当前配置摘要覆盖 Tool 的 key、远端原始名、会进入 Planner 候选说明的显示名、说明、输入/输出 schema、annotations、固定参数、分类和权限字段，以及 Server 的 key、URL、`transport_type`、鉴权方式、凭据提供方和 `project_id`。因此即使异常绕过 API 直接修改候选语义、协议或项目作用域，Catalog 重算摘要时也会失败关闭。

## 4. 前端与当前产品边界

`frontend/src/components/settings-center.tsx` 展示 `onboarding` 状态和合同/fixture digest，未完成审核时禁用启用开关，并明确页面不会自动批准或启用 Tool。`frontend/src/lib/types.ts` 同步后端返回字段。

当前设置页只展示审核状态；合同/fixture 的提交可以通过受控 API 或离线校验脚本完成。没有把远端 Tool 的 description、fixture 文本或 `readOnlyHint` 当成自动授权。第三方 Skill 市场、stdio MCP、任意写工具、无限轮 Agent 和跨请求 Durable DAG 都不属于本阶段。

## 5. 回归验证

- `backend/tests/test_tool_routes.py`：fixture → pending → 显式 review → 单独 enable 的状态机；描述改变后自动失效且不能再次启用；未审核 Tool 在网络调用前阻断。
- `backend/tests/test_tool_catalog.py`：只有完整审核的 Tool 可进入 Catalog；显示名/描述、transport 或项目作用域的配置摘要漂移即便还保留 `risk_reviewed/is_enabled` 也会被 Catalog 排除；项目作用域继续隔离。
- `backend/tests/test_mcp_security.py`：远端 schema/annotation 改变撤销原风险审核和接入审核。
- 前端 `npm run lint` 与 `npm run build`：设置页类型和生产构建通过。

本阶段解决的是“新增低风险只读 MCP Tool 的受控接入和版本失效”，不是对任意远端 MCP 的可信证明。每次真实上线仍应使用脱敏、代表性的 fixture；质量合同只能验证确定性的结构/字段/有限请求一致性，不能替代业务方对数据可靠性、时效性和授权范围的审核。
