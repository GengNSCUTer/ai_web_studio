# 统一工具执行内核：问题核对与阶段计划

本次目标是消除Chat和固定Durable工具调用的重复底层规则，保留不同业务图和Worker。基线为`bf86ee6`，开始前仓库为`6cbcd6a`且工作区干净。用户提供的分析是设计建议；下表区分当前事实和后续工作。

## 1. 六项问题核对

| 问题 | 当前源码事实 | 处理顺序 |
| --- | --- | --- |
| 单次调用逻辑重复 | Chat的_begin_call/_complete_call与Durable的_prepare/_finish_success分别计算尝试、校验产物和保存结果；实际Executor已经共用 | 阶段一提取共用内核，保留两类事务协调器 |
| 三层状态和体积 | Step/Artifact、业务Checkpoint、原生图记录并存；当前恢复已以业务为准，但Checkpoint重复保存观察/结果 | 阶段二统一恢复决策，优先保存引用，测量前后体积 |
| 恢复分类较粗 | 只支持低风险只读有限重试，结果不明写入阻断；没有可直接开放的外部幂等/对账写接口 | 明确retry/idempotency/reconciliation三个字段；未知副作用仍人工处理 |
| 脱敏参数不能直接恢复 | 审计快照脱敏会改变参数，当前代码拒绝执行占位符；认证凭据已有服务端解析器 | 保留拒绝规则，区分审计/执行表示；不因“统一”保存密钥或允许未实现的引用 |
| Artifact语义分散 | Chat内部恢复、Durable结果、文档取证/草稿/导出分别保存，前端/工具可见范围不同 | 阶段三统一保存、归属/时效/可见性及历史发现，不抹平文档业务 |
| 恢复指标不系统 | 已有真实进程退出/审批验证，但1269单测不代表恢复率、开销和重复副作用指标 | 阶段四做正常/故障对照，记录已测分母与未知成本 |

统一后的事实分工保持：Step决定实际执行状态，Artifact保存结果，Approval/Revision证明批准及文件版本；业务Checkpoint记录预算/循环位置，原生图位置只提示编排；ChatRun/Message保存最终回答。

## 2. 四阶段与验收

1. 共用调用内核：统一身份、快照、尝试、结果归属与保存，跑原三类任务回归并独立提交。
2. 共用恢复协议：统一已提交/缺结果/不明副作用/耗尽判断，Checkpoint引用化，测试业务提交与图保存的崩溃窗口。
3. 共用产物管理：类型、权限、哈希、时效和来源检查；当前项目有界发现历史成果，复用不绕过来源授权。
4. 工程验收：普通Chat、多轮/并发DAG、文档、审批及不明副作用，测恢复成功、重复副作用、恢复耗时、产物复用和额外成本。

详细可执行任务见[四阶段计划](../plan/refactor-tool-invocation-runtime-1.md)。没有把阶段三、四的能力写成当前已完成。

## 3. 阶段一实际改动

新增`backend/app/services/tool_invocation_runtime.py`。`InvocationIdentity`绑定用户、项目、Run、Step和调用；`InvocationRecoveryPolicy`由服务器ToolDefinition推导，不接受远端的replayable声明；`InvocationOutcome`共用原Quality判断，区分执行成功、仅预览、等待审批和失败。`ToolInvocationRuntime`负责快照核对、开始尝试、产物归属/大小/哈希与创建，但不独立commit、不领取任务、不扩大权限。

`chat_tool_runtime.py`和`durable_tool_runtime.py`实际调用这套方法，不是只增加空接口。两者仍在原业务锁下核对当前执行权，再调用内核并同事务更新Step/事件。`document_task_worker.py`使用同一尝试上限，继续保留文档图和原审批链。Document的Artifact保存留到阶段三收敛。

顺便修复两处可证实问题：

- Durable调用前统一检查Step尝试上限；反复崩溃不能触发第4次工具请求。文档阶段同样不能无限尝试。
- Chat有效的`approval_draft`预览保存为`preview`，不再误写成执行成功；`confirmation_required`仍为`waiting_approval`。这不改变正式审批服务或实际文件写入。

执行顺序是：协调器锁内校验 → 共享内核登记尝试 → 释放事务后调用原Executor → 锁内重新校验 → 共享内核创建Artifact → 协调器提交业务状态。没有把全部工具变为独立排队任务。
