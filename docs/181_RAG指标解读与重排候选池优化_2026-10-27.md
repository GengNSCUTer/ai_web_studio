## 简历里的评测究竟测什么

26篇论文入库后形成2,537个活动文本块。90个问题在检索前已绑定2—3个目标段落，共200个题目—目标块关联。检索评测比较Vector、BM25、Hybrid及两种重排配置；答案评测让DeepSeek-V3.2根据实际检索证据回答，再由独立Qwen2.5-72B模型评分。程序回归测试、检索指标、模型评分是三种不同证据，不能互换。

| 优化前指标 | 怎么理解 |
| --- | --- |
| Hit@6 84.44% | 90题中76题，在前6条中至少出现一个指定目标块；不要求全部找齐 |
| MRR@6 64.80% | 每题找到的第一个目标块若排第r名，得1/r；找不到得0，再取平均。不是64.8%的问题答对 |
| nDCG@6 50.63% | 综合多个目标的覆盖和排名；排得越前收益越高，并与理想排序归一化。不是答案正确率 |
| Context Recall@6 56.30% | 逐题计算“找回的目标块/本题目标块”，再平均；仍存在真实证据遗漏 |
| Context Precision@6 21.04% | 返回的块中属于指定目标的比例；标签只覆盖2—3段，不穷尽所有正确证据 |
| 检索均时1.11秒 | Embedding、数据库/词法检索与重排等检索链耗时，不是用户收到完整答案的时间 |
| Faithfulness 91.56/100 | 独立模型判断答案事实是否被提供证据支持，不等于人工标注的91.56%答案正确 |
| Citation Correctness 89.56/100 | 独立模型判断引用是否支持相应论断；与代码核对“引用标签是否存在”不同 |

例如，目标证据为A、B，返回X、A、Y、Z、U、V：Hit=1，Recall=1/2，Precision=1/6，RR=1/2。可见“找到一点证据”与“找到完整且排名靠前的证据”不是一回事。

两段目标配六段输出时，即使全部目标都命中，按精确ID标签计算Precision也只有33.33%；三段目标时为50%。21.04%不能直接断言约79%的结果无用，但也不能用标注不穷尽来掩盖漏召回。当前Doc Hit@6达98.89%，更需要检查同一论文的段落选择和证据完整性。

Tool的98.33%是58例中60组必需工具能力命中59组的候选Recall，不是98.33%的用户任务完成。20个真实任务只有8个满足完整断言，6/6安全案例只证明这6种测试输入被拒绝，不代表不存在其他漏洞。

## 定位与修改

原先每路召回20条，融合后先截到20条，再交给重排。200个标注关联中，两路候选并集包含132个目标，融合截断后126个，最终6条包含112个。5道题在融合截断时丢过目标，另外68个目标根本没有进入两路候选，无法靠最终回答模型补救。

本轮只改重排前的候选池：启用重排且请求规模为20时，每路适度扩到40，融合时保留更多不同候选，再由同一个重排模型选最终6段。每路通常最多50，两路合并送重排最多100；带元数据过滤时保留原有过滤过取逻辑。实际本次Hybrid重排输入为41—69条，平均约45条。未新增LLM查询改写、翻译或特定论文关键词规则，未改变题目、目标、Embedding模型、重排模型、分块和输出段数。

关闭重排不扩容；重排失败时按调用者原先请求数量收口，仍标记降级，不把扩大后的全部候选注入上下文。top_k小于rerank_top_n时仍尊重请求上限。返回来源增加实际重排候选数与输出上限，便于诊断。

## 相同90题的真实检索对照

以下均为前6条、精确块ID标签；两次五组运行均无检索异常或降级。旧、新题集、索引和标签相同。

| Hybrid+Rerank指标 | 修复前 | 修复后 |
| --- | ---: | ---: |
| Hit@6 | 84.44%（76/90） | 88.89%（80/90） |
| MRR@6 | 64.80% | 66.41% |
| nDCG@6 | 50.63% | 53.82% |
| Context Precision@6 | 21.04% | 22.22% |
| Context Recall@6 | 56.30% | 60.93% |
| Doc Hit@6 | 98.89% | 98.89% |
| 平均检索耗时 | 1,105.1ms | 1,457.1ms |

4道原来完全未命中指定目标的题新增命中，没有原先命中题变为完全未命中；11题Recall改善、4题有所下降，其余不变。旧20题的Recall从53.33%降至51.67%，新70题从57.14%升至63.57%，因此不能说每个子集、每道题都提高。整体Recall提升4.63个百分点，耗时增加约352ms（约32%）；保留这个明确的质量/成本取舍。

Vector+Rerank也从Hit85.56%/Recall56.67%变为88.89%/60.93%，平均1,014.2ms，说明这批语料上Hybrid并非始终更划算。不据此静默修改用户的知识库检索模式。

## 答案验证

同一90题的真实生成与独立Judge已全部完成，检索、生成、Judge及运行器失败均为0。答案与引用结果保存为 `backend/evals/results/rag_expanded_90_e2e_pool_20261027.json` 及同名Markdown。

| 答案指标 | 修复前 | 修复后 |
| --- | ---: | ---: |
| Faithfulness | 91.56/100 | 91.72/100 |
| Answer Relevancy | 92.50/100 | 92.39/100 |
| Citation Correctness | 89.56/100 | 88.89/100 |
| 引用标签有效率 | 98.89% | 98.89% |
| GT引用Precision | 40.83% | 45.59% |
| GT引用Recall | 52.59% | 57.96% |
| 平均答案流水线检索 | 1,207.7ms | 1,544.7ms |
| 平均答案生成 / Judge | 12,630.2 / 5,591.8ms | 14,871.0 / 5,597.0ms |

本轮检索和目标证据引用覆盖提高，但三个独立模型评分接近优化前，引用正确性还小幅下降。保留修复的依据是减少早期候选截断造成的证据损失，不宣称最终答案准确率全面提升。模型评分只做单次独立评审，仍需要重复运行和未参与诊断的新问题验证泛化与统计稳定性。

## 实现文件与验证边界

- `backend/app/services/knowledge_retrieval_pipeline.py`：在retrieve_async里决定内部候选池，融合后再精排；在_rerank_if_needed里控制最终返回、故障降级和实际候选诊断。
- `backend/tests/test_knowledge_retrieval_pipeline.py`：新增6项测试，覆盖融合截断外的证据、超时收口、不启用重排、小top_k、全局预算及既有过滤过取。
- `backend/scripts/summarize_expanded_eval.py`：原始结果统一@6重算，记录实际重排候选数，区分请求规模与精排输入规模。
- `scripts/stage46a_real_e2e.py`：补临时RAG会话清理时的日志外键处理，仅作用于本轮测试夹具，不改变产品删除逻辑。

已完成：769项全量后端测试（含真实PostgreSQL条件集成）、Python编译与diff检查。后端已通过原Supervisor单独重启，仍为前端32008/API32007，未新增第二套服务或启动本地模型。真实浏览器已跑通DeepEncoder问答、6条知识库来源保存与done终态，无页面错误；首轮夹具清理遗漏已修复，第二轮再次完成问答与清理，无残留临时项目。
