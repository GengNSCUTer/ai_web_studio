# LangGraph 迁移说明与最终验收

日期：2026-11-06。当前状态：阶段0—6已独立提交；阶段7清理已实现，正在最终业务验收。本文统一说明改了什么、代码在哪里、如何恢复、没有实现什么；阶段原始失败和报告继续保留，不用本说明覆盖。

## 先理解整体变化

原来各服务自行用循环、分支组织“下一步做什么”，现在由LangGraph的节点和条件边组织。模型供应商、知识库检索、记忆规则、工具执行器、权限、事务、前端和队列没有被框架替代。

- **模型**：生成工具计划、最终答案、摘要、记忆候选/关系判断、文档草稿。
- **图**：安排这些业务步骤的先后、续轮、停止及审批暂停/恢复。
- **业务代码**：真正发HTTP/操作文件，检查参数/权限/证据质量，处理数据库事务、幂等、租约、结果回传。
- **用户**：显式激活能力、确认后台任务、批准需确认的项目文件写入。

不是将旧完整循环包成一个节点。同步工具图有plan、execute、observe、finalize，观察后由条件边决定回到plan还是结束；Chat上下文有七个独立阶段，文档与后台任务也分别拆出真实动作。

## 各条链如何走

| 链路 | 当前步骤 | 主要代码 |
| --- | --- | --- |

| 上下文 | snapshot→memory→tools子图→rag→summary→govern→context_ready | `agent_graph/context_graph.py`、`chat_context_assembly_service.py`、`chat_assembly_runtime.py` |
| 同步工具 | plan→execute原DAG→observe质量/完成条件→继续plan或finalize | `agent_graph/sync_tool_graph.py`、`tools/loop_runtime.py`、`external_context_service.py` |
| 流式回答 | generate→persist_terminal；请求级单槽桥接保留NDJSON消费顺序 | `agent_graph/chat_stream_graph.py`、`chat_persistence_service.py`、`api/routes/chat.py` |
| 只读Durable Step | preflight复核业务产物/权限→execute_commit→reconcile | `agent_graph/durable_graph.py`、`durable_tool_runtime.py` |

| 文档任务 | 每个Step进入preflight→取证/模型草稿/导出/交付→保存产物/下一阶段→reconcile | `agent_graph/document_graph.py`、`document_task_worker.py`、`document_task_service.py` |
| 可选保存文档 | 用户主动请求→interrupt等待→认证批准/拒绝→consume_decision；批准只排队，Worker再校验写入 | `agent_graph/document_approval_nodes.py`、`document_task_service.py` |
| 记忆候选 | source_snapshot→extract→verify→conflicts→persist候选/游标→backlog | `agent_graph/memory_extraction_graph.py`、`memory_candidate_runtime.py` |
| 知识Job | parse→complete_parse，或index→activate；索引子图chunks→embed→persist_chunks→lexical_manifest | `agent_graph/knowledge_index_graph.py`、`knowledge_job_runtime.py`、`knowledge_index_service.py` |

上述服务文件均在`backend/app/services/`下。共享一个SQLAlchemy Session的上下文节点保持串行；实际工具DAG内的独立分支仍由原Workflow并发执行，不跨线程共享Session。

### 同步Chat

先保存用户消息和assistant占位消息，短事务结束后进入上下文图，再开始模型生成流；完成、失败、取消仍以message ID/generation ID做CAS。HTTP协议仍为NDJSON，浏览器取消和流断连仍按原机制保存已得到的内容。使用LangGraph并没有使普通Chat脱离浏览器连接，也没有生成到一半的token续接。

工具模式预算保留：quick_chat、guided_research、workspace_review、edit_proposal各用自己的轮次、调用数、并发和工具阶段时限。图的recursion_limit按节点跳转数另外设置，不拿一个superstep当一次规划轮次。有限预算是产品约束；换框架不会自动扩大工具权限或变成无限循环。

### Durable与文件审批

Handoff仍分Preview/Confirm：预览不创建Run/Step/Outbox；只有用户确认后才创建固定低风险只读计划。独立Worker领取Step，原业务租约和版本继续生效。同步工具循环没有被自动转换成任意可持久化的自主规划。

文件改写仍先读真实文件、生成Diff和PatchDraft，再按当前项目权限决定是否需要逐次确认。ask等待真实用户决定；read_only禁止写；full_workspace是用户提前授予的项目范围权限，仍保留参数、内容哈希、最新FileRevision与审计检查。本次用户明确“等待我确认”时，即使项目预授权也不会跳过确认。

文档导出成功即可预览下载，生成状态为succeeded；保存到工作区是用户另行选择的操作，才进入保存审批。等待期间没有Worker或数据库事务挂着等人。批准后Worker按当前租约/权限执行，拒绝保存不丢失已导出的文档。

## 哪些状态真正持久化

| 对象 | 存储和恢复依据 | 中断后的行为 |
| --- | --- | --- |
| 普通Chat及同步工具循环 | 正式消息/Trace；图为请求内编排，没有Checkpointer | 保留已收口部分；不续token、不承诺从中断轮自动恢复 |
| 只读Durable工具Step | Run/Step/Artifact为业务事实；原生PostgresSaver记录图位置 | 先检查已提交Artifact；已完成不重做，未提交只读请求可能重发 |
| 文件审批/文档保存审批 | AgentApproval、PatchDraft、FileRevision/Run，加原生interrupt记录 | 认证后的新请求恢复；再次校验当前版本/权限，不信任旧图决定 |
| 文档各阶段 | 已提交的阶段Artifact，加原生Step检查点 | 已提交草稿/导出复用；未提交模型草稿从本阶段重新生成 |
| 记忆提取和知识索引 | 原持久化Job、源快照/游标、generation、Outbox/Redis | 由原Job租约重领；没有额外原生子节点检查点，不续模型输出 |

图State只放ID、阶段、状态、计数等小字段。Session、ORM、原文、模型输出、API Key、确认令牌和客户端只在请求Runtime或原业务资源中，不序列化到图检查点。默认关闭外部LangSmith追踪，宿主残留开关也不能自动外传。

### 两份记录如何避免冲突

业务表才决定结果是否成功、文件是否写入。图检查点可能比业务提交晚：进程在Artifact提交后、图记录前退出，恢复先读业务产物再补图记录，不能因为图落后再执行一次外部动作。

Worker图写检查点时，在**同一个PG短事务中**锁当前Outbox事件并检查用户/项目/Run/Step、owner、lease_version、expiry；旧Worker不能先检查成功、接管后再偷偷写图。重放领取版本大于同Step及全部历史事件最大版本。审批图每次请求使用同审批串行锁，并复核业务版本；模型不能指定thread_id或伪造Command跳过业务服务。

这仍不是跨第三方服务的exactly-once。外部只读请求已返回、Artifact尚未提交时崩溃，允许至少一次重发。高风险任意操作没有因此进入Durable。

## 阶段7清理与审查

1. 删除同步`run_legacy`循环、构造参数和`TOOL_ORCHESTRATION_ENGINE`配置。当前同步工具入口只有LangGraph，异常不会再选另一个引擎重做。
2. 删除无版本Durable/文档任务的旧直接执行分支，以及文档保存函数中另行决定下一阶段的默认分支。退役前只读核对正式库AgentRun存量为0；今后未知/缺失运行时版本拒绝并要求重新发起，不静默升级。文件审批也不能缺版本绕过图。
3. PDF/中文资料导入脚本改为enqueue解析/索引Job并等待独立Worker，等待前结束数据库事务；旧`KnowledgeDocumentService.index_document`直接索引业务入口删除。`KnowledgeIndexService.index_document`仅保留给检索算法/隔离夹具及旧补偿回归，不是API或导入路径，没有崩溃原子性承诺。
4. 真实采样发现工具权限查询的只读事务可能跨后续Planner等待。`tools/db_boundary.py`在每轮规划和适配器等待前释放干净的只读事务；近期消息先复制为值，防止commit后ORM懒加载重新打开事务。若仍有未保存业务写入则拒绝等待，不顺便提交它。
5. 原生PG故障测试复现“重试已提交、图停在旧reconcile，新租约只对账而不执行”的空转窗口。Durable/文档图现在只有相同租约才沿原next继续；新租约从预检开始，按业务Artifact复用已完成成果，避免白占一次租约。不是无条件从头重做工具或文件副作用。

## 安装、迁移、回退

依赖固定`langgraph==1.2.20`、`langchain-core==1.7.6`、`langgraph-checkpoint-postgres==3.2.0`和`psycopg-pool==3.3.3`，Python3.10已实际验证。安装仍用现有`backend/.venv`，不能换旧conda环境启动业务。

数据库由显式Alembic迁移管理：`20261106_01`创建独立`aiws_graph`原生检查点表及业务thread映射；`20261106_02`允许同Step按`runtime_key`分别绑定执行图与审批图。新机器先备份、执行迁移，再启动服务；Web/Worker启动只校验，不自动Saver.setup建表。业务Run删除时通过映射级联清理图记录。

正式库两次备份保留在仓库外`/disk2/gengnan/aiws-backups/20261106-langgraph-stage3-d5d9c452`和`20261106-langgraph-stage5-c2b07e27`。代码回退按阶段提交点进行；保留迁移链，不将已经产生双角色线程的新库直接降级旧唯一约束。不把恢复旧备份当作无数据损失的应用回退。

继续使用唯一一套API32007、前端32008、PostgreSQL35433和Redis36379；知识/记忆/Durable三个Worker各一套，由现有Supervisor托管。原生检查点池独立有界，审批每次调用结束就归还连接；等待用户不占用池连接。运行/健康/备份命令见[部署说明](../deploy/README.md)。

## 明确边界与下一步

- 正式业务编排已逐条图化；普通CRUD、SQL、HTTP代理和每个底层算法无需为了形式做图节点。
- 仍有同步SQLAlchemy仓储和后台Worker，不把整个后端称作纯异步。
- 不承诺继续半截token、通用自主长程规划或跨外部系统exactly-once。
- 沙箱缺Rootless部署前提，真实容器仍未验收且保持禁用；没有开放Shell、Bash、SQL、删除文件、支付、邮件、任意本机路径写入或任意HTTP写接口。
- 阶段6真实记忆首批r1的严格冲突分类断言失败原因未定位，失败报告与诊断改动保留；后续通过不等于根因已修。
- RAG百题历史检索/答案指标仍是原语料、原模型、原版本测量，不能因本次迁移原样当作重新跑出的成绩。

面试表述建议：“我使用LangGraph组织Chat、工具循环和后台任务的状态流，但权限和副作用由业务代码控制。Durable和审批使用PG原生检查点，恢复时优先验证业务产物和当前租约；普通Chat及记忆/索引后台并不是token级恢复。迁移收益是统一编排与故障定位，不是框架自动提高答案准确率。”
