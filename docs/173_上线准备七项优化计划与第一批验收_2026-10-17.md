# 上线准备：七项优化计划与第一批验收

更新于 2026-10-17。实施入口：[分三批执行的计划](../plan/infrastructure-production-readiness-v1.md)。本轮只处理第一批，未扩展 Tool Catalog，也未把固定只读 DAG 恢复描述成完整 Agent 循环恢复。

## 七项问题怎么分批处理

项目已具备问答、知识库、记忆、权限确认、工具编排和后台任务。要进一步接近真实部署，重点是换环境能安装、服务故障可发现、数据可恢复，以及有人完成真实任务。

| 审查项 | 具体缺口 | 批次与当前范围 |
| --- | --- | --- |
| 1. 安装和交付 | bcrypt、cryptography 依赖未显式声明，启动脚本依赖个人目录，没有统一托管入口 | 第一批：补依赖、固定验证过的解析版本、统一入口 |
| 2. 服务可用性 | Screen 有进程不代表端口可用，旧 /health 不检查依赖 | 第一批：存活/就绪检查、BFF 转发检查、进程托管和真实故障演练 |
| 3. 资源保护 | 异步上传接口内直接同步落盘和解析；还缺用户级任务、并发与存储限额 | 第一批处理上传解析阻塞，第二批处理用户级限额 |
| 4. 生产配置 | 认证 Cookie 固定 secure=false，凭据加密密钥未在启动阶段统一检查 | 第一批：统一 Cookie 策略和生产密钥/CORS 检查 |
| 5. 数据恢复与升级 | 仍是启动检查/补表结构，没有版本化迁移和备份恢复演练 | 第二批：迁移、备份、恢复和自动回归 |
| 6. 后台任务的产品入口 | 当前从同步 Tool Trace 再确认后台执行，可能重复只读调用 | 第三批：执行前建议或安全复用产物，保留确认和权限检查 |
| 7. 真实使用证据 | 有检索评测和端到端脚本，缺持续容量与用户试用记录 | 第三批：三条固定业务流程、并发探测和小规模试用 |

当前应介绍为“个人自部署、账号数据隔离的知识工作台”。没有成员管理和团队权限模型时，不宣称已实现完整团队协作；可接在线模型和外部解析服务，也不等于资料从不上云。

## 第一批具体改了什么

**安装不再依赖当前机器碰巧装好的包。** `backend/requirements.txt` 增加 bcrypt、cryptography；`deploy/requirements.txt` 声明 Supervisor；`deploy/constraints-py310.txt` 固定本轮 Linux/Python 3.10 实际安装、测试过的间接依赖。API、知识库和记忆启动脚本支持仓库虚拟环境及显式 Python 配置，去掉个人 Conda 默认路径。前端通过现有 lockfile 执行 npm ci。

**上传解析让出事件循环。** `backend/app/api/routes/uploads.py` 保留原有文件数量和大小限制，先异步读取，再把整批落盘、解析和失败清理交给 `anyio.to_thread.run_sync`。独立 CapacityLimiter 限制每个 API 进程同时解析两批；不挤占普通同步接口的线程额度。任何文件解析失败会清理同批已落盘文件，写入一半失败也进入清理。

这解决的是同步解析直接拖住事件循环，并不让解析本身变快；线程无法强行终止卡死的 Python 解析器。当前尚无用户级上传排队/内存限额，恶意文件 CPU 隔离和这些限额不应被描述为已经完成。

**健康检查区分三个事实。** `backend/app/services/health_service.py` 并发检查 PostgreSQL SELECT 1 和 Redis PING；网络与查询有等待上限，失败仅返回通用状态，不输出连接地址、密钥或异常正文。`backend/app/api/routes/health.py` 保留 /health，新增 /health/live 和 /health/ready；依赖故障时 live 仍可为 200，ready 为 503。`frontend/src/app/api/health/ready/route.ts` 检查 Next.js 实际配置的后端地址，防止首页能打开但代理请求仍指向旧后端。

**进程自动重启，并能单独观察每个角色。** `deploy/run_services.sh` 和 `deploy/supervisord.conf` 管理 API、前端、知识库/记忆/Durable Worker，日志轮转，控制接口仅使用本机用户可访问的 Unix socket。`deploy/check_services.py` 检查前端页面、API 依赖、BFF 转发和五个应用进程；正常退出 0，失败退出 1。外部 Redis 模式下，可选 Redis 进程 STOPPED 不会造成误报。进程 RUNNING 不证明业务成功，Durable 的真实心跳与队列告警仍用既有运行面板。

**正式 Cookie 与密钥配置更明确。** `frontend/src/lib/auth-cookie.ts` 统一登录、注册、退出策略：HttpOnly、SameSite=Lax，生产默认 Secure，退出时使用相同属性清除。只有本地 HTTP 调试才显式设置 AUTH_COOKIE_SECURE=false。后端启动时要求生产 JWT 和凭据加密密钥各至少 32 字符、互不相同，并拒绝空/通配 CORS 来源。已有凭据加密密钥没有被替换，不能直接改它导致旧凭据无法解密。

## 当前服务器的实际处理

已核对并关闭五个旧 aiws-* Screen，其他项目和共享 PostgreSQL 不动。API、前端和三个 Worker 由用户级 aiws.service 启动 Supervisor，服务异常退出后可重启，不再保留另一套同职责 Screen。

配置中的本地 Redis 36379 原先不可达，未找到本项目旧 Redis 持久化目录；未动其他项目的 Redis 数据。在原配置端口启用专用 Redis，AOF 数据保存在本仓库 .runtime/redis。PostgreSQL 继续使用原服务与 35433 端口，业务任务仍以原数据库 Outbox/Job 为依据；不能宣称已经恢复不存在的旧 Redis 队列数据。

浏览器测试发现 frontend/.env.local 仍指向旧端口 32017，造成页面可打开、登录后的代理请求失败；已修正为当前 API 32007。这个本地配置不提交 Git。新的 BFF 就绪检查覆盖了此类故障。

本机入口为 http://127.0.0.1:32008，API 为 http://127.0.0.1:32007。用户级 unit 已启用；当前 linger=no，不能承诺退出所有登录会话后或无人登录的主机重启场景自动恢复。正式常驻部署应由管理员确认 linger 或使用系统级服务。尚未配置公网域名/TLS、高可用或外部告警通知，本地验收不等于已经公开上线。

已同步飞书[当前项目入口](https://my.feishu.cn/docx/ZyS5dt57nobU51xysZfcJjrYnwg)与[技术架构与运行](https://my.feishu.cn/docx/AeCyd8W8loPWSLxp0F2crhsUnwg)，分别更新七项计划/第一批进度和运行入口/验收结果，保留历史阶段内容。代码和本地文档本轮尚未 commit/push。
