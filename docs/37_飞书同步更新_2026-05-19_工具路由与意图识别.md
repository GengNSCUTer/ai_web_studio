# 2026-05-19 工具路由与意图识别同步

本次更新补充“开启联网搜索后是否每轮调用所有工具”的架构判断。

结论：

```text
联网搜索按钮 = 允许使用外部信息
不等于 每轮调用所有外部工具
```

真正调用哪个工具，应由 Tool Router 决定。

## 1. 为什么不能全量调用

如果每轮都调用 Tavily、天气、地图、MCP、知识库，会产生这些问题：

- 慢：每个工具都有网络耗时。
- 贵：在线搜索和 API 调用都有成本。
- 乱：无关结果会污染上下文。
- 难调试：不知道为什么调用了某个工具。
- 风险高：MCP 工具未来可能包含副作用操作。
- 不符合产品直觉：用户问“你好”不应该联网。

## 2. 参考对象

Ragent 的设计：

- 用 `IntentTree` 管理意图。
- 意图节点分 `KB / SYSTEM / MCP`。
- 叶子节点有 description、examples、promptTemplate、mcpToolId。
- LLM 对叶子节点打分。
- 后续按 score 和 kind 过滤。
- MCP 工具参数提取独立做。

Dify 的设计：

- Agent 支持 Function Calling / ReAct。
- 工具有 description、参数 schema、授权配置。
- 可设置最大迭代次数。
- 模型在工具集合中选择，而不是全量调用。

Coze 的设计：

- 插件和工作流都可以作为能力单元。
- 工具/插件有输入输出定义和 workspace 范围。
- 复杂能力适合封装成 workflow，再由 Agent 调用。

## 3. 我们项目的策略

采用：

```text
规则门控 + 轻量 LLM Router + 后端强校验
```

### 3.1 规则门控

先不调用模型，用关键词和上下文快速判断：

```text
问候 / 写作 / 翻译 / 代码解释 -> no_tool
天气 / 温度 / 下雨 -> weather
附近 / 路线 / 地址 / 地铁 -> map
最新 / 新闻 / 版本 / 官网 / 政策 -> web_search
上传的 / 附件 / 工作区 / 文档里 -> knowledge
```

### 3.2 轻量 LLM Router

当规则不确定，或候选工具超过一个时，调用 LLM Router，输出结构化 ToolPlan：

```json
{
  "should_use_tools": true,
  "calls": [
    {
      "tool_key": "weather.current",
      "confidence": 0.91,
      "reason": "用户询问明天天气",
      "arguments": {
        "city": "深圳"
      }
    }
  ],
  "fallback_tool_key": "web.tavily.search"
}
```

### 3.3 后端强校验

LLM 输出不能直接执行，后端必须校验：

- 工具是否存在。
- 工具是否启用。
- 用户是否允许外部工具。
- 参数是否符合 schema。
- 是否只读。
- 是否超过最大工具数量。
- 是否需要用户确认。

## 4. 默认调用策略

建议：

- 用户未开启联网搜索：不调用外部网络工具。
- 用户开启联网搜索：允许外部工具，但不保证一定调用。
- 工作区知识库和当前附件属于私有上下文，可以独立于联网搜索。
- 默认最多调用 1 个外部工具。
- 明确多意图时最多调用 2 个。
- Tavily 是默认 web fallback，但不是所有问题都先 Tavily。

示例：

```text
你好 -> no_tool
解释这段代码 -> no_tool
今天广州天气 -> weather
广州南站附近咖啡店 -> map
LangChain 最新版本 -> web_search
我上传的文档怎么配置数据库 -> knowledge
明天去深圳，天气怎么样，附近有地铁吗 -> weather + map
```
