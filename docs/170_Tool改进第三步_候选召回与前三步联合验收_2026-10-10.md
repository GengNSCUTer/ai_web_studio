# Tool 改进第三步：候选召回与前三步联合验收

日期：2026-10-10。对应 [167 审查](167_工具调用审查与主流方案对标_2026-10-09.md)第 3、4 项，并联合验证 [168 第一步](168_Tool改进第一步_统一截止时间与部分结果保留_2026-10-09.md)和 [169 第二步](169_Tool改进第二步_文件非阻塞与搜索范围_2026-10-09.md)。不新增 Tool 或扩大权限，第四步完整规划循环持久化/按需发现仍未实施。

## 一、宏观变化

候选筛选先把少量可能相关的工具给 Planner 看，不负责填写最终参数，也不是安全边界。现在两个选择循环都在添加前检查容量，修复专业工具满额后仍追加、最终挤掉联网兜底的问题。默认最多 6 个候选，有权使用且未禁用联网时保留一个联网候选；容量为 1 时唯一位置给该兜底，不能同时容纳专业工具。

“帮我看看 note.md 里讲了啥”以前没有命中文件旧规则，现在能识别常见扩展名、上传/附件/读一读等口语，提高只读文件类别相关性。内置 search/read 有有限排序偏好；新只读工具声明 workspace_file 类别也可参与召回，并非给每个工具硬编码名称。新工具仍需原有审核、Schema、权限和业务质量配置，不能称零配置适配。

明确短追问可用同会话最近 8 条消息中最近一个不同的用户问题，最多读取前 600 字。忽略助手和工具正文，不越过已切换的话题；当前问题明确问天气/路线/新闻或排除文件时不用旧文件话题。只补召回，不复制整段历史，不生成路径/参数。会话历史由上游按会话获取；真实用户、项目和文件权限由 Executor/Provider 继续校验。

“别联网”移除联网候选，“不要调用任何工具”返回空候选；规则兜底也限定在本轮候选中，fallback_tool_key 不能指向其外工具。真实测试发现旧规则兜底可能把本地文件问题送去联网，这次一起修复。

普通只读问题不再因为编辑预览标为 read_only 就一并召回编辑工具；通过已有 approval_draft/file_revision Profile 判断编辑用途，用户明确要修改或 Diff 时仍参与排序，不硬编码具体工具名称。

否定联网也不能被当成切换话题而丢弃文件历史线索。另修复“规划失败、规则没有候选内调用”被当成“无需工具”的分支：external_context_service.py 记录 tool_planning_unavailable，并将未取得本轮核验结果的状态交给最终模型；已有证据可保留，没有取得的原文不能凭历史猜测。用户明确禁用工具的空候选仍正常结束，不误标失败。

## 二、代码链路与文件

```text
Chat 当前问题、同会话近期消息
  → 工具开关、Skill 白名单、明确禁用要求
  → 当前文件名/口语或有限用户追问线索
  → 排序、类别覆盖、添加前检查容量
  → 少量候选和原因交给在线 Planner
  → 紧凑 ToolPlan，或候选内规则兜底
  → 既有 Schema、权限、依赖和质量校验
  → 证据/状态进入最终模型 → 流式回答和保存
```

## 三、V3.2 与真实验收发现

前后端在线默认值及固定测试账号已切为 deepseek-ai/DeepSeek-V3.2，密钥未修改或输出，新测试使用该模型。账号原有 14 个明确指定 V4 的历史会话保留原设置，需要继续使用时在界面切换模型。没有加载本地 Ollama。

初次真实场景未通过，不能算验收成功。旧完整规划输出的一次诊断约 42 秒，超过原 15 秒。减少重复元数据、要求紧凑 JSON/短原因/省略空可选字段后，一次诊断约 15.7 秒、146 输出 token。单次规划上限改为 25 秒，各模式 35/75/50/35 秒总时长不变。这是固定样例，不是总体性能提升指标；V3.2 排队/复杂输出仍可能超时，安全兜底本身是正常可测行为，不保证每轮都由模型成功规划。

现有非思考调用使用 enable_thinking=false，[硅基流动 V3.2 官方示例](https://www.siliconflow.com/zh/blog/deepseek-v3-2-now-on-siliconflow-reasoning-first-model-built-for-agents)也提供该参数；没有改成原生 Function Calling。候选修复没有新增工具 Embedding 或 LLM 召回。

## 四、联合验收

后端全量 637 项通过（PostgreSQL/pgvector 实际启用，0 跳过），前端 lint/build、compileall、git diff --check 通过。

第三步最终 V3.2 浏览器验收为同一会话连续 3 轮、无显式 Skill、浏览器错误 0，运行模式保持 workspace_review，均保存 assistant done：第一轮文件名口语取得目标文件搜索证据、回答 CedarLedger（1 次 search，Tool 阶段 8,164 ms）；第二轮明确要求复述刚才已核实的项目名，候选正确继承用户文件线索，Planner 判断无需重查，复用同会话真实证据回答 CedarLedger（0 次调用，20,746 ms）；第三轮明确禁用工具，空候选、0 次调用、回答已收到（1,766 ms）。第二轮不是取得新事实或重新读取文件，不把它计作 read 通过。

第一步 V3.2 故障验收复验通过：两次真实读取一份成功、一份延迟后取消，route partial，调用 success/timed_out，assistant done。模型使用 7 天、没有编造未取得的 41 天，并说明缺失部分。最终复验 Tool 总耗时 35,014 ms，规划 10,873 ms，执行 24,135 ms；协作式取消清理可有毫秒级超出，不承诺强制抢占阻塞线程。

规划失败的受控场景也完成真实 V3.2 最终回答和落库：Planner 在独立测试进程模拟超时，无安全规则调用、无 Tool Call；工具 route error，最终消息 done，291 字回答明确无法核实，没有编造原文。故障发生在规划，不把它描述成一次真实成功 Tool 调用，也不是浏览器中注入超时。

第二步 V3.2 浏览器复验：126 文件中目标在最新 120 个之外，exact_name 使用定向 search→read（2 次调用、2 轮规划、Tool 耗时 30,994 ms）；continue_search 搜索第一页→续页→read（3 次调用、3 轮规划、19,128 ms）。两个场景均由在线 Planner 完成，无 fallback，Tool success、assistant done、回答使用 CedarLedger 的 17 天事实、浏览器错误 0。独立 Worker 完成定向搜索→绑定→读取，2 Step、2 Artifact、Run succeeded、原会话结果消息 done；Worker 回写是代码模板，未额外调用最终模型。

初期原文第一行追问中，搜索摘录已经包含完整短文件，模型可以从搜索回答，不作为真实 read 验收。额外样例把第 81 行放到搜索摘录之外，并严格检查 read：多次在线规划超时，修复前曾编造原文，修复后正确说明无法核实；也出现只 search、未实际 read 的尝试，不计为成功。该额外场景未完成业务验收，保留为后续完善无 Skill 原文完成条件的回归入口；当前明确原文完成合同主要绑定显式文件 Skill，普通无 Skill 调用仍依赖 Planner 的选择。默认候选验收使用事实追问；实际 read 由第二步定向/分页和 Worker 场景验证，不为了凑通过数量把搜索说成读取。

以上成功场景是固定验收记录，不是无失败率或普适任务成功率。规划模型不可用时正常披露限制，但不保证业务任务仍能完成。

普通事实问题允许用真实搜索片段，复述已核实事实可复用同会话证据，不强迫增加无必要 read；显式文件 Skill 的原文读取、分页和 Worker 场景单独验证 read。验收检查业务事实、实际文件 ID、最终回答和保存状态，不能只看 HTTP 200。在线 Planner 出现安全兜底时如实记录，不将兜底伪装为模型成功。

## 五、边界与后续

规则只覆盖有限文件类型和追问表达，不保证任意代词或工具业务都召回。候选不是授权，Executor 的 Schema、ACL、凭据、风险和质量门继续生效；完整规划循环持久化未实施。

前三步按本轮明确授权联合提交并推送。Day 6 回到 Redis 数据结构、缓存读写、TTL 和一致性；实际讲解与问题记录本地/飞书。用户未完成 Redis 作答时不进入 Day 7，不安排算法题。
