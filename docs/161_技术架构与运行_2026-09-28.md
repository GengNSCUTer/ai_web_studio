## 运行形态和职责

前端基于 Next.js/React，负责工作区、会话、知识库、设置、工具追踪和任务页的交互。FastAPI 后端负责鉴权、项目与用户隔离、业务事务、上下文组装、Provider 适配、工具规划与执行。SQLAlchemy 连接 PostgreSQL；pgvector 承担同库向量检索，BM25、RRF 与可选 Rerank 构成查询链。Redis Stream 是后台任务投递通道，不与 PostgreSQL 共享事务。

5 月设计选择用户态 PostgreSQL 而非 SQLite，是为了在无管理员权限的共享服务器上保留正式的事务和并发语义；不强制 Docker，则是当时部署约束，不是产品宣称永远不支持容器。前端与后端分离、数据库持久化、后台 Worker 独立运行，这三点仍是当前架构基础。在线 OpenAI-compatible API 与本地 Ollama/vLLM 均有 Provider 入口；实际验证可使用在线 API，而不必启动大型本地模型。

## 数据与请求链路

用户发起 Chat 时，后端先保存用户消息和 assistant 占位消息，建立附件、检索、来源和 Tool Trace 的锚点。短事务结束后再调用模型并通过 NDJSON 流式回传；生成终态按 message ID 与 generation ID 做 CAS，避免旧请求覆盖重新生成后的结果。强杀进程时未收口的 partial 内容仍可能丢失，不把流式连接本身描述成 Durable Checkpoint。当前 NDJSON 事件还包含 context_info，将诊断放入流中，避免响应头超过限制后丢失诊断入口；历史设计的 SSE 讨论不能当作当前协议。

流式终态收口已使用独立的 PostgreSQL `AsyncSession`：开始模型流前释放请求侧同步会话，完成、失败和断连取消后以短事务写回消息，并对取消时的 partial 保存设置限时保护。准备与上下文组装阶段的 Repository 仍有同步 SQL，因此当前不是全异步后端；这一变化主要减少流式收口时的事件循环阻塞和长流期间闲置事务，不能未经压测宣称单条 SQL 变快或整站吞吐提升。对应实现位于 `backend/app/services/chat_persistence_service.py` 和 `backend/app/api/routes/chat.py`。

知识库索引则由 Document/Job 与 Outbox 在数据库事务内落库，经 Redis Stream 投递给 Worker。Worker 解析、分块、Embedding、建立向量和 BM25 索引，形成 inactive generation，校验后按版本 CAS 激活。重投递由幂等状态和版本保护处理；数据库与 Redis 没有跨服务原子事务。查询时在用户和项目范围内分别检索向量与词法候选，RRF 融合、可选 Rerank，再按证据预算注入模型。

Tool 链由 Catalog、候选筛选、LLM Planner、参数/依赖验证、Executor、质量合同和证据投影组成。Planner 输出结构化 ToolPlan，不发 HTTP 请求，也不能授予权限；服务端检查 Schema、凭据、ACL、项目作用域、风险与 SSRF，处理 Tool DAG 的并发、依赖阻断、部分成功和失败收口。动态 MCP 需要来源和版本审核；Skill 只组合已有 Tool，不自动扩大权限。文件写入由独立 Diff、审批审计与 FileRevision CAS 控制：默认 ask 逐次确认，read_only 禁写；full_workspace 是用户预先授权的项目范围写入，可省逐次弹窗，仍受 ACL、Patch 记录及版本保护。

## Durable 与同步的边界

2026-10-20 调度取舍复核：Durable 保留 PostgreSQL 任务队列。`DurableToolRunService.claim_next` 使用 `FOR UPDATE SKIP LOCKED` 领取 pending 或租约过期事件，在短事务中记录 owner/lease_version 后执行；空闲轮询默认一秒，不代表排队任务均一秒内启动。Redis Stream 仍只用于知识库索引投递。本次未测得 Durable 领取吞吐或延迟瓶颈；换 Redis 会增加 Publisher、XADD/数据库提交窗口、XACK/Pending 接管及投递对账，不能替代数据库任务状态、幂等和 Fencing。若后续测得领取瓶颈或需要多机器消费组调度，再评估增加 Redis 分发层。55 项相关测试通过，其中 2 项在独立真实 PostgreSQL 临时数据库验证并发幂等与租约接管；其余使用 SQLite/受控工具/FakeRedis，不属于在线模型或真实 Redis 故障演练。学习与证据见 [Day 15](/disk2/gengnan/简历/第二轮面试记录/Day15_DurableHandoff与跨服务一致性.md)。

2026-10-09 的 [Tool 改进第一步](168_Tool改进第一步_统一截止时间与部分结果保留_2026-10-09.md)使同步 Planner 和工具执行共用总截止时间。并发超时保留已完成且质量有效的证据，未完成调用记 timed_out，下游依赖阻断；系统未完成说明进入最终模型输入。准备阶段收到上游取消时按 generation CAS 收口为 cancelled；首次规划超时即使没有计划也有持久化错误轨迹。

[第二步](169_Tool改进第二步_文件非阻塞与搜索范围_2026-10-09.md)把文件同步查询移出事件循环：线程内独立 Session 获取快照、释放连接后匹配，再短事务按顺序锁行复核返回版本。文件名/ID 可定向查询，普通 list/search 返回扫描范围和绑定用户/项目/原条件的签名继续位置；Planner 仅收到有限事实，最终回答收到范围说明。619 项测试和真实浏览器/在线模型、独立 Worker 回写验收通过。这是线程池隔离，不称全后端原生异步数据库；查询进行中不能强杀，跨页也不冻结整库正文。

同步 Chat 有固定运行模式和总轮数、调用数、并发、时间预算。多步骤低风险只读 Tool Plan 可以由用户显式预览与确认，另建 Durable Run；Planner 的 `durable_candidate` 只是建议，普通 Chat 不会自动改为后台执行。AgentRun、AgentStep、Checkpoint、Artifact 和 Outbox 记录状态；独立 Worker 领取任务，凭 Lease、心跳与 fencing 阻止过期实例覆盖新结果。终态幂等回写原会话，任务页支持查询和需再次确认的 DLQ 重放。执行快照绑定 Tool/Skill 版本，漂移时拒绝回放；JSONL 审计只导出摘要和哈希，不导出凭据及完整 Tool 正文。

Durable 当前由独立 Worker 直接领取数据库 Outbox，最多 12 步冻结只读计划；Redis Stream 用于知识库索引任务。成功并提交的步骤产物可复用，中断的只读调用可能重新执行，这是有限重试和可恢复最终一致性，不是外部操作 Exactly Once。Durable 不承载任意写 Tool，也不允许借重放绕过审批。Worker 已有心跳指标与用户级 systemd/Supervisor 托管；尚未配置外部告警推送和自动扩容，进程存活也不替代业务成功判断。
