# AI Web Studio：技术架构与运行

更新于 2026-09-28。本专题吸收 5 月《技术实现设计》中仍有价值的环境约束、前后端分工、数据模型、SSE 和部署决策，并补齐当前 RAG、Tool、Skill 与 Durable 运行时。原设计全文仍在本地 [06 技术设计](06_技术实现设计.md)及飞书旧版中；早期只接 Ollama、尚未做 RAG/Agent 的段落不代表当前实现。

## 运行形态和职责

前端基于 Next.js/React，负责工作区、会话、知识库、设置、工具追踪和任务页的交互。FastAPI 后端负责鉴权、项目与用户隔离、业务事务、上下文组装、Provider 适配、工具规划与执行。SQLAlchemy 连接 PostgreSQL；pgvector 承担同库向量检索，BM25、RRF 与可选 Rerank 构成查询链。Redis Stream 是后台任务投递通道，不与 PostgreSQL 共享事务。

5 月设计选择用户态 PostgreSQL 而非 SQLite，是为了在无管理员权限的共享服务器上保留正式的事务和并发语义；不强制 Docker，则是当时部署约束，不是产品宣称永远不支持容器。前端与后端分离、数据库持久化、后台 Worker 独立运行，这三点仍是当前架构基础。在线 OpenAI-compatible API 与本地 Ollama/vLLM 均有 Provider 入口；实际验证可使用在线 API，而不必启动大型本地模型。

## 数据与请求链路

用户发起 Chat 时，后端先保存用户消息和 assistant 占位消息，建立附件、检索、来源和 Tool Trace 的锚点。短事务结束后再调用模型并通过 SSE 流式回传；生成终态按 message ID 与 generation ID 做 CAS，避免旧请求覆盖重新生成后的结果。强杀进程时未收口的 partial 内容仍可能丢失，不把 SSE 连接本身描述成 Durable Checkpoint。

知识库索引则由 Document/Job 与 Outbox 在数据库事务内落库，经 Redis Stream 投递给 Worker。Worker 解析、分块、Embedding、建立向量和 BM25 索引，形成 inactive generation，校验后按版本 CAS 激活。重投递由幂等状态和版本保护处理；数据库与 Redis 没有跨服务原子事务。查询时在用户和项目范围内分别检索向量与词法候选，RRF 融合、可选 Rerank，再按证据预算注入模型。

Tool 链由 Catalog、候选筛选、LLM Planner、参数/依赖验证、Executor、质量合同和证据投影组成。Planner 输出结构化 ToolPlan，不发 HTTP 请求，也不能授予权限；服务端检查 Schema、凭据、ACL、项目作用域、风险与 SSRF，处理 Tool DAG 的并发、依赖阻断、部分成功和失败收口。动态 MCP 需要来源和版本审核；Skill 只组合已有 Tool，不自动扩大权限。文件写入由独立 Diff、审批与 FileRevision CAS 控制。

## Durable 与同步的边界

同步 Chat 有固定运行模式和总轮数、调用数、并发、时间预算。多步骤低风险只读 Tool Plan 可以由用户显式预览与确认，另建 Durable Run；Planner 的 `durable_candidate` 只是建议，普通 Chat 不会自动改为后台执行。AgentRun、AgentStep、Checkpoint、Artifact 和 Outbox 记录状态；独立 Worker 领取任务，凭 Lease、心跳与 fencing 阻止过期实例覆盖新结果。终态幂等回写原会话，任务页支持查询和需再次确认的 DLQ 重放。执行快照绑定 Tool/Skill 版本，漂移时拒绝回放；JSONL 审计只导出摘要和哈希，不导出凭据及完整 Tool 正文。

这是至少一次投递、有限重试和可恢复最终一致性，不是 Exactly Once。Durable 不承载任意写 Tool，也不允许借重放绕过审批。当前 Worker 有启动脚本和心跳指标，但没有外部告警推送、自动扩容或正式生产 supervisor。
