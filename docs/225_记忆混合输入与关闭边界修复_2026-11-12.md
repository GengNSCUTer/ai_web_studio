# 长期记忆混合输入、关闭边界与文档收口

2026-11-12。核对用户提出的两个问题，均在原代码中复现后修复。没有增加每轮LLM价值判断，没有扩大自动启用或跨项目权限。

## 1. 稳定陈述后提问不应整条跳过

旧`rules-v2`先判断整条输入是否以问号结束，因此“我的项目使用 PostgreSQL，问题是如何优化索引？”被判为普通问题，既不提取，也进不了仅处理buffer的语义复核。原48例题本s13确实记录该漏例。

新`rules-v3`仍先处理外部资料、敏感信息、拒绝记忆、临时性和不确定性；去除引文后，若整条是问题，则检查问题之前是否存在独立明确的陈述分句。分句使用通用标点，不增加数据库/业务关键词；带“是否/什么/应该/吗”等疑问或建议语气的分句、缺少陈述值的分句不作为事实。纯问题继续skip，明确事实＋问题触发`stable_statement_with_question`，暂定/假设仍buffer。

这只是入队信号，不是直接生成事实：原消息仍交原候选提取器，由模型选出有长期价值的内容，再核验逐字原文、主体、敏感信息、范围、冲突与启用条件。问号也继续阻止该来源自动启用；本轮真实候选保持pending。不会把优化索引的问题或模型回答自动存为用户事实。

| 输入 | 当前动作 |
| --- | --- |
| 我的项目使用 PostgreSQL，问题是如何优化索引？ | extract_now |
| My project uses PostgreSQL. How do I optimize indexes? | extract_now |
| 我的项目是否使用 PostgreSQL，如何确认？ | skip |
| 我的项目使用 PostgreSQL 吗？如何检查？ | skip |
| 我的项目今天使用 PostgreSQL，如何优化索引？ | skip |
| 我在论文中看到‘我的项目使用 PostgreSQL’，如何理解？ | skip |
| 我的项目可能使用 PostgreSQL，如何优化索引？ | buffer |

边界：这仍是保守规则，不宣称理解任意混合句；无明显分句的含糊表达与复杂语气仍可能漏判。下一步优先用已实现的本人标注接口收集自然样本，不把规则自判结果当人工标签，不追求堆词让构造集满分。

## 2. 关闭长期记忆即停止新的触发分析

原实现关闭时仍读取最多50条用户原文、分类、计算来源摘要并写入`memory_trigger_decisions`，只是不创建提取Job。现在关闭分支在读取正文之前返回，不调用分类、上下文特征计算或观测写入；强制提取也不能绕过总开关。

只保留必要位置维护：读取当前已完成assistant的ID/序号，推进`memory_scan_cursor`、清空待处理缓冲，提交短事务。因此关闭期间的对话仍可正常Chat保存，但不作为记忆触发来源；重新开启只处理后续输入，不补记关闭期间内容。设置查询显式刷新Session内缓存，避免同一Session早先读到开启值后继续沿用。

已开始的外部模型请求不能撤回已经发出的资料；现有Worker在快照、语义结果与候选提交前复核同意状态，关闭后拒绝旧结果保存。关闭开关不会自动删除此前已创建的记忆、Job或观测，不等于数据擦除；旧记录仍受本人访问控制与会话删除级联清理。本次不批量删除用户既有数据库记录，不更改数据保留承诺。
