# 结构化证据预算与统一来源映射

2026-11-03。本次替换195中的“文本裁剪后按位置补齐来源”实现，只保留第一层标签审计，不接入线上语义Judge、答案改写或纠错请求。

## 现在如何执行

检索/工具产出来源 → EvidenceUnit保存标签、正文和出处 → EvidenceSection按预算保留、删除或显式节选 → 从保留单元渲染最终Prompt并生成final_source_map → 模型回答 → 标签审计 → 原回答、最终来源、审计结果按generation CAS同事务保存 → 页面卡片与引用跳转。

1. RAG来源保留chunk_id、document_id、source_start/source_end、检索日志和Parent命中关系。工具标签由服务端统一分配T编号。正文中伪造的标签不能注册来源，不通过扫描正文反推清单。跨知识库重新编号后保持本轮稳定，不因为预算删除中间来源而重新挪用其编号。
2. KB/Tool在PromptBuilder内部携带结构化单元，ContextGovernance按层优先级和单元预算处理。完整单元放不下时尝试边界节选；标题不单独算证据。节选记录citation_body_truncated、实际正文长度、相对原证据的保留范围及原正文长度，Prompt也标明未提供全文。普通Chunk的预裁剪也记录部分状态，不再只给Parent标记。
3. 节选优先保留行、句子或单词边界，避免半个代码块、行内代码和Markdown链接。完整JSON不截为半份JSON；没有可用边界则删除。Parent围绕命中区取窗，无法保留完整命中时可退回完整Child。这只是结构与来源检查，不证明节选足以回答问题，也不等同语义完整性判定。
4. GovernedContext.final_source_map从实际保留单元生成，和渲染Prompt共用输入。移除align_sources、citation_span以及生产路径的标签行扫描；不再先维护三份独立数据再补齐。Provider只收到标准messages，内部单元不发送。摘要、长期记忆、附件等原治理规则仍保留，本次统一的是有KB/T引用编号的证据。
5. Chat外发事件、消息external_sources、context_details.final_source_map、检索日志sources_json都来自最终映射；candidates_json/selected_json保留原检索及RAG阶段选择结果。已排除的编号单独进入诊断，不混入可引用来源卡片。检索阶段与最终输入阶段分别计数，不能把候选数称为注入数。
6. 第一层审计只认可最终映射；已注册后被排除与从未存在的编号分别报告。需要复核保留原文，正常Chat仍可done；取消/失败为incomplete。所有结果support_checked=false，旧消息不回填为通过。
7. 网页Markdown正文中的有效KB/T引用变为本消息的来源链接，点击展开来源并定位对应卡片；代码和已有链接不改写，不存在/被排除编号保持原文且提示复核。来源卡片不再只展示前6个，Tool Trace的“看来源”也只对本消息实际保留的来源开放。刷新使用已保存的同一组来源，部分正文明确标为节选。来源卡片可打开原文定位，但原文更长不表示它全部进入了模型。
