# 阶段 4.6B：工具完成条件与证据充分性

日期：2026-09-22

## 1. 为什么需要这一层

阶段 4.6A 的真实模型测试发现：Planner 可能只调用文件搜索，搜索结果中又恰好
包含了部分正文摘要，最终模型便直接回答文件标题。这种回答看起来正确，但并
不能证明模型真正读取并核对了原文。

因此，本阶段把“工具结果是否可用”和“最终回答是否有足够证据”分开处理：

```text
Input Schema
  -> 参数格式是否合法
Tool quality_contract
  -> 这一工具本次返回是否业务有效
Skill completion_contract
  -> 这个 Skill 的任务链是否完成
Evidence sufficiency
  -> 当前问题的最终回答是否有足够来源支撑
```

## 2. 本阶段实现

新增 `backend/app/services/evidence_sufficiency.py`：

- 对工作区文档审阅问题识别“原文、标题、内容、读取、核对、审阅、事实”等直接
  原文核验意图；
- 没有 `workspace_file_read` 时标记 `insufficient`，提示模型不能声称已核对原文，
  不能根据文件名、搜索摘要或模型记忆猜测；
- 读取结果为空或没有可解析文本时同样标记证据不足；
- 有非空文件读取片段时标记 `sufficient`，要求模型只引用读取片段明确出现的内容，
  读取范围不足时说明限制；
- 非工作区文档审阅问题不强行套用文件读取合同，普通 Chat 和其它 Tool 保持兼容。

`ContextPromptBuilder` 将代码侧生成的证据指导放入平台 system 约束；
`ChatContextAssemblyService` 将证据状态写入上下文诊断和详情；Chat header 只保留
状态、来源类型和原因，不回显文件正文或敏感内容。

## 3. 与已有 Contract 的区别

`quality_contract` 属于 Tool。比如文件读取返回空文本时，它可以把本次调用标记为
空结果；搜索工具可以判断是否至少找到一个文件。它回答的是“这一次调用结果是否
达到工具自己的业务质量标准”。

`completion_contract` 当前属于 Skill Manifest。它回答的是“这个 Skill 为完成任务
是否必须经过哪些步骤”。例如文档审阅在用户询问第一行标题时，搜索得到 `file_id`
后必须继续读取原文。它不能增加 Skill 未声明的工具权限。

`evidence_sufficiency` 位于最终回答之前。即使 Tool 结果本身 schema 合法、质量状态
也可接受，若来源类型不能支撑用户要求的事实，最终模型仍必须说明证据不足。

## 4. 真实验证

使用固定测试账号已有的在线 openai-compatible Provider，通过真实浏览器执行：

```text
浏览器 Chat
 -> 在线 LLM Planner
 -> workspace.files.search
 -> completion_contract 触发下一轮
 -> workspace.files.read
 -> 证据充分性 guidance 注入最终回答 Prompt
 -> 最终模型回答
```

结果：

- `planner_strategy = llm_primary`；
- 实际执行 `workspace.files.search` 和 `workspace.files.read`；
- assistant 状态为 `done`；
- `ToolRouteRun` 状态为 `success`；
- 文件未发生写入；
- Playwright 无 `pageerror` 或 console error；
- 临时项目、会话和文件已清理。
