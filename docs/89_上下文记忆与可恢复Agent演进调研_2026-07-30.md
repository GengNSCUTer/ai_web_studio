# 上下文、记忆与可恢复 Agent 演进调研

更新时间：2026-07-30

## 1. 结论先行

AI Web Studio 当前准确定位是“带 RAG、安全记忆生命周期与受控 Tool Workflow 的 Chat/Agent 平台”。工具链能进行候选筛选、LLM 结构化规划、Schema/Policy/Credential 校验、最多两轮的观察后再规划，以及低风险只读工具执行；文件修改已具备持久化 Run/Step/Checkpoint、Diff 审批、版本 CAS 和审批 continuation，但它仍不是能够长期自主执行、任意读写本机文件或从任意第三方 Tool Step 续跑的通用 Durable Agent。

本轮不通过夸大上下文窗口、增加不受约束的工具数来追求“更像 Agent”。主线是：

1. 让进入模型窗口的内容更少、更相关、来源可追溯。
2. 让长期记忆有候选、审核、冲突和遗忘生命周期，而不是无界追加。
3. 文件能力从用户/项目隔离的只读原语开始；写操作必须具备草稿、确认、幂等与恢复控制面。

## 2. 主流实践调研

### 2.1 上下文不是越大越好

Anthropic 在《Effective context engineering for AI agents》中把上下文描述为有限的 attention budget，并指出随着上下文变长，模型对其中信息的可靠回忆会下降（context rot）。工程目标应是“最小的高信号上下文”，而不是把所有历史、所有工具结果和所有文件内容一次性塞入 Prompt。

对产品的可复用策略：

- **稳定前缀**：系统约束、稳定项目说明放在前缀，便于缓存和保持行为一致。
- **最近对话 + 滚动摘要**：原始历史只保留最近窗口；更早消息按已覆盖边界增量摘要，不反复摘要同一段。
- **Just-in-time retrieval**：上下文先保留文件 ID、检索结果 ID、URL 等指针；真正需要时再读一个小片段，而不是预加载整个对象。
- **Tool result clearing / compaction**：较早的原始工具输出只留结构化 Trace/Artifact，Prompt 只保留被验证的摘要、引用和下一步需要的字段。
- **上下文隔离**：复杂研究可让独立任务在自己的上下文中探索，主流程只接收短摘要，而不是累积全部检索和工具日志。

Claude 的公开工程文章提到：Claude Code 采用“稳定说明预加载 + 文件导航/搜索按需读取”的混合方式；压缩时保留架构决策、未解决问题和实现细节，丢弃重复消息和原始工具输出，并保留近期访问文件。这是适合借鉴的上下文工程原则，不等于本项目已经复刻 Claude Code。

Codex 的公开开发者文档在本次环境中无法直接拉取（官方站点返回访问保护页面），因此不对其内部压缩实现做未经证实的推断。工程方案以公开、可核验的上下文管理原则和本项目现有代码为准。

### 2.2 自动长期记忆不是“模型直接写数据库”

主流 Memory 设计把“提取”和“生效”分开：模型可以从对话中提取候选，但候选不是可信事实。自动写入会面临幻觉、临时意图被误当成长约束、敏感信息、与旧记忆冲突以及记忆无限膨胀。

合理的生命周期是：

```text
conversation evidence
  -> candidate/pending
  -> dedupe + conflict + risk classification
  -> user confirmation or low-risk auto-activation
  -> active
  -> superseded / expired / rejected
```

其中每条记忆应有来源消息、置信度、重要度、敏感等级、有效期/复审时间和被替代关系。模型的内容提取只产生候选；是否进入 active，以及出现冲突时如何处理，必须由规则、用户确认和审计共同决定。

### 2.3 文件工具与 Durable Agent 是两层问题

像 Claude Code、豆包等产品的“文件能力”不等于给模型一个任意路径的读写接口。正确的最小工具原语是 `list -> search -> read_range`，只接受受控资源 ID，并在服务端做 workspace/ACL 校验。写入先做 `create_draft` 或 `apply_diff`，把待改内容、目标版本和 diff 呈现给用户；确认前不改变源文件。

“工具能循环调用”也不等于“可恢复”：当前请求内 ReAct/Workflow 进程崩溃后会丢失控制状态。真正的 Durable Runtime 需要数据库状态机、Worker、lease、fencing、checkpoint、重试/DLQ 和外部副作用幂等。MCP Tasks 的 taskId 与状态协议可帮助对接异步工具，但不会替应用实现这些可靠性控制。

### 2.4 三份飞书参考资料的适用性判断

本轮逐篇核对了《理论学习：上下文压缩与 Token 管理》《理论学习：跨会话记忆与会话持久化》《理论学习：Function Calling 与工具系统》。结论不是简单照搬，而是区分运行形态。

上下文资料中的“大结果外置 + 临界点全量摘要”适合会把文件读取、Shell 输出长期保存在消息链里的 Coding Agent。AI Web Studio 当前只把本轮压缩后的 Tool evidence 注入 Prompt，完整结构化结果单独存入 Tool Trace，并不会让旧 Tool output 随对话线性累积。因此当前没有必要把同一结果再写一份磁盘文件。真正值得借鉴的是：Tool evidence 先于用户历史压缩、摘要保留决策和未完成事项、摘要后明确要求重新读取细节，以及未来有持久化 Tool Step 后按稳定 artifact ID 冻结历史表示。

“决策冻结”只在同一个 Tool output 会跨多轮反复出现在消息前缀时成立。当前外部工具结果只服务当前轮，不存在后来把旧原文改成指针导致前缀变化的问题。`last_prompt_prefix_hash` 仍是本地诊断字段；本轮另外接入了 Provider 原生缓存参数与 usage 观测。两者不能混为一谈：前缀哈希相同只说明“理论上可复用”，`cached_input_tokens` / `cache_read_input_tokens` 才说明 Provider 实际命中。未来恢复历史大 Tool Result 时，仍需要 `ToolArtifact(call_id, content_hash, preview, replacement_state)` 冻结 kept/replaced 决策。

记忆资料中的用户级/项目级分层、自动提取和索引式加载值得采用；“模型每轮结束后直接增删 active 记忆”不适合多用户 SaaS。模型可能误提取临时事实、密钥或恶意指令，因此本项目坚持 `candidate -> deterministic risk check -> user review -> active`。本轮已经补齐持久化异步 Job、pending 生命周期、项目隔离、风险分类和用户开关；自动候选默认关闭，开启后也只产生 pending，不会绕过人工确认。

工具资料中的 `name/description/schema/read_only/destructive/concurrency/validate/execute` 抽象，与本项目已有 ToolDefinition、Catalog、Schema Validator、Executor 基本同构。本轮在“工具错误作为可修正反馈”和 `old_string` 唯一匹配之外，继续实现了文件修改专用 Approval Continuation、FileRevision CAS 和 Durable Run。Bash、SQL、删除、外部发布仍未开放，因为这些副作用还需要更强的 sandbox、命令策略、下游幂等和补偿能力。

## 3. 本轮已落地的改进

### 3.1 Query-aware、项目隔离与候选风险分级

改动位置：

- `backend/app/services/memory_service.py`
- `backend/app/services/chat_context_assembly_service.py`

旧行为按 `updated_at` 读取所有启用记忆，再尽量塞进字符预算。问题是“去年旅行”“当前工作项目”等无关事实也可能进入回答 Prompt，占用 Token 并造成干扰。

现在的第一阶段选择策略：

```text
current user query
  -> 英文词/标识符 + 中文二元词轻量词法匹配
  -> project/fact 只保留与 query 有命中的记忆
  -> profile/instruction 作为用户显式长期偏好/约束保留
  -> 仍由 memory_max_chars 做最终预算
```

这不是把词法相似冒充语义检索。其优点是无额外 Embedding 依赖、可解释、稳定，并可避免明显无关事实进入 Prompt；局限是同义改写、隐式关联和中文分词不足时可能漏召回。后续语义化前必须先定义 Memory embedding 的 `provider/model/dimension/version` 约束，不能混用不同模型的向量。

本轮继续补了两层边界：

- 由某个 conversation 提取出来的 `project` 记忆，会解析来源会话的 `project_id`，只在同一项目注入；来源会话丢失时失败关闭。没有来源会话的历史手工记忆暂时保持全局行为，避免破坏既有数据，后续应迁移到显式 `project_id`。
- 候选记忆新增确定性风险分类：凭证值、邮箱、手机号、身份证号标为 `sensitive`；带“今天/本周/暂时”等表达的事实标为 `volatile`；长期 `instruction` 标为 `review_required`。重复候选仍优先标为 `duplicate`，避免无价值写入。

这仍然不是自动记忆：当前 `/memories/suggest` 只生成候选，用户确认创建后才成为启用记忆。自动候选提取需要先有 pending 生命周期和异步 Job。

### 3.2 结构化滚动摘要与压缩边界

滚动摘要 Prompt 现在固定保留五类信息：用户目标与原话约束、关键事实与术语、已完成工作与决策、错误与解决方式、未完成事项与下一步。摘要调用明确禁止工具调用、禁止保存凭证；遇到缺失细节必须写“需重新读取/检索”，不能补写不存在的事实。

摘要注入模型时增加“压缩边界”：摘要只是高价值历史，不是文件或工具原文。后续任务依赖具体行、原始 Tool output 或未写入摘要的细节时，模型必须重新读取。这比单纯把一段自然语言摘要塞入 Prompt 更能减少摘要幻觉。

### 3.3 外部工具结果公平压缩

改动位置：`backend/app/services/tools/formatter.py`。

旧行为按来源顺序拼接，一条长网页结果可能占满 `max_chars`，让之后独立工具的事实完全不可见。现在在来源证据预算中为尚未处理的来源预留均分额度：

```text
remaining evidence budget / remaining sources
```

当预算小到不足以展示两条有意义的证据时，宁可保留一条完整些的来源，也不会把只有标题的第二条来源误标成“已注入”。原始结构化 `ExternalSource` 仍保留在 Tool Trace；Prompt 只注入压缩后的证据文本。

### 3.4 工作区只读文件工具与编辑预览

新增：

- `workspace.files.list`
- `workspace.files.search`
- `workspace.files.read`
- `workspace.files.propose_edit`

实现位置：

- `backend/app/services/tools/providers/workspace_files.py`
- `backend/app/services/tools/adapters.py`
- `backend/app/services/tools/executor.py`
- `backend/app/tool_manifests/default_tools.json`

它们沿用现有 `Catalog -> Candidate Selector -> LLM Planner -> Schema Validator -> Executor -> Adapter -> Trace` 链路，但不是远程 MCP：数据来自现有 `ProjectFile` 表中已解析的 `parsed_text`。关键限制如下：

1. 模型无法传入 OS path、`storage_key`、URL、Shell 参数或命令。
2. 后端只接受不透明 `ProjectFile.id`，查询始终附带 `user_id`；会话属于项目时再附带 `project_id`。
3. 读文件只能按行范围，单次最多 200 行、最多 12000 字符；搜索最多返回 5 条片段。
4. 跨用户或跨项目 ID 对外统一显示“未找到”，不泄露资源存在性。
5. list/search/read/propose_edit 都是 `auth_type=none`、`risk_level=low`、`read_only=true`；`workspace.files.apply_edit` 为 `risk_level=high`、`read_only=false`，由 Executor 转入审批控制面，首次调用绝不写入。
6. `propose_edit` 只接受 `file_id + old_string + new_string`，服务端要求 old_string 在当前解析文本中恰好出现一次，然后返回 Unified Diff；未找到或多次匹配会作为安全 Tool feedback 返回给最多第二轮 Planner 调整，源文件和数据库内容不会改变。

这让“文件按需读取、来源可追溯、上下文按片段注入、修改前校验和预览”成为可演示的真实能力。真正 Apply 现已通过独立审批 continuation 开放，但只修改数据库中受 ACL 保护的 `ProjectFile.parsed_text`；它不等于修改对象存储原文件或任意本机路径。

### 3.5 Provider Prompt Cache 与真实命中观测

Prompt 顺序调整为：

```text
system
-> 周期性滚动摘要
-> 已有最近历史
-> 当前 user query
   + 当前附件/RAG/Tool/Query-aware Memory evidence
```

当前问题始终在动态证据之前；治理层按前缀截断最后一条 user message 时，会先丢弃尾部 evidence，最后才可能影响 query。这样 `system + previous history` 是连续稳定前缀，当前轮动态检索结果不会让第二条消息每轮变化。

- 官方 OpenAI Base URL（仅 `https://api.openai.com`）会发送稳定、已哈希的 `prompt_cache_key`，并开启流式 usage；读取 `prompt_tokens_details.cached_tokens`。
- SiliconFlow（识别 `api.siliconflow.cn/.com`）路径不发送其官方 schema 未公开的 `prompt_cache_key`。服务读取官方响应中的 `prompt_cache_hit_tokens`、`prompt_cache_miss_tokens` 或 `prompt_tokens_details.cached_tokens`；只有 Provider 真的返回字段时才记为 usage 可观测，不能用本地 prefix hash 冒充命中。
- vLLM 使用服务端 Automatic Prefix Caching。请求发送 HMAC 派生的 43 字符 `cache_salt` 做多租户隔离，并发送 `stream_options.include_usage=true`；不会误发 OpenAI 的 `prompt_cache_key`。HMAC 使用服务端认证密钥，Trace 不暴露 salt。
- 通用 `openai-compatible` 不发送任何缓存扩展字段，避免未知兼容服务返回 400。
- Anthropic 作为独立 Provider 使用 Messages API；在 govern 后最后一个稳定 message block 设置 `cache_control: {type: ephemeral}`，流式读取 `cache_creation_input_tokens` 与 `cache_read_input_tokens`。
- Chat NDJSON 新增 `provider_usage`，区分“本地预测可复用”和“Provider 实际缓存命中”。

vLLM 的客户端兼容不等于服务端已经启用缓存。部署时仍需启用 `--enable-prefix-caching`；若需要在 OpenAI-compatible usage 中看到 `cached_tokens`，还需启用 prompt token details。APC 只减少共享前缀的 prefill 计算，不减少逐 token decode 时间。SiliconFlow 的缓存是否命中、适用模型、费用和 TTL 以真实 usage 与控制台规则为准。

本地测试通过 mock 验证 OpenAI、SiliconFlow、vLLM、通用兼容接口的请求形状与 usage 解析。本轮没有调用付费模型制造长前缀做重复计费实验，因此只声称“协议兼容和可观测字段已接入”，不声称线上账号已经获得缓存折扣。

### 3.6 安全自动长期记忆

新增 `MemoryExtractionJob`，聊天成功后只在用户显式开启且达到 N 轮间隔时创建持久化任务。独立 worker 以 PostgreSQL lease 领取任务，Provider I/O 不持有 claim 事务；失败按可重试/不可重试分类并有限退避。

Worker 的唯一输出是 `UserMemory(status=pending, is_enabled=false)`。候选保存来源 conversation/message IDs、项目范围、confidence/importance、risk/sensitivity、content hash 和冲突替代关系；重复内容哈希不会重复落库。审核 API 支持 approve/reject：

- `duplicate` 不能激活；
- `volatile` 必须提供未来的 `expires_at`；
- `instruction`、冲突和敏感候选均明确显示风险原因；
- 冲突候选确认后，旧 active 记忆原子切换为 superseded；
- 到期 active 记忆会变成 expired 并停止注入；
- Prompt 检索只读取 `status=active + is_enabled=true + 未过期`。

自动候选默认关闭，防止用户不知情的模型成本和记忆提取。用户开启后仍不等于自动信任模型。

### 3.7 文件修改 Agent 控制面

新增：`AgentRun`、`AgentStep`、`AgentCheckpoint`、`AgentApproval`、`PatchDraft`、`FileRevision`。受控写入流程：

```text
LLM plan workspace.files.apply_edit
-> Executor 做 ACL/Policy 检查
-> 唯一 old_string 校验
-> transaction: Run + Step + baseline Revision + Draft + Approval + Checkpoint
-> SSE 只返回 approval_id + reviewed Diff
-> 登录用户领取一次性 challenge（数据库仅存 nonce hash）
-> apply 校验 user/action/args hash/expiry/nonce
-> lock ProjectFile + CAS base_content_hash + 再次唯一匹配
-> transaction: parsed_text + FileRevision + consumed Approval
                + succeeded Step/Run + next Checkpoint
```

幂等键绑定用户、规范参数哈希和基线内容哈希，不依赖每次可能变化的 LLM `call_id`。应用成功、HTTP 响应丢失后重复请求会返回已有 revision，不重复写；审批期间文件改变则进入 conflict，不覆盖并发版本。Run 查询接口能从最新 Checkpoint 恢复“等待审批/已完成/冲突”的控制状态。

### 3.8 工作区权限模式

Codex 的关键做法不是只有一个“全权限”按钮，而是把两个问题分开：命令在哪个 sandbox 范围内运行，以及何时必须向用户请求 approval。云端多租户产品不能照搬本地 Agent 的 `danger-full-access`，否则模型会获得宿主机、其他租户和平台密钥的访问机会。

当前项目新增工作区级 `WorkspaceAgentPolicy`，界面提供三级模式：

| 模式 | 低风险只读 | `ProjectFile` 受控修改 | MCP/HTTP 外部写入 | Shell/SQL/支付/发布 |
| --- | --- | --- | --- | --- |
| `read_only` | 自动执行 | 拒绝 | 拒绝 | 不在 Catalog |
| `ask`（默认） | 自动执行 | 持久化 Diff，等待一次性确认 | 无专用 continuation 时拒绝 | 不在 Catalog |
| `full_workspace` | 自动执行 | 在 ACL、参数哈希、版本 CAS、Revision 和审计约束下自动应用 | 仍拒绝 | 不在 Catalog |

`full_workspace` 的准确含义是“当前用户当前项目内、服务端明确 allowlist 的完全工作区访问”，不是服务器 full access。Executor 是最终安全边界；LLM 的计划 JSON、MCP annotation 和前端选项都不能自行放行权限。支付、邮件发送、外部发布等即使未来加入，也应保留强制确认和下游幂等键，不能被该模式自动跳过。

本轮还修复了工具设置路由的 JSON 解析回归：函数定义位置错误曾导致非空 MCP schema/config 返回 `None`，现在恢复为结构化解析并增加测试。

### 3.9 工具市场定位：云侧优先，不把 Skill 当权限插件

面试中“端侧还是云侧工具市场”是在确认执行位置和信任边界：

- 端侧工具运行在用户电脑，可访问本机文件、Shell、IDE、浏览器和桌面应用，需要桌面客户端/本地守护进程、OS sandbox 与设备授权；API Key 可以只保留在本机。
- 云侧工具运行在平台后端，适合联网搜索、地图、SaaS、云知识库和团队协作，便于统一升级、审计、限额与凭证托管，但不能天然读取用户电脑上的任意文件。

本项目当前明确定位为：**云侧优先的 Agent 工作区，提供少量稳定内置工具、用户可安装 Skill、MCP 外部连接器，以及后续的云侧插件市场；需要本机能力时再增加可选 Local Companion。** 这是由现有 FastAPI + PostgreSQL + 服务端 Tool Catalog/Executor + 服务端凭证 + ProjectFile ID 访问模型决定的。

能力分层如下：

```text
内置 Tool = 稳定、可审计的原子能力（文件 list/search/read/edit、Web、地图、RAG）
MCP         = 动态发现并调用外部服务，负责 schema/transport/credential connector
Skill       = 指令、工作流和领域知识，组合已有 Tool/MCP，描述“怎么做”
Plugin 包   = 版本化、签名、可审核的 Skill + Tool manifest + MCP 配置 + UI/资产
Policy      = 决定当前用户/项目是否允许执行
Runtime     = Run/Step/Checkpoint/Approval/Retry，保证过程可追踪和可恢复
```

因此不采用“固定五个工具，其余全部改成 Skill”的简单方案。Skill 本身不能读文件、发邮件或调用支付；它必须依赖一个真实 Tool 或 MCP capability，并始终经过 Catalog、Schema Validator、Executor、Policy 和 Trace。第一版市场应优先上架云侧 Skill/连接器包，并要求版本、权限声明、风险审核、签名和卸载能力；Local Companion 放在后续阶段，通过设备注册和最小权限通道提供本地文件/Shell，而不是让云端后端直接访问宿主机路径。

## 4. 仍然保留的明确边界

本轮完成的是“聊天主链的缓存/记忆自动候选”和“文件修改这一类副作用的 durable approval slice”，不是完整通用 Runtime：

1. `FileRevision` 版本化的是 `ProjectFile.parsed_text`。对象存储中的原始 PDF/DOCX/图片没有同步改写；二进制格式必须用格式专用编辑器和一致性协议。
2. AgentStep 已预留 lease/version 字段，但普通 Tool DAG 仍在单个 HTTP 请求内执行；只有文件审批能跨请求从 Checkpoint continuation。要让任意长任务恢复，仍需 Agent Outbox、Worker、heartbeat、fencing、有限重试、DLQ 和 reconcile worker。
3. Memory worker 当前使用 PostgreSQL job polling；生产部署要独立启动 `run_memory_candidate_worker.py` 并监控 pending age、失败率和 provider cost。
4. Memory 相关性仍是可解释的词法首筛，不是语义向量检索；未来增加 embedding 必须保存 provider/model/dimension/version signature。
5. Provider Cache 是否节省费用取决于模型、最小可缓存 Token、TTL、请求间隔和 Provider 计费规则。vLLM 还依赖服务启动参数；必须观察真实 usage，不能用本地 prefix hash 代替。
6. Bash、SQL、删除文件、支付、邮件/外部发布继续不在 Tool Catalog 中。开放前至少需要 sandbox、allowlist/denylist、资源限额、审批分级、下游幂等、补偿和审计导出。

目标仍是“At-least-once delivery + idempotent effect + explicit approval”，不是跨 PostgreSQL、Redis、对象存储和第三方 API 的伪 Exactly Once。

## 5. 验证

常规后端回归共 239 项通过（其中 3 项 PostgreSQL/pgvector 测试在常规命令中按环境变量跳过）；随后使用本地 PostgreSQL 创建隔离临时数据库单独执行这 3 项，全部通过并自动删除临时库。实际 PostgreSQL runtime schema 也确认新表/列完整创建。前端 ESLint 与 Next.js production build 通过。新增覆盖：

- Query-aware memory 对相关项目记忆的保留、无关事实的剔除，以及无 query 时的兼容行为。
- 工具结果压缩的来源编号、来源公平性、极小预算回退。
- 工作区文件 list/search/read、跨项目/跨用户隔离、行范围限制和 `storage_key` 不泄露。
- Tool Catalog、Executor、凭据策略、Prompt Governance 的既有回归。
- project memory 跨项目隔离，敏感/短期/长期指令候选风险分级。
- 结构化摘要 Prompt 与压缩边界。
- 编辑预览唯一匹配、Diff 输出、零写入，以及可安全反馈给下一轮 Planner 的工具错误。
- OpenAI 官方缓存字段只发往官方 endpoint、第三方兼容服务安全降级、Anthropic cache breakpoint 和缓存 usage 解析。
- MemoryExtractionJob 幂等投递、worker lease、pending-only 候选和长期指令风险审核。
- File edit proposal 零写入、一次性 approval challenge、版本 CAS、重复 apply 幂等、并发变化失败关闭和跨用户隔离。
