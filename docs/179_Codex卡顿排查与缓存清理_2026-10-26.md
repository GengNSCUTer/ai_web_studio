# Codex 卡顿排查与缓存清理

日期：2026-10-26。本次只处理开发环境缓存和编辑器目录监听，不修改业务代码。

## 排查结论

项目所在 `/disk2` 磁盘空间使用率 61%，可用约 2.8 TiB；inode 使用率 6%。系统根分区空间使用率 44%，inode 使用率 5%。因此没有磁盘或 inode 耗尽的证据。

项目清理前约 931 MiB，主要是前端 `node_modules`（640 MiB）和后端 `.venv`（227 MiB）；两者是实际运行/测试依赖，均保留。正在提供前端服务的 `.next`、上传文件、数据库、模型、备份、Codex 会话和认证配置均保留。

找到的明确异常是文件监听额度不足：`fs.inotify.max_user_watches=8192`、`max_user_instances=128`。VS Code 远程日志 2026-10-23、25、26 均出现过 `Inotify limit reached (ENOSPC)`；Codex 2026-10-25 日志也出现 `Failed to watch workspace root` 和 `OS file watch limit reached`。这些错误中的 ENOSPC 指监听资源耗尽，不能按磁盘空间不足解释。日志显示曾监听整个 `/disk2/gengnan`，范围覆盖多个项目、模型、Conda 环境和用户缓存。

本次可读取的当前用户进程监听数，处理前约 3865、处理后约 3852，均低于上限；进程动态变化，不能把这 13 个差值解释成配置的性能收益，也不能宣称当前卡顿唯一由 inotify 导致。系统可用内存约 192 GiB，短时 vmstat 未观察到 swap 换入换出；虽然已有 8 GiB swap 占用，也不足以证明当前内存抖动。

## 清理和预防

| 范围 | 删除普通文件数 | 释放已分配空间（字节） |
| --- | ---: | ---: |
| 项目源码/脚本目录的 Python 缓存 | 462 | 6,344,704 |
| 用户 `.cache/pip` 中超过七天的下载缓存 | 161 | 55,205,888 |
| `pip_cache/http-v2` 中超过七天的下载缓存 | 8 | 52,629,504 |
| 用户 `.npm/_cacache` 中超过七天的下载缓存 | 966 | 356,986,880 |
| 合计 | 1,597 | 471,166,976 |

共释放约 449 MiB，删除失败 0。仅删除明确缓存中的普通文件，不跟随符号链接，并移除空缓存目录；项目内删除前排除 Git 跟踪文件。安装包下次需要时可以重新下载。共享磁盘上的 inode 统计会随其他用户变化，不能用 df 前后差值充当本次删除数量。

新增两个本地编辑器配置文件：

- `/disk2/gengnan/.vscode/settings.json`：对打开上级大目录的工作区，排除依赖、构建产物、模型、Conda 环境、运行数据、备份、编辑器服务及 Codex 会话/包缓存的递归监听和搜索。
- `/disk2/gengnan/ai_web_studio/.vscode/settings.json`：单独打开项目时，排除 node_modules、.venv、__pycache__、.next、Git 对象、测试缓存和 .runtime 的递归监听与搜索。

配置只设置 `files.watcherExclude` 和 `search.exclude`，没有隐藏或删除对应目录，也没有修改全机 sysctl。项目 `.vscode/` 已被 Git 忽略，本地配置不会随项目提交自动同步。删除这两个新文件即可撤销配置。下次可从 VS Code 工作区设置中重建相同排除项。

处理链路：编辑器打开目录 → 读取工作区 watcher/search 排除规则 → 对依赖与运行产物跳过递归扫描 → 源码继续参与监听和搜索。该规则不能保证约束所有扩展自行创建的原生监听器；建议本轮结束后执行 `Developer: Reload Window`，并优先单独打开项目目录，之后观察是否仍卡顿。本轮保留当前会话，未重启扩展宿主。
