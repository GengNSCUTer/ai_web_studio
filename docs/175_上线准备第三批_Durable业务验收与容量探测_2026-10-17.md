# 上线准备第三批：Durable 业务验收与容量探测

日期：2026-10-17

第三批的目标是让后台任务在用户侧可理解、可重复使用，并留下实际运行证据。范围收敛在 Durable handoff、三条业务验收和受控并发探测，没有新增高风险工具，也没有把普通 Chat 自动改成后台任务。

## 1. Durable handoff 的重复执行控制

之前每次从 Tool Trace 重新生成 handoff 令牌，确认时都会使用新的 `handoff_id`。即使工具计划完全相同，也可能重新创建一个只读 Run。第三批在 [durable_handoff_service.py](../backend/app/services/durable_handoff_service.py) 增加了由项目、会话、assistant 消息、Skill、最大尝试次数和原始 Tool DAG 组成的 SHA-256 计划指纹，并把它作为用户作用域的稳定幂等键。

现在流程是：

1. 预览阶段只校验并查询稳定键，返回已有 Run 的 ID、状态和 Artifact 数量，不落库、不自动执行。
2. 若已有 Run 为 `queued`、`running` 或 `succeeded`，用户确认后复用同一个 Run；成功结果可以直接在当前面板继续查看，不会再次调用只读工具。
3. 若已有 Run 为 `failed`、`dead_letter` 或 `cancelled`，界面明确提示这是一次重试，只有用户再次确认才创建新的重试 Run；同一个确认令牌重复点击仍保持幂等。
4. 确认接口仍只接受签名令牌，服务端仍重新执行 Tool Schema、Skill 版本、范围、风险等级和 DAG 检查。计划指纹只负责避免重复，不会扩大权限。

涉及前端 [tool-trace-panel.tsx](../frontend/src/components/tool-trace-panel.tsx)、接口 Schema 和 `agent_runtime` 路由。高风险和写入工具仍不进入 Durable handoff。

## 2. 三条固定业务验收

入口脚本为 `PYTHONPATH=backend backend/.venv/bin/python scripts/third_batch_acceptance.py`，本次 5 个测试全部通过，失败 0、错误 0、跳过 0。

| 业务场景 | 验收内容 | 结果 |
| --- | --- | --- |
| 带来源的研究回答 | 本地 MCP 返回结构化结果和来源，结果进入上下文；另一独立分支质量失败时保留成功分支 | 通过 |
| Diff/Approval 文件修改 | 先生成 Diff 草稿，用户确认挑战通过后才按 Revision CAS 写入；重复应用不重复修改 | 通过 |

这组验收也覆盖了“部分失败”和“失败收口”。撤销和权限拒绝仍由既有 `AgentRuntimeService`、Tool Workflow 测试覆盖，未把写入能力混进只读 Durable 队列。

## 4. 当前结论和剩余问题

第三批代码范围内的 Durable 重复控制、固定业务验收和受控探测已完成。当前仍不宣称“公网生产级”或“完整自主 Agent”：

- TASK-014 的少量真实外部用户试用尚未开展，需要在取得明确同意后记录任务、问题和修复；测试账号不作为用户证据。
- Durable 目前面向低风险只读 Tool Step，不能恢复完整的 LLM 思考循环；文件写入继续使用 Diff、Approval、Revision CAS。
- 尚未提供高可用 PostgreSQL/Redis、WAL/PITR、对象存储、多副本、公网 TLS 和集中告警，这些属于部署规模扩大后的运维工作。
- 暂不纳入 Shell、Bash、SQL、删除文件、支付、邮件、外部发布和任意 HTTP 写接口。

第三批的实现和验证记录已加入上线准备计划；后续优先做真实用户试用与产品定位收口，不再无需求扩展 Tool Catalog。
