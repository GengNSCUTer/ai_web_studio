## 3. 发现的 Agent 链路缺口

原行为已经正确做到了以下安全要求：

```text
Tool A 结果质量 invalid / uncertain
-> A 的 sources 不进入最终 Prompt
-> 依赖 A 的 Tool B 不执行
```

但外层 Observe -> Re-plan 主要能得到成功 source 或一段通用错误文本。对于“请求成功但质量合同不通过”的情形，下一轮 Planner 不能稳定区分：是哪个 Tool 失败、属于网络失败还是业务质量不足、应改参数/换工具/向用户澄清还是必须停止。

## 4. 本轮实现：安全 Tool Quality Feedback

新增 `ToolWorkflowFeedback`，只包含受控字段：

```text
call_id / tool_key / display_name
outcome: failed | blocked
quality_status: valid | uncertain | invalid | unknown
next_action: replan | block | clarify | ...
bounded reasons / depends_on
```

它被转换为 `source_type=tool_quality_feedback` 的 Planner observation。它不是 Tool 输出、不是 Adapter 异常、不是 Trace 全量回灌，因此不会把外部网页、Provider 原始错误、URL 或凭据带回模型提示词。

外层行为调整如下：

```text
A 质量不合格
-> Workflow 继续阻断 B，且不注入 A 的 evidence
-> 生成安全 quality feedback
-> 若 next_action=replan：记录 tool_agent_replan_required
-> 即使首轮 Planner 未主动请求继续，也仅在同步 Chat 最多 5 轮内再规划一次
-> Planner 根据反馈换低风险候选、修正参数或请求用户澄清
```

`block`、`clarify`、文件写入审批、Executor 的最终 Schema/ACL/权限检查都不受该逻辑放宽。该机制不是自动重试，更不允许跨轮次绕过风险限制。

## 5. 验证

新增定向测试覆盖：

- `invalid` 上游结果仍阻断下游依赖；
- Workflow 会生成 `first failed -> replan` 与 `second blocked -> replan` 的反馈；
- 首轮 Planner 即使 `need_more_rounds=false`，质量合同要求 `replan` 时仍能开始一轮有上限的后续规划；
- Planner 只收到结构化、脱敏反馈和 `tool_agent_replan_required` Trace，不收到 Provider 内部地址等原始数据。

定向 `test_tool_workflow + test_tool_router`：32 项通过。完整后端回归：368 项通过、5 项条件跳过。后端已重启并通过健康检查。

## 6. 后续小步路线

1. 建立最小固定 Tool/Skill Gold Set，开始记录 Candidate Recall、Planner 选择/参数正确率、成功率、失败类型和延迟；
2. 为同步 Chat 明确产品模式：普通问答、研究/只读 Tool、工作区审阅/修改提案；不把所有模式都伪装为同一种无限 Agent；
3. 对低风险、只读、耗时任务将 Skill 接入 Durable Run，复用已有 Run/Step/Checkpoint/Lease/DLQ，补真实 Worker 端到端回归；
4. 把已有 `read_only / ask / full_workspace` 规则变成前端可见、可理解、可审计的权限体验；
5. 最后才评估新 Skill / MCP。第三方市场、任意可执行插件、高风险副作用仍不在近期范围内。
