# AI Web Studio：上下文治理与预算

更新于 2026-10-26。本专题合并 5 月《上下文治理研究与实施路线》和《上下文配置与动态预算说明》的概念、设计理由与参数解释，并以当前代码校正。原始长文在本地 [08 治理研究](08_上下文治理研究与实施路线.md)、[09 预算说明](09_上下文配置与动态预算说明.md)及飞书旧版中保留。

## 为什么不能只截断历史

单次模型请求的窗口同时承载系统/项目/Skill 约束、当前问题、近期消息、滚动摘要、长期记忆、附件、RAG Chunk、Tool 证据和输出空间。把历史全塞进去会挤掉当前任务证据，也会增加时延与噪声；只按字符截断又可能切断重要事实。治理因此分成三层：决定哪些信息有资格进入、按优先级和预算组装、再把实际保留/丢弃情况反馈给用户和开发者。它不等同于推理服务自己的 KV Cache 或对话持久化。

## 当前组装和记忆

Chat 在调用模型前先形成消息锚点；上下文服务读取当前问题、最近消息、滚动摘要、已启用的长期记忆以及按需的附件、RAG 和 Tool evidence。System 与项目/Skill 约束保持最高信任级别；外部网页、文档、Tool 返回只能作带来源的数据。当前问题和必要约束优先保留，动态证据按相关性及预算进入，其余旧历史会摘要或裁剪。证据“检索到”不等于“实际注入”，诊断须分别记录这两层。

滚动摘要以边界消息 ID 记录已压缩到哪里，仅处理新增历史。模型摘要失败、超时或为空时回退到规则摘要，不阻断正常回答。长期记忆可手动创建或由独立 Worker 增量提取；默认只产待审核候选，用户另行开启自动模式后，仅原文直接支持、稳定低风险且无冲突的事实可自动生效。来源脱敏、逐条证据核验、用户/项目范围、时效与撤销历史由代码控制，实际注入再受问题相关性和预算限制。短期消息保留细节，摘要维持连续性，长期记忆保存跨会话事实和偏好。

2026-10-09 长期记忆三步已完成：[第一步](163_长期记忆第一步_正确性与版本治理_2026-10-08.md)是范围/事实/版本、原子切换与偏好/事实预算；[第二步](164_长期记忆第二步_增量提取与受控自动生效_2026-10-08.md)是原文证据、增量游标、来源脱敏、独立 opt-in 自动模式和撤销保护；[第三步](165_长期记忆第三步_混合召回与注入诊断_2026-10-09.md)是记忆语义/词法融合、缓存失效、网络后版本复核、降级与实际注入诊断。常驻偏好最多 2 条，相关事实存在时偏好不超过四分之一记忆字符预算；本轮语言要求排除保存的默认值，临时记忆不替换长期基线。总预算裁剪保留完整记忆行，诊断区分选中与最终注入，并显示 ID、版本、范围和原因。[后台聊天通知](166_长期记忆后台通知与全流程回顾_2026-10-09.md)也已完成：成功提交后显示“已记住”，待审显示“尚未生效”，可在聊天里撤销。采用短间隔状态查询，不将通知本身插入模型上下文，也不把模型承诺视为已保存。

## 用户可调的量与内部预算

前端高层设置包括“模型上下文窗口”和 `conservative`、`balanced`、`long-context` 三种上下文模式。窗口值是后端规划输入和输出的上限参考，不保证 Provider 实际可用窗口，也不是本轮必须填满的目标。模式控制保留历史、附件和动态证据时的侧重点；通常从 balanced 开始，再依据模型能力、延迟和诊断结果调整。不要把 5 月文档里的某个固定窗口或输出预留值当作所有 Provider 的常量。

`ContextBudgetPlanner` 在 `backend/app/services/context_governance_service.py` 中对窗口设上下限，再预留输出并按模式计算输入上限；不是把窗口剩余空间全部用满。当前 conservative/balanced/long-context 比例为 0.32/0.45/0.6，仍受最低输入和输出预留等约束。本轮直接调用代码：窗口 16000、请求输出 4000、balanced 得到输入上限 5400 token、字符上限 10800、近期最多 16 条消息；这是预算函数结果，不是在线模型实测。预留输出不是保证实际生成数量，Token 也不等于字数。本地 Tokenizer 与字符约束共同控制输入，估计值不保证等于 Provider 原生计数。

实际参考层丢弃优先级为摘要→旧兼容参考→长期记忆→附件→Tool→RAG；达到预算即停止，只剩最后一层证据时尽量截短保留。仍超限再删除较旧对话，极端时截当前用户内容；此前已有历史条数筛选。这个顺序与 Prompt 显示/组装顺序不同，也不是每轮由模型动态判断重要性。`chat_context_assembly_service.py` 在 PromptBuilder 后调用治理并记录实际注入；记忆/RAG 召回成功不代表最终进入输入。摘要边界丢失时，旧摘要无法核实覆盖范围，需要重置。文件任务 Tool 与 RAG 的固定优先级仍有优化空间，本轮只核对和记录，不改业务策略。详见 [Day24 预算推演与数据库日志](/disk2/gengnan/简历/第二轮面试记录/Day24_上下文预算推演与数据库日志.md)。

同步 Tool 的运行预算是另一层：`backend/app/services/tools/run_policy.py` 控制规划轮次、总调用、单计划调用、并发、重规划次数、工具阶段时长与证据字符量。它不能被模型输出或 Tool 内容修改，也不等于模型上下文窗口。快速对话、研究、工作区审阅和编辑提案有各自固定上限；低风险长任务则通过用户确认进入 Durable Run，而不是把同步请求的轮数无限放大。

## 缓存与性能的诚实口径

2026-10-26 边界修复：`legacy_reference_context` 仅兼容旧未分层参考前缀，当前主链生成结构化参考层。授权删除仍然允许；删改已摘要范围（包括边界）时，与消息变更同事务清空摘要、边界和更新时间，下次按剩余历史重建。重生成和 Durable 原结果消息改写也纳入；仅删除摘要范围外的近期消息不影响旧摘要。组装入口固定历史副本，摘要网络等待期间释放事务，返回后锁定会话、直接读取数据库历史核对内容和 generation；若历史/摘要已变，拒绝旧结果并在最终流开始前返回 409、占位 failed，提示重试。边界缺失检查仍兜底，没有新增数据库字段或哈希。已发送输入无法追回，也不宣称自动审计了修复前所有旧摘要。代码与数据库测试见 [178](178_滚动摘要历史变更失效修复_2026-10-26.md)，教学见 [Day24](/disk2/gengnan/简历/第二轮面试记录/Day24_上下文预算推演与数据库日志.md)。

稳定 Prompt 前缀及其 hash 可以帮助观察潜在复用，但 hash 相同不等于硅基流动或其他 Provider 的真实 Prompt Cache 命中。vLLM 兼容入口可利用其服务端缓存能力，但项目不能仅凭本地诊断声称得到某个官方缓存收益。5 月研究里关于 Codex、Claude、KV Cache 和长窗口的行业讨论属于设计参考；当前已实现能力只以上述代码路径和测试为准。

排查长对话问题时先看：窗口与模式设置、输出预留、摘要边界、候选与注入证据、Tool evidence 投影、最终 Prompt 估算以及 Provider 响应。答案不佳不一定是检索失败，也可能是证据被预算排除或模型未正确使用证据。更细的历史思路见 [08](08_上下文治理研究与实施路线.md)；旧版参数解释见 [09](09_上下文配置与动态预算说明.md)，其中具体默认值需再与当前代码核对。
