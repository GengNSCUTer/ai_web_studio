# 阶段 4.5 回顾与文件工具业务闭环

日期：2026-09-21

## 1. 阶段 4.5 到底在解决什么

阶段 4.4 以前，项目已经能把外部 Tool 结果做脱敏、质量校验、受限投影和安全展示，但还缺少三类可解释性：同一来源会不会重复占用上下文预算、为什么某个来源没有进入下一轮 Planner、下一次 Tool 调用依据的文件内容到底是不是最新版本。

因此，阶段 4.5 不是新增一批 Tool，而是给“外部证据进入 Agent 后续流程”补上去重、预算诊断和版本边界。三步分别解决不同问题，不能混为一个功能。

## 2. A/B/C 的清晰分工

| 小阶段 | 解决的问题 | 代码结果 | 不负责什么 |
| --- | --- | --- | --- |
| 4.5A 来源去重 | 同一网页或同一正文在一轮、多轮重规划中重复出现，浪费上下文 | URL 规范化或 canonical 正文摘要去重；记录原始数、重复数、策略 | 不判断来源真假，不证明网页新鲜度 |
| 4.5B 投影预算诊断 | 来源为什么没有进入 Planner，过去只能看最终结果猜 | 按 Tool Profile 记录允许/实际来源数、字符数、裁剪和抑制原因 | 不扩大正文可见范围，不自动提高预算 |
| 4.5C 版本与作用域绑定 | Planner 读取文件后，文件被其他请求修改，后续编辑仍沿用旧内容 | `FileRevision`、`expected_revision_id`、用户/项目 ACL、审批参数哈希和最终 CAS | 不把 URL 或远程 MCP 响应伪装成版本证明 |

可以用一句话记忆：

```text
4.5A 管“同一证据不要重复注入”
4.5B 管“证据为什么被裁剪要说得清楚”
4.5C 管“后续动作基于哪个版本、哪个工作区”
```

## 3. 文件工具在项目中的真实定位

文件工具目前不是默认 Chat 每次都会自动调用的主链能力，也不是类似 Codex 的任意本机文件操作。它是个人本地知识库工作平台中的“受控工作区文档能力”，只在用户明确提出文件相关任务时使用，例如：

- 查看当前项目有哪些已上传文档；
- 在项目文档中搜索某个主题；
- 读取指定文件的相关行；
- 请求把文档中的一个明确表述替换成另一个表述；
- 审阅修改 Diff，确认后写入并保留修订历史。

默认 `ask` 权限下，文件读取可以直接执行；文件修改不会直接写入，而是先产生 `PatchDraft` 和 Diff，等待用户确认。`full_workspace` 也只放行当前用户、当前项目、ACL 和版本 CAS 均通过的项目文件修改，不等于服务器、本机或 Shell 的完全访问权限。Bash、Shell、SQL、删除文件、任意本机文件写入、支付、邮件、外部发布和任意 HTTP 写入仍不在产品范围内。

## 4. 当前文件业务闭环

业务测试覆盖下面这条真实服务链路：

```text
用户要求处理项目文档
  -> workspace.files.list 定位文件
  -> workspace.files.search 找到相关文件
  -> workspace.files.read 读取内容并返回 revision_id
  -> 用户明确要求修改
  -> workspace.files.apply_edit 生成 PatchDraft + Diff
  -> 用户确认并领取一次性 challenge
  -> AgentRuntimeService 做参数哈希、基线哈希和 CAS 校验
  -> 写入 ProjectFile，创建新的 FileRevision
  -> 使用新 revision_id 重新 read，核验修改结果
```

这里的关键分工是：LLM 可以帮助理解“改什么”，但不拥有写文件权限；Tool Provider 负责当前用户/项目范围内的读取；Agent Runtime 负责审批、幂等和版本冲突；数据库负责最终一致写入。

## 5. 本次新增的业务测试

新增测试：

```text
backend/tests/test_workspace_file_tools.py
WorkspaceFileToolProviderTest.test_user_story_review_edit_approve_and_re_read_file
```

它不只调用单个 Provider，而是通过 `ToolExecutor -> AgentRuntimeService -> ProjectFile/FileRevision` 验证：

1. list/search/read 能定位和读取当前项目文件；
2. read 返回当前 Revision；
3. apply_edit 首次只返回 `confirmation_required + approval_draft`，正文没有被修改；
4. 一次性 challenge 确认后，写入生成新的 Revision；
5. 重新 read 使用新 Revision 成功读到修改内容。

另外，阶段 4.5C 的冲突测试验证文件在读取后发生变化时，旧 `expected_revision_id` 不能继续创建审批草案或继续读取旧版本。

## 6. 面试时的准确说法

不要说“项目已经实现了像 Codex 一样的完整文件 Agent”。更准确的说法是：

> 我们接入了一个受工作区 ACL 约束的文件工具集，支持项目文件列表、搜索、分段读取和受控编辑。读取会绑定当前 `FileRevision`；编辑先生成 Diff 和持久化审批记录，用户确认后再通过一次性 continuation、参数哈希和版本 CAS 写入。这样可以解决模型直接改文件、重复确认、并发覆盖和基于旧内容修改的问题。当前它是用户明确触发的辅助能力，不是默认自动编辑，也不开放本机路径、Shell 或任意文件写入。

如果被追问“是否实际用过”，可以明确说明：当前已完成服务层的业务闭环测试和安全回归，已经验证从定位文件到确认写入再读取核验的完整路径；它还不是每次 Chat 都自动调用的默认流程，后续如果要产品化，需要再补前端审批交互和真实用户场景演示。
