# 工具候选混合召回与验收

日期：2026-10-11。用户授权范围：升级规则/元数据候选筛选，比较改动前后，验证新工具适配与完整 Chat；不是完整自主 Agent 循环改造。

## 一、先理解这次解决什么

过去“深圳气温怎么样”能命中天气关键词，“出门带伞吗”和英文天气问题却可能漏掉天气工具。模型再强，也只能在候选里选择。本次让工具说明与问题经过在线 Embedding 模型形成向量，代码按语义相似度增加召回通道，和原规则排名合并，最多给 Planner 6 个工具。新工具可凭已有名称、说明、适用场景和参数描述参与语义召回，不需要把每个新类别写进正则表。

执行链现在是：代码过滤启用状态、Skill 范围和用户明确禁用项 → 规则排名＋模型向量语义排名 → 代码融合并返回少量候选 → LLM Planner 输出计划/参数/依赖 → Workflow/Executor 校验并执行 → 质量/证据预算 → 最终回答。Embedding 用模型；过滤、距离计算、排名融合、缓存、降级和请求执行由代码负责。候选筛选始终不授予权限，也不证明结果正确。

## 二、实际代码与边界

| 文件 | 关键函数与职责 |
| --- | --- |
| backend/app/services/tools/semantic_retrieval.py | ToolSemanticRetriever.scores：独立短 Session 读取配置、复用 KnowledgeEmbeddingService、向量校验、工具向量缓存和六秒超时 |
| backend/app/services/tools/selector.py | select_async：共用 _eligible 过滤；保留规则；按加权 RRF 融合排名；Trace 记录语义分数/通道/降级原因 |
| backend/app/services/tools/planner.py | plan 改为 await select_async；仍只在候选范围内生成、校验 ToolPlan |
| backend/app/services/external_context_service.py | 根据当前用户注入在线语义召回器，既有总截止时间继续约束全部规划阶段 |
| backend/tests/test_tool_semantic_selector.py | 超时、损坏向量、禁用/Skill/用户排除、取消传播、缓存隔离/失效/容量、新类别与候选容量 |
| scripts/evaluate_tool_candidates.py | 固定同一输入，读取 Git 574f457 的旧 selector，比较旧规则、修复规则降级、新混合候选 |
| scripts/tool_semantic_real_e2e.py | 浏览器→在线 Planner→真实只读 Tool→最终回答→数据库终态与来源；清理临时项目 |

规则修复包括去掉 it/in 等英文短词的子串误命中，负向 when_not_to_use 不再用于正向加分，MCP 身份不再凭空加“相关性”。英文禁用要求、有限文件追问和普通寒暄参与前置处理；普通读取不召回编辑草案/写入。

语义阈值为余弦相似度 0.35；RRF 常数 60，强规则权重 2、弱元数据权重 0.35、语义权重 1。这些是工程参数，不是概率。专业工具不再强行按“每个类别一个”占坑，同类别的搜索→读取、库定位→正文查询可以同时进入候选。普通任务仍保留一个已允许的 Tavily 兜底位，用户禁联网或 Skill 不包含它时不会加回。新搜索服务在未选 Skill 时仍服从既有单搜索兜底策略。

语义调用复用账号现有在线 Embedding；不加载 Ollama。问题上限 2,000 字，工具说明上限 1,800 字；文件追问仅参考最近 8 条里的最近一个用户问题、最多 600 字，助手/工具内容不提供历史线索。元数据向量按用户、模型、维度、地址、凭据轮换哈希和工具正文隔离；最多 512 条、TTL 一小时。缓存不保存用户问题，不写数据库。配置读取结束即释放该短事务，网络等待不持有它。

单次语义阶段最多六秒，包含配置读取；普通工具模式的总时限仍有效。异常只公开固定分类，取消继续向上层传播。缺少在线配置、超时、损坏响应或目录超过 128 个时退回修复后的规则；在线批量最多 32 个工具向量。当前 20 个工具适用，超大市场的向量索引/按需发现尚未实现。新 MCP 的语义召回不代替接入审核或质量合同。

## 三、候选评测口径与真实结果

开发集先于实现固定为 46 Case，40 个正例、47 个必需工具组，另 6 个空候选案例。每组可声明等价工具，比如文件搜索或读取；一组至少命中一个即算该组召回。不同必需组分别计数，例如“库定位＋查正文”必须两个都进入候选。工具组 Recall@6 = 已覆盖组 / 全部必需组；完整覆盖率 = 全部必需组均覆盖的正例 / 正例数。不是候选 Precision、Planner 正确率或任务成功率。

| 开发集方案 | 工具组 Recall@6 | 正例完整覆盖 | 空候选正确 | 禁止项/白名单泄漏 Case |
| --- | --- | --- | --- | --- |
| 旧 Git 574f457 规则 | 33/47，70.21% | 28/40，70.00% | 3/6 | 2 |
| 修复后规则降级 | 32/47，68.09% | 27/40，67.50% | 6/6 | 0 |
| 规则＋真实在线语义 | 46/47，97.87% | 39/40，97.50% | 6/6 | 0 |

最终开发集在线语义 40 次全部成功；其余 6 例被前置空候选规则拦截。候选阶段全 46 例平均 235.9 ms、P95 499.77 ms，包含快路径和冷缓存，不含 Planner/工具/最终回答。逐题、原因、原分数与输入哈希见 backend/evals/results/tool_candidate_v3_2026-10-11_r2.json。

开发集参与过调试，不能当独立盲测。完成策略调试后另外冻结 12 个补充案例，同一维护者标注，未按结果调参：11 个正例、13 个工具组、1 个空候选，旧方案召回 9/13（69.23%）、正例完整覆盖 8/11；新混合召回 13/13、11/11，空候选 1/1，禁止项泄漏从 1 变为 0。全 12 例平均 301.8 ms、P95 750.79 ms。小规模补充集不等于第三方泛化评估，测试型新类别工具只是临时目录定义，未实际注册到用户账号。

开发集未命中保留：d03“Polars lazy API 权威库参考”缺少 Context7 resolve，只有 query 等候选；尚不能保证所有技术查询的两步召回。修复后的纯规则指标低于旧规则，原因之一是取消 MCP 无条件加分，旧实现有些新工具是凭默认加分碰巧入选；语义不可用时仍有此限制。

第一版混合实现 40/47（85.11%），发生一次在线语义失败，并暴露强制类别多样性挤掉同类步骤的回归；修复融合策略后才得到上述 r2。早期 Python 3.10 下误用 asyncio.timeout 已改为 wait_for；不把失败尝试算通过，也不删首版实验记录。在线模型向量可能有数值微差，不要求重跑毫秒值或排名逐位相同。

## 五、源码学习与面试表达

先读 selector.py 的 select_async，而不是一次读完整工具包：_eligible 返回允许的工具；scores 返回“工具 ID→余弦分数”；代码计算排名再给 Planner 工具定义；语义服务失败时返回原规则候选和固定降级原因。最重要的分工是“模型产生向量，代码计算召回；Planner 模型规划；Executor 代码执行”。

可复述：我把候选筛选从关键词规则升级为规则与工具元数据 Embedding 的混合召回，前置范围过滤不变，使用有限缓存和超时降级控制开销；用固定开发集和补充集比较旧代码，记录漏召回与安全排除，再用真实在线模型、工具和浏览器验证最终回答。只报告候选阶段指标，不以此宣称完整 Agent 的通用成功率。完整规划循环持久化仍未完成。

Day 7 的缓存/ZSet 作答和这次短源码例子另存个人学习记录；代码优化不代替 GIL/Session 错题和周测总结。
