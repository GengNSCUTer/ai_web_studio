## 1. 改造原则与优先级

1. **正确完成 > 调用次数**：以用户目标、证据和最终交付物评估，不以返回 JSON、HTTP 200 或工具调用成功判定任务完成。
2. **安全边界先于能力开放**：LLM 只提议计划和参数，服务端拥有权限、截止时间、运行方式及最终认可权。
3. **可恢复 != 可以无脑重放**：只读/幂等且证据充分才重试；未知副作用写入禁止自动重放。
4. **业务功能形成闭环**：先把“资料查证 → 研究报告 → 可选文件修改建议”做通，不另造独立多 Agent 大框架。
5. **测试要分层**：确定性单测、真实数据库/进程崩溃、在线模型、真实浏览器、安全攻击、未见题集各自报告；不把不同来源结果拼成单个成功率。

| 优先级 | 专题 | 为什么现在做 | 依赖 |
|---|---|---|---|
| P0-A | TaskSpec / Completion Verifier | 200 题中部分成功主要来自缺步骤、缺正文、缺引用与计算 | 现有 `completion_contract.py` / `workflow.py` |
| P0-B | Docker-free 沙箱可行性与安全落地 | 共享服务器无 Docker，未来代码执行和第三方脚本不能直接跑在 API/Worker 主进程 | 首轮探测完成；下一步验证原生离线单进程的资源/系统调用/清理边界，不复用Docker已缺失的配额承诺 |
| P0-C | Agent 安全对抗回归 | MCP/网页/文档为不可信输入，需要验证注入、越权与外传边界 | 现有 ACL、网络过滤、审批 |
| P1-A | 资料研究→报告→审批交付 | 把已有工具和 Artifact 变成用户可感知的完整功能 | Completion Verifier + 持久化产物 |

## 2. 专题 A：任务完成判定与证据补救（P0）

### 问题

当前已有 `tools/completion_contract.py` 用于文件正文读取、Context7 正文、Skill 强制步骤等有限任务，但“执行过所需工具”并不一定代表用户的目标完成。例如找到文件 ID 却未阅读正文、得出结论却未引用源文件、生成报告缺少要求的部分。

### 建议设计

定义**数据结构，而不是新增高权限 Supervisor**：

```python
class TaskSpec(BaseModel):
    goal: str
    required_outputs: list[str]            # 需要交付什么
    required_evidence: list[str]           # 每项结果应从哪里取证
    acceptance_criteria: list[str]        # 可验证完成条件
    clarification_needed: list[str] = []

class CompletionVerdict(BaseModel):
    status: Literal["complete", "partial", "clarify", "blocked"]
    satisfied: list[str]
    missing: list[str]
    evidence_refs: list[str]
    permitted_repair_actions: list[str]
```

**安全不变量**：用户需求与可信工具定义决定授权范围；LLM 产出的 TaskSpec **不生成新权限**。`permitted_repair_actions` 仅是候选，再经过现有 Catalog / ACL / Schema / 原任务动作范围 / 执行预算校验。

**执行流程**：解析目标 → 原有 Planner/DAG → 收集已通过质量合同的证据及 Artifact → 确定性完成检查 → 必要时有限语义复核 → 若预算允许定向补证，否则 `partial/clarify/blocked`。

**第一版不做**：开放式自我循环、任意次数重试、增加独立 Agent 角色、靠模型声称“我完成了”直接收口。

**代码落点（建议）**：复用 `backend/app/services/tools/completion_contract.py`、`tools/workflow.py`、`tools/quality.py`、`tools/observation_projection.py`，新增局部 `task_spec.py`、`completion_verifier.py`；将判定写入现有 Run Trace，而非再建一套状态数据库。

**验收**：先冻结历史 23 个部分成功和 1 个失败的证据，按缺证据/参数/工具/正文/引用/预算分类；选择 5–8 个代表案例改造，并另设未参与开发的对照题。报告完整成功率、误判完成率、补救次数、Token、P50/P95、风险操作数。安全边界必须 0 次回退。

## 3. 专题 B：无 Docker 沙箱（P0，新增重点）

### 3.1 用户环境与定位

**确定的环境约束**：共享 Linux 服务器，无法使用 Docker。你提到之前考虑过一个“不需要 Docker 的框架”，但名称目前不确定，**不能凭描述断言就是某一个工具**。可能的选择包括：

| 选择 | 优点 | 约束/适用条件 | 判断 |
|---|---|---|---|
| **Bubblewrap (`bwrap`)** | 无 Docker，创建文件系统/用户/PID/网络命名空间，最小权限运行外部进程 | 依赖宿主机允许必要的 unprivileged user namespace；不自动提供 CPU/内存完整配额、审核、进程生命周期与 Artifact 管理 | **优先评估的原生 Linux 路线** |
| **NsJail** | namespace、rlimit、seccomp-bpf、cgroup 等能力较完整，适合专门设计代码执行 Runner | 编译/部署和策略配置更复杂，部分功能受内核、cgroup 和管理员限制；“无 Docker”不等于“无权限要求” | bwrap 不合适且权限满足时再评估 |
| **Wasmtime/WASI** | 无 Docker 的能力型 WebAssembly 沙箱；对受限 WASM 程序的文件/主机能力有清晰边界 | 不能透明运行任意 CPython + 原生包/Pandas/Shell；支持范围与任务类型要缩小 | **无法安全使用 namespace 时的受限计算备选** |
| 普通 `subprocess` + `venv` + `timeout`/`rlimit` | 简单 | **不是可靠的恶意代码安全边界**，无法阻止读取主机文件或调用危险系统接口 | 不允许作为任意不可信代码沙箱上线 |
| `proot` 等用户态路径仿真 | 可能无需 namespace | 一般不能视为防敌对代码突破的安全隔离边界 | 不作为安全承诺 |

参考官方文档：[bubblewrap](https://github.com/containers/bubblewrap)、[NsJail](https://github.com/google/nsjail)、[Wasmtime Security](https://docs.wasmtime.dev/security.html)、[Linux Landlock](https://docs.kernel.org/userspace-api/landlock.html)。

> **关键结论**：共享机器上的 rootless namespace 与宿主机共享内核。它可以显著降低权限，但不能宣传为不可突破的强隔离；正式开放给不可信用户前要有服务器管理员同意、威胁模型、内核安全更新和逃逸测试。如果必要命名空间不可用，直接禁用本机任意代码执行，或改用受限 WASM / 独立隔离执行服务。**禁止以特权 setuid、开放 Docker socket、放宽宿主机安全配置等方式绕过学校/共享服务器管理策略。**

### 3.2 第 0 阶段：只做环境可行性检测，不执行未知代码

在**获准的共享服务器账户**下运行并记录输出：

```bash
uname -r
command -v bwrap || true
command -v nsjail || true
command -v unshare || true
cat /proc/sys/kernel/unprivileged_userns_clone 2>/dev/null || true
cat /proc/sys/user/max_user_namespaces 2>/dev/null || true
cat /sys/fs/cgroup/cgroup.controllers 2>/dev/null || true
unshare -Ur true   # 只测试 user namespace 创建，失败并不自动允许更改宿主机配置
```

随后在管理员许可下，才执行 bwrap/nsjail 自带最小隔离烟测。明确确认：用户/PID/mount/net namespace 能否创建，`no-new-privileges`、seccomp、Landlock、cgroup v2、进程树清理及共享文件系统边界是否可用。**仅 `unshare -Ur true` 通过不代表沙箱安全达标。**

### 3.3 沙箱的业务边界（第一期只读计算）

先允许经过确认的低风险任务，如“针对用户明确提供的 CSV/JSON 做局部计算、解析、生成图表数据或执行有限 Python 数据处理”。

**暂不开放**：任意 Shell、`pip install`、读取服务器工作目录、直接操作 PostgreSQL、任意联网、访问 MCP 凭据、对项目正式文件的原地写入、接收外部公网用户提交的任意 native code。

建议流程：

```text
用户授权的代码/计算请求
  → SandboxPolicy（能力、输入范围、最大资源/时长）
  → SandboxJob（与 ChatRun/AgentStep 关联）
  → SandboxWorker（独立进程；主Worker不直接exec）
  → 选择已验证的隔离后端（bwrap / nsjail / 受限WASM）
  → 输出与临时文件完整性校验
  → 附 provenance 的 ResultArtifact
  → CompletionVerifier / Agent 后续处理
```

**最小接口草案**：

```python
class SandboxRequest(BaseModel):
    run_id: str
    step_id: str
    code_ref: str                   # 服务端保存的待审代码引用，不能是任意路径
    input_artifact_ids: list[str]  # 仅授权且校验过的输入工件
    profile: Literal["offline_python_readonly", "wasi_compute"]
    max_wall_seconds: int
    max_output_bytes: int

class SandboxResult(BaseModel):
    status: Literal["succeeded", "failed", "timed_out", "blocked"]
    exit_code: int | None
    stdout_artifact_id: str | None
    output_artifact_ids: list[str]
    audit_ref: str
```

### 3.4 必须验证的防护（不要仅凭框架名宣称“安全”）

- **文件**：显式白名单只读输入、独立临时目录、不可访问其他用户 HOME/SSH/API Key、不得将宿主根目录整体绑定进沙箱；验证符号链接、相对路径、FD/挂载边界。
- **网络**：第一版无网络；验证 DNS、环回、云元数据地址与本机数据库端口均不可达。不允许模型传入任意出站代理设置。
- **权限**：无宿主 root、无提权路径、无敏感环境变量/继承文件描述符；隔离子进程不能访问 API/Worker 控制通道。
- **资源**：wall-clock、CPU、RSS/地址空间、进程数、文件数、文件尺寸、stdout/stderr、并发配额；必须能终止整个进程树，防 fork bomb。
- **执行与产物**：结果先进入临时区，扫描、格式校验、哈希和用户/项目归属验证后才发布 Artifact；失败或取消必须清理。
- **恢复**：外部执行成功但 Artifact 未提交时不得假装完成；默认只有只读且可证明可重复的沙箱步骤能有限重试，保留尝试号及归档。
- **开关**：环境能力缺失或检查失败直接 fail closed，不回退到不隔离的 `subprocess`。

**验收矩阵**：文件越界、敏感环境变量、内部网络连接、非法重定向/符号链接、超长输出、fork bomb、无限循环、进程逃逸、故障重启、并发取消、临时目录清理、跨用户 Artifact。每项记录实际退出码、隔离层/内核能力与未覆盖风险。

### 3.5 三种可行结论与后续动作

- **A：namespace、资源限制、防护策略都可用**：先做 bwrap 最小 Runner，与当前 Tool/Artifact 接口集成，短期仅内部受控数据处理，完成攻击测试后再考虑对用户开放。
- **B：bwrap 不满足，而 nsjail 所需环境可用**：在不提高宿主权限的前提下评估 nsjail；不能为功能强行修改共享服务器配置。
- **C：必要内核隔离不可用**：不执行不可信本机 Python/Shell。改为 Wasmtime/WASI 的受限计算场景，或使用学校/团队明确授权的远程隔离服务。保留代码预览及用户确认，但“仅审核提示”不是执行隔离。

**交付物**：`sandbox-feasibility-report.md`、`SandboxPolicy` 契约、至少一个可独立关停的 Runner、攻击回归矩阵、资源/故障指标与回滚开关。

## 4. 专题 C：Agent 安全攻击回归（P0）

使用既有 `tools/action_guard.py`、`mcp_security.py`、MCP Schema 审核、FileRevision CAS 与 ToolExecutor，建立一批**攻击不变量测试**，优先：

1. 不可信 RAG/网页文本的提示注入，诱导读取/上传项目私有文件；验证没有新权限和危险外传。
2. MCP Server 的 Schema、注解和只读声明变化；未经复审不得继续执行。
3. URL → DNS → 实际连接目的地址的 SSRF/重定向绕过；不能只验证首次 URL 文本。
4. 跨账号、跨项目的 ChatRun/Artifact/Tool/Memory 访问；消除 IDOR。
5. 文件 Diff 审批后目标文件发生版本漂移；旧审批不得修改新版本。
6. 只读请求成功但回执丢失、未知副作用写入、Worker 旧租约晚提交、取消竞态。

**验收**：记录攻击目标、原任务、恶意载荷类别、允许的合法结果、最终外部副作用、是否阻断、误拦截正常业务成本。至少一个真实 PG/HTTP/MCP mock 组合场景；用安全框架及批准的测试目标验证，**不在共享服务器做未经授权的突破实验**。

## 5. 专题 D：三种用户可见的交付流程（P1）

| 场景 | 标准输入 | 交付物 | 必须满足 |
|---|---|---|---|
| 知识查证 | “按项目设计解释 ChatRun 恢复机制” | 有来源的回答 | 真正读取原文，注明依据与限制 |
| 项目研究报告 | “比较 A/B 方案并整理技术评估” | Markdown/Word + 证据清单 | 引用覆盖结论、预算与成本可见、失败可恢复 |
| 文件修改建议 | “根据审查建议更新文档” | Diff/PatchDraft + 待审批记录 | 版本一致、用户授权、未审批前不修改 |

新增 User-visible `TaskChecklist` 显示“已取证/待补证/报告已生成/等待审批/完成”，底层仍由 Run/Step/Artifact 的权威状态映射，不额外存一份可漂移的执行状态。

验收要做真实浏览器流程：关闭页面后 Worker 继续；重开显示真实进度；用户拒绝编辑不影响已生成报告；重复点击保存不会产生多份不一致工件。

## 6. 专题 E：RAG 断言可靠性、记忆价值及可观测性（P1/P2）

### RAG Evidence-to-Claim

- 保留现有混合检索与结构化引用；在最终回答中识别带数值、时间、版本、范围及绝对化措辞的**重要事实断言**。
- 代码首先核对显式数字/来源范围，只有无法确定的高风险断言触发一次受控语义复核；资料不足正确解释未知，而不是编造。
- 单列评测：检索命中、引用正确、事实支持、错误拒答、延迟和模型调用成本。不要只用一个总分代表 RAG。

### 长期记忆

- 冻结现有 48+24 构造集，只作规则回归；再收集经本人确认的自然语料标签和跨会话场景。
- 评价：真正有用的记忆被召回比例、过期/冲突记忆干扰率、不应记忆时的误触发率、平均 Job/LLM 成本；对照关闭记忆组。
- 暂不实现全量每日“自我反思/自动总结”，也不将含混高影响事实自动生效。

### Run/Step 可观测性

- 新增每次 Run 的请求数、Token、工具耗时、排队与 Worker 租约等待、重试/恢复次数、Artifact 体积、用户取消、失败分类。
- Trace 与安全审计分级脱敏；避免默认记录完整用户文档、密钥或远程 MCP 原始载荷。
- 如有实际外部服务部署条件，再按观察到的故障率设计告警；不以“进程存活”代替业务成功率。

## 7. 分阶段实施与停止条件

| 阶段 | 提交内容 | 进入下一阶段的条件 |
|---|---|---|
| K0：冻结基线 | 200 题分类；权限/网络/工件不变量；沙箱环境探测；完整当前 CI | 能复现旧失败，沙箱可行性被证实或明确放弃 |
| K1：完成判定 | TaskSpec + Verifier + 限次补证，先修 5–8 个代表问题 | 新题集无误判完成，风险工具不扩权，延迟/成本受控 |
| K2：沙箱最小闭环 | 合规隔离后端 + SandboxPolicy + SandboxJob + Artifact | 攻击矩阵通过；无不安全本机执行兜底 |
| K3：端到端业务 | 研究报告和文件审批一条链路；用户界面显示状态 | 真实浏览器、取消、重启、审批拒绝通过 |
| K4：证据与质量 | RAG 断言核验、长期记忆真实标签、Run 指标 | 未见场景指标改善且已统计额外成本 |
| K5：MCP/Skill | 连接诊断、Schema 变更复审、少量真正有用的数据源 | 权限回归不退步、工具完成率提升 |

每阶段单独提交、单独报告、通过后再推进。**如果共享服务器无法支持可核查的隔离，K2 不允许通过降低安全要求来“完成”。**
