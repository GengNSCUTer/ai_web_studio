# 文件确认写入：真实浏览器验收

2026-11-04，承接[201编辑预览修复](201_编辑提案发现规划与完成修复_2026-11-04.md)。目的不是再证明能输出Diff，而是验证用户在浏览器确认后，当前项目文件是否真的更新。

## 1. 使用边界

本次新建临时项目和脱敏Markdown，固定账号、在线DeepSeek-V3.2、默认`ask`权限；不安装或启用额外Skill，不修改账号设置、现有项目或任意宿主文件。同步模式仍是原`edit_proposal`预算，不开放自动写入。

两次用户动作要分开：

```text
只要预览 → read → propose_edit → 真实Diff，文件不变
正式申请修改 → read → apply_edit首次 → PatchDraft + pending审批卡片，文件仍不变
用户点击确认并应用Diff → challenge令牌 → apply → 文件更新 + 新FileRevision
```

数据库`AgentApproval.status=consumed`表示一次性审批已消费；`PatchDraft.status=applied`与apply API的`status=applied`表示修改已应用；`AgentRun.status=succeeded`表示文件任务完成。不能要求这三个对象使用相同状态名。

## 2. 实测发现并修复的缺口

原来“只读预览→正式申请修改”的自然语言追问不稳定：候选中已有apply_edit，但Planner只执行list就结束；最终模型声称“已创建审批”，数据库并无记录。保留失败报告`backend/evals/results/file_edit_approval_browser_20261104_before.json`。这不是审批API写入失败，也不应把这轮说成审批成功。

补齐最小规划与完成检查：

- `tools/file_edit_intent.py`区分明确申请审批与只读预览。不会自动把上一轮预览当成写入授权。
- `tools/selector.py`在用户确实申请审批时提高正式修改工具相关性；当前启用、权限和Skill白名单仍然限制候选。
- `tools/planner.py`正式申请必须定位→read→apply_edit，不能用propose_edit或文字申请代替；模板正确区分两类工具。旧轮已完成read仍使用真实ID、原文和版本，不写跨轮DAG边。
- `tools/completion_contract.py`、`tools/edit_preview_completion.py`及`external_context_service.py`不再以list/read为正式审批任务完成，缺少真实apply_edit步骤时在原预算内续轮。
- `evidence_sufficiency.py`只有真实审批ID/Run/文件来源或实际applied来源才允许对应结论；尚缺审批时明确禁止声称已创建或已写入。它是代码生成的证据约束，不是对最终自然语言的语义证明。

写入服务、一次性令牌、ACL、唯一替换、CAS和幂等继续复用`agent_runtime_service.py`与原审批接口，本次没有绕开它们。

## 3. 真实验收方法

新增脚本`scripts/file_edit_approval_browser_e2e.py`，使用真实UI发送预览问题、继续正式申请修改，再点击审批卡片。确认前核对文件仍是旧值；确认后精确比较整份正文，保证仅目标标题变化，并确认只新增一个FileRevision。随后重复发送同一次apply请求，检查不多写、不多建版本；另建只读会话，通过真实工具和模型读取新标题及原保留周期，最后刷新验证显示。

审批令牌仅在浏览器测试进程内存中捕获用于重复确认，不写日志、JSON报告或Git。验收结束按PatchDraft/Revision/Run依赖清理临时数据，再清理会话和项目。过程中修正了测试脚本按旧字段查询审批、把consumed误当失败以及清理顺序的问题，这些不能算作产品写入缺陷。
