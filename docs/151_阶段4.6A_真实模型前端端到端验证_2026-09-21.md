## 2. 初次真实验证与修复

首次真实浏览器执行暴露出一个 Tool 编排缺口：在线 Planner 有时只输出
`workspace.files.search`，随后就由最终回答模型给出文件标题。搜索摘要可能
恰好包含部分正文，但它不等价于“已经核对原文”，因此不能把正确性完全交给
Prompt 约束。

本轮已增加 Skill 级 `completion_contract`：对于 `workspace.document-review`，当
问题涉及原文、标题、内容、读取、核对、审阅或事实时，搜索/列表获得受限
`file_id` 后，代码会要求下一轮补齐 `workspace.files.read`。补充调用：

- 只使用上轮由执行器生成的 opaque `file_id` 和 Revision 标识；
- 仍受 Skill allowlist、Catalog、Input Schema、权限和质量门约束；
- 不猜测本机路径、不读取其它项目；
- 不将跨轮来源关系错误声明为本轮 `depends_on`。`depends_on` 只表达同一份
  ToolPlan 内的 DAG 边，跨轮证据通过受控 observation 传递，并在 Trace 中保留
  `upstream_call_id` 审计引用。

## 4. 当前结论

真实在线模型、浏览器前端和后端主链已经完成一次严格的 `search -> read -> final
answer` 端到端验证。最终回答引用了临时文件名、用途和第一行标题；assistant
持久化状态为 `done`；Playwright 未捕获 console/page error；测试文件未发生写入，
临时项目、会话和文件均已清理。

这不意味着任何新接入 Tool 都会自动得到同样的多步保证。`completion_contract`
是每个高价值 Skill 可审核声明的完成条件：只有业务确实需要“工具结果齐全”而
不只是“候选工具可用”时才添加，避免把普通查询无意义地拉长为多轮执行。
