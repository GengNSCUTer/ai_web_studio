## 三、确认的问题与证据

### 1. 整轮超时会丢失本轮已经完成的有效结果（高优先级）

位置：`tools/workflow.py:898` 和 `external_context_service.py:267`。

Workflow 用 `asyncio.gather` 等本批次全部调用返回后才合并结果；外层 `wait_for` 在总时长耗尽时取消整个 Workflow。某个工具即使已经完成，外层还没有拿到本轮结果，就会丢失这份证据。

受控复现使用真实外部门面和 Workflow、模拟 Planner/Executor：两工具并发，快工具约 0.01 秒完成，慢工具等待 1.4 秒，总预算 1 秒。记录显示快工具已完成，但最终返回的来源数为 0，结束原因是 `tool_wall_clock_budget_exhausted`。

影响：部分成功被变成“没有证据”，模型可能重复查找、少回答或给出不准确的失败说明。这里丢失的是本轮尚未交给外层的成功结果；此前轮次已汇总的结果不会因此全部清空。

建议：逐项收集并保留完成结果；到截止时间时取消尚未完成的调用，分别记录成功、失败和超时，把已通过质量门的证据交给最终回答。取消和超时不能都被当成普通工具失败，更不能重发已完成的有副作用操作。

验收：一个快、一个慢；一个成功、一个失败；依赖步骤未完成；用户主动取消。检查已完成证据、调用账本、轨迹和最终回答的一致性，随后再用真实在线模型走完整 Chat。

### 2. 文件工具的异步入口仍直接执行同步数据库操作（高优先级）

位置：`tools/providers/workspace_files.py:45`、`:130`。`async def run` 直接进入同步的 `_list_files`、`_search_files`、`_read_file` 等方法，使用同步 SQLAlchemy Session 查询并遍历文本。

受控复现用模拟数据库查询睡眠 0.08 秒，同时安排一个 0.01 秒心跳协程。心跳约 0.082 秒才得到运行机会，证明该调用路径阻塞事件循环。这是人工构造的阻塞诊断，不是生产 PostgreSQL 的查询延迟。

影响：慢查询或较大文本搜索会拖延同一事件循环上的其他请求。之前 Chat 数据库优化不能推导出所有 Tool Provider 都已无同步阻塞。

建议：采用异步数据库短事务，或在独立线程中使用独立 Session 获取必要快照，再释放连接。不能将同一个请求 Session 直接放进多个并发线程；文件版本基线生成也可能写入/flush，需要保留事务边界。

验收：多个会话同时读/搜文件、数据库慢查询、版本快照生成、取消后的连接释放；保持用户/项目隔离和既有审批测试。

### 3. 候选初筛可能漏掉明确的本地文件意图（中优先级）

位置：`tools/selector.py` 的 `_score_tool`，以及 `tools/planner.py` 先初筛后调用 LLM 的路径。

默认工具目录、不显式激活文件 Skill 的诊断结果：

| 查询 | 返回候选 |
| --- | --- |
| 帮我看看 note.md 里讲了啥 | 仅 `web.tavily.search` |
| 读取工作区里的 note.md 文件 | 包含文件 list/read/search 等工具和 Web 搜索 |
| 这份预算有没有漏项 | 仅 `web.tavily.search`；没有结合前文判断“这份预算”的候选初筛机制 |

前两行显示同一文件意图因措辞不同而有明显召回差异。第三行本身需要历史才能消歧；当前 Selector 不接收历史，Planner 虽能看历史，也不能选一个已经被排除在候选外的工具。显式 Skill allowlist 是另一条约束路径，不能将此诊断泛化为所有文件 Skill 都失效。

建议：先覆盖文件名/扩展名、口语表达、用户指定的当前文件等明确线索；把相关历史实体作为受控初筛输入。目录较小时保留少量基础只读工具；目录扩大后再考虑词法/语义混合召回和按需发现。文件任务不能因漏召回静默变成网页检索。

验收：语义等价措辞、当前文件指代、跨项目指代、只读 Skill allowlist，以及不需要工具的普通问题。先测漏召回，再讨论是否引入额外 LLM。

### 4. 候选满额时，预留的联网兜底位置可能被截掉（中优先级）

位置：`tools/selector.py:80–135`。

第一段循环已经填满专项候选额度时，第二段补充循环仍先追加一个候选再检查上限；随后追加 Web，最后整体切片，可能把 Web 丢掉。额度为 0 时也会先追加一个专项工具。

受控复现：用六个不同类别、均匹配当前问题的工具加 Web 组成扩展目录。`max_candidates=6` 时返回六个专项工具，没有 Web；`max_candidates=1` 时同样没有 Web。现有“小目录保留 Web”测试未覆盖这个容量边界。

建议：追加前检查专项额度，明确额度为 0 时的行为，并保证候选总量和预留策略同时满足。这里修复的是现有容量算法，不代表所有用户问题都应执行联网搜索。

### 5. Planner 没有受剩余总时长约束，时延指标也未覆盖规划时间（中优先级）

位置：`external_context_service.py:198`、`:267`、`:512`；`tools/planner.py:30`、`:123`。

Workflow 使用剩余总时长超时，但 Planner 仍使用独立的 15 秒上限。前轮接近耗尽预算时，下一轮规划仍能继续等待，不能保证整个工具阶段在配置的总时长内结束。`external_context_latency_ms` 累加 Workflow 时延，没有计入规划等待，也容易误导排障。

受控复现：合法策略总预算 1 秒，模拟 Planner 等 1.15 秒返回“不需工具”，实际耗时约 1.155 秒，结束原因仍是 `no_tool_needed`。这证明预算覆盖缺口，不是实际在线模型的延迟测量。

建议：统一使用一个截止时间，规划、工具执行和后续处理都受剩余预算约束；如实记录总时延，并区分规划与执行分项。超时取消要与第 1 项的部分结果保留一起验证。

### 6. 文件搜索只检查最近最多 120 个文件，却没有说明未穷尽（中优先级）

位置：`tools/providers/workspace_files.py:130–195`。

代码取当前项目最新最多 480 个文件，过滤敏感文件名后只扫描前 120 个，再返回最多 5 个搜索结果。响应没有扫描数量、截断标志或分页入口；空结果文字是“当前项目中未找到与本次查询匹配的文件”。

内存 SQLite 复现：同项目共 126 个文件，较早的文件确实包含 `Durable`，但 125 个较新文件不含关键词。搜索返回 `matched_files=0`，没有说明搜索范围。这不是“确实没有目标”，而是目标没有进入扫描窗口。

建议：提供明确的扫描范围、是否截断以及分页/继续搜索方式；用户明确指定文件名或文件 ID 时，优先定向查找。空结果只能说明已检查范围未命中，不能直接推导整个项目不存在文件。数据量扩大后才考虑索引化，不能靠取消所有上限来解决。

## 四、与主流公开方案对比

以下比较基于官方公开资料，不推断闭源产品内部实现，也不把厂商自测提升当成我们的指标。

| 公开方案 | 可借鉴机制 | 对当前项目的实际意义 |
| --- | --- | --- |
| Anthropic Tool Search | 少量常用工具保留，其余按需发现；可用 regex、BM25 或自定义检索；复杂参数辅以调用示例 | 初筛由代码实现并不落后，问题在召回覆盖和补找能力；先补明确文件意图与容量边界，再按目录规模升级 |
| Codex agent harness | 宿主程序管理状态、流式事件、工具、权限审批和跨轮执行，模型在边界内决策 | 借鉴全过程状态及取消/失败收口；当前应先保留超时前的成功证据，不能把放大轮数当成可靠性改造 |
| 腾讯 WorkBuddy Enterprise/CodeBuddy 的 MCP 文档 | 工具/服务器粒度的 allow、ask、deny，明确拒绝优先 | 保留服务端校验和显式审批，动态工具只能获得用户明确允许的能力；当前不是缺“全权限开关” |

## 五、建议实施顺序

1. 先一起修复超时部分结果保留和全过程截止时间，覆盖并发、依赖、主动取消与最终回答。
2. 再修文件工具的同步阻塞和搜索范围披露，保证短事务、独立 Session 与项目隔离；补定向查找/分页。
3. 然后修候选容量边界与文件口语召回，保留“不必调用工具”的路径；不先引入所有工具定义或额外模型调用。
4. 上述边界稳定后，再评估是否需要持久化完整规划循环和按需发现工具。此项是产品能力演进，不是当前阻塞问题。

每步完成后，除针对缺口补测试，还要用在线模型跑真实 Chat，检查“工具证据是否保留、回答是否反映范围/部分失败、前端轨迹是否与后端一致”。本次只列计划，未实施。

## 六、本次验证范围

既有九个工具相关测试模块共 160 项通过，覆盖 Planner、Workflow、Executor、Quality、Run Policy、MCP 安全、工作区文件、接入和集成测试。另运行六类受控诊断：口语文件意图、候选容量、Planner 总预算、并发整轮超时、同步文件查询阻塞、旧文件超出扫描窗口。

这些诊断使用实际服务实现搭配模拟 Planner/Executor/数据库，文件窗口复现使用临时内存 SQLite；未向真实账号添加文件或修改权限。通过既有测试和找到边界缺口并不矛盾：既有测试没有覆盖这些具体组合。

本次没有调用在线模型、真实 Tavily/高德或浏览器进行端到端验证，因此不能据此声称工具任务成功率、实际响应时间或所有安全边界均已验收。
