# 阶段 4.5A：跨来源去重与基础 Evidence 诊断（2026-09-21）

## 目的

同一网页或相同正文可能在一次受限 Agent Workflow 的多轮调用中重复出现。若每轮都把它重新投影给 Planner、重新拼进最终上下文，会浪费 Token 预算，也会让模型把重复信息误当成多份独立证据。

本步只解决“同一个来源不要重复占预算”，不改变哪个 Tool 被选择、Tool 的质量判定、权限或最终回答的安全规则。

## 实现链路

```text
Tool Adapter / MCP Mapper
  -> ExternalSource
  -> ExternalContextService._merge_sources
  -> 新来源才进入下一轮 Planner observation
  -> 去重后的来源进入最终 Context Assembler
```

实现文件：

- `backend/app/services/external_context_service.py`
  - 在每轮 Workflow 完成后累计原始来源数；
  - 合并来源并得到“本轮新增来源 / 重复来源数”；
  - 只把新增来源投影给后续 Planner；
  - 在最终 diagnostics 中写入无敏感信息的计数。
- `backend/tests/test_tool_router.py`
  - 覆盖 URL 追踪参数与 fragment 去重；
  - 覆盖跨 Provider 的相同 canonical 正文去重；
  - 覆盖无 URL 的不同短结果不误合并；
  - 覆盖多轮重规划时同一来源不会重复进入 Planner observation。

## 去重规则

1. 有 URL：规范化 scheme/host，移除 fragment，移除 `utm_*`、`gclid`、`fbclid`、`msclkid` 等追踪参数；实际资源定位 query 参数保留。
2. 无 URL：优先使用 `metadata.raw.content`，否则使用 `display_text`。规范化空白后的正文长度达到 32 字符时，用 SHA-256 摘要作为身份。
3. 无 URL 的短文本：使用 Provider、source type、标题和短文本共同区分，避免“北京”和“上海”这类不同结果被误合并。

摘要只存在进程内去重键中，不写入 diagnostics 或 Trace；诊断不会泄露来源正文、URL、凭据或 Provider 原始 JSON。

## 当前边界

- 同 URL 不一定意味着内容在每次抓取时完全相同；本步优先解决上下文重复，不将 URL 身份伪装成内容版本证明。
- 相同长正文在不同 Provider 中会被合并；如果后续需要保留不同 Provider 的独立可信度或发布时间，应在阶段 4.5C 引入显式 provenance / freshness 字段，而不是放宽重复正文。
- 新 Tool 仍必须通过既有 Mapper、ResultQualityContract 和 Evidence Projection Profile 审核；该去重层不能替代任何质量或安全边界。

- 完整后端回归：使用项目 PostgreSQL 18.3 + pgvector 0.8.5（`127.0.0.1:35433`）显式运行，457 项通过，0 项跳过。
- `compileall`、默认 Tool manifest JSON 解析、`git diff --check` 通过。

## 数据库服务统一

项目现在只管理 PostgreSQL 18 + pgvector 的 `127.0.0.1:35433`：`start_postgres.sh` 和 `stop_postgres.sh` 都指向该实例。旧 PostgreSQL 12 的数据目录保留为停止状态的离线回滚备份，但旧启动脚本已从项目移除，避免运行期间误启动两个数据库或切回旧实例。已核对新库是旧库的完整超集，因此不做重复导入。

## 下一步

阶段 4.5B 只补充 Evidence Projection Profile 的预算可观测性：允许/实际来源数、允许/实际字符数、`source_limit_reached`、`total_budget_exhausted`、`suppressed_suspicious_content` 等原因计数。它不应在 Trace 中保存正文或 URL，也不应为此扩大 Tool 正文可见范围。
