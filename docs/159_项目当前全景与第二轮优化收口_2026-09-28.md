# AI Web Studio：当前项目全景与第二轮优化收口

更新时间：2026-10-09。本文是当前实现与面试表述的入口。项目定位是个人与小团队的本地知识工作台，不是通用代码 Agent，也未商业上线或交付涉密客户。它把知识库、流式对话、记忆、受控工具和可恢复的只读长任务放进一个可观察的工作流。详细阶段记录见[文档导航](README.md)。

## 一条主链

前端为 Next.js/React，后端为 FastAPI/SQLAlchemy；PostgreSQL/pgvector 保存业务状态和向量，Redis Stream 投递后台任务。用户问题进入 Chat 后，先创建消息锚点，再组装最近对话、滚动摘要、已启用的长期记忆、附件及 RAG 证据。代码选择候选工具，LLM Planner 只在候选内提出 ToolPlan 和参数；Executor 重新检查 Schema、ACL、凭据、风险、项目范围和 SSRF，执行后检查结果质量。工具结果和外部网页只作为有来源的证据供模型继续规划或回答，不赋予其指令权限。最终流式回答按 generation ID 收口为完成、取消或失败状态。

知识库写入使用 Outbox、Redis Stream 和 Worker；文档解析、Parent-Child Chunk、Embedding、BM25、generation 和激活 CAS 在后台完成。查询侧为向量检索加 BM25，经 RRF 融合和可选 Rerank 后再进入上下文预算。20 Case 固定评测及答案指标有独立报告；它们是特定论文库与模型条件下的实验结果，不代表线上全场景指标。

## 第二轮优化解决了什么

**工具结果质量。** Tool 返回 JSON 合法不等于内容有用。阶段 0-2.3 将结果区分为有效、合法空结果、质量不确定和无效；新工具可先声明字段映射与语义规则、提供测试样例，再经过审核接入。固定规则覆盖通用情况，特殊业务语义仍需明确配置或适配，不能声称“任意新工具零配置即可接入”。核心实现位于 `backend/app/services/tools/`。

**依赖、并发与预算。** Tool DAG 中独立分支可以并发；A 质量不合格时，依赖 A 的 B 不执行，成功的其他分支仍可供最终回答或重规划。结果决策包含部分收口、重规划、澄清和停止，不因单一分支失败就把整个会话直接判失败。同步模式由代码侧固定预算控制：快速对话最多 5 轮/10 次调用，研究模式 8 轮/16 次，工作区审阅 6 轮/12 次，编辑提案 4 轮/6 次；另有限制单计划调用、并发与墙钟时间。它仍是有界同步 Agent，不是无限循环。核心实现为 `backend/app/services/tools/run_policy.py`、`workflow.py` 和 Chat 上下文服务。

**外部证据与文件。** Tavily、动态 MCP 等外部返回在进入下一轮 Planner 前做来源标注、字段投影、受限摘录和预算诊断；“不可信”表示不能改变系统指令和权限，不表示不能用于回答事实。投影规则可由声明式配置扩展。工作区文件读取和编辑提案可以在真实 Chat 中使用；写入必须经过 Diff/PatchDraft、用户审批、一次性 challenge 与 FileRevision CAS，不开放任意本机文件写入。核心实现为 `backend/app/services/tools/observation_projection.py` 及文件审批服务。

**显式 Durable Handoff。** 用户可以把当前低风险只读 Tool Plan 先预览、再确认转为独立 Run；确认只提交签名 token，不能借前端改参数。Planner 可建议 `durable_candidate`，但不会据此自动转后台或扩权，而且当前 Chat 仍先同步执行；后台任务会独立重做那组只读查询。Run/Step/Checkpoint/Artifact 与 Outbox 保存在数据库，Worker 使用心跳、Lease/Fencing、续租、有限重试和 DLQ。Run 终态只回写一条原会话消息；任务页可查看步骤、错误和产物，DLQ 重放须再次确认。执行快照绑定 Tool/Skill 版本；漂移时拒绝继续或回放，审计下载为脱敏 JSONL。主要文件是 `backend/app/services/durable_handoff_service.py`、`durable_tool_runtime.py`、`durable_worker_registry.py`、`durable_audit_service.py` 和前端 `task-dashboard.tsx`。

## 现有边界

2026-10-09 记忆三步已完成：[第一步正确性与版本治理](163_长期记忆第一步_正确性与版本治理_2026-10-08.md)实现事实值变更、原子替换/历史、范围与预算；[第二步增量提取与受控自动生效](164_长期记忆第二步_增量提取与受控自动生效_2026-10-08.md)新增游标、逐条用户原文证据、提取前脱敏及默认关闭的独立自动开关；[第三步混合召回与注入诊断](165_长期记忆第三步_混合召回与注入诊断_2026-10-09.md)增加语义/词法 RRF、版本绑定向量缓存、失败回退和实际注入诊断。明确稳定、可逐字核验的低风险事实可在用户授权后生效，改写无法核实、冲突和长期指令继续待审；撤销历史阻止旧来源重新自动生效。记忆使用现有 Embedding Provider，在过滤后的记忆集合上由应用精确计算相似度，未建立记忆 ANN 索引，不混入知识库 Chunk。

- 只读 Durable Run 是至少一次投递、幂等状态机，不承诺跨 Redis/PostgreSQL 的 Exactly Once；写入类工具不走这条重放链。
- 同步 Chat 仍会受请求生命周期约束；强杀进程时未收口的流式 partial content 可能丢失。
- Worker 有独立启动脚本、心跳与任务页指标，但没有声称外部告警推送、自动扩容或生产级集中托管。
- Planner 建议发生于同步规划链，尚不是“执行前模型自动选择同步/后台”协议。
- 暂不开放 Shell/Bash、SQL、删除文件、任意本机路径写入、支付、邮件、外部发布和任意 HTTP 写。
- 当前 Tool Catalog 冻结，下一步以面试复盘和部署口径核查为主，不继续以数量堆叠能力。

## 面试时怎么讲

30 秒：我做的是本地知识工作台，主链从混合 RAG、记忆与上下文预算，到模型规划工具、代码执行和结果质量判断，再到用户确认的可恢复后台任务。模型负责提出计划和回答，权限、预算、执行、失败状态与恢复由代码控制。

展开时依次讲：文档如何入库和检索；消息锚点、摘要、长期记忆与证据如何组装；Tool 候选、Planner、校验、质量合同与 DAG 失败如何闭环；最后说明 Handoff、Worker、原会话结果回写、任务页、审计及边界。不要把同步 Chat 说成已能崩溃恢复，也不要把 Planner 建议说成自动后台执行。
