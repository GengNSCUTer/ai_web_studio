# 上下文配置与动态预算说明

这份文档专门回答两个问题：

1. 前端设置页里的“模型上下文窗口”和“上下文模式”分别是什么意思
2. 后端内部到底有哪些上下文治理参数，它们分别控制什么

这份说明尽量贴近当前项目代码，而不是抽象讨论。

---

## 1. 前端当前这两个设置是什么意思

当前前端设置页里，和上下文治理直接相关的只有两个高层参数：

- `模型上下文窗口`
- `上下文模式`

另外当前前端已经提供一层只读诊断展示：

- 上下文治理诊断卡片
- 上下文提示列表

它们不是用户配置项，而是后端每轮返回的治理观测结果。

这两个参数的设计思路是：

- 用户只调“高层策略”
- 后端自动推导“底层预算细节”

诊断面板的设计思路则是：

- 用户和开发者能直接看到当前预算结果
- 能快速判断这一轮是否发生裁剪、摘要刷新、附件预算收缩
- 为后续调参提供观测面

也就是说，用户不需要直接面对一大堆 `max_history_messages`、`max_attachment_chars` 之类的内部参数。

## 2. 模型上下文窗口

### 2.1 它表示什么

`模型上下文窗口` 表示：

**你希望后端按多大的上下文容量来规划本轮请求。**

它不是“本轮一定会塞满这么多内容”，而是：

- 后端会把它当作一个总预算上限参考
- 再从里面预留一部分给模型输出
- 剩下的部分再分配给历史消息、附件、摘要等内容

当前代码里，后端会先固定预留：

- `8192 tokens`

给模型输出。

也就是说：

- 如果你设置 `128000`
- 后端不会把 128000 全拿去塞输入
- 而是会预留一部分输出空间，避免模型“还没回答就把窗口占满”

### 2.2 它现在是“混合预算”，不是纯字符拍脑袋

当前这一版已经升级为：

**token 预算输入 + 字符预算执行 + tokenizer 级观测**

具体说：

1. 先把 `模型上下文窗口` 当作 token 级总容量参考
2. 扣掉保留给输出的 `8192`
3. 再用一个保守换算，把可用 token 预算映射成字符预算，用于稳定裁剪
4. 同时用 `TokenizerEstimator` 对 Prompt、摘要、附件、稳定前缀做 token 估算，并把结果回传到前端诊断面板

所以它现在是一个：

- 接近真实能力的高层控制量
- 带 tokenizer 观测的混合预算框架
- 还不是严格等价于 provider 真实计费 / 真实上下文切分的最终形态

### 2.3 当前默认值

当前项目里，后端按 provider 给默认值：

- `ollama` 默认 `100000`
- `openai-compatible` 默认 `128000`

这是在 `SettingService` 里做的默认策略，不是写死在前端页面里的唯一真理。

### 2.4 你怎么理解这个值

可以简单理解成：

- 值越大，后端越愿意保留更多历史和附件
- 值越小，后端越保守，裁剪会更早发生

但它的影响不是线性的“只多一点点”，因为后端还会叠加 `上下文模式` 一起计算。

### 2.5 什么时候该调大，什么时候该调小

适合调大：

- 你在做长对话
- 你经常上传较长文档
- 你用的是在线 API，窗口本来就比较大
- 你希望模型尽量记住更多前文

适合调小：

- 你本地显存紧张
- 你发现 Ollama 长上下文明显变慢
- 你当前任务其实不需要很长记忆
- 你更在意稳定和响应速度

### 2.6 当前建议

对你现在这个项目，建议先这样用：

- 本地 `ollama`：
  `100000`
- 在线 `openai-compatible`：
  `128000`

如果后面你确认本地模型在你机器上能稳定扛住更长上下文，再继续往上试。

## 3. 上下文模式

### 3.1 它表示什么

`上下文模式` 表示：

**在当前上下文窗口内，后端采用什么风格来分配预算。**

它不是简单的标签，而是会直接影响：

- 最多保留多少条历史消息
- 总字符预算有多激进
- 附件预算占比有多大
- 摘要预算有多大

### 3.2 当前 3 种模式

当前代码里有 3 档：

- `conservative`
- `balanced`
- `long-context`

### 3.3 这三档的直觉理解

`conservative`

- 更保守
- 更偏向稳定
- 更早裁剪历史和附件
- 适合本地模型、显存紧张、追求响应稳定时使用

`balanced`

- 默认档
- 在稳定性和上下文保留之间折中
- 适合作为绝大多数场景的起步设置

`long-context`

- 更激进
- 尽量保留更多历史和附件
- 适合长文档、多轮复杂追问
- 但也更容易让本地模型变慢

### 3.4 它和“模型上下文窗口”的关系

可以这样理解：

- `模型上下文窗口` 决定“总盘子有多大”
- `上下文模式` 决定“这个盘子怎么分”

例如：

- 同样是 `128000`
- `conservative` 和 `long-context` 得到的历史条数、附件预算、摘要预算都不一样

## 4. 当前后端是怎么换算预算的

当前核心逻辑在：

- [context_governance_service.py](/disk2/gengnan/ai_web_studio/backend/app/services/context_governance_service.py)

### 4.1 固定硬边界

当前后端先有 3 个硬边界：

- 最小上下文窗口：`8192`
- 最大上下文窗口：`262144`
- 输出保留：`8192`

含义分别是：

- 小于 `8192` 会被自动抬到 `8192`
- 大于 `262144` 会被自动压到 `262144`
- 不管你设置多少，都会先留 `8192` 给模型生成回答

### 4.2 预算换算流程

当前换算大致是：

1. 读取用户设置的 `model_context_window`
2. 做上下限裁剪
3. 扣掉 `RESERVED_OUTPUT_TOKENS = 8192`
4. 把剩余 token 预算近似换算成字符预算
5. 再根据 `context_mode` 乘不同的比例
6. 得到历史、附件、摘要、图片等预算

### 4.3 当前模式参数

#### 历史消息条数上限

- `conservative = 10`
- `balanced = 16`
- `long-context = 24`

#### 总字符预算比例

- `conservative = 0.32`
- `balanced = 0.45`
- `long-context = 0.6`

含义是：

- 同样的窗口大小下
- `long-context` 会给输入上下文更多字符预算
- `conservative` 会更早收缩

#### 附件预算比例

- `conservative = 0.20`
- `balanced = 0.28`
- `long-context = 0.34`

含义是：

- 上下文模式越激进，越愿意把预算分给附件文本

#### 摘要预算比例

- `conservative = 0.10`
- `balanced = 0.12`
- `long-context = 0.14`

含义是：

- 越激进的模式，越愿意保留更大的摘要预算
- 这样长会话里更容易维持“摘要替代旧历史”的能力

#### 图片等价 token / chars 预算

当前还额外给图片做了一个“等价预算”：

- `max_image_equiv_tokens = max(300, min(1800, int(max_total_tokens * 0.08)))`
- `max_image_equiv_chars = max(1200, min(6000, int(max_total_chars * 0.08)))`

这不是把图片真的转成字符，而是为了让：

- 多模态输入
- 图片消息

也能进入统一预算框架。

也就是说，现在后端预算已经不只是“纯文本预算”。

## 5. 当前真实代码里还做了哪些上下文治理动作

前面主要讲的是预算规划器，这里补充一下当前完整链路。

### 5.1 会话摘要不是每轮都重算

摘要刷新逻辑当前在：

- [context_governance_service.py](/disk2/gengnan/ai_web_studio/backend/app/services/context_governance_service.py)
- [chat.py](/disk2/gengnan/ai_web_studio/backend/app/api/routes/chat.py)

它不是每轮强制重做，而是满足以下条件之一才刷新：

- 还没有已有摘要
- 待压缩消息数 `>= 6`
- 待压缩字符数 `>= 4000`

刷新流程：

1. 先找出摘要边界之后、且不在最近窗口中的历史消息
2. 优先调用模型做摘要
3. 模型失败则走 fallback 结构化摘要
4. 保存：
   - `context_summary`
   - `context_summary_boundary_message_id`
   - `context_summary_updated_at`

### 5.2 Prompt 前缀稳定性已经在观测

当前后端会把稳定前缀单独取出来做：

- `stable_prefix_messages`
- `prompt_prefix_hash`
- `prompt_prefix_tokens`
- `prompt_prefix_reused_last_turn`

这一步的意义是：

- 当前虽还没有接真实 provider cache 命中数据
- 但已经可以观察“我们自己的 Prompt 前缀是否稳定”

这对于后续接：

- OpenAI Prompt Caching
- Gemini context cache
- vLLM/SGLang prefix cache

是前置基础。

### 5.3 tokenizer 观测已经回传前端

当前使用：

- [tokenizer_service.py](/disk2/gengnan/ai_web_studio/backend/app/services/tokenizer_service.py)

它会按模型名推断模型家族，再映射到 encoding：

- `openai -> o200k_base`
- `qwen / deepseek / claude / gemini / generic -> cl100k_base`

然后估算：

- 单文本 token
- 单消息 token
- 多消息总 token

这些估算值已经进入上下文诊断面板。

### 5.4 长期记忆、附件、外部工具都在同一条诊断链里

当前 `chat.py` 里每轮会同时构建：

- memory context
- attachment context
- external context
- governed messages

并把相关统计统一汇总回前端。

这意味着我们当前已经有“统一上下文观测面”，而不是每个模块各算各的。

## 7. 这些参数用户该不该直接配

这是一个很关键的问题。

当前建议继续保持：

- 用户只配置高层参数
- 后端掌控底层预算

也就是：

前端允许用户调：

- `model_context_window`
- `context_mode`
- `memory_enabled`

后端内部控制：

- `RESERVED_OUTPUT_TOKENS`
- `MODE_HISTORY_LIMITS`
- `MODE_CHAR_RATIOS`
- `MODE_ATTACHMENT_RATIOS`
- `MODE_SUMMARY_RATIOS`
- `SUMMARY_REFRESH_MIN_MESSAGES`
- `SUMMARY_REFRESH_MIN_CHARS`
- `memory_max_chars`

原因很简单：

1. 底层参数过多会让普通用户完全不知道怎么调
2. 很多参数是联动的，单独暴露反而更容易把系统调坏
3. 我们现在项目还处在快速迭代期，底层参数需要频繁改，不适合一开始就全部产品化

所以更合理的是：

- 用户调“窗口大小”和“治理风格”
- 开发者调“具体预算公式”

## 8. 当前怎么调最合适

### 8.1 对本地 Ollama

如果本地模型上下文较长时明显变慢，建议：

- `model_context_window = 100000`
- `context_mode = balanced`

如果你只是普通问答，且更关心稳定性：

- `context_mode = conservative`

如果你要做长文档问答、上下文追问很多：

- `context_mode = long-context`

但前提是你确认本地模型和显存能扛住。

### 8.2 对在线 openai-compatible provider

如果在线 API 本来就支持较大上下文，建议：

- `model_context_window = 128000`
- 默认从 `balanced` 开始

如果你明确在做长文档推理，再切 `long-context`。

### 8.3 如果你发现模型经常“失忆”

优先排查：

1. `context_mode` 是否太保守
2. `model_context_window` 是否设置过低
3. 摘要是否已经刷新，但摘要内容质量不够
4. 是否是长期记忆根本没进入本轮

不要第一反应就把上下文无限拉大，因为可能真正的问题是：

- 摘要质量差
- 附件预算占太多
- Prompt 结构不稳定

### 8.4 如果你发现模型很慢

优先排查：

1. `model_context_window` 是否过大
2. `context_mode` 是否太激进
3. 当前附件是否过多
4. 工具结果 / 外部来源是否太重
5. 是否处于摘要刷新轮次

## 9. 当前这一版还不是什么

为了避免理解偏差，也要明确说当前这版还不是什么。

### 9.1 还不是严格 token-first 切分

现在是：

- token 预算输入
- 字符预算执行
- tokenizer 观测回传

这已经很实用，但不是最终形态。

### 9.2 还没有真实 provider cache hit 指标

现在的：

- `prompt_prefix_hash`
- `prompt_prefix_reused_last_turn`

只是应用层近似观察，不等于真正的推理缓存命中率。

### 9.3 还没有把知识库召回接进来

当前治理的是：

- 历史消息
- 摘要
- 长期记忆
- 当前轮附件
- 外部工具

还没有治理：

- 工作区知识库召回
- 跨历史附件召回
- 重排后的知识片段

## 10. 后续最值得升级的 4 个点

### 10.1 做真正的分层预算

后续可以把预算显式拆成：

- stable prefix budget
- recent history budget
- summary budget
- memory budget
- attachment budget
- external tool budget
- future knowledge budget

这样调优会更清楚。

### 10.2 接真实缓存观测

后续如果 provider 支持：

- `cached_tokens`
- cache key
- cache hit / miss

就把它们回传到当前诊断面板。

### 10.3 把知识库召回接到当前框架

后续 P3 做工作区知识库后，应该直接复用当前上下文治理主链路，而不是再起一套平行系统。

### 10.4 增强摘要和记忆质量观测

后续建议继续增加：

- 摘要压缩倍率长期趋势
- 记忆注入命中情况
- 记忆冲突 / 去重提示
- 记忆来源追踪

> 当前 AI Web Studio 已实现“高层窗口设置 + 上下文模式 -> 动态预算规划 -> 历史/摘要/记忆/附件/外部工具统一治理 -> tokenizer 级诊断回传”的第一版混合上下文治理框架。

这句话是贴近当前真实代码状态的，也适合以后写项目总结或简历。

- 长上下文模式下，允许保留更长的压缩摘要

#### 图片等效字符预算

当前规则是：

- `max(1200, min(6000, int(max_total_chars * 0.08)))`

可以简单理解为：

- 每张图片在预算估算时，会按一个“等效字符成本”计入
- 当前这个值会落在 `1200 ~ 6000` 之间

它不是图片真实大小，而是：

- 为了让图片也参与预算竞争
- 避免图片输入无限堆叠

## 6. 后端当前有哪些“设置参数”

这里要区分两类：

- 用户可配置参数
- 后端内部参数

### 6.1 用户可配置参数

当前和上下文治理直接相关的用户参数只有两个：

- `model_context_window`
- `context_mode`

它们存储在数据库 `user_settings` 表中。

其中：

- `model_context_window` 是整型
- `context_mode` 是字符串

### 6.2 后端内部参数

这些参数当前不直接暴露给用户，而是在后端代码里控制：

- `HARD_MAX_CONTEXT_WINDOW = 262144`
- `MIN_CONTEXT_WINDOW = 8192`
- `RESERVED_OUTPUT_TOKENS = 8192`
- `MODE_HISTORY_LIMITS`
- `MODE_CHAR_RATIOS`
- `MODE_ATTACHMENT_RATIOS`
- `MODE_SUMMARY_RATIOS`

这些参数分别控制：

- 允许的最小 / 最大窗口
- 给回答保留多少输出空间
- 每种模式下保留多少历史消息
- 每种模式下给总输入、附件、摘要分多少预算

### 6.3 老的环境变量参数

在 [config.py](/disk2/gengnan/ai_web_studio/backend/app/core/config.py) 里还保留着这些旧参数：

- `CONTEXT_MAX_HISTORY_MESSAGES`
- `CONTEXT_MAX_TOTAL_CHARS`
- `CONTEXT_MAX_ATTACHMENT_CHARS`
- `CONTEXT_MAX_IMAGE_EQUIV_CHARS`
- `CONTEXT_MAX_SUMMARY_CHARS`
- `CONTEXT_KEEP_TRUNCATION_NOTICE`

当前状态是：

- `CONTEXT_KEEP_TRUNCATION_NOTICE` 仍然可以视为全局行为开关候选项
- 其余几个 `CONTEXT_MAX_*`，已经不再是主链路的核心控制参数
- 现在主链路已经切到“动态预算框架”

也就是说，当前真正起主要作用的是：

- 用户设置里的两项高层参数
- `ContextBudgetPlanner` 里的内部换算规则

## 7. 当前实际裁剪时，后端做了什么

当前治理流程大致是：

1. 先根据会话里的 `context_summary` 和 `context_summary_boundary_message_id`，把“较早历史”折叠成滚动摘要
2. 只回放边界之后的最近原始消息
3. 把系统提示、滚动摘要、最近原始消息、当前输入、图片、文件拼到候选上下文里
4. 估算总字符量
5. 如果超预算，优先移除较旧的原始历史消息
6. 还超预算，就截断最后一条用户输入
7. 如果未被摘要覆盖的较早历史积累到一定规模，就刷新滚动摘要并更新边界

这意味着当前优先级大致是：

- `system prompt` 尽量保留
- 会话级滚动摘要尽量保留
- 当前轮用户输入尽量保留
- 较旧原始历史先被裁
- 附件先按预算截断

### 7.1 当前滚动摘要刷新策略

当前不是每轮都重算摘要，而是按“增量刷新”做：

- 如果还没有摘要，那么首次满足条件时生成
- 如果已经有摘要，就只看“边界之后、最近窗口之前”的那部分较早历史
- 当这部分内容达到下面任一条件时，刷新摘要：
  - 至少 `6` 条消息
  - 或至少 `4000` 字符

这样做的目的有两个：

- 避免每轮都重算摘要，减少抖动
- 保证最近窗口仍然保留原文，不会过早被压缩掉

## 8. 这些参数要不要给用户全部开放

我的建议是：

**不要把底层全部开放给用户。**

更合理的做法是：

- 前端只保留少量高层设置
- 后端掌握底层预算细节

原因很直接：

- 参数太多，用户很难理解
- 多个参数之间有联动，不适合手工单独调
- 容易把产品变成“调参面板”，而不是正常聊天产品

当前比较合适的分层是：

前端开放：

- `模型上下文窗口`
- `上下文模式`

后端保留：

- 输出预留
- 历史条数上限
- 附件占比
- 摘要占比
- 图片等效成本
- 最小 / 最大窗口边界

## 9. 你现在怎么调最合理

对你当前这个项目，我建议：

如果是本地 Ollama：

- 先用 `100000`
- 模式先用 `balanced`

如果发现：

- 响应慢
- 模型经常卡住
- 长对话明显拖性能

那就改成：

- `100000 + conservative`

如果你在做长文档问答，且模型表现稳定：

- 可以试 `100000 + long-context`

如果是在线 API：

- 先用 `128000 + balanced`

如果后面你明确需要更长历史保留：

- 再试 `128000 + long-context`

## 10. 后续还可以怎么继续升级

当前这套框架已经比“固定裁剪”好很多，但还只是第一阶段。

后面最值得继续做的是：

1. 上下文统计面板
   当前已经完成第一版：能看到当前轮字符预算、Token 预算、摘要触发情况、附件片段统计和稳定前缀观测

2. 模型级摘要压缩
   当前已经完成第一版：滚动摘要刷新时优先调用当前 provider/model 生成语义摘要，并在失败时回退到规则摘要

3. provider / model 级动态模板
   当前已经完成第一版：新增 `ContextPromptBuilder`，统一生成 provider 消费的消息结构，并输出 `prompt_template_version`、`provider_template`、`model_family` 等诊断字段。后续还可以继续做不同模型的深度差异化模板

4. 附件索引化与按需展开
   当前已经完成第一版：新增 `AttachmentContextService`，当前轮文档会被切块、关键词打分，并按 `budget.max_attachment_chars` 只注入相关片段。当前仍是运行时轻量索引，不是持久化索引表，也不是 embedding 检索

5. tokenizer 级预算
   当前已经完成第一版：引入 `TokenizerEstimator`，可返回 `total_tokens_estimate`、`attachment_context_tokens`、`summary_tokens`、`summary_refresh_source_tokens`、`prompt_prefix_tokens`、`prompt_total_tokens` 等指标。后续还可以继续做更贴近具体模型的精细化预算

6. 长期记忆
   当前已经完成手动长期记忆 MVP：用户可以在设置面板保存、启停和删除长期记忆，并通过 `memory_max_chars` 控制注入预算

7. 模型建议记忆
   当前已经完成第一版：模型可从当前会话中提取候选记忆，用户确认后再写入长期记忆库

8. 记忆冲突检测和来源追踪
   当前已经完成规则版：保存候选记忆前会提示可能重复或冲突的已有记忆，并记录候选来源会话、来源消息和置信度

9. 长期记忆来源可视化
   当前已经完成来源会话级可视化：长期记忆卡片会展示来源会话，并支持点击跳转到对应历史会话

10. 来源消息级定位
   后续可继续做“点击查看来源消息”，跳到具体消息并高亮；当前只做到来源会话级跳转

11. 语义级记忆去重
   后续可用 embedding 或轻量语义模型替代当前字符相似度规则

12. 缓存命中观测
   当前已经完成第一版：可观测稳定前缀 hash、稳定前缀 Token 数、Prompt 总 Token 数、最近历史 Token 数，以及“是否复用上一轮稳定前缀”的启发式结果。后续再继续做 provider 真实缓存命中率和成本统计

## 11. 一句话总结

当前前端这两个设置，本质上就是：

- `模型上下文窗口`：决定总盘子多大
- `上下文模式`：决定这个盘子怎么分

而后端的动态预算器负责把这两个高层参数自动换算成：

- 历史保留多少
- 附件能进多少
- 摘要保留多长
- 图片按多大成本计算

同时，前端“上下文治理诊断”弹层已经能把这些换算结果可视化出来，包括：

- 本轮字符 / Token 估算
- 附件片段字符 / Token 估算
- 摘要 Token、摘要源 Token、压缩比
- 稳定前缀 Hash、稳定前缀 Token、Prompt 总 Token、最近历史 Token

这样既保留了可调性，又不会把用户暴露在一堆底层细参数面前。

## 12. 2026-05-13 当前参数体系校准与后续优化

结合当前实现，前端继续只暴露两个高层参数是合理的：

- `模型上下文窗口`
- `上下文模式`

但后续需要把“预算配置”从静态经验值，逐步升级为“按 provider / model 能力和真实观测动态调整”。

### 12.1 当前已经能支撑的能力

当前预算框架已经能支撑：

- 本地 Ollama 和 OpenAI-compatible provider 使用不同默认上下文窗口
- 用户按模型实际启动参数调整窗口大小
- conservative / balanced / long-context 三档模式切换
- 附件、摘要、历史、长期记忆共用同一个预算盘子
- 前端诊断看到字符估算、token 估算、摘要压缩比、附件片段注入、稳定前缀 hash

### 12.2 当前还不够精细的地方

当前仍然存在这些限制：

- tokenizer 仍然是估算，不等于每个模型真实 tokenizer
- 图片等效 token 成本仍是经验值
- 不同 provider 的真实 prompt cache 命中情况还没有回写
- 附件片段只做当前轮运行时筛选，没有持久化索引
- 上下文诊断默认不落库，刷新页面后不能复盘某一条回答的完整诊断

### 12.3 后续参数体系建议

后续可以把设置分成三层：

第一层：用户可见

- 模型上下文窗口
- 上下文模式
- 是否启用长期记忆
- 长期记忆预算

第二层：模型能力配置

- 最大上下文窗口
- 是否支持图片
- 是否支持工具调用
- 是否支持 provider 侧缓存
- 默认输出 token 预留

第三层：后端策略参数

- 历史消息保留上限
- 摘要刷新阈值
- 附件 chunk 大小
- 附件召回 top-k
- 记忆召回 top-k
- 图片等效 token 成本
- 缓存稳定前缀层级

前端不应该暴露第三层所有细参数，但后端应该集中管理，并在诊断中解释关键结果。

### 12.4 性能观测建议

后续建议新增这些指标：

- 请求总耗时
- 首 token 延迟
- 流式输出持续时间
- prompt token 估算
- completion token 估算
- 稳定前缀 token 数
- provider 返回的缓存命中 token 数
- 摘要刷新耗时
- 附件解析 / 切块 / 召回耗时

这些指标能帮助判断：

- 是模型冷启动慢
- 还是上下文太长导致 prefill 慢
- 还是附件解析慢
- 还是 provider 网络慢
- 还是前端流式展示慢

### 12.5 推荐的下一步配置改造

下一步最建议做：

1. 新增消息级上下文诊断持久化
2. 新增附件 chunk 持久化表
3. 在设置页增加“模型能力说明”，展示当前模型是否支持图片、上下文窗口、provider 类型
4. 在上下文诊断中区分“估算 token”和“provider 返回 token”
5. 如果 provider 支持缓存统计，则记录真实缓存命中数据

这样可以把当前预算器从“可用”推进到“可解释、可复盘、可优化”。
