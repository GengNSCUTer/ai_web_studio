### 2.5 发现的问题

#### 问题 1：`retrieval-test` 不写检索日志

测试中 `/retrieval-test` 返回结果正常，但 `/retrieval-logs` 返回 0 条。

原因从源码看是：

- `KnowledgeDocumentService.test_retrieval()` 只调用 `KnowledgeRetrievalPipeline.retrieve()` 并返回结果。
- 聊天内知识库检索走 `KnowledgeContextService._build_single_context()`，该路径会调用 `KnowledgeRetrievalLogRepository.create()`。

这说明当前“测试检索”和“聊天实际检索”的观测行为不一致。

影响：

- 用户在知识库页面测试检索，不会沉淀到检索日志。
- 后续如果希望从测试结果加入评测集，缺少日志记录基础。
- 检索调参时，页面测试和真实聊天的日志链路不统一。

建议：

- 后续让 `retrieval-test` 也可选写入 retrieval log。
- 或者增加 `save_log: bool = true` 参数。
- 日志中区分来源：`source=chat_context` / `source=retrieval_test` / `source=evaluation`。

#### 问题 2：上传接口会提前解析 PDF

`backend/app/api/routes/uploads.py` 在上传文件时会调用 `FileParserService.parse_file()`。

这会导致：

- 上传 PDF 时已经做了一次解析。
- 后续加入知识库后，`parse_document()` 又会再次解析。
- 对 MinerU / OCR / 大 PDF 来说，上传阶段提前解析不一定合理。

当前影响：

- 对小 PDF 问题不大。
- 对扫描版 PDF 或复杂 PDF，上传阶段解析失败会直接阻止上传，即使知识库本身配置了 MinerU 也无法进入后续解析。

建议：

- 区分“聊天附件上传”和“知识库文档上传”。
- 知识库上传只做类型/大小校验和保存，不在 upload 阶段强制解析。
- 解析职责收敛到 `KnowledgeParserService`。

#### 问题 3：索引文档时会重算全知识库 embedding

`KnowledgeIndexService.index_document()` 当前流程：

```text
replace current document chunks
-> list all chunks in knowledge base
-> embed all chunks
-> rebuild FAISS
-> rebuild BM25
```

优点：

- 实现简单。
- 能保证 FAISS / BM25 和数据库 chunks 一致。

缺点：

- 每新增一个文档，都会重新 embedding 全库 chunks。
- 文档越多，索引成本越高。
- API embedding 成本和耗时会随知识库增长快速上升。

建议：

- 近期可以接受，但需要标记为性能边界。
- 后续引入增量索引：
  - 只 embedding 新/变更 chunks。
  - FAISS 支持按 id remove/add 或重建时复用已有向量。
  - BM25 postings 支持文档级更新。

#### 问题 4：解析/索引是同步请求，长任务容易阻塞

`parse_document()` 和 `index_document()` 都是同步服务方法，API 请求会等待任务完成。

风险：

- 大 PDF / MinerU / 大知识库索引会长时间占用请求。
- 前端容易超时或用户误以为卡住。
- 后续多用户使用时服务吞吐会受影响。

建议：

- 将解析、索引改为后台任务。
- API 只创建 job 并返回 job id。
- 前端轮询 job 状态或用 SSE/WebSocket 接收进度。

#### 问题 5：Auth 默认 secret 不适合生产

`backend/app/core/config.py` 默认：

```text
AUTH_SECRET_KEY = change-this-before-production-ai-web-studio-secret
```

本地开发可接受，但正式部署必须强制检查。

建议：

- `APP_ENV=production` 时，如果仍使用默认 secret，后端启动失败。
- 同样检查 `SECRET_ENCRYPTION_KEY`、数据库密码、API key 等生产必需配置。

## 6. 当前结论

当前项目后端不是简单 CRUD，已经形成了几条比较完整的业务链路：

- 用户认证与设置。
- 聊天执行与上下文治理。
- 文件/图片/附件上下文。
- 知识库解析、索引、检索、评测。
- 外部工具与 MCP 调用。

从工程质量看，核心方向是正确的，但接下来更重要的是：

- 把同步重任务改成后台任务。
- 统一测试检索、聊天检索和评测检索的日志模型。
- 降低上传、解析、索引之间的职责耦合。
- 为知识库规模增长做增量索引和任务队列准备。
