# 长期记忆数据库召回与 LangGraph 迁移取舍

日期：2026-11-05。承接 [207 容量测量](207_Chat与长期记忆并发容量优化_2026-11-05.md)。本次实际修改记忆查询，不接入 LangGraph，不改变模型、数据库地址、普通 Chat 或 Durable 的权限边界。

## 1. 这次解决什么

原实现：新问题把当前范围内全部记忆正文和 JSON 向量拿回 Python，逐条解析、算相关性；Redis 主要复用相同问题，命中也读取整份版本清单。

新实现：数据库先返回有限的词法/向量候选，后端只处理这些正文，再按原规则选最多 8 条。Redis 仍缓存派生 ID 与分数，但失效检查改成用户记忆修订号与最早有效到期边界。不是把全部记忆改存 Redis，也不是只取最近若干条旧事实。

## 2. 当前读取链路

1. 短事务读取设置、用户修订号及当前范围下一到期边界，然后释放连接，再访问 Redis。
2. 缓存有效时只读取选择出的 ID，重新检查授权/正文版本；没有整份版本清单传输。
3. 新问题先走 PostgreSQL 中文双字/英文词的 GIN 词法查询，最多 32 个；少量 profile/instruction 最多 8 个；未完成向量补建的事实最多 32 个。
4. 在事务外调用真实 Embedding，问题向量在数据库执行语义检索，最多 32 个结果。每用户有效索引候选不超过 256 时精确距离；超过后支持固定维度的 HNSW。过滤后数量不足或最高相似度低于现有 0.45 门槛时补精确检索。近似路径不是 100% 召回保证。
5. 合并候选后保留原词法/语义融合、偏好配额、范围覆盖和预算规则，应用处理的唯一正文不超过 104 条，不再取全部 JSON 向量。候选数/语义路由/积压在诊断中记录，`eligible_count` 在生产有界路径为 null，不能把候选数冒充全部合规记忆数。
6. 注入前复核修订号、设置、候选的 active/启用/TTL/用户项目来源范围、敏感内容和正文版本。网络期间事实发生变更时，本轮可不注入记忆，不让旧结果覆盖新事实。

修订号由数据库触发器与事实变更同事务推进，覆盖直接 SQL、新建/修改/撤销/删除以及来源会话/项目范围变化；回滚也回滚修订号。到期是时间变化，不依赖触发器，因此另查到期边界。纯向量更新和重试时间不会推进事实版本或更新时间。

## 3. 向量维护与失败边界

正文仍保存在 user_memories；原 JSON 向量暂保留给 SQLite 业务单测和既有冲突判断。新增原生 pgvector 派生列、词法列与索引，由写入触发器维护。转换前验证现有正文/版本哈希；坏 JSON、零向量、旧正文向量不进入原生索引。同维度不同 Provider/模型/地址继续用现有签名隔离。

既有 memory-worker 没有提取任务时，复用新 MemoryIndexWorker 每批最多 32 条补建向量；90 秒领取/失败退避，网络外短事务，迟到结果需复核原文、版本、当前配置与领取时间。Web 冷查询也只允许有限补建，不会为了首次查询发无限向量请求。模型切换后失效旧原生索引并允许重新补建。

积压未完成时可能暂时漏掉没有词法重合的未索引事实，诊断明确 `index_backlog_pending`；不是静默宣称索引完整。后台领取、原生索引异常不能把敏感资料或 Provider 错误输出到日志。SQL 设置 1.5 秒 statement_timeout 和 250 毫秒 lock_timeout，取消线程并不等于能取消已发 SQL。

## 4. 同机前后测试

固定 1,000 条合成事实、每个问题不同、Redis 全 miss，每格 24 次计时请求；Embedding 采用确定性测试替身以隔离 API 耗时。是真实 PostgreSQL/Redis 组件测试，不是多用户 HTTP 持续负载或线上 QPS。

| 并发 | 旧 P95 | 新 P95（r3） | 应用正文读取 |
| --- | ---: | ---: | --- |
| 1 | 809.418 ms | 116.742 ms | 1,000 → 64 |
| 8 | 11,315.121 ms | 918.245 ms | 1,000 → 64 |
| 16 | 25,969.710 ms | 2,262.722 ms | 1,000 → 64 |

两轮各 72 次、错误为 0，结束连接借出为 0。最终新路径单请求 19 条 SQL，旧路径 7 条；减少的是正文/向量搬运和 Python 处理，不宣称 SQL 条数更少。新 16 并发仍约 2.3 秒，不能说所有容量问题已消失。r2 与 r3 有共享机器波动，全部中间报告保留，不挑选最快一格。

已在仓库外备份正式 PG、上传与索引，迁移到 20261105_02，继续使用 API 32007、前端 32008、PG 35433。备份脚本恢复服务时新代码因迁移未完成拒绝启动；迁移后重新启动后端，服务恢复正常。没有新开重复服务或加载 Ollama。

仍未完成：历史页面完整游标分页、混合读写的多用户 HTTP 长压、不同真实模型下大规模记忆召回质量、缓存独立实例容量部署。ANN 过滤/极端分布存在召回风险；目前只对少量实际失败路径精确补齐，不能保证所有近似漏召回被发现。

## 5. 全量迁移 LangGraph 的收益和影响（尚未实施）

比较对象是将同步 Agent Loop 与后台工作流编排统一交给 LangGraph，不是只在现有服务外再套一个节点。

| 方面 | 现有实现 | 全量迁移的潜在收益 | 实际仍要维护/改变 |
| --- | --- | --- | --- |
| 循环与分支 | ExternalContextService 内维护轮次、观察与终止 | 用图节点、条件边组织，复杂分支/子图更清晰 | 将 query、ToolPlan、观察、预算和结束原因设计成状态；替换现有循环 |
| 并发与依赖 | ToolWorkflowService 已实现 DAG/绑定/部分失败 | 可统一表达上层并行分支 | 先保留单计划 DAG 调度；若也迁移，必须重写 Result Binding 和失败传播测试，避免两层重复调度 |
| 检查点与暂停 | 自研 Run/Step/Checkpoint/Approval | 可复用框架 checkpoint、interrupt/resume 基础能力 | 对齐 thread/run/checkpoint 与用户/项目/审批；数据库业务状态和图状态不能各说各话 |
| Worker 恢复 | 已有 Lease/Heartbeat/Fencing/幂等/DLQ | 图状态恢复可减少部分自写状态管理 | Worker 进程托管、租约、防旧写、副作用幂等不会自动消失；需明确恢复可能重进节点 |
| 流式与前端 | NDJSON/消息 generation/CAS | 可将节点/任务事件适配成现有事件 | 保留前端协议；适配取消、错误、重复事件和最终消息落库，不自动改 SSE |
| 调试与生态 | 已有结构化 Trace、业务评测 | 标准图和事件接口便于团队阅读、接生态工具 | 日志脱敏和自托管范围仍自己控制；不默认向外部托管平台发送数据 |
| 记忆与 RAG | 业务检索、范围/版本、预算、引用治理 | 可作为图节点调用和复用 | 本次数据库候选检索仍必需，换框架不会直接提高 PG 容量或检索准确率 |

迁移主要触及 `external_context_service.py`、`tools/workflow.py`、`durable_tool_runtime.py`、`document_task_service.py`/`document_task_worker.py`、Chat 事件适配、持久状态模型/迁移及相关测试。模型 Provider、MCP Client、Executor、安全策略、RAG、记忆和文件业务可以复用，不必为了框架重写。

建议下一次若授权迁移，先取“检索文件→读取→失败重规划→回答”同任务试点，对照原版业务完成、错误语义、取消、检查点恢复、副作用重复、代码维护量与延迟，再决定后台任务迁移。没有对照前，不能断言 LangGraph 一定更慢/更快或框架更难改。选型的主要收益是减少编排维护，不是让模型更聪明或凭框架名称获得生产可靠性。

官方参考：[Overview](https://docs.langchain.com/oss/python/langgraph/overview)、[Durable execution](https://docs.langchain.com/oss/python/langgraph/durable-execution)、[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)。
