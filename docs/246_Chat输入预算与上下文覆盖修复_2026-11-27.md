# Chat 输入预算与上下文覆盖修复

| 项目 | 源码复核 | 实现 |
| --- | --- | --- |
| 8.1 最终预算 | 原裁剪结束后可能返回仍超限的 Prompt。 | Chat 快照阶段先估算平台及用户系统提示、Skill 约束和当前问题的实际 Provider 消息。最终资料渲染后重新校验字符和 Token，超限转为 `context_budget_exceeded`。 |
| 8.2 图片计数 | Ollama 图片按张估算，OpenAI 图片为零，Anthropic 可能编码 Base64 字符串。 | `images`、`image_url` 和 `image` 均使用每张等效字符及 Token。Base64 正文不参与编码。 |
| 8.3 当前问题 | 原兜底会二分截短用户问题，结尾约束可能丢失。 | 当前用户正文和图片整体保留。必要项超限时给出缩短输入、减少图片或上传文件附件的提示。已上传文件继续走现有片段选择流程。 |
| 8.4 裁剪优先级 | 原固定顺序无法体现附件、显式资料和任务要求。 | 显式偏好回顾、Skill 或 MCP、当前附件、已选知识库、联网及摘要参与本轮排序。可选旧历史在优先资料前释放空间。当前附件与知识库同时有结果时，附件优先于知识库。 |
| 8.5 召回并发 | 长期记忆和知识库原来顺序执行，两者不消费对方结果。 | 一次冻结查询文本、历史、设置和归属，再以独立会话同时召回。发生失败或取消时回收另一侧协程。工具执行和摘要仍按序使用主会话，摘要核验历史及生成版本，Prompt 生成前再次核验记忆资格。 |
| 8.6 重复编码 | 每次试裁剪重复估算未变化的消息。 | 单次治理缓存原始消息字符和 Token，移除旧历史时从总量扣除。参考资料变化时重算受影响的消息，最终渲染后完整校验。 |
| 8.7 历史覆盖 | 摘要按数据库 24 条读取窗口分界，balanced 等模式的注入窗口更短，刷新阈值也可能跳过一小段未摘要历史。 | 摘要同步选批、后台恢复目标与本轮 10、16 或 24 条注入窗口对齐。窗口外有未覆盖内容就补齐，批次超限或有积压时走现有后台恢复，Chat 收到明确状态后结束。 |

## 主要代码

- `chat_context_assembly_service.py` 在快照阶段预检，固定本轮输入并准备附件。治理阶段确定本轮资料优先级，保持最终证据来源映射与实际 Prompt 一致。
- `context_governance_service.py` 和 `tokenizer_service.py` 统一多模态估算、保留当前问题、裁剪可选历史和资料，并核对最终预算。图片费用使用现行预算中的按张等效值，实际计费按 Provider 和模型处理。
- `agent_graph/context_graph.py` 合并长期记忆与知识库召回结果。`conversation_summary_service.py` 将后台摘要目标固定到当前模式和本轮历史上界。
- `chat_run_worker.py` 将超限转成已持久化的失败码。SSE 提供可操作提示，前端从终态快照恢复同一提示。

## 验证与运行

303 项后端回归通过，覆盖真实 PostgreSQL、图并发与取消、历史模式切换边界、长期记忆、知识库检索与来源审计。ESLint、12 项前端 SSE 测试和 `npm run build` 通过。Playwright 使用真实 Chat Worker 和受控 Provider，验证长输入按原文保存、生成尝试为 0、刷新后提示可见及后续普通聊天成功，控制台错误数为 0。

费用估算采用本地 Tokenizer 和图片等效值。最终总预算仍可能裁剪可选历史及摘要，摘要保留的是压缩内容。并发收益已用事件同步验证执行可重叠，线上首 Token 延迟和视觉模型实际输入用量需要单独测量。本批代码无需新增数据库迁移，运行实例部署仍需应用上一批 `20261127_01`。
