# 2026-08-01 安全权限五层防御与 Agent 项目落地

本轮阅读《理论学习：五层纵深权限防御》。文档对项目的借鉴重点是 Defense in Depth：硬拒绝、资源作用域、细粒度工具规则、权限模式和 HITL 确认各自承担不同责任。当前产品定位是个人本地知识库工作平台，不开放 Bash、Shell、SQL、删除、任意本机写入、支付、邮件、外部发布和任意 HTTP 写入，因此没有照搬代码代理的 Bash 黑名单，而是把同一原则映射到知识库、MCP、Skill 和 ProjectFile。

## 本轮完成

- MCP Server 支持项目作用域：`project_id` 可绑定 Server，项目级 Server 只进入对应项目的 Tool Catalog；用户级 Server 才能跨用户自己的项目复用。设置接口也不再向项目页面展示其他项目的 Server。
- 设置页创建 MCP Server 时会显式提交当前工作区作用域并展示范围；旧 PostgreSQL 部署由启动时幂等补齐 `mcp_servers.project_id` 列和索引，避免升级环境的 ORM/数据库不一致。
- 项目级 `WorkspaceToolSetting` 禁用的工具在项目 Catalog 中不再作为 Candidate Selector 候选，Executor 仍会在真实执行前二次读取设置并 fail-closed。
- Workspace File Tool 持续使用 `user_id + project_id + opaque ProjectFile.id` 作用域，不接受 OS 路径、storage key 或 Shell 表达式。
- Agent Tool 隐藏 `.env`、credentials、secrets、`id_rsa`、`.pem`、`.key` 等敏感命名文件；对常见 `API_KEY`、password、token 和常见云凭据做输出脱敏，编辑 Diff 也会脱敏。
- 保留三种权限模式：`read_only`、`ask`、`full_workspace`。`full_workspace` 仅对 ACL、Approval continuation 和 CAS 保护的项目文件编辑有效，不授权任意外部写入。
- MCP 远程 read-only hint、Schema、description 和返回内容仍按不可信 metadata/evidence 处理；Schema 或 annotation 变化会使本地审核失效。

## 验证

后端全量回归 `289 passed, 3 skipped`；compileall 和相关权限、MCP、Workspace File、Tool Executor 测试通过。被拒绝的 Tool 仍会以安全错误观察进入有界 Chat 循环，但不能通过改名、换工具或 Prompt Injection 绕过 Executor。

## 设计边界

当前不实现通用 Bash 规则引擎，也不把 `full_workspace` 设计成万能权限。未来新增副作用工具前，必须先具备不可逆操作硬拒绝、输入作用域、持久化审批、幂等键、审计、恢复和补偿闭环。
