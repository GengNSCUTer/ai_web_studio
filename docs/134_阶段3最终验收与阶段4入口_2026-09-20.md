## 阶段 3 的最终结论

阶段 3 解决的是多工具任务执行后的可靠收口，而不是增加更多 Tool。现在由代码完成以下判断：

```text
多个 Tool Plan
  ↓
并发执行 / 严格依赖阻断
  ↓
每个 Step 的执行状态与质量状态
  ↓
Workflow 聚合：succeeded / partial / failed / blocked / waiting_approval
  ↓
Chat 决策：finalize_partial / replan / clarify / stop
```

固定外层回归覆盖：

1. 两个独立 Tool 实际并发且均成功，聚合为 `succeeded`；
2. 一个独立 Tool 质量失败、另一个成功，聚合为 `partial`，只保留有效 evidence；
3. 所有独立 Tool 失败时，允许在预算内受控重规划，但没有 evidence 时不会伪造部分回答，预算耗尽后停止；
4. 严格依赖的上游质量失败时，下游不进入 Executor，外层 `clarify`；
5. 等待用户确认时只展示草案，依赖下游不执行，外层 `clarify`。

真实低风险烟测额外通过 Chat API 验证：LLM 规划高德天气与 Tavily 搜索，两项只读调用成功、通过质量门、聚合 `succeeded`，并在第一轮正常结束。烟测日志只记录状态、Tool Key 和计数，不保存或展示 API Key、原始参数、完整 URL、Provider 原文或模型回答正文。

## 阶段 4 的第一小步

阶段 4 处理 Tool Result 的 Prompt Injection 边界。已有质量门负责判断“结果是否可用”，但不能代替“外部文本是否会影响下一轮 Planner”的隔离。

第一小步实现了 `PlannerObservationProjection`：

```text
合格 Tool evidence
  ↓
按 Tool 类型提取白名单事实
  ↓
明确标记为不可信资料的 Planner observation
  ↓
下一轮 Planner
```

实现后，下一轮 Planner 默认不再接收网页、文件或 MCP 的标题、正文、`display_text`、URL 或 `metadata.raw`；只会收到平台生成的受限摘要和按 Tool 类型白名单化的标量事实。恶意网页结果回归已验证其指令文本不会进入 Planner observation。最终回答仍可引用资料，但只处于 reference evidence 层，不进入 system 消息；已通过受控假模型验证从上下文组装、流式输出到 assistant 消息落库的完整链路。

不在这一步实现 Durable handoff、新 Tool、高风险权限、开放插件市场或完整自动化长任务。后续仍需单独处理工作区文件/MCP 的受限摘录策略、最终回答的引用细化，以及更强的多语言注入样本集。
