## pgvector 替换 FAISS：第一阶段环境评估

### 架构决策

- 目标是让 PostgreSQL + pgvector 直接承担 Chunk Embedding 的持久化和向量检索。
- FAISS 在迁移完成后删除，不长期保留“pgvector 缓存 + FAISS 查询”双索引。
- generation 仍保留，但最终收敛为 PostgreSQL 内的 Chunk + Vector 快照和 active pointer 事务。

### 现有环境结论

- 原数据库是 PostgreSQL 12.20，端口 35432，数据库约 14 MB。
- 原环境没有 pgvector 扩展文件，不能只执行 `CREATE EXTENSION vector`。
- Docker CLI 存在，但当前用户没有 Docker daemon socket 权限。
- 已保留原 PostgreSQL 12 和原数据目录，它们继续作为回滚点。

### 已准备的隔离新环境

- PostgreSQL 18.3，端口 35433。
- pgvector 0.8.5。
- 已通过 PostgreSQL 12 `pg_dump -Fc` 和 PostgreSQL 18 `pg_restore` 完成逻辑恢复。
- 恢复后校验为 376 个 KnowledgeChunk、3 个 KnowledgeDocument。

### 验证结果

- pgvector 的 vector/halfvec/sparsevec、HNSW、IVFFlat、cast、copy 等 14 项自带回归测试全部通过。
- `vector(3)` + HNSW cosine 冒烟查询的相似度排序符合预期。
- 现有后端使用 `POSTGRES_PORT=35433` 临时启动成功，`/health` 返回 HTTP 200，验证后已停止临时进程。

### 下一步

- 为 `KnowledgeChunk` 增加允许为 null 的 pgvector Embedding 列。
- 明确多 Embedding 维度与 HNSW 索引的约束，不直接把现有配置能力写死为 1024 维。
- 先使用精确 pgvector 距离查询建立与 FAISS 的结果对照基线，再引入合适的 HNSW 索引。
