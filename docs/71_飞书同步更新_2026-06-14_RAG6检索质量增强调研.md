## 核心结论

不建议马上直接实现 Hybrid Search。

原因：

- 当前还没有完整检索日志详情页。
- 当前还没有可重复跑的小型评测集。
- 没有 baseline 时，BM25、Hybrid、RRF、Parent-Child 等优化无法判断是否真的有效。

更合理的顺序是：

```text
先可观测
再可评测
再优化检索算法
```

## 对标调研结论

主流 RAG 系统和平台通常采用组合式检索管线：

```text
文档解析质量
-> metadata 结构化
-> 多路召回
-> 融合排序
-> rerank 精排
-> 上下文压缩 / 引用
-> 检索日志与评测闭环
```

参考方向包括：

- Dify：知识库级配置、Hybrid Search、Rerank、Metadata Filter、多知识库节点。
- Anthropic Contextual Retrieval：Contextual Embeddings + Contextual BM25 + Rerank。
- OpenAI File Search / Vector Stores：托管向量库、ranker、score threshold、file_search result trace。
- LlamaIndex：Retriever、Metadata Filter、RRF、Recursive / Parent-Child Retrieval。
- RAGFlow：复杂文档解析、表格 / PDF / layout 质量、可追踪引用。
- Ragas：context precision、context recall、faithfulness 等 RAG 评测指标。

## 推荐实施路线

建议 RAG-6 按以下顺序做：

1. `RAG-6.0`：检索日志详情页 + 小型评测集。
2. `RAG-6.1`：Metadata schema + Metadata Filter。
3. `RAG-6.2`：多知识库检索。
4. `RAG-6.3`：BM25 / lexical retriever。
5. `RAG-6.4`：Hybrid Search + RRF。
6. `RAG-6.5`：Parent-Child / Recursive Retrieval。
7. `RAG-6.6`：Contextual Retrieval 实验。

第一轮建议做到 `RAG-6.4` 阶段性收尾。

## 为什么先做 RAG-6.0

`RAG-6.0` 最值得先做，因为它直接服务后续所有优化：

- 能回看每次检索的完整候选。
- 能比较 vector / rerank / 后续 BM25 / Hybrid 的效果。
- 能知道优化有没有提高 hit@k、MRR、context precision、context recall。
- 能让用户理解“为什么召回这些片段”。

这比直接实现 Hybrid 更稳，也更适合作为项目亮点：

```text
不是只接了 RAG，而是做了检索质量治理和评测闭环。
```

## 后续暂缓

以下方向暂缓：

- GraphRAG。
- 多模态图片向量检索。
- Agentic RAG 自动多轮检索。
- 大规模向量数据库迁移。

原因是当前项目还没有完成基础检索评测闭环，过早进入这些方向会增加复杂度，但很难证明收益。
