# Tool 执行状态语义与阶段 0 验收规范

更新时间：2026-09-11
阶段：阶段 0、阶段 1 已完成（同步状态机与失败传播）；阶段 1 未修改权限、Tool 范围或 Durable schema

## 1. 为什么需要这一阶段

当前项目已经具备受限 Tool Calling、DAG、Result Binding、Result Quality Gate、文件审批写入和低风险 Durable Runtime。但这些能力经历多轮迭代后，同一个“工具没有产生可用结果”的事实会分散表达为 `error`、`skipped`、`confirmation_required`、`quality invalid`、Trace event、Planner feedback 或 Durable Step status。

这在正常单工具调用时可工作，但会让以下问题缺少唯一答案：

- A 的结果不好时，B 是被阻断、换备用工具、请求澄清，还是转长任务？
- 多个并行 Tool 有一个失败时，Chat 是成功、部分成功，还是失败？
- 相同 Tool 在下一轮 Planner 中重复出现，是正常重规划，还是无意义循环？
- 用户看到“等待确认”时，系统到底是完成、失败，还是暂停？
- 达到同步循环上限时，为什么不能只是把 5 改大？

阶段 0 的目标是统一这些语义，不在这一阶段变更任何执行结果。

## 2. 当前真实实现边界

### 2.1 同步 Tool Workflow

当前同步链路是：

```text
Query Rewrite
-> Catalog / Scope 硬过滤
-> Candidate Selector
-> LLM Planner 或确定性 fallback
-> ToolPlan
-> ToolWorkflow DAG
-> ToolExecutor
-> Result Quality Gate
-> evidence / 最终回答
```

当前硬限制为：

```text
最多 5 轮 plan -> execute -> observe
每份 ToolPlan 最多 5 次 Tool Call
```

这不是“整个请求只能调用 5 个工具”：理论上五个 planning round 各自最多五次调用。但它仍是同步 HTTP 路径，没有 Run 级调用账本、全局墙钟预算、用户可见 handoff 或跨轮持久恢复，因此不能通过简单放大常量演变为长任务 Agent。

当前已具备：

- 无依赖 Tool 并发执行；
- `depends_on` 严格依赖；
- 受限 Result Binding 与绑定后的 Input Schema 重验；
- 低风险只读 fallback；
- `valid / uncertain / invalid` 质量门；
- 不合格 evidence 不进入最终 Answer Prompt；
- 安全的 Tool Quality Feedback 驱动有界 replan；
- Executor 侧 Schema、项目范围、ACL、凭据、风险和 SSRF 最终检查。

### 2.2 Durable Runtime

当前低风险、只读 Tool DAG 可进入：

```text
AgentRun / AgentStep / AgentCheckpoint / AgentArtifact
-> Outbox
-> Worker Claim
-> Lease + Heartbeat + Fencing
-> retry / DLQ / replay / reconcile
```

它已经能从持久化 Step 状态继续有限 DAG，并具备幂等、lease version、CAS/fencing、受控重放和对账能力。但当前 Chat 尚未能将验证后的计划显式转交给它；更没有“持久化 Planner 每轮继续思考”的功能。

### 2.3 Approval 与权限

工作区文件写入实际采用：

```text
PatchDraft -> Diff -> AgentApproval -> one-time challenge -> FileRevision CAS
```

`read_only / ask / full_workspace` 已由 Executor 生效。`full_workspace` 只会在当前项目、ACL、Diff 和 Revision CAS 保护下放行已有的工作区文件修改；它不是任意主机权限，也不放开 Shell、SQL、删除、外部发布或任意 HTTP 写。

## 3. 阶段 0 的统一三维模型

### 3.1 执行生命周期

| 状态 | 含义 | 是否允许严格依赖继续 | 当前或未来拥有者 |
| --- | --- | --- | --- |
| `pending` | 已在 Plan / Run 中声明，尚未满足执行条件 | 否 | Workflow / Durable Runtime |
| `ready` | 依赖满足、参数可解析，等待调度 | 否 | Workflow / Durable Runtime |
| `running` | Executor 或 Worker 已取得执行权 | 否 | Executor / Worker Lease |
| `succeeded` | 调用完成，且其结果已通过质量门 | 是，但还要求质量为 `valid` | Workflow / Durable Runtime |
| `failed` | 调用或 Provider 失败，未产生可用结果 | 否 | Workflow / Durable Runtime |
| `blocked` | 因依赖、策略、Schema、Scope 或重复调用而未执行 | 否 | Workflow / Executor |
| `waiting_approval` | 已生成持久化提案，等待用户确认；尚未执行副作用 | 否 | Approval Runtime |
| `cancelled` | 用户或上层 Run 已取消 | 否 | Chat / Runtime |
| `timed_out` | 已超出单调用或 Run 预算 | 否 | Budget / Runtime |

注意：`waiting_approval` 不是失败，也绝不是“修改已完成”。它是可持久化、可过期、可拒绝的暂停状态。

### 3.2 结果质量

| 质量状态 | 含义 | 能否作为最终回答 evidence | 能否给下游 Result Binding |
| --- | --- | --- | --- |
| `valid` | 满足 Tool 的业务质量合同 | 可以 | 可以 |
| `uncertain` | 请求可能成功，但时效、数量、置信度或关键字段不足 | 不可以 | 不可以 |
| `invalid` | 空结果、缺必需字段、结构错误、范围不匹配或未知非法状态 | 不可以 | 不可以 |
| `not_applicable` | 没有业务结果可评估，例如执行前被策略阻断 | 不可以 | 不可以 |

`valid_empty` 不作为新的质量状态。未来阶段 2 会用独立的 `result_semantics` 表达“没有命中也是一个合法业务答案”，例如空的文件搜索或空 Artifact 列表，避免把它和 Provider 返回空白/损坏响应混淆。

### 3.3 后续动作

| 动作 | 触发主体 | 语义 |
| --- | --- | --- |
| `continue` | 代码 | valid 上游结果允许严格依赖和最终 evidence 继续使用 |
| `fallback` | 代码 | 只允许当前预算内、低风险、只读、已审核的备用 Tool |
| `replan` | 代码触发，Planner 只提出新 Plan | 需要换 Tool、改参数或重新拆分；不得无意义重复同一失败指纹 |
| `clarify` | 代码 | 用户信息不足、写入需确认、结果不确定或风险不允许猜测 |
| `finalize_partial` | 代码 | 独立分支部分成功，使用 valid evidence 给出明确的不完整回答 |
| `handoff_durable` | 代码建议，用户确认 | 同步预算不适合继续且任务仍属低风险只读时，显式转交 Durable Runtime |
| `stop` | 代码 | 无可用证据、策略拒绝、取消、终态失败或预算不允许继续 |

LLM 不拥有上述状态转换或权限升级权。它只能在候选 Tool 范围内提出 Plan，并在安全 feedback 下建议下一步。

## 4. DAG 失败传播表

| A 的执行/质量结果 | B 对 A 有严格 `depends_on` | 与 A 独立的 C | Chat 级别行为 |
| --- | --- | --- | --- |
| `succeeded + valid` | B 可进入 `ready` | C 独立执行 | 正常继续 |
| `failed` 且可受限重规划 | B `blocked` | C 继续 | 安全 feedback 后 replan，或有 C evidence 时 partial |
| `invalid / uncertain` | B `blocked`，A evidence 不入 Prompt | C 继续 | fallback、replan 或 clarify，取决于代码 Policy |
| `blocked` | B `blocked` | C 继续 | 不允许模型绕过 Scope、Schema、权限或重复调用限制 |
| `waiting_approval` | B 保持不可执行 | C 可完成 | 返回待确认提案；不能声称写入完成 |
| `cancelled / timed_out` | B 不执行 | C 是否保留由 Run 终止 Policy 决定 | 同步收口；后续可建议显式 Durable handoff |

当前实现已经有“质量不合格阻断依赖”的核心行为。阶段 1 要做的是把它从局部集合、Trace 与 feedback 中收敛成统一 Step Outcome，并增加跨 replan 指纹账本。

## 5. Tool evidence 与 Prompt Injection 边界

当前系统已做三层基础防护：

1. Executor 在结果进入 Trace、Observation、Artifact 和 API 前做脱敏；
2. Prompt Builder 明确把 Tool、RAG、附件、Memory 视为不可信资料而非指令；
3. Executor 在真正副作用前重新执行 Schema、Scope、ACL、Credential、Risk 和 SSRF 检查。

后续仍需补的缺口是：同步链路会将成功 Tool 的部分 `display_text` 投影回下一轮 Planner。阶段 4 将改为按 Tool 类型白名单化事实投影，例如地图结果只给结构化地点/坐标/距离事实，网页研究只给受限来源摘要，而不是默认把整段外部文本作为 Planner 观察结果。

任何外部文本即使写着“忽略规则”“调用更高权限工具”“导出数据”，也只能被视为内容，不能改变：

```text
Tool allowlist
风险等级
用户/项目作用域
审批状态
预算
System 指令
```

## 6. 运行模式与 Budget 的目标模型

阶段 0 不新增模式、不改变当前五轮限制。后续阶段 5 将由代码和用户选择运行模式，而不是由模型自行延长循环：

| 模式 | 用途 | 可用能力 | 终止或转交方式 |
| --- | --- | --- | --- |
| `quick_chat` | 简单问答、少量实时信息 | 少量只读 Tool | 同步快速收口 |
| `guided_research` | 多来源资料研究 | 只读搜索、地图、Artifact | 受限同步；预算到达时可建议 Durable |
| `workspace_review` | 文件/知识库审阅 | 项目范围只读 Tool | 同步或显式 Durable |
| `edit_proposal` | 生成受控修改建议 | Diff / Approval / Revision CAS | 等待确认，不自动完成写入 |
| `durable_task` | 耗时、可恢复的低风险只读 DAG | 已审核低风险只读 Tool / Skill | Worker、Checkpoint、重试、DLQ、重放 |

每种模式未来都由 `ToolRunBudget` 限制，而不仅仅是最大轮数：

```text
max_planner_turns
max_total_tool_calls
max_concurrent_tool_calls
max_wall_time
per_tool_timeout
max_replans_per_call_fingerprint
max_evidence_chars / token budget
max_provider_token or cost budget（先预留）
max_result_artifact_size
```

达到预算时，系统只允许受控收口：给出部分回答、请求澄清，或经用户确认转交静态低风险只读 DAG。不会在后台静默无限运行。

## 9. 阶段 1 验收结果：同步 DAG 状态机与失败传播

完成时间：2026-09-11。

阶段 1 将阶段 0 定义的语义真正落到了**同步** Tool Workflow；它没有变更 Durable Runtime 的数据库模型、没有扩大 Tool 或权限范围，也没有放大同步 Chat 的五轮上限。

### 9.1 单 Step 的唯一终态记录

`ToolWorkflowService` 为每个已声明的同步调用生成不可变 `ToolStepOutcome`。该记录包含：

- `call_id`、`tool_key`、显示名和 `depends_on`；
- 执行状态、质量状态、受限质量原因、错误类别和代码决定的 `next_action`；
- 是否可作为最终 Answer evidence、耗时、可重试标记；
- `sha256(tool_key + canonical_arguments)` 形式的调用指纹，而不保留原始参数。

`ToolWorkflowResult.step_outcomes` 是同步 Step 终态的唯一真相源；Trace 的 `tool_workflow_step_state` / `tool_workflow_step_outcome` 和下一轮 Planner 的反馈都从它派生。每个正常 Step 会留下 `pending -> ready -> running -> terminal` 的可审计轨迹。超出单 Plan 调用预算、重复 `call_id`、环状/未解析依赖、Result Binding 失败和同 Plan 重复调用也会形成明确 `blocked` Outcome，而不是被静默忽略。

### 9.2 严格依赖与部分结果

严格 `depends_on` 现在只在上游同时满足下式时解锁：

```text
upstream.execution_status == succeeded
AND upstream.quality_status == valid
```

因此 `failed`、`blocked`、`waiting_approval`、`invalid`、`uncertain` 和 `not_applicable` 都会让下游停在 `blocked`，并记录 `dependency_not_succeeded`、`dependency_quality_not_usable` 或 `result_binding_invalid` 等确定类别；下游不会进入 Executor。独立分支仍可并行：一个分支失败不会取消另一个有效分支，Workflow 会以 `succeeded / partial / waiting_approval / failed / blocked / empty` 汇总本 Plan 的真实终态。

`partial` 只表示“存在可用的严格成功 evidence，同时另有失败、阻断或预算未执行的 Step”；它不表示所有任务已经完成。等待审批也不会被视为写入完成，更不会解锁依赖。

### 9.3 单次同步请求内的跨 replan 防重

`ExternalContextService.build_context()` 在一次 Chat 请求开始时创建内存态 `ToolRunCallLedger`，并把同一个账本传给该请求中的每一轮 Workflow。对同一 Tool Key 和规范化参数：

- 若前一轮为非可重试失败、`invalid / uncertain` 质量失败、等待审批，或确定性的策略/Schema/Binding 拒绝，后续 Planner 即使换了 `call_id` 也会在网络调用前得到 `blocked + duplicate_across_run`；
- 参数发生真实变化时仍允许重新规划；可重试的 Provider/传输异常、预算暂未执行、依赖暂未满足和环状依赖不会被该账本误当作永久重复；
- Executor 可能在调用前补默认参数，因此指纹在 Executor 规范化前计算并随 Step 传递，避免“同一 Planner 意图因 Adapter 改写参数而漏去重”。

该账本只活在当前同步 HTTP 请求内，请求结束即释放。它不是跨请求幂等、不是 Durable checkpoint、不是 Provider Exactly Once，也不替代 Durable Runtime 的 Lease、Fencing、Retry、DLQ 与受控重放。

### 9.4 Planner 安全反馈与验证

`ToolWorkflowFeedback` 现在只从非成功 Outcome 投影，最多传回受限原因、状态、依赖、错误类别和 `next_action`。Provider 原始异常、URL、远端正文、原始调用参数和未通过质量门的 sources 不会被回灌到 Planner。质量决策为 `replan` 时，外层会在既有五轮上限内显式增加一次规划；`clarify`、`block` 与审批边界不会被模型绕过。

本阶段验证：

- 定向 Workflow / Router / Executor / Quality / Integration / Durable 回归：`87` 项通过；
- 完整后端回归：`371` 项通过、`5` 项因 PostgreSQL/pgvector 专用环境未配置而跳过；
- `compileall` 和 `git diff --check` 通过；
- 新增覆盖：严格依赖质量阻断、普通失败阻断、等待审批、并发分支部分成功、预算阻断显式 Outcome、跨 replan 相同指纹阻断、不同参数允许重规划，以及 Executor 参数规范化后的稳定指纹。

下一步应进入阶段 2：覆盖全部默认 Tool 的 `ResultQualityContract`，并把“合法业务空结果”与损坏/不完整响应区分开；不应在尚无多维 Budget 与显式 Durable handoff 前直接提高同步轮数。

## 10. 2026-09-11 阶段 2.1 实施记录：本地只读 Tool 的合法空结果

阶段 2.1 没有新增 Tool、权限、数据库 schema 或同步循环次数，只落实“合法业务空结果”的最小可信闭环。`ToolCallResult` 记录受限的 `result_semantics`，其中 `empty_answer` 只能由 `workspace_file`、`agent_artifact` 本地受控 Adapter 在 Executor 白名单下写入；普通 evidence、远端 MCP metadata、Tool 正文和模型输出不能自行声明该语义。

`empty_answer` 通过质量门必须同时满足项目内可信 Provider 与 manifest 的 `allow_empty=true`。普通 `sources=[]` 即使配置了 `allow_empty=true` 仍为 `invalid`；未知语义也为 `invalid`。工作区文件 list/search/read 与 Artifact list 在正常无数据时返回固定、安全的 Source；内部只保留空集合或已知文件 ID 等最小 canonical 字段，不能伪造任何不存在的下游参数。Durable Artifact 另外持久化质量状态、原因、元数据和结果语义。

本小步的完整说明和验证结果见 [116_阶段2_1_本地Tool合法空结果质量闭环_2026-09-11.md](116_阶段2_1_本地Tool合法空结果质量闭环_2026-09-11.md)。阶段 2 的外部 Tavily / 高德字段合同、编辑提案 / 实际写入语义和 Tool-specific evaluator 仍未完成。

### 10.1 2026-09-14：编辑草案不解锁严格依赖

阶段 2 完成后，`approval_draft` 的边界进一步明确：它是“已生成、可审查、未写入”的产品状态，不是普通 Tool evidence。即使 Diff 预览通过自己的质量合同（`valid`、`applied=false`），`is_usable_tool_result()` 也会拒绝将它供普通严格依赖、Result Binding 或 Durable 成功 Artifact 消费。

同步 Workflow 则保留专用展示路径：将合格草案标为 `waiting_approval`、允许其 Diff 进入面向用户的受控 Prompt，并投影 `clarify` feedback；所有依赖该草案的普通 Step 都会被阻断。实际写入只能经过 `workspace.files.apply_edit` 创建的一次性审批 continuation 与 Revision CAS，不能靠下游 Plan 绕过该边界。

## 11. 2026-09-14 阶段 2.2A 实施记录：声明式语义 Profile

阶段 2.2A 将“业务字段校验不能每个 Tool 重复手写”收敛为三层：Provider Adapter/Mapper 负责归一化，固定能力 Profile 负责复用质量规则，只有特殊跨字段业务才保留 Tool-specific evaluator。`semantic_profile` 从代码白名单选择，`profile_mapping` 只声明有限 JSON Pointer，不允许动态脚本、模型规则或远端 metadata 改写质量结论。

本轮通用质量门检查：证据字段至少一个非空、身份字段至少一个非空；搜索/地图/天气/路线/POI Profile 必须存在结果集合，集合项必须是对象且具备非空业务证据；文件 Profile 可直接消费已展平 Source。路径最多 16 条、单路径最长 256 字符，解析集合和条目设有固定上限；未知 Profile、未知 mapping 字段、绝对/反向 item 路径、错误结构和超限均失败关闭。合法空集合仍须同时满足可信本地 Adapter 的 `empty_answer` 与 `allow_empty=true`。

通过两种不同 Provider 字段结构的离线 fixture，以及缺证据/身份、空集合、非对象集合项、最少条数、超限和 display_text 伪结构等回归，证明了“同类能力复用、字段差异由 mapping 吸收、安全边界由代码固定”。这不等同于 Tavily/高德生产合同已经完成；2.2B 需先锁定真实 Mapper fixture，再逐类接入 manifest。

## 12. 2026-09-14 阶段 2.2B/C 实施记录：真实 Provider 与请求一致性

本轮完成真实 Tavily/高德 MCP 响应接入。统一 payload 提取优先使用 `structuredContent`，再兼容 `content[].text` JSON；高德参数归一化与最终结果 Mapper 共用同一提取器。Tavily、geo、weather、distance、route、POI 均使用专用 Mapper，只保留有限 canonical 字段，缺少关键字段时返回空 Source 并由 Profile 失败关闭，不再使用任意 JSON 的 generic fallback 伪造业务成功。

阶段 2.2C 将 Executor Schema 校验后的 normalized arguments 作为受控 `request_context` 传入 Profile。天气城市、显式 geo 城市、路线起终点会做确定性比较；可选参数缺失时跳过对应规则，必填参数由 Input Schema 保证。该机制能捕获“结构合法但地点/路线与本次请求不一致”，但不宣称完成搜索语义相关性或完整地理空间证明。

真实只读烟测覆盖 Tavily 搜索、天气、geo、关键词/周边 POI、距离和驾车路线，均成功解析并达到 `quality_status=valid`。完整设计、字段表和脱敏测试口径见 [118_阶段2_2B_C_真实Provider映射与请求一致性_2026-09-14.md](118_阶段2_2B_C_真实Provider映射与请求一致性_2026-09-14.md)。

## 13. 2026-09-14 阶段 2 提交前复审

阶段 2 已按“全部默认 Tool”口径收口：16 个 manifest Tool 都具备质量合同。`artifact_list/artifact_read`、文件 list/search/read、`approval_draft` 和 `file_revision` 分别覆盖持久产物、只读文件、Diff 预览与实际 Revision。Diff 预览只能是 `approval_draft + applied=false`；等待用户确认不是写入成功；受控写入只有在 `file_id + revision_id + applied=true` 的完整 Revision 证据存在时才会以 `valid` 结束。
