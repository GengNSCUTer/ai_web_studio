## 1. 当前版本定位

当前项目已经不再是最初的 Streamlit 教学 demo，而是一个已经跑通基础闭环的：

**前后端分离式智能问答网页**

更准确地说，它现在已经具备：

- 登录 / 注册
- 用户级会话隔离
- 历史会话持久化
- 流式聊天
- 本地 Ollama 与 OpenAI-compatible 双 provider
- 设置面板
- 文件 / 图片上传入口
- `txt / md / pdf / docx` 文档解析支持
- 本地 PostgreSQL 持久化
- Markdown 渲染
- 代码块复制
- 会话重命名 / 删除
- 消息级失败 / 停止状态展示
- 图片缩略图展示
- 消息创建时间展示
- 每条会话右侧展开菜单
- 上传阶段类型校验与解析失败提示
- 第一版上下文治理已开始接入后端聊天链路
- 图片已真正进入多模态上下文
- 文档解析文本已真正进入当前轮上下文
- 上下文统计 / 裁剪提示已开始前端展示
- 会话级压缩摘要字段已接入数据库与后端链路
- 用户可配置模型上下文窗口
- 用户可切换上下文治理模式
- 后端动态上下文预算框架已接入主聊天链路
- 已实现“最近原始消息窗口 + 会话级滚动摘要”的双层上下文结构
- 前端默认中文文案已统一
- 已支持在设置页切换中文 / English
- 前端已提供按钮式上下文治理诊断弹层与提示区

但它还不是完整的“主流 AI 网页端成品”，目前仍处于：

**可用 MVP + 持续产品化整理阶段**

## 2. 当前已经完成的能力

下面按模块整理当前已完成项。

### 2.1 账户与用户体系

已完成：

- 用户注册
- 用户登录
- JWT 登录态
- 用户会话隔离
- 用户设置隔离
- 用户上传目录隔离

当前实现说明：

- 后端用户信息存储在 PostgreSQL `users` 表
- 密码以 `bcrypt` 哈希存储，不是明文

### 2.2 聊天主页面

已完成：

- 左侧历史会话列表
- 中间聊天线程
- 顶部当前会话标题与当前模型选择
- 底部输入区
- 新建会话
- 会话重命名
- 会话删除

已做过一轮 UI 调整：

- 左栏和上下区域已多次收窄
- 中间消息区有效宽度已明显增加
- 输入框支持自适应高度

### 2.3 多轮会话与持久化

已完成：

- 同一会话内多轮上下文拼接
- 消息持久化
- 会话持久化
- 自动生成会话标题

说明：

- 当前已经具备基础上下文治理能力
- 已支持最近若干轮消息保留、动态字符预算裁剪、会话级滚动摘要记忆层
- 长期记忆与更精细的压缩策略仍未完成

补充说明：

- 当前预算不再是单一固定值，而是根据用户设置的上下文窗口和上下文模式动态计算
- 不同 provider 的默认窗口不同：
  - `ollama` 默认 `100000`
  - `openai-compatible` 默认 `128000`
- 当前前端设置页已经可以直接修改这两个高层参数
- 当前滚动摘要采用“边界消息 id”管理已压缩历史，避免摘要和最近原始窗口重复注入
- 当前前端上下文诊断默认收起，只有在需要时通过“上下文”按钮展开浮层查看

### 2.4 流式输出

已完成：

- 主聊天链路切换到文本流方案
- 前端通过 `fetch + ReadableStream` 消费文本流
- 后端提供 `POST /api/chat/text-stream`
- 前端支持停止生成
- 前端支持“等待首 token”状态提示

当前结论：

- 已经不再使用旧的手写 SSE 主链路
- 当前以纯文本流为主

### 2.5 Provider 与模型配置

已完成：

- Provider 切换：
  - `ollama`
  - `openai-compatible`
- 支持设置：
  - `base_url`
  - `api_key`
  - `default_model`
  - `temperature`
  - `top_p`
  - `max_tokens`
  - `system_prompt`
- 设置保存后主页即时同步
- 支持“测试连接”
- 支持按当前表单配置实时拉模型列表

当前默认在线 provider 配置：

- `https://api.siliconflow.cn/v1`
- `Qwen/Qwen3.5-35B-A3B`

### 2.6 文件上传入口

已完成：

- 上传文件入口
- 上传图片入口
- 文件落盘保存
- 上传文件列表前端展示
- 附件发送后绑定到用户消息
- 历史消息显示附件记录
- 上传阶段前置拦截不支持文件类型
- 支持类型但解析失败时明确报错
- 图片缩略图展示
- 消息创建时间展示
- 消息失败 / 停止状态展示
- 每条会话支持展开菜单操作

当前未完成：

- 还没有做更细粒度的上下文预算分层
- 还没有做真正基于模型的高质量摘要压缩
- 还没有做长期记忆
- 还没有做附件内容的索引化展示

所以当前它属于：

**上传链路、附件入上下文链路、基础上下文治理链路都已跑通**

### 2.7 数据存储与运行环境

已完成：

- 用户态 PostgreSQL 跑通
- FastAPI 后端跑通
- Next.js 前端跑通
- 普通 Linux 用户权限下可独立启动
- 独立 Conda 环境可用

说明：

- 当前设计已经符合 06 文档里的主要技术路线
- 第一阶段没有用 Docker，这个决策仍然成立

## 4. 当前最合理的产品判断

如果把现在这个版本放到简历或项目说明里，更准确的说法应该是：

**一个支持用户登录、会话持久化、流式输出、多 provider 配置与本地部署的 ChatGPT 类智能问答网页 MVP。**

而不是：

- 完整多模态成品
- 完整知识库问答系统
- 完整 Agent 平台

这个判断很重要，因为它决定后续开发应该继续做“产品完成度”，而不是重新发散到 RAG 或 Agent。

---

## 5. 下一阶段开发优先级

接下来建议按 `P0.5 -> P1 -> P2` 推进，而不是同时开很多线。

### 5.1 `P0.5` 当前最应该先补的

这部分是“让它像一个成熟聊天产品”的关键补完。

优先建议按这个顺序做：

1. 把当前规则式滚动摘要升级为更高质量的模型摘要
2. 设计长期记忆雏形，明确跨轮和跨会话边界
3. 为上下文治理补缓存命中与复用策略
4. 继续做附件内容索引化展示与按需展开

1. 上下文统计与可视化
2. 历史消息摘要压缩升级
3. 会话级上下文裁剪策略优化
4. 附件索引化与按需展开
5. 会话搜索
6. 重新生成最后一条回答

原因：

- 这些都不要求重构底层架构
- 都直接提升长会话质量和可控性
- 都更接近成熟产品里的上下文治理路径

### 5.2 `P1` 第二优先级

这一层主要解决“附件真正可用”。

建议顺序：

1. 图片参与对话
2. 文本文件内容抽取并注入上下文
3. PDF / DOCX 基础解析
4. 附件预览与消息关联

说明：

- 如果你后续切回真正多模态本地模型，这一块价值会很高

### 5.3 当前下一阶段的主线

现在阶段已经从“P0 收尾”切换到：

**上下文治理专项**

主线目标是：

- 不让会话历史无限膨胀
- 不让附件全文无序抢占上下文
- 不让系统提示和用户消息相互污染
- 为长期记忆和缓存命中优化打基础
- 这会比先做 RAG 更符合当前产品定位

### 5.3 `P2` 后续增强

- 深浅主题
- 会话导出
- 设置面板继续细化
- provider 安全性优化
- 消息编辑与重试
- 长会话上下文压缩

## 6. 关于 RAG / Agent 的建议

目前不建议立刻把 RAG 或 Agent 并回这个网页主线，理由很简单：

- 当前聊天产品本身还没做扎实
- 附件能力还只是入口，不是真正可用
- 基础产品体验仍有不少细节待完善

更稳的路径是：

1. 先把当前 Web 聊天产品做完整
2. 再在此基础上加“文档问答模式”
3. 再继续扩展成 RAG / Agent 工作台

这样比“一上来就重新发散回 LangChain / LangGraph”更稳，也更适合做成长期项目。

---

## 7. 当前建议的最近迭代顺序

如果按最近几轮对话的实际推进节奏，建议你后续继续这样做：

1. 先整理现有代码，删掉旧残留链路和过时说明
2. 补 Markdown 渲染与代码块复制
3. 补失败态消息展示
4. 做会话搜索
5. 再做附件真正参与对话

这条路线既不会失焦，也不会把项目重新带回“教学 demo 堆功能”的方向。
