## 1. 当前版本定位

当前项目已经不再是最初的 Streamlit 教学 demo，而是一个已经跑通基础闭环的：

**前后端分离式智能问答网页**

更准确地说，它现在已经具备：

- 登录 / 注册
- 用户级会话隔离
- 历史会话持久化
- 流式聊天
- 本地 Ollama 与 OpenAI-compatible 双 provider
- 设置面板
- 文件 / 图片上传入口
- `txt / md / pdf / docx` 文档解析支持
- 本地 PostgreSQL 持久化
- Markdown 渲染
- 代码块复制
- 会话重命名 / 删除
- 消息级失败 / 停止状态展示
- 图片缩略图展示
- 消息创建时间展示
- 每条会话右侧展开菜单
- 上传阶段类型校验与解析失败提示
- 第一版上下文治理已开始接入后端聊天链路
- 图片已真正进入多模态上下文
- 文档解析文本已真正进入当前轮上下文
- 上下文统计 / 裁剪提示已开始前端展示
- 会话级压缩摘要字段已接入数据库与后端链路
- 用户可配置模型上下文窗口
- 用户可切换上下文治理模式
- 后端动态上下文预算框架已接入主聊天链路
- 已实现“最近原始消息窗口 + 会话级滚动摘要”的双层上下文结构
- 已实现模型驱动滚动摘要刷新，摘要失败时自动回退到规则摘要
- 已实现手动长期记忆 MVP：记忆新增、启停、删除、预算注入和诊断展示
- 已实现模型建议记忆 v1：从当前会话提取候选长期记忆，由用户确认后保存
- 已实现规则级记忆去重、冲突提示和来源追踪
- 已实现长期记忆来源会话可视化：记忆卡片显示来源会话，并可点击跳转到对应历史会话
- 已实现缓存友好型 Prompt 结构 v1：新增 `ContextPromptBuilder`，固定 system prompt、长期记忆、会话摘要、最近历史、当前附件的拼装顺序
- 已调整上下文治理裁剪策略：优先保留稳定 system 前缀，再裁剪历史消息，避免长会话挤掉关键上下文层
- 上下文诊断面板已补充 Prompt 模板版本、provider 模板、模型族、上下文层级和注入消息统计
- 已实现附件索引化与按需展开 v1：当前轮文档会被切块、按问题关键词打分，并只注入预算内相关片段

- 已实现 prompt prefix hash 与缓存复用观测 v1：后端会记录稳定前缀 hash，并返回是否复用上一轮稳定前缀的启发式结果
- 已修复重复点击“提取建议记忆”时的前端卡住体感：增加请求中防重入、旧候选清空、90 秒超时兜底

- 前端默认中文文案已统一
- 已支持在设置页切换中文 / English
- 前端已提供按钮式上下文治理诊断弹层与提示区
- 已完成 `P1` 首批产品补完：

  - 最后一条回答重生成

  - 会话归档 / 置顶
- 已完成 `P1` 第二轮交互修补：

  - 输入区待发送附件已支持点击预览，不需要先发出消息才能查看
  - 会话切换期间不再把短时间内仍在生成的回答直接标记为失败
  - 会话切回后，若服务端仍记录为 `streaming`，前端会显示等待态而不是空白回答框
- 已完成 `P1` 第三批产品能力：
  - 深色 / 浅色主题：支持跟随系统、浅色、深色，并通过用户设置持久化
  - 会话导出：左侧会话菜单支持导出 Markdown / JSON
  - Prompt 模板：支持新增、编辑、删除、设为默认，并可应用到 System Prompt
- 已完成 `P1` 第三批修复：

但它还不是完整的“主流 AI 网页端成品”，目前仍处于：

**可用 MVP + 持续产品化整理阶段**

## 2. 当前已经完成的能力

下面按模块整理当前已完成项。

### 2.1 账户与用户体系

已完成：

- 用户注册
- 用户登录
- JWT 登录态
- 用户会话隔离
- 用户设置隔离
- 用户上传目录隔离

当前实现说明：

- 后端用户信息存储在 PostgreSQL `users` 表
- 密码以 `bcrypt` 哈希存储，不是明文

### 2.2 聊天主页面

已完成：

- 左侧历史会话列表
- 中间聊天线程
- 顶部当前会话标题与当前模型选择
- 底部输入区
- 新建会话
- 会话重命名
- 会话删除

已做过一轮 UI 调整：

- 左栏和上下区域已多次收窄
- 中间消息区有效宽度已明显增加
- 输入框支持自适应高度
- 设置面板已改为左侧分区导航，避免模型、上下文、长期记忆和系统提示全部堆在一个页面里
- 最后一条用户消息的“编辑后重答”已改为主流网页端风格的消息内联编辑，而不是浏览器弹窗

### 2.3 多轮会话与持久化

已完成：

- 同一会话内多轮上下文拼接
- 消息持久化
- 会话持久化
- 自动生成会话标题

说明：

- 当前已经具备基础上下文治理能力
- 已支持最近若干轮消息保留、动态字符预算裁剪、会话级滚动摘要记忆层
- 已支持模型摘要优先、规则摘要兜底的摘要压缩策略
- 已支持手动长期记忆，用户可以在设置面板维护跨会话注入的稳定记忆
- 已支持模型建议记忆，用户可以从当前会话提取候选记忆并确认保存
- 已支持规则级记忆冲突检测与来源追踪
- 已支持长期记忆来源会话展示和跳转
- 语义级记忆去重和来源消息级高亮定位仍未完成

补充说明：

- 当前预算不再是单一固定值，而是根据用户设置的上下文窗口和上下文模式动态计算
- 不同 provider 的默认窗口不同：
  - `ollama` 默认 `100000`
  - `openai-compatible` 默认 `128000`
- 当前前端设置页已经可以直接修改这两个高层参数
- 当前滚动摘要采用“边界消息 id”管理已压缩历史，避免摘要和最近原始窗口重复注入
- 当前滚动摘要刷新会调用当前 provider/model 做一次非流式摘要生成；如果模型调用失败，则不阻断聊天，自动使用规则式结构摘要
- 当前长期记忆按用户隔离存储，只有启用的记忆会在聊天请求中注入
- 当前前端上下文诊断默认收起，只有在需要时通过“上下文”按钮展开浮层查看
- 当前上下文诊断不落数据库，只在前端按会话缓存最近一次结果；这样切换会话再切回仍能查看，但刷新整页后不会恢复
- 后续如果要做持久化，目标不是“存一份最后诊断结果”，而是升级为“按回答粒度的消息级诊断追踪”

### 2.4 流式输出

已完成：

- 主聊天链路切换到文本流方案
- 前端通过 `fetch + ReadableStream` 消费文本流
- 后端提供 `POST /api/chat/text-stream`
- 前端支持停止生成
- 前端支持“等待首 token”状态提示

当前结论：

- 已经不再使用旧的手写 SSE 主链路
- 当前以纯文本流为主
- 重新生成与编辑后重答两条消息级重放链路，也已统一复用同一套流式主链路

补充稳定性说明：

- 后端对历史消息列表中的 `streaming` 助手消息不再做“无条件失败兜底”
- 当前改为“超时后才判定为失败”的策略，优先避免用户切换会话时把仍在进行中的回答误伤成失败态

### 2.5 Provider 与模型配置

已完成：

- Provider 切换：
  - `ollama`
  - `openai-compatible`
- 支持设置：
  - `base_url`
  - `api_key`
  - `default_model`
  - `temperature`
  - `top_p`
  - `max_tokens`
  - `system_prompt`
- 设置保存后主页即时同步
- 支持“测试连接”
- 支持按当前表单配置实时拉模型列表

当前默认在线 provider 配置：

- `https://api.siliconflow.cn/v1`
- `Qwen/Qwen3.5-35B-A3B`

### 2.6 文件上传入口

已完成：

- 上传文件入口
- 上传图片入口
- 文件落盘保存
- 上传文件列表前端展示
- 待发送附件点击预览
- 附件发送后绑定到用户消息

- 图片缩略图展示

- 消息失败 / 停止状态展示
- 每条会话支持展开菜单操作

## 4. 当前最合理的产品判断

如果把现在这个版本放到简历或项目说明里，更准确的说法应该是：

**一个支持用户登录、会话持久化、流式输出、多 provider 配置与本地部署的 ChatGPT 类智能问答网页 MVP。**

而不是：

- 完整多模态成品
- 完整知识库问答系统
- 完整 Agent 平台

这个判断很重要，因为它决定后续开发应该继续做“产品完成度”，而不是重新发散到 RAG 或 Agent。

## 5. 下一阶段开发优先级

接下来更合理的顺序已经可以调整为：

**以上下文治理第一阶段阶段性收口为界，主线转入 `P1` 的产品能力补完。**

### 5.1 `P0.5` 当前最应该先补的

这部分是“让它像一个成熟聊天产品”的关键补完。

优先建议按这个顺序做：

1. 语义级记忆去重
2. 来源消息级高亮定位
3. 附件片段持久化索引
4. 更精细的缓存命中 / 成本观测
5. 跨历史附件召回

原因：

- 这几项属于上下文治理的“第二阶段深挖项”，价值很高，但已经不再阻塞 `P1`
- 当前第一阶段闭环已经形成：动态预算、滚动摘要、长期记忆、附件片段筛选、可视化诊断、tokenizer 观测、稳定前缀观测已经串起来了
- 因此下一步可以把更多精力转向 `P1` 的产品化能力

### 5.2 `P1` 第二优先级

这一层主要解决“通用产品能力补完”。

建议顺序：

1. 深色 / 浅色主题
2. 前端参数设置面板更细化
3. 会话导出 / 分享
4. 更完整的消息级操作体验打磨

### 5.3 当前下一阶段的主线

现在阶段更准确地说，是：

**`P0` 已基本完成，`P0.5` 第一阶段已阶段性收口，下一步主线建议切到 `P1`。**

主线目标是：

- `P1` 主线：补完会话搜索、重生成、编辑后重答、附件预览、主题、会话归档等产品能力
- `P1` 首批已完成，当前下一步更适合继续补主题、设置面板细化，以及更完整的消息级操作体验
- 上下文治理副线：继续推进语义级记忆去重、来源消息级定位、附件索引持久化和更细粒度缓存观测
- 上下文诊断持久化当前不作为主线任务；后续若做，按“assistant message 级诊断记录”方案推进
- 保持现有上下文治理框架稳定，不要为了继续深挖而打断主产品节奏
- 这会比现在直接跳 `P2` 或回头发散到 RAG / Agent 更符合当前产品定位

### 5.3 `P2` 后续增强

- 深浅主题
- 会话导出
- 设置面板继续细化
- provider 安全性优化

## 6. 关于 RAG / Agent 的建议

目前不建议立刻把 RAG 或 Agent 并回这个网页主线，理由很简单：

- 当前聊天产品本身还没做扎实
- 附件能力还只是入口，不是真正可用
- 基础产品体验仍有不少细节待完善

更稳的路径是：

1. 先把当前 Web 聊天产品做完整
2. 再在此基础上加“文档问答模式”
3. 再继续扩展成 RAG / Agent 工作台

这样比“一上来就重新发散回 LangChain / LangGraph”更稳，也更适合做成长期项目。

- 图片 / 文档进入上下文
  当前支持当前轮附件，后续要升级为长期知识库和跨历史附件召回。

- 长期记忆
  当前支持手动记忆和模型建议记忆，后续要做语义级去重、冲突合并和来源消息定位。

- 上下文诊断
  当前能看本轮统计，后续要考虑按 assistant message 持久化诊断记录。

- 重生成 / 编辑重答
  当前支持最后一轮，后续如果要支持任意历史轮次，需要设计分支会话或截断重放策略。

### 8.2 接下来建议优先实现的产品功能

建议下一阶段按这个顺序推进：

1. Project / 工作区雏形
2. 会话分享
3. Prompt 模板增强：变量占位符、分类、搜索、快捷插入
4. 会话导出增强：导出范围选择、附件打包、分享链接
5. 消息级定位和高亮

这些功能的价值是提升“像一个成熟 AI 网页端”的完整度，也方便后续写简历和演示。

### 8.3 接下来建议优先实现的上下文治理功能

上下文治理继续推进时，建议按这个顺序：

1. 附件片段持久化索引
2. 跨历史附件召回
3. 语义级记忆去重
4. 来源消息级定位
5. 摘要质量观测增强
6. provider 真实缓存命中观测

这些功能不一定要连续全部做完，但它们共同构成“上下文治理第二阶段”。

### 8.4 长远优化方向

长远可以分为 5 条线：

1. 产品线
   做主题、导出、分享、工作区、Prompt 模板、多模型比较。

2. 知识线
   做文档库、chunk 持久化、embedding 检索、重排、引用溯源。

3. 记忆线
   做语义级长期记忆、来源消息高亮、冲突合并、自动记忆策略。

4. 性能线
   做 prompt cache 观测、首 token 延迟分析、后台任务、附件索引复用。

5. 工程线
   做 Alembic 迁移、结构化日志、API key 加密、对象存储、Docker 化部署。

### 8.5 下一次建议开工项

如果继续按“先产品完成度，再深水区”的节奏，下一次最建议做：

1. Project / 工作区雏形
2. 会话分享
3. 附件片段持久化索引设计

其中前两个偏产品体验，第三个是后续 RAG 和跨历史附件召回的技术地基。
