## 1. 当前版本定位

当前项目已经不再是最初的 Streamlit 教学 demo，而是一个已经跑通基础闭环的：

**前后端分离式智能问答网页**

- 登录 / 注册
- 用户级会话隔离
- 历史会话持久化
- 流式聊天
- 本地 Ollama 与 OpenAI-compatible 双 provider
- 设置面板
- 文件 / 图片上传入口
- `txt / md / pdf / docx` 文档解析支持

## 2. 当前已经完成的能力

下面按模块整理当前已完成项。

### 2.2 聊天主页面

已完成：

- 左侧历史会话列表
- 中间聊天线程
- 顶部当前会话标题与当前模型选择
- 底部输入区
- 新建会话
- 会话重命名

已做过一轮 UI 调整：

- 左栏和上下区域已多次收窄
- 中间消息区有效宽度已明显增加
- 输入框支持自适应高度
- 设置面板已改为左侧分区导航，避免模型、上下文、长期记忆和系统提示全部堆在一个页面里
- 最后一条用户消息的“编辑后重答”已改为主流网页端风格的消息内联编辑，而不是浏览器弹窗

### 2.3 多轮会话与持久化

已完成：

- 同一会话内多轮上下文拼接
- 消息持久化
- 会话持久化
- 自动生成会话标题

说明：

- 当前已经具备基础上下文治理能力
- 已支持最近若干轮消息保留、动态字符预算裁剪、会话级滚动摘要记忆层
- 已支持模型摘要优先、规则摘要兜底的摘要压缩策略
- 已支持手动长期记忆，用户可以在设置面板维护跨会话注入的稳定记忆
- 已支持模型建议记忆，用户可以从当前会话提取候选记忆并确认保存
- 已支持规则级记忆冲突检测与来源追踪
- 已支持长期记忆来源会话展示和跳转
- 语义级记忆去重和来源消息级高亮定位仍未完成

补充说明：

- 当前预算不再是单一固定值，而是根据用户设置的上下文窗口和上下文模式动态计算
- 不同 provider 的默认窗口不同：
  - `ollama` 默认 `100000`
  - `openai-compatible` 默认 `128000`
- 当前前端设置页已经可以直接修改这两个高层参数
- 当前滚动摘要采用“边界消息 id”管理已压缩历史，避免摘要和最近原始窗口重复注入
- 当前滚动摘要刷新会调用当前 provider/model 做一次非流式摘要生成；如果模型调用失败，则不阻断聊天，自动使用规则式结构摘要
- 当前长期记忆按用户隔离存储，只有启用的记忆会在聊天请求中注入
- 当前前端上下文诊断默认收起，只有在需要时通过“上下文”按钮展开浮层查看
- 当前上下文诊断不落数据库，只在前端按会话缓存最近一次结果；这样切换会话再切回仍能查看，但刷新整页后不会恢复
- 后续如果要做持久化，目标不是“存一份最后诊断结果”，而是升级为“按回答粒度的消息级诊断追踪”

### 2.4 流式输出

已完成：

- 主聊天链路切换到文本流方案
- 前端通过 `fetch + ReadableStream` 消费文本流
- 后端提供 `POST /api/chat/text-stream`
- 前端支持停止生成
- 前端支持“等待首 token”状态提示

当前结论：

- 已经不再使用旧的手写 SSE 主链路
- 当前以纯文本流为主
- 重新生成与编辑后重答两条消息级重放链路，也已统一复用同一套流式主链路

补充稳定性说明：

- 后端对历史消息列表中的 `streaming` 助手消息不再做“无条件失败兜底”
- 当前改为“超时后才判定为失败”的策略，优先避免用户切换会话时把仍在进行中的回答误伤成失败态

  - `ollama`

### 2.6 文件上传入口

## 4. 当前最合理的产品判断

如果把现在这个版本放到简历或项目说明里，更准确的说法应该是：

**一个支持用户登录、会话持久化、流式输出、多 provider 配置与本地部署的 ChatGPT 类智能问答网页 MVP。**

而不是：

- 完整多模态成品
- 完整知识库问答系统
- 完整 Agent 平台

这个判断很重要，因为它决定后续开发应该继续做“产品完成度”，而不是重新发散到 RAG 或 Agent。

## 5. 下一阶段开发优先级

接下来更合理的顺序已经可以调整为：

**以上下文治理第一阶段阶段性收口为界，主线转入 `P1` 的产品能力补完。**

### 5.1 `P0.5` 当前最应该先补的

这部分是“让它像一个成熟聊天产品”的关键补完。

优先建议按这个顺序做：

1. 语义级记忆去重
2. 来源消息级高亮定位
3. 附件片段持久化索引
4. 更精细的缓存命中 / 成本观测
5. 跨历史附件召回

原因：

- 这几项属于上下文治理的“第二阶段深挖项”，价值很高，但已经不再阻塞 `P1`
- 当前第一阶段闭环已经形成：动态预算、滚动摘要、长期记忆、附件片段筛选、可视化诊断、tokenizer 观测、稳定前缀观测已经串起来了

## 10. 2026-05-19 深度思考与联网搜索规划更新

本次未开发代码，只做调研和方案设计。新增规划来自两个产品缺口：

- 深度思考按钮
- 联网搜索按钮

### 10.1 当前项目相关基线

当前代码里已经具备这些基础：

- 多 provider：Ollama + OpenAI-compatible
- 文本流式输出
- 图片和文件进入上下文
- 动态上下文预算
- 上下文诊断面板
- Prompt prefix hash 观测
- 工作区、Prompt 模板、分享、导出、长期记忆

但也有两个明确缺口：

- 当前“思考中”只是 UI 等待首 token，不是模型 reasoning。
- 当前没有外部搜索服务，Prompt 也没有 web search context layer。

后端现状：

- Ollama 调用中固定 `think=false`。
- OpenAI-compatible 调用中固定 `enable_thinking=false`。
- 流式接口当前只输出纯文本，无法区分 reasoning、搜索状态、来源和最终回答。

### 10.2 深度思考调研结论

调研结论：

1. 深度思考必须 provider-specific。
   Ollama 使用 `think`；SiliconFlow/Qwen 一类 OpenAI-compatible 常用 `enable_thinking` 和 `thinking_budget`；Claude、Gemini、OpenAI reasoning 模型又有各自不同的 reasoning / thinking 配置。

2. 前端不能承诺展示完整思维链。
   有些 provider 返回完整可见 thinking，有些只返回 summary，有些启用推理但不返回可见 reasoning。产品文案应该区分“思考过程”和“思考摘要”。

3. 当前纯文本流式协议不够。
   后续要展示 thinking，需要把流升级为 NDJSON/SSE event，包括 `reasoning_delta` 和 `answer_delta`。

### 10.3 联网搜索调研结论

调研结论：

1. Provider 原生 web search 不适合作为第一版主线。
   OpenAI Responses API 有原生 Web Search Tool，但它绑定 OpenAI API；本地 Ollama 和 SiliconFlow Chat Completions 不一定支持。

2. 第一版更适合做应用层搜索。
   后端调用 Tavily 搜索，把结果清洗后注入上下文，模型只负责基于搜索资料回答。这样 Ollama 和在线 API 都能复用。

3. 搜索结果必须可追踪。
   回答下方应展示来源卡片，上下文面板应展示 query、结果数、token 占用、裁剪原因。后续知识库引用也可以复用这一套 Source Citation 组件。

### 10.4 新增近期实施建议

建议把这两个能力作为 `P2.5` 插入到 P3 知识库前后：

1. 深度思考按钮 MVP
   原因：当前后端已经明确关闭 thinking，改造入口清晰；可先完成 provider profile、Ollama `think`、SiliconFlow `enable_thinking`、reasoning 展示。

2. 联网搜索按钮 MVP
   原因：它能显著提升产品完整度，并为后续知识库引用、Trace 和 Source Citation 打基础；第一版用 Tavily。

3. 再继续 P3 附件片段持久化索引
   原因：知识库主线仍然是长期价值最高的方向，联网搜索和 reasoning 是聊天体验补齐，不应替代知识库主线。

### 10.5 下一步可开工项

如果下一轮开始开发，建议从“深度思考按钮 MVP”开始，拆成：

1. 后端 schema 增加 `thinking_enabled` 和 `thinking_budget`。
2. 增加 provider capability profile。
3. Ollama 支持 `think=true`。
4. SiliconFlow/Qwen 支持 `enable_thinking=true`。
5. 新增 events-stream，区分 `reasoning_delta` 和 `answer_delta`。
6. 前端增加“深度思考”按钮和折叠 reasoning panel。
7. 持久化 reasoning 内容或 summary。

完成后再做“联网搜索按钮 MVP”：

1. 设置页增加 Tavily API key、搜索深度、top_k。
2. 后端新增 `WebSearchService` 和 `TavilySearchProvider`。
3. 聊天请求增加 `web_search_enabled`。
4. Prompt Builder 新增 `web_search_results` 上下文层。
5. 前端展示搜索状态和来源卡片。
6. 搜索结果进入上下文诊断和导出。

### 10.6 风险提醒

- `enable_thinking` 不是 OpenAI 标准字段，不能对所有 OpenAI-compatible provider 默认发送。
- thinking 会增加延迟和 token 成本，默认应关闭。
- 联网搜索会把用户问题发送给第三方服务，需要前端提示隐私边界。
- 搜索结果可能错误或过时，回答中必须保留来源引用。
- 如果不升级流式协议，前端很难优雅展示搜索状态、reasoning 和最终回答。

## 11. 2026-05-19 外部信息源与工具增强架构修正

在进一步调研主流 AI 网页端和 MCP / 搜索 API 后，对第 10 节的“联网搜索按钮”做了架构修正。

### 11.1 修正原因

原先只把联网搜索规划成 Tavily Search 有两个问题：

1. 过窄。
   用户真正需要的不是 Tavily，而是外部实时信息能力。天气、地图、路线、POI、金融、网页、知识库、MCP 都属于外部信息源。

2. 容易变成屎山。
   如果每新增一个工具都在聊天接口里加 if/else，后续会出现 `web_search / weather / amap / mcp / knowledge / browser` 混在一起的聊天主流程，难以测试和维护。

### 11.2 主流产品对照

调研后主流方案可分为：

- 模型厂商原生搜索：OpenAI web_search、Gemini Google Search grounding、Claude web search。
- 带搜索的模型服务：Perplexity / Sonar。
- 应用层搜索 API：Tavily、Brave Search、SerpAPI、Exa。
- 垂直工具 / MCP：天气、地图、金融、GitHub、数据库、飞书、高德地图 MCP 等。

AI Web Studio 不应绑定其中一个方案，而应该用统一外部信息源架构承接它们。

### 11.3 新架构判断

`联网搜索` 按钮在产品层可以保留，但技术上它应该触发：

```text

```

```text

```

```text

```

## 12. 2026-05-19 工具路由与意图识别补充

本次补充解决一个关键问题：

> 开启联网搜索后，系统不能每轮调用所有外部工具。

### 12.1 判断结论

`联网搜索` 按钮应该只是权限开关：

```text
external_context_allowed = true
```

它不等于：

```text
call_all_tools = true
```

真正调用哪个工具，应由 Tool Router 判断。

### 12.2 参考结论

Ragent 的实现值得参考：

- 它用 `IntentTree` 管理意图。
- 意图节点分 `KB / SYSTEM / MCP`。
- 叶子节点有 description、examples、promptTemplate、mcpToolId。
- LLM 对叶子节点打分。
- 后续按分数和类型过滤。
- MCP 工具参数提取独立做。

Dify 和 Coze 的思路也类似：

- 工具有 description 和参数 schema。
- Agent / Workflow 根据工具定义选择调用。
- 不会每轮把所有工具都调用一遍。
- 都需要最大迭代次数、权限、工具配置和调用日志。

### 12.3 我们项目的推荐策略

采用三段式：

1. 规则门控
   快速判断明显不需要工具、明显天气、明显地图、明显网页、明显知识库的问题。

2. 轻量 LLM Router
   当规则不确定或候选超过一个时，让模型输出结构化 ToolPlan。

3. 后端强校验
   校验工具是否启用、是否允许外部工具、参数是否符合 schema、是否超过最大工具数、是否只读。

### 12.4 默认调用策略

建议默认：

- 用户未开启联网搜索：不调用外部网络工具。
- 用户开启联网搜索：允许调用外部工具，但不保证一定调用。
- 工作区知识库和当前附件不属于外网，可以独立使用。
- 默认最多调用 1 个外部工具。
- 明确多意图时最多调用 2 个。
- Tavily 是默认 web fallback，不是所有问题的默认第一步。

示例：

```text
你好 -> no_tool
解释这段代码 -> no_tool
今天广州天气 -> weather
广州南站附近咖啡店 -> map
LangChain 最新版本 -> web_search
我上传的文档怎么配置数据库 -> knowledge
明天去深圳，天气怎么样，附近有地铁吗 -> weather + map
```

### 12.5 近期实现顺序修正

新增 Tool Router 后，建议顺序再细化为：

1. 结构化事件流
2. ToolPlan / ToolRouteCandidate 数据结构
3. RuleBasedToolRouter
4. 深度思考按钮 MVP
5. ExternalSource / ExternalContextChannel 抽象
6. Web Search channel 接入 ToolPlan
7. Weather channel 接入 ToolPlan
8. Map channel 接入 ToolPlan
9. Tool route run 持久化
10. LLM Tool Router
11. MCP Client / MCP Tool Router
12. P3 工作区知识库索引和跨历史召回

### 12.6 短期不做

- 不做无限多轮 Agent 工具循环。
- 不把所有工具一次性暴露给模型。
- 不做无阈值并发工具调用。
- 不接有副作用工具。
- 不让前端放很多工具按钮。

前端保持简单，复杂路由放到后端。

## 14. 2026-05-19 联网搜索天气失败与按钮状态修复

本次修复两个实际测试问题：

- 打开 `联网搜索` 后询问 `今天深圳天气怎么样`，前端显示回答失败。
- 回答结束后，`联网搜索` 按钮状态自动取消。

### 14.1 失败原因

高德天气工具本身正常，`今天深圳天气怎么样` 可以返回深圳天气来源。真正失败发生在后续调用硅基流动 OpenAI-compatible 模型时。

原因是原 Prompt Builder 会把系统提示、长期记忆、会话摘要、外部信息源分别构造成多个 `system` message。硅基流动接口在开启外部信息源后返回：

```text
System message must be at the beginning.
```

因此本次把所有系统层合并成一个 leading `system` message，外部信息源、长期记忆、摘要都作为该 system message 内部的分层文本。

### 14.2 按钮状态修复

`ChatThread` 会根据会话消息变化被 `key={threadKey}` 重新挂载，原来 `联网搜索` 和 `深度思考` 状态放在 `ChatThread` 内部，所以刷新会话后会回到默认关闭。

本次把两个 toggle 状态提升到 `ChatApp`，即使 `ChatThread` 重挂载，按钮状态也会保留。

### 14.3 验证

- 高德天气工具：`今天深圳天气怎么样` 返回 1 个 weather 来源。
- 硅基流动模型：合并 system message 后可正常流式返回深圳天气回答。
- 后端编译通过：`python -m compileall app`。
- 前端构建通过：`npm run build`。

## 15. 2026-05-19 Tavily 搜索 Header Overflow 修复

本次继续修复 `联网搜索` 下问 `美国现任总统是谁` 仍失败的问题。

### 15.1 失败原因

Tavily 搜索和模型调用本身正常，FastAPI 直连 `/api/chat/events-stream` 可以返回正确答案。真正失败发生在 Next.js `/api/chat` 代理层：

```text
UND_ERR_HEADERS_OVERFLOW
```

原因是后端把完整 `external_sources` 同时放进了：

- NDJSON body 的 `tool_sources` 事件
- `x-context-details` 响应头

Tavily 搜索结果较长时，`x-context-details` 经过 base64 编码后过大，超过 Node/undici 的响应头限制，导致 Next 代理直接返回 500。

### 15.2 修复方式

- 完整外部来源继续通过 NDJSON body 的 `tool_sources` 事件发送。
- `x-context-details` 只保留用于上下文诊断的小摘要。
- 对 header 中的 attachment chunk 和 external source 做数量限制和字段截断。

### 15.3 验证

- 临时端口启动当前后端代码后，`美国现任总统是谁` 返回 200。
- `x-context-details` header 从可能溢出的完整来源压缩到约 7KB。
- NDJSON body 仍保留完整 `tool_sources` 和流式 `answer_delta`。

  2. 如果 `lives` 为空，则用高德地理编码解析地点。
  3. 从 geocode 中提取 `adcode / district / city` 作为候选值重试天气查询。

## 2026-06-11：RAG-5 知识库检索卡住修复

问题现象：

- 在聊天页选择知识库后提问，例如“介绍一下 skill route”，前端长时间停留在“模型正在思考，请稍候...”。
- 该状态发生在首 token 返回前，说明请求可能卡在知识库检索、prompt 组装或模型首包之前。

直接原因：

- RAG-5 第一版把 `knowledge_base_name` 等上下文诊断字段放入 `x-context-stats` 响应头。
- 当知识库名包含中文时，Starlette 在构造 HTTP header 时会按 `latin-1` 编码。
- 中文无法编码为 `latin-1`，导致后端抛出 `UnicodeEncodeError`，StreamingResponse 构造失败。
- 前端请求停在首 token 前，因此表现为“模型正在思考，请稍候...”，但实际没有进入正常流式输出。

同时发现的稳定性问题：

- 聊天链路会在模型调用前同步执行知识库检索。
- 知识库检索需要调用 embedding 和可选 rerank。
- 之前 OpenAI-compatible embedding 没有显式 timeout；rerank/httpx 也复用了 `OLLAMA_REQUEST_TIMEOUT_SECONDS=600`，网络或 provider 慢时仍可能拖住整轮聊天。

已修复：

- `x-context-stats` 改为 ASCII-safe 的 `json64:` base64 JSON 格式。
- 前端 `parseContextStatsHeader()` 已兼容新 `json64:` 格式，并保留旧 `a=b;c=d` 格式解析。
- 新增知识库模型调用超时配置：
  - `KNOWLEDGE_MODEL_REQUEST_TIMEOUT_SECONDS=60`
  - `KNOWLEDGE_CONTEXT_TIMEOUT_SECONDS=25`
- `KnowledgeContextService` 对整段聊天内知识库检索使用 `asyncio.wait_for()`：
  - 超时后返回上下文 notice。
  - 不让知识库检索拖死聊天。
  - 记录 `knowledge_retrieval_latency_ms`。
- `KnowledgeEmbeddingService` 的 OpenAI-compatible client 显式设置 timeout。
- `KnowledgeRerankService` / Ollama embedding 的 httpx client 改用知识库模型请求 timeout。
- 前端上下文诊断面板新增“知识库检索耗时”。
- 新增单测覆盖中文 stats header 编码和慢检索超时降级。
- 后端已重启，当前监听 `127.0.0.1:32007`。
