# 上下文治理研究与实施路线

本文档用于系统梳理“上下文治理”这一块到底是什么、主流大厂现在怎么做、哪些能力适合我们当前项目，以及后续应该如何逐步落地。

写作时间：2026-05-08  
适用项目：`/disk2/gengnan/ai_web_studio`

---

## 1. 先给结论：上下文治理不是“截断历史消息”这么简单

很多人一开始理解“上下文治理”，会以为就是：

- 历史消息太长了，就删掉前面的几轮
- 或者做个摘要，把前面的内容压缩一下

这其实只覆盖了很小一部分。

更完整地看，上下文治理至少包含 5 个层面：

1. **会话状态管理**
   也就是当前这一轮到底把哪些消息带给模型。

2. **上下文压缩 / 裁剪 / 编辑**
   也就是当历史越来越长时，哪些内容保留原文，哪些做摘要，哪些直接删除。

3. **记忆体系**
   也就是哪些信息不应该只留在当前会话里，而应该沉淀为跨轮、跨会话的长期信息。

4. **缓存命中优化**
   也就是如何让重复的前缀、重复的文件、重复的系统提示不要每次都重新 prefill。

5. **推理服务侧优化**
   也就是 KV Cache、Prefix Cache、Chunked Prefill、Disaggregated Prefill、MLA 这类更底层的性能工程。

所以，后面你如果把“上下文治理”写进简历，不能只写“做了消息截断”。  
真正更像样的说法应该是：

- 设计多层上下文架构
- 构建短期上下文 + 摘要记忆 + 长期记忆
- 通过稳定前缀、缓存复用和上下文压缩降低时延与成本
- 提高长会话质量稳定性和缓存命中率

## 2. 为什么上下文治理重要

### 2.1 因为“长上下文”不等于“可以无脑塞”

现在很多模型都支持超长上下文：

- Claude API 文档写到部分场景可用 **1M token context window**，常规主力模型也长期有 **200K** 级别窗口  
  参考：<https://platform.claude.com/docs/en/build-with-claude/context-windows>
- Qwen 官方已经公开了 **Qwen2.5-Turbo 1M**、**Qwen2.5-1M**  
  参考：<https://qwenlm.github.io/blog/qwen2.5-turbo/>  
  参考：<https://qwenlm.github.io/blog/qwen2.5-1m/>
- Gemini 这边也一直在强化长上下文与上下文缓存能力  
  参考：<https://ai.google.dev/gemini-api/docs/caching>

但“窗口大”不代表应该把所有东西都原样塞进去。原因有三类：

- **成本问题**：输入 token 越多，计费越高
- **时延问题**：prefill 越长，首 token 越慢
- **质量问题**：上下文越长，噪音越大，模型更容易失焦

所以真正成熟的系统，不是“尽量塞满”，而是：

- 尽量只给模型当前真正需要的上下文
- 让重复内容尽量走缓存
- 让过旧但仍有价值的信息变成摘要或长期记忆

### 2.2 因为大模型的“工作记忆”本质上是昂贵且有限的

Anthropic 在上下文编辑文档里讲得很直接：  
上下文是有限资源，而且收益递减；无关内容会降低模型专注力。  
参考：<https://platform.claude.com/docs/en/build-with-claude/context-editing>

这句话非常重要。

它意味着：

- 上下文不是越多越好
- 上下文治理不是“省钱技巧”，也是“质量技巧”

## 3. 先统一几个核心概念

如果不把这些概念分清楚，后面很容易混。

### 3.1 Context Window

模型单次请求能“看到”的总 token 范围。  
它一般包含：

- 输入 token
- 输出 token
- 某些模型内部的 reasoning token

### 3.2 Prefill 和 Decode

可以把一次生成分成两个阶段理解：

- **Prefill**：先把整段输入跑一遍，建立注意力状态
- **Decode**：然后逐 token 生成输出

当输入很长时，慢的往往不是输出，而是 prefill。

### 3.3 KV Cache

在 Transformer 推理里，前面 token 的 key/value 会缓存下来，避免后续重复计算。  
这就是大家常说的 KV Cache。

它有两个层面：

- **单次请求内的 KV Cache**：为了逐 token decode 加速
- **跨请求可复用的 KV Cache / Prefix Cache**：为了让相同前缀不用重新 prefill

### 3.4 Prompt Cache / Prefix Cache

如果两个请求前面一大段内容完全相同，那么这部分理论上可以直接复用。

常见命名：

- Prompt Caching
- Context Caching
- Prefix Caching

本质都和“重复前缀复用”有关。

### 3.5 短期上下文 vs 长期记忆

这是最容易混淆的一组概念。

#### 短期上下文

指当前会话里，模型这一次回答时直接看到的内容：

- 最近几轮消息
- 本轮上传的文件片段
- 当前任务相关的摘要

#### 长期记忆

指不一定每轮都原样带入，但在需要时可以被召回的信息：

- 用户偏好
- 用户身份信息
- 长期目标
- 某个项目的稳定背景
- 过往会话中沉淀出来的重要事实

### 3.6 摘要压缩 vs RAG 检索

这两个也要分清。

#### 摘要压缩

是把已有对话历史压缩成更短的结构化或非结构化摘要。

#### RAG 检索

是把信息放到外部知识库，需要时再检索召回。

两者可以一起用，但不是同一个东西。

## 4. 主流大厂现在大致怎么做

这一节不追求“所有细节完全一致”，而是抽出主流方向。

### 4.1 OpenAI：状态管理 + 自动 Prompt Caching

#### 4.1.1 会话状态：Responses API / Conversations API / `previous_response_id`

OpenAI 官方现在把“conversation state”单独作为一类能力来讲。  
它给了三种典型做法：

- 你自己手动回放历史消息
- 使用 **Responses API + `previous_response_id`** 串接前后响应
- 使用 **Conversations API** 把对话状态持久化成长生命周期对象

官方文档原意很明确：

- 如果你手动管消息，那就是你自己承担上下文构造逻辑
- 如果你用 `previous_response_id` 或 `conversation`，平台能帮你减少自己拼历史的工作

参考：

- <https://developers.openai.com/api/docs/guides/conversation-state>

其中比较关键的点：

- `previous_response_id` 可以把新请求挂到上一条响应后面
- `conversation` 则更像“持久化会话对象”
- 但即便用了 `previous_response_id`，**历史 token 仍然会计入输入 token 计费**

这说明一件事：

> “状态托管”不等于“成本自动消失”。

它主要解决的是**工程复杂度**，不自动解决**上下文过长**。

#### 4.1.2 Prompt Caching：自动开启、前缀精确匹配

OpenAI 的 Prompt Caching 是目前非常值得学习的一套思路：

- 对 **1024 token 及以上** 的 prompt 自动启用
- 只对 **exact prefix match** 生效
- 静态内容放前面，动态内容放后面
- 支持用 `prompt_cache_key` 影响路由，提高命中率

官方文档还给了几个很关键的细节：

- 路由通常会基于 prompt 前缀 hash，典型会看前 **256 tokens**
- 相同 prefix + `prompt_cache_key` 组合如果请求频率太高，可能溢出到更多机器，导致缓存效果下降
- in-memory retention 通常是 **5 到 10 分钟 inactivity**，最长到 **1 小时**
- extended retention 最长可到 **24 小时**
- `usage.prompt_tokens_details.cached_tokens` 可以直接观测命中量

参考：

- <https://developers.openai.com/api/docs/guides/prompt-caching>

对我们最有启发的不是 API 细节，而是设计原则：

1. **让稳定前缀尽量长**
2. **让变化内容尽量靠后**
3. **缓存治理本质上先是 prompt 结构治理**

#### 4.1.3 OpenAI 在“记忆”上的产品思路

ChatGPT 产品里的 Memory 也很值得借鉴。  
OpenAI Help 文档把记忆分成两层：

- Saved memories
- Chat history reference

这个区分很像：

- **显式长期记忆**
- **从历史聊天中动态抽取的隐式记忆**

参考：

- <https://help.openai.com/en/articles/8983136-what-is-memory>

这对我们项目的启发是：

- “长期记忆”不要直接等于“全部历史会话”
- 更合理的做法是把历史信息分层：
  - 明确可持久化的用户画像
  - 可变的历史偏好
  - 当前会话里的工作记忆

### 4.2 Anthropic：提示结构、Prompt Caching、Compaction、Context Editing

Anthropic 这块资料很系统，而且对“上下文治理”讲得比很多厂商更直白。

#### 4.2.1 Long Context Prompting：长文档放上面，问题放后面

Anthropic 官方建议：

- 长文档、大输入放 prompt 顶部
- 查询问题放后面
- 多文档最好加 XML 标签组织结构
- 长文档任务里可以先让模型提取引用，再回答

官方甚至提到，在复杂多文档输入里，“query 放后面”可以显著改善效果。  
参考：

- <https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#long-context-prompting>

这件事看起来像提示工程，其实也是上下文治理。

因为它说明：

- 不只是“带哪些内容”重要
- “这些内容按什么顺序摆”也重要

#### 4.2.2 Prompt Caching：自动缓存 / 显式断点 / TTL

Anthropic 的 Prompt Caching 也很成熟：

- 可以做 **automatic caching**
- 也可以做 **explicit cache breakpoints**
- 默认 TTL 是 **5 分钟**
- 也支持 **1 小时** TTL
- 缓存覆盖的是 `tools -> system -> messages` 这一整段前缀层级

官方还提到：

- 自动缓存会把缓存点移动到最后一个可缓存块
- 适合多轮长对话
- 命中要求依然是严格前缀一致

参考：

- <https://platform.claude.com/docs/en/build-with-claude/prompt-caching>

这个思路和 OpenAI 很一致：  
**大厂对缓存命中的核心原则几乎都是“稳定前缀 + 精确匹配”**。

#### 4.2.3 Compaction：服务端自动摘要压缩

Anthropic 最近非常值得关注的一点，是把**上下文压缩做成了平台能力**。

它的 Compaction 文档描述的是：

- 当输入 token 接近阈值时
- 服务端自动生成当前对话摘要
- 生成一个 `compaction` block
- 后续请求只需要沿着这个摘要继续

也就是说，它不是让开发者每次自己手写“摘要策略”，而是把：

- 触发条件
- 摘要生成
- 替换旧上下文

做成了系统能力。

参考：

- <https://platform.claude.com/docs/en/build-with-claude/compaction>

这个趋势非常值得注意：

> “上下文压缩”正在从应用层手工逻辑，变成模型平台原生能力。

#### 4.2.4 Context Editing：不是只会摘要，也可以选择性删除

Anthropic 还有一块更细的能力：**Context Editing**。

它强调一个核心思想：

> 上下文治理不只是为了节省 token，更是为了主动策划模型现在该看什么。

它目前支持的方向包括：

- 清理旧的 tool results
- 清理 thinking blocks
- 对长期 agent 工作流做更细粒度的上下文修剪

参考：

- <https://platform.claude.com/docs/en/build-with-claude/context-editing>

这对我们特别有启发。

因为我们后面如果做通用智能问答系统，会出现很多“只在一小段时间有价值”的内容：

- 某轮解析出来的大文件片段
- 某次图片 OCR 结果
- 某次工具执行日志

这些内容未必应该永远保留在工作上下文里。

#### 4.2.5 用独立上下文隔离子任务

Anthropic 在 Claude Code 文档里还强调：

- subagents 使用**独立上下文窗口**
- 这样可以防止主对话被无关细节污染

参考：

- <https://docs.anthropic.com/en/docs/claude-code/sub-agents>

这本质上是另一种上下文治理：

- 不是把所有内容都塞进一个窗口
- 而是把任务拆到多个局部上下文中处理

这对后续如果我们做 Agent / 工作流系统也很关键。

### 4.3 Google Gemini：隐式缓存 + 显式缓存 + 多模态缓存

Gemini / Vertex AI 这一套，对“缓存”描述得非常工程化。

#### 4.3.1 Gemini API：Implicit + Explicit

Gemini API 文档明确分两种缓存：

- **Implicit caching**
  默认开启，命中会自动省钱，但不保证一定命中

- **Explicit caching**
  需要你主动创建 cache，对成本收益更可控

官方还给了几个关键参数：

- Gemini 2.5/3 系列上 implicit caching 默认开启
- 显式缓存如果不设置 TTL，默认 **1 小时**
- 最小缓存 token 数因模型而异，例如 1024 或 4096

参考：

- <https://ai.google.dev/gemini-api/docs/caching>

#### 4.3.2 Vertex AI：缓存命中折扣非常明确

Vertex AI 文档更进一步，把“缓存收益”讲得非常具体：

- implicit caching 默认开启
- cached tokens 相比标准输入 token，可拿到明显折扣
- 文档里写到 implicit caching 对 cached tokens 提供 **90% discount**
- explicit caching 也提供确定性折扣
- 默认 cache expiration 是 **60 分钟**

参考：

- <https://cloud.google.com/vertex-ai/generative-ai/docs/context-cache/context-cache-overview>

这里最值得学的是：

- Google 把缓存当成一等公民能力
- 而且支持缓存大文本、音频、视频等多模态上下文

也就是说，在多模态场景里，上下文治理不只是文本历史管理。

#### 4.3.3 Gemini 的设计启发

对我们来说，Gemini 这套最重要的启发有两条：

1. **多模态资源也应该考虑缓存复用**
   比如同一张图、同一个 PDF、多轮围绕同一文件追问，不能每次都从零开始。

2. **缓存应该可观测**
   不是“有缓存就行”，而是要能看见：
   - cached token 数
   - 命中率
   - 时延变化

### 4.4 Qwen / 阿里云百炼：长上下文 + Context Cache + 运行时裁剪

Qwen 这边对我们尤其相关，因为你后面大概率还会继续用本地 Qwen / Qwen 系列 API。

#### 4.4.1 Qwen 官方：长上下文能力持续强化

Qwen 官方博客已经公开：

- Qwen2.5-Turbo 支持到 **1M context**
- Qwen2.5-1M 开源模型也支持 **1M**
- 同时在长文本任务上强调不希望明显损伤短文本能力

参考：

- <https://qwenlm.github.io/blog/qwen2.5-turbo/>
- <https://qwenlm.github.io/blog/qwen2.5-1m/>

这说明一个趋势：

- 厂商确实在不断把“硬窗口”做大
- 但这不代表应用侧可以不做治理

#### 4.4.2 百炼 Context Cache：显式缓存 + 隐式缓存都提供

阿里云百炼的 Context Cache 文档非常实用，尤其适合国内工程落地参考。

它给出的模式是：

- **显式缓存**
  - 创建缓存 token 按输入单价的 **125%**
  - 命中缓存 token 按输入单价的 **10%**
  - 最少 **1024 token**
  - 有效期 **5 分钟，命中后重置**

- **隐式缓存**
  - 自动开启
  - 基于前缀匹配
  - 命中不是 100%，系统 best-effort
  - 小于 **256 token** 的内容不会被缓存

并且 OpenAI 兼容返回里可以直接看：

- `usage.prompt_tokens_details.cached_tokens`

参考：

- <https://help.aliyun.com/zh/model-studio/context-cache>

这套设计和 OpenAI / Anthropic / Gemini 的共同点非常明显：

- 稳定前缀
- 精确匹配
- 观测 cached token
- 区分自动模式与显式模式

#### 4.4.3 Qwen-Agent：运行时上下文裁剪策略值得直接借鉴

Qwen-Agent 目前文档里已经公开了一套比较清晰的上下文治理流程：

- S1：先删最老的完整对话轮
- S2：再从最老的 tool-response 开始折叠 / 摘要
- S3：再删更旧的 tool-call step
- S4：再处理最近一步里的 tool-response
- S5：最后才截断 user query 或 final response

参考：

- <https://qwenlm.github.io/Qwen-Agent/en/guide/core_moduls/context/>

这套策略很有价值，因为它体现了一个成熟原则：

> 不同类型上下文的“保留优先级”应该不同。

也就是说：

- 用户原始问题，优先级通常高
- 最终回答，优先级通常高
- 中间过程、工具返回、环境信息，优先级通常低一些

这对我们后续做“文件问答 + 多轮会话 + 可能接工具”非常重要。

### 4.5 DeepSeek：磁盘上下文缓存 + 从架构层缩小 KV Cache

DeepSeek 在“缓存”和“长上下文推理成本”上有两层值得关注。

#### 4.5.1 DeepSeek API：默认磁盘 Context Caching

DeepSeek API 文档写得很清楚：

- Context Caching on Disk 默认开启
- 后续请求如果和之前请求有重叠前缀，会直接从磁盘缓存取
- 返回里可以看：
  - `prompt_cache_hit_tokens`
  - `prompt_cache_miss_tokens`

参考：

- <https://api-docs.deepseek.com/guides/kv_cache/>

更细一点，它还强调了：

- 由于 Sliding Window Attention 机制，缓存命中不是简单“任意子串匹配”
- 一个请求能否命中，取决于对应 prefix 是否已经被持久化成完整缓存单元
- 系统会在请求边界、公共前缀检测、固定 token 间隔等位置持久化 cache unit

这比很多“只说 prefix cache”更工程化。

#### 4.5.2 DeepSeek-V2：从模型结构上降低 KV Cache 压力

DeepSeek-V2 技术报告中一个非常关键的点是 **MLA (Multi-head Latent Attention)**。

官方仓库介绍里提到：

- MLA 利用低秩 key-value 压缩减少 inference-time KV cache 瓶颈
- DeepSeek-V2 相比前代把 KV cache 降低了 **93.3%**

参考：

- <https://github.com/deepseek-ai/DeepSeek-V2>

这说明一个很重要的事实：

> 上下文治理不全是应用层逻辑，模型架构本身也在参与治理。

如果模型天然更省 KV Cache，那么：

- 长上下文更便宜
- prefix cache 更容易存
- 多并发时显存压力更可控

### 4.6 开源推理框架：vLLM 已经把“前缀缓存 / Prefill 调度”产品化

如果以后你不满足于 Ollama，而想进一步做性能工程，vLLM 是必须理解的一层。

#### 4.6.1 Automatic Prefix Caching

vLLM 官方已经把 APC（Automatic Prefix Caching）做成标准能力：

- 复用相同前缀的 KV Cache
- 只缓存完整 block
- 用哈希组织 block
- 有 eviction 逻辑

参考：

- <https://docs.vllm.ai/en/latest/design/prefix_caching/>

这件事很关键，因为它说明：

- 未来如果我们把后端从 Ollama 切到 vLLM
- 就不只是“换个推理框架”
- 而是会真正获得更多“上下文治理可控性”

#### 4.6.2 Disaggregated Prefill

vLLM 还有一个非常重要的工程能力：**Disaggregated Prefill**。

官方解释得很直接：

- 把 prefill 和 decode 放在不同实例
- 可以分别调 TTFT 和 ITL
- 有助于控制 tail latency

参考：

- <https://docs.vllm.ai/en/latest/features/disagg_prefill/>

#### 4.6.3 Chunked Prefill

另外还有 Chunked Prefill：

- 把长 prefill 切成小块
- 更好地和 decode 请求混排
- 改善调度

参考：

- <https://docs.vllm.ai/en/v0.4.2/models/performance.html>

所以，站在系统工程角度看：

- 上下文治理 = 应用层裁剪 + 服务层缓存 + 调度层优化

### 4.7 工具层最佳实践：Codex 和 Claude Code 怎么做上下文治理

这一节非常重要。

前面 4.1 到 4.6 更多是在讲模型平台、API 平台、推理服务。

但你现在特别关心的是另外一层：

> 为什么 Codex 和 Claude Code 这类“真正能长期干活的编码代理”看起来更稳定？

我的判断是，它们做得更好的地方，不只是模型本身，而是：

- 上下文分层更清楚
- 上下文注入更克制
- 有明确的按需加载机制
- 有成体系的记忆机制
- 更擅长把噪音隔离到子线程 / 子代理

下面分开讲。

#### 4.7.1 Codex：更像“分层记忆 + 按需技能 + 子代理隔离”

##### A. Codex 的技能系统本身就是上下文治理

Codex 官方技能文档里有一个非常关键的设计：progressive disclosure。

它不是一上来就把所有技能全文都塞进上下文，而是：

- 先只放每个 skill 的：
  - 名称
  - 描述
  - 文件路径
- 只有当 Codex 判断要用这个 skill 时，才加载对应的完整 `SKILL.md`

官方还明确写了：

- 初始 skills 列表会被限制在大约上下文窗口的 2%
- 如果窗口大小未知，就限制在 8,000 字符
- 如果技能太多，会先压缩 description
- 再多的话，甚至会省略一部分技能

这其实是非常典型的上下文治理思想：

> 不把“可能会用到的全部知识”一次性注入，而是先注入轻量索引，再按需展开。

这和我们后面做附件索引、记忆索引、规则索引的思路非常一致。

##### B. Codex 的子代理不是“多开几个模型”，而是主动防上下文污染

Codex 的 subagents 概念页写得很直接：

- 主线程里如果堆太多探索日志、测试日志、堆栈、命令输出
- 会出现 context pollution
- 长时间会出现 context rot

它给出的解决办法是：

- 把 noisy work 移出主线程
- 让主代理保留需求、约束、决策和最终输出
- 让子代理去跑：
  - exploration
  - tests
  - triage
  - summarization
- 子代理返回的是摘要，不是原始长日志

这件事非常值得学：

> 它不是在一个大窗口里拼命治理噪音，而是在架构上减少噪音进入主窗口。

##### C. Codex 的长期记忆是后台两阶段流水线

这也是我这次查资料时最有价值的发现之一。

OpenAI 官方 Codex 文档只讲了一个较高层的 memories 概念：

- memories 默认关闭
- 可以开启
- Chronicle 会帮助 Codex 从最近工作上下文恢复线索

但更深入看 OpenAI 官方公开仓库 `openai/codex` 里的 memory pipeline README，会发现它不是一个“把对话全文存起来”的粗糙实现，而是明确分成两阶段：

**Phase 1: Rollout Extraction**

- 对近期 eligible rollouts 做逐线程提取
- 每个 rollout 抽出结构化 memory
- 输出 raw_memory、rollout_summary 等
- 会做 secret redaction
- 并行执行，有并发上限和重试回退

**Phase 2: Global Consolidation**

- 把阶段 1 的结果做全局整合
- 只允许一个全局 consolidation job 同时运行
- 根据 usage_count、last_usage、generated_at 这类信息挑选保留内容
- 同步到本地 memory artifacts，例如 raw_memories.md、rollout_summaries/
- 再启动一个内部 consolidation sub-agent 来做更高层整合

这说明 Codex 在记忆上已经明确采用了：

1. 先逐线程抽取
2. 再全局合并
3. 按使用频率和最近性做保留
4. 把记忆从聊天全文转换成结构化 artifacts

##### D. Codex 对我们最有启发的 4 点

1. 技能要按需加载，不要把所有规则全文常驻上下文。
2. 噪音最好在架构层隔离，而不是事后再清理。
3. 记忆应该先做局部抽取，再做全局 consolidation。
4. 长期记忆应以可维护的 artifacts 存在，而不是只有一段大摘要。

#### 4.7.2 Claude Code：更像“层级指令系统 + 会话压缩 + 显式上下文控制”

Claude Code 在上下文治理上最大的特点是：

- 文档更透明
- 用户可控性更强
- 文件层级、会话压缩、命令面板都做得非常明确

##### A. CLAUDE.md 层级本身就是上下文分层

Claude Code 官方 memory 文档说明了几类持久指令来源：

- managed policy
- 项目级 `CLAUDE.md`
- 用户级 `~/.claude/CLAUDE.md`
- 可选的 `CLAUDE.local.md`

并且它有非常明确的加载规则：

- 从当前目录向上递归查找 `CLAUDE.md`
- 祖先目录的文件先加载
- 更靠近当前工作目录的文件后加载
- 子目录下的 `CLAUDE.md` 不会在启动时全量加载，而是当 Claude 读到该子目录文件时再按需加载

这个机制天然实现了：

- 全局规则
- 仓库规则
- 子目录规则
- 按需生效

这和我们后面如果做项目级系统提示、模块级规则、某类附件处理规则的设计几乎一一对应。

##### B. Claude Code 的 auto memory 是“轻量入口 + 详情按需读取”

Claude Code 的 auto memory 文档有几个关键点：

- memory 存在 `~/.claude/projects/<project>/memory/`
- 启动时只加载 `MEMORY.md` 的前 200 行或前 25KB
- 详细 topic files 不在启动时加载
- 需要时 Claude 再通过文件工具读取
- `/memory` 可以直接查看和管理这些 memory files

这说明它采用的不是“全记忆一次性喂给模型”，而是：

- 启动时只给一个轻量 memory 入口
- 更细的内容按需读

##### C. Claude Code 对“上下文过长”提供了显式操作面板

Claude Code 的文档里有一套非常明确的显式控制：

- `/compact`
  用于压缩更早对话，释放上下文空间
- `/clear`
  用于直接清空当前会话上下文
- `/context`
  用于查看当前上下文消耗构成

官方错误文档甚至会直接建议：

- prompt 太长时先跑 `/compact`
- 看 `/context` 找出是 system prompt、tools、memory files 还是 messages 占得太多
- 禁用不需要的 MCP servers
- 裁剪过大的 `CLAUDE.md`

这说明 Claude Code 不只是“内部自动做点优化”，而是把上下文治理变成了：

- 可观察
- 可解释
- 可干预

##### D. Claude Code 也把技能和子代理当作上下文隔离工具

Claude Code 文档里提到：

- skills 可以只在被调用或被判断相关时加载
- 如果 skill 配置 `context: fork`
- 它会在 subagent 中运行
- 这个 subagent 不会访问你的当前 conversation history

这点很关键：

> Claude Code 不是只会在主线程里压缩，它也会把某些工作明确地 fork 到隔离上下文里。

#### 4.7.3 Codex 和 Claude Code 的共同点

这两个工具虽然实现风格不同，但核心思路其实非常一致。

##### 共同点 1：都不追求全量常驻上下文

它们都强调：

- 先放轻量索引 / 规则入口
- 真正的大块内容按需展开

##### 共同点 2：都在主动隔离噪音

它们都明确意识到：

- exploration notes
- tool logs
- test logs
- intermediate outputs

这些内容会污染主线程。

##### 共同点 3：都把“记忆”做成独立层

Codex 走的是：

- per-rollout extraction
- global consolidation

Claude Code 走的是：

- CLAUDE.md 层级规则
- auto memory files
- topic files on demand

##### 共同点 4：都非常重视只在需要时注入上下文

这是你后面设计自己系统时最该学的一条。

#### 4.7.4 Codex 和 Claude Code 的差异

##### Codex 更像

- 面向代理工作流的上下文工程
- 更强调：
  - skills progressive disclosure
  - subagent parallelism
  - rollout memory extraction
  - global consolidation pipeline

##### Claude Code 更像

- 面向开发者直接操控的上下文操作系统
- 更强调：
  - 文件层级规则
  - `/compact`、`/clear`、`/context`
  - auto memory 的本地可编辑性
  - 用户对上下文构成的显式可见性

#### 4.7.5 对我们项目最值得直接学的 6 个原则

1. 按需加载，不要把所有知识、规则、附件全文常驻上下文。
2. 噪音隔离，中间过程、日志、解析详情不要直接污染主聊天线程。
3. 分层记忆，会话历史、摘要记忆、长期记忆、规则文件应该分开。
4. 局部提取 + 全局整合，不要每次只维护一个大摘要。
5. 显式可观测，开发者应该能看见当前上下文主要由哪些部分构成。
6. 预算意识，工具定义、规则文件、技能、附件、历史消息都应视作上下文预算的一部分。

#### 4.7.6 对我们当前 ai_web_studio 的直接启发

如果把 Codex 和 Claude Code 的思路映射回我们当前项目，我建议后面逐步做到：

1. 把上下文拆成 5 层：
   - system / rules
   - 最近消息
   - 会话摘要
   - 附件内容
   - 长期记忆
2. 把附件从“全文直塞”改成“索引 + 按需展开”
3. 给上下文增加可视化面板，类似 Claude Code 的 `/context`
4. 把长会话压缩做成后台任务，更接近 Codex 的 extraction + consolidation 思路
5. 后续如果接工具 / agent，把探索类、日志类、分析类任务放到隔离子上下文

## 5. 现在行业里的主流技术路线，可以概括成什么

综合上面的资料，当前主流路线大致可以归纳为 6 层。

### 5.1 第一层：稳定前缀设计

这是最基础的一层。

目标是：

- system prompt 尽量稳定
- 工具定义尽量稳定
- 文件正文 / 资料正文尽量稳定
- 用户的变化提问放到后面

因为如果前缀经常抖动：

- OpenAI/Claude/Gemini/百炼/DeepSeek 的缓存都很难命中

### 5.2 第二层：短期上下文窗口治理

也就是当前会话到底带哪些消息。

常见做法：

- 最近 N 轮保留原文
- 更早历史做摘要
- 工具结果单独折叠
- 超大附件只保留相关片段

### 5.3 第三层：服务端 / 推理层缓存

包括：

- prompt caching
- prefix caching
- context cache
- disk cache
- KV cache 复用

这层主要目标是：

- 降成本
- 降 TTFT
- 提升吞吐

### 5.4 第四层：摘要压缩 / Compaction / Context Editing

这层主要是：

- 让上下文长度不会无限增长
- 同时尽量保留关键语义

常见做法：

- 对话摘要
- 文件摘要
- 工具结果清理
- 中间思考过程清理
- 老轮次内容折叠

### 5.5 第五层：长期记忆系统

这层主要解决跨会话问题。

常见拆法可以是：

- **Profile Memory**
  用户稳定偏好、身份、语言习惯

- **Task Memory**
  当前长期任务目标、工作区背景

- **Episode Memory**
  某次会话里沉淀出的关键事实

- **Artifact Memory**
  文件、图片、摘要、结构化提取结果

### 5.6 第六层：观测与评估

这层特别重要，但很多个人项目容易忽略。

至少应该观测：

- 每次请求输入 token / 输出 token
- 首 token 时延
- 总时延
- 命中缓存 token 数
- 摘要触发次数
- 历史裁剪次数
- 长会话质量回归情况

如果没有观测，你就很难证明“治理真的有效”。

## 6. 对我们当前项目来说，最值得学的不是“谁窗口最大”，而是这些原则

### 6.1 原则一：上下文要分层，不要一锅端

至少要分成：

- 当前轮输入
- 最近几轮原始消息
- 历史摘要
- 附件内容
- 长期记忆

### 6.2 原则二：不是所有内容都值得永久留在工作上下文

尤其是：

- 大文件全文
- 图片 OCR 中间结果
- 某轮工具返回日志
- 模型中间过程

这些内容很多时候是“曾经有用”，不等于“应该一直存在”。

### 6.3 原则三：缓存命中率取决于 prompt 结构纪律

缓存不是魔法。

如果你每次都：

- 改 system prompt
- 改消息顺序
- 改文件拼接方式
- 动态插入一堆前缀噪音

那缓存命中会很差。

### 6.4 原则四：长期记忆不等于保存全部聊天记录

真正好的长期记忆应该是：

- 少而精
- 可更新
- 可删除
- 可解释

而不是把所有旧消息硬塞给模型。

### 6.5 原则五：先做“可观测”，再做“高阶优化”

如果连：

- 当前输入 token 有多少
- 哪些内容在膨胀
- 缓存是否命中

都不知道，那后面的压缩、缓存、记忆优化就容易变成拍脑袋。

## 7. 回到我们当前项目：现在处在哪个阶段

我们当前 `ai_web_studio` 的上下文能力，严格说还比较初级。

### 7.1 现在已经有的

- 多轮聊天
- 历史消息持久化
- 图片进入当前轮多模态输入
- 文件解析后进入当前轮上下文
- 用户级会话隔离

### 7.2 现在还缺的

- 历史消息分层治理
- 长会话摘要压缩
- 附件内容分层治理
- 跨会话长期记忆
- 缓存命中可观测
- 结构化上下文预算控制
- 根据 provider / serving backend 的差异做优化

### 7.3 当前项目最像什么

更准确地说，现在它还是：

**“带多模态附件的基础多轮聊天系统”**

而不是：

**“上下文工程成熟的智能问答平台”**

这很正常。  
P0 本来就只是闭环。

## 8. 我建议我们后续怎么做：分 4 个阶段推进

这一部分最重要，因为它直接关系到我们后面怎么改代码。

### 阶段 A：先做可观测和预算控制

这是下一步最应该先落的。

目标：

- 能看到每次请求的上下文组成
- 能看到大概 token 消耗
- 能知道哪些内容占上下文最多

建议做法：

1. 后端组装上下文时，打印 / 记录上下文结构
   - system prompt 长度
   - 历史消息条数
   - 附件文本长度
   - 图片数量

2. 给每次请求打上下文字段统计
   - `history_chars`
   - `attachment_chars`
   - `message_count`
   - `image_count`

3. 加一个“上下文预算器”
   - 为不同来源分配预算
   - 例如：
     - 最近消息预算
     - 附件预算
     - 摘要预算
     - system 预算

### 阶段 B：做短期上下文治理

目标：

- 不再把历史消息机械性全量回放

建议做法：

1. 最近若干轮保留原文
2. 更老轮次压缩成会话摘要
3. 附件不再永久全文保留，只保留：
   - 当前轮附件全文
   - 历史附件摘要或关键片段
4. 给 user / assistant / attachment / summary 设置不同优先级

这一步很适合直接借鉴 Qwen-Agent 的“不同内容分层删除顺序”。

### 阶段 C：做长期记忆

目标：

- 让跨会话信息不依赖硬塞所有历史

建议做法：

1. 先只做轻量长期记忆
   - 用户偏好
   - 常用语言
   - 关注主题
   - 长期项目背景

2. 由模型在会话结束或若干轮后抽取
3. 存数据库
4. 新会话开始时按需注入，不是全量注入

### 阶段 D：做缓存命中优化

目标：

- 让重复对话、重复附件、重复系统提示更便宜更快

建议做法：

1. 固定 system prompt 和上下文拼装顺序
2. 保持附件注入模板稳定
3. 让“文件正文”放在用户问题前面且结构固定
4. 如果将来迁移到支持更强缓存可观测的 serving stack
   - 接入 vLLM prefix caching
   - 或支持显式 context cache 的 provider

## 9. 如果以后要写进简历，这一块可以怎么表述

等我们后面真正落地后，这块可以写得比“做了多轮对话”更有技术含量。

例如可以表述为：

- 设计并实现多层上下文治理体系，将会话上下文拆分为近期消息、历史摘要、附件内容与长期记忆四层，提升长会话稳定性
- 构建上下文预算与裁剪策略，对不同来源内容分配 token 配额，避免长附件和历史噪音挤占有效上下文
- 引入摘要压缩与记忆抽取机制，降低长会话输入长度与首 token 时延
- 通过稳定前缀设计与缓存友好型 prompt 结构提升上下文缓存命中率，降低重复问答成本
- 建立上下文可观测指标，包括输入长度、附件占比、摘要触发次数、缓存命中量等

这样的描述，明显比“支持上下文记忆”有技术深度。

## 10. 对你现在最应该记住的 10 句话

1. 上下文治理不只是消息截断，它是一个分层系统工程。
2. 长上下文窗口很重要，但绝不是无脑全塞的理由。
3. 成本、时延、质量，三者都会被上下文结构影响。
4. 稳定前缀是缓存命中的前提。
5. Prompt 结构本身就是上下文治理。
6. 摘要不是记忆，RAG 也不是记忆。
7. 短期上下文和长期记忆必须分开设计。
8. 工具结果、附件全文、中间过程通常不该永久保留在工作上下文里。
9. 没有观测，就谈不上优化。
10. 真正成熟的上下文治理，一定同时涉及应用层和推理服务层。

## 11. 对我们项目的直接结论

基于当前资料和我们项目现状，我给出的直接判断是：

### 11.1 现在不该先做什么

现在先不要一上来就做：

- 复杂向量记忆库
- 过度抽象的 Agent 记忆系统
- 花哨但不可观测的“自动智能压缩”

因为基础层还没打稳。

### 11.2 现在最该先做什么

最合理的顺序是：

1. **上下文可观测**
2. **上下文预算控制**
3. **短期上下文裁剪 + 摘要压缩**
4. **轻量长期记忆**
5. **缓存命中优化**

### 11.3 为什么这样排

因为这条路线最适合你当前这个项目：

- 代码体量不算太大
- 当前还是 Web 聊天主流程
- 模型现在主要跑本地 Ollama
- 先把应用层上下文结构治理好，比先折腾重型 infra 更划算
