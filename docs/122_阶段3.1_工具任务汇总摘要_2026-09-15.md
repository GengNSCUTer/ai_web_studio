# 阶段 3.1：工具任务汇总摘要

更新时间：2026-09-15  
状态：已完成（阶段 3 的第一小步）

## 解决的问题

一次用户问题可能同时触发多个工具。此前系统已经能执行并发调用、阻断严格依赖，也有简单的 `aggregate_status`；但外层 Chat 只有一个状态字符串，无法稳定知道“有几项可靠结果”“多少项失败”“是否在等待用户确认”。这会让后续的部分回答、重新规划或请求澄清缺少统一输入。

本小步不改变工具数量、权限、同步五轮上限或 Planner 行为，只把既有 Step Outcome 汇总为安全、可追踪的任务摘要。

## 现在的执行链路

```text
每个 Tool Step 的终态
  └─ 执行状态 + 质量状态 + 是否可进入 Prompt
        ↓
ToolWorkflowAggregate（代码计算）
  └─ 总状态 + 成功/失败/阻断/等待确认等计数
        ↓
tool_workflow_end Trace
ExternalContextService diagnostics / details
        ↓
阶段 3.2 / 3.3 再据此决定严格失败传播和 Chat 收口动作
```

## 汇总规则

| 整体状态 | 含义 |
|---|---|
| `succeeded` | 所有 Step 都是 `succeeded + valid`，可以完成任务。 |
| `partial` | 至少一个 Step 已完成且质量有效，但另有 Step 失败或被阻断；可靠结果保留，不能假装全部完成。 |
| `waiting_approval` | 没有已完成的业务结果，但存在编辑预览或其他等待用户确认的 Step；预览可展示，不能当成已写入。 |
| `failed` | 没有可靠完成结果，且至少有执行失败、超时或取消。 |
| `blocked` | 没有可靠完成结果，且调用因依赖、策略、预算或校验问题被阻断。 |
| `empty` | 没有可汇总的 Tool Step。 |

摘要只保留以下无敏感计数：总 Step、执行成功数、`succeeded + valid` 数、可进入 Prompt 数、失败数、阻断数、等待确认数、`invalid/uncertain` 质量数，以及“是否有可靠完成结果 / 是否在等用户确认”两个布尔值。它不保存 Tool 参数、Provider 原始异常、URL 或工具返回正文。

## 实现文件

- `backend/app/services/tools/workflow.py`
  - 新增不可变 `ToolWorkflowAggregate`；唯一负责从 `ToolStepOutcome` 计算整体状态和安全计数。
  - `ToolWorkflowResult.aggregate` 保存完整摘要；旧的 `aggregate_status` 继续保留，保证既有接口兼容。
  - `tool_workflow_end` Trace 写入摘要，便于排障与后续前端展示。
- `backend/app/services/external_context_service.py`
  - 将最后一轮 Workflow 摘要传递到 `diagnostics` 与 `details`；本阶段不据此改变重规划或最终回答策略。
- `backend/tests/test_tool_workflow.py`
  - 覆盖独立并发分支“一个成功、一个失败”的 `partial` 摘要，以及“等待审批 + 被依赖阻断”的摘要。
- `backend/tests/test_tool_router.py`
  - 覆盖 Chat 外层能够取得同步 Workflow 的安全摘要。

## 验证与边界

- 定向回归：`backend.tests.test_tool_workflow`、`backend.tests.test_tool_router` 共 37 项通过。
- 此阶段没有把同步 Chat 从 5 轮改为无限循环，也没有新增 Tool、权限、数据库字段或 Durable handoff。
- 阶段 3.2 才会把“独立失败可保留其他结果”和“关键依赖失败必须硬阻断”整理成明确策略；阶段 3.3 才会让外层 Chat 基于摘要选择部分回答、受控重规划、澄清或停止。
