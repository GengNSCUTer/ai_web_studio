# 项目当前实现全景与面试口径

更新时间：2026-08-03

本文是当前项目实现和面试表述的权威入口。代码参数优先于历史学习笔记；历史文档中如果保留旧方案，必须明确标注为历史阶段。

## 1. 当前定位

本项目是面向个人与小团队的本地知识工作平台，服务论文、技术文档和项目资料的组织、检索、审阅与受控行动。核心目标不是做无限自主 Agent，而是把模型能力放进可持久化、可追溯、可评测和有权限边界的后端工作流。

当前不表述为已商业上线、已交付研究所或涉密客户，也不表述为任意工具均可恢复或跨系统 Exactly Once。

## 2. 总体架构

```text
Next.js / React
        |
FastAPI + SQLAlchemy
        |
PostgreSQL / pgvector ---- Redis Stream ---- Worker
        |
OpenAI-compatible / Ollama / vLLM Provider
        |
RAG、Memory、Context、Tool/Skill、Durable Runtime
```

请求链路按职责分为：鉴权与项目隔离、文档索引、查询检索、上下文组装、流式 Chat、受控 Tool Workflow，以及低风险长任务 Runtime。PostgreSQL 保存业务事实和状态；Redis Stream 负责后台任务投递，不与 PostgreSQL 共享事务。

## 3. 六条核心链路

### 3.1 文档索引与混合 RAG

```text
上传 -> Document / KnowledgeJob / Outbox
-> Redis Stream -> Worker -> 解析 Markdown
-> Parent-Child Chunk -> Embedding + pgvector
-> generation-specific BM25 -> manifest -> inactive generation
-> Lease / version CAS 激活 active generation
```

查询时先做确定性 Query Rewrite，再分别执行向量和 BM25 检索，用 RRF 融合排名，可选 Rerank；随后进行 metadata / generation 过滤和 Parent-Child 上下文展开。检索日志区分“召回候选”和“实际注入模型的证据”，并支持 Eval Set、配置快照、来源追踪和 Skill/Tool Gold Set 评测。

### 3.2 流式 Chat

```text
User Message -> Assistant 占位消息
-> Context Assembly -> Provider 流
-> answer / reasoning / tool 事件
-> done / cancelled / failed 收口
```

Assistant 占位消息是后续来源、Tool Trace、重生成和失败状态的数据库锚点，不承担跨模型调用的长锁职责。新轮次/重生成/编辑重答只在短准备事务内使用 Conversation/Assistant 行锁，并给每次 generation 分配 opaque `generation_id`；流式收口按 `message_id + generation_id` CAS，旧请求不能覆盖新请求。流式回答不逐 Token 写库，完成、取消或失败时统一收口；因此进程被强制终止时，尚未收口的 partial content 仍可能丢失，这是当前明确边界。Provider 兼容 OpenAI-compatible、Ollama 和 vLLM。

### 3.3 记忆管理

- 最近原始消息：保留短期对话细节。
- 滚动摘要：以 `summary_boundary_message_id` 记录压缩边界，只处理新增历史，失败时回退规则摘要。
- 长期记忆：会话结束或达到周期后异步提炼候选；候选先进入 `pending`，经过敏感信息、时效、置信度、重复和冲突检查，用户审核后才激活，并按用户 / 项目作用域注入后续会话。
- 记忆带来源会话、状态和可停用能力，避免模型生成内容直接污染跨会话事实。

### 3.4 Context / Token 预算

上下文采用分层组装和 Token + 字符双预算：

```text
System / 项目指令 / Skill 约束
-> 滚动摘要 -> 近期历史
-> 当前问题 -> 长期记忆 / 附件 / RAG / Tool evidence
```

系统约束和当前问题不可裁剪；动态证据作为不可信 reference，不进入 System。预算不足时优先保留与当前问题强相关的 RAG / Tool evidence，再压缩或裁剪旧历史，并预留输出空间。稳定前缀记录 prefix hash，为 vLLM / OpenAI-compatible 的缓存兼容和观测留出接口，但不宣称已获得 Provider 官方 Prompt Cache 命中数据。

### 3.5 Tool / Skill Workflow

```text
Query Rewrite -> Catalog 硬过滤 -> Candidate Selector
-> LLM Planner / 确定性 fallback -> ToolPlan JSON
-> Validator / Executor -> MCP 或 HTTP Adapter
-> Observation -> 继续重规划或最终回答
```

代码负责工具目录、候选召回、Schema、ACL、项目范围、凭据、风险、SSRF 和调用预算；LLM 只在候选内选择工具并生成结构化参数，不能直接发送请求；Executor 才是最终安全边界。外部结果按不可信 evidence 处理，Result Binding 只允许读取已声明依赖中的受限 JSON Pointer，并在绑定后重新校验目标 Schema。

当前同步 Chat 的硬上限是 **最多 5 轮 `plan -> execute -> observe`**；每份 ToolPlan 最多 **5 次调用**。第 5 轮仍要求继续时写入 `max_rounds_reached` 并终止。Candidate Selector 不是安全边界，也不是自动安装 Skill 的授权。

默认工具范围包括 Tavily 搜索、高德地图 / 天气 / 路径 / 距离 / POI、Agent Artifact 查询、当前工作区文件 list / search / read，以及 `workspace.files.propose_edit`。实际写文件必须经过 PatchDraft、用户审批、一次性 challenge、baseline hash 和 FileRevision CAS。

Skill 是声明式 manifest，只能引用已有 Tool Key，不自行扩大权限；安装、启用、升级和回滚均需显式操作，系统只能推荐，第三方市场暂不开放。

### 3.6 Durable Runtime 与可靠性

低风险、只读、适合长时间执行的 Tool DAG 才进入独立 Durable Runtime：

```text
AgentRun / AgentStep / AgentCheckpoint / AgentArtifact
-> PostgreSQL Outbox -> Redis Stream
-> Lease + Heartbeat + version fencing
-> retry / DLQ / controlled replay / reconcile
```

它提供至少一次投递下的幂等状态机和崩溃后从已持久化 Step 继续的能力，不是 Exactly Once，也不覆盖支付、邮件、外部发布、任意 HTTP 写、Bash、Shell、SQL、删除文件或任意本机文件写入。同步 Chat 的 `generation_id` CAS 只保护在线消息收口；知识索引 Worker 另采用 Outbox、Lease、inactive generation 和 CAS，两者是边界不同的运行时。

## 4. 权威参数与安全边界

| 项目 | 当前口径 |
| --- | --- |
| 同步 Tool Workflow | 最多 5 轮 observe -> re-plan |
| 单份 ToolPlan | 最多 5 次 Tool 调用 |
| Durable Runtime | 仅低风险只读长任务 / Tool DAG |
| 文件写入 | PatchDraft -> 用户审批 -> one-time challenge -> FileRevision CAS |
| Skill | manifest digest、版本锁、allowlist、显式启用 / 升级 / 回滚 |
| 未纳入范围 | Bash、Shell、SQL、删除文件、任意本机写、支付、邮件、外部发布、任意 HTTP 写 |

## 5. 面试推荐口径

### 30 秒

这是一个面向个人知识工作的 RAG Agent 后端。我把文档索引、混合检索、流式 Chat、滚动摘要、长期记忆、受控 Tool Calling 和低风险长任务运行时串成了有状态闭环。模型只负责候选内的计划和参数生成，代码负责权限、Schema、执行、状态与恢复；同步工具循环最多 5 轮，避免把系统包装成无限自主 Agent。

### 90 秒

项目底座是 FastAPI、PostgreSQL/pgvector、Redis Stream 和 OpenAI-compatible/Ollama/vLLM。文档入库走 Outbox + Worker，解析后建立 Parent-Child Chunk、向量和 BM25 索引，用 RRF、可选 Rerank、generation CAS 和来源追踪保证检索可解释。Chat 每轮先保存 assistant 锚点，再把摘要、近期历史、长期记忆、RAG 和 Tool evidence 按统一预算组装，流式结束时统一收口。Tool 侧代码先过滤候选，LLM Planner 只生成 ToolPlan，Executor 重新做 Schema、ACL、凭据、风险和 SSRF 校验；同步最多 5 轮、单计划最多 5 次调用。低风险只读长任务才进入 AgentRun/Step/Checkpoint Runtime，利用 Outbox、Lease、Fencing、重试、DLQ 和对账实现可恢复的最终一致性；文件写入则单独走审批和 CAS。

## 6. 已实现、边界与下一步

已实现：混合 RAG 与评测、流式 Chat、滚动摘要、自动候选长期记忆审核、Context/Token 预算、五轮受限 Tool Workflow、Result Binding、Skill 治理、低风险 Durable Run、文件审批写入链路。

明确边界：没有 Provider 官方 Prompt Cache 成果；没有跨数据库强事务或 Exactly Once；同步 Chat 进程崩溃时未收口 partial content 仍可能丢失；不支持任意高风险副作用自动恢复；不开放通用本机执行权限。

后续只围绕个人知识工作的可信闭环迭代，例如检索与记忆评测、上下文诊断、低风险 Skill 质量和旧 generation GC，不以无限增加工具数量为目标。

## 7. 2026-08-03 增量：质量合同与消息顺序

Tool Result Quality Contract 已成为 Tool Workflow 和 Durable Runtime 共用的执行合同。Catalog 加载时校验质量配置；运行时根据结构化结果返回 `valid`、`uncertain` 或 `invalid`，未知或显式非法状态也按 `invalid` fail-closed。只有 `valid` 结果可以继续依赖链；`uncertain/invalid` 会阻断下游，并且其 sources 不会进入最终回答 Prompt，只保留质量诊断事件。非 `success` 结果即使携带 sources 也默认不暴露；待确认 Diff 只有显式标记为 evidence 时才会展示。Durable Worker 对这类结果直接写不可重试的 `failed` 终态，错误码为 `tool_result_quality_invalid/uncertain`，不会将不合格结果写成成功 Artifact 或解锁下游。

消息表的 `sequence` 是会话内顺序辅助字段，不是全局时间替代物。列表按 `created_at`、`sequence`、`id` 排序；分配新序号前锁定对应 `Conversation` 行，PostgreSQL 下避免同会话并发 `MAX(sequence)+1` 冲突。应用侧使用高精度 UTC 创建时间来减少 SQLite/旧数据库秒级时间戳的同秒歧义。该锁只保护序号分配，不代表所有生成请求已经串行化，也不代表 Exactly Once。

本轮后端完整回归为 311 项，3 项 PostgreSQL/pgvector 集成测试因未设置 `TEST_POSTGRES_URL` 跳过；`compileall`、默认 Tool manifest JSON 校验和 `git diff --check` 通过。

## 8. 代码审查收尾增量：持久化边界

Tool Executor 是参数和副作用的最终边界：Planner、Workflow 或 Durable Worker 的前置校验都不能替代 Executor 的最终 Input Schema 重验。Adapter 返回值会在进入下一轮观察、Result Binding、API 公开字段和 Artifact 前统一脱敏；Artifact 结果同时受到 200,000 字符上限和 JSON 可序列化检查，超限不会伪造成功。

generation_id 的运行时 DDL 可以从缺列、nullable 或无默认值的中间状态恢复；stale streaming 自愈先锁定消息行再轮换 generation token，旧模型流无法在自愈后重新写回 done，也不会覆盖已经正常收口的消息。Artifact JSON 严格拒绝非有限数值。这些措施增强的是边界可验证性和失败可诊断性，仍不能宣称跨 PostgreSQL、Redis、Provider、文件系统和第三方 API 的强事务或 Exactly Once。

最终验证：后端完整回归 `325 tests`，`OK (skipped=3)`；3 项跳过是未设置 `TEST_POSTGRES_URL` 的 PostgreSQL/pgvector 集成测试。`compileall`、默认 Tool manifest JSON 解析和 `git diff --check` 均通过。

## 9. 2026-08-03 增量：Durable 参数与依赖重放

Durable Runtime 的参数边界现在与同步执行器一致：入队和 Worker 都按 `default -> model/binding -> fixed` 合并后校验 Schema，默认值进入规范化持久化参数，fixed 值只在可信 Adapter 侧生效。固定值不会被模型参数覆盖，也不会写入模型可控的 Trace/Step 参数。

DLQ 重放按依赖图恢复源 Step 及其安全下游。只有因该源失败而 `dependency_failed` 的下游、且其它依赖已成功时才会恢复；每个恢复 Step 产生新的 outbox event，原 event 保留用于审计。Durable metrics 统一按 runtime kind 过滤，避免把 file-edit 运行误算成 Durable 健康数据。

本批新增 9 项行为测试，后端完整回归 `334 tests`，`OK (skipped=3)`。启动 schema DDL 已增加 PostgreSQL advisory lock，stale generation CAS 已改为 savepoint；3 项 PostgreSQL/pgvector 集成测试因未设置 `TEST_POSTGRES_URL` 跳过，这不代表 SQLite 已证明多进程 PostgreSQL 锁语义。

## 10. 2026-08-03 增量：质量决策、RAG 分层评测与并发验证

本轮只处理可信闭环中的高优先级问题，没有新增高风险工具。

### 10.1 错误信息安全收口

- 知识库检索异常对外只返回稳定错误码对应的安全文案，不再把 Provider、URL、Token 或内部异常原文放入用户 notice。
- RAG 评测 Case 错误只记录 `error_code` 和安全提示；完整异常通过服务端日志定位。
- 已增加 Provider 异常脱敏回归测试，验证用户响应、评测记录和运行错误文案均不含内部地址或凭据。

### 10.2 Tool Result Quality 的显式决策

在原有 `valid / uncertain / invalid` 质量状态上增加了显式 `quality_action`：

| 结果 | 当前受限同步链路动作 |
| --- | --- |
| `valid` | `continue`，允许 Result Binding 和依赖步骤继续 |
| `invalid` 且可用低风险只读备用工具 | `fallback` |
| `invalid` 且可重试但同步预算不足 | `replan`，不隐藏重试 |
| `invalid` 且不可恢复 | `block` |
| `uncertain` 且有低风险备用工具 | `fallback` |
| `uncertain` 且无备用工具 | `replan`；高风险或写操作改为 `clarify` |

所有动作都会写入质量决策事件。`uncertain/invalid` 永远不能解锁依赖步骤；A -> B 中 A 质量不合格时，B 不执行，并记录 `next_action`、质量原因和阻断状态。自动 fallback 还会在执行前再次检查目标工具必须是低风险、只读工具，不能由 Planner 借 fallback 配置绕过权限边界。动作必须消耗当前 ToolPlan / Agent Run 的已有预算，不能通过隐式循环突破同步 5 轮和单计划 5 次调用上限。Durable Runtime 仍只允许低风险只读 Tool，并由自己的有限重试、DLQ 和 Checkpoint 负责恢复。

### 10.3 RAG 评测口径

现有评测仍然区分“检索到了什么”和“最终注入了什么”，本轮增加：

- `nDCG@K`：考虑相关证据排序位置；
- `expected_keyword_recall`：评测标注关键词在召回证据中的覆盖率；
- 每个 Case 的 nDCG、关键词命中和关键词覆盖明细；文档级标注支持多个相关 Chunk，MRR 取首个命中位置，Context Precision 统计实际命中的相关 Chunk 数；
- `score_answer()` 确定性答案关键词评分辅助函数；
- 运行报告中的 `answer_correctness.status=not_scored` 明确表示当前运行没有自动生成或评审最终答案。

因此当前可以准确表述为：项目已有可复现的 RAG 检索和证据覆盖评测，包括 Hit@K、MRR、Context Precision、Context Recall、nDCG 和延迟；最终答案语义正确性、Faithfulness 和引用正确率尚未被这条检索评测链自动宣称为已完成。

### 10.4 PostgreSQL 并发集成验证

新增真实 PostgreSQL 集成测试入口，覆盖：

- 两个 Worker 竞争同一个 Outbox Step 时只有一个获得 Lease；
- Lease 过期后新 Worker 接管且版本递增；
- 旧 Worker 的 heartbeat 被版本 Fencing 拒绝；
- 同一幂等键并发入队最终只产生一个 Run。

运行前提和命令见 [backend/README.md](/disk2/gengnan/ai_web_studio/backend/README.md)。未设置 `TEST_POSTGRES_URL` 时这两项和原有 pgvector 集成测试会明确跳过，不能把 SQLite 单测当作 PostgreSQL 锁语义证明。

本轮验证结果：后端 `343 tests` 通过，`5 skipped`（PostgreSQL/pgvector 环境未设置）；后端 `compileall`、`git diff --check` 和前端 ESLint 通过。前端 `tsc --noEmit` 仍受已有 `.next/types/validator.ts` 路由生成错误影响，与本轮业务类型改动无关。
