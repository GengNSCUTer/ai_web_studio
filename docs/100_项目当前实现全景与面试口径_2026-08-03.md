# 项目当前实现全景与面试口径

更新时间：2026-08-03

本文是当前项目实现和面试表述的权威入口。代码参数优先于历史学习笔记；历史文档中如果保留旧方案，必须明确标注为历史阶段。

## 1. 当前定位

本项目是面向个人与小团队的本地知识工作平台，服务论文、技术文档和项目资料的组织、检索、审阅与受控行动。核心目标不是做无限自主 Agent，而是把模型能力放进可持久化、可追溯、可评测和有权限边界的后端工作流。

当前不表述为已商业上线、已交付研究所或涉密客户，也不表述为任意工具均可恢复或跨系统 Exactly Once。

## 2. 总体架构

```text
Next.js / React
        |
FastAPI + SQLAlchemy
        |
PostgreSQL / pgvector ---- Redis Stream ---- Worker
        |
OpenAI-compatible / Ollama / vLLM Provider
        |
RAG、Memory、Context、Tool/Skill、Durable Runtime
```

请求链路按职责分为：鉴权与项目隔离、文档索引、查询检索、上下文组装、流式 Chat、受控 Tool Workflow，以及低风险长任务 Runtime。PostgreSQL 保存业务事实和状态；Redis Stream 负责后台任务投递，不与 PostgreSQL 共享事务。

## 3. 六条核心链路

### 3.1 文档索引与混合 RAG

```text
上传 -> Document / KnowledgeJob / Outbox
-> Redis Stream -> Worker -> 解析 Markdown
-> Parent-Child Chunk -> Embedding + pgvector
-> generation-specific BM25 -> manifest -> inactive generation
-> Lease / version CAS 激活 active generation
```

查询时先做确定性 Query Rewrite，再分别执行向量和 BM25 检索，用 RRF 融合排名，可选 Rerank；随后进行 metadata / generation 过滤和 Parent-Child 上下文展开。检索日志区分“召回候选”和“实际注入模型的证据”，并支持 Eval Set、配置快照、来源追踪和 Skill/Tool Gold Set 评测。

### 3.2 流式 Chat

```text
User Message -> Assistant 占位消息
-> Context Assembly -> Provider 流
-> answer / reasoning / tool 事件
-> done / cancelled / failed 收口
```

Assistant 占位消息是后续来源、Tool Trace、重生成和失败状态的数据库锚点，不承担并发锁职责。流式回答不逐 Token 写库，完成、取消或失败时统一收口；因此进程被强制终止时，尚未收口的 partial content 仍可能丢失，这是当前明确边界。Provider 兼容 OpenAI-compatible、Ollama 和 vLLM。

### 3.3 记忆管理

- 最近原始消息：保留短期对话细节。
- 滚动摘要：以 `summary_boundary_message_id` 记录压缩边界，只处理新增历史，失败时回退规则摘要。
- 长期记忆：会话结束或达到周期后异步提炼候选；候选先进入 `pending`，经过敏感信息、时效、置信度、重复和冲突检查，用户审核后才激活，并按用户 / 项目作用域注入后续会话。
- 记忆带来源会话、状态和可停用能力，避免模型生成内容直接污染跨会话事实。

### 3.4 Context / Token 预算

上下文采用分层组装和 Token + 字符双预算：

```text
System / 项目指令 / Skill 约束
-> 滚动摘要 -> 近期历史
-> 当前问题 -> 长期记忆 / 附件 / RAG / Tool evidence
```

系统约束和当前问题不可裁剪；动态证据作为不可信 reference，不进入 System。预算不足时优先保留与当前问题强相关的 RAG / Tool evidence，再压缩或裁剪旧历史，并预留输出空间。稳定前缀记录 prefix hash，为 vLLM / OpenAI-compatible 的缓存兼容和观测留出接口，但不宣称已获得 Provider 官方 Prompt Cache 命中数据。

### 3.5 Tool / Skill Workflow

```text
Query Rewrite -> Catalog 硬过滤 -> Candidate Selector
-> LLM Planner / 确定性 fallback -> ToolPlan JSON
-> Validator / Executor -> MCP 或 HTTP Adapter
-> Observation -> 继续重规划或最终回答
```

代码负责工具目录、候选召回、Schema、ACL、项目范围、凭据、风险、SSRF 和调用预算；LLM 只在候选内选择工具并生成结构化参数，不能直接发送请求；Executor 才是最终安全边界。外部结果按不可信 evidence 处理，Result Binding 只允许读取已声明依赖中的受限 JSON Pointer，并在绑定后重新校验目标 Schema。

当前同步 Chat 的硬上限是 **最多 5 轮 `plan -> execute -> observe`**；每份 ToolPlan 最多 **5 次调用**。第 5 轮仍要求继续时写入 `max_rounds_reached` 并终止。Candidate Selector 不是安全边界，也不是自动安装 Skill 的授权。

默认工具范围包括 Tavily 搜索、高德地图 / 天气 / 路径 / 距离 / POI、Agent Artifact 查询、当前工作区文件 list / search / read，以及 `workspace.files.propose_edit`。实际写文件必须经过 PatchDraft、用户审批、一次性 challenge、baseline hash 和 FileRevision CAS。

Skill 是声明式 manifest，只能引用已有 Tool Key，不自行扩大权限；安装、启用、升级和回滚均需显式操作，系统只能推荐，第三方市场暂不开放。

### 3.6 Durable Runtime 与可靠性

低风险、只读、适合长时间执行的 Tool DAG 才进入独立 Durable Runtime：

```text
AgentRun / AgentStep / AgentCheckpoint / AgentArtifact
-> PostgreSQL Outbox -> Redis Stream
-> Lease + Heartbeat + version fencing
-> retry / DLQ / controlled replay / reconcile
```

它提供至少一次投递下的幂等状态机和崩溃后从已持久化 Step 继续的能力，不是 Exactly Once，也不覆盖支付、邮件、外部发布、任意 HTTP 写、Bash、Shell、SQL、删除文件或任意本机文件写入。知识索引 Worker 也采用 Outbox、Lease、inactive generation 和 CAS，但它与同步 Chat 的任意 Agent 恢复是两个边界不同的运行时。

## 4. 权威参数与安全边界

| 项目 | 当前口径 |
| --- | --- |
| 同步 Tool Workflow | 最多 5 轮 observe -> re-plan |
| 单份 ToolPlan | 最多 5 次 Tool 调用 |
| Durable Runtime | 仅低风险只读长任务 / Tool DAG |
| 文件写入 | PatchDraft -> 用户审批 -> one-time challenge -> FileRevision CAS |
| Skill | manifest digest、版本锁、allowlist、显式启用 / 升级 / 回滚 |
| 未纳入范围 | Bash、Shell、SQL、删除文件、任意本机写、支付、邮件、外部发布、任意 HTTP 写 |

## 5. 面试推荐口径

### 30 秒

这是一个面向个人知识工作的 RAG Agent 后端。我把文档索引、混合检索、流式 Chat、滚动摘要、长期记忆、受控 Tool Calling 和低风险长任务运行时串成了有状态闭环。模型只负责候选内的计划和参数生成，代码负责权限、Schema、执行、状态与恢复；同步工具循环最多 5 轮，避免把系统包装成无限自主 Agent。

### 90 秒

项目底座是 FastAPI、PostgreSQL/pgvector、Redis Stream 和 OpenAI-compatible/Ollama/vLLM。文档入库走 Outbox + Worker，解析后建立 Parent-Child Chunk、向量和 BM25 索引，用 RRF、可选 Rerank、generation CAS 和来源追踪保证检索可解释。Chat 每轮先保存 assistant 锚点，再把摘要、近期历史、长期记忆、RAG 和 Tool evidence 按统一预算组装，流式结束时统一收口。Tool 侧代码先过滤候选，LLM Planner 只生成 ToolPlan，Executor 重新做 Schema、ACL、凭据、风险和 SSRF 校验；同步最多 5 轮、单计划最多 5 次调用。低风险只读长任务才进入 AgentRun/Step/Checkpoint Runtime，利用 Outbox、Lease、Fencing、重试、DLQ 和对账实现可恢复的最终一致性；文件写入则单独走审批和 CAS。

## 6. 已实现、边界与下一步

已实现：混合 RAG 与评测、流式 Chat、滚动摘要、自动候选长期记忆审核、Context/Token 预算、五轮受限 Tool Workflow、Result Binding、Skill 治理、低风险 Durable Run、文件审批写入链路。

明确边界：没有 Provider 官方 Prompt Cache 成果；没有跨数据库强事务或 Exactly Once；同步 Chat 进程崩溃时未收口 partial content 仍可能丢失；不支持任意高风险副作用自动恢复；不开放通用本机执行权限。

后续只围绕个人知识工作的可信闭环迭代，例如检索与记忆评测、上下文诊断、低风险 Skill 质量和旧 generation GC，不以无限增加工具数量为目标。
