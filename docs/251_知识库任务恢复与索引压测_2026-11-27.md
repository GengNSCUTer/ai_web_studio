# 知识库任务恢复与索引压测

2026-11-27

## 任务恢复

现有 `knowledge-worker` 在启动时及每 30 秒从 PostgreSQL 检查一批最多 50 个任务。只有已经创建 Outbox 的任务才进入补偿范围。发布超过 120 秒且仍等候执行的任务重新登记最近一次已发布的事件，继续使用同一个事件 ID。租约过期时按现有次数和退避规则重试，次数用尽时置为 `dead_letter`。维护循环独立于文档解析与索引，负责扫描和发布。Stream 或消费组丢失时，消费端会重建消费组。

索引构建使用领取时得到的基线版本。CAS 发现指针已更新时，持有有效租约的 Worker 在同一事务废弃本次快照、释放租约并写入重试事件，提交后 ACK。待处理任务从新的活动快照重新构建。只有有效租约可以将本次快照标记为就绪或激活。检索始终以活动指针为准。

后台解析的 Markdown 和 MinerU 图片包含 Job 与租约版本。同一个文档被重新领取时，各次尝试写各自的路径。成功提交的租约更新文档产物指针，已有路径继续可读。Parent-Child 切分从同一份规范化 Markdown 按 Child 起始偏移写入章节路径和幻灯片编号，父块正文仍由第一个 Child 保存。旧索引在新建时自然采用这套规则。

## 构建成本与后续评估

每个 Generation 的日志记录复制及新增 Chunk、Embedding 请求数和耗时、数据库写入、BM25 构建及词法文件字节数。构建阶段的开始与完成日志按 Generation 对应，`knowledge_job_recovery` 记录失效的租约版本。BM25 直接使用刚持久化的 Chunk 数据，避免提交后重新逐条加载 ORM 记录。

本机基线为 4 库、35 个文档、2,874 个活动 Chunk，最大单库 2,537 个。运行库只读清单检查 24 小时以上且未被当前指针或有效构建租约使用的 Generation，分别报告 Chunk 行数及词法文件字节数。

```bash
PYTHONPATH=backend backend/.venv/bin/python backend/scripts/report_knowledge_generations.py
```

隔离压测对同一个临时 PostgreSQL 知识库逐个写入 100 个文档，每个文档 100 个 Chunk。Embedding 使用可重复的 4 维测试向量，以分离数据库与 BM25 成本，结果用于观察扩展趋势。每档取最近 5 个文档的构建耗时中位数。

| 文档 | 活动 Chunk | 累计写入 Chunk | 构建中位数 | 数据库写入中位数 | BM25 与清单中位数 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 10 | 1,000 | 5,500 | 0.75 秒 | 0.36 秒 | 0.20 秒 |
| 20 | 2,000 | 21,000 | 1.67 秒 | 0.73 秒 | 0.56 秒 |
| 50 | 5,000 | 127,500 | 3.92 秒 | 1.90 秒 | 1.38 秒 |
| 100 | 10,000 | 505,000 | 7.85 秒 | 3.84 秒 | 2.74 秒 |

100 份文档累计构建 407.4 秒，全部版本的 PostgreSQL Chunk 表及索引为 545 MiB，当前版本 BM25 约 5.9 MiB。测试读写临时 PostgreSQL 和本地词法文件，真实 Embedding 网络开销需从运行日志另行读取。

实际单库达到约 10,000 个活动 Chunk，或有一次导入至少 50 个文档的需求时，优先用同一次 Generation 提交同库的多份已解析文档。当前单库规模沿用逐文档快照。采集 14 天构建日志后，若至少 3 次中断且重算超过同期 Embedding 耗时的 5%，再引入可复用的向量批次。本阶段继续按 Job 恢复。

## 验证与运行

真实隔离 PostgreSQL 和 Redis 测试覆盖发布后删去 Stream、消费组重建、双 Worker 补偿、过期租约、重试耗尽以及两个同基线索引最终均可检索。另测迟到解析产物、Parent-Child 结构字段及引用偏移。Playwright 通过知识库页面提交解析、预览 Markdown、生成索引，页面与控制台错误均为 0。此变更沿用现有 API 和数据库字段。
