# 详细需求清单

本文档是在 [04_智能问答网页方案.md](/disk2/gengnan/rag_agent/P4_RAG项目案例/docs/04_智能问答网页方案.md:1) 基础上的进一步收敛版本，目标是把第一版产品的功能边界定死，避免后续开发过程中范围漂移。

本文档主要解决 4 个问题：

1. 第一版到底做什么，不做什么
2. 每个页面和功能具体需要支持什么交互
3. 核心业务流程应该如何跑通
4. 完成到什么程度算“可交付”

## 1. 项目范围结论

### 1.1 第一版产品名称

先沿用上一版方案中的名称：

**Ollama 多模态智能问答工作台**

### 1.2 第一版目标

第一版目标不是做成一个全能 AI 平台，而是做成一个：

- 前后端分离
- 可持续迭代
- 支持本地 Ollama
- 支持多轮聊天
- 支持图片与文档附件
- 具备完整 Web 产品基本形态

的多模态智能问答网页。

### 1.3 第一版核心价值

从用户视角，第一版要提供的是：

- 一个像 ChatGPT / 豆包 / DeepSeek 的聊天网页
- 能调用本地 `qwen3.5:27b-q8_0`
- 能保存历史会话
- 能上传图片问问题
- 能上传文档让模型分析
- 能流式看到回答

### 1.4 第一版明确不做

为了确保开发聚焦，第一版明确不做这些：

- 不做 RAG 知识库索引
- 不做向量检索
- 不做 Agent / LangGraph 工作流
- 不做联网搜索
- 不做插件系统
- 不做语音输入
- 不做复杂权限体系
- 不做多租户
- 不做企业后台
- 不做移动端原生 App

### 1.5 第一版默认模型

- 默认模型：`qwen3.5:27b-q8_0`
- 默认推理服务：本地 `Ollama`

### 2.2 `P0.5` 建议尽快完成

这一层不是第一版最小闭环必须项，但它会明显提升产品完成度和后续简历表达质量。

- 上下文统计与可视化
- 上下文预算控制
- 历史消息摘要压缩
- 长会话上下文裁剪策略优化
- 附件内容按需展开和索引化展示
- 长期记忆雏形

补充说明：

- “上下文预算控制”当前已经进入第一阶段落地：后端已有动态预算框架，预算会根据 provider、用户配置的上下文窗口、上下文模式自动计算
- “上下文统计与可视化”当前已完成第一版落地：后端会返回预算与裁剪统计，前端已提供按钮式上下文治理诊断弹层与提示区
- “历史消息摘要压缩”当前已完成第二阶段升级：滚动摘要刷新时优先调用当前 provider/model 生成模型摘要，失败或返回空时自动回退到规则式摘要
- “长期记忆雏形”当前已完成 MVP：支持用户手动新增、启停、删除长期记忆，并在聊天上下文中按预算注入
- “模型建议记忆”当前已完成第一版：可从当前会话提取候选长期记忆，由用户确认后保存
- “记忆冲突治理”当前已完成规则版：候选记忆会提示可能重复、可能冲突或建议保存，并记录来源会话信息
- “缓存友好型 Prompt 结构”当前已完成第一版：后端通过 `ContextPromptBuilder` 固定上下文层级顺序，前端诊断面板可展示 Prompt 模板和上下文层级信息
- “附件内容按需展开”当前已完成第一版：当前轮文档会被切成片段，并按用户问题做关键词级相关性筛选后再注入上下文
- “附件片段可视化预览”当前已完成第一版：前端上下文诊断弹层可以查看已选附件片段摘要，并支持点击展开更长片段
- “tokenizer 级预算与摘要质量观测”当前已完成第一版：后端已引入 `TokenizerEstimator`，可返回总 Token 估算、附件 Token、摘要 Token、摘要源 Token、压缩比等指标
- “prompt prefix hash 与缓存命中观测”当前已完成第一版：后端会对稳定前缀做 hash 与 token 估算，并给出“是否复用上一轮稳定前缀”的启发式观测
- 当前真正未完成的重点，已经收敛为：附件索引化持久化、语义级记忆去重、来源消息级高亮定位、更精细缓存优化

### 2.3 `P1` 推荐完成

这些不是第一版最小闭环必须项，但只要时间允许，应尽量做。

- 会话搜索
- 重新生成最后一条回答
- 编辑上一条用户消息并重新回答
- 附件预览
- 深色 / 浅色主题
- 会话归档 / 置顶
- 前端参数设置面板更细化

补充说明：

- 用户登录 / 注册当前已经提前完成，不再属于待做 `P1`
- 模型列表查询当前已经提前完成，不再属于待做 `P1`
- 当前更适合把 `P1` 理解为“通用产品功能补完”，而不是“基础链路补课”
- `P1` 首批功能当前已经完成第一轮落地：
  - 左侧会话搜索
  - 最后一条回答重生成
  - 最后一条用户消息编辑后重答
  - 附件预览
  - 会话归档 / 置顶
- `P1` 交互修补当前已经完成第二轮落地：
  - “编辑上一条用户消息并重新回答”已改为消息内联编辑，不再使用浏览器弹窗
  - 编辑态已支持同时修改文本和附件，并复用现有附件预览能力
  - 输入区已支持点击待发送附件直接预览
  - 切换会话时不再把短时间内仍在生成的回答直接误判为失败
- 当前 `P1` 剩余重点已收敛为：深浅主题、设置面板继续细化，以及后续更完整的消息级操作体验打磨

- API Key / Base URL 自定义 provider

- Prompt 模板

### 2.5 上下文治理专项说明

上下文治理在本项目里的目标不是简单截断历史消息，而是：

- 保证短期多轮问答的连续性
- 避免长会话把上下文窗口撑爆
- 避免附件、图片、系统提示互相抢占预算
- 为后续长期记忆和缓存命中优化留接口

第一版上下文治理优先级建议：

1. 近期消息保留
2. 附件内容拼接
3. 上下文预算控制
4. 摘要压缩
5. 长期记忆
6. 缓存命中优化

当前阶段说明：

- 第 1 到第 3 项已经完成第一阶段实现
- 第 4 项已经进入第二阶段实现：
  当前已具备“最近原始消息窗口 + 会话级滚动摘要”的基础分层能力，并已接入“模型摘要优先 + 规则摘要兜底”的滚动摘要刷新策略
- 第 5 项已经完成手动长期记忆 MVP、模型建议记忆第一版、规则级冲突治理和来源追踪
- 第 6 项已经完成缓存友好型 Prompt 结构第一版，并已补上 prefix hash / 稳定前缀复用观测；更精细缓存优化仍属于后续重点方向

当前对这条主线更准确的阶段判断是：

- `P0` 已基本成立
- 当前主要处于 `P0.5` 阶段性收尾位置：上下文治理第一阶段闭环已经基本成型
- 现阶段不建议全面切到 `P2`
- 下一步更合理的是：以 `P1` 产品能力补完为主线，同时把上下文治理剩余深水区问题作为专项继续迭代

第一版暂不做：

- 复杂知识库检索
- 复杂 agent memory
- 自动跨会话知识融合
- 多模型记忆对齐

## 3. 用户角色定义

### 3.1 第一版角色简化

第一版先按两种模式考虑：

#### 模式 A：单用户模式

特点：

- 无需登录
- 所有会话属于当前本地用户
- 开发速度快

#### 模式 B：基础登录模式

特点：

- 支持注册 / 登录
- 会话按用户隔离
- 每个用户有独立设置

### 3.2 当前推荐策略

这部分属于早期规划时的建议，当前实际实现已经发生变化。

当前真实状态是：

- 产品已经采用基础登录模式
- 已支持注册 / 登录 / 退出登录
- 会话、设置、长期记忆、上传目录都已按用户隔离

所以后续不再按“先单用户再登录”的路线推进，而是直接按：

- 登录态优先
- 用户隔离优先
- 在此基础上继续补产品能力和上下文治理能力

## 4. 页面级需求

第一版页面数量不要过多，建议控制在 3 个主页面以内。

### 4.1 主聊天页

这是第一版的绝对核心页面。

#### 页面目标

让用户完成以下行为：

- 新建或切换会话
- 查看历史消息
- 输入文本
- 上传图片或文档
- 流式接收 AI 回复
- 管理当前会话

#### 页面布局建议

- 左侧：会话侧边栏
- 中间：消息线程
- 底部：输入区
- 顶部：会话标题 + 设置入口

#### 页面必须具备的模块

##### 1. 会话侧边栏

- 新建会话按钮
- 会话列表
- 当前会话高亮
- 每条会话显示标题
- 每条会话支持展开操作菜单

##### 2. 消息线程区

- 展示用户消息
- 展示 AI 消息
- 展示消息附件
- 展示加载 / 生成中状态
- 支持 Markdown
- 支持代码块复制

##### 3. 输入区

- 文本输入框
- 统一上传附件按钮
- 发送按钮
- 停止按钮

##### 4. 当前会话操作区

- 重命名当前会话
- 删除当前会话

#### 页面交互要求

##### 会话切换

- 点击侧边栏会话，右侧立即加载对应消息
- 切换过程中要有 loading 状态

##### 发送消息

- 回车发送
- `Shift + Enter` 换行
- 发送时按钮状态变化
- 发送后用户消息立刻插入线程

##### 流式响应

- 回复生成中显示“正在思考”状态
- 文本逐步追加显示
- 用户可点击“停止生成”

##### 附件行为

- 图片和文档显示在输入框上方的待发送区域
- 发送成功后附件挂到对应用户消息上
- 发送失败时附件仍保留，允许重试

#### 页面异常状态

- 会话加载失败
- 消息发送失败
- 流式中断
- 上传失败
- 附件解析失败

#### 页面空状态

- 无会话时显示欢迎页
- 当前会话无消息时显示引导文案

## 5. 核心业务流程需求

### 5.1 新建会话流程

#### 目标

用户点击“新建会话”后，立刻得到一个新的聊天线程。

#### 流程

1. 用户点击新建会话
2. 前端请求创建 conversation
3. 后端返回新会话 ID
4. 前端切换到该会话
5. 消息区显示空状态

#### 验收标准

- 新会话在侧边栏立即可见
- 可直接输入第一条消息
- 刷新页面后该会话仍存在

---

### 5.2 文本聊天流程

#### 目标

用户发送文本后，AI 能基于当前会话上下文连续回答。

#### 流程

1. 用户输入文本
2. 前端创建本地待发送消息
3. 后端保存用户消息
4. 后端加载会话历史
5. 后端组装模型输入
6. 后端调用 Ollama 流式生成
7. 前端实时展示流式内容
8. 回复完成后保存 AI 消息

#### 验收标准

- 可连续多轮问答
- 上一轮内容会影响下一轮回答
- 页面刷新后消息仍可查看

---

### 5.3 图片聊天流程

#### 目标

用户上传图片并提问，模型能结合图片和文本回答。

#### 流程

1. 用户选择图片
2. 前端展示缩略图
3. 前端发送图片和文本
4. 后端保存图片
5. 后端将图片与文本共同传给模型
6. 前端流式显示回答

#### 边界要求

- 支持单张图片发送
- 第一版不要求多图批量复杂推理

#### 验收标准

- 至少能完成“描述图片内容”“回答图片中的显式信息”这类问题
- 图片在消息中有可见记录

---

### 5.4 文档聊天流程

#### 目标

用户上传文档后，模型能基于文档内容回答当前问题。

#### 流程

1. 用户选择文档
2. 前端显示文件名与类型
3. 后端上传并保存文件
4. 后端解析文本
5. 解析文本作为当前轮上下文或本会话临时上下文
6. 用户输入问题
7. 后端将问题与文档内容一起喂给模型
8. 前端展示回答

#### 边界要求

- 第一版只做“聊天附件上下文”
- 不做向量索引
- 不做长期知识库

#### 验收标准

- 能对上传文档做总结、摘要、提问
- 解析失败时要明确报错，不可静默失败

---

### 5.5 停止生成流程

#### 目标

用户在模型生成过程中，可以主动停止。

#### 流程

1. 用户点击停止
2. 前端中断当前流
3. 后端中止当前推理请求
4. 已生成内容保留为部分回答
5. 消息状态标记为已中止

#### 验收标准

- 点击后 1 秒内前端停止继续输出
- 保留已生成部分

---

### 5.6 会话删除流程

#### 目标

用户删除会话后，对应数据不再显示。

#### 流程

1. 用户点击删除
2. 前端二次确认
3. 后端删除 conversation、messages、attachments 关联记录
4. 前端侧边栏刷新

#### 验收标准

- 删除后会话从列表消失
- 再次刷新页面不再出现

---

## 6. 详细功能清单

下面按模块进一步拆细。

### 6.1 会话管理模块

#### 必须支持

- 新建会话
- 列出所有会话
- 查看会话详情
- 重命名会话
- 删除会话

#### 建议行为

- 第一条用户消息发送后自动生成标题
- 用户也可手动改标题
- 最近更新的会话排在前面

#### 不做

- 多层文件夹分类
- 会话共享链接
- 团队协作会话

---

### 6.2 消息模块

#### 消息类型

第一版至少支持：

- `user`
- `assistant`
- `system`

其中页面上默认只展示：

- `user`
- `assistant`

#### 消息状态

建议支持：

- `sending`
- `streaming`
- `done`
- `failed`
- `stopped`

#### 必须支持

- 发送消息
- 流式接收回复
- 保存消息
- 展示消息创建时间
- 展示失败状态

#### 推荐支持

- 重新生成最后一条回答
- 编辑上一条用户消息

#### 不做

- 多分支对话树
- 消息级点赞 / 点踩
- 复杂消息 reaction

---

### 6.3 附件模块

#### 支持文件类型

##### 图片

- `png`
- `jpg`
- `jpeg`
- `webp`

##### 文档

- `txt`
- `md`
- `pdf`
- `docx`

#### 必须支持

- 文档单文件建议限制在 `20MB` 以内

## 7. 上下文治理需求

### 7.1 目标定义

本项目里的“上下文治理”不是简单做历史截断，而是要解决 4 个问题：

1. 同一会话内模型能连续追问，不丢主线
2. 历史越来越长时，不能无限膨胀
3. 文本、图片、文档附件不能无序互相挤占上下文
4. 要为后续长期记忆和缓存命中优化预留空间

### 7.2 第一阶段必须满足

第一阶段至少要做到：

- 同一会话内可追问
- 新建会话默认无历史
- 切换会话后上下文隔离
- 最近若干轮消息保留原文
- 当前轮图片和文件内容可以进入上下文
- system prompt 稳定注入
- 超出预算时有可控裁剪

### 7.3 第一阶段上下文结构

第一阶段建议把模型输入拆成这些层：

1. `system_prompt`
2. 会话级近期消息
3. 当前用户消息
4. 当前轮图片附件
5. 当前轮文件附件解析文本

这 5 层在后端必须有明确拼接顺序，不能随意漂移。

### 7.4 第二阶段上下文治理需求

在第一阶段稳定后，第二阶段建议补上：

- 历史消息摘要压缩
- 附件内容预算控制
- 会话级上下文统计
- 可视化上下文组成
- 基础长期记忆

### 7.5 长期记忆需求边界

长期记忆不是“保存全部聊天记录”，而是只沉淀这些高价值信息：

- 用户长期偏好
- 当前项目长期目标
- 多次会话重复出现的重要事实

当前已经实现手动长期记忆、模型建议记忆、规则级去重/冲突提示、来源字段记录和来源会话可视化。

当前长期记忆仍需明确控制这些边界：

- 不是向量检索
- 不是自动长期记忆
- 不是全历史扫描
- 去重/冲突检测是规则级，不是 embedding 语义级
- 来源追踪已经有字段和来源会话跳转，但还没有做“点击查看来源消息并高亮定位”的交互

### 7.6 上下文治理必须控制的边界

- 不能无限拼全部历史
- 不能把所有附件全文永久保留在工作上下文
- 要根据消息轮数、字符数或 token 预算裁剪
- 不同类型内容要有不同优先级
- 中间过程、日志类内容后续要优先清理

### 7.7 第一阶段不做

第一阶段先不做：

- 跨会话自动知识融合
- 复杂用户画像系统
- 向量化长期记忆库
- 智能工具日志折叠系统
- 面向 Agent 的多任务上下文编排

## 8. 错误与异常处理需求

第一版必须把错误处理做出来，否则产品会非常像半成品。

### 8.1 模型服务错误

必须能识别并提示：

- Ollama 服务未启动
- 地址不可达
- 模型不存在
- 推理失败
- 响应超时

### 8.2 上传错误

必须能识别并提示：

- 文件类型不支持
- 文件过大
- 图片损坏
- 文档解析失败

### 8.3 会话错误

必须能识别并提示：

- 会话不存在
- 消息加载失败
- 会话删除失败

### 8.4 前端交互要求

- 错误要给出明确文案
- 不允许只在控制台报错
- 用户可感知失败原因

## 9. 非功能性要求

这些不是“功能按钮”，但第一版也要定边界。

### 9.1 响应式

必须支持：

- 桌面端正常使用
- 手机端基本可用

### 9.2 性能要求

第一版不做极致优化，但至少要满足：

- 会话切换不能明显卡死
- 消息列表加载不能阻塞数秒
- 流式开始等待时间尽量可控

### 9.3 可维护性

必须满足：

- 前后端分离
- 代码模块清晰
- 配置集中管理

### 9.4 安全性

第一版至少要注意：

- 上传文件类型校验
- 后端接口基本参数校验
- 不把敏感配置直接暴露给前端

## 10. 第一版验收标准

这一节最重要。后面开发完成后，就是按它验收。

### 10.1 产品验收标准

第一版完成后，至少应该做到：

1. 用户可以进入聊天页并新建会话
2. 用户可以连续发送多轮文本消息
3. 用户可以看到 AI 流式回复
4. 刷新页面后，会话和消息仍然存在
5. 用户可以切换历史会话继续聊
6. 用户可以上传图片并发起多模态提问
7. 用户可以上传文档并基于文档问答
8. 用户可以删除、重命名会话
8. 用户可以删除、重命名会话
9. 页面支持 Markdown 和代码块复制
10. 当 Ollama 或上传发生异常时，页面有明确提示

### 10.2 技术验收标准

至少满足：

- 前后端分离
- 后端可独立启动
- 前端可独立启动
- 聊天接口支持流式输出
- 数据库持久化会话与消息
- 附件有独立存储记录

### 10.3 不作为第一版验收阻塞项的内容

以下内容即使没做，也不影响第一版成立：

- 登录
- 会话搜索
- 深浅主题切换
- 重新生成
- 编辑消息
- provider API Key 配置

这些可以作为下一轮迭代目标。
