# 详细需求清单

本文档是在 [04_智能问答网页方案.md](/disk2/gengnan/ai_web_studio/docs/04_智能问答网页方案.md:1) 基础上的进一步收敛版本，目标是把第一版产品的功能边界定死，避免后续开发过程中范围漂移。

本文档主要解决 4 个问题：

1. 第一版到底做什么，不做什么
2. 每个页面和功能具体需要支持什么交互
3. 核心业务流程应该如何跑通
4. 完成到什么程度算“可交付”

## 1. 项目范围结论

### 1.1 第一版产品名称

先沿用上一版方案中的名称：

**Ollama 多模态智能问答工作台**

### 1.2 第一版目标

第一版目标不是做成一个全能 AI 平台，而是做成一个：

- 前后端分离
- 可持续迭代
- 支持本地 Ollama
- 支持多轮聊天
- 支持图片与文档附件
- 具备完整 Web 产品基本形态

的多模态智能问答网页。

### 1.3 第一版核心价值

从用户视角，第一版要提供的是：

- 一个像 ChatGPT / 豆包 / DeepSeek 的聊天网页
- 能调用本地 `qwen3.5:27b-q8_0`
- 能保存历史会话
- 能上传图片问问题
- 能上传文档让模型分析
- 能流式看到回答

### 1.4 第一版明确不做

为了确保开发聚焦，第一版明确不做这些：

- 不做 RAG 知识库索引
- 不做向量检索
- 不做 Agent / LangGraph 工作流
- 不做联网搜索
- 不做插件系统
- 不做语音输入
- 不做复杂权限体系
- 不做多租户
- 不做企业后台
- 不做移动端原生 App

### 1.5 第一版默认模型

- 默认模型：`qwen3.5:27b-q8_0`
- 默认推理服务：本地 `Ollama`

### 2.2 `P0.5` 建议尽快完成

这一层不是第一版最小闭环必须项，但它会明显提升产品完成度和后续简历表达质量。

- 上下文统计与可视化
- 上下文预算控制
- 历史消息摘要压缩
- 长会话上下文裁剪策略优化
- 附件内容按需展开和索引化展示
- 长期记忆雏形

补充说明：

- “上下文预算控制”当前已经进入第一阶段落地：后端已有动态预算框架，预算会根据 provider、用户配置的上下文窗口、上下文模式自动计算
- “上下文统计与可视化”当前已完成第一版落地：后端会返回预算与裁剪统计，前端已提供按钮式上下文治理诊断弹层与提示区
- “历史消息摘要压缩”当前已完成第二阶段升级：滚动摘要刷新时优先调用当前 provider/model 生成模型摘要，失败或返回空时自动回退到规则式摘要
- “长期记忆雏形”当前已完成 MVP：支持用户手动新增、启停、删除长期记忆，并在聊天上下文中按预算注入
- “模型建议记忆”当前已完成第一版：可从当前会话提取候选长期记忆，由用户确认后保存
- “记忆冲突治理”当前已完成规则版：候选记忆会提示可能重复、可能冲突或建议保存，并记录来源会话信息
- “缓存友好型 Prompt 结构”当前已完成第一版：后端通过 `ContextPromptBuilder` 固定上下文层级顺序，前端诊断面板可展示 Prompt 模板和上下文层级信息
- “附件内容按需展开”当前已完成第一版：当前轮文档会被切成片段，并按用户问题做关键词级相关性筛选后再注入上下文
- “附件片段可视化预览”当前已完成第一版：前端上下文诊断弹层可以查看已选附件片段摘要，并支持点击展开更长片段
- “tokenizer 级预算与摘要质量观测”当前已完成第一版：后端已引入 `TokenizerEstimator`，可返回总 Token 估算、附件 Token、摘要 Token、摘要源 Token、压缩比等指标
- “prompt prefix hash 与缓存命中观测”当前已完成第一版：后端会对稳定前缀做 hash 与 token 估算，并给出“是否复用上一轮稳定前缀”的启发式观测
- 当前真正未完成的重点，已经收敛为：附件索引化持久化、语义级记忆去重、来源消息级高亮定位、更精细缓存优化

- Project / 工作区：基础雏形已提前完成，后续可扩展为项目文件库、项目级统计、项目成员、项目级默认上下文策略
- API Key / Base URL 自定义 provider
- 分享会话
- 会话导出：基础 Markdown / JSON 导出已提前完成，后续可扩展为带附件打包、分享链接和导出范围选择
- Prompt 模板：基础 CRUD、可见范围和显式应用目标已提前完成，后续可扩展为变量占位符、分类、快捷插入和团队共享
- 多模型并行比较
- 后续接 RAG
- 后续接 Agent

### 2.5 上下文治理专项说明

上下文治理在本项目里的目标不是简单截断历史消息，而是：

- 保证短期多轮问答的连续性
- 避免长会话把上下文窗口撑爆
- 避免附件、图片、系统提示互相抢占预算
- 为后续长期记忆和缓存命中优化留接口

第一版上下文治理优先级建议：

1. 近期消息保留
2. 附件内容拼接
3. 上下文预算控制
4. 摘要压缩
5. 长期记忆
6. 缓存命中优化

当前阶段说明：

- 第 1 到第 3 项已经完成第一阶段实现
- 第 4 项已经进入第二阶段实现：
  当前已具备“最近原始消息窗口 + 会话级滚动摘要”的基础分层能力，并已接入“模型摘要优先 + 规则摘要兜底”的滚动摘要刷新策略
- 第 5 项已经完成手动长期记忆 MVP、模型建议记忆第一版、规则级冲突治理和来源追踪
- 第 6 项已经完成缓存友好型 Prompt 结构第一版，并已补上 prefix hash / 稳定前缀复用观测；更精细缓存优化仍属于后续重点方向

当前对这条主线更准确的阶段判断是：

- `P0` 已基本成立
- 当前主要处于 `P0.5` 阶段性收尾位置：上下文治理第一阶段闭环已经基本成型
- 现阶段不建议全面切到 `P2`
- 下一步更合理的是：以 `P1` 产品能力补完为主线，同时把上下文治理剩余深水区问题作为专项继续迭代

第一版暂不做：

- 复杂知识库检索
- 复杂 agent memory
- 自动跨会话知识融合
- 多模型记忆对齐

## 3. 用户角色定义

### 3.1 第一版角色简化

第一版先按两种模式考虑：

#### 模式 A：单用户模式

特点：

- 无需登录
- 所有会话属于当前本地用户
- 开发速度快

#### 模式 B：基础登录模式

特点：

- 支持注册 / 登录
- 会话按用户隔离
- 每个用户有独立设置

### 3.2 当前推荐策略

这部分属于早期规划时的建议，当前实际实现已经发生变化。

当前真实状态是：

- 产品已经采用基础登录模式
- 已支持注册 / 登录 / 退出登录
- 会话、设置、长期记忆、上传目录都已按用户隔离

所以后续不再按“先单用户再登录”的路线推进，而是直接按：

- 登录态优先
- 用户隔离优先
- 在此基础上继续补产品能力和上下文治理能力

## 4. 页面级需求

第一版页面数量不要过多，建议控制在 3 个主页面以内。

### 4.1 主聊天页

这是第一版的绝对核心页面。

#### 页面目标

让用户完成以下行为：

- 新建或切换会话
- 查看历史消息
- 输入文本
- 上传图片或文档
- 流式接收 AI 回复
- 管理当前会话

#### 页面布局建议

- 左侧：会话侧边栏
- 中间：消息线程
- 底部：输入区
- 顶部：会话标题 + 设置入口

#### 页面必须具备的模块

##### 1. 会话侧边栏

- 新建会话按钮
- 会话列表
- 当前会话高亮
- 每条会话显示标题
- 每条会话支持展开操作菜单

##### 2. 消息线程区

- 展示用户消息
- 展示 AI 消息
- 展示消息附件
- 展示加载 / 生成中状态
- 支持 Markdown
- 支持代码块复制

##### 3. 输入区

- 文本输入框
- 统一上传附件按钮
- 发送按钮
- 停止按钮

##### 4. 当前会话操作区

- 重命名当前会话
- 删除当前会话

#### 页面交互要求

##### 会话切换

- 点击侧边栏会话，右侧立即加载对应消息
- 切换过程中要有 loading 状态

##### 发送消息

- 回车发送
- `Shift + Enter` 换行
- 发送时按钮状态变化
- 发送后用户消息立刻插入线程

##### 流式响应

- 回复生成中显示“正在思考”状态
- 文本逐步追加显示
- 用户可点击“停止生成”

##### 附件行为

- 图片和文档显示在输入框上方的待发送区域
- 发送成功后附件挂到对应用户消息上
- 发送失败时附件仍保留，允许重试

#### 页面异常状态

- 会话加载失败
- 消息发送失败
- 流式中断
- 上传失败
- 附件解析失败

#### 页面空状态

- 无会话时显示欢迎页
- 当前会话无消息时显示引导文案

## 5. 核心业务流程需求

### 5.1 新建会话流程

#### 目标

用户点击“新建会话”后，立刻得到一个新的聊天线程。

#### 流程

1. 用户点击新建会话
2. 前端请求创建 conversation
3. 后端返回新会话 ID
4. 前端切换到该会话
5. 消息区显示空状态

#### 验收标准

- 新会话在侧边栏立即可见
- 可直接输入第一条消息
- 刷新页面后该会话仍存在

---

### 5.2 文本聊天流程

#### 目标

用户发送文本后，AI 能基于当前会话上下文连续回答。

#### 流程

1. 用户输入文本
2. 前端创建本地待发送消息
3. 后端保存用户消息
4. 后端加载会话历史
5. 后端组装模型输入
6. 后端调用 Ollama 流式生成
7. 前端实时展示流式内容
8. 回复完成后保存 AI 消息

#### 验收标准

- 可连续多轮问答
- 上一轮内容会影响下一轮回答
- 页面刷新后消息仍可查看

---

### 5.3 图片聊天流程

#### 目标

用户上传图片并提问，模型能结合图片和文本回答。

#### 流程

1. 用户选择图片
2. 前端展示缩略图
3. 前端发送图片和文本
4. 后端保存图片
5. 后端将图片与文本共同传给模型
6. 前端流式显示回答

#### 边界要求

- 支持单张图片发送
- 第一版不要求多图批量复杂推理

#### 验收标准

- 至少能完成“描述图片内容”“回答图片中的显式信息”这类问题
- 图片在消息中有可见记录

---

### 5.4 文档聊天流程

#### 目标

用户上传文档后，模型能基于文档内容回答当前问题。

#### 流程

1. 用户选择文档
2. 前端显示文件名与类型
3. 后端上传并保存文件
4. 后端解析文本
5. 解析文本作为当前轮上下文或本会话临时上下文
6. 用户输入问题
7. 后端将问题与文档内容一起喂给模型
8. 前端展示回答

#### 边界要求

- 第一版只做“聊天附件上下文”
- 不做向量索引

## 7. 上下文治理需求

### 7.1 目标定义

本项目里的“上下文治理”不是简单做历史截断，而是要解决 4 个问题：

1. 同一会话内模型能连续追问，不丢主线
2. 历史越来越长时，不能无限膨胀
3. 文本、图片、文档附件不能无序互相挤占上下文
4. 要为后续长期记忆和缓存命中优化预留空间

### 7.2 第一阶段必须满足

第一阶段至少要做到：

- 同一会话内可追问
- 新建会话默认无历史
- 切换会话后上下文隔离
- 最近若干轮消息保留原文
- 当前轮图片和文件内容可以进入上下文
- system prompt 稳定注入
- 超出预算时有可控裁剪

### 7.3 第一阶段上下文结构

第一阶段建议把模型输入拆成这些层：

1. `system_prompt`
2. 会话级近期消息
3. 当前用户消息
4. 当前轮图片附件
5. 当前轮文件附件解析文本

这 5 层在后端必须有明确拼接顺序，不能随意漂移。

### 7.4 第二阶段上下文治理需求

在第一阶段稳定后，第二阶段建议补上：

- 历史消息摘要压缩
- 附件内容预算控制
- 会话级上下文统计
- 可视化上下文组成
- 基础长期记忆

### 7.5 长期记忆需求边界

长期记忆不是“保存全部聊天记录”，而是只沉淀这些高价值信息：

- 用户长期偏好
- 当前项目长期目标
- 多次会话重复出现的重要事实

当前已经实现手动长期记忆、模型建议记忆、规则级去重/冲突提示、来源字段记录和来源会话可视化。

当前长期记忆仍需明确控制这些边界：

- 不是向量检索
- 不是自动长期记忆
- 不是全历史扫描
- 去重/冲突检测是规则级，不是 embedding 语义级
- 来源追踪已经有字段和来源会话跳转，但还没有做“点击查看来源消息并高亮定位”的交互

### 7.6 上下文治理必须控制的边界

- 不能无限拼全部历史
- 不能把所有附件全文永久保留在工作上下文
- 要根据消息轮数、字符数或 token 预算裁剪
- 不同类型内容要有不同优先级
- 中间过程、日志类内容后续要优先清理

### 7.7 第一阶段不做

第一阶段先不做：

- 跨会话自动知识融合
- 复杂用户画像系统
- 向量化长期记忆库
- 智能工具日志折叠系统
- 面向 Agent 的多任务上下文编排

## 15. P3：个人知识库与工作区知识召回

### 15.1 P3 目标

P3 的目标是把当前“上传附件进入当前轮上下文”升级为“工作区知识库”。

完成后，用户应该可以：

- 在工作区中长期保存文件
- 文件上传后自动解析、切分和索引
- 后续提问时，即使不重新上传文件，系统也能从工作区历史文件中召回相关片段
- 回答中可以展示使用了哪些文件和片段
- 用户可以查看、删除、重建文件索引

### 15.2 P3-1：附件片段持久化索引

需求说明：

- 当前文档解析结果只服务于当前轮上下文，缺少可复用的 chunk 存储。
- 需要新增 `attachment_chunks` 或类似表，将文档解析后的片段持久化。
- 第一版先不做 embedding，只做文本 chunk 和元数据管理。

建议字段：

- `id`
- `attachment_id`
- `conversation_id`
- `project_id`
- `message_id`
- `user_id`
- `chunk_index`
- `content`
- `content_hash`
- `char_count`
- `estimated_tokens`
- `page_number`
- `section_title`
- `source_file_name`
- `mime_type`
- `created_at`
- `updated_at`

前端需求：

- 附件预览中显示索引状态：
  - 未索引
  - 索引中
  - 已索引
  - 索引失败
- 附件详情中展示 chunk 数量、字符数、token 估算。
- 工作区文件库中展示文件是否已生成知识片段。

后端需求：

- 上传文档并解析后，自动生成 chunk。
- 支持根据 attachment 查询 chunk。
- 支持删除附件时级联删除 chunk 或标记删除。
- 支持重复文件 hash 复用，避免同一文件重复解析。

验收标准：

1. 上传 `txt / md / pdf / docx` 后，数据库能看到对应 chunk。
2. chunk 能关联到附件、会话、工作区和用户。
3. 前端能看到文件索引状态。
4. 不影响当前附件进入上下文的既有能力。
5. 后端异常时不阻塞普通聊天，前端能提示索引失败。

### 15.3 P3-2：工作区文件库升级为知识库

需求说明：

- 当前工作区文件库只是文件挂载和统计雏形。
- 需要把工作区文件库升级为“项目知识库”入口。

功能需求：

- 工作区文件列表展示：
  - 文件名
  - 文件类型
  - 文件大小
  - 上传时间
  - 所属会话
  - chunk 数量
  - 索引状态
  - 最近召回时间
- 文件操作：
  - 预览
  - 删除
  - 重新解析
  - 重建索引
  - 启用 / 禁用参与召回
- 工作区统计：
  - 文件总数
  - 已索引文件数
  - chunk 总数
  - 总 token 估算
  - 最近 7 天新增文件数

验收标准：

1. 用户能在工作区查看所有知识文件。
2. 用户能禁用某个文件参与召回。
3. 用户能删除文件索引，不影响历史消息展示。
4. 用户能重新解析失败文件。

### 15.4 P3-3：跨历史附件召回

需求说明：

- 用户在某个工作区提问时，系统应从该工作区历史文件 chunk 中召回相关内容。
- 第一版使用可解释的关键词 / 简单相关性召回，不急着引入 embedding。

召回范围：

- 当前会话附件 chunk
- 当前工作区文件库 chunk
- 用户显式选择的文件 chunk
- 可选：长期记忆

第一版评分策略：

- chunk 内容命中用户问题关键词：加分
- 文件名命中关键词：加分
- section title 命中关键词：加分
- 当前会话文件：加分
- 用户手动选择文件：高优先级加分
- 最近上传文件：轻微加分
- 禁用文件：不参与召回

后端需求：

- 新增 `knowledge_retrieval_service`
- 输入：
  - `query`
  - `project_id`
  - `conversation_id`
  - `selected_attachment_ids`
  - `top_k`
  - `token_budget`
- 输出：
  - chunk 列表
  - 分数
  - 命中原因
  - 来源文件
  - 来源页码 / 段落

前端需求：

- 聊天设置中增加“启用工作区知识召回”开关。
- 输入区可选择“本轮仅使用当前附件 / 使用工作区知识库 / 不使用知识库”。
- 回答后上下文面板显示被召回的知识片段。

验收标准：

1. 用户不重新上传文件，也能问历史文件内容。
2. 系统能显示本轮召回了哪些文件片段。
3. 被禁用的文件不会参与召回。
4. 超出预算时，低分 chunk 会被裁掉，并在诊断中说明。

### 15.5 P3-4：引用来源与片段预览

需求说明：

- RAG 系统必须能解释答案来源。
- 第一版不要求模型回答中自动插入复杂引用标记，但上下文面板必须能查看来源。

功能需求：

- 回答下方或上下文面板显示“本轮参考来源”。
- 每个来源包含：
  - 文件名
  - chunk 序号
  - 页码 / 段落
  - 片段预览
  - 命中分数
  - 命中原因
- 点击来源可打开附件预览并定位到片段。

验收标准：

1. 每轮知识库问答都能查看来源。
2. 来源可以追溯到具体文件和 chunk。
3. 不显示内部 storage path 等敏感路径。
4. 导出会话时可选择是否包含引用来源。

### 15.6 P3-5：知识召回接入上下文治理

需求说明：

- 知识片段不能无脑塞入 Prompt。
- 必须接入现有上下文预算系统。

预算优先级建议：

1. System Prompt / 工作区 System Prompt
2. 当前用户问题
3. 当前轮附件
4. 关键最近消息
5. 会话摘要
6. 长期记忆
7. 工作区知识 chunk
8. 更早历史消息

诊断需求：

- 展示知识 chunk 的 token 占用。
- 展示保留 / 裁剪的 chunk。
- 展示裁剪原因：
  - 超出预算
  - 分数较低
  - 文件被禁用
  - 与当前问题相关性不足

验收标准：

1. 长文档召回不会撑爆上下文。
2. 诊断面板能解释知识片段选择过程。
3. 不破坏普通聊天体验。

### 16.2 P4-2：轻量多通道检索

需求说明：

建议通道：

后处理器：

- 去重
- 分数归一化
- 文件启用状态过滤

验收标准：

1. 各通道可独立启停。
2. 召回结果能记录通道来源。
3. 后处理过程能进入 Trace。
4. 同一 chunk 不会重复注入。

### 16.3 P4-3：问题重写与多轮消歧

需求说明：

Ragent 在聊天链路中会做记忆加载、问题重写、意图解析和歧义引导。我们可以先做轻量版本。

功能需求：

- 多轮省略问题重写：
  - 用户问“那它怎么配置？”时，结合上一轮补全指代。
- 知识库问答改写：
  - 把口语问题改写为更适合检索的关键词。
- 歧义澄清：
  - 当工作区有多个可能相关文件，但问题不明确时，先向用户确认。

验收标准：

1. 用户追问时召回准确率提升。
2. 问题重写结果能在 Trace 中查看。
3. 用户可以关闭问题重写。

### 16.4 P4-4：模型能力声明与路由

需求说明：

当前支持 provider 和模型切换，但还没有完整模型能力层。

需要新增模型能力：

- 是否支持文本
- 是否支持图片
- 是否支持长上下文
- 是否支持 tool calling
- 是否支持 JSON 输出
- 最大上下文
- 推荐输出 token
- 是否启用 thinking
- 是否本地模型

模型健康记录：

- 最近成功时间
- 最近失败时间
- 连续失败次数
- 平均首 token 延迟
- 平均总耗时
- 最近错误类型

路由策略：

- 默认模型
- 工作区默认模型
- 图片问题优先多模态模型
- 长文档问题优先长上下文模型
- 失败后提示用户切换备用模型

验收标准：

1. 前端设置页能看到模型能力标签。
2. 图片请求不会误发到纯文本模型。
3. 模型连续失败时，前端给出明确提示。
4. Trace 记录实际使用模型和 provider。

### 16.5 P4-5：知识库管理面板

工作区弹窗已经不适合承载后续知识库能力，需要升级为轻量管理页面或右侧面板。

验收标准：

## 19. P2.5：深度思考按钮

### 19.1 背景

当前前端已有“思考中”文案，但它只表示模型尚未返回首个 token，不是真正的模型 reasoning。后端当前也明确关闭了 thinking：

- Ollama 请求中 `think=false`
- OpenAI-compatible 请求中 `extra_body={"enable_thinking": False}`

因此，如果要做类似 ChatGPT / 豆包 / DeepSeek 的“深度思考”，需要从 provider 参数、流式协议、前端展示和数据持久化四层一起设计。

### 19.2 需求目标

目标：

- 用户可在发送前选择是否启用深度思考。
- 系统能根据当前 provider / model 能力决定是否可用。
- 支持 provider 返回的可见 thinking / reasoning summary 流式展示。
- 不支持可见思考的模型，也要明确提示“已尝试开启，但该模型不返回可见思考过程”。
- 深度思考的耗时、是否启用、是否返回可见 reasoning，要进入上下文/Trace 诊断。

非目标：

- 不承诺获取所有模型的完整原始思维链。
- 不用 Prompt 伪造“思考过程”。
- 不把当前 loading 文案当成真实 thinking。

### 19.3 前端需求

输入区：

- 新增 `深度思考` toggle。
- 与 `联网搜索`、`上传附件`、`发送` 放在同一输入操作区。
- 默认关闭。
- 当前模型明确不支持时置灰。
- 当前模型能力未知时允许开启，但 tooltip 提示“将尝试开启，失败时降级为普通回答”。

生成中展示：

- 如果后端返回 reasoning chunk，则在回答区域显示折叠块。
- 折叠块标题：
  - 返回完整 thinking：`思考过程`
  - 返回 summary：`思考摘要`
  - 只启用但无可见内容：`深度思考已启用`
- 默认折叠，避免占用聊天区。
- 流式输出时支持 thinking 和 answer 两条流分离展示。

历史消息展示：

- 已完成消息若有 reasoning 内容，切换会话后仍能看到折叠块。
- 导出时可选择是否包含 reasoning。
- 分享页默认不展示 reasoning，后续可做分享权限开关。

### 19.4 后端需求

请求字段：

```text
ChatStreamRequest
  thinking_enabled: bool = false
  thinking_budget: int | None
```

设置字段：

```text
UserSetting
  default_thinking_enabled
  default_thinking_budget
```

模型能力字段：

```text
model_capabilities
  supports_thinking
  supports_reasoning_stream
  supports_thinking_budget
  reasoning_visibility: none | summary | full | provider_specific
```

消息持久化字段建议：

```text
messages
  reasoning_content
  reasoning_summary
  thinking_enabled
  thinking_elapsed_ms
  reasoning_visible
```

如果不想扩展 `messages` 表，也可以先新增：

```text
message_reasoning
  id
  message_id
  provider
  model
  thinking_enabled
  visibility
  content
  summary
  elapsed_ms
  created_at
```

### 19.5 Provider 适配需求

Ollama：

- 使用 `/api/chat` 的 `think` 字段。
- `think=false`：普通回答。
- `think=true` 或 provider 支持的模式：启用思考。
- 流式解析 `message.thinking` 与 `message.content`。

SiliconFlow / Qwen / OpenAI-compatible：

- 对支持 thinking 的 provider profile 使用：

```json
{
  "enable_thinking": true,
  "thinking_budget": 4096
}
```

- 对不支持 thinking 的通用 OpenAI-compatible provider 不默认发送扩展字段，避免 400。
- 流式解析要兼容：
  - `choices[].delta.reasoning_content`
  - `choices[].delta.content`
  - provider-specific `reasoning` / `thinking` 字段

OpenAI 官方：

- Chat Completions 和 Responses API 的推理能力不同。
- 不应假设 OpenAI 返回 raw chain-of-thought。
- 如果后续接 OpenAI Responses API，则优先展示 reasoning summary / reasoning events。

Gemini / Claude：

- 暂不作为第一版 provider，但能力模型要预留：
  - Claude Extended Thinking：thinking budget + thinking blocks。
  - Gemini Thinking：thinking budget + thought summary。

### 19.6 验收标准

1. 选择支持 thinking 的 Ollama 模型时，开启按钮后后端实际发送 `think=true`。
2. 选择 SiliconFlow 支持 thinking 的模型时，开启按钮后后端实际发送 `enable_thinking=true`。
3. 如果 provider 返回 reasoning chunk，前端能与最终回答分开展示。
4. 如果 provider 不返回可见 reasoning，前端不报错，并显示合理提示。
5. 切换会话后，已保存的 reasoning 仍可查看。
6. 上下文/Trace 面板能看到 `thinking_enabled`、`reasoning_visible`、`thinking_elapsed_ms`。
7. 普通回答路径不受影响，默认仍关闭 thinking。

## 20. P2.5：联网搜索按钮

### 20.1 背景

第一版需求曾明确“不做联网搜索”，这是 MVP 边界。现在项目已经具备多 provider、上下文治理、引用来源、导出和工作区基础，可以把联网搜索作为 ChatGPT / 豆包 / DeepSeek 类产品体验的下一步补齐。

联网搜索不能只是在 Prompt 里写“请联网搜索”，因为本地 Ollama 没有浏览器能力，OpenAI-compatible API 也未必支持原生 web search。更稳的做法是由应用后端调用搜索 API，再把搜索结果作为上下文交给模型。

### 20.2 需求目标

目标：

- 用户可在发送前点击 `联网搜索`。
- 后端先检索互联网，再把搜索结果作为上下文注入模型。
- 本地 Ollama 和在线 OpenAI-compatible provider 都能使用。
- 回答中有来源引用。
- 前端能展示本轮搜索 query、来源卡片和引用。
- 搜索结果进入上下文治理预算和 Trace 诊断。

非目标：

- 第一版不做浏览器自动打开网页深度浏览。
- 第一版不让模型自主无限次搜索。
- 第一版不做公开搜索广场。
- 第一版不默认把用户附件全文发送给搜索 API。

### 20.3 前端需求

输入区：

- 新增 `联网搜索` toggle。
- 单轮生效，发送后默认恢复关闭，避免用户无感把隐私问题发给搜索服务。
- 第一次开启时展示隐私提示：
  - 当前问题会发送给第三方搜索服务。
  - 附件全文不会默认发送。

生成状态：

```text
正在搜索...
已找到 5 条来源
正在生成回答...
```

回答展示：

- 正文支持 `[1] [2]` 形式引用。
- 回答下方展示来源卡片：
  - 序号
  - 标题
  - 域名
  - URL
  - 摘要
  - 发布时间（如果有）
- 点击来源打开原网页。
- 上下文面板展示搜索结果的预算占用和裁剪原因。

设置页：

- 搜索 provider：第一版 `Tavily`
- API key：`TAVILY_API_KEY`
- 搜索深度：`basic / advanced`
- 返回条数：`top_k`

### 20.5 Tavily 第一版实现要求

可以参考旧示例：

```text
/disk2/gengnan/学习hello_agent/01搭建智能体/search.py
```

旧示例已经使用：

- `TavilyClient`
- `TAVILY_API_KEY`
- `search_depth="basic"`
- `include_answer=True`

新项目里不要直接复用为单函数，而应封装为 provider：

- API key 从用户设置或环境变量读取。
- 返回结构统一为 `SearchResult`。
- `include_answer` 可保留，但第一版不要把 Tavily answer 当最终回复，只作为搜索摘要参考。
- 要记录搜索失败原因和耗时。

### 20.6 与上下文治理的关系

联网搜索结果应成为新的上下文层：

```text
system
long_term_memory
conversation_summary
web_search_results
recent_history
current_attachment_context
current_user_message
```

预算建议：

- conservative：最多 10%-15% 输入预算。
- balanced：最多 15%-25% 输入预算。
- long-context：最多 25%-35% 输入预算。

优先级：

1. 当前用户问题
2. system prompt
3. 当前轮附件片段
4. 联网搜索结果
5. 最近历史
6. 会话摘要
7. 长期记忆

原因是联网搜索多用于实时问题，如果用户主动打开搜索，其优先级应高于旧历史，但不应挤掉当前问题和系统约束。

### 20.7 验收标准

1. 前端点击 `联网搜索` 后，本轮请求携带 `web_search_enabled=true`。
2. 后端能调用 Tavily 搜索并返回结构化来源。
3. 模型回答能基于搜索结果生成，并尽量使用 `[1] [2]` 引用。
4. 本地 Ollama 和 OpenAI-compatible provider 都可使用同一套搜索上下文。
5. 前端展示来源卡片。
6. 搜索失败时不导致整个聊天页卡死。
7. 上下文面板能看到搜索结果数量、token 占用、裁剪结果。
8. 导出会话时可以包含搜索来源。

## 21. P2.5 实施顺序建议

这两个能力建议在 P3 知识库主线前或并行插入，因为它们可以提升聊天产品完整度，同时给后续知识库引用、Trace 和模型能力层打基础。

推荐顺序：

1. 深度思考按钮 MVP
   修改范围相对集中，主要在 provider 调用层、流式协议和前端展示。

2. 联网搜索按钮 MVP
   需要新增搜索服务、设置项、来源展示和上下文层，复杂度高于 thinking。

3. 深度思考与联网搜索的 Trace 持久化
   把 thinking、search run、source、latency 记录到后端，避免只存在前端临时状态。

4. 回到 P3 附件片段持久化索引
   搜索来源展示和知识库引用展示可以共用 `SourceCitation` 组件。

暂不建议第一版就做：

- 多搜索 provider 同时并行。
- 浏览器级网页全文抓取。
- 模型自主多轮工具调用。
- Agent 自动规划搜索。
- 搜索结果 embedding 入库。

## 22. P2.6：外部信息源与工具增强平台

### 22.1 背景

`联网搜索` 不能只等价于 Tavily。用户实际想要的是“模型能获取当前上下文外的信息”。这些信息可能来自：

- 通用网页搜索：Tavily、Brave Search、SerpAPI、Exa、OpenAI web_search、Gemini Google Search、Claude web search。
- 垂直 API：天气、地图、路线、POI、股票、汇率、体育、航班。
- 私有知识：工作区知识库、历史附件、长期记忆。
- MCP 工具：高德地图 MCP、百度地图 MCP、GitHub MCP、数据库 MCP、飞书 MCP 等。

如果每种能力都直接写到聊天接口里，项目会快速变成不可维护的功能堆叠。因此需要新增一个 `External Context / Tool Layer`。

### 22.2 P2.6 目标

目标：

- 把 Web Search、天气、地图、知识库召回、MCP 工具都统一抽象成外部信息通道。
- 前端仍然保持简单按钮，不暴露复杂 provider 细节。
- 后端通过统一 Tool Registry、Tool Router、External Context Channel 和 Trace 管理外部调用。
- 搜索结果、天气结果、地图结果、知识库片段都能进入统一来源展示和上下文治理。
- 后续新增一个工具时，只需要新增 provider，不需要改聊天主流程。

非目标：

- 第一版不做完整 Agent 自动规划。
- 第一版不接有副作用的工具。
- 第一版不做可视化工具编排。
- 第一版不把所有 MCP server 都接入。

### 22.3 能力分层

建议拆成五层：

```text
Tool Catalog
  工具注册、工具能力声明、参数 schema、权限声明

Tool Router
  判断本轮是否需要外部信息，选择哪些工具

External Context Channels
  真正执行搜索、天气、地图、知识库、MCP 调用

PostProcessors
  去重、排序、来源归一、预算裁剪、rerank

Context Governance / Prompt Builder
  把工具结果注入 Prompt，并进入上下文诊断
```

### 22.4 工具类型

第一阶段建议只做只读工具：

```text

  通用网页搜索

web_fetch
  指定 URL 网页内容提取，后续做

weather_lookup
  天气查询，可先接 wttr.in 或高德天气

map_geocode
  地址转经纬度

map_poi_search
  地点 / POI 搜索

map_route
  路线规划

workspace_knowledge_search
  工作区知识库召回

current_attachment_search
  当前轮附件片段召回

mcp_tool_call
  MCP 工具调用
```

第二阶段再考虑：

- database_query
- github_search
- lark_doc_search
- calendar_lookup
- finance_quote
- browser_extract

### 22.6 Tool Router 需求

第一版使用规则 + 开关：

- 用户关闭“联网搜索”时，不调用外部 web / weather / map 工具。
- 用户打开“联网搜索”时：
  - 天气类问题优先 `weather_lookup`
  - 地点、路线、附近、距离类问题优先 `map_*`
  - 新闻、政策、价格、版本、网页资料类问题优先 `web_search`
  - 工作区资料类问题优先 `workspace_knowledge_search`

规则示例：

```text

附近 / 路线 / 怎么去 / 公交 / 驾车 / 地址 -> map_poi_search / map_route
今天 / 最新 / 新闻 / 官网 / 价格 / 版本 -> web_search
我上传的 / 文档里 / 工作区 / 资料 -> workspace_knowledge_search
```

第二版再引入 LLM intent classifier：

- 输入用户问题、当前会话、可用工具列表。
- 输出结构化 tool plan。
- 后端仍要校验工具权限和参数。

验收标准：

1. 天气问题不会走普通网页搜索。
2. 地图路线问题不会只返回一堆网页链接。
3. 当前工具不可用时，前端能看到降级原因。

## 23. P2.7：工具路由与意图识别

### 23.1 需求背景

`联网搜索` 打开后，不能每轮都调用所有外部服务。正确行为应该是：

- 用户允许使用外部信息。
- 系统判断本轮是否真的需要外部信息。
- 系统判断应该调用哪个工具。
- 系统限制调用数量、超时、预算和权限。
- 系统把调用原因、置信度和结果写入 Trace。

否则会出现：

- 天气问题同时调用地图和 Tavily。
- 代码问题误调用天气。
- 普通闲聊调用外网。
- 工具返回太多无关内容，污染上下文。
- 调试时不知道为什么调用某个工具。

### 23.2 参考对象

Ragent：

- 用 `IntentTree` 管理意图。
- 意图节点分 `KB / SYSTEM / MCP`。
- 叶子节点包含 description、examples、promptTemplate、mcpToolId。
- LLM 对叶子节点打分。
- 后续按分数和类型过滤出 KB / MCP / SYSTEM。
- MCP 节点单独做参数提取。

Dify：

- Agent 节点支持 Function Calling / ReAct。
- 工具有描述、参数 schema、授权配置。
- 可以设置最大迭代次数。
- 核心是让模型在可用工具集合中选择，而不是全量调用。

Coze：

- 插件和工作流都可以作为能力单元。
- 工具/插件有输入输出定义和 workspace 范围。
- 复杂流程适合封装成 workflow，再由 Agent 调用。

### 23.3 产品需求

前端：

- `联网搜索` 按钮文案保持简单。
- tooltip 改为：`允许本轮使用外部实时信息，系统会按问题自动选择搜索、天气、地图或知识库工具。`
- 回答生成时展示工具计划：
  - `判断需要查询天气`
  - `正在搜索网页`
  - `未调用外部工具：当前问题不需要实时信息`
- 上下文 / Trace 面板展示：
  - 候选工具
  - 实际调用工具
  - 置信度
  - 调用原因
  - 参数摘要
  - 耗时
  - 是否进入 Prompt

后端：

- 新增 Tool Router。
- 新增工具候选生成规则。
- 新增工具置信度阈值。
- 新增最大工具调用数量。
- 新增工具调用预算。
- 所有工具调用都写入 Trace。

### 23.4 路由模式

第一版采用 `规则门控 + 轻量 LLM Router + 后端强校验`。

#### 23.4.1 规则门控

明显问题直接处理：

```text
问候 / 写作 / 翻译 / 代码解释 / 当前上下文总结 -> no_tool
天气 / 温度 / 气温 / 下雨 / 台风 -> weather_lookup
附近 / 路线 / 怎么去 / 地址 / POI -> map_tool
最新 / 今天 / 新闻 / 价格 / 版本 / 官网 / 政策 -> web_search
文档 / 附件 / 上传的 / 工作区 / 资料 -> knowledge_search
```

规则门控输出：

```json
{
  "mode": "no_tool | single_candidate | ambiguous",
  "candidates": ["weather_lookup"],
  "reason": "命中天气关键词"
}
```

#### 23.4.2 轻量 LLM Router

当规则判断不明确，或候选超过一个时，调用 LLM Router。

输入：

- 当前用户问题
- 当前会话简短上下文
- 可用工具列表
- 每个工具的 description / input_schema / examples
- 当前按钮状态

输出：

```json
{
  "should_use_tools": true,
  "calls": [
    {
      "tool_key": "weather.current",
      "confidence": 0.91,
      "reason": "用户询问明天天气",
      "arguments": {"city": "深圳", "date": "2026-05-20"}
    }
  ],
  "fallback": "web_search"
}
```

#### 23.4.3 后端强校验

LLM Router 结果不能直接执行。必须校验：

- 工具是否存在。
- 工具是否启用。
- 用户是否允许外部工具。
- 参数是否符合 schema。
- 是否只读。
- 是否需要用户确认。
- 是否超过最大调用数量。
- 是否超过总超时。

### 23.5 调用策略

默认策略：

- 用户未开启联网搜索：不调用外部网络工具。
- 用户开启联网搜索：允许调用外部工具，但不保证一定调用。
- 工作区知识库和当前附件可以独立于联网搜索，因为它们是本地/私有上下文。
- 默认最多调用 1 个外部工具。
- 多意图明确时最多调用 2 个。
- 工具总超时建议 8-12 秒。
- 单个工具超时建议 3-5 秒。

置信度策略：

```text
weather >= 0.75 -> weather
map >= 0.75 -> map
knowledge >= 0.65 -> knowledge
web_search >= 0.65 -> Tavily / web provider
all low + web_search_enabled -> Tavily 兜底
all low + web_search_disabled -> no_tool
```

Tavily 默认策略：

- Tavily 是默认 web fallback。
- 不是所有问题都先 Tavily。
- 专用工具高置信度时优先专用工具。
- Tavily 适合实时网页资料、新闻、版本、政策、官网资料。

### 23.7 验收标准

8. 工具失败时能降级，不影响整个聊天页。

## 26. P2.7 工具层可观测、可配置与插件化需求

本节对应下一阶段工具层建设。当前不要求一次性实现完整 Agent 平台，而是把已存在的 Tavily、高德天气、高德地图整理成可扩展、可观测、可配置的工具体系。

### 26.1 P2.7.1 工具调用过程可视化

优先级：高。

目标：用户开启联网搜索后，前端应该能看到系统到底有没有调用工具、调用了什么、是否失败、耗时多少，而不是只看到最终答案和来源。

后端流式事件需求：

```json
{"type":"tool_plan","plan":{"should_use_tools":true,"router":"rule_based_v1","calls":[...]}}
{"type":"tool_call_start","call_id":"...","tool_key":"amap.weather.current","display_name":"高德天气","arguments":{"city":"深圳"}}
{"type":"tool_call_end","call_id":"...","tool_key":"amap.weather.current","elapsed_ms":320,"sources_count":1}
{"type":"tool_call_error","call_id":"...","tool_key":"web.tavily.search","error":"timeout","fallback":"none"}
```

前端展示需求：

- 回答生成前显示工具状态条。
- 工具过程默认折叠，类似当前 `思考过程` 和 `来源`。
- 成功显示工具名、耗时、来源数量。
- 失败显示友好提示，不暴露 API Key、完整堆栈和敏感请求参数。
- 历史消息重新打开时仍可查看工具 Trace。

验收标准：

- 天气问题显示“调用高德天气”。
- 地图问题显示“调用高德地图”。
- 最新网页问题显示“调用 Tavily 搜索”。
- 工具失败不会导致前端白屏。
- 工具过程可折叠，不挤占主回答空间。

### 26.2 P2.7.2 外部工具层重构

优先级：高。

当前问题：

- `ExternalContextService` 内部同时包含路由、Tavily 请求、高德请求、地图 query 抽取、结果格式化、Prompt 注入文本组装。
- 后续新增 Brave、Exa、SerpAPI、知识库检索、MCP 时会继续膨胀。

目标结构：

```text
backend/app/services/tools/
  schemas.py
  registry.py
  router.py
  executor.py
  formatter.py
  assembler.py
  trace_repository.py
  providers/
    tavily.py
    amap_weather.py
    amap_map.py
```

核心要求：

- 聊天主流程仍只依赖一个 facade，例如 `ExternalContextService.build_context(...)`。
- 工具实现从 facade 内部拆出去。
- 每个工具必须有 `tool_key`、名称、描述、类别、输入 schema、凭证需求、是否只读、默认超时。
- 工具执行统一经过 `ToolExecutor`，不能在聊天路由里直接写 provider 请求。
- 结果统一转成 `ExternalSource`。

验收标准：

- 拆分后现有 Tavily、高德天气、高德地图行为不变。
- 新增一个工具时不需要修改聊天流主逻辑。
- 工具失败、timeout、fallback 都走统一处理。

### 26.3 P2.7.3 Tool Trace 持久化

优先级：高。

目标：把每轮工具选择和调用过程存入数据库，支撑历史回放、排错、质量分析和后续简历项目亮点。

建议新增表：

```text
tool_route_runs

  router_type
  query
  external_context_allowed
  plan_json
  selected_tools_json
  status
  elapsed_ms
  created_at

tool_call_runs
  id
  route_run_id
  call_id
  tool_key
  provider
  arguments_json
  status
  started_at
  finished_at
  elapsed_ms
  error_message
  sources_count
  sources_json
```

展示需求：

- 历史回答中可以打开“工具过程”。
- 工具过程来自后端持久化数据，而不是只依赖当前前端内存。
- 可以区分“没有调用工具”和“工具调用失败”。

### 26.4 P2.7.4 来源卡片增强

优先级：中高。

当前来源卡片比较通用，适合网页，但不适合天气、地图和未来知识库。

新增卡片类型：

- `WebSourceCard`：网页标题、域名、摘要、score、跳转链接。
- `WeatherSourceCard`：城市、天气、温度、湿度、风向、发布时间。
- `MapPoiSourceCard`：地点名、地址、类型、距离、电话、地图跳转。
- `MapRouteSourceCard`：起终点、距离、耗时、路线步骤。
- `KnowledgeSourceCard`：文件名、页码/chunk、相似度、点击定位。
- `GenericSourceCard`：兜底。

验收标准：

- 天气来源不再显示成普通网页摘要。
- 地图 POI 和路线结果能一眼看出地点、地址、距离和路径信息。
- 后续知识库引用可以复用来源面板结构。

### 26.5 P2.7.5 用户级工具配置

优先级：高。

当前 Tavily / 高德 API Key 写在后端 `.env`。这适合开发测试，但不适合多用户系统。

需求：

- 用户可以在前端配置 Tavily API Key。
- 用户可以在前端配置高德 API Key。
- 可以测试连接是否成功。
- 可以启用/禁用某个工具。
- 可以按工作区覆盖默认工具配置。
- 后端 `.env` 保留为开发 fallback。

配置优先级：

```text
工作区级工具配置
-> 用户级工具配置
-> 后端环境变量 fallback
-> 未配置则禁用该工具并提示
```

安全要求：

- 前端不能回显完整 API Key，只显示掩码。
- 后端日志不能记录 API Key。
- 工具调用 Trace 不能记录 API Key。
- 数据库存储建议使用后端 secret 做加密；第一版至少不能明文暴露到接口响应。

设置页要求：

- 当前设置弹窗需要升级为独立设置页。
- 新增 `工具与集成`、`工具凭证` 两个区域。
- 工具配置不要混在模型参数里。

### 26.6 P2.7.6 工具导入与选择

优先级：中。

参考 Dify / Coze 的插件体系，但本项目不直接复制完整市场。推荐阶段式实现。

第一阶段：内置工具目录。

- Tavily Search。
- 高德天气。
- 高德地图。
- 后续 Brave / Exa / SerpAPI 可以作为可选 Web Search provider。

第二阶段：本地 manifest。

用 JSON/YAML 描述工具：

```json
{
  "tool_key": "web.tavily.search",
  "display_name": "Tavily 搜索",
  "category": "web_search",
  "description": "查询互联网最新网页资料",
  "credential_schema": [{"name":"api_key","type":"secret","required":true}],
  "input_schema": {"type":"object","properties":{"query":{"type":"string"}}},
  "read_only": true
}
```

第三阶段：自定义 HTTP 工具。

允许用户配置：

- URL。
- method。
- headers。
- query/body 参数模板。
- 鉴权方式。
- 结果字段映射。

限制：

- 第一版只允许只读 GET/POST。
- 默认禁止访问内网危险地址。
- 默认禁止副作用工具。
- 需要 timeout 和返回大小限制。

第四阶段：MCP Client。

- 连接本地或远程 MCP Server。
- 获取 server 暴露的 tools。
- 用户选择启用哪些工具。
- 每个工具仍走统一 Tool Registry、Credential、Trace。

第五阶段：插件市场。

仅当内置目录、自定义 HTTP 工具、MCP 都稳定后再考虑。

7. 自定义 HTTP 工具。
8. MCP Client。

短期不做：

- 完整插件市场。
- 任意第三方代码包安装。

- 完全自主多轮 Agent 循环。

早期文档里的“第一版不做 RAG”是 MVP 边界，用于保证聊天工作台先落地。当前项目已经完成聊天、上下文治理、工具调用和设置产品化，因此现在正式进入 `P3：个人知识库 / RAG` 主线。

### 27.1 P3 总目标

把当前“上传附件进入当前轮上下文”的能力升级为“用户级个人知识库”：

```text
创建知识库
-> 配置解析 / 分块 / embedding / rerank / 检索策略
-> 上传文档
-> 后台解析与索引
-> 检索测试
-> 聊天时选择知识库
-> 回答展示引用来源
```

### 27.2 P3 产品原则

- 知识库是独立模块，不直接塞进聊天页。
- 知识库按用户隔离，第一版只做私有知识库。
- 知识库可以关联工作区，但不做团队权限。
- 文档上传后走异步任务，不阻塞聊天主链路。
- 聊天页必须显式选择知识库，未选择时不触发 RAG。
- RAG 召回片段进入现有上下文治理预算，不另起一套 prompt 拼装逻辑。
- 回答必须能展示引用来源，并能跳转查看原文片段。

### 27.3 P3-0：文档与路线确认

当前阶段要完成：

- 明确 Dify 风格知识库创建流程。
- 明确 MinerU 是文档解析 provider，而不是聊天时工具。
- 明确默认 embedding 使用 `BAAI/bge-m3`。
- 明确默认 rerank 使用 `BAAI/bge-reranker-v2-m3`。
- 明确当前 PostgreSQL 不具备 pgvector 扩展，第一版使用 `FAISS + PostgreSQL metadata`。
- 明确数据库表、后端服务边界、前端页面和验收顺序。

验收标准：

- 本地文档 05/06/07/52 已对齐。
- 不在文档或代码里写入任何用户 API Key / MinerU token。

- 第一版没有新增 `knowledge_embeddings` 表，embedding 向量不落 PostgreSQL；FAISS 文件保存向量，PostgreSQL 保存 chunk metadata 和 vector id。
- 当前重建索引采用“重新 embedding 当前知识库全部 chunks 并重建 FAISS”的保守方案，规模小的时候更简单可靠；大规模知识库后续再做增量索引、向量持久化或后台 worker。
- 删除文档时 SQLAlchemy cascade 会删除 chunks，但 FAISS 文件中的旧 vector id 需要后续 rebuild 清理；检索阶段会过滤数据库中不存在的 chunk。
- 当前检索测试是 vector recall，不含 rerank；rerank 进入 `P3-4`。
- 当前只索引文本。PDF 内图片、截图、复杂表格暂不做语义索引，只保留 `parsed_assets_json` 等扩展字段，后续可参考 Dify multimodal knowledge base 和 Knowledge Pipeline 路线做 OCR / caption / multimodal embedding。
