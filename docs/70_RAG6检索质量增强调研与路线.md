# RAG-6 检索质量增强调研与路线

更新时间：2026-06-14

本文档用于承接 `RAG-5` 阶段之后的知识库优化。当前项目已经完成：

- 知识库创建、文档上传、解析、分块、Embedding、FAISS 索引。
- 检索测试与 Rerank。
- 聊天页选择知识库并注入上下文。
- 知识库来源卡片与 chunk 定位。
- 知识库检索日志持久化。

因此 `RAG-6` 不应该马上堆功能，而应该围绕“检索质量”系统化推进。

---

## 1. 调研结论

### 1.1 主流平台的共同方向

对比 Dify、OpenAI File Search / Vector Stores、Anthropic Contextual Retrieval、LlamaIndex、RAGFlow、Ragas 等资料后，可以看到成熟 RAG 系统通常不是单一路线，而是分层组合：

```text
文档解析质量
-> metadata 结构化
-> 多路召回
-> 融合排序
-> rerank 精排
-> 上下文压缩 / 引用
-> 检索日志与评测闭环
```

关键共识：

- 单纯向量检索不够，尤其对错误码、术语、函数名、表格字段、论文指标等精确匹配不稳定。
- BM25 / 全文检索仍然有价值，适合精确词、短语、编号、英文缩写。
- Hybrid Search 通常是向量召回 + 关键词召回，再通过加权或 RRF 合并。
- Rerank 是精排层，不应替代召回层。
- Metadata Filter 是生产级 RAG 的必要能力，不只是“筛选文件”，还涉及权限、文档类型、时间、项目、版本。
- Parent-Child / Recursive Retrieval 用于解决“短 chunk 适合召回，长上下文适合回答”的冲突。
- 评测集和检索日志必须先行，否则优化无法判断是否真的有效。

### 1.2 对当前项目最有价值的路线

当前 AI Web Studio 是个人智能问答 + 个人知识库系统，不是企业级知识库平台。现阶段最值得做的是：

1. 先把检索日志从“记录摘要”升级为“可分析”。
2. 建一个小型 RAG 评测集，能计算 top-k 命中、context precision、context recall。
3. 补 metadata 体系和过滤器。
4. 再做 Hybrid Search，而不是直接重构成复杂向量数据库。
5. Parent-Child 作为论文 / PDF / 长文档体验增强。

不建议当前立即做：

- GraphRAG。
- 多模态图片向量检索。
- Agentic RAG 自动多轮检索。
- 大规模向量数据库迁移。

这些方向有价值，但不是当前瓶颈。

## 2. 参考资料要点

### 2.1 Dify

Dify 的知识库设计把“知识库级设置”和“节点级检索设置”分开。

可借鉴点：

- 创建知识库时就配置索引方法、Embedding、检索策略。
- 高质量索引支持 Vector Search、Full-Text Search、Hybrid Search。
- 工作流知识检索节点可以添加多个知识库，先并行检索，再在节点级做 rerank 或缩小结果池。
- metadata filter 用于提高检索精度。
- 支持 Parent-Child Retrieval 和多模态知识库检索。

对我们的启发：

- 当前我们只有“聊天页单知识库选择”，后续应该改成“可选择多个知识库 + 本轮检索设置覆盖”。
- 知识库级参数和聊天本轮参数要分层：知识库定义默认召回方式，聊天本轮可以覆盖 top_k、rerank、score threshold。

资料：

- Dify Knowledge：https://docs.dify.ai/en/use-dify/knowledge/readme
- Dify Index & Retrieval Settings：https://docs.dify.ai/en/use-dify/knowledge/create-knowledge/setting-indexing-methods
- Dify Knowledge Retrieval Node：https://docs.dify.ai/en/use-dify/nodes/knowledge-retrieval
- Dify Hybrid Search & Rerank：https://dify.ai/blog/hybrid-search-rerank-rag-improvement

### 2.2 Anthropic Contextual Retrieval

Anthropic 的重点不是“换一个向量库”，而是给每个 chunk 增加文档级上下文，再结合 BM25 和 rerank。

可借鉴点：

- Contextual Embeddings：在 chunk 前补充上下文说明，让孤立片段更容易被正确检索。
- Contextual BM25：同样把上下文加入关键词检索。
- 初召回可以取较多候选，再用 rerank 压到最终 top-k。
- Anthropic 报告中，Contextual Embeddings、Contextual BM25、Rerank 的组合能显著降低 top-20 retrieval failure rate。

对我们的启发：

- 等 Hybrid/评测基础做好后，可以增加 `contextual_chunk_text` 字段。
- 对论文类 PDF，chunk 上下文可以包含标题路径、摘要、章节名、表格标题、图注。
- 不应该一开始就把 contextual chunk 做成默认，因为会增加 token 和 embedding 成本。

资料：

- Anthropic Contextual Retrieval：https://www.anthropic.com/engineering/contextual-retrieval
- Claude Cookbook Contextual Embeddings：https://platform.claude.com/cookbook/capabilities-contextual-embeddings-guide

### 2.3 OpenAI File Search / Vector Stores

OpenAI 的方向是把文件、向量存储、file_search、ranker、score threshold、结果内容追踪做成托管工具。

可借鉴点：

- File Search 返回结果可带 score。
- 支持 ranking options，例如 ranker 和 score threshold。
- Run step 可追踪 file_search results content。
- Vector Stores 作为独立资源，支持文件批处理。

对我们的启发：

- 我们已经有 `knowledge_retrieval_logs`，应该继续加强“检索结果可追踪”。
- 日志应保存 query、候选、score、rank_source、最终注入、最终回答引用。
- 后续可以设计“检索日志详情页”，对标 hosted tool trace。

资料：

- OpenAI API Reference - Run Step / File Search Results：https://platform.openai.com/docs/api-reference/run-steps/getRunStep
- OpenAI API Reference - Vector Store File Batches：https://platform.openai.com/docs/api-reference/vector-stores-file-batches

### 2.4 LlamaIndex

LlamaIndex 的价值在于抽象清晰：Retriever、Metadata Filter、Recursive Retriever、Fusion Retriever。

可借鉴点：

- Retriever 是独立模块，不应和聊天服务耦合。
- Metadata Filtering 是检索前约束候选范围。
- Reciprocal Rerank Fusion / Query Fusion 用于合并多路检索结果。
- Recursive Retriever / Node References 可以先检索摘要节点，再展开到原文节点。

对我们的启发：

- 当前 `KnowledgeIndexService.retrieve()` 可以拆成更明确的 pipeline：
  - candidate selector
  - vector retriever
  - lexical retriever
  - fusion
  - rerank
  - context expander
- Parent-Child 可以用 `parent_chunk_id` / `child_chunk_id` 实现，不必直接引入框架。

资料：

- LlamaIndex Retriever：https://developers.llamaindex.ai/python/framework/module_guides/querying/retriever/
- LlamaIndex RRF Retriever：https://developers.llamaindex.ai/python/framework/integrations/retrievers/reciprocal_rerank_fusion/
- LlamaIndex Recursive Retriever：https://developers.llamaindex.ai/python/framework/integrations/retrievers/recursive_retriever_nodes/
- LlamaIndex Metadata Filtering：https://developers.llamaindex.ai/typescript/framework/modules/rag/query_engines/metadata_filtering/

### 2.5 RAGFlow / RAG-Anything

RAGFlow 强调复杂文档理解、模板化 chunking、可追踪引用和对多格式文档的处理。

可借鉴点：

- PDF、表格、图片、扫描件的解析质量是 RAG 上限。
- chunk 可视化和人工干预很重要。
- 来源引用必须可追踪。
- 对复杂文档，需要 layout、OCR、表格结构识别等能力。

对我们的启发：

- 我们已经接入 MinerU 解析，后续应优先把 `page_start/page_end/title_path/table_caption/figure_caption` 等 metadata 持久化。
- 对论文 PDF，短期先做文本 + 表格结构；图片/图表向量检索留到 RAG-7。

资料：

- RAGFlow GitHub：https://github.com/infiniflow/ragflow
- RAGFlow Quickstart：https://ragflow.io/docs/
- RAGFlow DeepDoc README：https://github.com/infiniflow/ragflow/blob/main/deepdoc/README.md
- RAG-Anything：https://arxiv.org/html/2510.12323v1

### 2.6 Ragas / 评测

RAG 系统不能只靠“看起来回答得不错”判断效果。

可借鉴指标：

- Context Precision：相关 chunk 是否排在前面。
- Context Recall：重要信息是否被召回。
- Faithfulness：回答是否忠实于上下文。
- Response Relevancy：回答是否回应了问题。

对我们的启发：

- RAG-6 第一件事应该不是 Hybrid，而是评测集和日志分析。
- 没有基线指标，Hybrid、RRF、Parent-Child 的效果无法判断。

资料：

- Ragas Metrics：https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/
- Ragas Context Precision：https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_precision/
- Ragas Context Recall：https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_recall/

## 3. RAG-6 推荐实施顺序

### RAG-6.0：检索日志详情页与评测基线

目标：

- 让每次检索可回看、可比较、可评估。

实现内容：

- 前端新增检索日志详情页或知识库详情页中的“检索日志”Tab。
- 展示：
  - query。
  - 候选 chunks。
  - vector_score。
  - rerank_score。
  - rank_source。
  - 最终注入 chunks。
  - 来源卡片。
  - 回答消息跳转。
- 新增小型评测集表：
  - query。
  - expected_document_id。
  - expected_chunk_id。
  - expected_answer_keywords。
  - difficulty。
  - tags。
- 支持手动运行评测：
  - top_k hit。
  - MRR。
  - context precision@k。
  - context recall@k。

为什么先做：

- 后续所有优化都要靠它判断是否有效。
- 当前已有 `knowledge_retrieval_logs`，成本最低。

### RAG-6.1：Metadata 体系与过滤

目标：

- 让检索可以按文档、类型、页码、标题路径、时间、工作区等筛选。

实现内容：

- 扩展 `knowledge_documents`：
  - `source_type`
  - `tags_json`
  - `author`
  - `published_at`
  - `language`
  - `doc_type`
- 扩展 `knowledge_chunks`：
  - `title_path`
  - `section_title`
  - `page_start`
  - `page_end`
  - `chunk_kind`
  - `table_caption`
  - `figure_caption`
- 检索请求支持 `metadata_filter`：
  - document_id in
  - doc_type eq
  - page range
  - title_path contains
  - tags overlap
- 前端知识库检索测试支持过滤条件。

为什么第二步：

- Metadata Filter 是多知识库和生产检索的基础。
- 这一步也能改善来源定位体验。

### RAG-6.2：多知识库检索

目标：

- 聊天时支持选择多个知识库，并合并结果。

实现内容：

- 前端知识库选择器从单选改成多选。
- 后端 `knowledge_base_id` 扩展为 `knowledge_base_ids`。
- 每个知识库独立执行检索。
- 合并候选后统一 rerank。
- 检索日志支持多个知识库：
  - `knowledge_base_ids_json`
  - 每个候选标记来源知识库。

为什么第三步：

- 用户实际使用时经常会有“论文库 + 课程资料 + 项目文档”。
- 这一步依赖日志和 metadata。

### RAG-6.3：BM25 / 全文检索

目标：

- 解决向量检索对精确词、缩写、编号、表格字段不稳定的问题。

实现选择：

当前项目运行在 PostgreSQL + 本地用户态环境，不建议马上引入 Elasticsearch。

优先方案：

- PostgreSQL full-text search：
  - 英文文档可先用 `to_tsvector`。
  - 中文可先做简化 tokenization，后续再接 jieba / pg_trgm。
- 或者本地 Python BM25：
  - `rank_bm25` / 自实现轻量 BM25。
  - 对当前规模足够简单。

建议第一版：

- 先实现 Python BM25 索引文件，和 FAISS 一样保存在 `knowledge_index_dir`。
- 后续如果规模变大，再考虑 PostgreSQL FTS / Elasticsearch / OpenSearch。

### RAG-6.4：Hybrid Search + RRF

目标：

- 合并向量检索和 BM25 检索，提高召回稳定性。

推荐策略：

```text
query
-> vector top_k_vector
-> bm25 top_k_keyword
-> normalize / RRF fusion
-> optional rerank
-> score_threshold
-> final top_k
```

第一版推荐 RRF，不推荐简单加权分数。

原因：

- 向量分数和 BM25 分数量纲不同，加权需要复杂归一化。
- RRF 只依赖排名，更稳。
- LlamaIndex 等框架也常用 Fusion/RRF 处理多路结果。

### RAG-6.5：Parent-Child / Recursive Retrieval

目标：

- 用小 chunk 做召回，用大 parent chunk 做回答上下文。

实现方式：

- 新增 parent chunk：
  - 更长，按章节或大段生成。
- 新增 child chunk：
  - 更短，适合 embedding 和 BM25。
- 检索命中 child 后：
  - 注入 parent。
  - 或注入 child + parent 摘要。

适用场景：

- 论文 PDF。
- 长章节。
- 表格周围说明。
- 需要跨段理解的文档。

### RAG-6.6：Contextual Retrieval

目标：

- 给 chunk 增加文档级上下文，减少孤立 chunk 语义丢失。

实现方式：

- 新增字段：
  - `contextual_content`
  - `contextual_summary`
  - `contextual_generated_at`
- 在索引前，用 LLM 为每个 chunk 生成短上下文：
  - 本文档主题。
  - 章节位置。
  - chunk 与文档整体的关系。
- Embedding / BM25 使用 `contextual_content`。
- 最终展示仍引用原 chunk。

注意：

- 成本更高。
- 应先用评测集证明收益。
- 不建议作为默认打开。

## 4. 当前项目推荐路线图

结合当前代码基础，建议按以下阶段推进：

```text
RAG-6.0 检索日志详情页 + 小型评测集
RAG-6.1 Metadata schema + 过滤器
RAG-6.2 多知识库检索
RAG-6.3 BM25 / lexical retriever
RAG-6.4 Hybrid Search + RRF
RAG-6.5 Parent-Child retrieval
RAG-6.6 Contextual Retrieval 实验
```

第一轮收敛目标：

- 做到 `RAG-6.4` 即可阶段性收尾。
- `RAG-6.5 / 6.6` 可以作为高级优化继续探索。

验收标准：

- 至少有一个评测集可以重复跑。
- 能看到每种检索策略的 top-k hit / MRR / context precision。
- 用户可以在前端理解“为什么召回这些片段”。
- 多知识库和 Hybrid 结果可追踪到原始日志。

## 5. 不建议现在做的方向

### 5.1 GraphRAG

GraphRAG 对实体关系、社区摘要、跨文档关系推理有价值，但当前项目还没解决基础 Hybrid 和评测问题。

暂缓原因：

- 实现复杂。
- 数据构建成本高。
- 不适合当前个人知识库 MVP。

### 5.2 多模态图片向量检索

当前 MinerU 能解析图片和图表资源，但我们还没有：

- 图片 caption 持久化。
- 图片 embedding。
- multimodal rerank。
- 图片引用 UI。

建议放到 `RAG-7`。

### 5.3 Agentic RAG

让 LLM 自动多轮检索、改写 query、反思是否需要再检索，这是后续方向，但当前更需要稳定的基础检索层。

## 6. 对代码架构的建议

当前 `KnowledgeIndexService` 已经开始承担过多职责。RAG-6 开始前建议拆成：

```text
KnowledgeChunkService
KnowledgeEmbeddingService
KnowledgeVectorStore
KnowledgeLexicalIndexService
KnowledgeRetrieverService
KnowledgeFusionService
KnowledgeRerankService
KnowledgeRetrievalLogService
KnowledgeEvaluationService
```

但不建议一次性大重构。更稳的做法：

1. 先新增 `KnowledgeRetrievalPipeline`，把当前 retrieve 流程包起来。
2. 新功能都接 pipeline，不再继续塞进 `KnowledgeIndexService`。
3. 等 Hybrid / Evaluation 稳定后，再拆旧 service。

---

## 7. 最终建议

下一步不要直接做 Hybrid。

建议先做：

```text
RAG-6.0：检索日志详情页 + 小型评测集
```

理由：

- 当前已经有 `knowledge_retrieval_logs`，开发成本最低。
- 后续所有检索优化都需要可重复评估。
- 这一步能让项目在简历里更有说服力：不是只会接 RAG，而是能做“检索质量治理”和“评测闭环”。

## 8. 2026-06-14 RAG-6.0 实现记录

本轮已按本文档建议完成第一步落地。

### 8.1 已完成

- 新增 `KnowledgeRetrievalPipeline`：
  - query embedding。
  - FAISS vector search。
  - chunk metadata merge。
  - optional rerank。
  - score threshold。
- `KnowledgeIndexService` 保留索引构建职责，retrieve 变成兼容包装。
- 新增 `KnowledgeEvaluationService`：
  - 评测集管理。
  - 评测用例管理。
  - 调用 pipeline 执行检索评测。
  - 计算 `hit_at_k` / `mrr` / `context_precision` / `context_recall`。
- 新增评测相关表：
  - `knowledge_eval_sets`
  - `knowledge_eval_cases`
  - `knowledge_eval_runs`
  - `knowledge_eval_results`
- 前端知识库详情页新增 `RAG-6.0 检索观测` 面板：
  - 最近检索日志摘要。
  - 小型评测集创建。
  - 评测用例添加。
  - 手动运行评测。
  - 指标展示。

### 8.2 当前边界

- 尚未实现完整检索日志详情页，只展示最近日志摘要。
- 评测用例仍需手动维护 expected chunk id。
- 当前评测只覆盖检索质量，不覆盖最终回答质量。
- 检索算法仍是现有 vector + optional rerank。

### 8.3 下一步

`RAG-6.1` 应继续做 metadata schema + filter，而不是立刻大改所有检索算法。原因是 metadata 是 Hybrid、多知识库、日志解释和来源定位共同依赖的基础结构。

## 9. 2026-06-14 RAG-6.1 实现记录

本轮完成 Metadata Filter 第一版。

### 9.1 已完成

- 新增 `KnowledgeRetrievalFilter`：
  - `document_ids`
  - `file_types`
  - `page_start`
  - `page_end`
  - `section_query`
- `KnowledgeRetrievalPipeline` 支持过滤参数。
- 启用过滤时，Pipeline 会把 FAISS 候选数从 `top_k` 放大到 `min(max(top_k * 5, top_k + 20), 200)`，再进行过滤，减少过滤后空召回。
- 新建索引写入更完整 chunk metadata：
  - `document_id`
  - `file_name`
  - `mime_type`
  - `file_type`
  - `chunk_index`
  - `source_start`
  - `source_end`
  - `document_version`
  - `parser_provider`
- 检索测试 API 支持 metadata filter。
- 前端检索测试面板新增过滤控件。
- 单测覆盖 document_id、file_type 过滤和非法 document_id。

### 9.2 当前边界

- 当前仍是 FAISS 后置过滤，不是向量库原生 metadata filter。
- 当前不新增数据库列，优先保持低风险和兼容历史数据。
- 已索引的历史 chunk 需要重建索引才能拥有新 metadata。
- 页码和章节字段依赖解析器输出；当前本地基础解析一般没有页码 / 标题路径。

### 9.3 下一步

推荐继续做 `RAG-6.2` 多知识库检索。

原因：

- Metadata filter 已为多知识库和按文档过滤打基础。
- 多知识库检索是产品功能上最直接的增强。
- BM25 / Hybrid 需要在多知识库合并和日志结构稳定后再做，避免重复调整接口。
