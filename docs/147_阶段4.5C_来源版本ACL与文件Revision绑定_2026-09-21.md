# 阶段 4.5C：来源版本、ACL 与文件 Revision 绑定

日期：2026-09-21

## 1. 本阶段目标

阶段 4.5A/4.5B 已经解决了外部证据的请求内去重和投影预算可解释性。本阶段继续解决一个不同的问题：**下一步 Tool 调用到底基于哪个可验证版本、哪个工作区范围**。

本阶段优先覆盖本地工作区文件和 Durable Agent Artifact。网页 URL、网页发布时间、远程 MCP 响应本身都不能被代码凭空当作版本证明，因此本阶段不做这类推断。

## 2. 已实现的文件版本闭环

### 2.1 读取时建立可审计基线

`ProjectFile` 继续保存当前可读正文，`FileRevision` 保存不可变快照。工作区文件 `list/search/read/propose_edit` 在需要来源身份时调用 `workspace_file_provenance.py`：

- 当前正文的 SHA-256 与最新 `FileRevision` 一致时复用已有 Revision；
- 当前正文发生变化时只补建 `baseline_sync` 快照，不修改正文；
- 返回最小来源身份：`file_id`、`revision_id`、`revision_number`、`content_hash`；
- 对外只返回 `access_scope=current_user_current_project` 这一可解释标签，不暴露用户 ID、项目 ID、存储键或本机路径。

这类基线是审计和并发校验快照，不代表文件发生了 Agent 修改。

### 2.2 后续调用绑定读取版本

`workspace.files.read` 和 `workspace.files.propose_edit` 接受可选的 `expected_revision_id`。Planner 可以通过 Result Binding 把上一次读取结果中的：

```text
/sources/0/metadata/raw/revision_id
```

绑定到下游调用参数 `expected_revision_id`。Provider 会重新按当前用户 + 当前项目查询文件，再比较当前 Revision；版本不一致时立即失败关闭并要求重新读取。这样可以阻止“先读取旧文件，文件被其他请求修改后仍沿用旧证据生成编辑”的问题。

### 2.3 写入和审批继续做第二道校验

Agent Runtime 的 `propose_file_edit` 同样校验 `expected_revision_id`，并将该字段纳入参数哈希、`AgentStep.arguments_json` 和审批关联的 `arguments_hash`。最终 `apply_edit` 仍会校验：

- 当前正文哈希是否等于 Diff 基线哈希；
- `old_string` 是否仍唯一；
- 生成内容哈希是否等于审批草案中的 `proposed_content_hash`；
- Revision/CAS 写入是否只产生一次结果。

因此读取层、审批层和最终写入层都有版本边界，不能只依赖 `call_id` 或 `old_string`。

## 3. Artifact 的版本和作用域

Durable Agent Artifact 是不可变 Tool 结果，不是可编辑文件，因此不伪造文件式 `revision_id`。它使用已有的 `artifact_id`、`run_id`、`step_id` 和不可变 `content_hash` 标识具体结果；查询仍强制：

```text
AgentArtifact.user_id == 当前用户
AgentRun.user_id == 当前用户
AgentRun.project_id == 当前项目
```

本阶段为 Artifact Source 补充 `access_scope=current_user_current_project`，用于诊断和审计解释。该字段不是授权凭据，真正的 ACL 仍由数据库查询条件执行。

## 4. 明确没有做的推断

- URL 只能表示来源地址，不能证明网页当前版本或发布时间；
- 没有远端 digest、版本号、ETag/If-None-Match 合同或人工审核记录时，MCP 响应不能被称为“已验证版本”；
- 文件 `content_hash` 证明的是当前快照内容，不自动证明外部来源的真实性；
- 版本绑定不等于 Prompt Injection 检测，原有 Evidence Projection、质量合同和权限边界仍然有效。

## 5. 主要实现文件

- `backend/app/services/workspace_file_provenance.py`：生成文件内容摘要、补建/复用当前 Revision、返回最小 provenance。
- `backend/app/services/tools/providers/workspace_files.py`：工作区 ACL、读取/编辑预览的版本校验和 Result Binding 可用字段。
- `backend/app/services/agent_runtime_service.py`：审批草案、参数哈希、最终 CAS 写入的版本绑定。
- `backend/app/services/tools/executor.py`：将 `expected_revision_id` 传入受控编辑运行时，并覆盖可信 Tool 身份元数据。
- `backend/app/services/tools/providers/agent_artifacts.py`：Artifact 的当前用户/项目作用域标签。
- `backend/app/tool_manifests/default_tools.json`：声明 `expected_revision_id` 输入字段和可供绑定的 Revision 事实路径。

## 7. 阶段结论

阶段 4.5C 的第一步已经把本地文件来源从“有一个 file_id”提升为“用户/项目 ACL 下的可验证 Revision 身份”，并把该身份贯穿读取、规划绑定、审批和最终写入。对于网页和远程 MCP，当前保持诚实边界：没有版本合同就不声称具备新鲜度证明。
