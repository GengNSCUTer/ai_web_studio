# 工具调用增强调研与实施路线

更新时间：2026-06-06

本文档用于整理 AI Web Studio 下一阶段工具调用层的优化方向。目标不是马上开发，而是先把“为什么要改、改成什么样、按什么顺序落地、哪些先不做”讲清楚。

当前重点问题：

- Tool Trace 还不够可解释，用户只能看到调用了什么工具，但看不到规划理由、schema 校验、fallback 原因。
- Tavily / 高德虽然已经接入 MCP，但 MCP server 来源仍偏固定，用户不能自己注册 MCP server。
- 工具 API Key 和权限策略还不够产品化，后续多用户使用时不能继续把 key 写死在后端环境变量里。
- LLMToolPlanner 还不是主路径，很多明确问题仍依赖 deterministic fast path。
- 复杂问题还没有真正的多工具动态规划，例如“查深圳到汕头路线、路上服务区、天气、预计耗时”。
- 工具 manifest 还需要我们手写，MCP 工具发现能力没有充分用起来。

---

## 1. 行业调研结论

### 1.1 MCP 已经成为工具接入的主流协议

MCP 的核心价值是让外部服务通过标准协议暴露工具、上下文和资源。官方文档把 MCP 类比成 AI 应用的 USB-C：AI 应用可以通过统一方式连接数据源、工具和工作流。

对我们项目最重要的是：

- MCP server 可以通过 `tools/list` 暴露工具列表。
- 每个工具天然带有：
  - `name`
  - `description`
  - `inputSchema`
- MCP client 可以通过 `tools/call` 调用具体工具。
- 这可以缓解“每接一个工具就手写一堆描述和参数解析”的问题。

参考：

- https://modelcontextprotocol.io/docs/getting-started/intro
- https://modelcontextprotocol.io/specification/2025-06-18/basic/security_best_practices

### 1.2 OpenAI Agents SDK 的启发

OpenAI Agents SDK 已经支持多种 MCP 接入方式：

- Hosted MCP：由 OpenAI Responses API 直接调用公开可达的 MCP server。
- Streamable HTTP MCP server。
- SSE MCP server。
- stdio MCP server。

它的设计里有几个很值得参考的点：

- 支持把 MCP schema 尽量转换成 strict JSON schema。
- 支持工具失败如何暴露给模型。
- 支持给 MCP 工具名加 server 前缀，避免多个 server 暴露同名工具时冲突。
- Hosted MCP 和本地 MCP 是不同执行边界，需要明确工具在哪里执行。

对我们项目的启发：

- 我们现在已经有 `McpHttpClient`，短期继续支持 HTTP / SSE / Streamable HTTP 是合理的。
- 后续如果支持多个 MCP server，工具 key 应该带 server namespace，例如：
  - `tavily.web_search`
  - `amap.maps_distance`
  - `notion.search_page`
- 工具失败不能只显示“失败”，要在 trace 里区分：
  - planner 失败
  - schema 校验失败
  - permission 拒绝
  - MCP server 调用失败
  - fallback 生效

参考：

- https://openai.github.io/openai-agents-python/mcp/

### 1.3 Claude Connectors 的启发

Claude 的 Connectors 已经把 MCP 产品化成“连接器”：

- 用户可以连接远程 MCP server。
- 连接器可以提供工具、信息和 UI 组件。
- 有预置连接器目录，也支持第三方 connector。
- Claude API 的 Managed Agents 把 MCP server 声明和用户认证拆开：
  - Agent 创建时声明 MCP server 名称和 URL。
  - Session 创建时再提供该用户的认证引用。

这个拆分非常重要：

```text
工具定义 / server 配置
  !=
用户密钥 / 用户授权
```

对我们项目的启发：

- MCP server 是“工作区或用户可配置资源”。
- API Key / OAuth Token 是“用户级凭据”。
- 同一个 MCP server 可以被多个用户使用，但每个用户使用自己的凭据。
- 前端设置里应该有独立的“工具与连接器”页面，而不是继续塞在小弹窗里。

参考：

- https://claude.com/docs/connectors/overview
- https://platform.claude.com/docs/en/managed-agents/mcp-connector

### 1.4 Dify 的启发

Dify 的工具体系更接近我们要做的产品形态。它有几个关键点：

- Tools 页面可以添加 MCP server。
- Dify 会自动连接 MCP server、处理 OAuth、拉取工具列表，并把工具放进 app builder。
- MCP tools 会按 server 分组展示，例如 `Notion MCP » Create Page`。
- 每个工具可以自定义：
  - 描述覆写
  - 参数是让 AI 自动生成，还是固定值
- Agent 节点有两种主流策略：
  - Function Calling：适合支持原生函数调用的模型。
  - ReAct：适合需要显式 Thought -> Action -> Observation 的模型。
- Agent 执行有最大迭代次数，避免无限循环。
- Agent 输出包括 tool outputs、reasoning trace、iteration count、agent logs。

对我们项目的启发：

- MCP 工具注册页应该支持：
  - 添加 server URL
  - 测试连接
  - 刷新 tools/list
  - 展示工具列表
  - 启用 / 禁用单个工具
  - 覆写工具描述
  - 固定某些参数
- Agent planner 不应该无限循环，必须有：
  - 最大迭代次数
  - 最大工具调用次数
  - 单工具超时
  - 总耗时上限
  - fallback 策略

参考：

- https://docs.dify.ai/en/use-dify/build/mcp
- https://docs.dify.ai/en/use-dify/nodes/agent
- https://docs.dify.ai/en/develop-plugin/getting-started/choose-plugin-type

### 1.5 Coze / 插件平台的启发

Coze Studio 开源版把插件分成：

- 官方内置插件
- 自定义插件
- 商业版插件

插件有独立配置和鉴权。部分插件需要 OAuth 或第三方平台凭据。

对我们项目的启发：

- 工具目录要区分来源：
  - 内置工具：项目默认提供，如 Tavily、高德。
  - 用户 MCP server：用户自己添加。
  - 后续自定义 HTTP API / OpenAPI 导入：先规划，暂不急做。
- 不同来源的工具要有不同信任等级。
- 未审核的第三方 MCP server 默认不能高权限启用。

参考：

- https://github.com/coze-dev/coze-studio/wiki/4.-Plugin-Configuration

### 1.6 LangGraph 的启发

LangGraph 的核心价值不是“工具更多”，而是把 agent loop 显式建模为状态机：

```text
LLM node
  -> ToolNode
  -> LLM node
  -> ...
  -> final answer
```

它有几个值得借鉴的设计：

- ToolNode 执行模型请求的工具调用。
- 多个工具调用可以并行执行。
- Human-in-the-loop 可以在关键节点暂停，等待用户批准。
- persistence/checkpointer 可以保存中间状态，支持恢复。

对我们项目的启发：

- 短期不一定引入 LangGraph。
- 但要借鉴它的架构思想，把我们的工具调用从“一次性外部上下文增强”升级为“有限循环的 tool workflow”。
- 高风险工具调用可以先做人工确认弹窗，后续再决定是否引入图执行框架。

参考：

- https://reference.langchain.com/javascript/langchain-langgraph/prebuilt/ToolNode
- https://docs.langchain.com/oss/python/langgraph/human-in-the-loop

### 1.7 安全调研结论

MCP 不是“接上就安全”。官方安全文档和近期研究都强调了几个风险：

- Token passthrough 是反模式，不能把上游 token 原样传给下游服务。
- 本地 MCP server 可能造成任意代码执行、数据泄露、文件破坏。
- 工具描述可能被污染，诱导模型错误调用。
- 工具返回结果可能包含 prompt injection。
- 多个工具组合时可能发生权限升级或数据外泄。

对我们项目的底线要求：

- 短期只开放 HTTP / SSE / Streamable HTTP MCP，不开放本地 stdio MCP。
- 工具默认只读。
- 写操作 / 删除操作 / 发消息 / 发邮件 / 文件修改等高风险工具必须人工确认。
- 工具调用必须审计记录。
- 用户密钥必须后端加密存储，前端不可回显明文。
- 工具输出作为“外部数据”，不能作为系统指令信任。

参考：

- https://modelcontextprotocol.io/specification/2025-06-18/basic/security_best_practices
- https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization
- https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/plugin-authentication

## 2. 我们当前实现的定位

当前 AI Web Studio 的工具调用链路大致是：

```text
用户问题
  -> QueryRewriteService
  -> LLMToolPlanner
      -> deterministic fast path
      -> 或 LLM JSON plan
      -> schema validate
      -> fallback deterministic plan
  -> ToolExecutor
  -> ToolAdapterRunner
  -> MCP HTTP / Python fallback
  -> ExternalSource
  -> 注入模型上下文
  -> 前端展示来源与 Tool Trace
```

当前已经完成的基础：

- ToolCatalog。
- `default_tools.json` manifest。
- `McpHttpClient`。
- Tavily MCP。
- 高德 MCP。
- Tool Trace 流式事件与持久化。
- 来源卡片。
- Schema 校验。
- LLMToolPlanner 第一版。
- Deterministic fallback。
- 高德天气、路线、距离、POI 多步 workflow。

当前主要差距：

- MCP server 不能由用户自定义注册。
- MCP tools/list 的发现结果还没有落库成工具目录。
- 工具 key、server namespace、工具描述覆写、参数固定值还没有产品化。
- API Key 虽然已有配置雏形，但还没有完整的加密、权限、审计、不可回显策略。
- LLM planner 还没有真正成为主路径。
- 没有有限循环 tool workflow。
- Tool Trace 还没有展示 planner 内部细节。
- 没有高风险工具的用户确认。

## 3. 目标架构

下一阶段不要把目标定成“马上做完整 Agent 平台”，而是定成：

```text
可解释、可配置、可扩展、安全默认关闭的工具调用系统
```

目标链路：

```text
用户问题
  -> 上下文改写 / coreference rewrite
  -> Tool Discovery Context 构建
      -> 当前用户启用的 MCP servers
      -> 当前会话/工作区启用的工具
      -> 工具描述覆写
      -> 固定参数
      -> 权限策略
  -> LLMToolPlanner 主路径
      -> 输出 tool plan
      -> schema validate
      -> policy validate
      -> confidence / fallback decision
  -> Tool Workflow Engine
      -> step 1 call tool(s)
      -> observe
      -> step 2 decide continue or final
      -> max iterations / timeout
  -> ToolExecutor
      -> MCP / Python adapter
      -> retry / fallback
      -> structured result mapper
  -> ExternalSource + ToolTrace
  -> 注入回答模型上下文
  -> 前端展示：
      -> 规划理由
      -> 参数校验
      -> 权限判断
      -> 工具调用
      -> fallback
      -> 来源
```

## 4. 核心模块设计

### 4.1 Tool Trace 增强

目标：

让用户知道“为什么调用这个工具，以及中间发生了什么”。

后端新增或增强事件：

- `tool_planner_start`
  - planner 类型：`llm_tool_planner_v1 / deterministic_tool_planner_v2`
  - 可用工具数量
  - 是否启用 MCP discovered tools
- `tool_planner_end`
  - 输出计划
  - 每个工具的选择理由
  - confidence
- `tool_schema_validation`
  - tool_key
  - 原始 arguments
  - normalized arguments
  - validation status
  - errors
- `tool_policy_check`
  - risk_level
  - permission result
  - credential source
  - 是否需要用户确认
- `tool_fallback`
  - from planner/tool/adapter
  - fallback to
  - reason
- `tool_workflow_step`
  - iteration
  - selected tools
  - observation summary
  - continue / stop reason

前端展示：

- 回答下方工具过程继续折叠展示。
- 默认只显示简洁摘要：
  - “规划器选择了高德距离测量，因为用户询问多地点距离比较。”
  - “schema 校验通过，2 个起点、1 个终点。”
  - “调用高德 MCP 成功，耗时 2.6s。”
- 展开后显示详细 JSON 和 fallback 原因。

### 4.2 用户自定义 MCP Server 注册

目标：

把高德/Tavily 从“写死工具”升级为“内置 MCP server 示例”，并允许用户添加自己的 MCP server。

数据库建议：

```text
mcp_servers
  id
  owner_user_id
  workspace_id nullable
  server_id
  name
  description
  transport_type            # streamable_http / sse，短期不支持 stdio
  url
  auth_type                 # none / api_key / bearer / oauth_later
  credential_id nullable
  trust_level               # builtin / user_added / workspace_added
  enabled
  last_sync_at
  last_error
  created_at
  updated_at

mcp_tools
  id
  server_id
  raw_name
  tool_key                  # server namespace + raw tool name
  display_name
  description
  input_schema_json
  output_schema_json nullable
  annotations_json nullable
  enabled
  risk_level                # low / medium / high
  read_only
  description_override
  fixed_arguments_json
  auto_arguments_json
  last_seen_at
  created_at
  updated_at
```

核心 API：

- `POST /api/mcp-servers`
  - 添加 server。
- `POST /api/mcp-servers/{id}/test`
  - 测试连接。
- `POST /api/mcp-servers/{id}/sync-tools`
  - 调 `tools/list` 并写入 `mcp_tools`。
- `GET /api/mcp-servers`
  - 列表。
- `GET /api/mcp-servers/{id}/tools`
  - 工具列表。
- `PATCH /api/mcp-tools/{id}`
  - 启用/禁用、描述覆写、参数 fixed/auto、risk_level。

前端页面：

```text
设置页
  -> 工具与连接器
      -> 内置工具
          -> Tavily
          -> 高德地图
      -> MCP Servers
          -> 添加 MCP Server
          -> 测试连接
          -> 同步工具
          -> 工具列表
          -> 单工具启用/禁用
          -> 描述覆写
          -> 固定参数
```

短期限制：

- 只支持远程 HTTP / SSE MCP。
- 不支持 stdio MCP。
- 不支持自动 OAuth，全量 OAuth 放后续。
- 支持 API Key / Bearer Token 作为第一版凭据。

### 4.3 工具配置安全增强

目标：

每个用户使用自己的 API Key 或 Token；密钥后端加密存储，前端不回显。

数据库建议：

```text
tool_credentials
  id
  owner_user_id
  workspace_id nullable
  provider
  auth_type
  encrypted_secret
  display_hint              # 例如 sk-...abcd
  status                    # active / invalid / expired
  last_used_at
  created_at
  updated_at
```

后端策略：

- 使用服务器环境变量 `APP_SECRET_KEY` 派生 Fernet key 或使用现有加密方案。
- 前端只显示：
  - 是否已配置
  - 尾号提示
  - 上次使用时间
- 前端不返回明文。
- 保存新 key 时覆盖旧 key。
- 支持“测试凭据”按钮。
- 工具执行前根据用户和工作区解析 credential：
  1. 用户级配置
  2. 工作区级配置
  3. 系统环境变量 fallback，仅限本地开发/管理员默认配置

权限策略：

```text
low risk + read_only
  -> 默认允许

medium risk
  -> 需要用户显式启用

high risk / write / destructive
  -> 每次调用前确认，或用户设置 always allow

unknown third-party MCP server
  -> 默认不启用任何高风险工具
```

### 4.4 LLMToolPlanner 主路径化

目标：

减少硬规则，把“工具选择和参数规划”交给模型，但保留工程安全兜底。

不是直接删除 deterministic fast path，而是改成三层：

```text
1. Tool Candidate Retrieval
   从已启用工具里选出 5-12 个候选工具，避免把所有工具塞进上下文。

2. LLM Planner
   让模型基于候选工具、schema、用户问题、最近上下文输出结构化 plan。

3. Validator + Policy + Fallback
   schema 校验、权限校验、超时保护、fallback。
```

为什么不能把所有工具都给模型：

- 工具太多会浪费上下文。
- 工具描述会污染模型注意力。
- 延迟更高。
- 工具冲突更多。

候选工具检索策略：

- 第一版用关键词 + provider/category 粗召回。
- 后续可以给工具描述建 embedding，做语义召回。
- 用户当前工作区启用的工具优先。
- 最近使用过且成功的工具提高权重。

Planner 输出结构：

```json
{
  "should_use_tools": true,
  "reason": "用户询问路线、天气和途中服务区，需要地图路线、天气和网页/POI搜索。",
  "calls": [
    {
      "tool_key": "amap.route.plan",
      "confidence": 0.91,
      "reason": "需要获取深圳到汕头的驾车路线和耗时。",
      "arguments": {
        "origin": "深圳",
        "destination": "汕头",
        "mode": "driving"
      }
    },
    {
      "tool_key": "amap.weather.current",
      "confidence": 0.82,
      "reason": "需要查询目的地或沿途天气。",
      "arguments": {
        "city": "汕头"
      }
    }
  ]
}
```

deterministic fast path 的新定位：

- 不是主路径，而是 fallback / shortcut。
- 当 LLM planner 超时、输出非法、模型不支持结构化输出时使用。
- 对非常明确且低风险的问题可以作为 shortcut，但 trace 必须说明“使用快速规则路径”。

### 4.5 有限循环 Tool Workflow

目标：

支持复杂问题拆成多步，而不是一次规划后固定执行。

第一版不做完整 LangGraph，先做轻量有限循环：

```text
iteration = 1
  -> planner 生成 tool calls
  -> 执行工具
  -> 生成 observation summary

iteration = 2
  -> planner 读取 observation
  -> 判断是否还需要工具
  -> 如果需要继续调用
  -> 否则输出 final_context_ready

达到 max_iterations 或 max_tool_calls
  -> 停止工具循环
  -> 用已有来源回答
```

推荐默认限制：

- `max_iterations = 3`
- `max_tool_calls_per_turn = 6`
- `single_tool_timeout = 15s`
- `workflow_timeout = 45s`
- `max_tool_context_chars = 8000`

例子：

```text
用户：
查一下深圳到汕头路上有哪些服务区，顺便看天气和预计耗时

第 1 轮：
  amap.route.plan 深圳 -> 汕头

观察：
  路线经过沈海高速等，耗时约 N 小时

第 2 轮：
  amap.poi.search 沿途/高速服务区
  amap.weather.current 汕头

观察：
  返回服务区和天气

第 3 轮：
  planner 判断信息足够
  stop
```

### 4.6 工具结果结构化和来源增强

目标：

工具结果不仅给模型一段文本，也保留结构化字段。

`ExternalSource` 需要继续增强：

```text
display_text       # 给用户/模型看的自然语言
structured_data    # 路线、天气、搜索结果等结构化数据
provenance         # 来自哪个 MCP server/tool/call_id
confidence         # 结果置信度或匹配质量
warnings           # 地点可能模糊、天气粒度回退等
```

这样模型回答时可以更准确，前端来源卡片也能展示更美观。

## 5. 分阶段实施路线

### 阶段 A：Tool Trace 可解释性增强

优先级：最高。

当前状态：已完成第一版落地。

原因：

- 这是低风险改造。
- 能直接帮助调试工具调用。
- 后续做 LLM planner、MCP server 注册、权限策略时都依赖更完整 trace。

任务：

1. 后端补 planner 事件：
   - planner start/end
   - planner 输入摘要
   - candidate tools

## 6. 不建议现在做的事情

### 6.1 不建议马上完整引入 LangGraph

原因：

- 当前项目已有自己的聊天执行、上下文治理、工具 trace、数据库结构。
- 直接引入 LangGraph 会带来状态迁移和调试复杂度。
- 我们当前最需要的是工具目录、权限、trace、MCP 注册，不是图框架本身。

建议：

- 先实现轻量 `ToolWorkflowService`。
- 等工具循环复杂到明显需要状态图时，再评估 LangGraph。

### 6.2 不建议开放本地 stdio MCP

原因：

- 当前服务器是多人共享 Linux。
- 本地 stdio MCP 可能执行任意命令。
- 安全边界复杂。

建议：

- 第一版只支持远程 HTTP / SSE / Streamable HTTP MCP。
- stdio MCP 放到后续独立部署环境再考虑。

### 6.3 不建议一开始做完整插件市场

原因：

- 插件市场需要审核、版本、权限、依赖、安全扫描。
- 当前个人项目阶段不需要这么重。

建议：

- 先做“本地工具目录 + 用户自定义 MCP server”。
- 后续再考虑内置推荐列表。

### 6.4 不建议完全删除 deterministic planner

原因：

- 模型规划不稳定。
- 本地 Ollama 模型的 function calling/JSON 稳定性不一定好。
- 明确低风险问题使用 shortcut 更快。

建议：

- deterministic planner 保留为 shortcut/fallback。
- 但必须在 trace 中透明展示。

### 11.1 已落地能力

用户自定义 MCP Server：

- 用户可以在设置页添加远程 MCP Server。
- 每个 server 有独立 `server_key`、URL、鉴权方式、credential provider。
- 支持测试连接和同步 `tools/list`。
- 同步后的工具写入数据库，默认禁用。

动态工具目录：

- `ToolCatalog` 现在有两个来源：
  - 静态 manifest：项目内置 Tavily、高德等工具。
  - DB MCP tools：当前用户同步并启用的 MCP 工具。
- 动态 MCP 工具被统一转换成 `ToolDefinition`，进入 planner、schema validator、executor 和 Tool Trace。
- 这意味着后续接一个新远程 MCP server，不需要改聊天主链路。

用户级凭据：

- 用户可以配置 MCP server 对应的 API Key。
- 数据库存储使用 `SecretService` 加密。
- 前端只显示掩码。
- 后端不会在接口响应和 Tool Trace 中返回明文 key。
- 支持 `none`、URL `{api_key}`、Bearer、`X-API-Key` 四类第一版鉴权方式。

权限策略第一版：

- 工具保存 `read_only` 和 `risk_level`。
- MCP `annotations.readOnlyHint` 会映射成只读标记和风险等级。
- 新发现工具默认禁用，需要用户明确开启。
- 当前只是策略元数据和执行前 trace，不包含高风险调用暂停确认。

### 11.2 当前边界

没有做的能力需要明确留到后续：

- 不支持本地 stdio MCP。
- 不支持 OAuth / MCP Authorization 完整授权流程。
- 不支持 OpenAPI 自动导入。
- 不支持完整插件市场。
- 不支持高风险工具调用前确认。
- 不支持工具 marketplace 审核、签名、版本升级。
- 不支持真正的多轮 Agent tool loop。

这些不是遗漏，而是当前阶段刻意收敛边界。当前服务器是多人共享 Linux 普通用户环境，本地 stdio MCP 和任意插件安装都不适合直接开放。

### 11.3 继续实施后的当前状态

  - 只做候选召回，不做最终参数抽取。

  - deterministic planner 退到 runtime 缺失、超时、JSON/schema 失败时 fallback。

- `ToolWorkflowService`

### 11.5 默认工具 Schema 原则调整

2026-06-06 继续调整默认工具 schema 策略：

- 默认 MCP 工具不再使用项目手写 input schema。
- Tavily / 高德默认工具的 `input_schema` 改为 MCP server `tools/list` 返回的原始 `inputSchema`。
- 项目只补充运行元数据，例如 category、credential provider、result mapper、风险等级和只读标记。
- 对 MCP raw schema 与自然语言之间的落差，在 adapter 执行层处理。

典型例子：

- 高德 `maps_direction_driving` 的 MCP schema 要求 `origin/destination` 是经纬度。
- 用户通常输入“深圳到汕头”这种地点名。
- 现在执行器会在调用 `maps_direction_driving` 前自动调用 `maps_geo` 把地点名转坐标。
- 这样既保留 MCP schema 作为真实接口契约，也避免用户自然语言参数直接导致工具失败。

对“深圳到汕头路上有哪些服务区，顺便看天气和预计耗时”这类复杂问题：

- 候选工具会包含路线、天气、地点搜索和网页搜索。
- 预计耗时走 `amap.maps.direction.driving`。
- 天气走 `amap.maps.weather`。
- 服务区当前优先召回 `amap.maps.text_search` 和 `web.tavily.search`。
- 真正沿路线轨迹分段查服务区，还需要后续实现“观察路线结果后继续规划下一轮工具”的 Agent loop。

### 11.6 Tool DAG 与有限 Agent Loop 第一版

2026-06-06 继续完成：

- Planner 输出工具依赖图。
- Executor 按依赖图并行/顺序调度。
- ExternalContextService 最多 2 轮观察结果后继续规划。

核心设计：

```text
LLM 负责生成 depends_on
后端负责校验和调度
无依赖节点并行执行
依赖节点等待上游完成
每轮结果压缩成 observations
下一轮 planner 基于 observations 继续判断
```

这避免了继续用规则写：

- 天气多城市并行。
- 路线后查服务区。
- 先 geo 后 route。

后端不需要知道具体业务规则，只需要执行通用 DAG。

当前仍保留限制：

- 最大 2 轮。
- 每轮最大工具数受 workflow 限制。
- 高风险工具阻断。
- 重复调用跳过。

后续如果要继续增强，应优先做：

- outputSchema 驱动的变量引用。
- 更结构化的 observations。
- 跨 round 去重。
- 高风险工具确认 resume。

### 11.7 工具调用阶段收尾

2026-06-07 完成工具调用阶段收尾。本阶段目标不是继续堆工具，而是把工具调用链路整理成可解释、可配置、可观测、可扩展的基础设施。

本轮完成：

- 流式稳定性：
  - 前端三个聊天代理 route 统一轻量 header。
  - 后端诊断 header 增加大小限制。
  - 模型错误通过 `model_error` 事件返回。
  - 前端区分主动停止、模型错误、流式中断、工具错误。
- Planner：
  - LLM planner 保持主路径。
  - deterministic fallback 只处理异常兜底。
  - prompt 增强多工具计划、并行/依赖关系和结构化工具优先策略。
  - 增加“路线 + 天气 + POI + 网页搜索”复杂 query 测试。
- MCP 工具目录：
  - 自定义 MCP Server 注册改为弹窗。
  - MCP tools 支持 schema 展示、描述覆盖、分类编辑、测试调用、启用/禁用。
  - 单工具测试直接调用对应 MCP `tools/call`，使用用户级凭据。
- 引用与 Trace：
  - `ExternalSource.metadata` 增加 `call_id/tool_key/tool_display_name/source_index`。
  - 回答来源卡片可查看原始结果。
  - 来源卡片可跳到 Tool Trace；Tool Trace 可跳到对应来源。

阶段性结论：

- 当前工具调用链路已经可以阶段性收尾。
- 短期不继续做“插件市场”或任意代码执行类工具。
- 后续主线应切换到知识库 / RAG：文档入库、索引、检索、引用定位、召回进入上下文治理。

工具层未来可继续探索：

- outputSchema 强类型变量引用：让下游工具可以引用上游工具结构化字段，而不是让 LLM 从文本观察里猜。
- 更结构化 observations：按 route/weather/poi/web_result 等类型压缩，降低第二轮 planner 的误判概率。
- MCP 安全治理：内网地址拦截、超时限制、响应大小限制、server 信任等级、危险工具确认。
- 工具统计看板：调用次数、成功率、平均耗时、失败原因、provider 维度成本估算。
- 工具能力 marketplace：仅在 MCP 安全、凭据隔离和权限确认成熟后再考虑。
