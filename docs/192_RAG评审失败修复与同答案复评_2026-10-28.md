# RAG评审失败修复与同答案复评

本次只修评审执行与可复核性，不修改题目、Gold标注、检索结果、答案内容或引用。原始报告中英文73/100、中文76/100完成评分；其余27/24题只有统一失败代码，不能据后来复现的数据虚构历史原因比例。

回看原始记录可精确区分为1例记录了无效响应、50例未保存请求错误细节；不能将51例全部说成JSON解析失败。新增诊断后真实复现了429，也复现了未转义公式，不据此倒推50例请求错误必然全部为限流。

## 原因与改动

原先只通过提示词要求JSON，没有使用供应商JSON模式；评审说明可能复制带反斜杠的公式而产生无效JSON，500 token的输出上限也缺少截断诊断。单次评审失败没有独立补评入口，批量调用时的429与格式错误均被压成judge_failed。

`backend/app/services/chat_provider_service.py` 为非流式兼容API补全增加可选 `response_format` 参数，仅请求方显式使用时传入，其余Chat/摘要请求保持原行为。不支持这一参数的协议显式拒绝，不静默宣称结构化输出生效。

评审端按已知Provider能力启用JSON模式；本次使用的硅基流动Qwen已通过真实请求验证。未知兼容服务默认不附加未经确认支持的参数，调用方可通过 `judge_json_mode` 显式配置；仍严格解析JSON并记录实际是否启用，不将未验证的自定义模型视为支持同一参数。

`backend/app/services/knowledge_e2e_evaluation_service.py` 新增 `judge_answer()`：评审使用JSON对象模式，说明限制80字且不复制公式；输出预算1000 token，总尝试最多3次，当前代码单次最多等60秒。格式缺失、超时、429与5xx可有限重试，401/403等永久错误不重试；429按Retry-After退避，缺失时等待15秒，超过60秒或无法解释的等待提示则直接保留失败待后续补评，不提前重打。严格校验缺字段、截断和布尔值冒充分数，不从不合法JSON里拼出评分。首次合法评分立即采用，低分也不追加重打。尝试数是应用层调用数，不包含SDK内部可能发生的HTTP重试。

诊断保留尝试序号、错误类型、HTTP状态、JSON错误位置、脱敏响应片段和耗时。不给模型发送接口凭据，不记录请求头或原始异常URL。新评测结果保留完整证据正文，避免只有800字符预览而无法复评。

`backend/scripts/rejudge_rag_answers.py` 读取原报告，按原文档/Chunk/顺序恢复同一活动版本的正文，并核对用户范围、文档、版本及已保存预览；不匹配即拒绝。旧报告没有完整输入快照，因此这是依据未重建的当前同版本资料与预览核对的重建，不能宣称拥有旧完整快照的密码学证明。

对全部200份原答案使用同一新格式统一复评，避免只补失败项而混用两套评审格式。续跑保留已取得的有效评分；显式补失败时保留上次全部尝试，汇总计入累计次数。初次两个库共四路并发仍触发429，这些失败完整保留；随后改为单Worker、至少6秒请求间隔，两个库顺序执行。部分已完成请求在新增60秒截止控制前执行，不能把新代码默认值说成全部历史请求的执行参数；这一差异不改变评分字段、解释限制和首次有效评分策略。没有重新发起Embedding、Rerank或答案生成。

复评报告的平均Judge耗时是每题最后一次执行组的耗时，不包含之前失败执行组、人工暂停、队列和请求节流等待；不能用它宣传整体评测提速。应用层累计尝试数保留历史失败，但SDK内部实际HTTP次数没有完整计数，也不应把两者混淆。
