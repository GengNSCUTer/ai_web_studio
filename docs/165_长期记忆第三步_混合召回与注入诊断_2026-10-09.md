## 一、三步各解决什么

第一步解决记忆的正确性：同一事实更正后，新旧版本一起切换；不能串用户或项目；本轮要求可以覆盖保存的默认偏好；凭证不进入记忆。

第二步解决记忆的产生：按新增用户消息后台提取，逐条核对原话；自动提取与自动启用分开，只有用户授权后的明确稳定低风险信息能自动生效，冲突等情况保留审核；可以更正、撤销并防止旧任务重新自动启用。

第三步解决记忆的使用：少量偏好常驻，事实按当前问题进行词法和语义混合召回；经过范围、版本、时效和总上下文预算后，记录真正交给模型的记忆，而不是把“查到了”当作“已经使用了”。

当前链路：

```text
当前问题
  → SQL 过滤用户/项目、active、enabled、TTL 和来源归属
  → 常驻偏好 + 事实词法匹配/向量相似度
  → RRF 融合候选
  → 复核最新设置、正文版本和撤销状态
  → 完整记忆行按预算组装
  → 全局上下文治理
  → 实际注入 ID/版本/范围/原因诊断
  → 在线模型最终回答 + 消息/运行指标持久化
```

## 二、实现方式与边界

`MemoryRetrievalService` 复用用户现有的 Embedding Provider、模型与维度设置。记忆向量是独立于知识库 Chunk 的缓存，当前将向量 JSON 存在记忆表的 Text 字段，在已过滤的小规模记忆集合上由应用代码精确计算余弦相似度。没有为记忆引入 pgvector ANN、BM25、Rerank 或图数据库；不能把知识库的索引结构与评测指标直接套在记忆上。

缓存签名包含 Provider、地址、模型、维度和模板版本；正文哈希包含记忆版本、标题和内容。改正文或切换模型后旧缓存不再复用，同维度不同模型也不能比较。缓存更新使用状态、版本与正文条件，不修改事实版本或更新时间，避免缓存生成把旧事实伪装成“刚更新”。

事实词法分数与语义排名通过 RRF 融合；当前语义最低相似度为 0.45，是实现初始值，尚未通过大规模记忆 Gold Set 调参。少量 profile/instruction 沿用有数量限制的画像选择，不把长期指令当普通事实自动启用。偏好最多 2 条，有事实时不超过四分之一记忆字符预算；总选择默认最多 8 条。

冷启动每次最多为 32 条未缓存事实补向量，其余事实仍参与词法检索，后续请求逐批补齐。问题输入最多 2,000 字符，单条记忆送 Embedding 前最多 4,000 字符，并先脱敏。Embedding 整体等待上限为 8 秒；不可用、超时、返回数量/维度不对、非有限数值或零向量都会回退词法。异常正文、地址和凭据不会进入诊断。

数据库快照与最终复核在独立短 Session 中执行，网络等待期间不持有该 Session/事务。调用 Embedding 前关闭读取事务，结束后重新查询当前范围和状态：中途撤销、更正、过期、关闭记忆或改变模型设置，旧网络结果不能重新注入或复活记忆。这不意味着模型已经收到的上下文可以事后撤回。

## 三、诊断与浏览器修复

诊断区分“记忆预算选中”和“全局预算后实际注入”，显示实际记忆 ID、版本、有效项目范围以及入选原因：常驻偏好、词法、语义或两路共同命中。它不宣称能证明模型内部实际使用了哪条记忆；最终答案仍需业务断言验证。

治理层保留结构化的记忆段，按完整行计算注入数量，不靠在整个 Prompt 中搜索标签，避免网页或历史内容伪造标签影响计数。预算截断时不保留半条事实。

真实浏览器测试发现原先上下文诊断只通过响应头传递，内容超过限制后会被省略，界面没有诊断入口。本次增加 NDJSON `context_info` 事件，普通发送和重新生成/编辑流程均可接收；保留原响应头兼容。当前 Chat 协议为 NDJSON，历史设计中讨论过的 SSE 不代表当前实现。

## 五、验证记录

验证使用在线 OpenAI-compatible Chat 和硅基流动 Embedding，不加载 Ollama。配置真实 PostgreSQL/pgvector 后，全量后端 578 tests OK，无跳过；前端 lint/build、compileall 和 diff 检查通过。测试中的流式故障、超时日志为模拟场景，不是失败用例。

第三步固定场景已通过：10 个独立 API 会话加 1 个浏览器会话，全部检查最终回答，API 会话同时检查实际注入记录与持久化运行指标一致。覆盖：

1. 同义问题找到项目事实。
2. 无共有词的问题靠语义召回事实，词法分数为 0，最终答案使用正确数据库版本。
3. 新会话复用已生成的记忆向量。
4. 跨项目事实不注入、不出现在回答中。
5. 本轮英文要求排除保存的中文默认。
6. 更正后使用 PostgreSQL 17 和新代号，旧版本不注入。
7. 撤销后旧代号不再注入。
8. 过期事实不再注入。
9. Embedding 连接故障时回退词法，仍完成正确回答。
10. 关闭长期记忆后不注入事实。
11. 浏览器完成真实对话并显示实际记忆诊断，console/page error 为 0。

第一步和第二步也在最终代码上重新跑了真实回归：独立记忆 Worker 提取、冲突候选审核、新旧版本替换、新会话回答、本轮语言覆盖、自动授权、原文证据、普通陈述自动生效、更正/忘记与撤销保护均通过；两套浏览器回归错误均为 0。自动开关恢复原值，临时项目、会话及测试记忆清理。

单元/集成测试另覆盖同维度换模型、坏向量及数值边界、API 故障、超时、网络期间配置变化/更正/撤销/过期、缓存不改事实时间、画像不挤占事实、总预算只注入完整行。真实 PostgreSQL 用例在外部调用期间检查没有闲置事务，并以短 lock_timeout 验证撤销可完成。

以上是固定场景功能验收，不是整体提取准确率或召回率，也没有声称相对旧版本的平均延迟下降。它证明了一个词法漏召回实例被语义路径补上，并验证既有正确性、自动性与 Chat 链路能一起工作。

重复实测中曾有一次“更正后新会话”的最终回答未包含全部预期事实，随后完整复跑通过。失败时的旧断言未记录缺少哪个测试事实，不能据此断言是召回错误或某个具体模型错误；脚本现已先核对注入 ID，再明确指出缺少哪个合成测试值。保留这次未通过记录，说明“最终一轮通过”不等于模型在重复运行中始终完整利用记忆，不把重跑后通过描述成零失败稳定性指标。

## 六、保留的限制

自动生效仍保守：以用户原文、有限规则与冲突/范围校验决定，复杂语义继续审核；没有自动判断任意事实冲突。设置页能查看来源并撤销，但后台记忆自动生效的实时“已记住”聊天通知还未做，新增的 `context_info` 是召回诊断事件。缓存初次补齐可能增加 Chat 准备时间；大规模记忆检索需另行测量再考虑索引。语义阈值、总体召回质量和复杂跨语言场景仍需扩大测试集验证。

目前服务保持同一套：前端 `http://127.0.0.1:32018`，后端 `http://127.0.0.1:32017`，PostgreSQL `127.0.0.1:35433`；记忆、知识库及 Durable Worker 按各自职责独立运行。
