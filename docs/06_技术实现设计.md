1. 所有服务都能在用户目录下启动

5. 优先选单机、用户态、可迁移的组件

## 2. 为什么第一版不建议用 Docker

这个问题要单独说清楚。

### 2.1 当前用户没有 Docker 权限

实际验证结果已经说明：

- `docker` 命令虽然存在
- 但访问 `/var/run/docker.sock` 被拒绝

也就是说你现在无法直接运行容器。

### 2.2 即使管理员以后给权限，也不建议现在以 Docker 为前提

因为当前第一版目标是：

- 快速落地 MVP
- 可在普通用户环境内独立完成

如果你现在把第一版绑死在 Docker 上，会产生额外复杂度：

- 需要镜像构建
- 需要端口映射
- 需要容器持久化卷
- 需要处理共享服务器上的 Docker 权限和资源竞争

### 2.3 第一版建议策略

所以第一版明确建议：

- **不使用 Docker**

后续如果项目做成熟，需要：

- 部署到独立机器
- 或自己有容器权限

再补 Docker 化。

### 2.4 第二阶段可以再做容器化

也就是说：

- 第一版：本地用户态运行
- 第二版：补 Dockerfile / compose

这条路径更稳。

## 3. 为什么这次改成直接用 PostgreSQL

你提的这个顾虑是对的：

> 如果后续本来就想走正式架构，那一开始为了省事用 SQLite，后面再迁库，反而会浪费时间。

所以这一版设计改成：

- **从第一天开始就按 PostgreSQL 设计**

### 3.1 为什么 PostgreSQL 更适合作为正式底座

原因包括：

- 更接近标准 Web 项目
- 事务能力更好
- 并发和扩展能力更强
- 后续接登录、多用户、统计、RAG、pgvector 更自然
- 简历上也更像完整工程项目

### 3.2 为什么普通用户环境下仍然可以考虑 PostgreSQL

虽然你不是管理员，但这不等于不能用 PostgreSQL。

可行思路通常有两种：

#### 方案 A：安装到个人目录 / conda 环境

也就是：

- PostgreSQL 二进制放在你的 `HOME` 或个人工作目录下
- 数据目录也放在你的个人目录下
- 进程由你自己启动，不注册成系统服务

#### 方案 B：以后有条件再 Docker 化

也就是：

- 当前阶段先跑用户态 PostgreSQL
- 将来迁到自己机器或有权限环境时，再容器化

### 3.3 这次为什么不再把 SQLite 作为主方案

因为当前项目的目标已经不是：

- 一个临时脚本 demo

而是：

- 一个后续要继续扩展的前后端分离 AI Web 应用

那么底层数据库从一开始就按 PostgreSQL 定下来，会更合理。

## 5. 共享服务器上的运行模式设计

这是这份文档里最重要的现实问题之一。

### 5.1 不建议默认对外暴露服务

在共享服务器上，第一版建议所有服务默认绑定：

- `127.0.0.1`

不要默认绑定：

- `0.0.0.0`

原因：

- 更安全
- 避免被同机其他用户或外网直接访问
- 不需要考虑公网暴露和额外权限

### 5.2 访问方式建议

推荐使用：

- `SSH 端口转发`
- 或 VS Code Remote / 端口转发功能

也就是：

- 服务只在服务器本地监听
- 你本地浏览器通过隧道访问

### 5.3 为什么这样最适合你

因为你现在：

- 不是管理员
- 不一定能配 Nginx
- 不一定能开公网端口
- 不一定知道机器上哪些端口已经被占

而 `127.0.0.1 + 高位端口 + SSH 转发` 是最稳妥的用户态方案。

### 5.4 端口选择策略

第一版建议统一使用：

- **高位非特权端口**

不要用：

- `80`
- `443`
- `5432`

这类常见系统端口。

推荐风格：

- 前端：`31xxx`
- 后端：`32xxx`

例如：

- 前端：`31007`
- 后端：`32007`

也可以按你的 uid 做一个偏移，但第一版不必太复杂，只要：

- 选高位端口
- 放进配置文件
- 冲突时可改

即可。

### 5.5 端口冲突怎么处理

在共享机器上，端口冲突很常见。

所以设计上要求：

- 前端端口可配置
- 后端端口可配置
- 配置集中放 `.env` 或配置文件

第一版不要把端口写死在代码里。

## 9. API 设计

### 9.1 总体原则

第一版 API 设计遵循：

- REST + SSE
- JSON 请求响应
- 流式聊天单独一个接口
- 前端统一通过 Next.js 自身的 `/api/*` 代理后端，避免浏览器直接跨域请求 FastAPI

### 9.2 推荐接口

#### 会话接口

- `GET /api/conversations`
- `POST /api/conversations`
- `GET /api/conversations/{id}`
- `PATCH /api/conversations/{id}`
- `DELETE /api/conversations/{id}`

#### 消息接口

- `GET /api/conversations/{id}/messages`
- `POST /api/conversations/{id}/messages`
- `POST /api/conversations/{id}/stream`
- `POST /api/messages/{id}/regenerate` 可放 P1
- `PATCH /api/messages/{id}` 可放 P1

#### 文件接口

- `POST /api/files/upload`
- `DELETE /api/files/{id}`

#### 设置接口

- `GET /api/settings`
- `PATCH /api/settings`

#### 模型接口

- `GET /api/models`

这个接口用于：

- 读取 Ollama 当前可用模型列表

对产品体验很有帮助。

### 9.3 为什么流式接口单独设计

因为普通 CRUD 请求和流式聊天不是一回事。

建议：

- 非流式接口走普通 JSON
- 聊天生成走 `SSE`

这样前端实现简单很多。

### 9.4 前后端联通策略

在共享服务器 + 本地端口转发场景下，前端和后端之间建议明确采用：

- **Next.js BFF / 代理层模式**

也就是：

1. 浏览器只访问 Next.js 前端服务
2. Next.js 内部再去请求 FastAPI
3. 前端页面不直接暴露 FastAPI 地址

这样做的好处：

- 浏览器侧不需要单独处理 CORS
- 本地访问时只需要转发一个前端端口也可以工作
- 后面如果后端地址变化，前端页面层不需要大改

## 10. 为什么第一版建议用 SSE，而不是 WebSocket

这里给你一个明确建议：

- **第一版优先用 SSE**

### 原因

第一版的核心流式场景本质上是：

- 前端发起一次请求
- 后端持续往前端推文本增量

这是一个非常典型的单向流式响应场景。

SSE 的优势：

- 实现简单
- 和 FastAPI 集成容易
- 前端处理比 WebSocket 简单
- 对“边生成边展示回答”足够用

### WebSocket 什么时候更值得用

只有当你需要：

- 更复杂的双向实时通信
- 多事件通道
- 多客户端协同

时，WebSocket 才更必要。

第一版没有这个必要。

## 11. Ollama 接入设计

### 11.1 第一版模型适配层

后端不要在 route 里直接写 Ollama 请求。

应该单独做：

- `ollama_service.py`

它负责：

- 调模型列表接口
- 调聊天接口
- 处理流式响应
- 统一错误处理

### 11.2 为什么要单独封装

因为以后你大概率会扩展：

- OpenAI-compatible API
- 别的本地模型服务
- 多 provider 切换

如果一开始不封装，后面会很难看。

### 11.3 输入组织原则

第一版聊天输入分 3 类：

- 文本消息历史
- 图片附件
- 文档解析文本

后端在调用 Ollama 前，需要先把这些统一整理成模型输入格式。

也就是说：

- 聊天 route 不直接“拼 prompt”
- `chat_service` 负责做上下文组装
- `ollama_service` 只负责真正调用模型

## 12. 图片与文档处理设计

### 12.1 图片处理

第一版建议：

- 上传后保存在本地目录
- 保存数据库附件记录
- 聊天时读取图片文件并交给模型

不做：

- 图片长期知识索引
- 图像编辑
- OCR 流水线拆分

### 12.2 文档处理

第一版文档支持：

- `txt`
- `md`
- `pdf`
- `docx`

建议单独做：

- `parser_service.py`

按文件类型分别解析。

### 12.3 文档上下文策略

第一阶段不做 RAG，所以建议策略明确收敛为“会话附件上下文”：

- 文档解析出纯文本
- 后端按字符或 token 上限截取
- 作为当前轮或当前会话的补充上下文拼接给模型

这意味着：

- 文档不是长期检索索引
- 文档也不是永久工作记忆
- 文档是“当前任务上下文”的一部分

### 12.4 为什么要限制文档上下文长度

即便模型支持 128k / 256k 输入，也不能无限拼：

- 解析文本太长会拖慢响应
- 多轮会话叠加后很快膨胀
- 图片、文件、system prompt 和历史消息会互相抢预算
- 共享服务器资源有限

第一阶段建议做一个简单但可控的策略：

- 文档文本只取前 N 字符或前 N token
- 超过预算时优先裁剪更老的附件或低优先级内容
- 后续再做更细的上下文治理

## 13. 上下文治理设计

这一章是本项目后续最重要的技术点之一。

### 13.1 上下文治理目标

第一阶段上下文治理要解决 4 个问题：

1. 同一会话可连续追问
2. 上下文不会无限膨胀
3. 图片、文件、历史消息、系统提示有明确优先级
4. 为后续摘要、长期记忆、缓存命中优化留接口

### 13.2 上下文来源分层

第一阶段模型输入建议拆成 5 层：

1. `system_prompt`
2. 会话级近期消息
3. 当前用户输入
4. 当前轮图片附件
5. 当前轮文件附件解析文本

这 5 层必须保持明确顺序和稳定拼接模板。

### 13.3 短期上下文策略

第一阶段建议使用简单但可控的策略：

- 保留最近 `N` 轮消息原文
- 文档上下文限制最大长度
- 图片只带当前轮附件
- system prompt 永远保留

建议起步值：

- 最近 `10` 轮消息
- 每个文档截取前 `8000` 到 `12000` 字符
- 总上下文超预算时优先裁剪较旧消息或低优先级附件

### 13.4 上下文预算控制

后端应增加一个轻量“上下文预算器”，用于控制：

- 历史消息预算
- 附件预算
- 文档预算
- system prompt 预算

如果后续有 token 统计能力，优先按 token；否则第一版先按字符数近似。

当前实现已经从“固定阈值”升级到“动态预算框架”，核心规则如下：

- 用户设置里新增 `model_context_window`
- 用户设置里新增 `context_mode`
- 后端根据这两个字段动态推导：
  - 最大历史消息数
  - 最大总字符预算
  - 最大附件字符预算
  - 图片等效字符预算

### 13.5 前端上下文诊断面板

为了让上下文治理不再是“后端黑盒”，当前前端已经接入一层轻量诊断可视化：

- 后端通过响应头返回 `x-context-stats`
- 后端通过响应头返回 `x-context-notices`
- 前端将其解析为独立诊断卡片和提示列表

当前前端可直接展示的治理指标包括：

- 上下文模式
- 模型上下文窗口
- 本轮估算字符数
- 被裁剪的历史消息数
- 摘要字符数
- 是否触发摘要刷新
- 摘要刷新源消息数
- 摘要刷新源字符数
- 总字符预算上限
- 附件字符预算上限

当前交互形式不是长期固定占位，而是：

- 输入区旁的轻量“上下文”按钮
- 点击后弹出诊断浮层查看详情

这样做的原因是：

- 日常对话时不干扰主聊天空间
- 需要调试和观察时仍然能快速展开

这层设计的作用是：

- 方便开发阶段验证预算是否合理
- 方便后续做参数调优和问题排查
- 为后续“更高质量摘要压缩”和“缓存命中优化”提供可观察性基础
  - 最大摘要长度

当前 `context_mode` 分为 3 档：

- `conservative`
  更保守，优先保证响应稳定和资源可控
- `balanced`
  默认模式，兼顾上下文长度和推理稳定性
- `long-context`
  更激进，优先保留更多历史和附件内容

当前预算器仍然是“字符级近似预算”，不是精确 token 预算。这样做的原因是：

- 兼容 Ollama 和 OpenAI-compatible 两类 provider
- 不依赖额外 tokenizer
- 在当前共享服务器环境下实现成本更低

后续如果要继续优化，可以再演进为：

- provider 级 token 预算器
- 模型级 tokenizer 估算
- 命中缓存时的差异化预算策略

### 13.5 上下文压缩策略

参考 Anthropic / Codex / Claude Code 的思路，后续建议引入两类压缩：

#### 局部压缩

- 对最老的消息做摘要
- 对工具结果做折叠
- 对超长附件只保留摘要和关键片段

#### 全局压缩

- 会话级摘要
- 长会话关键事实抽取
- 长期记忆写入

当前实现状态：

- 已支持“滚动摘要记忆层”
- 摘要会写入 `conversations.context_summary`
- 已新增 `context_summary_boundary_message_id`，用于标记当前摘要已经覆盖到哪一条历史消息
- 后续请求会把该摘要作为较早历史的压缩记忆注入，只回放边界之后的最近原始消息
- 已接入模型驱动摘要压缩：摘要刷新时优先使用当前会话 provider/model 做非流式摘要生成
- 已保留规则摘要兜底：如果模型摘要失败、超时或返回空内容，会自动回退到原来的结构化规则摘要，避免影响正常聊天

当前这一版摘要策略的特点是：

- 质量优先：优先由模型抽取用户目标、约束、重要事实、已完成决策和待办
- 稳定兜底：模型摘要不可用时仍能使用规则摘要继续运行
- 成本可控：不每轮重算，只在未压缩历史超过阈值时刷新

当前摘要刷新策略：

- 不再每轮都重算摘要
- 当“未被摘要覆盖的较早历史”超过一定消息数或字符量时，才触发滚动刷新
- 当前阈值是：
  - 至少 `6` 条消息
  - 或至少 `4000` 字符

当前摘要分层方式：

- `system_prompt`
- 会话级滚动摘要
- 最近原始消息窗口
- 当前轮用户输入 / 图片 / 文件

这意味着当前项目已经从“单层历史裁剪”升级成了“短期工作记忆 + 压缩记忆”的双层结构。

但缺点也很明确：

- 摘要会额外消耗一次 provider 调用
- 仍然使用字符级预算估算，不是 tokenizer 级精确预算
- 摘要质量依赖当前模型能力和 provider 稳定性

所以下一步应重点升级：

- 区分“短期对话摘要”和“长期事实记忆”
- 增加摘要刷新和失效策略
- 引入 tokenizer 级预算和摘要质量评估

### 13.6 长期记忆设计

长期记忆不是把全部历史挂到每次请求里，而是只保留高价值事实。

建议分成 4 类：

- Profile Memory
  用户稳定偏好、身份、语言习惯

- Task Memory
  当前长期任务目标、工作区背景

- Episode Memory
  某次会话里沉淀出的关键事实

- Artifact Memory
  文件、图片、摘要、结构化提取结果

当前实现状态：

- 已新增 `user_memories` 表，按用户隔离存储长期记忆
- 已支持 4 类手动长期记忆：
  - `profile`：用户偏好、交流习惯、技术偏好
  - `project`：长期项目背景、项目目标、技术栈
  - `fact`：用户明确保存的重要事实
  - `instruction`：希望系统长期遵守的规则
- 已新增 `memory_enabled` 和 `memory_max_chars` 用户设置
- 已新增记忆 CRUD 接口：
  - `GET /api/memories`
  - `POST /api/memories`
  - `PATCH /api/memories/{id}`
  - `DELETE /api/memories/{id}`
- 聊天链路会在 `system_prompt` 后、会话滚动摘要前注入启用的长期记忆
- 上下文诊断会返回：
  - `memory_enabled`
  - `memory_injected`
  - `memory_count`
  - `memory_chars`

当前长期记忆 MVP 的边界：

- 第一版只做手动保存、启停和删除，避免模型自动误记
- 不做跨用户共享记忆
- 不做自动跨会话知识融合
- 不做向量化长期记忆库

下一步升级方向：

- 模型生成“建议记忆”，用户确认后再保存
- 增加记忆冲突检测和去重
- 给长期记忆增加来源会话和来源消息追踪
- 将 Artifact Memory 与附件索引化能力结合

### 13.7 缓存命中策略

为了后续兼容 OpenAI / Claude / Gemini / 百炼 / DeepSeek / vLLM 一类能力，第一阶段就要尽量保持：

- system prompt 稳定
- 附件注入模板稳定
- 历史消息顺序稳定
- 不要频繁改前缀结构

缓存命中本质上依赖 prompt 结构纪律。

### 13.8 为什么不建议第一版就做“全历史拼接”

因为共享服务器资源有限，而且模型越大，长上下文越容易导致：

- 响应慢
- 显存和算力压力大
- 模型注意力分散

所以第一阶段必须做可控裁剪，而不是全量历史直塞。

删除消息或会话时，要同步处理：

- 数据库记录
- 实际文件

否则会积累垃圾文件。
