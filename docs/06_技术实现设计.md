## 1. 环境约束与结论

先把你当前环境约束讲清楚，因为这会直接影响架构选型。

### 1.1 已确认的环境事实

当前服务器环境里，已经确认到这些情况：

- 你是普通用户，不是管理员
- `docker` 命令存在，但当前用户无权访问 Docker daemon
- `sqlite3` 可用
- `node` 可用，版本是 `v24.14.0`
- `npm` 可用，版本是 `11.9.0`
- `python` 可用
- 当前已有 `conda` 环境 `agent_study`
- 已创建独立应用环境：`/disk2/gengnan/conda_envs/ai_web_studio`
- 已验证可用的独立 PostgreSQL 运行环境：`/disk2/gengnan/conda_envs/pg_runtime`

这意味着：

- **第一版不要把 Docker 当成前提**
- **第一版不要依赖系统级数据库安装**
- **第一版不要依赖管理员帮你配 Nginx / systemd / PostgreSQL 服务**

### 1.2 设计原则

基于这个环境，第一版设计遵循 5 条原则：

1. 所有服务都能在用户目录下启动
2. 不要求 root 权限
3. 不要求 Docker
4. 不要求系统级守护进程
5. 优先选单机、用户态、可迁移的组件

### 1.3 第一版技术结论

因此，第一版建议如下：

#### 前端

- `Next.js`
- `TypeScript`
- `Tailwind CSS`
- `shadcn/ui`
- 聊天线程侧继续补齐主流网页端交互：
  - 最后一条回答重生成
  - 最后一条用户消息内联编辑后重答
  - 消息附件预览
  - 输入区待发送附件预览

#### 后端

- `FastAPI`
- `SQLAlchemy`
- `Pydantic`
- `Uvicorn`
- 聊天接口在主 `/api/chat/text-stream` 之外，额外补两条最后一轮消息级重放链路：
  - `POST /api/chat/regenerate-last-stream`
  - `POST /api/chat/edit-last-user-stream`
- 其中“编辑上一条用户消息并重答”不仅会更新消息文本，也会同步替换该条用户消息的附件绑定
- 历史消息加载时，对 `streaming` 助手消息采用“超时后才失败”的 stale 判定，避免用户切换会话时误伤仍在生成中的回答

#### 数据存储

- **架构目标直接定为 PostgreSQL**

但运行方式采用：

- **用户态 PostgreSQL**

也就是：

- PostgreSQL 不装到系统服务里
- 而是装到你的个人目录或个人环境里运行

这样做的原因是：

- 避免第一版用 SQLite，后续还要迁移
- 保持数据库架构从第一天就贴近正式版
- 同时又不依赖管理员权限或 Docker daemon

#### 模型服务

- 本地 `Ollama`
- 默认模型：`qwen3.5:27b-q8_0`

#### 文件存储

- 本地磁盘目录

## 2. 为什么第一版不建议用 Docker

这个问题要单独说清楚。

### 2.1 当前用户没有 Docker 权限

实际验证结果已经说明：

- `docker` 命令虽然存在
- 但访问 `/var/run/docker.sock` 被拒绝

也就是说你现在无法直接运行容器。

### 2.2 即使管理员以后给权限，也不建议现在以 Docker 为前提

因为当前第一版目标是：

- 快速落地 MVP
- 可在普通用户环境内独立完成

如果你现在把第一版绑死在 Docker 上，会产生额外复杂度：

- 需要镜像构建
- 需要端口映射
- 需要容器持久化卷
- 需要处理共享服务器上的 Docker 权限和资源竞争

### 2.3 第一版建议策略

所以第一版明确建议：

- **不使用 Docker**

后续如果项目做成熟，需要：

- 部署到独立机器
- 或自己有容器权限

再补 Docker 化。

### 2.4 第二阶段可以再做容器化

也就是说：

- 第一版：本地用户态运行
- 第二版：补 Dockerfile / compose

这条路径更稳。

## 3. 为什么这次改成直接用 PostgreSQL

你提的这个顾虑是对的：

> 如果后续本来就想走正式架构，那一开始为了省事用 SQLite，后面再迁库，反而会浪费时间。

所以这一版设计改成：

- **从第一天开始就按 PostgreSQL 设计**

### 3.1 为什么 PostgreSQL 更适合作为正式底座

原因包括：

- 更接近标准 Web 项目
- 事务能力更好
- 并发和扩展能力更强
- 后续接登录、多用户、统计、RAG、pgvector 更自然
- 简历上也更像完整工程项目

### 3.2 为什么普通用户环境下仍然可以考虑 PostgreSQL

虽然你不是管理员，但这不等于不能用 PostgreSQL。

可行思路通常有两种：

#### 方案 A：安装到个人目录 / conda 环境

也就是：

- PostgreSQL 二进制放在你的 `HOME` 或个人工作目录下
- 数据目录也放在你的个人目录下
- 进程由你自己启动，不注册成系统服务

#### 方案 B：以后有条件再 Docker 化

也就是：

- 当前阶段先跑用户态 PostgreSQL
- 将来迁到自己机器或有权限环境时，再容器化

### 3.3 这次为什么不再把 SQLite 作为主方案

因为当前项目的目标已经不是：

- 一个临时脚本 demo

而是：

- 一个后续要继续扩展的前后端分离 AI Web 应用

那么底层数据库从一开始就按 PostgreSQL 定下来，会更合理。

## 5. 共享服务器上的运行模式设计

这是这份文档里最重要的现实问题之一。

### 5.1 不建议默认对外暴露服务

在共享服务器上，第一版建议所有服务默认绑定：

- `127.0.0.1`

不要默认绑定：

- `0.0.0.0`

原因：

- 更安全
- 避免被同机其他用户或外网直接访问
- 不需要考虑公网暴露和额外权限

### 5.2 访问方式建议

推荐使用：

- `SSH 端口转发`
- 或 VS Code Remote / 端口转发功能

也就是：

- 服务只在服务器本地监听
- 你本地浏览器通过隧道访问

### 5.3 为什么这样最适合你

因为你现在：

- 不是管理员
- 不一定能配 Nginx
- 不一定能开公网端口
- 不一定知道机器上哪些端口已经被占

而 `127.0.0.1 + 高位端口 + SSH 转发` 是最稳妥的用户态方案。

### 5.4 端口选择策略

第一版建议统一使用：

- **高位非特权端口**

不要用：

- `80`
- `443`
- `5432`

这类常见系统端口。

推荐风格：

- 前端：`31xxx`
- 后端：`32xxx`

例如：

- 前端：`31007`
- 后端：`32007`

也可以按你的 uid 做一个偏移，但第一版不必太复杂，只要：

- 选高位端口
- 放进配置文件
- 冲突时可改

即可。

### 5.5 端口冲突怎么处理

在共享机器上，端口冲突很常见。

所以设计上要求：

- 前端端口可配置
- 后端端口可配置
- 配置集中放 `.env` 或配置文件

第一版不要把端口写死在代码里。

## 9. API 设计

### 9.1 总体原则

第一版 API 设计遵循：

- REST + 文本流
- JSON 请求响应
- 流式聊天单独一个接口
- 前端统一通过 Next.js 自身的 `/api/*` 代理后端，避免浏览器直接跨域请求 FastAPI

### 9.2 推荐接口

#### 会话接口

- `GET /api/conversations`
- `POST /api/conversations`
- `GET /api/conversations/{id}`
- `PATCH /api/conversations/{id}`
- `DELETE /api/conversations/{id}`

#### 消息接口

- `GET /api/conversations/{id}/messages`
- `POST /api/conversations/{id}/messages`
- `POST /api/chat/text-stream`
- `POST /api/chat/regenerate-last-stream`
- `POST /api/chat/edit-last-user-stream`

#### 文件接口

- `POST /api/files/upload`
- `DELETE /api/files/{id}`

#### 设置接口

- `GET /api/settings`
- `PATCH /api/settings`

当前这组接口在前端的映射关系是：

- `/api/chat`
  新发一条用户消息并流式获取回答
- `/api/chat/regenerate`
  重新生成当前会话最后一条 assistant 回答
- `/api/chat/edit-last-user`
  编辑当前会话最后一条 user 消息，并复用同一条 assistant 消息重新流式回答

当前消息级操作边界：

- 只支持“最后一轮”操作，不支持任意历史轮次直接编辑重放
- 这样做的原因是：可以保证实现简单、上下文一致性清晰，也避免前端出现过深的分叉历史管理

#### 模型接口

- `GET /api/models`

这个接口用于：

- 读取 Ollama 当前可用模型列表

对产品体验很有帮助。

### 9.3 为什么流式接口单独设计

因为普通 CRUD 请求和流式聊天不是一回事。

建议：

- 非流式接口走普通 JSON
- 聊天生成走文本流接口，前端通过 `fetch + ReadableStream` 消费

这样前端实现简单很多。

### 9.4 前后端联通策略

在共享服务器 + 本地端口转发场景下，前端和后端之间建议明确采用：

- **Next.js BFF / 代理层模式**

也就是：

1. 浏览器只访问 Next.js 前端服务
2. Next.js 内部再去请求 FastAPI
3. 前端页面不直接暴露 FastAPI 地址

这样做的好处：

- 浏览器侧不需要单独处理 CORS
- 本地访问时只需要转发一个前端端口也可以工作
- 后面如果后端地址变化，前端页面层不需要大改

## 10. 为什么第一版建议用文本流 / SSE，而不是 WebSocket

这里给你一个明确建议：

- **第一版优先用文本流 / SSE 这类单向流式方案**

当前实际实现说明：

- 主聊天链路已经使用纯文本流
- Next.js API route 负责把后端流式响应转发给浏览器
- 前端通过 `fetch + ReadableStream` 逐块读取并更新消息
- 重新生成与编辑后重答也复用这套流式主链路

### 原因

第一版的核心流式场景本质上是：

- 前端发起一次请求
- 后端持续往前端推文本增量

这是一个非常典型的单向流式响应场景。

文本流 / SSE 的优势：

- 实现简单
- 和 FastAPI 集成容易
- 前端处理比 WebSocket 简单
- 对“边生成边展示回答”足够用

### WebSocket 什么时候更值得用

只有当你需要：

- 更复杂的双向实时通信
- 多事件通道
- 多客户端协同

时，WebSocket 才更必要。

第一版没有这个必要。

## 11. Ollama 接入设计

### 11.1 第一版模型适配层

后端不要在 route 里直接写 Ollama 请求。

应该单独做：

- `ollama_service.py`

它负责：

- 调模型列表接口
- 调聊天接口
- 处理流式响应
- 统一错误处理

### 11.2 为什么要单独封装

因为以后你大概率会扩展：

- OpenAI-compatible API
- 别的本地模型服务
- 多 provider 切换

如果一开始不封装，后面会很难看。

### 11.3 输入组织原则

第一版聊天输入分 3 类：

- 文本消息历史
- 图片附件
- 文档解析文本

后端在调用 Ollama 前，需要先把这些统一整理成模型输入格式。

也就是说：

- 聊天 route 不直接“拼 prompt”
- `chat_service` 负责做上下文组装
- `ollama_service` 只负责真正调用模型

## 12. 图片与文档处理设计

### 12.1 图片处理

第一版建议：

- 上传后保存在本地目录
- 保存数据库附件记录
- 聊天时读取图片文件并交给模型

不做：

- 图片长期知识索引
- 图像编辑
- OCR 流水线拆分

### 12.2 文档处理

第一版文档支持：

- `txt`
- `md`
- `pdf`
- `docx`

建议单独做：

- `parser_service.py`

按文件类型分别解析。

### 12.3 文档上下文策略

第一阶段不做 RAG，所以建议策略明确收敛为“会话附件上下文”：

- 文档解析出纯文本
- 后端按字符或 token 上限截取
- 作为当前轮或当前会话的补充上下文拼接给模型

这意味着：

- 文档不是长期检索索引
- 文档也不是永久工作记忆
- 文档是“当前任务上下文”的一部分

### 12.4 为什么要限制文档上下文长度

即便模型支持 128k / 256k 输入，也不能无限拼：

- 解析文本太长会拖慢响应
- 多轮会话叠加后很快膨胀
- 图片、文件、system prompt 和历史消息会互相抢预算
- 共享服务器资源有限

第一阶段建议做一个简单但可控的策略：

- 文档文本只取前 N 字符或前 N token
- 超过预算时优先裁剪更老的附件或低优先级内容
- 后续再做更细的上下文治理

## 13. 上下文治理设计

这一章是本项目后续最重要的技术点之一。

### 13.1 上下文治理目标

第一阶段上下文治理要解决 4 个问题：

1. 同一会话可连续追问
2. 上下文不会无限膨胀
3. 图片、文件、历史消息、系统提示有明确优先级
4. 为后续摘要、长期记忆、缓存命中优化留接口

### 13.2 上下文来源分层

第一阶段模型输入建议拆成 5 层：

1. `system_prompt`
2. 会话级近期消息
3. 当前用户输入
4. 当前轮图片附件
5. 当前轮文件附件解析文本

这 5 层必须保持明确顺序和稳定拼接模板。

### 13.3 短期上下文策略

第一阶段建议使用简单但可控的策略：

- 保留最近 `N` 轮消息原文
- 文档上下文限制最大长度
- 图片只带当前轮附件
- system prompt 永远保留

建议起步值：

- 最近 `10` 轮消息
- 每个文档截取前 `8000` 到 `12000` 字符
- 总上下文超预算时优先裁剪较旧消息或低优先级附件

### 13.4 上下文预算控制

后端应增加一个轻量“上下文预算器”，用于控制：

- 历史消息预算
- 附件预算
- 文档预算
- system prompt 预算

如果后续有 token 统计能力，优先按 token；否则第一版先按字符数近似。

当前实现已经从“固定阈值”升级到“动态预算框架”，核心规则如下：

- 用户设置里新增 `model_context_window`
- 用户设置里新增 `context_mode`
- 后端根据这两个字段动态推导：
  - 最大历史消息数
  - 最大总字符预算
  - 最大附件字符预算
  - 图片等效字符预算

### 13.5 前端上下文诊断面板

为了让上下文治理不再是“后端黑盒”，当前前端已经接入一层轻量诊断可视化：

- 后端通过响应头返回 `x-context-stats`
- 后端通过响应头返回 `x-context-notices`
- 前端将其解析为独立诊断卡片和提示列表

当前前端可直接展示的治理指标包括：

- 上下文模式
- 模型上下文窗口
- 本轮估算字符数
- 被裁剪的历史消息数
- 摘要字符数
- 是否触发摘要刷新
- 摘要刷新源消息数
- 摘要刷新源字符数
- 总字符预算上限
- 附件字符预算上限
- Prompt 模板版本
- Provider 模板
- 模型族
- Prompt 上下文层级
- 系统前缀层数
- Prompt 历史消息数
- 注入文件消息数
- 注入图片消息数

当前交互形式不是长期固定占位，而是：

- 输入区旁的轻量“上下文”按钮
- 点击后弹出诊断浮层查看详情

这样做的原因是：

- 日常对话时不干扰主聊天空间
- 需要调试和观察时仍然能快速展开

这层设计的作用是：

- 方便开发阶段验证预算是否合理
- 方便后续做参数调优和问题排查
- 为后续“更高质量摘要压缩”和“缓存命中优化”提供可观察性基础
  - 也能直接观测附件片段、摘要压缩和稳定前缀复用情况

当前这层诊断信息的持久化策略刻意保持克制：

- 当前不写入数据库
- 当前只在前端按“会话 id -> 最近一次诊断结果”做内存态缓存
- 这样切换会话再切回时，仍可继续查看最近一次上下文诊断
- 但刷新整个页面后，这类运行时诊断信息不会回放恢复

这样设计的原因是：

- 这批数据本质上是“单轮请求的运行时观测”，主要用于调试和治理观察
- 现阶段把它们持久化到数据库，收益主要只是“刷新后还能看”，性价比不高
- 如果现在就落库，会额外引入表结构设计、清理策略、历史兼容和回放接口复杂度
- 当前项目主线已经从 `P0.5` 转向 `P1`，不适合继续为了诊断信息持久化打断节奏

后续如果确实要做持久化，不建议只在 `conversations` 上挂一份“最后一次上下文信息”，而建议升级为：

- 按 assistant message 粒度保存诊断记录
- 一条回答对应一条上下文诊断
- 形成真正可回放、可追踪、可比对的“消息级上下文诊断链路”

也就是说，后续更合理的方向不是“为了显示按钮而落库”，而是“为了消息级调试追踪而落库”。

当前 `context_mode` 分为 3 档：

- `conservative`
  更保守，优先保证响应稳定和资源可控
- `balanced`
  默认模式，兼顾上下文长度和推理稳定性
- `long-context`
  更激进，优先保留更多历史和附件内容

当前预算器已经从“纯字符级近似预算”升级为“字符硬裁剪 + tokenizer 估算观测”的混合形态。

当前做法是：

- 仍保留字符级裁剪兜底，保证各 provider 下行为稳定
- 同时引入 `TokenizerEstimator`，基于 `tiktoken` 对 Prompt、摘要、附件和稳定前缀做 token 估算
- 当前诊断面板已经可以直接显示总 Token、附件 Token、摘要 Token、摘要压缩比、稳定前缀 Token 等指标

后续如果要继续优化，可以再演进为：

- provider 级更精细 token 预算器
- 更贴近具体模型的 tokenizer 映射
- 命中缓存时的差异化预算策略

### 13.5.1 缓存友好型 Prompt 结构

当前聊天链路已经新增 `ContextPromptBuilder`，把原本散落在 `chat.py` 里的 system prompt、长期记忆、会话摘要、历史消息、图片和文件附件拼装逻辑收敛到独立服务。

当前 Prompt 固定分层顺序为：

1. 稳定系统前缀：`AI Web Studio 上下文模板 v1`
2. 用户系统提示：用户在设置里配置的 `system_prompt`
3. 长期记忆：启用的 `user_memories`
4. 会话滚动摘要：`conversations.context_summary`
5. 最近原始消息窗口
6. 当前轮图片附件
7. 当前轮文档片段上下文

实现要点：

- 每一层使用稳定中文标题，例如“长期记忆”“会话滚动摘要”“当前轮附件片段”
- `ContextGovernanceService` 先保留前置 system 层，再裁剪历史消息，避免长会话时稳定前缀被末尾切片挤掉
- Prompt Builder 返回 provider 可直接消费的 `messages`
- Prompt Builder 同时返回诊断字段，用于前端上下文面板展示
- 当前已有 provider 模板标识：
  - `ollama_chat_v1`
  - `openai_chat_completions_v1`

### 13.5.2 附件索引化与按需展开

当前已经新增 `AttachmentContextService`，用于把当前轮文档附件从“全文直接注入”升级为“运行时轻量索引 + 相关片段注入”。

当前流程：

1. 上传阶段仍负责解析 `txt / md / pdf / docx` 得到 `parsed_text`
2. 发送消息时，后端读取当前用户消息绑定的文件附件
3. `AttachmentContextService` 将每个文件按约 `1200` 字符切块，并保留约 `160` 字符重叠
4. 根据当前用户问题抽取中英文关键词
5. 对每个片段做规则级相关性打分
6. 按 `budget.max_attachment_chars` 选择得分最高的片段
7. `ContextPromptBuilder` 只把选中的附件片段注入最后一条用户消息

当前上下文诊断新增：

- `attachment_files_seen`
- `attachment_chunks_total`
- `attachment_chunks_selected`
- `attachment_context_chars`
- `attachment_truncated_chunks`
- `attachment_truncated_chars`
- `attachment_context_tokens`
- `prompt_attachment_context_injected`

缓存友好型 Prompt 当前边界：

- 这是运行时轻量索引，不是持久化附件索引表
- 这是关键词级相关性打分，不是 embedding 向量检索
- 当前只处理当前轮上传附件，不会跨历史附件做召回
- 当前前端已经支持附件片段可视化预览和点击展开，但仍未做到持久化附件索引表

当前边界：

- 这一步是“缓存友好型结构治理”，不是 provider 真实缓存 API 调用
- 暂未做不同模型的深度差异化模板
- 已做 prompt prefix hash 与“稳定前缀是否复用上一轮”的启发式观测，但还不是 provider 真实缓存命中率
- 暂未做成本统计

### 13.5 上下文压缩策略

参考 Anthropic / Codex / Claude Code 的思路，后续建议引入两类压缩：

#### 局部压缩

- 对最老的消息做摘要
- 对工具结果做折叠
- 对超长附件只保留摘要和关键片段

#### 全局压缩

- 会话级摘要
- 长会话关键事实抽取
- 长期记忆写入

当前实现状态：

- 已支持“滚动摘要记忆层”
- 摘要会写入 `conversations.context_summary`
- 已新增 `context_summary_boundary_message_id`，用于标记当前摘要已经覆盖到哪一条历史消息
- 后续请求会把该摘要作为较早历史的压缩记忆注入，只回放边界之后的最近原始消息
- 已接入模型驱动摘要压缩：摘要刷新时优先使用当前会话 provider/model 做非流式摘要生成
- 已保留规则摘要兜底：如果模型摘要失败、超时或返回空内容，会自动回退到原来的结构化规则摘要，避免影响正常聊天

当前这一版摘要策略的特点是：

- 质量优先：优先由模型抽取用户目标、约束、重要事实、已完成决策和待办
- 稳定兜底：模型摘要不可用时仍能使用规则摘要继续运行
- 成本可控：不每轮重算，只在未压缩历史超过阈值时刷新

当前摘要刷新策略：

- 不再每轮都重算摘要
- 当“未被摘要覆盖的较早历史”超过一定消息数或字符量时，才触发滚动刷新
- 当前阈值是：
  - 至少 `6` 条消息
  - 或至少 `4000` 字符

当前摘要分层方式：

- `system_prompt`
- 会话级滚动摘要
- 最近原始消息窗口
- 当前轮用户输入 / 图片 / 文件

这意味着当前项目已经从“单层历史裁剪”升级成了“短期工作记忆 + 压缩记忆”的双层结构。

但缺点也很明确：

- 摘要会额外消耗一次 provider 调用
- 当前仍不是“完全按真实 provider tokenizer 严格裁剪”的终态，只是第一版混合预算框架
- 摘要质量依赖当前模型能力和 provider 稳定性

所以下一步应重点升级：

- 区分“短期对话摘要”和“长期事实记忆”
- 增加摘要刷新和失效策略
- 做摘要质量回归和更细粒度预算校准

### 13.6 长期记忆设计

长期记忆不是把全部历史挂到每次请求里，而是只保留高价值事实。

建议分成 4 类：

- Profile Memory
  用户稳定偏好、身份、语言习惯

- Task Memory
  当前长期任务目标、工作区背景

- Episode Memory
  某次会话里沉淀出的关键事实

- Artifact Memory
  文件、图片、摘要、结构化提取结果

当前实现状态：

- 已新增 `user_memories` 表，按用户隔离存储长期记忆
- 已支持 4 类手动长期记忆：
  - `profile`：用户偏好、交流习惯、技术偏好
  - `project`：长期项目背景、项目目标、技术栈
  - `fact`：用户明确保存的重要事实
  - `instruction`：希望系统长期遵守的规则
- 已新增 `memory_enabled` 和 `memory_max_chars` 用户设置
- 已新增记忆 CRUD 接口：
  - `GET /api/memories`
  - `POST /api/memories`
  - `PATCH /api/memories/{id}`
  - `DELETE /api/memories/{id}`
- 聊天链路会在 `system_prompt` 后、会话滚动摘要前注入启用的长期记忆
- 上下文诊断会返回：
  - `memory_enabled`
  - `memory_injected`
  - `memory_count`
  - `memory_chars`

当前长期记忆 MVP 的边界：

- 第一版只做手动保存、启停和删除，避免模型自动误记
- 不做跨用户共享记忆
- 不做自动跨会话知识融合
- 不做向量化长期记忆库

下一步升级方向：

- 已完成模型生成“建议记忆”的第一版：用户在长期记忆面板中从当前会话提取候选记忆，确认后再保存
- 增加记忆冲突检测和去重
- 给长期记忆增加来源会话和来源消息追踪
- 将 Artifact Memory 与附件索引化能力结合

模型建议记忆实现状态：

- 新增 `POST /api/memories/suggest`
- 输入当前会话 id 和候选数量上限
- 后端读取当前会话最近消息、已有长期记忆、当前用户 provider/model 配置
- 使用当前 provider/model 生成 JSON 候选记忆
- 后端解析并规范化候选，只返回给前端，不直接写入数据库
- 前端长期记忆面板展示候选卡片，用户可以保存或忽略
- 已新增规则级风险检测：
  - 同类型 + 内容高度相似：标记为 `duplicate`
  - 同类型 + 标题相近但内容差异较大：标记为 `conflict`
  - 无明显风险：标记为 `safe`
- 已新增来源追踪字段：
  - `source_conversation_id`
  - `source_message_ids`
  - `confidence`
- 已实现来源可视化：
  - 后端返回长期记忆时会根据 `source_conversation_id` 补充 `source_conversation_title`
  - 前端长期记忆卡片展示来源会话
  - 用户可从记忆卡片点击“打开来源”，跳转到对应历史会话

当前暂不做：

- 自动悄悄写入长期记忆
- 复杂语义去重和冲突检测
- 向量相似度检测
- 来源消息级高亮定位

### 13.7 缓存命中策略

为了后续兼容 OpenAI / Claude / Gemini / 百炼 / DeepSeek / vLLM 一类能力，第一阶段就要尽量保持：

- system prompt 稳定
- 附件注入模板稳定
- 历史消息顺序稳定
- 不要频繁改前缀结构

缓存命中本质上依赖 prompt 结构纪律。

当前第一版已经落地的缓存观测包括：

- 稳定前缀结构固定化：system prompt、长期记忆、滚动摘要的顺序固定
- 稳定前缀 hash：每轮对稳定前缀做 hash，便于判断模板或记忆层是否发生变化
- 稳定前缀 token 数估算：便于评估“缓存友好部分”大致占了多少上下文
- 与上一轮是否复用同一稳定前缀的启发式判断

当前仍未完成的部分：

- provider 真实缓存命中率
- prefix cache 成本收益统计
- 针对命中/未命中的差异化预算与路由策略

### 13.8 为什么不建议第一版就做“全历史拼接”

- 响应慢
- 显存和算力压力大
- 模型注意力分散

所以第一阶段必须做可控裁剪，而不是全量历史直塞。

### 22.2 近期技术优化建议

近期更适合做这些技术补齐：

1. 主题系统
   已完成第一版。前端通过 `data-theme` 和 CSS token 实现 light / dark 两套变量，后端用 `user_settings.theme_mode` 持久化用户选择。深色模式已补充控件 hover 和原生 `select option` 的深色样式，避免设置页下拉项/按钮 hover 出现白底浅字。聊天输入区额外使用 `chat-composer` 例外类，避免全局 dark 表单背景把透明输入框强制渲染成突兀矩形。

2. 会话导出
   已完成第一版。后端提供 conversation export endpoint，支持 Markdown / JSON；前端在左侧会话菜单触发文件下载。导出响应头使用 ASCII fallback + RFC 5987 `filename*`，避免中文会话标题进入 `Content-Disposition` 时触发服务端 header 编码错误。

   已完成第一版。新增 `prompt_templates` 表，并提供 `GET / POST / PATCH / DELETE /api/prompt-templates`；前端可管理模板。当前产品语义明确拆成两层：`prompt_templates.project_id` 只表示模板可见范围 / 分类，不代表自动生效；模板卡片里的“应用目标”才会真正写入全局 `user_settings.system_prompt` 或指定 `projects.system_prompt`，避免“模板归属”和“工作区生效提示词”混淆。

4. Project / 工作区

5. 会话分享
   已完成第一版。新增 `conversation_shares` 表，并提供 `GET / POST / PATCH / DELETE /api/conversations/{conversation_id}/share` 管理私有分享链接；`GET /api/shares/{token}` 提供无需登录的只读分享数据。前端新增 `/share/[token]` 分享页，支持只读查看消息和附件元数据。

6. 会话导出增强
   已完成第一版并完成一轮语义修补。`GET /api/conversations/{conversation_id}/export` 支持 `message_ids`、`include_attachments`、`include_attachment_files`、`include_context`、`as_zip` 参数；其中 `include_attachments` 只控制 Markdown / JSON / ZIP manifest 中是否包含附件元数据，`include_attachment_files` 只在 `as_zip=true` 时控制是否把真实附件文件写入 ZIP。前端会话菜单只保留一个“导出选项”入口，用户在弹窗内选择 Markdown / JSON / ZIP、导出范围、附件元数据、ZIP 附件文件和上下文摘要。ZIP 内附件优先保留原始文件名；如果同名冲突，则追加 `_2`、`_3` 等序号，避免之前用附件 ID 前缀导致导出文件名不可读。

   已完成第一版。`prompt_templates` 新增 `category` 和 `variables` 字段；前端支持模板搜索、分类展示、变量填充、快捷插入到 System Prompt，以及应用到全局或指定工作区。

8. 工作区增强

9. 消息级诊断持久化

10. 附件片段持久化
   当前附件切块是运行时轻量索引，后续建议新增 `attachment_chunks` 表，为跨历史附件召回和 RAG 打底。

### 22.3 中期 RAG 技术路线

如果进入知识库阶段，建议不要直接把当前“上传附件进入上下文”硬改成 RAG，而是新增一条知识库链路：

```text
Upload File
   |
   v
Parse Text
   |
   v
Chunk + Metadata
   |
   v
Embedding
   |
   v
Vector Store / pgvector
   |
   v
Retriever + Reranker
```

1. 先做 PostgreSQL 普通表持久化 chunk
2. 再引入 `pgvector` 或独立向量库
3. 最后补 contextual compression / rerank / citation

### 23.3 P3 知识索引流程

上传附件后的新流程：

```text
POST /api/uploads
  -> 保存附件文件
  -> 写 attachment 记录
  -> 文档解析
  -> 生成 attachment_chunks
  -> 写 knowledge_documents / 更新状态
  -> 返回附件与索引状态
```

为了不影响聊天体验，第一版可以同步执行；如果后续文件变大，再改成后台任务：

```text
upload request
  -> status = pending
  -> background index task
  -> status = indexed / failed
```

解析与切分策略：

- `txt / md`：按标题、空行和段落优先切分
- `pdf`：保留页码，按页内段落切分
- `docx`：按段落和标题切分
- chunk 目标大小：`800-1200` 中文字符或可配置 token
- chunk overlap：第一版可不做，后续再加 `100-200` 字符 overlap
- `content_hash`：用于去重

### 23.4 P3 知识召回流程

```text

  -> 排序
  -> 按上下文预算裁剪
```

### 24.4 流式协议设计

当前 `StreamingResponse` 是纯 `text/plain`，只能流 answer content。要支持 thinking / search status / source / final answer，建议升级为 SSE 或 NDJSON。

推荐第一版使用 NDJSON：

```json
{"type":"search_status","status":"searching","query":"..."}
{"type":"search_result","rank":1,"title":"...","url":"...","snippet":"..."}
{"type":"reasoning_delta","text":"..."}
{"type":"answer_delta","text":"..."}
{"type":"context_diagnostics","stats":{...},"details":{...}}
{"type":"done","assistant_message_id":"..."}
{"type":"error","message":"..."}
```

原因：

- 比纯文本流更容易扩展。
- Next.js fetch 读取 ReadableStream 仍然可用。
- 后续 Trace、工具调用、引用来源都可以复用。

兼容方案：

- 保留旧 `/chat/text-stream` 一段时间。
- 新增 `/chat/events-stream`。
- 前端新功能走 events-stream。

### 24.5 深度思考 Provider Adapter

新增内部结构：

```python
@dataclass
class ChatStreamEvent:
    type: Literal["reasoning_delta", "answer_delta", "done", "error"]
    text: str | None = None
    metadata: dict[str, Any] = field(default_factory=dict)
```

Provider service 不再只 yield string，而是 yield event：

```python
async def stream_chat_events(...) -> AsyncGenerator[ChatStreamEvent, None]:
    ...
```

Ollama 适配：

```python
payload = {
    "model": model_name,
    "messages": messages,
    "stream": True,
    "think": thinking_enabled,
    "keep_alive": settings.ollama_keep_alive,
}
```

解析：

```python
thinking = data.get("message", {}).get("thinking")
content = data.get("message", {}).get("content")
```

OpenAI-compatible / SiliconFlow / Qwen 适配：

```python
extra_body = {}
if profile.thinking_param_style == "qwen_enable_thinking":
    extra_body["enable_thinking"] = thinking_enabled
    if thinking_enabled and thinking_budget:
        extra_body["thinking_budget"] = thinking_budget
```

解析时兼容：

```python
reasoning = getattr(delta, "reasoning_content", None)
content = getattr(delta, "content", None)
```

同时保留 dict fallback：

```python
if isinstance(delta, dict):
    reasoning = delta.get("reasoning_content") or delta.get("thinking")
```

注意：

- 不是所有 OpenAI-compatible provider 都接受 `enable_thinking`，必须由 profile 决定是否发送。
- 当前 SiliconFlow/Qwen 场景可以先支持 `enable_thinking`。
- 如果启用 thinking 后 provider 报 400，可记录 capability failure，并提示用户关闭。

## 25. 通用 External Context / Tool Layer 技术设计

第 24 节里的 Web Search 设计需要进一步抽象。否则后续接天气、高德地图、MCP、知识库召回时，聊天接口会被各种 provider-specific 逻辑污染。

## 26. Tool Router 与意图识别技术设计

External Context / Tool Layer 还需要一个关键组件：`Tool Router`。它负责判断当前问题是否需要工具，以及选择哪些工具。

核心原则：

> `联网搜索按钮` 只是 permission gate，不是 execution plan。真正执行哪些工具必须由 Tool Router 决定。

### 26.1 参考实现

Ragent 的意图识别链路：

```text
IntentTree
  -> leaf IntentNode
  -> DefaultIntentClassifier
  -> NodeScore
  -> NodeScoreFilters.kb / mcp
  -> RetrievalEngine / MCP Context
  -> Prompt Builder
```

Ragent 的关键设计：

- 意图节点有 `kind`：`KB / SYSTEM / MCP`。
- MCP 节点挂 `mcpToolId`。
- 每个叶子节点有 description 和 examples。
- LLM 对所有叶子节点输出 score。
- 后续用分数阈值过滤。
- MCP 参数提取独立做，不直接相信分类结果。

我们可以复用这个思想，但把 `IntentKind` 扩展到更通用的工具类别。

### 26.2 数据结构

新增：

```python

class ToolRouteCandidate:
    tool_key: str
    category: str
    confidence: float
    reason: str
    arguments: dict[str, Any] = field(default_factory=dict)
```


### 26.5 LLM Tool Router

当规则路由不确定时，调用 LLM Router。

输入 Prompt 应包含：

- 用户问题。
- 可用工具列表。
- 每个工具的 category、description、input_schema、examples。
- 当前是否允许外部工具。
- 输出 JSON schema。

输出 schema：

```json
{
  "should_use_tools": true,
  "calls": [
    {
      "tool_key": "web.tavily.search",
      "confidence": 0.82,
      "reason": "用户询问最新版本变化",
      "arguments": {
        "query": "LangChain latest version changes"
      }
    }
  ],
  "fallback_tool_key": "web.tavily.search",
  "reason": "需要实时网页信息"
}
```

后端校验：

```python
class ToolPlanValidator:
    def validate(self, plan: ToolPlan, context: ToolRouterContext) -> ToolPlan:
        ...
```

校验规则：

- tool_key 必须存在。
- tool 必须 enabled。
- 外部工具必须在 `external_context_allowed=true` 时才能执行。
- arguments 必须符合 input_schema。
- 只读工具才能无确认执行。
- 工具数量不能超过 max_tool_calls。
- 低于 confidence 阈值的工具剔除。

### 26.6 阈值策略

建议配置：

```text
TOOL_CONFIDENCE_THRESHOLDS
  weather_lookup: 0.75
  map_geocode: 0.75
  map_poi_search: 0.75
  map_route: 0.75
  workspace_knowledge_search: 0.65
  current_attachment_search: 0.65
  web_search: 0.65
  mcp_tool_call: 0.8
```

默认：

- 单工具：取最高置信度工具。
- 多工具：只有当多个工具都超过阈值，并且问题包含多个明确子任务时，才取前 2。
- 低置信度：如果用户允许外部信息，fallback 到 web_search；否则 no_tool。

### 26.7 执行策略

工具调用器：

```python
class ToolExecutionService:
    async def execute_plan(self, plan: ToolPlan, context: ToolRouterContext) -> ExternalContextResult:
        ...
```

执行规则：

- 默认串行执行，避免过早并发导致限流。
- 明确多意图时可并行执行最多 2 个只读工具。
- 每个工具有 timeout。
- 总工具阶段有 timeout。
- 每个工具失败不应导致整个聊天失败。
- 失败结果进入 Trace 和前端事件。

事件：

```json
{"type":"tool_plan","plan":{...}}
{"type":"tool_call_start","tool_key":"weather.current"}
{"type":"tool_call_end","tool_key":"weather.current","status":"success","latency_ms":320}
{"type":"tool_source","source":{...}}
```

新增工具路由记录：

## 29. 工具层可观测、可配置与插件化技术设计

本节基于当前代码实现提出下一阶段技术路线。当前代码中的关键入口是：

- `backend/app/services/external_context_service.py`

- `frontend/src/components/chat-app.tsx`

当前 `ExternalContextService` 已经能调用 Tavily、高德天气和高德地图，但还不是一个真正可扩展工具层。

### 29.1 目标架构

目标是把外部工具能力拆成稳定分层：

```text

      -> ToolRouter
```

聊天主流程只依赖 facade：

这样聊天路由不需要知道 Tavily、高德、MCP、知识库、HTTP 工具的细节。

### 29.6 凭证解析策略

工具调用时不直接读取 `settings.tavily_api_key` 或 `settings.amap_api_key`，而是通过 `ToolCredentialResolver`：

```text
conversation workspace setting credential
-> user default credential
-> backend .env fallback
-> unavailable
```

安全策略：

- API Key 使用后端 secret 加密存储。
- 接口返回只显示掩码，例如 `tvly-dev-****-xxxx`。
- Trace、日志、前端事件不输出完整凭证。
- 测试连接接口只返回成功/失败和 provider 诊断，不返回 key。

第一版加密可以使用 Fernet 或等价对称加密：

```text
TOOL_CREDENTIAL_SECRET=...
```

如果 secret 未配置，生产模式禁止保存凭证；开发模式可以提示仅使用 `.env fallback`。

### 29.10 工具导入策略

第二阶段：本地 manifest。

第三阶段：自定义 HTTP 工具。

第五阶段：插件市场。

### 29.11 和上下文治理的关系

工具结果本质是外部上下文。它必须纳入上下文治理预算：

- 每个工具有最大来源数量。
- 每个来源有最大字符数。
- 每轮外部工具总字符数受 `max_external_context_chars` 控制。
- Tool Trace 全量保存，但注入 Prompt 的内容需要裁剪。
- 来源卡片展示不等于全部进入 Prompt。

后续可以在上下文面板中增加：

- 工具来源总数。
- 实际注入来源数。
- 外部上下文 token。
- 工具总耗时。
- 工具失败数。

当前接口设计重点：

- `GET /api/tools/settings` 一次返回内置工具目录、用户凭证摘要、当前工作区工具开关。
- `PATCH /api/tools/credentials/{provider_key}` 只接受 provider 级配置，例如 `tavily`、`amap`。
- `POST /api/tools/credentials/{provider_key}/test` 使用当前保存的凭证测试连通性。
- `PATCH /api/tools/workspaces/{project_id}/{tool_key}` 用于工作区级禁用具体工具，例如只禁用 `amap.map.basic` 但保留 `amap.weather.current`。

凭证解析优先级：

```text
工作区禁用具体 tool_key
-> 直接跳过该工具

用户显式禁用 provider
-> 禁用该 provider 下所有工具

用户 provider 已启用且保存了 API Key
-> 使用用户 API Key

用户 provider 已启用但未保存 API Key
-> 使用后端 .env fallback

.env 也没有配置
-> 该 provider 视为 missing，工具调用跳过并写入 tool_call_error/skipped
```

代码落点：

- `backend/app/models/tool_config.py`：用户凭证和工作区工具配置模型。
- `backend/app/repositories/tool_config_repo.py`：工具配置读写仓储。
- `backend/app/services/tools/credentials.py`：`ToolCredentialResolver`，统一处理 user/env/missing/disabled。
- `backend/app/api/routes/tools.py`：工具设置、凭证保存、连通性测试、工作区工具开关。
- `backend/app/services/tools/registry.py`：manifest 驱动的内置工具目录加载器，当前从 `backend/app/tool_manifests/default_tools.json` 读取 Tavily 搜索、高德天气、高德地图。
- `backend/app/services/tools/executor.py`：执行前检查工作区开关和 provider 凭证，事件中只记录 `credential_source`，不记录完整 API Key。
- `backend/app/services/secret_service.py`：统一负责 provider / tool API Key 的加解密和掩码输出；兼容历史明文行，便于渐进迁移。

## 30. 2026-05-29 高德天气工具修复

本次修复了高德天气工具在街道/片区级地点上的错误处理问题。

问题表现：

- 用户开启联网搜索后询问“深圳松岗天气怎么样”。
- 工具面板显示：`高德天气 调用失败：高德天气查询失败：OK`。
- 这不是高德接口鉴权失败，也不是网络失败，而是接口返回 `status=1, info=OK, lives=[]`。

根因：

- 高德天气接口的 `city` 参数更适合传城市、区县或 adcode。
- “深圳松岗”是街道/片区级地点，直接作为天气接口 `city` 参数时，高德可能返回成功状态但没有天气结果。
- 旧逻辑只要 `lives` 为空就抛错，并把 `info=OK` 拼进错误信息，导致用户看到“失败：OK”这种矛盾提示。

修复设计：

- `AmapToolProvider.query_weather()` 先按用户原始地点直查。
- 如果返回成功但 `lives` 为空，则调用高德地理编码解析原始地点。
- 从地理编码结果中按优先级提取：
  - `adcode`
  - `district`
  - `city`
- 再用这些候选值重试天气查询。
- 返回来源 metadata 中补充：
  - `requested_location`
  - `resolved_city`

这样可以保留用户问的原始地点，同时让天气查询落到高德支持的行政区/adcode 粒度。

新增测试：

- `backend/tests/test_amap_provider.py`
- 覆盖“深圳松岗天气怎么样”先直查无结果，再 fallback 到 `440306` 并成功返回宝安区天气的路径。

## 31. 2026-05-29 工具路由 v2 与轻量 Query Rewrite

本次针对“他们离汕头市潮阳区西凤村多远”这类问题做了前两步优化。

### 31.1 第一步：规则路由增强

问题：

- 旧版 `RuleBasedToolRouter` 只识别 `距离`，没有识别 `多远 / 相距 / 几公里 / 开车多久` 等地图距离意图。
- 因此这类问题会落到 Tavily 网页搜索，而不是高德地图。

修复：

- `RuleBasedToolRouter.MAP_PATTERN` 增加：
  - `多远`
  - `相距`
  - `离.+远`
  - `几公里`
  - `多少公里`
  - `开车多久`
  - `步行多久`
  - `要多久`
  - `多久到`
- `AmapToolProvider._extract_route_query()` 增加距离类句式：
  - `A 离 B 多远`
  - `A 距离 B 多少公里`
  - `A 和 B 相距多远`
  - `A 到 B 开车多久`
  - `A 到 B 步行多久`

这样不带指代的 query，例如：

```text
深圳松岗离汕头市潮阳区西凤村多远
深圳松岗和汕头市潮阳区西凤村相距多少公里
深圳松岗到汕头市潮阳区西凤村开车多久
```

会直接路由到 `amap.map.basic`。

### 31.2 第二步：轻量 QueryRewriteService

问题：

- 用户说“他们 / 它们 / 这些 / 刚才 / 上面”时，单看当前 query 无法知道指代对象。
- 完整 LLM Router 或 Agent 还没必要马上做，因此先做窄范围规则改写。

新增：

- `backend/app/services/tools/query_rewriter.py`
- `QueryRewriteService`

触发条件：

- 当前 query 同时满足：
  - 有指代词：`他们 / 它们 / 这些 / 那些 / 这几个 / 上面 / 前面 / 刚才`
  - 有地图距离意图：`多远 / 相距 / 距离 / 几公里 / 多少公里 / 开车多久 / 步行多久`

处理方式：

- 从当前 query 提取目标地点。
- 从最近 8 条历史消息中抽取候选地点。
- 改写成独立地图 query。

示例：

```text
原始问题：
他们离汕头市潮阳区西凤村多远

最近历史中抽取到：
深圳松岗、广州南站

改写后：
深圳松岗、广州南站分别到汕头市潮阳区西凤村有多远
```

### 32.3 MCP Connector 实现细节

当前优先支持 HTTP / Streamable HTTP MCP，不支持本地 stdio MCP。

  - `https://mcp.amap.com/mcp?key={api_key}`

MCP client 的一个重要实现点：

### 33.7 Planner Fast Path 与超时保护

补充修复：

- 对高置信高德工具问题启用 deterministic fast path。
- `amap.weather.current / amap.route.plan / amap.distance.measure` 这类明确意图不再先等待 LLM 规划。
- LLM planner 仅用于开放网页问题或低置信复杂问题。
- LLM planner 调用包裹 `asyncio.wait_for`，当前超时为 6 秒。
- 超时、JSON 非法、schema 不通过时，全部 fallback 到 `DeterministicToolPlanner`。

原因：

- 工具规划是辅助步骤，不能阻塞主聊天链路。
- 对“深圳松岗到汕头市潮阳区西凤村开车多久？”这类明确路线问题，确定性规划已经足够准确，直接执行高德 MCP 路线工具更快、更稳定。

### 33.8 多起点距离比较修复

问题：

- “深圳松岗和广州南站分别离汕头市潮阳区西凤村多远，哪个近一点？”这类问题，本质是多起点到同一终点的距离测量。
- 高德 MCP `maps_distance` 支持多个起点坐标用 `|` 拼接，因此高德能力本身可以完成。
- 之前错误点在工具规划层：
  - 起点被抽成 `深圳松岗和广州南站分别` 一个合并字符串。
  - 后续 geocode 会偏向其中一个地点，导致距离结果只有一条或起点错误。

修复：

- `DeterministicToolPlanner` 增加多起点拆分：
  - 支持 `和 / 与 / 跟 / 及 / 以及 / 、 / , / ， / |`。
  - 清理 `分别 / 各自 / 两者 / 二者` 等比较提示词。
- `amap.distance.measure` workflow 保持 MCP 多步调用：
  - 多次 `maps_geo` 解析起点。
  - 一次 `maps_geo` 解析终点。
  - 一次 `maps_distance` 计算多个起点到同一终点的驾车距离。
- 距离来源卡片增强为：
  - `起点 -> 终点：距离 / 预计耗时`。
  - 多个起点时补充“哪个更近”的结论。

验证：

- `深圳松岗 -> 汕头市潮阳区西凤村`：约 327.0 公里，约 3 小时 50 分钟。
- `广州南站 -> 汕头市潮阳区西凤村`：约 403.1 公里，约 4 小时 8 分钟。
- 结论：深圳松岗更近。

### 35.2 LLMToolPlanner 主路径策略

旧策略：

```text
天气 / 地图 / 路线高置信问题
  -> deterministic fast path

  -> LLM planner
```

新策略：

```text

  -> LLMToolPlanner

      -> 成功则执行 LLM plan
```

关键变化：

- LLM planner 最多返回 4 个 tool calls。
- 每个 tool call 必须通过 `ToolSchemaValidator`。

这样能缓解之前的问题：

- 用户问法稍微变化时，不再完全依赖正则抽取起点/终点/城市。
- LLM 可以根据工具 schema 自己生成 `origin`、`destination`、`city`、`origins` 等参数。
- 多工具问题可以一次规划多个工具，而不是只能走单个规则分支。

## 37. 2026-06-06 Tool DAG、并行执行与有限 Replan Loop

本轮继续把工具编排从“扁平 calls 顺序执行”升级为“LLM 输出依赖图，后端按依赖图调度”。

### 37.1 Planner 输出结构扩展

`PlannedToolCall` 增加：

- `depends_on: list[str]`
- `can_parallel: bool`

`ToolPlan` 增加：

- `need_more_rounds: bool`

LLM planner 输出格式调整为：

```json
{
  "should_use_tools": true,
  "need_more_rounds": false,
  "calls": [
    {
      "id": "weather_shenzhen",
      "tool_key": "amap.maps.weather",
      "arguments": {"city": "深圳"},
      "depends_on": [],
      "can_parallel": true,
      "reason": "查询深圳天气"
    }
  ]
}
```

后端负责校验：

- `tool_key` 必须存在于候选工具集合。
- `arguments` 必须符合 MCP schema。
- `depends_on` 只能引用本 plan 中存在的 call id。
- 自依赖会被过滤。

### 37.2 ToolWorkflowService DAG 调度

旧逻辑：

```text
for call in calls:
  await execute(call)
```

新逻辑：

```text
pending = 所有 calls
completed = {}

while pending:
  ready = depends_on 都已完成的 calls
  如果 ready 中存在 can_parallel=false 的调用，则一次只执行其中一个
  否则并行执行 ready calls
  completed += 执行结果
```

新增 trace：

- `tool_workflow_batch`
  - `mode=parallel` 表示本批次并行执行。
  - `mode=single` 表示单步执行。
- `tool_workflow_step`
  - 展示每个 call 的 `depends_on`、`can_parallel` 和 reason。

效果：

- “深圳广州天气怎么样”可以规划两个无依赖 weather call，并行执行。
- “先查路线，再根据路线查服务区”可以通过 `depends_on=["route"]` 表达顺序依赖。

### 37.3 有限 Replan Loop

`ExternalContextService` 现在支持最多 2 轮工具规划：

```text
round 1:
  planner(query, observations=[])
  workflow 执行工具图
  把工具结果压缩成 observations

round 2:
  planner(query, observations=[round1 results])
  如果仍需要工具，继续执行
```

新增 trace：

- `tool_agent_round_start`
- `tool_agent_round_end`

这不是无限 Agent loop，而是受控循环：

- 当前最大轮数：2。
- 每轮最大工具数仍由 `ToolWorkflowService.max_tool_calls` 限制。
- 重复调用会被 workflow 跳过。
- 高风险工具仍会被阻断。

### 37.4 当前边界

### 38.1 总体架构

知识库链路独立于聊天链路实现，但最终检索结果进入现有上下文治理。

```text
Browser
  |
  | /knowledge
  v
Knowledge API
  |
  | create KB / upload docs / jobs / retrieval test
  v
Knowledge Services
  |
  | parse -> chunk -> embed -> index
  v
PostgreSQL metadata + FAISS index files


Chat API
  |
  | selected knowledge base
  v
KnowledgeRetriever
  |
  | KnowledgeSource[]
  v
ContextAssemblyService
  |
  | budgeted prompt
  v
LLM Provider
```

关键原则：

- 知识库不是聊天附件的增强版，而是独立数据域。
- 聊天 route 不直接调用 MinerU、FAISS、SiliconFlow embedding 或 rerank。
- 知识库检索结果和工具来源一样，都作为外部上下文通道进入 prompt builder。
- 所有用户 token/API key 均按用户级加密凭据处理，不写入代码、文档、Git 或命令历史。

Embedding：

- 默认 provider：`siliconflow`。
- 默认模型：`BAAI/bge-m3`。
- 默认维度：`1024`。

Rerank：

- 默认 provider：`siliconflow`。
- 默认模型：`BAAI/bge-reranker-v2-m3`。
- 默认开启。

向量库：

### 38.6.3 RAG-4 当前检索与 Rerank 流程

2026-06-10 已完成 `RAG-4：检索测试与 Rerank` 的最小可用闭环。

当前检索模式不是 Dify 的完整多路检索，而是：

```text
用户输入 query
-> KnowledgeEmbeddingService.embed_texts([query])
-> KnowledgeFaissStore.search(top_k)
-> KnowledgeChunkRepository 根据 vector_id 映射 chunk
-> 如果 knowledge_base.rerank_enabled:
     KnowledgeRerankService.rerank(query, candidate chunk contents, rerank_top_n)
     -> 按 rerank_score 重排
   否则:
     保持 vector score 排序
-> score_threshold 过滤
-> 返回 retrieval-test 结果
```

Rerank provider：

- `siliconflow / openai-compatible`
  - 使用 `{knowledge_rerank_base_url or knowledge_embedding_base_url}/rerank`
  - API Key 从 `knowledge_rerank_api_key` 读取。
  - 请求体包含 `model / query / documents / top_n / return_documents`。
- `ollama`
  - 当前不支持 rerank。
  - 如果误配置为 Ollama，检索测试会捕获异常并回退到向量召回。

Rerank 失败回退：

```text
rerank 调用异常
-> 不抛出给前端导致整个检索失败
-> rank_source = vector_fallback
-> metadata.rerank_fallback = true
-> metadata.rerank_error = 原始错误信息
-> 继续返回向量召回结果
```

这样做的原因：

- 检索测试页的目标是帮助定位质量问题，不应该因为 rerank key 未配或 provider 临时失败而完全不可用。
- 第一阶段需要让用户清楚知道“当前看到的是 rerank 结果还是向量回退结果”。
- 后续接聊天时也应保留类似回退策略，避免 RAG 因重排服务短暂失败导致聊天整体失败。

检索结果字段：

```text
score         最终用于排序和展示的分数；如果 rerank_score 存在则等于 rerank_score，否则等于 vector_score
vector_score  FAISS 向量召回分数，normalize + inner product，近似 cosine similarity
rerank_score  rerank 模型返回的 relevance_score；未启用或失败时为 null
rank_source   vector / rerank / vector_fallback
```

前端检索测试面板展示：

- 知识库当前是否启用 Rerank。
- Rerank 模型名。
- 每个 chunk 的最终分数、向量分数、Rerank 分数。
- 排序来源 badge：向量召回、Rerank、向量回退。
- Rerank 失败原因。

当前边界：

- 暂未实现全文检索 / BM25。
- 暂未实现 Hybrid Search / RRF。
- 暂未实现多 query rewrite。
- 暂未实现 parent-child 检索。
- 暂未实现 retrieval logs 持久化。
- 暂未接入聊天上下文。

后续技术路线：

1. RAG-5 先把单知识库检索结果接入聊天上下文治理。
2. 进入聊天前新增 `KnowledgeContextService`，把 `RetrievalResult` 转成统一外部上下文片段和来源对象。
3. RAG-6 再做 Hybrid/BM25/RRF，避免在聊天接入前过早扩大检索复杂度。

### 38.6.4 PDF 与图片处理边界

当前本地 PDF 解析：

- 使用 `pypdf.PdfReader.extract_text()` 提取文本。
- 适合文本型 PDF。
- 对扫描版 PDF、图片中的文字、图表截图不做 OCR。

- RAG-3 不对图片做语义索引。
- 不把 PDF 图片直接送 embedding。
- 只保留 `parsed_assets_json` 扩展位。
- 后续可参考 Dify Knowledge Pipeline / multimodal knowledge base 的路线：
  - MinerU / OCR 提取图片文字。
  - 对图表做 caption。
  - 图片文件保存为 document assets。
  - 文本 chunk 与 image caption 一起索引。

- 先把文本 RAG 主链路跑通。

#### 38.9.6 RAG-5 Header 编码、超时与降级策略

上下文诊断通过 HTTP header 传给前端时，不能直接写入中文或任意 Unicode 字符。Starlette 会按 `latin-1` 编码响应头，中文知识库名会导致 `UnicodeEncodeError`。

当前策略：

- `x-context-stats` 使用 ASCII-safe 的 `json64:` base64 JSON 格式。
- 前端 `parseContextStatsHeader()` 优先解析 `json64:`。
- 前端保留旧 `a=b;c=d` 格式解析，用于兼容历史响应。
- `x-context-notices` 和 `x-context-details` 继续使用 base64 JSON。

聊天内知识库检索不能复用 Ollama 长生成超时，否则 embedding/rerank provider 卡住时会让前端一直停留在首 token 前。

知识库检索策略：

- `KNOWLEDGE_MODEL_REQUEST_TIMEOUT_SECONDS`：单次知识库模型请求超时，默认 60 秒。
- `KNOWLEDGE_CONTEXT_TIMEOUT_SECONDS`：聊天内整段知识库检索总超时，默认 25 秒。
- `KnowledgeContextService` 使用 `asyncio.wait_for()` 包住整段检索。
- 超时、知识库不存在、未索引、检索异常时：
  - 不抛出到聊天主链路。
  - 返回上下文 notice。
  - 不注入知识库片段。
  - 普通模型回答继续执行。
- 上下文诊断记录：
  - `knowledge_retrieval_error`
  - `knowledge_retrieval_latency_ms`

后续如果要做“严格知识库回答模式”，可以在 `strict_knowledge_answer=true` 时把检索失败升级为用户可见阻断错误；默认模式仍应保持降级不中断聊天。

- 知识库选择器。

### 38.13 知识库模型服务配置拆分

2026-06-09 补充设置体系调整：聊天问答模型服务和知识库模型服务必须分开管理。

原因：

- 聊天模型用于回答生成，关心 `temperature / top_p / max_tokens / system_prompt / context_window`。
- 知识库模型用于入库和检索，关心 `parser / embedding provider / embedding model / embedding dimensions / rerank provider / rerank model`。

- 两类模型服务的 provider 可能不同，例如：
  - 聊天用本地 Ollama。
  - Embedding 用 SiliconFlow 的 `BAAI/bge-m3`。
  - Rerank 用 SiliconFlow 的 `BAAI/bge-reranker-v2-m3`。
- 如果继续共用“模型服务”配置，后续 RAG-3 会被迫把 embedding/rerank 逻辑写死或污染聊天配置。

### 41.7 2026-06-15 RAG-6.3 / RAG-6.4 实现落地

本轮在 `KnowledgeRetrievalPipeline` 内完成 BM25 和 Hybrid Search 第一版，不再继续把 query-time 逻辑塞回 `KnowledgeIndexService`。

当前检索模式：

```text
vector
  query -> embedding -> FAISS search -> metadata filter -> optional rerank -> threshold

lexical
  query -> tokenize -> BM25 over chunks -> metadata filter -> optional rerank -> threshold

hybrid
  query -> vector candidates
       -> lexical candidates
       -> RRF fusion
       -> optional rerank
       -> threshold
```

BM25 第一版：

- 数据来源：直接读取当前知识库的 `knowledge_chunks`。
- 分词策略：
  - 英文 / 数字 / 下划线 / 短横线 token。
  - 中文单字。
  - 中文 bigram。
- 排序策略：标准 BM25 近似实现，使用 `k1=1.5`、`b=0.75`。
- 返回 metadata：
  - `lexical_score`
  - `normalized_score`
  - `retrieval_mode=lexical`

Hybrid 第一版：

- 向量召回和 BM25 召回分别取候选。
- 使用 RRF 融合排名，而不是直接融合原始分数。
- RRF 默认常数 `k=60`。
- 返回 metadata：
  - `retrieval_mode=hybrid`
  - `rrf_score`
  - `normalized_score`
  - `vector_rank`
  - `lexical_rank`
  - `vector_score`
  - `lexical_score`
  - `hybrid_fallback`
  - `vector_error`

Rerank 关系：

- Rerank 仍是最终精排层。
- Rerank 后保留召回阶段 metadata，不再把 Hybrid 的 RRF score 覆盖成 `vector_score`。
- `pre_rerank_score` 用于记录进入 rerank 前的最终召回分数。

前端接入：

- 新建知识库默认 `retrieval_mode=hybrid`。

  - 混合检索（向量 + BM25 + RRF）。

- 检索测试结果展示：
  - 最终分数。
  - 向量分数。
  - BM25 分数。
  - RRF 分数。
  - Rerank 分数。

当前边界：

- BM25 是 query-time in-memory 实现，不适合百万级 chunk。

### 41.11 2026-06-22 RAG-6.6 BM25 持久化倒排索引

本轮把 RAG-6.3 / RAG-6.4 中的 query-time in-memory BM25 升级为持久化 lexical index。

#### 目标

旧 BM25 流程：

```text
query
-> load all chunks from database
-> tokenize every chunk at query time
-> compute BM25
-> filter / rerank
```

这个实现简单，但每次查询都要扫描全库 chunks。知识库文档变多后，Hybrid Search 的 lexical 分支会成为明显瓶颈。

新流程：

```text
index_document
-> chunking
-> embed all chunks
-> rebuild FAISS index
-> rebuild BM25 lexical_index.json

retrieve lexical / hybrid
-> load lexical_index.json
-> tokenize query
-> score only postings touched by query terms
-> map vector_id back to KnowledgeChunk
-> metadata filter / RRF / rerank
```

#### 后端结构

新增 `KnowledgeLexicalStore`，与 `KnowledgeFaissStore` 并列：

```text
KnowledgeFaissStore
  index.faiss

KnowledgeLexicalStore
  lexical_index.json
```

文件路径：

```text
{settings.knowledge_index_dir}/{knowledge_base_id}/lexical_index.json
```

索引文件结构：

```json
{
  "version": 1,
  "knowledge_base_id": "...",
  "doc_count": 123,
  "avgdl": 456.7,
  "document_lengths": {
    "1": 120
  },
  "document_frequency": {
    "rag": 12
  },
  "chunk_refs": {
    "1": {
      "chunk_id": "...",
      "document_id": "...",
      "chunk_index": 0
    }
  },
  "postings": {
    "rag": [[1, 3], [2, 1]]
  }
}
```

其中：

- `postings[term]` 保存 `[vector_id, term_frequency]`。
- `document_frequency` 用于计算 BM25 IDF。
- `document_lengths` 和 `avgdl` 用于 BM25 长度归一。
- `chunk_refs` 主要用于调试和未来增量索引，不作为最终权限判断依据。

#### 检索流程

`KnowledgeRetrievalPipeline._retrieve_lexical_results()` 现在只负责编排：

```text
query
-> KnowledgeLexicalStore.search()
-> hits: vector_id + raw BM25 score
-> load chunks from DB
-> vector_id -> KnowledgeChunk
-> apply metadata filters
-> normalize lexical score
-> optional rerank
```

如果 `lexical_index.json` 缺失、损坏或版本不兼容：

```text
catch RuntimeError
-> load chunks from DB
-> KnowledgeLexicalStore.rebuild()
-> search again
```

这保证了：

- 旧知识库不会因为缺少 BM25 文件直接不可用。
- 手动删除索引文件后可自动恢复。
- 后续索引版本升级时，可以通过 version 触发重建。

#### Hybrid / RRF 保留来源

Hybrid 融合后 metadata 会保留：

```json
{
  "retrieval_mode": "hybrid",
  "rrf_score": 0.032,
  "vector_rank": 1,
  "lexical_rank": 2,
  "vector_score": 0.71,
  "lexical_score": 3.92,
  "lexical_index": "persistent"
}
```

这样前端检索测试、日志和后续来源卡片可以区分 lexical 分支是否来自持久化索引。

#### 索引生命周期

当前生命周期：

```text
index document
-> replace document chunks
-> list all chunks in KB
-> rebuild FAISS for all chunks
-> rebuild BM25 for all chunks

delete knowledge base
-> delete DB records/logs
-> remove {knowledge_index_dir}/{knowledge_base_id}
```

设计取舍：

- 第一版继续沿用“索引文档时全库重建”的方式，和当前 FAISS 流程一致。
- 删除知识库时清理整个索引目录，避免 FAISS / BM25 孤儿文件。
- 删除单文档后暂不立即重建 BM25；检索时会根据 DB chunks 映射过滤旧 vector_id。后续如果文档删除频率高，应在删除文档后触发全库索引重建任务。

#### 当前边界和后续升级

当前 JSON 倒排索引适合：

- 个人知识库。
- 小到中等规模文档。
- 便于调试和快速验证。

## 2026-07-15：BM25 发布失败补偿

当前向量已由 PostgreSQL/pgvector 持久化，BM25 仍使用 `lexical_index.json`。索引顺序为：

```text
生成/复用 Embedding
-> replace_document_chunks() commit 新 Chunk + Vector
-> rebuild() 原子替换 BM25 JSON
```

为覆盖 BM25 重建的普通异常，索引前新增两份短期快照：

```text
previous_document_chunks：目标文档旧 Chunk 的脱离 ORM 副本
lexical_snapshot：旧 BM25 文件 bytes，无旧索引时为 None
```

BM25 发布抛错时：

```text
删除本轮新 Chunk，恢复 previous_document_chunks
-> 用临时文件 + fsync + os.replace 恢复旧 BM25 bytes
-> 继续抛出原 BM25 异常
-> 上层将 Document/Job 标记 failed
```

故障测试覆盖「新 BM25 已经替换后再失败」，断言旧 Chunk 的 ID、vector_id、内容、Embedding 和模型签名全部恢复，且旧 BM25 bytes 一致。

边界：这是 normal-exception compensation，不是掉电安全的原子发布。进程在两个恢复动作之间终止，或恢复本身失败，仍需 inactive generation + manifest + CAS active pointer 才能彻底收口。

## 2026-07-15：MCP HTTP 错误脱敏

内置 MCP endpoint 可以使用 `{api_key}` 查询参数。`httpx` 的 HTTP status 异常包含完整 URL，原实现将 `str(exc)` 交给 Executor/Trace，存在密钥写入数据库或前端 Trace 的风险。

## 2026-07-15：动态 MCP 安全边界与市场演进设计

动态 MCP Server 不再直接信任远端 `readOnlyHint`。首次同步生成的 Tool 默认处于：

```text
risk_reviewed=false
read_only=false
risk_level=high
is_enabled=false
```

用户显式审核只读后才允许启用；远端 inputSchema 或 annotations 发生变化时自动撤销旧审核并重新禁用。Planner arguments 在 strict Schema 下拒绝未声明字段，且只为显式声明 `query` 的 Tool 自动补 query。

MCP Client 新增协议与资源边界：

- `result.isError=true` 作为 Tool 执行失败处理；远端 JSON-RPC error message 不直接写入 Trace，只保留协议错误码。
- JSON/SSE 响应默认限制为 1 MiB。
- HTTP 错误不携带 endpoint/API Key 进入 Trace。
- 动态 URL 只允许 HTTP/HTTPS，默认拒绝回环、私网、保留地址和云元数据目标。

SSRF 当前是 DNS/IP 出站前预检查，不宣称完整防 DNS rebinding；如升级为公网多租户平台，应增加连接级地址固定、域名 allowlist/egress proxy 和网络层隔离。

市场采用 Catalog 与 Installed Server 分离设计：外部 Registry/Aggregator 只提供可发现元数据，平台自己的 curated/trust 层负责筛选；安装只创建用户级 McpServer，配置凭证、`tools/list`、逐 Tool 风险审核和启用仍是独立步骤。第一版只考虑 remote Streamable HTTP，不执行 Registry 提供的 npm/PyPI/Docker/stdio 包。

### Schema-first 工具适配分层

工具执行采用三档策略，避免每接一个 Tool 都增加 Provider-specific Python：

1. L0 通用 MCP：inputSchema 校验，outputSchema/structuredContent 校验，通用 ExternalSource。
2. L1 声明式 Mapper：后续用字段路径/模板选择 title、url、content、items。
3. L2 Domain Adapter：只承担地点转坐标、多调用 Workflow、业务 fallback 和专用 ViewModel。

当前已补齐 MCP outputSchema 同步与持久化，执行时用 JSON Schema 2020-12 验证 structuredContent，并优先使用机器可读 structuredContent 而非兼容文本 content。input/output Schema 或 annotations 变化都会撤销动态 Tool 的旧风险审核。

该设计与 MCP Client Best Practices、Dify 的 output schema/variables、Google ADK OpenAPI Toolset 和 AWS AgentCore Gateway 的方向一致：协议/Schema/网关覆盖通用转换，复杂业务语义仍由 Server、Workflow 或少量 Domain Adapter 提供。

### Day 6 后端横切安全收尾

- 上传改为 1 MiB 分块读取，单文件超限立即终止；单次最多 10 个文件、单批最多 50 MiB。
- production 启动时拒绝示例/短 `AUTH_SECRET_KEY`，要求至少 32 字符独立 JWT Secret。
- 当前仍以 Repository 自行 commit 为主，跨仓储 Unit of Work 不在本轮重构。
- 文件 magic bytes、病毒扫描、解析沙箱、JWT denylist/refresh、统一业务错误码和跨请求幂等保留为真实后续边界。

## 2026-07-26：KnowledgeJob 同步执行可靠性增强（方案 A）

当前文档解析和索引仍在 HTTP 请求内同步执行，本轮不引入 `BackgroundTasks` 冒充可靠 Worker。`KnowledgeJob` 的定位是可查询的任务状态记录，不包含 Redis Stream、ACK、lease、heartbeat、自动重试、DLQ 或跨进程恢复。

同步执行链新增以下约束：

- 创建 `KnowledgeDocument + pending parse Job` 使用同一事务；Job 写入失败时不留下孤立 Document。
- 解析/索引开始前对目标 Document 使用 PostgreSQL `SELECT ... FOR UPDATE`，只串行化短暂的 Job 领取阶段；Job 标成 `running` 并提交后立即释放锁，MinerU/Embedding 外部调用不在长事务中执行。
- 相同 Document 与索引请求签名的 `running/succeeded` Job 直接复用；索引签名包含文档版本、内容哈希和 Embedding provider/model/dimensions，配置变化仍会创建新 Job。
- `retry_count` 表示真实执行次数：pending 为 0，第一次执行为 1；只有失败后用户再次显式触发才递增，当前没有后台自动重试。
- Job 新增机器可读 `error_code`；数据库和 API 只保存脱敏文案，不持久化第三方 URL、响应正文或原始异常消息。
- 每次 Job 状态迁移和对应 Document 状态由 Service 作为一个 Unit of Work 提交，避免 `Job=running`、`Document=pending` 等普通异常下的半状态。

仍未解决：进程在 `running` 阶段崩溃后没有 lease 接管；索引结果已提交但 Job 最终状态未提交时需要人工核对；跨进程并发仍应由未来 Worker 的 lease/version CAS、幂等 Key 和 generation fencing 共同保护。方案 B 再引入独立 Broker/Worker、ACK、有限重试和 DLQ。

## 2026-07-26：KnowledgeJob 方案 B 落地

上一节保留的是方案 A 的历史状态。当前生产 HTTP 链已经改为真正的后台任务模式：

```text
HTTP
-> PostgreSQL 同一事务写 Document/KnowledgeJob/OutboxEvent
-> 立即返回 pending Job

Outbox Publisher
-> SELECT FOR UPDATE SKIP LOCKED 领取事件
-> Redis Stream XADD
-> PostgreSQL 标记 published

Knowledge Worker
-> XREADGROUP / XAUTOCLAIM
-> PostgreSQL Lease 领取 Job
-> Heartbeat 续租
-> MinerU Parse 或 inactive generation Index
-> owner + lease_version + lease_expires_at CAS 写回
-> 数据库成功状态提交后 XACK
```

### 为什么需要 Outbox

HTTP 如果先提交 Job、再单独写 Redis，进程可能在两步之间崩溃，留下永远没有消息的 pending Job。现在 Job 与 OutboxEvent 在一个 PostgreSQL 事务中创建：要么两者都存在，要么都回滚。Publisher 再把尚未发布的 OutboxEvent 投递到 Redis。

Redis `XADD` 成功、Publisher 标记 `published` 前仍可能崩溃，因此同一个 OutboxEvent 允许重发。消息携带稳定 `event_id`，Worker 以数据库 Job 状态和 Lease 做幂等判断。这是至少一次投递，不是 Exactly Once。

### Worker 状态与失败策略

`KnowledgeJob` 记录 `available_at/max_attempts/retry_count/lease_owner/lease_expires_at/lease_version/heartbeat_at/dead_lettered_at`。Worker 只在 Job 可执行且旧 Lease 已过期时领取；每次接管递增 `lease_version`。旧 Worker 即使在网络恢复后完成外部调用，也必须通过 owner、version 和未过期时间三项检查才能写回。

瞬时故障进入有限指数退避，并在同一事务中创建下一次 OutboxEvent；无权限、资源缺失、参数错误等永久故障，或达到最大尝试次数后进入 `dead_letter`。当前 dead letter 是数据库终态，支持查询和人工重试设计，但还没有单独的管理页面和自动重放按钮。

### 索引发布不再暴露半成品

索引 Worker 不修改在线 generation，而是先构建完整的 inactive snapshot：

```text
复制 active generation 中未变化文档的 Chunk/Embedding
-> 用目标文档的新 Chunk 替换旧 Chunk
-> 按内容哈希复用签名一致的 Embedding
-> 补齐缺失向量
-> 写 generation-specific PostgreSQL Chunk
-> 写 generation-specific BM25
-> 计算 manifest hash
-> generation=ready
```

最终只在一个短事务里锁住 Job、KnowledgeBase、Generation 和 Document，检查：

```text
当前 Worker 仍持有有效 Lease
AND lease_version 未变化
AND KnowledgeBase.active_generation == generation.base_generation_id
```

检查通过才切换 `active_index_generation`。因此 Embedding、Chunk 或 BM25 任一步失败，都只留下未激活 generation，在线检索仍读取旧快照；并发 Worker 基于旧 generation 构建完成后也不能覆盖较新的 active pointer。

### MinerU 的真实位置

上传接口只保存原文件并创建 Document。用户触发解析后，Parse Job 才由 Worker 调用 MinerU；解析结果是 Markdown 和资源元信息。索引 Job 随后读取 Markdown，切 Chunk、生成 Embedding、写 pgvector 和 BM25。MinerU 不负责向量化，也不会在文件上传请求中同步执行。

### 已验证内容

- 8 项定向测试覆盖 Job/Outbox 原子创建、Lease 抢占、过期接管、旧 Worker 写回拒绝、有限重试、永久错误 DLQ、稳定 event id 和成功提交后 ACK。
- 完整后端 195 项测试通过，跳过 3 项；前端 lint 和 production build 通过。
- 真实 HTTP 入队约 31.9 ms 后返回，独立 Worker 完成纯文本解析，Job=`succeeded`、Document=`parsed`、Outbox=`published`、Redis Pending=`0`。

### 仍需诚实保留的边界

- Redis Stream 与 PostgreSQL 仍不是一个事务；保证来自至少一次投递、Job 幂等状态机和对账，而不是跨库原子提交。
- Redis 自身仍需 AOF/主从等持久化配置。若 Stream 数据整体丢失而 Outbox 已标记 published，需要定期扫描非终态 Job 并重新生成事件。
- failed/superseded generation 和旧 BM25 目录需要保留期与垃圾回收任务。
- 当前启动时使用运行时 DDL 兼容开发环境；正式部署应迁移到 Alembic 等版本化 schema migration。
- Worker 指标、DLQ 管理页、人工受控重放和故障告警尚未完成。

准确表述是：

```text
至少一次投递 + 消费幂等 + 有限重试/DLQ
+ 对账补偿 + Lease/Heartbeat + CAS/Fencing
= 可恢复的最终一致性
```

## 2026-07-28：确定性 RAG Query Rewrite 与受控 Result Binding

### 检索词与用户原问题分离

`KnowledgeQueryRewriteService` 在检索前返回 `original_query` 与 `rewritten_query`。只有不超过 240 字且包含明确中英文指代的 Query 才进入扩展；上下文限定为最近 12 条消息中的最后一条 user 消息，最多取 480 字。`KnowledgeContextService` 将 rewritten query 传给 Retrieval Pipeline，但 Retrieval Log 主 query 和最终模型问题仍保存 original query。

这种设计把“改善召回输入”和“改变用户问题”分开，也避免使用 Assistant 幻觉改写检索意图。当前是确定性规则，误判/漏判应通过 Gold Set 评测后再决定是否引入 LLM。

### Binding 执行顺序

```text
LLM Planner 输出 ToolPlan
-> 校验 Binding 声明、来源依赖、目标字段和冲突
-> 暂缓由 Binding 提供的 required 字段
-> Workflow 等待 depends_on 全部成功
-> 从上游 ExternalSource.metadata.raw 解析受限 JSON Pointer
-> 限制绑定值为标量或短标量数组
-> 合并 default/model/bound/fixed arguments
-> 完整 Draft 2020-12 Input Schema 重验
-> Executor 执行下游 Tool
```

Planner 不能让 Binding 读取 `display_text`，不能绑定未声明字段，也不能让模型/fixed arguments 与 Binding 同时控制同一目标。Workflow 只在调用确实存在 Binding 时查询 Catalog，普通调用仍由 Executor 负责目录和策略判断，避免改变旧职责边界。

Binding 是一次 HTTP 请求内的受控数据传递，不会持久化 Agent 当前节点。要实现审批恢复、跨请求幂等和崩溃续跑，仍需 AgentRun/AgentStep/Checkpoint 表、状态版本、lease/CAS 和外部副作用幂等契约。
