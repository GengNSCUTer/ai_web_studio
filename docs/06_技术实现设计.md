## 1. 环境约束与结论

先把你当前环境约束讲清楚，因为这会直接影响架构选型。

### 1.1 已确认的环境事实

当前服务器环境里，已经确认到这些情况：

- 你是普通用户，不是管理员
- `docker` 命令存在，但当前用户无权访问 Docker daemon
- `sqlite3` 可用
- `node` 可用，版本是 `v24.14.0`
- `npm` 可用，版本是 `11.9.0`
- `python` 可用
- 当前已有 `conda` 环境 `agent_study`
- 已创建独立应用环境：`/disk2/gengnan/conda_envs/ai_web_studio`
- 已验证可用的独立 PostgreSQL 运行环境：`/disk2/gengnan/conda_envs/pg_runtime`

这意味着：

- **第一版不要把 Docker 当成前提**
- **第一版不要依赖系统级数据库安装**
- **第一版不要依赖管理员帮你配 Nginx / systemd / PostgreSQL 服务**

### 1.2 设计原则

基于这个环境，第一版设计遵循 5 条原则：

1. 所有服务都能在用户目录下启动
2. 不要求 root 权限
3. 不要求 Docker
4. 不要求系统级守护进程
5. 优先选单机、用户态、可迁移的组件

### 1.3 第一版技术结论

因此，第一版建议如下：

#### 前端

- `Next.js`
- `TypeScript`
- `Tailwind CSS`
- `shadcn/ui`
- 聊天线程侧继续补齐主流网页端交互：
  - 最后一条回答重生成
  - 最后一条用户消息内联编辑后重答
  - 消息附件预览
  - 输入区待发送附件预览

#### 后端

- `FastAPI`
- `SQLAlchemy`
- `Pydantic`
- `Uvicorn`
- 聊天接口在主 `/api/chat/text-stream` 之外，额外补两条最后一轮消息级重放链路：
  - `POST /api/chat/regenerate-last-stream`
  - `POST /api/chat/edit-last-user-stream`
- 其中“编辑上一条用户消息并重答”不仅会更新消息文本，也会同步替换该条用户消息的附件绑定
- 历史消息加载时，对 `streaming` 助手消息采用“超时后才失败”的 stale 判定，避免用户切换会话时误伤仍在生成中的回答

#### 数据存储

- **架构目标直接定为 PostgreSQL**

但运行方式采用：

- **用户态 PostgreSQL**

也就是：

- PostgreSQL 不装到系统服务里
- 而是装到你的个人目录或个人环境里运行

这样做的原因是：

- 避免第一版用 SQLite，后续还要迁移
- 保持数据库架构从第一天就贴近正式版
- 同时又不依赖管理员权限或 Docker daemon

#### 模型服务

- 本地 `Ollama`
- 默认模型：`qwen3.5:27b-q8_0`

#### 文件存储

- 本地磁盘目录

## 2. 为什么第一版不建议用 Docker

这个问题要单独说清楚。

### 2.1 当前用户没有 Docker 权限

实际验证结果已经说明：

- `docker` 命令虽然存在
- 但访问 `/var/run/docker.sock` 被拒绝

也就是说你现在无法直接运行容器。

### 2.2 即使管理员以后给权限，也不建议现在以 Docker 为前提

因为当前第一版目标是：

- 快速落地 MVP
- 可在普通用户环境内独立完成

如果你现在把第一版绑死在 Docker 上，会产生额外复杂度：

- 需要镜像构建
- 需要端口映射
- 需要容器持久化卷
- 需要处理共享服务器上的 Docker 权限和资源竞争

### 2.3 第一版建议策略

所以第一版明确建议：

- **不使用 Docker**

后续如果项目做成熟，需要：

- 部署到独立机器
- 或自己有容器权限

再补 Docker 化。

### 2.4 第二阶段可以再做容器化

也就是说：

- 第一版：本地用户态运行
- 第二版：补 Dockerfile / compose

这条路径更稳。

## 3. 为什么这次改成直接用 PostgreSQL

你提的这个顾虑是对的：

> 如果后续本来就想走正式架构，那一开始为了省事用 SQLite，后面再迁库，反而会浪费时间。

所以这一版设计改成：

- **从第一天开始就按 PostgreSQL 设计**

### 3.1 为什么 PostgreSQL 更适合作为正式底座

原因包括：

- 更接近标准 Web 项目
- 事务能力更好
- 并发和扩展能力更强
- 后续接登录、多用户、统计、RAG、pgvector 更自然
- 简历上也更像完整工程项目

### 3.2 为什么普通用户环境下仍然可以考虑 PostgreSQL

虽然你不是管理员，但这不等于不能用 PostgreSQL。

可行思路通常有两种：

#### 方案 A：安装到个人目录 / conda 环境

也就是：

- PostgreSQL 二进制放在你的 `HOME` 或个人工作目录下
- 数据目录也放在你的个人目录下
- 进程由你自己启动，不注册成系统服务

#### 方案 B：以后有条件再 Docker 化

也就是：

- 当前阶段先跑用户态 PostgreSQL
- 将来迁到自己机器或有权限环境时，再容器化

### 3.3 这次为什么不再把 SQLite 作为主方案

因为当前项目的目标已经不是：

- 一个临时脚本 demo

而是：

- 一个后续要继续扩展的前后端分离 AI Web 应用

那么底层数据库从一开始就按 PostgreSQL 定下来，会更合理。

## 5. 共享服务器上的运行模式设计

这是这份文档里最重要的现实问题之一。

### 5.1 不建议默认对外暴露服务

在共享服务器上，第一版建议所有服务默认绑定：

- `127.0.0.1`

不要默认绑定：

- `0.0.0.0`

原因：

- 更安全
- 避免被同机其他用户或外网直接访问
- 不需要考虑公网暴露和额外权限

### 5.2 访问方式建议

推荐使用：

- `SSH 端口转发`
- 或 VS Code Remote / 端口转发功能

也就是：

- 服务只在服务器本地监听
- 你本地浏览器通过隧道访问

### 5.3 为什么这样最适合你

因为你现在：

- 不是管理员
- 不一定能配 Nginx
- 不一定能开公网端口
- 不一定知道机器上哪些端口已经被占

而 `127.0.0.1 + 高位端口 + SSH 转发` 是最稳妥的用户态方案。

### 5.4 端口选择策略

第一版建议统一使用：

- **高位非特权端口**

不要用：

- `80`
- `443`
- `5432`

这类常见系统端口。

推荐风格：

- 前端：`31xxx`
- 后端：`32xxx`

例如：

- 前端：`31007`
- 后端：`32007`

也可以按你的 uid 做一个偏移，但第一版不必太复杂，只要：

- 选高位端口
- 放进配置文件
- 冲突时可改

即可。

### 5.5 端口冲突怎么处理

在共享机器上，端口冲突很常见。

所以设计上要求：

- 前端端口可配置
- 后端端口可配置
- 配置集中放 `.env` 或配置文件

第一版不要把端口写死在代码里。

## 9. API 设计

### 9.1 总体原则

第一版 API 设计遵循：

- REST + 文本流
- JSON 请求响应
- 流式聊天单独一个接口
- 前端统一通过 Next.js 自身的 `/api/*` 代理后端，避免浏览器直接跨域请求 FastAPI

### 9.2 推荐接口

#### 会话接口

- `GET /api/conversations`
- `POST /api/conversations`
- `GET /api/conversations/{id}`
- `PATCH /api/conversations/{id}`
- `DELETE /api/conversations/{id}`

#### 消息接口

- `GET /api/conversations/{id}/messages`
- `POST /api/conversations/{id}/messages`
- `POST /api/chat/text-stream`
- `POST /api/chat/regenerate-last-stream`
- `POST /api/chat/edit-last-user-stream`

#### 文件接口

- `POST /api/files/upload`
- `DELETE /api/files/{id}`

#### 设置接口

- `GET /api/settings`
- `PATCH /api/settings`

当前这组接口在前端的映射关系是：

- `/api/chat`
  新发一条用户消息并流式获取回答
- `/api/chat/regenerate`
  重新生成当前会话最后一条 assistant 回答
- `/api/chat/edit-last-user`
  编辑当前会话最后一条 user 消息，并复用同一条 assistant 消息重新流式回答

当前消息级操作边界：

- 只支持“最后一轮”操作，不支持任意历史轮次直接编辑重放
- 这样做的原因是：可以保证实现简单、上下文一致性清晰，也避免前端出现过深的分叉历史管理

#### 模型接口

- `GET /api/models`

这个接口用于：

- 读取 Ollama 当前可用模型列表

对产品体验很有帮助。

### 9.3 为什么流式接口单独设计

因为普通 CRUD 请求和流式聊天不是一回事。

建议：

- 非流式接口走普通 JSON
- 聊天生成走文本流接口，前端通过 `fetch + ReadableStream` 消费

这样前端实现简单很多。

### 9.4 前后端联通策略

在共享服务器 + 本地端口转发场景下，前端和后端之间建议明确采用：

- **Next.js BFF / 代理层模式**

也就是：

1. 浏览器只访问 Next.js 前端服务
2. Next.js 内部再去请求 FastAPI
3. 前端页面不直接暴露 FastAPI 地址

这样做的好处：

- 浏览器侧不需要单独处理 CORS
- 本地访问时只需要转发一个前端端口也可以工作
- 后面如果后端地址变化，前端页面层不需要大改

## 10. 为什么第一版建议用文本流 / SSE，而不是 WebSocket

这里给你一个明确建议：

- **第一版优先用文本流 / SSE 这类单向流式方案**

当前实际实现说明：

- 主聊天链路已经使用纯文本流
- Next.js API route 负责把后端流式响应转发给浏览器
- 前端通过 `fetch + ReadableStream` 逐块读取并更新消息
- 重新生成与编辑后重答也复用这套流式主链路

### 原因

第一版的核心流式场景本质上是：

- 前端发起一次请求
- 后端持续往前端推文本增量

这是一个非常典型的单向流式响应场景。

文本流 / SSE 的优势：

- 实现简单
- 和 FastAPI 集成容易
- 前端处理比 WebSocket 简单
- 对“边生成边展示回答”足够用

### WebSocket 什么时候更值得用

只有当你需要：

- 更复杂的双向实时通信
- 多事件通道
- 多客户端协同

时，WebSocket 才更必要。

第一版没有这个必要。

## 11. Ollama 接入设计

### 11.1 第一版模型适配层

后端不要在 route 里直接写 Ollama 请求。

应该单独做：

- `ollama_service.py`

它负责：

- 调模型列表接口
- 调聊天接口
- 处理流式响应
- 统一错误处理

### 11.2 为什么要单独封装

因为以后你大概率会扩展：

- OpenAI-compatible API
- 别的本地模型服务
- 多 provider 切换

如果一开始不封装，后面会很难看。

### 11.3 输入组织原则

第一版聊天输入分 3 类：

- 文本消息历史
- 图片附件
- 文档解析文本

后端在调用 Ollama 前，需要先把这些统一整理成模型输入格式。

也就是说：

- 聊天 route 不直接“拼 prompt”
- `chat_service` 负责做上下文组装
- `ollama_service` 只负责真正调用模型

## 12. 图片与文档处理设计

### 12.1 图片处理

第一版建议：

- 上传后保存在本地目录
- 保存数据库附件记录
- 聊天时读取图片文件并交给模型

不做：

- 图片长期知识索引
- 图像编辑
- OCR 流水线拆分

### 12.2 文档处理

第一版文档支持：

- `txt`
- `md`
- `pdf`
- `docx`

建议单独做：

- `parser_service.py`

按文件类型分别解析。

### 12.3 文档上下文策略

第一阶段不做 RAG，所以建议策略明确收敛为“会话附件上下文”：

- 文档解析出纯文本
- 后端按字符或 token 上限截取
- 作为当前轮或当前会话的补充上下文拼接给模型

这意味着：

- 文档不是长期检索索引
- 文档也不是永久工作记忆
- 文档是“当前任务上下文”的一部分

### 12.4 为什么要限制文档上下文长度

即便模型支持 128k / 256k 输入，也不能无限拼：

- 解析文本太长会拖慢响应
- 多轮会话叠加后很快膨胀
- 图片、文件、system prompt 和历史消息会互相抢预算
- 共享服务器资源有限

第一阶段建议做一个简单但可控的策略：

- 文档文本只取前 N 字符或前 N token
- 超过预算时优先裁剪更老的附件或低优先级内容
- 后续再做更细的上下文治理

## 13. 上下文治理设计

这一章是本项目后续最重要的技术点之一。

### 13.1 上下文治理目标

第一阶段上下文治理要解决 4 个问题：

1. 同一会话可连续追问
2. 上下文不会无限膨胀
3. 图片、文件、历史消息、系统提示有明确优先级
4. 为后续摘要、长期记忆、缓存命中优化留接口

### 13.2 上下文来源分层

第一阶段模型输入建议拆成 5 层：

1. `system_prompt`
2. 会话级近期消息
3. 当前用户输入
4. 当前轮图片附件
5. 当前轮文件附件解析文本

这 5 层必须保持明确顺序和稳定拼接模板。

### 13.3 短期上下文策略

第一阶段建议使用简单但可控的策略：

- 保留最近 `N` 轮消息原文
- 文档上下文限制最大长度
- 图片只带当前轮附件
- system prompt 永远保留

建议起步值：

- 最近 `10` 轮消息
- 每个文档截取前 `8000` 到 `12000` 字符
- 总上下文超预算时优先裁剪较旧消息或低优先级附件

### 13.4 上下文预算控制

后端应增加一个轻量“上下文预算器”，用于控制：

- 历史消息预算
- 附件预算
- 文档预算
- system prompt 预算

如果后续有 token 统计能力，优先按 token；否则第一版先按字符数近似。

当前实现已经从“固定阈值”升级到“动态预算框架”，核心规则如下：

- 用户设置里新增 `model_context_window`
- 用户设置里新增 `context_mode`
- 后端根据这两个字段动态推导：
  - 最大历史消息数
  - 最大总字符预算
  - 最大附件字符预算
  - 图片等效字符预算

### 13.5 前端上下文诊断面板

为了让上下文治理不再是“后端黑盒”，当前前端已经接入一层轻量诊断可视化：

- 后端通过响应头返回 `x-context-stats`
- 后端通过响应头返回 `x-context-notices`
- 前端将其解析为独立诊断卡片和提示列表

当前前端可直接展示的治理指标包括：

- 上下文模式
- 模型上下文窗口
- 本轮估算字符数
- 被裁剪的历史消息数
- 摘要字符数
- 是否触发摘要刷新
- 摘要刷新源消息数
- 摘要刷新源字符数
- 总字符预算上限
- 附件字符预算上限
- Prompt 模板版本
- Provider 模板
- 模型族
- Prompt 上下文层级
- 系统前缀层数
- Prompt 历史消息数
- 注入文件消息数
- 注入图片消息数

当前交互形式不是长期固定占位，而是：

- 输入区旁的轻量“上下文”按钮
- 点击后弹出诊断浮层查看详情

这样做的原因是：

- 日常对话时不干扰主聊天空间
- 需要调试和观察时仍然能快速展开

这层设计的作用是：

- 方便开发阶段验证预算是否合理
- 方便后续做参数调优和问题排查
- 为后续“更高质量摘要压缩”和“缓存命中优化”提供可观察性基础
  - 也能直接观测附件片段、摘要压缩和稳定前缀复用情况

当前这层诊断信息的持久化策略刻意保持克制：

- 当前不写入数据库
- 当前只在前端按“会话 id -> 最近一次诊断结果”做内存态缓存
- 这样切换会话再切回时，仍可继续查看最近一次上下文诊断
- 但刷新整个页面后，这类运行时诊断信息不会回放恢复

这样设计的原因是：

- 这批数据本质上是“单轮请求的运行时观测”，主要用于调试和治理观察
- 现阶段把它们持久化到数据库，收益主要只是“刷新后还能看”，性价比不高
- 如果现在就落库，会额外引入表结构设计、清理策略、历史兼容和回放接口复杂度
- 当前项目主线已经从 `P0.5` 转向 `P1`，不适合继续为了诊断信息持久化打断节奏

后续如果确实要做持久化，不建议只在 `conversations` 上挂一份“最后一次上下文信息”，而建议升级为：

- 按 assistant message 粒度保存诊断记录
- 一条回答对应一条上下文诊断
- 形成真正可回放、可追踪、可比对的“消息级上下文诊断链路”

也就是说，后续更合理的方向不是“为了显示按钮而落库”，而是“为了消息级调试追踪而落库”。

当前 `context_mode` 分为 3 档：

- `conservative`
  更保守，优先保证响应稳定和资源可控
- `balanced`
  默认模式，兼顾上下文长度和推理稳定性
- `long-context`
  更激进，优先保留更多历史和附件内容

当前预算器已经从“纯字符级近似预算”升级为“字符硬裁剪 + tokenizer 估算观测”的混合形态。

当前做法是：

- 仍保留字符级裁剪兜底，保证各 provider 下行为稳定
- 同时引入 `TokenizerEstimator`，基于 `tiktoken` 对 Prompt、摘要、附件和稳定前缀做 token 估算
- 当前诊断面板已经可以直接显示总 Token、附件 Token、摘要 Token、摘要压缩比、稳定前缀 Token 等指标

后续如果要继续优化，可以再演进为：

- provider 级更精细 token 预算器
- 更贴近具体模型的 tokenizer 映射
- 命中缓存时的差异化预算策略

### 13.5.1 缓存友好型 Prompt 结构

当前聊天链路已经新增 `ContextPromptBuilder`，把原本散落在 `chat.py` 里的 system prompt、长期记忆、会话摘要、历史消息、图片和文件附件拼装逻辑收敛到独立服务。

当前 Prompt 固定分层顺序为：

1. 稳定系统前缀：`AI Web Studio 上下文模板 v1`
2. 用户系统提示：用户在设置里配置的 `system_prompt`
3. 长期记忆：启用的 `user_memories`
4. 会话滚动摘要：`conversations.context_summary`
5. 最近原始消息窗口
6. 当前轮图片附件
7. 当前轮文档片段上下文

实现要点：

- 每一层使用稳定中文标题，例如“长期记忆”“会话滚动摘要”“当前轮附件片段”
- `ContextGovernanceService` 先保留前置 system 层，再裁剪历史消息，避免长会话时稳定前缀被末尾切片挤掉
- Prompt Builder 返回 provider 可直接消费的 `messages`
- Prompt Builder 同时返回诊断字段，用于前端上下文面板展示
- 当前已有 provider 模板标识：
  - `ollama_chat_v1`
  - `openai_chat_completions_v1`

### 13.5.2 附件索引化与按需展开

当前已经新增 `AttachmentContextService`，用于把当前轮文档附件从“全文直接注入”升级为“运行时轻量索引 + 相关片段注入”。

当前流程：

1. 上传阶段仍负责解析 `txt / md / pdf / docx` 得到 `parsed_text`
2. 发送消息时，后端读取当前用户消息绑定的文件附件
3. `AttachmentContextService` 将每个文件按约 `1200` 字符切块，并保留约 `160` 字符重叠
4. 根据当前用户问题抽取中英文关键词
5. 对每个片段做规则级相关性打分
6. 按 `budget.max_attachment_chars` 选择得分最高的片段
7. `ContextPromptBuilder` 只把选中的附件片段注入最后一条用户消息

当前上下文诊断新增：

- `attachment_files_seen`
- `attachment_chunks_total`
- `attachment_chunks_selected`
- `attachment_context_chars`
- `attachment_truncated_chunks`
- `attachment_truncated_chars`
- `attachment_context_tokens`
- `prompt_attachment_context_injected`

缓存友好型 Prompt 当前边界：

- 这是运行时轻量索引，不是持久化附件索引表
- 这是关键词级相关性打分，不是 embedding 向量检索
- 当前只处理当前轮上传附件，不会跨历史附件做召回
- 当前前端已经支持附件片段可视化预览和点击展开，但仍未做到持久化附件索引表

当前边界：

- 这一步是“缓存友好型结构治理”，不是 provider 真实缓存 API 调用
- 暂未做不同模型的深度差异化模板
- 已做 prompt prefix hash 与“稳定前缀是否复用上一轮”的启发式观测，但还不是 provider 真实缓存命中率
- 暂未做成本统计

### 13.5 上下文压缩策略

参考 Anthropic / Codex / Claude Code 的思路，后续建议引入两类压缩：

#### 局部压缩

- 对最老的消息做摘要
- 对工具结果做折叠
- 对超长附件只保留摘要和关键片段

#### 全局压缩

- 会话级摘要
- 长会话关键事实抽取
- 长期记忆写入

当前实现状态：

- 已支持“滚动摘要记忆层”
- 摘要会写入 `conversations.context_summary`
- 已新增 `context_summary_boundary_message_id`，用于标记当前摘要已经覆盖到哪一条历史消息
- 后续请求会把该摘要作为较早历史的压缩记忆注入，只回放边界之后的最近原始消息
- 已接入模型驱动摘要压缩：摘要刷新时优先使用当前会话 provider/model 做非流式摘要生成
- 已保留规则摘要兜底：如果模型摘要失败、超时或返回空内容，会自动回退到原来的结构化规则摘要，避免影响正常聊天

当前这一版摘要策略的特点是：

- 质量优先：优先由模型抽取用户目标、约束、重要事实、已完成决策和待办
- 稳定兜底：模型摘要不可用时仍能使用规则摘要继续运行
- 成本可控：不每轮重算，只在未压缩历史超过阈值时刷新

当前摘要刷新策略：

- 不再每轮都重算摘要
- 当“未被摘要覆盖的较早历史”超过一定消息数或字符量时，才触发滚动刷新
- 当前阈值是：
  - 至少 `6` 条消息
  - 或至少 `4000` 字符

当前摘要分层方式：

- `system_prompt`
- 会话级滚动摘要
- 最近原始消息窗口
- 当前轮用户输入 / 图片 / 文件

这意味着当前项目已经从“单层历史裁剪”升级成了“短期工作记忆 + 压缩记忆”的双层结构。

但缺点也很明确：

- 摘要会额外消耗一次 provider 调用
- 当前仍不是“完全按真实 provider tokenizer 严格裁剪”的终态，只是第一版混合预算框架
- 摘要质量依赖当前模型能力和 provider 稳定性

所以下一步应重点升级：

- 区分“短期对话摘要”和“长期事实记忆”
- 增加摘要刷新和失效策略
- 做摘要质量回归和更细粒度预算校准

### 13.6 长期记忆设计

长期记忆不是把全部历史挂到每次请求里，而是只保留高价值事实。

建议分成 4 类：

- Profile Memory
  用户稳定偏好、身份、语言习惯

- Task Memory
  当前长期任务目标、工作区背景

- Episode Memory
  某次会话里沉淀出的关键事实

- Artifact Memory
  文件、图片、摘要、结构化提取结果

当前实现状态：

- 已新增 `user_memories` 表，按用户隔离存储长期记忆
- 已支持 4 类手动长期记忆：
  - `profile`：用户偏好、交流习惯、技术偏好
  - `project`：长期项目背景、项目目标、技术栈
  - `fact`：用户明确保存的重要事实
  - `instruction`：希望系统长期遵守的规则
- 已新增 `memory_enabled` 和 `memory_max_chars` 用户设置
- 已新增记忆 CRUD 接口：
  - `GET /api/memories`
  - `POST /api/memories`
  - `PATCH /api/memories/{id}`
  - `DELETE /api/memories/{id}`
- 聊天链路会在 `system_prompt` 后、会话滚动摘要前注入启用的长期记忆
- 上下文诊断会返回：
  - `memory_enabled`
  - `memory_injected`
  - `memory_count`
  - `memory_chars`

当前长期记忆 MVP 的边界：

- 第一版只做手动保存、启停和删除，避免模型自动误记
- 不做跨用户共享记忆
- 不做自动跨会话知识融合
- 不做向量化长期记忆库

下一步升级方向：

- 已完成模型生成“建议记忆”的第一版：用户在长期记忆面板中从当前会话提取候选记忆，确认后再保存
- 增加记忆冲突检测和去重
- 给长期记忆增加来源会话和来源消息追踪
- 将 Artifact Memory 与附件索引化能力结合

模型建议记忆实现状态：

- 新增 `POST /api/memories/suggest`
- 输入当前会话 id 和候选数量上限
- 后端读取当前会话最近消息、已有长期记忆、当前用户 provider/model 配置
- 使用当前 provider/model 生成 JSON 候选记忆
- 后端解析并规范化候选，只返回给前端，不直接写入数据库
- 前端长期记忆面板展示候选卡片，用户可以保存或忽略
- 已新增规则级风险检测：
  - 同类型 + 内容高度相似：标记为 `duplicate`
  - 同类型 + 标题相近但内容差异较大：标记为 `conflict`
  - 无明显风险：标记为 `safe`
- 已新增来源追踪字段：
  - `source_conversation_id`
  - `source_message_ids`
  - `confidence`
- 已实现来源可视化：
  - 后端返回长期记忆时会根据 `source_conversation_id` 补充 `source_conversation_title`
  - 前端长期记忆卡片展示来源会话
  - 用户可从记忆卡片点击“打开来源”，跳转到对应历史会话

当前暂不做：

- 自动悄悄写入长期记忆
- 复杂语义去重和冲突检测
- 向量相似度检测
- 来源消息级高亮定位

### 13.7 缓存命中策略

为了后续兼容 OpenAI / Claude / Gemini / 百炼 / DeepSeek / vLLM 一类能力，第一阶段就要尽量保持：

- system prompt 稳定
- 附件注入模板稳定
- 历史消息顺序稳定
- 不要频繁改前缀结构

缓存命中本质上依赖 prompt 结构纪律。

当前第一版已经落地的缓存观测包括：

- 稳定前缀结构固定化：system prompt、长期记忆、滚动摘要的顺序固定
- 稳定前缀 hash：每轮对稳定前缀做 hash，便于判断模板或记忆层是否发生变化
- 稳定前缀 token 数估算：便于评估“缓存友好部分”大致占了多少上下文
- 与上一轮是否复用同一稳定前缀的启发式判断

当前仍未完成的部分：

- provider 真实缓存命中率
- prefix cache 成本收益统计
- 针对命中/未命中的差异化预算与路由策略

### 13.8 为什么不建议第一版就做“全历史拼接”

因为共享服务器资源有限，而且模型越大，长上下文越容易导致：

- 响应慢
- 显存和算力压力大
- 模型注意力分散

所以第一阶段必须做可控裁剪，而不是全量历史直塞。

### 22.2 近期技术优化建议

近期更适合做这些技术补齐：

1. 主题系统
   已完成第一版。前端通过 `data-theme` 和 CSS token 实现 light / dark 两套变量，后端用 `user_settings.theme_mode` 持久化用户选择。深色模式已补充控件 hover 和原生 `select option` 的深色样式，避免设置页下拉项/按钮 hover 出现白底浅字。聊天输入区额外使用 `chat-composer` 例外类，避免全局 dark 表单背景把透明输入框强制渲染成突兀矩形。

2. 会话导出
   已完成第一版。后端提供 conversation export endpoint，支持 Markdown / JSON；前端在左侧会话菜单触发文件下载。导出响应头使用 ASCII fallback + RFC 5987 `filename*`，避免中文会话标题进入 `Content-Disposition` 时触发服务端 header 编码错误。

3. Prompt 模板
   已完成第一版。新增 `prompt_templates` 表，并提供 `GET / POST / PATCH / DELETE /api/prompt-templates`；前端可管理模板。当前产品语义明确拆成两层：`prompt_templates.project_id` 只表示模板可见范围 / 分类，不代表自动生效；模板卡片里的“应用目标”才会真正写入全局 `user_settings.system_prompt` 或指定 `projects.system_prompt`，避免“模板归属”和“工作区生效提示词”混淆。

4. Project / 工作区
   已完成雏形。新增 `projects` 表与 `GET / POST / PATCH / DELETE /api/projects`；会话和 Prompt 模板新增 `project_id` 字段。前端左侧栏可按工作区筛选会话，新会话默认归属当前工作区，并可使用工作区默认模型和 System Prompt。左侧工作区入口已压缩为 ChatGPT 类似的轻量选择器，减少对历史会话列表空间的挤占。

5. 会话分享
   已完成第一版。新增 `conversation_shares` 表，并提供 `GET / POST / PATCH / DELETE /api/conversations/{conversation_id}/share` 管理私有分享链接；`GET /api/shares/{token}` 提供无需登录的只读分享数据。前端新增 `/share/[token]` 分享页，支持只读查看消息和附件元数据。

6. 会话导出增强
   已完成第一版并完成一轮语义修补。`GET /api/conversations/{conversation_id}/export` 支持 `message_ids`、`include_attachments`、`include_attachment_files`、`include_context`、`as_zip` 参数；其中 `include_attachments` 只控制 Markdown / JSON / ZIP manifest 中是否包含附件元数据，`include_attachment_files` 只在 `as_zip=true` 时控制是否把真实附件文件写入 ZIP。前端会话菜单只保留一个“导出选项”入口，用户在弹窗内选择 Markdown / JSON / ZIP、导出范围、附件元数据、ZIP 附件文件和上下文摘要。ZIP 内附件优先保留原始文件名；如果同名冲突，则追加 `_2`、`_3` 等序号，避免之前用附件 ID 前缀导致导出文件名不可读。

7. Prompt 模板增强
   已完成第一版。`prompt_templates` 新增 `category` 和 `variables` 字段；前端支持模板搜索、分类展示、变量填充、快捷插入到 System Prompt，以及应用到全局或指定工作区。

8. 工作区增强
   已完成第一版。新增 `project_files` 表与 `GET / POST / DELETE /api/projects/{project_id}/files`，并新增 `GET /api/projects/{project_id}/stats` 返回项目会话数、消息数、文件数、模板数和文件总量。前端工作区设置弹窗中可维护项目文件库并查看项目统计。

9. 消息级诊断持久化
   当前上下文诊断只在前端按会话缓存，后续可新增 `message_context_diagnostics` 表，按 assistant message 保存本轮上下文统计。

10. 附件片段持久化
   当前附件切块是运行时轻量索引，后续建议新增 `attachment_chunks` 表，为跨历史附件召回和 RAG 打底。

### 22.3 中期 RAG 技术路线

如果进入知识库阶段，建议不要直接把当前“上传附件进入上下文”硬改成 RAG，而是新增一条知识库链路：

```text
Upload File
   |
   v
Parse Text
   |
   v
Chunk + Metadata
   |
   v
Embedding
   |
   v
Vector Store / pgvector
   |
   v
Retriever + Reranker
   |
   v
Context Builder
   |
   v
Chat Provider
```

建议分三步：

1. 先做 PostgreSQL 普通表持久化 chunk
2. 再引入 `pgvector` 或独立向量库
3. 最后补 contextual compression / rerank / citation

这样可以保持当前聊天主链路稳定，同时逐步把“临时附件分析”扩展成“长期知识库问答”。

### 22.4 长期性能优化方向

长期性能优化重点不是单点提速，而是减少不必要的上下文和请求成本：

- Prompt prefix 稳定化：系统提示、项目说明、长期记忆、摘要层顺序固定

- 首 token 延迟观测：拆分模型冷启动、prefill、decode、网络转发耗时

- Provider 能力声明：按模型记录最大上下文、是否支持图片、是否支持工具调用、是否支持缓存

### 23.3 P3 知识索引流程

上传附件后的新流程：

```text
POST /api/uploads
  -> 保存附件文件
  -> 写 attachment 记录
  -> 文档解析
  -> 生成 attachment_chunks
  -> 写 knowledge_documents / 更新状态
  -> 返回附件与索引状态
```

为了不影响聊天体验，第一版可以同步执行；如果后续文件变大，再改成后台任务：

```text
upload request
  -> status = pending
  -> background index task
  -> status = indexed / failed
```

解析与切分策略：

- `txt / md`：按标题、空行和段落优先切分
- `pdf`：保留页码，按页内段落切分
- `docx`：按段落和标题切分
- chunk 目标大小：`800-1200` 中文字符或可配置 token
- chunk overlap：第一版可不做，后续再加 `100-200` 字符 overlap
- `content_hash`：用于去重

### 23.4 P3 知识召回流程

第一版不做 embedding，先做关键词与规则召回：

```text

  -> 提取关键词

  -> 文件名 / 标题 / chunk 内容匹配

  -> 去重
  -> 排序
  -> 按上下文预算裁剪
  -> 注入 Prompt
```

### 24.1 当前代码基线

### 24.4 流式协议设计

当前 `StreamingResponse` 是纯 `text/plain`，只能流 answer content。要支持 thinking / search status / source / final answer，建议升级为 SSE 或 NDJSON。

推荐第一版使用 NDJSON：

```json
{"type":"search_status","status":"searching","query":"..."}
{"type":"search_result","rank":1,"title":"...","url":"...","snippet":"..."}
{"type":"reasoning_delta","text":"..."}
{"type":"answer_delta","text":"..."}
{"type":"context_diagnostics","stats":{...},"details":{...}}
{"type":"done","assistant_message_id":"..."}
{"type":"error","message":"..."}
```

原因：

- 比纯文本流更容易扩展。
- Next.js fetch 读取 ReadableStream 仍然可用。
- 后续 Trace、工具调用、引用来源都可以复用。

兼容方案：

- 保留旧 `/chat/text-stream` 一段时间。
- 新增 `/chat/events-stream`。
- 前端新功能走 events-stream。

### 24.5 深度思考 Provider Adapter

新增内部结构：

```python
@dataclass
class ChatStreamEvent:
    type: Literal["reasoning_delta", "answer_delta", "done", "error"]
    text: str | None = None
    metadata: dict[str, Any] = field(default_factory=dict)
```

Provider service 不再只 yield string，而是 yield event：

```python
async def stream_chat_events(...) -> AsyncGenerator[ChatStreamEvent, None]:
    ...
```

Ollama 适配：

```python
payload = {
    "model": model_name,
    "messages": messages,
    "stream": True,
    "think": thinking_enabled,
    "keep_alive": settings.ollama_keep_alive,
}
```

解析：

```python
thinking = data.get("message", {}).get("thinking")
content = data.get("message", {}).get("content")
```

OpenAI-compatible / SiliconFlow / Qwen 适配：

```python
extra_body = {}
if profile.thinking_param_style == "qwen_enable_thinking":
    extra_body["enable_thinking"] = thinking_enabled
    if thinking_enabled and thinking_budget:
        extra_body["thinking_budget"] = thinking_budget
```

解析时兼容：

```python
reasoning = getattr(delta, "reasoning_content", None)
content = getattr(delta, "content", None)
```

同时保留 dict fallback：

```python
if isinstance(delta, dict):
    reasoning = delta.get("reasoning_content") or delta.get("thinking")
```

注意：

- 不是所有 OpenAI-compatible provider 都接受 `enable_thinking`，必须由 profile 决定是否发送。
- 当前 SiliconFlow/Qwen 场景可以先支持 `enable_thinking`。
- 如果启用 thinking 后 provider 报 400，可记录 capability failure，并提示用户关闭。

## 25. 通用 External Context / Tool Layer 技术设计

第 24 节里的 Web Search 设计需要进一步抽象。否则后续接天气、高德地图、MCP、知识库召回时，聊天接口会被各种 provider-specific 逻辑污染。

新的设计目标是：

> 让所有外部信息源都通过统一的 Tool Registry、External Context Channel、PostProcessor、Trace 和 Context Governance 接入。

### 25.1 架构总览


- 后端校验工具是否存在、是否启用、是否只读、参数是否符合 schema。
- 不直接信任模型输出。

原则：

- Provider 返回原始结果。
- Channel 负责把 provider 结果转为 `ExternalSource`。
- PostProcessor 负责去重、排序、预算裁剪。
- Prompt Builder 不知道具体 provider，只处理 `ExternalSource`。

### 25.7 Prompt Builder 接入方式


```text
【外部信息源】
以下信息来自外部工具或检索通道。回答中使用时请标注来源编号。

[1] 类型：网页搜索
```

### 25.10 Weather Tool 落地设计

用户旧示例：

```text
/disk2/gengnan/学习hello_agent/01搭建智能体/get_weather.py
```

它调用 `wttr.in/{city}?format=j1` 并返回当前天气。正式项目中应改造成：

```python
class WttrWeatherProvider:
    async def get_current_weather(self, city: str) -> WeatherResult:
        ...
```

Channel：

```python
class WeatherToolChannel(ExternalContextChannel):
    async def retrieve(self, context):
        city = extract_city(context.query)
        result = await provider.get_current_weather(city)
        return ExternalContextResult(
            sources=[ExternalSource(source_type="weather", ...)]
        )
```

第一版城市抽取可以规则化，后续交给 LLM Tool Router。

### 25.11 Map Tool 落地设计

地图工具不要用普通网页搜索替代。建议两条路线：

1. 直接接高德 REST API。
   优点是可控、简单、性能好。

2. 接高德 MCP Server。
   优点是更符合工具生态，后续可统一接其他 MCP server。

第一版建议先做 REST 或 MCP 二选一，不要同时做。

工具范围：

```text
map_geocode
map_poi_search
map_route
```

输出转为 `ExternalSource(source_type="map")`，前端展示地图结果摘要，不一定第一版就嵌入地图。

### 25.12 MCP Client 设计

MCP 接入点：

```text
backend/app/external/providers/mcp_client.py
```

需要支持：

- 配置 MCP server。
- 获取 `tools/list`。
- 执行 `tools/call`。
- 读取 `resources/read`。
- 映射 MCP tool 到 `external_tools`。
- 调用前做 allowlist、readonly、confirmation 校验。

安全规则：

- 默认禁用所有 MCP server。
- 用户显式启用。
- 第一版只允许只读工具。
- 有副作用工具必须用户确认。
- 所有调用写入 `external_tool_runs`。

### 25.14 实施顺序

推荐顺序：

1. 抽象 `ExternalSource`、`ExternalContextResult`、`ExternalContextChannel`。
2. 把 Tavily Web Search 实现为第一个 channel。
3. 前端来源卡片改成基于 ExternalSource。
4. 新增 `external_tool_runs` 和 `external_sources`。
5. 增加 Weather Tool，验证非网页类工具。
6. 增加 Map Tool，验证结构化垂直工具。
7. 增加 RuleBasedToolRouter。
8. 增加 MCP Client。
9. 增加 LLM Tool Router。
10. 再考虑 provider-native web_search。

不要反过来先接一堆 provider。接口没稳定前 provider 越多，维护成本越高。
